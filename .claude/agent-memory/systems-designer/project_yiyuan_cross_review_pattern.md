《弈緣》(game-concept.md)的 GDD 群(`design/gdd/affinity-data-pool.md`、`save-system.md`、`cursor-highlight-state.md`)採多輪 `/design-review` 高度成熟化,但反覆出現同一類根因:**單份文件內部完備性檢查已很成熟,但跨文件的「宣稱」(A 文件說 B 文件已宣告某事實)從未被實際查證**——`design/gdd/gdd-cross-review-2026-08-06.md` 的 Verdict FAIL 即源於此模式,13 項去重 BLOCKING 全部屬此類。

**Why**: 2026-08-06 的 `/review-all-gdds` 發現此模式後,使用者已修訂五份文件堵住 13 項 BLOCKING。但於 2026-08-07 我執行對抗性覆核時,發現同一類「修了一處、引用同一結論的其他角落未同步」的模式在本輪修訂中**再次出現**——即使 save-system.md 本身新增了「完備性執行紀錄表」(逐 Core Rule 三件套掃描)試圖系統性防範此問題,該表的掃描粒度停在「規則層級」,新增在某條 Core Rule *內部*的子義務(例如 Core Rules #5 新增的 begin/end 生命週期呼叫義務)仍可能完全沒有專屬 AC、沒有矩陣列,而規則層級的三件套仍顯示「齊全」。

**How to apply**: 未來覆核此專案(或任何有「規則交互矩陣」+「完備性執行紀錄表」的高輪次 GDD)時:
1. 不要只看完備性表格是否宣稱「N/N 齊全」——要往下鑽到本輪新增的**具體句子**,逐句確認是否真的有對應 AC,而非只確認其所屬的整條 Core Rule 有 AC。
2. 對每個「A 文件呼叫 B 文件介面」的新增義務,檢查**失敗路徑**是否也被定義(本輪發現一例:save-system.md Core Rules #5 新增「遷移完全結束後呼叫 affinity-data-pool 的 end」義務,但只定義了「回寫確認完成」〔成功路徑〕觸發 end 的條件,完全未定義遷移失敗〔Core Rules #6 拒絕〕路徑下 end 何時被呼叫——literal reading 下失敗路徑永遠不會呼叫 end,导致旗標永久卡住、後續所有 affinity 寫入被靜默拒絕。此為 BLOCKING 等級的狀態機缺口,且無任何 AC 覆蓋)。
3. 用 grep 搜尋舊措辭關鍵字(例如本輪的「同步/非同步」二分法舊詞)確認所有引用同一結論的段落都已同步——save-system.md 的 Interactions with Other Systems 章節(好感度數值池列)在 Dependencies 章節已正確修訂的情況下,仍殘留一句完整重述舊結論的句子,直接與同文件 Dependencies 章節矛盾。这类"一处改、其余引用未同步"是本專案最常見的殘留缺陷形態。

相關文件:`design/gdd/gdd-cross-review-2026-08-06.md`(原始跨文件審查報告,含使用者裁決紀錄與 13 項修訂清單)。

**2026-08-07 第二次對抗性覆核(save-system.md 已進到第五輪 Approved)發現,舊缺口仍未修復 + 新增 2 項同型缺口**:

1. **舊缺口仍在(未修復)**:`save-system.md` Detailed Rules → Interactions with Other Systems 章節的「好感度數值池(持久化義務,讀取方向)」列,仍寫著「由於本系統目前採同步阻塞式寫入…該文件要求的『序列化生命週期通知介面』(begin/end)目前不需要實作」——這與同文件 Dependencies 章節(已於 2026-08-06 修正)、Core Rules #5(已要求分步遷移 begin/end)直接矛盾。第五輪的六位專家審查與「完備性執行紀錄表」皆未抓到此處,因為兩者都是規則層級掃描,不掃 Interactions 章節的自由文字複述。
2. **舊缺口仍在(未修復)**:Core Rules #5 新增的「遷移完全結束(含 Core Rules #13 兩階段回寫確認完成)後呼叫 end」義務,**只定義了成功路徑**(回寫確認完成)觸發 end 的條件,**完全未定義 Core Rules #6 遷移失敗路徑下 end 何時被呼叫**——States and Transitions「遷移失敗」列、Core Rules #6 皆未提及呼叫 affinity 的 end。Core Rules #16 矩陣的 #5 列只登記「同槽重入不變量」,未登記這條 begin/end 跨文件義務;AC-59/AC-60(#5 唯二專屬 AC)驗證的是重入拒絕,不是 begin/end 呼叫時機——即 begin/end 義務完全沒有專屬 AC、也沒有矩陣列,但「完備性執行紀錄表」表一仍把 #5 列標記為「✅ 多列」「✅ AC-14b、AC-59、AC-60」而未發現這個子義務被漏掉。literal reading 下失敗路徑永遠不呼叫 end,旗標永久卡住、後續所有 affinity 寫入被靜默拒絕。**此為本專案「完備性表格粒度不夠深」失敗模式的持續實例,經兩輪覆核仍未被表格本身抓到。**
3. **新發現(2026-08-07 第五輪自產)**:Core Rules #16「完備性要求」段落自我矛盾——開場括號宣稱「已補上 #1/#2/#3/#6/#15/#16 六列/宣告」,但同段落下方機械掃描結果句卻寫「結果是要求本身未被滿足(#1/#2/#3/#15/#16 五條規則缺列或宣告)」,漏了 #6。「完備性執行紀錄表」表一與矩陣本身都把 #6 列為第五輪新增(與開場括號一致),只有這句機械掃描結果句本身算錯——即防止此類算術缺口的機制,自己在同一輪產出了同型算術缺口。
4. **新發現(2026-08-07 第五輪自產)**:Core Rules #15 新增的「介面分類表」中,「唯讀存取介面(Core Rules #13)」列聲稱「僅在『遷移失敗』狀態下可用」——但 Edge Cases(「若讀取時偵測到存檔槽的位元組本身已損毀」條款)與 AC-54 都明文使用同一個唯讀存取介面服務**從未觸發遷移、單純一般寫入位元腐蝕(`DATA_CORRUPTED`)**的存檔槽(States and Transitions 表甚至沒有為這個情境定義獨立狀態)。表格的「否(不受重入約束)」結論可能仍然成立(該情境同樣沒有進行中的分步狀態機),但表格陳述的**適用條件**與既有 Edge Cases/AC-54 矛盾。
5. **已查證、確認一致、無缺陷**:affinity-data-pool.md 新增的「反序列化語意驗證規則宣告」段落(Section N)在「全新戰役、尚未發生任何寫入」邊界情況(`t_now=0`,Delta Log 與標記列表皆空)下無矛盾——`t_i≥1` 規則對空集合是 vacuously true,`t_now`/`c_now` 的定義與此一致,AC-24b(save-system.md)與 AC-59(affinity 側)皆已覆蓋此邊界。此項為覆核後判定「可接受」,非缺口。

**Why**: 這確認了本文件先前記錄的模式論斷本身——「完備性執行紀錄表」的掃描粒度停在 Core Rule 層級,新增在某條規則*內部*的子義務(begin/end 呼叫時機、失敗路徑）仍可能完全沒有專屬 AC/矩陣列,而規則層級的三件套仍顯示「齊全」。且這個問題具有自我遞迴性:連「完備性要求」段落自己的機械掃描結果陳述、以及新增的「介面分類表」本身,都在同一輪產出了同一類型的疏漏,防呆機制本身尚未對自己達到它要求別人達到的精確度。

**How to apply**: 下次覆核此文件時,除了既有的三條方法論(見上方),新增第四條:**對每一份「本輪新增的完備性/分類/矩陣表格」,不要相信表格自己宣稱的「齊全」結論——用表格陳述的具體條件(例如某介面「僅在 X 狀態下可用」、某規則「已補齊 N 條」)去反向搜尋文件其他地方(尤其是舊輪次遺留的 Edge Cases/AC),確認該條件本身在全文範圍內成立,而不只是在表格自己的上下文裡自洽。

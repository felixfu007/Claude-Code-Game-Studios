> **New lesson from this correction**: rounds 1–5 of `/architecture-review` reported this
> same file missing while checking `design/accessibility-requirements.md` (no `ux/`).
> When verifying a punted obligation, glob by **filename**, never by the path the prose
> happens to quote. "Not at the path I checked" is not "does not exist."

Rule: Whenever a design document defers a concern with language like "已裁定轉交 [other file]" or "不屬本 GDD 範圍,見 [other system]," treat that as an unverified claim, not a resolved fact. Check three things before accepting the punt as adequate:
1. Does the target file actually exist on disk (Glob/Read), or only a generic unfilled template?
2. Is the obligation registered somewhere trackable with an owner and closure condition — either the originating GDD's own Open Questions table, or `design/gdd/systems-index.md`'s Cross-System Obligations Registry?
3. Does the downstream system that would own the concern even list the originating system as a dependency in `systems-index.md`'s Dependency Map? If not, the obligation has nowhere to land even if someone tries to register it.

**Why**: Found in `design/gdd/cursor-highlight-state.md` round 8 adversarial review — the doc's review log claimed motor accessibility was "已裁定轉交 `design/ux/accessibility-requirements.md`," but that file doesn't exist anywhere in the project (only an unfilled generic template lives at `.claude/docs/templates/accessibility-requirements.md`), the punt was never written into the GDD itself (no Open Questions row, no Dependencies mention) or into `systems-index.md`'s registry, and the file only ever appeared in the review log's prose. A punt recorded only in a review log (not in the document or the index) evaporates the moment nobody re-reads that log — it is not actually a mitigation, just a note that one was discussed.

**Recurrence pattern — repeat "nice-to-have" items**: Same review also found `cursor-highlight-state.md`'s onboarding/tutorial-hook gap for the mouse-reclaim progressive-feedback mechanic had been reflagged as a "nice-to-have" for 7 consecutive review rounds, and round 7's creative-director explicitly ordered it "轉為登記義務,不再以建議項循環" (converted to a tracked obligation, stop cycling) — but round 8 showed this directive itself was never executed: no Open Questions row was added, and `systems-index.md`'s dependency map for the one system that would own teaching it (教學/上手引導系統) doesn't even list the cursor system as a dependency. **When a review log shows the same advisory item recurring 3+ rounds, or shows a "this must become a tracked obligation next round" directive, explicitly check whether that conversion actually happened in the next round's diff — don't assume a stated intent was carried out.**

**How to apply**: In any GDD adversarial review, before accepting a cross-document punt as closing an issue, run Glob/Grep on the target path and on `systems-index.md`'s registry and dependency map. If any of the three checks above fails, the punt is orphaned and should be reported as a finding (typically blocking, since it represents an untracked requirement with no owner) — not treated as already-resolved.

**Round 9 follow-up (2026-08-05)**: Round 8's fixes were real (the accessibility-requirements.md obligation and the tutorial-hook obligation both got proper Open Questions rows + `systems-index.md` registry entries in round 8's diff — the earlier finding above was correctly resolved as a tracking gap). But two *other* round-7 "recommended" items quietly disappeared between round 7 and round 8's review-log diff without being resolved, carried forward, or explicitly closed with rationale: "無障礙覆寫點應在 Tuning Knobs 明文承認" (accessibility override points should be acknowledged in Tuning Knobs) and "三態視覺跨系統一致性義務登記" (three-state visual consistency should be registered as a cross-system obligation). Neither appears in round 8's resolved list nor its own "留待後續" carry-forward list — they just vanished. **Lesson**: even after a round properly registers an obligation (passing all three checks above), still diff each round's "留待後續" list against the *previous* round's list item-by-item — items can be silently dropped from the carry-forward list itself, not just left permanently as recurring nice-to-haves. Also confirmed separately: properly registering an obligation (Open Questions + registry row) is necessary but not sufficient — `design/ux/accessibility-requirements.md` still does not exist on disk as of round 9, one full round after the registration was added.

**Round 10 follow-up (2026-08-05)**: `design/ux/accessibility-requirements.md` still does not exist on disk as of round 10 (two full rounds after the round-8 registration, and the underlying obligation was first raised round 6 — 4 rounds of tracked-but-undelivered). The persistent-ledger format adopted in round 9 (see `design/gdd/reviews/cursor-highlight-state-review-log.md`) tracks this item (L10) as "持續追蹤中" rather than auto-escalating it, because round 8 changed its *disposition* (from bare mention to registered obligation) — but a disposition change is not the same as delivery, and the ledger's 3-consecutive-round auto-escalation counter appears to reset on any status-field edit, not just on resolution. **Lesson**: when a persistent ledger's auto-escalation counter is driven by "rounds since last status change" rather than "rounds since the underlying deliverable was produced," a punt can be kept perpetually one status-edit away from escalating without ever actually closing. When reviewing ledger-tracked items, check whether the counter is tracking real progress (the file exists, the obligation is closed) or just tracking bookkeeping churn (the status cell got reworded).

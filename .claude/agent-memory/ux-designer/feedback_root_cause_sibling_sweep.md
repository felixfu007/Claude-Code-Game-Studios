Rule: A confirmed, spike-verified defect is not the same thing as a confirmed, spike-verified *scope* for that defect. Once a review round identifies the underlying mechanism (not just the symptom) — e.g. "any rule that grants a zero-threshold/immediate state change on every repeated/held-input event, without distinguishing a genuinely new discrete player action from continuation of a sustained input, is vulnerable" — search the whole document for every OTHER rule built on that same mechanism before proposing or accepting a fix scoped to just the rule where the symptom was first observed.

**Why**: Found in `design/gdd/cursor-highlight-state.md` round 12 (2026-08-11). The confirmed defect "持續按住方向鍵/搖桿導致滑鼠奪權永久鎖死" (Known Confirmed Defects row 1) lives in Core Rules #3's same-frame veto trigger (d). The candidate fix (filter same-frame veto by `InputEventKey.echo`) targets *only* that rule. A non-engineer human tester's round-12 keyboard-path retest incidentally discovered a second, distinct symptom — mouse briefly completes a reclaim (highlight visibly moves) and is then instantly snapped back by Core Rules #3's *separate* "反方向零門檻豁免" (reverse zero-threshold exemption) rule, which shares the exact same root cause (held-input repeat events treated as fresh discrete navigation intent) but lives in a different rule with a different code path. The candidate fix, confirmed by the same test (keyboard Mode 1/Mode 2 identical), does nothing for this second symptom — proving the fix was scoped to the symptom's *location*, not the defect's *root-cause class*.

**How to apply**: When a design doc registers a confirmed defect with a proposed/candidate fix, before signing off on that fix (or before declaring a hard gate lifted), grep the whole document for every rule that shares the same underlying mechanism as the defect (in this case: every rule that treats an input event as authority-transferring without checking whether it's a "new press" vs. "continuation of a hold/repeat/analog-threshold-crossing"). If sibling rules exist and the fix doesn't address them, either (a) recommend redesigning all sibling manifestations together in one pass, or (b) explicitly widen the hard-gate condition to require all siblings resolved, not just the first-discovered one — don't let "fixed the rule where we found it" be mistaken for "fixed the defect class." This is the same failure family as [[feedback_mechanism_removal_sweep]] (a change made in one place silently leaves siblings/dependents unswept) but applies to *defect root-cause scope* rather than *removed-mechanism terminology*.

# 權限規則與提交閘門的實際涵蓋範圍

> **本檔只記錄量到什麼,不記錄應該如何。** 建立於 2026-09-14,起因是管理者指出
> 「hook 越走越歪,沒防堵到失誤,還讓專案空轉」,隨後的全面實測證實了大半。

## 一、為什麼需要這份文件

專案有三道看起來在保護自己的機制:允許清單、禁止清單、提交閘門。
2026-09-14 實測發現其中兩道大部分時間在空轉 —— **而空轉不留任何痕跡**,
所以沒有人會發現。這正是 `docs/consistency-failures.md` 模式 D 的形狀。

## 二、根因:指令前綴(已於 2026-09-14 停止)

實測語料:51 個對話紀錄、6096 條 Bash 指令。

| 指令開頭 | 筆數 | 佔比 |
|---|---|---|
| `cd <專案路徑>` | 4400 | **72%** |
| 其他 | 1696 | 28% |

專案裡每一道守門都是**從指令開頭比對**的,那個前綴讓它們全部落空。
工作目錄本來就已經在專案根目錄,該前綴是多餘的。**協調者自 2026-09-14 起不再使用。**

## 三、允許清單:實測命中 3/691(0.4%)

`.claude/settings.json` 的 `allow` 共 10 條,對真實指令的命中狀況:

- 五條 git 規則(`git status*` / `git diff*` / `git log*` / `git branch*` / `git rev-parse*`)
  —— **命中 0 筆**
- `ls *` —— 命中 3 筆
- `dir *` —— 0 筆
- 三條 `python` / `py` 規則 —— **在本機不可能命中**:這台機器沒有 Python
  (`python` 是 Windows 商店的空殼,執行只印安裝提示),而本專案測試框架是
  GdUnit4、用 Godot 執行檔跑。**這三條是範本預設值,從未適配本專案。**
  ✅ **已於 2026-09-14 移除,`allow` 由 10 條降為 7 條(本批)。**

🔴 **停止使用 `cd` 前綴後,前七條才開始有機會命中。本檔建立時尚未累積新數據。**

## 四、禁止清單:對裸指令確實有效,對串接指令未知

✅ **已實測會擋**:裸寫 `cat does-not-exist.env` 當場被 `Bash(cat *.env*)` 擋下。
**它不是裝飾品。**

⚠️ **未驗證**:`cd . && cat *.env` 會不會被擋。管理者 2026-09-14 裁定不做這個探測
(理由:那個探測的形狀是「測試禁令能不能被繞過」)。

🔴 **因此本專案一律假設「前綴會讓禁令失效」**,這是最保守的立場。
**不要把禁止清單當成安全邊界** —— 它是前綴比對,不是防護牆。

## 五、自動模式分類器 ≠ 權限清單

**這是兩個不同的機制,常被混為一談:**

- **分類器**逐次判斷該不該做,**不看白名單**。加規則對「被分類器擋下」**無效**。
- 錯誤訊息本身會建議「加一條 Bash permission rule」—— **那個建議會誤導**。

實測分類器的實際行為(2026-09-14,540 次工具呼叫):

| 指令性質 | 是否送審 | 耗時 |
|---|---|---|
| 唯讀(`sed -n` / `grep` / `cat` / `git log` / `git diff`) | **否** | < 50 ms |
| 會寫檔、複製、執行外部程式 | 是(第一關) | 平均 1.3~1.6 秒 |
| 第一關拿不定主意 | 是(第二關) | **17~109 秒**,15 次 |

**決定快慢的是「這條指令會不會寫東西」,不是任何清單。**

📌 log 裡的「Slow permission decision」**包含等人按按鈕的時間**。
最長那筆 318 秒 = 分類器 109 秒 + 等人約 210 秒。**不要把它當成系統耗時。**

## 九、死胡同稽核(2026-09-14)

管理者提問:「會不會有擋下了卻沒有任何回報,讓 agent 空等的狀況」。
13 支掛載中的 hook 逐支查過。

### ✅ 三項確認沒有問題

- **沒有「擋下但不說話」的路徑。** 只有 2 支能擋(`validate-commit` 4 處、
  `validate-doc-consistency` 1 處),5 個阻擋路徑**全部先寫 stderr 才 `exit 2`**。
- **沒有卡死風險。** 7 支會讀 stdin 的**全部是 `timeout 2 cat`**,無裸 `cat`。
- **時間餘裕充足。** 實測耗時全部在各自逾時上限的 **15% 以內**。

### 🔴 找到並修掉的一項:python 空殼把合法 JSON 判成不合法

| | |
|---|---|
| 引爆條件 | 提交 `assets/data/*.json`(稽核當時該目錄尚無 .json,故從未引爆) |
| 機制 | `command -v python` 找得到 Windows 商店空殼 → `python -m json.tool` 回傳 **49** → 判定 not valid JSON → `exit 2` |
| 🔴 最糟的部分 | 錯誤訊息 `BLOCKED: xxx is not valid JSON` **是假的**,會讓人去修一個本來就對的檔案 |
| 實測 | 暫存一個合法 JSON 後分別餵給新舊版:**舊版 exit 2 + 假訊息,新版 exit 0** |
| 修法 | 判準由「找得到」改為「跑得起來」:`command -v "$cmd" && "$cmd" --version` |

### ⚠️ 找到但只能緩解的一項:hook 逾時是靜默的

hook 被 harness 逾時取消時,逐字紀錄裡只留下:

```json
{"type":"hook_cancelled","durationMs":11340,"timedOut":true,"timeoutMs":10000}
```

**沒有訊息內容。** 當下你和 agent 都收不到任何提示,只有事後翻逐字紀錄才查得到 ——
也就是「閘門沒跑」與「閘門通過」在畫面上長得一樣。

`validate-commit` 歷史最慢 **73.3 秒**、當時上限 90 秒 = 用掉 **81%**,餘裕不足。
**緩解:上限提高到 150 秒**(最壞情況降到 49%)。

🔴 **這只降低機率,沒有解決「逾時本身不會說話」。** 真正的解法需要 harness 支援,
不在本專案可控範圍內。**查逾時的唯一方法是事後 grep 逐字紀錄的 `hook_cancelled`。**

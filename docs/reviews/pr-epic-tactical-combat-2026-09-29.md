## 一、問題 2:能在里程碑期限前完成嗎

**答:能 —— 但這個「能」的成立條件與大多數人預期的不同,而且風險不在 #4 身上。**

### 1-1 先釐清要對照的是什麼:退出條件,不是 epic 的完整範圍

派工單明文要求對照第 2 階段的退出條件。原文:

```
$ sed -n '105p' production/milestones/one-year-plan.md
| **2. 能動** | 3-5 | 游標/高亮(#3)、戰棋移動與交戰(#4)、好感度—位置連鎖(#5) |
棋子能走、能交戰,且**好感度確實改變戰鬥結果** | 🔵 **進行中 —— 2026-09-29 是本階段第 1 天**
```

🔴 **這個退出條件已經在 2026-08-28 達成過一次,而且有建置產物。** 一年計畫第四之二節①:

```
| 第 2 階段退出條件(棋子能走、能交戰、好感度確實改變戰鬥結果) | 第 3–5 個月 | **2026-08-28 達成**(第 1 個月) |
```

且該節逐字寫明那批的內容:「含棋盤地形、5 名我方單位、敵方 AI、勝負判定、鍵盤/手把/滑鼠
三種操作,**且好感度確實進入傷害公式**(`combat_rules.gd`:`max(0, atk - def + phi)`)」。

**所以 #4 這個 epic 不是去達成退出條件的工作,它是把一個已經達標的東西換成經得起驗收的版本。**
這與一年計畫自己對那 8 天的判讀完全一致(同節逐字):「3 天那批是『先讓它動』;5 天那批是把
同一件事換成經過完整設計與審查的版本 —— **期間玩家看得到的新功能為零**。」

⚠️ **這不是說可以不做。** 退出條件達成過一次,但達成它的那批東西自己不合格:同節明文
「不要把 3 天當成可外推的速度 —— 那批用的數值來自暫定值,美術是暫用圖,只有 1 張關卡,
**而且它自己那套輸入處理正是 #3 要取代的東西**」。**要點是:期限風險不來自「做不完就沒東西
可交」,而來自「做不完就交一個不合格的東西」** —— 這兩種風險的緩解手段完全不同,
後者可以靠**分批驗收**化解,前者不行。

## 二、問題 1:六個模組放在一個 epic 裡對嗎

**答:對的,維持一個 epic。但 M1 應該移出去(見第六節 C3)。**

### 2-1 有一條看起來很漂亮的切線,而它是錯的

最誘人的拆法是照目錄切:**邏輯層 epic(M2+M3)** vs **呈現層 epic(M4+M5+M6)**。
目錄邊界確實乾淨:

```
$ ls src/gameplay/board/ src/gameplay/battle/ | grep -v uid
board.gd  line_of_sight.gd
battle_controller.gd  battle_loop.gd  battle_state.gd  turn_order.gd
```
M2→`src/gameplay/board/`,M3→`src/gameplay/battle/`,M4/M5/M6→`src/ui/battle/`。**零重疊。**

而且**本專案已經有這個先例**:`skill-card-system`(邏輯層 8 張)+ `card-play-interface`
(呈現層 18 張)就是同一個系統切成兩個 epic。

🔴 **但那個先例不支持這裡照做,它剛好是反面教材。** `production/epics/index.md` 的
`skill-card-system` 列逐字:

```
🟡 進行中(邏輯層完成;**介面層已由 [card-play-interface](card-play-interface/EPIC.md) 接手,不要再開第三份**)
```

那句「**不要再開第三份**」是在收拾一個已經發生的混亂 —— 一個系統散在兩個 epic、
狀態欄互相對不上,而且**它的索引列在 2026-09-29 才被更正,錯了 14 天**
(同檔檔頭逐字:「本檔檔頭曾停在 2026-09-15 整整 14 天,而期間兩個 epic 都動過,
這是下方兩列同時寫錯的共同成因」)。**那不是一個成功的拆分,是一個補救。**

### 2-2 三個不該拆的實質理由

**(一)M3 的介面形狀由呈現層的需求決定,拆開等於叫邏輯層用猜的。**
epic 自己寫明(M3 第 1 點):

> 介面形狀(三個方法 vs 一個回傳多切面的結構)**由本模組定案**,UX 規格只定案「三個切面必須都查得到」。

若 M2+M3 是獨立 epic,它會在 M4/M5 還沒開始時就把介面定死,而定死的依據只有 UX 規格
—— 而 UX 規格自陳七項未核對。**拆分會把「等一下再決定」變成「現在必須猜」。**

**(二)依賴鏈橫跨那條切線,且是緊耦合的。** M3→M4、M3→M5 都是直接的資料源依賴,
不是鬆散的。跨 epic 的阻塞交接在本專案已經被證明管不好 —— 就是 2-1 引的那 14 天。
**同一個 epic 內的模組依賴由 story 的 `Depends On` 欄管,跨 epic 的依賴由索引檔管,
而索引檔是本專案目前已知最會漂的東西。**

**(三)規模沒有大到非拆不可。** 依第 1-3 節推估 25~35 張、預期 17~23 個開發日。
對照 `card-play-interface` 的 18 張 / 7 個開發日,#4 大約是它的 1.5~2 倍。
**那是「大一點」,不是「大到要拆」。**

### 2-3 一項要正面登記的代價(拆不拆都存在)

⚠️ **25~35 張 story 的追蹤成本是真的,而本專案在 18 張就已經漏過一次。**
`production/epics/index.md` 的 `card-play-interface` 收尾提交訊息逐字:

```
$ git log --format="%s" -1 6c92014
feat(epic): 卡牌介面 epic 18/18 收尾 —— 而最該記的是 5 張程式做完的工作單狀態欄停了 12 天沒人發現
```

**18 張裡有 5 張的狀態欄停了 12 天。** #4 若是 25~35 張,同樣密度會是 7~10 張。
**這不構成拆 epic 的理由**(拆成兩個 epic 不會讓狀態欄自己更新),但它構成
**一項 `/create-stories` 時的具體要求**:見第六節 C3 附帶項。

### 2-4 反向:有沒有模組小到該併?

**有一個 —— M1。但它的問題不是「小」,是「種類不對」,所以答案是移出而非合併。**
詳見第四節與第六節 C3。

**M2~M6 五個模組沒有任何一個小到該併**:每個都有獨立的檔案集合、獨立的驗收形狀
(M2 演算法/M3 契約/M4 截圖/M5 互動語意/M6 輸入收斂),合併任兩個都會讓驗收條件混在一起。

## 三、問題 3:順序對嗎(查證 M4/M5 可並行、M2→M3 不可壓縮)

**答:骨幹順序對,但 epic 明文強調的那兩個宣稱 —— 逐字查證下來 —— 一個是錯的,
一個是過度宣稱。而且它們錯的方向相反:一個讓你以為可以並行(實際會撞車),
一個讓你以為不能並行(實際可以)。**

epic 的原句(第 216 行):`🔴 **M4 與 M5 可並行,M2→M3 不可壓縮。** 若要排兩條工作線,切點在 M3 完成之後。`

---

### 3-1 宣稱甲「M4 與 M5 可並行」—— ❌ **與 epic 自己的風險 R4 直接互相否定**

**這不是我跟 epic 的意見不同,是 epic 的兩節互相打架。** 同一份檔案:

| 位置 | 原文 |
|---|---|
| 「依賴與實作順序」節 | 🔴 **M4 與 M5 可並行** |
| 「已知風險」R4 | 排程上讓 **M4/M5/M6 對 `battle_screen.gd` 的改動序列化,不要並行** |

**實測支持 R4 那一邊:** M4 宣稱「`board_view.gd` 現有繪製路徑不動」,但它畫的東西要有人餵,
而餵它的是 `battle_screen.gd`:

```
$ grep -c "_refresh_view" src/ui/battle/battle_screen.gd
36
$ grep -c "_board_view\." src/ui/battle/battle_screen.gd
16
```

`_refresh_view` 在 `battle_screen.gd` 出現 **36 次**,`_board_view.` 出現 **16 次** ——
M4 要把 M3 新查到的三態/三層/四態傳進世界層,**必經 `battle_screen.gd`**。
而 M5 要拆的 `_confirm_at_cursor()`、M6 要動的輸入分派,也都在這個 2702 行的檔案裡。

🔴 **結論:M4 與 M5 在「規劃層」可並行(它們的產出互不依賴),在「執行層」不可並行
(它們改同一個檔案)。** epic 的那一行沒有區分這兩件事,而 story 的依賴欄會照抄它。

### 3-2 宣稱乙「M2→M3 不可壓縮」—— ⚠️ **只對五分之一成立,其餘四項今天就能開工**

epic 說 M3 的前置是 M2、M2 是「唯一一個沒有任何上游的實作模組」。**逐項查證 M3 的五組切面:**

| M3 切面 | 真的需要 M2 嗎 | 實測依據 |
|---|---|---|
| 1. 移動範圍三切面 + 第四態 | ✅ **需要** | 第四態就是 `passable`,三切面要靠兩個 ignore 開關拆。`grep -c "passable" src/gameplay/board/board.gd` → `0` |
| 2. 射程內但視線被擋 | ❌ **不需要** | 視線在獨立檔案的 static 函式裡,不碰 `board.gd` 的可通行概念:`grep -n "func " src/gameplay/board/line_of_sight.gd` → `28: static func is_clear(...)` / `94: static func _blocks(...)` |
| 3. 單位行動四態 getter | ❌ **不需要** | 資料源是 `turn_order.gd` / `battle_controller.gd`,與棋盤地形無關 |

### 4-1 M1:不是過大或過小,是**放錯層級**

M1 的產出是「文件與測試」,零功能。epic 自己寫:`**輸出是文件與測試,不是功能。**`

1. **epic 完成度會失真** —— 「6 個模組完成 1 個」聽起來是 17%,但玩家可見的進度是 0%。

3. 它沒有上限。epic 寫「成本低(讀碼 + 少量測試)」——**但沒有寫低到哪裡**。

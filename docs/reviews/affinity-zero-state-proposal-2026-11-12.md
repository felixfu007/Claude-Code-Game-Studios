# 好感度「剛好歸零」狀態提案(2026-11-12,數值設計師)

> 性質:提案,不是裁決。管理者今天已定的前提見 `production/session-state/active.md` 第九十九批節:10 組配對皆可變友/變敵;麥子健騎牆「身上沒關係時有效、一有關係就失效」;歸零怎麼算交本提案。
> 本文件只寫這一檔,未改任何既有檔。標「未驗證」者 = 我沒有讀到原始碼或資料支持。

## 一、問題與已核實現況

**已讀原始碼核實(協調者轉述與檔案相符,無需停下):**
- `src/gameplay/affinity/affinity_phi_provider.gd`:`links()` 對所有存活我方單位做兩兩組合(10 對),`_link_for_pair()` 呼叫 `AffinityDataPool.combat_strength_read(pair)`:
  - 讀取被拒 → 無線(並 `push_warning`);
  - `n_pair == 0`(從未互動)→ 無線;
  - `value > 0.0` → 正向線、`value < 0.0` → 負向線、`value == 0.0` 且 `n_pair > 0` → 無線(檔內自承是「作者建議、未經管理者核准」的權宜解)。
- `AffinityReadResult.value` 是 **float**(`affinity_data_pool.gd`),由 `_weighted_sum(... lambda_combat ...)` 算出,即「各次互動量值 × 衰減^(經過時間)」的加總。`lambda_combat` 合法範圍 `[0,1]`(`affinity_calibration.gd`)。
- `tuning_knobs.txt` 檔頭規定:**值必須是整數**、每個已知鍵必載、未知鍵是解析失敗。所以任何新旋鈕必須是整數(浮點門檻要用「百分之一單位」之類的整數編碼)。
- 騎牆:`CombatRules.lone_guard()` / `hold_back()`;`battle_state.gd` 的 `_lone_guard_of()`、`_hold_back_of()`、`lone_guard_if_at()` 都只判「名冊第 12 欄 `lone_guard` 旗標 + 我方單位」,**完全不看好感度池**。
- 目前傷害端的影響(`tuning_knobs.txt` 與 GDD 公式):正向相鄰 +3、正向遠離 −1、負向相鄰 −1、負向遠離 +2、無線 0。

**未驗證(需要後續量測,不影響方案比較的結構,影響旋鈕初值):**
1. 池值的實際量級(單次互動 `m_i` 多大、`lambda_combat` 的設定值、`t` 的單位是回合還是場次)。我沒讀到校準資料檔,下面的數字都是**示意占位值**,不是量測。
2. 池值衰減是否會隨戰役進行讓舊關係自己滑向 0。

**兩個由原始碼讀出、會改變問題形狀的事實:**
- **事實 A:`value == 0.0` 在 float 加權和下幾乎不會「剛好」發生**(除非 `lambda_combat = 1` 且量值整數互相抵銷,未驗證)。真正的問題不是那一個點,而是「**0 附近的一大片**」:目前 `+0.001` 與 `+5.0` 都給完整的 +3(相鄰)——**關係強度與加成大小脫鉤**,而且衰減只會把值縮向 0、不會翻號,所以舊關係衰到近乎 0 仍拿滿額加成。
- **事實 B:極性一翻面,相鄰加成從 +3 直接掉到 −1(落差 4)**,中間沒有任何緩衝。「關係從好變壞」在玩家眼中是一個斷崖。

## 二、三個方案的比較

### 共用定義(只有一套,騎牆、戰鬥線、營火全部讀它)

| 符號 | 型別 | 範圍 | 說明 |
|---|---|---|---|
| `v` | float | 無界 | `combat_strength_read(pair).value` |
| `n` | int | ≥0 | `.n_pair`,互動筆數 |
| `k` | float | ≥0 | 中性帶半寬(方案 c 的旋鈕;k=0 即方案 a) |
| `S(pair)` | enum | {POS, NEG, NONE} | 該配對的**關係狀態** |

方案 (a) / (c) 共用一條式子(無需兩套程式):

`S = NONE 若 n == 0 或 |v| ≤ k;POS 若 v > k;NEG 若 v < −k`

- 輸出範圍:三值離散,無夾限問題。
- 方案 (a) = `k = 0`(僅 `v == 0` 為 NONE,現狀)。方案 (c) = `k > 0`。
- 方案 (b) 另需「上一次的非零極性」`last_s`:`S = last_s 若 v == 0 且 n > 0`,**必須持久化新欄位**。

示意算例(占位值,未驗證量級;設 k = 0.5):藍亭萱×徐培恩 `v = +2.0 → POS`;營火連續質問後 `v = +0.4 → NONE`;再質問 `v = −1.2 → NEG`。

### 比較

| 面向 | (a) 維持現狀(k=0) | (b) 遲滯(維持上一極性) | (c) 中性帶(−k..+k 算無關係) |
|---|---|---|---|
| 關係從好變壞的過程 | +3 → 瞬間 −1,無緩衝;幾乎不會出現「剛好 0」,但 `+0.001` 仍給滿額,過程是斷崖 | 過了 0 以前一直維持「好」,翻號那一次才翻 → **斷崖更晚、更突然**;玩家看見數字已負、戰鬥仍給友好加成 | 經過一段「冷淡期」(加成 0),**漸進:好 → 無 → 壞**,最貼「沒有永遠的朋友/敵人」的敘事 |
| 騎牆何時生效/失效 | 只要有任一線(`n>0` 且 `v≠0`)就失效;一次小互動(`|v|` 很小)就永久失效,實務上等於「戰過一場就失效」 | 一旦有過非零極性就永不回到「沒有關係」→ **騎牆一失效永遠不會恢復**,與管理者「身上沒關係時有效」不符 | 關係被磨回帶內就恢復騎牆,**可逆**;小擾動不會立刻關閉騎牆 |
| 營火競爭/合作卡強度 | 合作與競爭強度無法與「很弱的關係」區分;近 0 的配對仍拿滿額,「關係越差越強」的起點不清楚 | 中性時沿用舊極性,可能讓兩人其實已沒感覺卻仍出合作卡,卡面與劇情不符 | 強度可定義成「超出中性帶的部分」`max(0,|v|−k)`,近 0 自然是底價,關係越深越強,梯度乾淨 |
| 玩家可預測性 | 簡單但遇到「+0.001」時結果反直覺 | 最難預測:同一個 `v=0`,結果取決於看不見的歷史 | 容易講清楚:UI 可顯示三態「友好/冷淡/敵對」,玩家看得懂門檻 |
| 實作/資料成本 | 零 | 需新增持久化欄位 `last_s`,且 `links()` 目前「每次查詢重算、不快取」(story-005)與存檔格式(ADR-0003)都要動;**成本最高**(影響範圍未驗證) | 1 個整數旋鈕 + 一個共用判定函式;不動存檔 |
| 風險 | 事實 A、B 不解決 | 與管理者「騎牆可回復」意圖衝突,且新增存檔欄位 | 初值 `k` 要靠量測訂(量級未驗證);`k` 過大會讓關係太難成形 |

## 三、騎牆「身上沒關係」的判定(與第二節同一套)

定義:**麥子健(roster id 5 的角色)「身上沒關係」⇔ 他與其餘四位的 4 對配對,`S(pair)` 全部為 NONE。** 任何一對為 POS 或 NEG 即「有關係」,`lone_guard` 與 `hold_back` 兩項一律 0(不得只關一項,否則騎牆半開)。

- 重用同一個 `S()`,不得在 `CombatRules` 另寫第二套門檻。判定結果以**布林參數**交給 `CombatRules.lone_guard/hold_back`(目前 `CombatRules` 是純函式、不認識好感度池,維持這個邊界;由 `BattleState` 查完再傳入)。
- **待管理者/設計確認的子題(兩種讀法)**:
  - 讀法一「池內」:看 4 對配對的池值(不管對方是否存活/在場)。可預測,但與 `links()` 只掃「存活單位」不同範圍——**判定函式相同,掃描範圍不同**,須在 GDD 註明。
  - 讀法二「場上」:只看存活隊友的線(與 `links()` 同範圍)。隊友陣亡會讓麥子健突然回到騎牆,可能出現「靠隊友死亡生效」的怪事。
  - 我推薦**讀法一**(關係是故事事實,不是戰場事實)。
- 連帶後果:GDD 公式五寫「戊 Φ 恆為 0、不加關係線」。若麥子健可與任何人建立關係,這句在「有關係」時不再成立——**這是需同步修訂的文件事實,本提案不改**,留給修 GDD 的人(須走管理者核准)。
- 邊界:麥子健是隊伍中唯一存活的我方單位時,既無關係也無隊友 → 沿用現行 `lone_guard`/`hold_back` 對「無存活隊友」的規則(0),不受本提案影響。

## 四、推薦案、資料欄位與旋鈕

**推薦 (c) 中性帶。** 理由:唯一同時滿足(1)管理者「沒有固定朋友/敵人」(關係能被磨回中性再往反向走);(2)騎牆「無關係時有效」可逆;(3)不需新增存檔欄位;(4)修掉事實 A(近 0 滿額加成)。(b) 與管理者的騎牆意圖衝突;(a) 實質上讓騎牆被一次小互動永久關掉。

**建議新鍵(皆為整數,符合檔頭格式):**

| 建議鍵 | 型別 | 建議初值 | 說明 / 安全範圍 |
|---|---|---|---|
| `affinity,neutral_band_centi` | int | **待量測**(占位 50 = k 為 0.50) | 中性帶半寬,單位 1/100 池值;0 = 方案 (a)。範圍 0 ~ (一次典型互動 `m` 的 100 倍)以內,過大則關係難以成形。**量級未驗證,不得直接用占位值** |
| `camp,strength_floor_pct` | int | 待營火規格決定 | 營火卡在中性狀態的底價強度(百分比);強度公式見下 |

營火強度建議式(待營火規格採用,非本提案強制):
`strength = base × (1 + gain × max(0, |v| − k))`,競爭卡用 `|v|` 取負向側(關係越差越強)、合作卡取正向側。`base`、`gain` 屬營火規格旋鈕,本提案不定。

**實作面需求(不寫程式碼):**
- 新增一個共用判定(例:`AffinityRelation.state_of(pair)`),供 `AffinityPhiProvider._link_for_pair`、騎牆閘門、營火三處共用。
- `AffinityPhiProvider._link_for_pair` 第 3 分支(`value == 0.0`)改為併入 `|v| ≤ k`;其診斷計數器 `_diagnostic_zero_value_pair_count` 語意需順改。
- `TuningKnobs` 預設值表與 `tuning_knobs.txt` 須同時加鍵(缺鍵=載入失敗)。

**模擬/量測規格(上線前驗證,因量級未驗證):**
1. 以現有名冊與卡牌寫入規則跑一份「10 對配對的 `|v|` 分布」(寫入來源與衰減參數須用專案真實類別,見 `technical-preferences.md` 對 (A) 級證據的要求)。
2. 取單次互動 `|m|` 的中位數,令初始 `k` = 該值的 0.5~1 倍;確認一場戰鬥內至少有兩對進出中性帶(否則帶太寬或太窄)。
3. 驗證 k=0 時行為與現行程式逐位相同(回歸)。

## 五、給管理者的選項(白話)

**要回答的事**:藍亭萱和徐培恩感情好,你在營火一直質問,感情慢慢掉。掉到「不好也不壞」時,戰鬥和麥子健要怎麼算?

- **選項一:維持現狀(只有剛好 0 才算沒關係)。** 優點:不用改。缺點:幾乎不會剛好是 0,所以感情「淡到快沒了」時,藍亭萱和徐培恩並肩仍拿滿額加成;麥子健只要跟任何人打過一次互動,騎牆就永久關掉,等於這個角色特色形同虛設。
- **選項二:記住最後是好還是壞(遲滯)。** 優點:不會在 0 附近來回跳。缺點:感情明明掉到 0,戰鬥還當他們是朋友;麥子健一旦有過關係,就再也回不到「沒有關係」,與你說的「身上沒關係時有效」不合;還要多存一個欄位、改存檔。
- **選項三:設一段「冷淡帶」(推薦)。** 感情在冷淡帶內算沒關係:藍亭萱和徐培恩從並肩有加成,變成冷淡期沒加成,再繼續掉才變成敵對。麥子健在冷淡帶內仍可騎牆,感情被磨回冷淡就恢復。優點:最貼「沒有永遠的朋友和敵人」,可逆、好懂、不動存檔,營火卡強度也能隨關係深淺。缺點:要先量測決定冷淡帶多寬,太寬關係難成形、太窄形同選項一。

**我推薦選項三**,最終由你決定。另有一題需你選:麥子健「有沒有關係」只看池內數字(推薦,不受隊友陣亡影響),還是只看場上活著的人?

## 三、編號形狀提案

### 3.1 結論

> **`OBL-001` ~ `OBL-043`,純流水號、不分段、固定三位數補零,放在表格最左邊的新增欄位 `ID`。**
> 號碼依**現有表格由上而下**發給 43 列(現有順序即登記時序,見 2.4)。

### 3.2 為什麼不分段(推翻稽核報告順帶提的 `OBL-CUR-01` 形狀)

分段的唯一好處是「看得出屬於誰」。問題是**這張表沒有一個穩定且單值的「誰」可以當段碼**:

- **用「承接系統」當段碼 —— 不可行,而且是最危險的一種不可行。**
  實測 43 列中,承接系統欄位是**多值**的很常見(例如
  `敘事解鎖與結局分支系統、好感度—位置連鎖系統`、
  `好感度視覺呈現 UI / 未來的存檔槽瀏覽器 / 戰鬥 HUD`),一列同時指派給 2~3 個系統。
  更關鍵的是**它會變**:第 19 列的承接系統今天是「無(原候選:…)」,
  第 42 列今天是「✅ 2026-09-09 同日指派並產出…」—— **指派會改、會取消、會轉手。**
  段碼若綁在會變的欄位上,改一次指派就要改號碼,**而改號碼正是本提案第四節要永久禁止的事。**
- **用「登記來源」當段碼 —— 穩定,但答非所問。**
  來源文件是歷史事實、不會變,看似適合。但實測來源欄是複合字串
  (例:`affinity-data-pool.md Dependencies + Core Rules #3(第七輪新增,2026-08-10 第八輪拆分)`,
  另有一列同時列出三份文件),要當段碼必須先替每份來源文件發一組代碼 —— 等於**多養一張對照表**,
  而對照表就是本專案登記過最多次會脫節的東西。
  而且讀者實際上會問的是「**這個系統欠哪些義務**」(承接系統),不是「這條是哪份文件登記的」——
  **段碼就算做出來也不服務主要查詢。**
- **純流水號的壞處是真的**:`OBL-031` 本身看不出屬於誰。
  **但它已經被現有欄位解決了** —— 表格第三欄就是承接系統,要分組就當場 `grep`:
  ```bash
  awk -F'|' '/^\|/ && $4 ~ /存檔系統/ {print $2, $4}' design/gdd/systems-index.md
  ```
  **ID 的職責只有一個:當一個永不漂移的把手。** 讓它同時承載分類語意,等於把會變的東西
  焊進不能變的東西裡。

### 3.3 為什麼是三位數,不是兩位

這一條是**成本不對稱**的判斷,不是美感:

- **兩位數現在夠用**(43 列,2.3 的速率顯示設計爆發期已過)。
- **但位數一旦要加寬,就是一次全表重排等級的事故。** `OBL-07` 與 `OBL-007` 是**兩個不同的
  字串**;加寬之後,所有既有引用的 `grep "OBL-07"` 會找不到新表、找得到舊引用,
  **而且不會報錯** —— 這正是本專案登記最多次的失效形狀(散文複本與權威來源安靜脫節)。
- **不補零的變長號碼更糟**:`grep "OBL-7"` 會同時命中 `OBL-70`~`OBL-79`。
  **而 `grep` 是本專案唯一真的在運作的執行手段**(見第七節:沒有任何閘門會檢查這套編號)。
  **凡是會讓 grep 失準的設計,在這個專案等於沒有執行手段。**
- 三位數固定寬度的代價是**每次引用多一個字元**,收益是
  **`grep "OBL-007"` 永遠精確、永遠不會前綴誤命中、永遠不需要再做一次寬度決策。**

📌 **1000 列是不可達的上限嗎?** 2.3 的實測速率下是。但若真的逼近,
**正確動作是拆表(例如依承接系統拆成數張),不是加寬位數** —— 這一點寫在第七節的長期承諾裡。

## 四、退役列的處理(🔴 本提案最承重的一節)

### 4.1 三條硬性規則

> **R1 — 號碼終身制。** 一個 ID 一旦寫進表裡並經核准,**永不改號、永不移作他用、永不回收**。
> **R2 — 退役是原地標記,不是刪列。** 退役列留在表上、留在原來的位置、保留原 ID,
> 在 `義務內容` 欄開頭加 `❌ 已退役(日期,裁決出處)` 並一句話寫明**為什麼退役**
> (已解決 / 作廢 / 已併入他列)。**不刪列、不補空號、不重排。**
> **R3 — 空號是合法的、而且必須看得見。** 若日後出現 ID 不連續,那是退役或拆併的痕跡,
> **不是錯誤**,任何人不得「順手補齊」。

### 4.2 為什麼必須這樣,以及它防的是什麼

- **本專案已有明文慣例,本節只是讓登記表接上它。**
  `.claude/hooks/validate-doc-consistency.sh` 對 AC 編號不連續的警告逐字就寫著
  「Retirements are fine (this project keeps retired ids on the books)」
  (查法:`grep -n "Retirements are fine" .claude/hooks/validate-doc-consistency.sh`)。
  `cursor-highlight-state.md` 的 AC-27/AC-55 退役也逐字寫著
  「標記已退役,保留編號,不重新編號、不填補空號」。
- **登記表自己已經這樣做過一次了,而且成功了。** 見 2.4:第 19 列在 2026-09-03 被管理者裁決
  作廢,處置是**原地改成 `❌ 作廢,非解決`、列留著**。那一列今天還在表上第 19 個位置。
  **本節不是提案一個新做法,是把那次正確的做法訂成規則。**
- 🔴 **重排的代價是一次全庫靜默失效。** 若刪一列導致後面的號碼往前遞補,
  **所有既有引用會同時指向「錯誤但存在」的另一條義務** —— 它不會找不到、不會報錯,
  它會**解析成功並回答錯的問題**。這比行號漂移更危險:行號漂掉通常會指到空行或章節標題
  (稽核實測:第 175 列是空行、第 26 列是章節標題),人一看就知道壞了;
  **號碼遞補後指到的是一條格式完全正確的義務,看不出任何異常。**

### 4.3 兩個會逼出判斷的邊緣情況,先把判準寫死

**(甲)拆分**(實際發生過:第 6 列於第八輪由一列拆成讀取性質不同的規則)

> **判準:原 ID 留在原位的那一列(拆分後位置較上者),新產生的那一半拿新號(接在表尾)。**
> 原列的 `義務內容` 必須加一句 `(本列 YYYY-MM-DD 拆分,另一半見 OBL-0xx)`。

理由:**不需要任何人判斷「哪一半才是主體」。** 位置是客觀的、既有引用也是指著原位置那一列
建立的。若改成「兩半都拿新號、原號退役」,既有引用會全部失效一次 —— 而拆分是**擴充**,
不該有失效成本。

**(乙)合併**

> **判準:存活列保留自己的 ID;被併入的那一列原地退役,義務內容改為
> `❌ 已併入 OBL-0xx(日期)` + 一句話。**

理由:被併入那一列的既有引用仍然找得到自己的號碼,並且**一步就能跳到接手的那一列**。
刪掉它會讓引用變成死指標。

### 4.4 退役列會讓表無限長嗎?會,而且本提案接受它

43 列已經不短,只增不減意味著十年後它只會更長。**本提案的處置是「可以縮,不可以刪」**:

> 退役列允許**把內容壓成一行殘根**(ID + 一句話 + 退役日期 + 指向何處),
> **但 ID 那一格與列本身不得消失。**

這樣讀者掃表時退役列只佔一行,而引用仍然落得了地。
⚠️ **這是權衡不是解法**:壓縮會讓「當年那條義務的完整措辭」只剩 git 歷史。
要保留全文就不要壓縮 —— **兩者擇一,不要壓縮完又宣稱全文還在表上。**

## 五、發號規則(誰發號、怎麼避免撞號)

### 5.1 發號公式

> **下一個號碼 = 表內現存 ID 的「最大值」+ 1,當場計算,不得讀任何計數器。**

```bash
# 取目前最大號(要新增列時當場跑)
grep -o "OBL-[0-9]\{3\}" design/gdd/systems-index.md | sort -u | tail -1
```

🔴 **必須用「最大值」,不是「列數」。** 有退役與拆併就會有空號(第四節 R3),
**列數會小於最大號** —— 用列數發號必然發出一個已經用過的號碼,
而那正是 4.2 描述的「解析成功但指錯」的事故。

### 5.2 誰發號:**不設發號人,因為這張表的寫入本來就有鎖**

`design/gdd/systems-index.md` 是設計文件。依 CLAUDE.md 2026-10-12 裁決的分界,
**文件類既有檔一律「必須先問」** —— 任何 agent 要新增一列,都必須先取得管理者核准。
**亦即:核准閘門本身就是這張表的序列化鎖,不需要再發明一個發號角色。**

### 5.3 平行 agent 撞號的真實窗口,與處置

鎖存在不代表沒有窗口。實際會撞的情境是:**A 擬稿時算出 max=043 → 寫成 OBL-044 →
送審等待;期間 B 的批次先被核准、也拿了 OBL-044 → A 的核准下來時兩列同號。**

> **處置 D1 —— 號碼在「寫進表並核准」之前只是草稿號,可以隨意重排。**
> 提案階段寫 `OBL-044` 不構成佔號。
> **處置 D2 —— 落檔前必須重算一次 max,不得沿用擬稿時算的。**
> 提出核准請求時,把 5.1 那條指令**當下的原始輸出行**貼在請求裡
> (本專案明文:貼原始輸出行,不貼數字)。
> **處置 D3 —— 落檔後立刻跑重號檢查,輸出必須為空:**
> ```bash
> grep -o "OBL-[0-9]\{3\}" design/gdd/systems-index.md | sort | uniq -d
> ```
> (⚠️ 這條會把**引用**也算進去 —— 若同檔內有引用該 ID 的句子,它會被誤報。
>  只掃表格列的版本:
>  `awk -F'|' '/^\| *OBL-/{print $2}' design/gdd/systems-index.md | tr -d ' ' | sort | uniq -d`)

🔴 **D1 與 D2 合起來才成立。** 單有 D2 不夠,因為沒有 D1 的話,
「重算後發現號碼變了」會被當成要去改別人的號碼;有了 D1 才知道**該退讓的永遠是還沒落檔的那一方**。

### 5.4 誠實標註:這三條沒有任何自動檢查

**與本專案其餘同類規則一樣,沒有 lint、hook 或閘門會檢查發號是否照做。**
5.1 / 5.3 的兩條指令是**人要自己跑的**。本節買到的是
「下一個人有明文可查對、而且查法是一行指令」,**不是「不會有人發錯號」**。
要讓它可觀測,需要在 `.claude/hooks/validate-doc-consistency.sh` 加一條檢查
(格式合法 + 無重號 + 引用的 ID 存在)—— **本提案不順便改 hook**,那是另一次裁決。

## 六、指向登記表的那些引用,逐處「現在寫什麼 → 改成什麼」

### 6.0 🔴 先講一件會改變這件事規模的事:「14 處」裡只有 **4 處**真的會被改寫

本節**完全取用稽核報告的既有分類,一處都沒有重新分類**(依派工要求)。
取用之後逐處讀下來,得到兩個必須先講清楚的事實:

**(一)稽核報告自己的分類已經判定:B 類不修。**
報告逐字:「把它們的行號改掉會讓紀錄失去可核對性(讀者無法再判斷當年那次修訂到底動了什麼)」。
指向登記表的那些引用裡,**絕大多數是 B 類** —— 它們是「某年某月某人核對了第 N 列」的歷史紀錄,
不是指路。**加了 ID 也不會去動它們。**

> **所以:加編號能「修掉」的是 4 處,不是 14 處。**
> 其餘的價值不在回頭修,在**從今天起新寫的每一處引用都有東西可以寫** ——
> 這才是本案真正買到的東西(資料結構缺口被補上),回頭修那 4 處只是順帶。

**(二)「14」這個數字對不上稽核報告自己的逐處表,本提案不採用它。**
稽核報告「結構性建議」第 1 點寫的是
`14 處(A-06/07/08/09 + B 的 7 處 + affinity-data-pool.md:333 等)`,
而 **`affinity-data-pool.md:333` 就是 A-06 本身**(查法:

### 7.2 長期成本:**「永不重排」這個承諾實際綁住了什麼**

這是本提案最需要管理者知情的一段。發出去的號碼不能動,連帶綁住以下這些事 ——
**每一條都是從此以後都成立的,不是一次性的:**

1. **這張表從此只能追加,不能刪列、不能排序、不能重組。**
   包含「看起來很合理」的整理:依承接系統分組、依日期排序、把已關閉的挪到最後面 ——
   **只要列的順序動了,ID 與位置就會脫節。**
   ⚠️ 嚴格說「重排列的位置」不會讓 ID 失效(ID 綁的是列,不是位置),但會讓
   「見**上方** OBL-006」這種方向性措辭失真。**建議:連位置也不動,維持 append-only
   (這本來就是 2.4 實測的既有行為)。**
2. **任何自動產生/重新產生這張表的工具,從此是被禁止的。** 一個會「重建」表格的腳本
   必然要自己決定每列的號碼,而它無從知道哪些號碼已經發出去、哪些是退役空號。
3. **表會單調變長,永遠不會變短。** 43 → 只增。十年後它仍然只增。
   4.4 給了「壓成殘根」的減壓閥,但那是減少**行內字數**,不是減少列數。
4. **位數不能再改。** 三位數是終局決定;真的逼近 1000 時,正確動作是**拆表**
   (而拆表時 ID 必須原封不動搬過去,不得重編)。
5. **ID 不綁定檔案。** 若日後登記表從 `systems-index.md` 搬到獨立檔案,
   `OBL-xxx` 必須原樣搬過去。**搬家不是重編的機會。**
6. **退役列的 ID 不得被新義務借用,哪怕新義務「幾乎就是同一條」。**
   「幾乎一樣」是最危險的情況 —— 舊引用會解析成功、看起來合理、但指的是另一條規則。
7. 🔴 **這一整套沒有任何自動檢查。**
   2.6 實測:目前沒有任何 skill / hook 解析這張表 ——
   **好處是加欄不會打破任何東西,壞處是也沒有任何東西會在有人重排、發錯號、
   或引用一個不存在的 ID 時出聲。**
   **本提案買到的是「下一個人有明文可查對、而且查法是一行 `grep`」,
   不是「不會有人做錯」。** 這與本專案其餘同類規則的處境完全一樣,
   請不要在日後把它描述成「因為有了編號所以引用不會壞」。

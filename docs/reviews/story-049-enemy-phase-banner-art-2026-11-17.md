## 1. 回合標題色(敵方回合)

| 狀態 | 色票列 | 色值 |
|---|---|---|
| 玩家回合 | `ui_text_primary_01` | `#FFFFFF`(建議明確設定;現況為引擎預設) |
| **敵方回合** | **`ui_state_negative_01`** | **`#FF5252`** |

選擇理由:
1. `#FF5252` 已經是專案裡的「敵方」顏色 —— `PIECE_LABEL_COLOR_ENEMY = #FF5252`(棋子首字敵方色)。標題與敵兵首字同色,語意一致,不新增色語。
2. 避開琥珀(`#FFBF4D`)—— 琥珀已被「可攻擊環/卡牌目標」占用;標題若用琥珀會與玩家的選取訊號混淆。

**對比判斷(手算,WCAG 2.x 相對亮度)**

- `#FF5252`:R=1.0 → 1.0;G=B=82/255=0.3216 → ((0.3216+0.055)/1.055)^2.4 = 0.0844。
  L = 0.2126×1.0 + 0.7152×0.0844 + 0.0722×0.0844 = **0.2791**
- `#FFFFFF`:L = 1.0
- 兩態字色對比 = (1.0+0.05)/(0.2791+0.05) = **3.19 : 1**
  (若玩家態沿用引擎預設 `#DFDFDF`〔未驗證〕,L=0.7378,對比 = 0.7878/0.3291 = **2.39 : 1**)
- 判斷:這是「兩種狀態字色能不能分辨」,不是文字可讀性門檻。3.19:1 的亮度差 + 色相差(白 vs 紅)足以分辨,
  且**文字內容本身也變了**(「敵方行動」),符合「不得只靠顏色」。
- 標題對底色可讀性:標題**目前沒有底襯**(未見底襯節點,**未驗證**所有畫面狀況)。`#FF5252` 對 `ui_panel_bg_01 #1A1A1F`
  手算 = 0.3291 / 0.0605 = 5.43 : 1(過 4.5)。但標題實際壓在棋盤地形上,地形亮色(如 `nature_open_highlight_01 #9FAF7A`)
  上的對比**未計算**。**建議敵方回合標題與橫幅使用同一個深色底襯(見第 2 節),或標題加 `#0E0F14` 描邊
  (同 `PIECE_LABEL_OUTLINE_COLOR` 慣例)。** 這項由實作者擇一,我偏好描邊(沿用既有慣例、不新增節點)。

## 2. 橫幅視覺

| 項目 | 指定 |
|---|---|
| 底色 | `cloth_warm_shadow_01` **`#5C1F22`**,不透明度 **α 0.78** |
| 文字色 | `ui_text_primary_01` **`#FFFFFF`** |
| 框 | 上、下各一條實線,色 `ui_state_negative_01` **`#FF5252`**,粗細 = **N 螢幕像素**(= 1 個世界像素,依專案 1px 描邊規則;N 同樣來自 `compute_scale()`,不自算)。左右不畫框(橫幅若兩端貼邊則無需;若不貼邊由介面設計師決定是否閉合) |
| 文字描邊 | 不加(已有深色底襯)。若橫幅底襯在實作時被取消,改加 `#0E0F14` 描邊 |
| 字型 | `HUD_FONT`(Cubic 11)。字級 = `HudLayout.font_size()`(11×N)**或**現成的 `HudLayout.result_font_size()`。**不新發明字級**;二選一由介面設計師依橫幅高度定 |
| 動畫 | 僅淡入淡出(α 乘數),不位移、不縮放(縮放會破壞點陣字整數倍) |

文字對底色對比(手算):
- `#5C1F22`:R=92/255 → 0.1071(線性);G=31/255 → 0.0137;B=34/255 → 0.0160;L = 0.0337。
  白字 = 1.05/0.0837 = **12.5 : 1**(假設底色不透明)。
- 最壞情況(α0.78 疊在色票中最亮的地形 `#9FAF7A` 上):混合底色約 (107,63,53),手算 L ≈ 0.0688,
  白字 = 1.05/0.1188 = **8.8 : 1**,仍遠高於 4.5。
  這是對「色票內最亮地形」的計算;**實際畫面其他亮元素(單位精靈、範圍填色疊加)上的情形未驗證**,AC6 人眼開圖時一併看。
- 框線 `#FF5252` 對橫幅底 `#5C1F22`:(0.2791+0.05)/(0.0337+0.05) = **3.93 : 1**(非文字圖形元素,WCAG 門檻 3:1,過)。

為何選暗紅底而非中性深底(`#0E0F14`/`#1A1A1F`):敵方回合是「狀態轉換」,要讓人在周邊視覺就感知到換手;
中性深底與既有 HP 字底襯(`HP_TEXT_BG_COLOR`、`PIECE_LABEL_BACKDROP_COLOR`)同質,不夠醒目。
代價:見第 3 節。若管理者/介面設計師覺得太搶,**退路是 `#0E0F14` α0.72 + 同樣的 `#FF5252` 上下線**(視覺差異靠線與字色),其餘規格不變。

## 5. 位置可行性備註(視覺角度,不替介面設計師決定)

- **不可行**:畫面正中央的橫幅(典型「ROUND START」樣式)。1080p 下單格 = 32×4 = 128px,橫幅一行字 44px 加內距,
  橫跨全寬必然壓住中央列的敵我單位格;違反 AC2。
- **不可行**:左右固定側欄(1080p/4K 零邊區)。
- **視覺上可行**:貼螢幕**最上緣或最下緣**的細長橫帶 —— 前提是橫帶高度與當前棋盤、單位位置的實際關係**由 AC2 的矩形函式驗證**;
  棋盤最上/最下兩列若有敵方單位仍會被壓。我**未查**任何關卡的敵方起點,故不能保證。
- 另一個選項:不做全寬橫帶,而是**緊貼左上標題區下方、寬度只到文字**的短橫幅 —— 左上角已有 StatusLabel 與 EGM 計數框

## 7. 我方回合橫幅配色(2026-11-17 管理者裁決追加:我方回合開始也顯示對稱橫幅「我方行動」)

需求來源:`docs/reviews/story-049-enemy-phase-banner-ux-2026-11-17.md` 第 9.6 節五項(已讀)。
位置、尺寸、時長與敵方組相同,**本節只指定顏色**。以下色值皆取自 `color-palette.csv` 既有列(本節新引用 `#3A6B9C` `cloth_cool_base_01`,已逐列讀過存在),色票用量不變。

### 7.1 指定

| 項目 | 我方組 | 敵方組(第 2 節,不變) |
|---|---|---|
| 底色 | `cloth_cool_base_01` **`#3A6B9C`**,α **0.78** | `cloth_warm_shadow_01` `#5C1F22`,α0.78 |
| 文字色 | `ui_text_primary_01` **`#FFFFFF`** | `#FFFFFF` |
| 上下線色 | `ui_text_primary_01` **`#FFFFFF`**,粗 N 螢幕像素 | `#FF5252` |
| 玩家回合標題色 | **維持 `#FFFFFF`**(不改) | 標題 `#FF5252` |

設計邏輯:兩組共用「白字」,靠**底色明度 + 上下線色**區分;我方用冷色(藍)、敵方用暖色(紅),且**我方底色刻意取 base 階、敵方取 shadow 階**,讓兩組有明度差,不只靠色相。

### 7.2 為什麼不選更「對稱」的做法(都算過,否決)

手算相對亮度 L(WCAG 公式,同第 1~2 節方法):
- `#74A6C9`(`cloth_cool_highlight_01`):R=116→0.1747、G=166→0.3813、B=201→0.5836;L = 0.2126×0.1747+0.7152×0.3813+0.0722×0.5836 = **0.3520**
- `#1F3A5C`(`cloth_cool_shadow_01`):L = **0.0409**(R 0.0137、G 0.0423、B 0.1071)
- `#3A6B9C`(`cloth_cool_base_01`):R=58→0.0423、G=107→0.1471、B=156→0.3323;L = 0.2126×0.0423+0.7152×0.1471+0.0722×0.3323 = **0.1382**
- 敵方:`#FF5252` L=0.2791;`#5C1F22` L=0.0337

**否決 A:我方標題改用 `#74A6C9`(與敵方標題 `#FF5252` 「對稱」)** —— 亮度比 (0.3520+0.05)/(0.2791+0.05) = 0.4020/0.3291 = **1.22 : 1**,幾乎等亮,色盲(紅綠弱、或全色盲)下兩態標題接近無法分辨。故玩家回合標題**維持白 `#FFFFFF`**:白對 `#FF5252` = 1.05/0.3291 = **3.19 : 1**。
**否決 B:我方底色 `#1F3A5C`(shadow 階,與敵方 shadow 階對稱)** —— 底色亮度比 (0.0409+0.05)/(0.0337+0.05) = 0.0909/0.0837 = **1.09 : 1**,等於兩組只剩色相不同,違反 UX 9.6 第 2 項「須同時有明度差」。
**否決 C:我方底色 `#1A1A1F` / `#0E0F14` 中性深色** —— `#1A1A1F` L=0.0105 對敵方底:(0.0337+0.05)/(0.0105+0.05) = **1.38 : 1**,差距小且我方橫幅失去「我方 = 冷色」的色語。

### 7.3 兩組可區分度(手算)

- **底色**:`#3A6B9C` vs `#5C1F22`:(0.1382+0.05)/(0.0337+0.05) = 0.1882/0.0837 = **2.25 : 1**。(不算高,所以第二道區分靠線色。)
- **上下線**:我方白 L=1.0 vs 敵方 `#FF5252` L=0.2791 → (1.0+0.05)/(0.2791+0.05) = **3.19 : 1**。
- **色相**:藍(冷)vs 暗紅(暖),**不使用紅/綠對立**,符合 UX 9.6 第 2 項。
- 綜合判斷:兩組在「底色明度差 2.25:1 + 線色亮度差 3.19:1 + 色相相反 + 文字不同(我方行動/敵方行動)」四道上都可分,沒有任何一道單獨承載。
- 色盲:未用模擬工具,**未驗證**;依上述亮度差與藍紅軸(藍黃軸不受紅綠色盲影響)推論可辨。

### 7.4 文字與底色對比(手算,**未驗證**——未用引擎/程式量測)

- 白字 vs 我方底 `#3A6B9C`,假設不透明:(1.0+0.05)/(0.1382+0.05) = 1.05/0.1882 = **5.58 : 1**(過 4.5)。
- 最壞情況:α0.78 疊在色票最亮地形 `#9FAF7A` 上,混合底色 ≈ (80,122,149)(0.78×(58,107,156) + 0.22×(159,175,122)),手算 L ≈ 0.1779,白字 = 1.05/(0.1779+0.05) = **4.61 : 1** —— **僅略過 4.5,餘裕小。**
  處置:兩個備案擇一,由實作者在 AC6 開圖後決定 ①我方文字加 `#0E0F14` 描邊(沿用 `PIECE_LABEL_OUTLINE_COLOR` 慣例);②我方底色不透明度升到 α0.85(未重算,須重算)。**我預設不改,先看實拍。**
- 上下白線 vs 我方底:同 5.58:1(非文字圖形,門檻 3:1,過)。
- 上述 4.5 門檻出自 WCAG AA,**非本專案明文規定**(同 UX 文件已揭露,我也未查專案無障礙文件)。

### 7.6 回應 UX 9.6 五項

1. 底色/文字色/邊框色:見 7.1。
2. 可區分度:見 7.3,明度差已寫算式。
3. 對比 ≥4.5:見 7.4,最壞情況 4.61(餘裕小,已列備案)。
4. 不透明度:兩組皆 α0.78;橫幅蓋住的背景我未查,960×540 / 1920×1080 的實際可讀性**未驗證**,靠 AC6 開圖。
5. 與標題換色一致:敵方標題 `#FF5252` = 敵方橫幅線色,同一色族;我方標題 `#FFFFFF` = 我方橫幅線色與文字色,同一色族。**一致性成立,但我方的「族」是白而不是藍**(原因見 7.2 否決 A)。

## 0. 先講清楚 B 與 A 的結構差異(都出自讀程式)

1. **v4 代打完全不走 `BattleScreen`。** 它用 `BattleState.create()` + `BattleLoop` + `AffinityPhiProvider` 在記憶體裡跑,沒有畫面節點。
   `BattleScreen._guess_delta_for_cell` 本身只有三行:`_phi.positions()`、`_phi.links()`、`_phi.positions_with(uid, cell)`,
   加上 `AffinityRules.bonus_for_at − bonus_for`,用 `_state.affinity_tuning`。v4 的 `prov`/`state` 是同一批真實類別。
   → **A 級(載入真實 `BattleScreen.tscn`)在 B 做不到,除非能把站位注入真實畫面**(第 3 節)。
2. **候選格**:A 用 `ctl.select_unit()` + `move_targets().cells`;其實質就是 `BattleState.legal_moves(id)` 再排序
   (`_move_targets_for`:僅多一道 `phase`/`can_move` 閘門)。玩家階段開始時所有存活單位 `can_move` 皆真,兩者等價。
3. **好感度答案只看**:存活我方單位的站位、連線表(`prov.links()`,只含雙方存活的我方單位對)、`AffinityTuning`、該單位與候選格。
   **與 HP、已移動/已攻擊旗標、手牌皆無關;敵方位置只透過「決定候選格集合(佔位)」間接影響。**(讀自 `_guess_delta_for_cell` 與 `phi_of`;
   `units_of()` 已排除陣亡單位,故死者既不在連線也不在 `links()` 用到的我方集合。)
4. A 的 `U=0`、`P1=P2=100` 是在開場站位量的:開場時各連線距離大概率是 1 或 ≥3(沒有距離 2 的虛線;此為我對 A 結果的推論,A 的 log 可查)。
   **戰鬥中單位會走到距離 2,`0` 虛線才會出現**——這正是 B 要看的東西,也是我對「A 偏樂觀」的主要懷疑(假說,未驗證)。

## 3. 正解

**路線:在 v4 的 `BattleState` + `AffinityPhiProvider` 上,鏡像 `_guess_delta_for_cell` 的三行本體**(在觀察段內,與 `battle_screen.gd` 該函式逐字對齊):

    hypo  = prov.positions_with(u, cell)
    delta = AffinityRules.bonus_for_at(u, cell, hypo, prov.links(), state.affinity_tuning)
            - AffinityRules.bonus_for(u, prov.positions(), prov.links(), state.affinity_tuning)

再經 `EffectGuessTracker.classify_delta`。**零條重新實作規則**(只是把真實 `BattleScreen` 那三行用同樣的真實類別組合出來)。

- **誠實等級:B 級,不是 (A)。** 依 `technical-preferences.md` 第 5 點,(A) 要求 `load()` 真實 `BattleScreen.tscn`;
  B 的站位來自無畫面的 v4 狀態機,**沒有走真實宿主鏈**,所以**不得在報告裡寫 (A)**。能做的是三道**對拍(parity)**,把鏡像與真實畫面的差距壓到可查證:
  1. **開場對拍(逐格)**:B 工具對每個關卡取回合 1(不計入 B 樣本)的決策,與 A 的真實 `BattleScreen` 輸出對拍:
     `N_d`/`N_c`/正解分布須與 A 的 `run_output_1.txt` **完全相同**(例:`vs02` 68 格 25/38/5、`vs03` 52 格 19/28/5、`vs04` 74 格 25/44/5;`vs05` 取該檔值)。
     不同 ⇒ 鏡像或候選格取法有誤,**停止**。
  2. **移動後對拍(真實畫面,只用公開 API)**:另寫一支小腳本,`load()` 真實 `BattleScreen.tscn`(同 A 的注入順序:`instantiate()` → 設 override → `call_deferred add_child` → 等 2 幀),
     對每個有連線的我方單位 u、每個合法目的格 d:**每個 d 各開一個新畫面實例**,呼叫公開的 `screen._state.move_unit(u, d)`,
     然後拿真實 `screen._guess_delta_for_cell(v, c)`(v 為有連線單位、c 為其候選格)與 B 鏡像在同站位的值**逐格比對**。
     它證明「鏡像在非開場站位上與真實畫面函式同值」(涵蓋單位位置改變)。只用公開 API 寫狀態,不改 `src/`,腳本在 `prototypes/` 內。
     **未涵蓋:陣亡單位**(公開 API 製造擊殺的路徑未查證)——它靠第 0 節 3 的程式閱讀(`units_of()` 排除陣亡),**不靠實測**,標「未查證」。
  3. **調校值對拍**:v4 用 `BattleState.create(rows, roster)`(預設 `TuningKnobs`),真實畫面用場內載入的調校。B 的 log 須印 `TUNING`(欄位同 A 的 TUNING 行),
     並與 A 的 `run_output_1.txt` TUNING 行**逐值相同**(目前 A 為 `3/-1/-1/2/0`,phi 範圍 `-4..12`)。不同 ⇒ 停止。
- **會/不會被「重建」的狀態**:B 不重建任何東西,是在 v4 真實跑到該回合時**當場讀取**,所以陣亡、已移動、HP 都是 v4 自己的真實狀態,沒有重建誤差。
  好感度答案只看站位+連線+調校(第 0 節 3),HP 與旗標不改變答案——**這是讀程式的結論,由對拍 2 部分實測。**
- **不採用的替代路線(記錄理由)**:①把站位寫進真實 `BattleScreen._state` 的私有欄位——寫私有狀態,且對錯誤站位沒有防護;
  ②把 v4 整局重播到真實畫面(重播所有攻擊與擊殺)——工作量大,且重播本身可能與 v4 分岔。**兩者都不需改 `src/`,選鏡像是因為它風險最低。**

### 判讀規則(看數據前定死;「→」後為唯一允許的結論)

|---|---|

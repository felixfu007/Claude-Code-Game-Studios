## 0. 先講三個會影響實作的發現

1. **實際綁定與既有提示列字串完全一致,沒有對不上的鍵**(逐項對過 `project.godot`):確認 = Enter / A(另有 Space、小鍵盤 Enter 同效,**刻意不寫**,避免提示列變長);取消 = Esc / B;開收手牌 = C / X;跳目標 = Tab / RB(上一個 = Shift+Tab / LB,**刻意不寫**);選單 = M / Start;結束單位 = Q / Back。手把按鈕編號對 Godot 慣例(4=Back、6=Start、10=RB、2=X)已核。
2. 🔴 **`FINISHED` 狀態下 `BattleScreen._input()` 第一行就 `return`**(`battle_screen.gd` 的 `_input` 開頭 `phase() == FINISHED` 即返回),所以**這個畫面本身沒有任何鍵會作用**。工單草稿寫「FINISHED 只顯示確認/離開」,但**確認在 FINISHED 沒有作用**,照寫等於再說一次謊。離開靠的是選單(`battle_menu.gd` 有「回主選單/離開遊戲」),但**選單在 FINISHED 能不能開,我沒讀到證據**。見第 4 節題目 1。
3. **滑鼠已有打牌/確認接線**(2026-10-28 管理者試玩回饋第 4 點取代了舊註解):選牌/棄牌時左鍵點牌 = 確認、選目標時左鍵點格 = 確認、確認面板上左鍵點面板內 = 確認、右鍵 = 取消。所以滑鼠欄在手牌/選目標/確認面板三態都**有**可用操作,不能只寫「無」。
   另外底部有**兩顆有字的按鈕「手牌 %d/%d」「選單」**(`battle.hud.hand_button`、`battle.hud.menu_button`),滑鼠玩家本來就看得到,所以滑鼠欄**不重複寫「手牌」「選單」段**,省寬度。

**為什麼新增第 9 種 `FORCED_DISCARD`,不併入 `HAND_OPEN`**:既有字串 `battle.hand_bar.forced_discard`「手牌已滿，請選一張棄掉」說明此時**不能取消、不能收手牌**(`battle.menu.rejection_forced_discard`「請先完成棄牌」也佐證選單被拒開)。若併入 `HAND_OPEN` 就會顯示「取消 Esc」「收手牌 C」——**教玩家按一個不會作用的鍵**,與 N6 同一類說謊。`BattleController.has_pending_discard()` 已有現成判斷可映射。

**其他逐項理由**:
- **`NO_SELECTION` 不含「取消」「結束單位」「跳目標」**:沒選單位時這三個沒有對象。工單草稿 AC2 表把「取消、結束單位」列在 `NO_SELECTION`/`UNIT_SELECTED` 共用;**我認為 `NO_SELECTION` 不該有,請 lead-programmer 實測確認這兩鍵在未選取時確實無作用**(我讀碼只看到入口,沒追到每個分支)。若實測有作用,再依實測補回。動詞用「選取」而非「確認」:此時按確認是「選這個單位」。
- **`UNIT_SELECTED` 的「取消」排第 3**:呼應 M2 建議(取消優先於選單、手牌)。「結束單位」排在取消之後、手牌之前:每個單位每回合都要用。
- **`CARD_TARGET` 以「請選擇目標」開頭,取消排第 2**:M4 的缺口就是「沒人說現在要選目標」;此段無鍵名、短,不佔寬度。**滑鼠欄無「移動」「跳目標」**:游標隨滑鼠走、點格即確認。
- **`CARD_CONFIRM` 滑鼠欄「確認 左鍵」**:實作上只有點在面板矩形內才算(`CardConfirmPanel.panel_rect`),點面板外**不會**確認。字句不用再加「點面板」(太長),但 AC 應含一條「面板外左鍵不確認」的既有行為不得被提示列改變——這屬現有行為,提示字句不擴寫。
- **`MENU_OPEN` 滑鼠欄**:我**未驗證**選單列是否支援滑鼠點選與右鍵關閉(讀到的 `battle_menu.gd` 片段只涉及文案)。**請實作者在落字前實測**;若選單不吃滑鼠,滑鼠欄改為「關閉 選單鈕」之類並回報我。
- **`ENEMY_PHASE`**:敵方行動中選單可開(`REASON_NOT_PLAYER_TURN` 證明選單此時會開、只是「結束回合」列被停用),故保留選單段。**絕不含**:移動、確認、取消、手牌、結束單位、跳目標(滑鼠欄因此只剩一句狀態)。
- **鍵盤欄「結束單位 Q」**:本案「結束單位」對滑鼠**沒有已知操作**(兩顆按鈕是手牌與選單),所以滑鼠欄不列。**請實作者回報滑鼠是否有結束單位的辦法**(選單內、或行動完自動結束皆可);若確實沒有,滑鼠玩家的單位行動結束路徑是設計缺口,不屬本單,但要登記。

## 4. 需管理者(或先由 lead-programmer 實測)決定的題目

### 題目 1:戰鬥結束(勝/敗)後,提示列該寫什麼?—— 取決於「結束後玩家怎麼離開」

**白話**:勝利/戰敗畫面出來後,`BattleScreen` 自己不再接收任何按鍵。工單原寫「顯示確認/離開」,但**按確認沒有任何作用**,提示列若寫了就是假的。真正能離開的路徑是開選單選「回主選單」——我**讀不到「選單在結束後還開得了」的證據**。需要先查一件事再選:

- **前置查證(lead-programmer,一個動作)**:戰鬥結束後按 M / Start / 點「選單」鈕,選單會不會開?
- **選項 A(若選單開得了,我推薦)**:鍵盤「選單 M」、手把「選單 Start」、滑鼠「選單 點按鈕」。優點:提示列說的是真的,也補上 N6「勝敗畫面無下一步」。缺點:玩家要多一步(開選單再選回主選單);「戰役完成」畫面也是此路。
- **選項 B(若選單開不了)**:提示列在 FINISHED 顯示空白。優點:不說謊。缺點:玩家看不到任何下一步,且其實**沒有下一步**——這是流程缺口(只能關視窗),應另開工單,不屬本單。
- **選項 C**:另開一張小工單讓結束畫面接收「確認 = 回主選單」,提示列寫「離開 Enter / A / 左鍵」(即工單草稿原意)。優點:最直觀。缺點:動 `BattleScreen` 輸入、等於新增功能,需 game-designer/管理者同意,超出本單範圍。
- **我的建議**:先查,再選 A;查不到選單就走 B 並另登記缺口。**在此題決定前,實作者對 `FINISHED` 只做「回傳非空」以外的內容會失去依據——建議本單先以選項 A 的字串實作,查證不符就停下回報。**

### 其他題目:無需管理者決定,但有三項請實作者先實測、不符回報
1. `NO_SELECTION` 下「取消」「結束單位」是否真的無作用(第 1 節)。
2. `MENU_OPEN` 是否吃滑鼠點選與右鍵關閉。
3. 滑鼠是否有「結束單位」的路徑。

## 7. FINISHED 重判(2026-11-13)

> **取代**第 0 節第 2 點、第 1 節表中第 9 列、第 3 節 `FINISHED` 列、第 4 節題目 1 的結論。上列原文保留作紀錄。

**查證(我自己 grep,不採信轉述)**:`battle_screen.gd` 的 `_on_battle_ended()` 與 `_on_result_display_finished()` 證實 game-designer 的結論。
- 結果文字出現後,啟動一顆 3 秒子 Timer(`RESULT_DISPLAY_SECONDS = 3.0`),時間到自動分流:勝且非最後一場 → 有支援對話進對話、無則直接下一場;戰役完成 / 戰役戰敗 / 無戰役 → 回標題;教學場 → 下一場教學、重打或進戰役第 1 場。
- 該常數註解明寫「選固定秒數而非等玩家按鍵」,且 `_input()` 在 `FINISHED` 直接返回。**結果畫面沒有任何玩家可按的鍵、沒有重試或離開按鈕。**
- 所以第 4 節題目 1 的前提(「離開靠選單」)作廢,選項 A/C 都不需要;「還需要選單路徑嗎」= **不需要**。

**重判結論:`FINISHED` 提示列顯示【空白】(三種裝置皆然)。**
- 理由一:沒有任何可按的鍵,寫鍵名就是說謊(正是 N6 的病)。
- 理由二:046 會在結果文字加「稍後自動進入下一場」這類下一步行;提示列再說一次是同一件事講兩遍,而且兩處措辭會漂移。**下一步資訊只放一處(結果文字)**,提示列不碰。
- 理由三:結果遮罩已壓暗整個畫面,空白提示列不會讓人誤以為壞掉。

**對實作的影響(須改回第 1、6 節)**:
1. `segments_for(FINISHED, 任一裝置)` 回傳**空陣列**;提示列文字為空字串(隱藏或留空由 art-director/實作者依既有版面決定,不得塞佔位字)。
2. AC1/AC2 的防空洞「6(實為 9)狀態 × 3 裝置都非空」**改為「除 `FINISHED` 外都非空」**,並**另加一條斷言 `FINISHED` 三裝置都【為空】**(否則「FINISHED 又被填回移動…確認」會綠)。仍須保留「至少兩個狀態回傳不同」。
3. 不為 `FINISHED` 新增任何 `battle.hud.hint.*` 字串;第 2 節 41 個字串數不變。

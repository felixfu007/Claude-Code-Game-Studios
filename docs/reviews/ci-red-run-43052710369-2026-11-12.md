## 6. 處理建議(只寫建議,不改檔)

選項 A:**維持現狀 + 寫下辨識與重跑規則**(見第 7 節)。
- 優點:零改動,不碰 CI 閘門定義。
- 缺點:約每 5 次推送會有一次紅燈,每次都要人判讀;`test-results` check 會永久卡在 `in_progress`(見下)。
- 推薦度:短期可行。

選項 B:**加 `concurrency` 群組**。
- 不推薦。時間戳記顯示 reporter 沒有重疊,加 concurrency 不會消除 404;而 `cancel-in-progress` 在 main 上會取消仍在跑的綠燈 run,反而丟失證據。

選項 C:**讓 reporter 失敗不再直接判紅**(例:對 gdUnit4 步驟加 `continue-on-error`,另加一個我們自己的步驟讀 `reports/` 的 XML,由測試結果決定紅或綠)。
- 優點:reporter 的非關鍵錯誤不再造成假紅,閘門仍以測試結果為準。
- 缺點:這改變了「測試失敗即擋」的閘門實作方式,必須寫成新的 gate 規則並經審核;實作細節要確認 XML 解析不會變成新的假綠燈來源(本專案已登記多種假綠燈形狀)。
- 推薦度:中期推薦,但須經管理者/technical-director 核准,不是 devops 單方決定。

選項 D:**對 reporter 步驟加一次自動重跑**(例:失敗後僅重跑 publish 步驟)。
- 缺點:gdUnit4-action 的 reporter 步驟是 action 內部的,我們的 workflow 無法只重跑它;只能重跑整個 job,會重跑測試約 90 秒。
- 推薦度:低。

另有一個需要注意的副作用(與選項無關):**`d716293` 與 `098180d` 各留下一個永遠 `in_progress` 的 `test-results` check run。** 目前 `main` 沒有 branch protection(API 回 404 "Branch not protected"),也沒有 ruleset,所以不會擋合併。但若日後設為 required check,這些卡住的 check 會擋住新提交。這一點需要在啟用 branch protection 之前處理。

## 7. 「紅燈但測試全過」的快速辨識方式

下次看到紅燈,依序做以下三步(都是只讀,不需要 log 文字搜尋):

1. 看失敗的 job 與步驟:
   `gh api repos/felixfu007/Claude-Code-Game-Studios/actions/runs/<id>/jobs --jq '.jobs[] | select(.conclusion=="failure") | .id'`
2. 看 annotation 有沒有 `update-a-check-run` 的 HttpError(這是 reporter-only 紅燈的特徵):
   `gh api repos/felixfu007/Claude-Code-Game-Studios/check-runs/<job-id>/annotations --jq '.[] | select(.annotation_level=="failure") | .message'`
3. 看測試段自己的結果(這段在 log 前段,不會被截斷):
   `gh run view <id> --log | sed 's/\x1b\[[0-9;]*m//g' | grep -E "Overall Summary|Exit code"`
   若 `Overall Summary` 顯示 0 failures、`Exit code: 0`,而第 2 步有 `update-a-check-run` 的 HttpError,即為 reporter-only 紅燈。

判讀規則:
- reporter-only 紅燈:**重跑一次**(`gh run rerun <id> --failed` 或推一個空提交),若綠燈即記為「reporter 瞬間 404」並在本檔補一行。若連續兩次都紅,升級處理(可能是 GitHub 端持續性問題)。
- 若 `Overall Summary` 有 failures 或 `Exit code` 不是 0/101,那是真的測試問題,照常處理,不適用本規則。
- 若 `Overall Summary` 完全沒有出現,先看 exit code 與 log 尾端是否有 `Parse Error` / `Abnormal exit`(見 `.claude/docs/coding-standards.md` 的 exit code 105 段),不要 grep 到空結果就判斷為通過。

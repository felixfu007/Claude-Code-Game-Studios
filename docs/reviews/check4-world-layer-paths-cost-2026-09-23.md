## 2. 逐題回答

### Q1(核心):「檢查退化成廢話」風險 —— 兩個方向都要評,結果不對稱

**路①會不會退化成「不可能失敗」?—— 會,而且已被引擎實測命中,但風險可控,條件是規則要多寫一段目前完全沒寫的東西。**

引用 `prototypes/godot-specialist-check4-subviewport-readback-2026-09-23/run_output_windowed.txt`:
```
CHECK4 [Q3A-native-scale1 (structural tautology check, expect 0 by construction)] = 0 / 129600
```
`_scale=1` 時方塊退化成單一像素,「方塊內每個像素等於左上角像素」對 1×1 恆真 —— 這是**結構性保證**,不是巧合,README 自己這樣寫:「這正是派工單擔心的『不可能失敗的檢查』那個形狀,已於本次確認為真」。

但同一份 README 也證明偵測力可以保住:
```
CHECK4-REGION [Q3B-GOOD-integer-scale-3.0-aligned] = 0 / 16
CHECK4-REGION [Q3B-BAD-nonint-scale-3.3-aligned] = 21 / 25
```
條件是呼叫端傳入的 `_scale` 必須是「這段世界層內容自己應有的整數縮放倍率」,**不是** 1,也**不是**容器/視窗的整數放大倍率(現行 2、4、5、8……對原生緩衝區讀法沒有意義)。

**這正是風險落腳的地方**:規則現在對「呼叫端怎麼選 `_scale`」**一個字都沒寫**。README 原話:
> 「Check4 的呼叫端需要知道『這一段測的是什麼』才能選對 `_scale` 值 —— 不能再像現行容器版那樣,全螢幕一個 `_scale` 打天下。」

寫得出這一段規則嗎?——**寫得出「不准選 1」「不准沿用容器倍率」這種否定式禁令,但寫不出一條放諸四海皆準的正面選值公式**,因為 Q4 已指出:世界層內容裡「大多數(棋盤格、單位精靈)理論上是 1:1 繪製、只有少數動畫/特效元素才有自己的縮放」——也就是說「正確的 `_scale`」是**逐段內容各自不同**的判斷,規則能做到的頂多是「呼叫端必須明確聲明自己在測哪一段、那一段的設計縮放倍率是多少」這種**紀律要求**,不是一條可以自動驗證「你選對了嗎」的機制。**與本專案其餘同類規則一樣,遵守與否會是不可觀測的**——這本身不是阻擋路①的理由(專案已有多條這種規則),但代表路①不會讓「退化成廢話」風險降為零,只會降為「跟規則說了但沒人擋」的同一種舊風險形狀。

**路②會不會退化成「不可能通過」?—— 這是派工單指名「目前沒有人評估過」的方向,答案是:目前的數字支持不出一個非任意的門檻,而不是「必然失敗」。**

引用 `prototypes/godot-specialist-u013-worldlayer-attribution-2026-09-23/run_output_windowed.txt`:
```
CHECK4 [BASELINE-whole-window] = 4601 / 129600            (≈ 3.55%)
CHECK4-EXCL [EXCL-3-HUD-rects] = 1109 / 112490             (≈ 0.99%)
CHECK4-EXCL [EXCL-4-rects (3 HUD + HandBar)] = 478 / 108134 (≈ 0.44%)
WITHIN [WITHIN HandBar.slot_bar_rect] = 631 / 4356          (≈ 14.5%)
```
若路②的寫法是「承認在量 UI 層,訂一個門檻」,問題不是「一定過不了」——排除已知 UI 矩形後違規率可以壓到 0.44%~0.99% 這個量級,不是天文數字。**真正的問題是這個 0.44% 殘值目前無人能解釋成因**(同份 README:「478 目前無人能解釋成因」「兩支探針的 baseline 相差 38 …成因同樣無人知道」)。**在殘值成因不明的情況下,任何非零門檻(0.5%?1%?)都只能是拍腦袋數字,沒有證據基礎** —— 這正是派工單擔心的「憑空捏一個數字」,而不是「必然全紅」。若門檻設得比殘值寬(例如 2%),則檢查形同虛設(容得下未知成因的殘值,也容得下真正的世界層縮放缺陷,只要它不太離譜);若設得比殘值窄,則需要先解掉那 478 與那 38 的成因,而這兩件事都不在本次任務範圍內、也沒有人排它。

**兩者的方向性差異(這是最值得管理者知道的一點)**:路①的「退化成重言式」風險是**已證實存在、且已證實可以透過參數選擇避開**(有明確的 0 vs 21/25 對照組);路②的「退化成任意門檻」風險是**尚未證實能避開**——目前沒有任何一組已排除的量測讀出「0」或者一個可以解釋的乾淨基線,殘值一直存在。就「能不能寫出一條不是拍腦袋的規則」而言,路①目前手上有一個可操作但不完整的答案(禁用 `_scale=1`、不用容器倍率),路②目前手上**沒有**任何候選門檻的證據基礎。

### Q2:三處原文的實際改動量

**路①**:
- Category A 段改動量最大——現有段落用「裁容器矩形/裁棋盤區域」的框架描述方法(「Restricted to the board region」),且引用的示範數字(`0/66300`、`splash 2265`)是舊方法量出來的,路①改成「讀原生緩衝區」後,方法敘述與示範數字都需要換掉或另外補充說明兩者不是同一件事;還需要新增「`_scale` 不得為 1、不得沿用容器倍率」與「物件在原生座標系裡的位置需對齊所選 `_scale`」兩條新約束(見 Q5)。
- Category B、C 兩段只寫「same carve-out as Category A」,改動量較小——主要是把「world layer only」指向新的操作型定義(原生緩衝區讀取),同一組 `_scale` 選值與對齊約束會透過「same carve-out」的措辭自動繼承,不需要在 B、C 段落逐字重寫一次。
- 三處 📌 指向的兩則「前提查證」小節:兩則現有文字皆以「本條目不修改 Check 4 的判準…是下一次的管理者裁決」收尾——若走路①,這兩則需要補一句指向新方法生效,但兩則本身記載的「478 無法歸因」「baseline 差 38」這兩個開放項**依然存在**,路①不會替這兩個數字提供解釋,只是把它們與「新方法下還要不要管」脫鉤。

**路②**:
- Category A 段改動性質不同——不是換一種「裁切方法」,而是整段的**存在理由**要改寫。現有段落的邏輯是「量到 world layer 才有意義,UI 層量了會判反,所以限縮範圍」;路②要改成「這個檢查結構上量到的就是全畫面內容(含 UI),所以不再限縮範圍,改訂門檻」——這等於拿掉「限縮範圍」這個框架本身,換成「承認量測範圍、訂門檻容忍」的框架,是兩種不同的規則寫法,不是同一段落換幾個字。
- Category B、C 兩段:這兩段目前各自已經因為「Check 3 對它們的形狀judge backwards」而各自寫了一套替代檢查(B 用邊角遮罩覆蓋檢查、C 用結構差異/正向存在檢查)——路②等於要再疊加第三種「這個類別專屬的 Check 4 門檻」,兩段各自需要新增一段解釋為什麼 Check 4 在這個類別下的正確使用方式是門檻而非豁免。
- 兩則「前提查證」小節:路②不能只改 Check 4 條文本身——這兩則小節目前登記的正是「world layer only」這行字與實際量到的東西不符,一旦條文本身改寫成承認量 UI 層,這兩則小節的**開場前提**(「三處豁免共用的同一條前提」)就不再適用,需要整段改寫或退休,而不只是補一句話。

### Q3:追溯適用 —— 兩條路對既有證據的實際影響不對稱(已用原始檔案查證,非推論)

管理者已裁決「只往後生效,不重做」(`production/session-state/active.md`:「二 | 只往後生效,不重做 —— 既有 U-007 / U-011 / U-013 三批畫面證據的追溯適用」),本檔不重提這個裁決。以下只回答:三條路裡有沒有哪一條會讓**既有證據的書面結論**在新定義下變成錯的(即使不用重做工作,結論本身是否站得住)。

**已用原始檔案核對,不是猜測**:

`production/qa/evidence/story-u011-hand-bar-evidence.md`:
> 「依 `.claude/docs/coding-standards.md` 截圖規則第 4 點與 EPIC.md 陷阱十四:該點逐字警告只量世界層,對介面層文字/元件量測會判反方向 … **Z1 全部落在介面層**,第 4 點對本畫面不成立,本次證據不套用該項。」

`production/qa/evidence/battle-menu-layout-evidence.md`:
> 「本 story 的截圖規則只套用第 1/2/3/5 點,不套用第 4 點(… 理由:**本畫面全部在介面層**,一般中文字型抗鋸齒文字在真實畫面產生的網格違規比啟動畫面還多,第 4 點的判準對它是反的)。」

**兩者用的都是同一套邏輯**:「這張圖沒有世界層內容 → Check 4 不適用 → 明講並跳過」。這是現行規則(三處「world layer only」)明文允許、甚至要求的行為(「If the screen has no world layer at all, say so explicitly」)。

- **路①**:不影響。路①改的是「有世界層內容時怎麼量」,對「完全沒有世界層內容 → 跳過」這個分支的判準(有沒有世界層)不變。U-007、U-011 的既有結論在路①下**依然成立**——它們宣稱的是「這張圖沒有世界層」,不是「世界層量出來是乾淨的」,兩件事路①都沒有動。
- **路②**:**有實質衝突**。路②的方向是「承認 Check 4 實際在量 UI 層,別再談『世界層』這個概念,改訂門檻」——一旦「world layer only,沒有就跳過」這個豁免框架本身被拿掉,U-007、U-011 引用來跳過 Check 4 的**規則依據字面上就不再存在**。這不代表兩者的實際版面有問題(U-007 的模態框、U-011 的手牌列裁圖都已由人工複核判定正確),但代表:**兩份已核准證據裡「不套用第 4 點」這句話所引用的規則原文,在路②之後將不再是規則說了什麼**——下一個對照這兩份證據與規則文字的人會發現兩者對不上,而管理者的「不重做」裁決管的是「不必重跑量測」,沒有處理「書面依據字面消失」這件事本身要不要一併登記或補一句銜接說明。
- **路③**:不影響,維持現狀,U-007、U-011 的引用原文不變。

**結論**:路②是三條裡唯一一條會讓既有證據的**書面論證依據**(不是結論本身、不是版面正確性)出現追溯性斷裂的路。這是管理者需要知道的新資訊——它不要求重做,但若選路②,U-007/U-011 這兩份文件裡「引用規則跳過 Check 4」的那句話會變成一句指向已不存在寫法的引用,需要在收尾時決定要不要處理這個斷裂(哪怕只是「刻意登記為已知的追溯性文字失準,不回頭改」)。

### Q4:路③(維持現狀)的持續成本

**下一個讀到那三處豁免的人會做什麼錯誤動作**:對一張新的 Category A 全畫面截圖(例如未來 U-014/U-015 若涉及戰鬥畫面世界層),照現行條文字面操作 = 「裁到世界層矩形」;在目前的畫面配置下(`WorldViewportContainer` 滿版,`position=(0,0) size=(960,540)`,`run_output_windowed.txt` 的 `SANITY` 行已實測)這等於裁到整張視窗,量出的數字會混入 UI 疊加內容。**現行條文本身沒有任何字眼提示這件事**——三處條文原文完整讀過(見 Q2 引用),只講「裁到世界層」「棋盤區域訊號是乾淨的」,不講「容器可能滿版導致裁切失效」。

**兩則登記小節擋不擋得住**:擋得住*細心到會主動搜尋「world layer only 這行字還有沒有別的說明」*的人(三處條文各自帶 📌 指標指向兩則小節),但擋不住兩種人:

2. **就算讀了兩則小節的人**——兩則小節的結論句都明講「本條目只登記事實」「是下一次的管理者裁決,不是本條目的職權」,**沒有提供任何可執行的替代做法**。一個讀完兩則小節的人得到的訊息是「這裡有問題,而且我不能自己決定怎麼修」,對「那我這次量測到底該怎麼做」沒有答案——除非他們自己重新跑一次歸因探針(這次花了兩輪 `godot-specialist` 探針才做到),沒有人會期待每一個新故事的實作者都重跑一次這種調查。

### Q5:格線對齊問題 —— 對路①是阻擋項還是小注意事項

**已知事實(不外推)**:Check 4 的方塊格線是從影像原點 `(0,0)` 起算的絕對格線,不是相對於被測物件自己邊界的格線。實測(`run_output_windowed.txt` Q3):精靈縮放乾淨(`scale=3.0`)但位置在 `(4,4)`(非 3 的倍數)時被誤判 `16/16` 全違規;移到 `(3,3)`(對齊)後正確判 `0/16`。

**我的判斷(附推理過程,供管理者核對,不是既定結論)**:

這個問題**不會阻擋路①最主要的用途**,原因是路①目前唯二兩種用途裡,較大宗的那種根本不需要用到會撞上對齊問題的那個計算路徑:
- 用途一(容器級:「原生緩衝區有沒有整體被非整數放大」)——Q3A 已證這在 `_scale=1` 下是結構性重言式,恆為 0,**不依賴任何物件位置**,對齊問題無從發生,因為根本沒有格線比對這回事(1×1 方塊必然自己等於自己)。
- 用途二(世界層內部元件自己的縮放,如 Tween 動畫、卡牌翻面):**這才是對齊問題真正會發作的地方**——而且發作方向是**假陽性**(乾淨的縮放因為位置沒對齊而被判違規),不是假陰性。這比「檢查測不出真缺陷」更麻煩,因為假陽性會讓人去修一段本來沒問題的程式碼(本專案已有 U-013 那次 194 違規差點被 `art-director` 拿去改 `board_view.gd` 的實例作為前車之鑒)。

**是否阻擋,取決於一件沒人查過的事**:真實世界層內容(棋盤格 32×32、單位精靈)在原生座標系裡的實際擺放位置,是不是天生對齊到「該元件自己應有的縮放倍率」的整數倍。README 誠實承認沒查過。我**傾向認為**(非事實,是推理)風險可能沒有聽起來那麼高,因為 `technical-preferences.md` 記載本專案棋盤單格是 32×32、立繪 128×128 這種偏好 2 的冪次的資產尺寸慣例,若擺放同樣落在這類格線上,常見的小整數縮放倍率(2、3、4)對齊的機率不低——**但這只是推理,不是驗證,不能拿來當作「路①沒事」的依據**。

**結論**:我判斷這是**路①「用途二」這條窄用途的阻擋項,不是整條路①的阻擋項**——因為用途一(結構性重言式)本來就不需要對齊,而用途二本來就是路①相對於「什麼都不做」唯一多出來的偵測力(見 Q1)。若對齊問題在真實內容上成立(未驗證),路①能提供的「額外偵測力」這個賣點會被同等數量的假陽性抵銷,只是形式從「檢查漏掉真缺陷」變成「檢查誤咬乾淨程式碼」——兩者對這個專案而言,依 `coding-standards.md` 記載的既有教訓(U-013 194 違規差點誤導 `art-director`),**後者已經發生過一次,不是假設性風險**。

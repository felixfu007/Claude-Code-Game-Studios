> 委託:管理者 2026-11-05「請創意總監查並給選項(推薦)」。問題由 `qa-lead` 發現、協調者已核程式。

## 一、問題(白話)

每一對有關係的角色,其實有**兩件不同的事**:

| | 是什麼 | 會不會因為走一步而改變 |
|---|---|---|
| **關係本身**(好感/惡感) | 這兩人合得來還是合不來 | 不會(只隨劇情、支援對話、卡牌改變) |
| **目前的效果**(+ / − / 0) | 依他們現在的距離,這條線此刻是加成、懲罰還是沒作用 | 會,每走一步都可能變 |

距離 → 效果的對照(來源:`src/gameplay/affinity/affinity_rules.gd` 與 `assets/data/tuning/tuning_knobs.txt`;
設計權威是 `design/gdd/affinity-position-chain.md` 的 AC-R3):

| | 相鄰(距 1) | 距 2 | 太遠(距 ≥3) |
|---|---|---|---|
| 好感 | **+3** | 0 | **−1** |
| 惡感 | **−1** | 0 | **+2** |

戰鬥畫面目前**只畫第二件事**:
- 棋盤連線顏色由 `src/ui/battle/battle_screen.gd` 的 `line_tone_for()` 決定,輸入是 `AffinityLineStatus.State`,
  而該列舉只有 `POSITIVE / NEGATIVE / NEUTRAL`,由**目前的數值正負**分類(`affinity_line_status.gd` 的 `_classify()`)。
- 關係圖迷你地圖 `src/ui/battle/relation_minimap.gd` 同樣依 `AffinityLineStatus.State` 畫。
- 程式裡**確實有**「關係本身」這份資料(`AffinityLink.Polarity`,`battle_screen.gd` 開場種子那段有讀它),只是**沒有任何畫面用它**。

**玩家會遇到什麼**:
- 一條紅色「−」線:可能是「好感的兩人離太遠」(該**靠近**),也可能是「惡感的兩人靠太近」(該**拉開**)。兩者該做的事**正好相反**。
- 一條灰色「0」線(距離 2):好感與惡感**看起來完全一樣**;往前走一步會變成 +3 還是 −1,畫面上**完全無從得知**。

📌 **精確說法(避免誇大)**:懂規則的人,在線**不是灰色**時,其實能從「顏色 + 兩人的距離」反推關係本身
(紅色+相鄰=惡感,紅色+太遠=好感)。**真正光看畫面無解的只有灰線(距離 2)**;
但對新手而言,「看顏色 + 數格子 + 心裡查表反推」這件事本身就是負擔 —— 這正是測驗一要量的東西。

## 二、這是故意的還是漏掉的?(查證結果)

**結論:漏掉的。** 沒有任何文件裁決「不顯示極性」或「讓玩家自行觀察/從對話得知」;反而有三處明文**要求**顯示。

### 2.1 明文要求顯示極性的地方

1. **`design/gdd/game-concept.md`「心流狀態設計」節,「跨棋子比較能力的過載約束」條(ux-designer 第四輪,2026-07-29)**,逐字:
   > 全圖檢視模式**僅顯示好感度極性與強度**,不得同時顯示即時聯動加成/懲罰預覽——加成/懲罰預覽僅在單選聚焦模式下呈現
   
   🔴 這條說的是:關係圖(全圖)該顯示的正是「關係本身」,而且**明文不該**顯示「目前效果」。
   **現在的迷你地圖恰好做成了反過來。**
2. **同節「回饋清晰度」條**:戰鬥介面要能「事前判讀加成/懲罰」;同節「色盲友善原則」條寫「**正/負好感連線**不得僅靠色彩區分」—— 把連線本身稱作「正/負好感連線」,即以極性命名。
3. **支柱二(`game-concept.md`「遊戲支柱」節)**:「角色間的好感度系統必須永遠是**清楚可見**、可操作的空間戰術要素」。
   **支柱一**:「每一步行動的後果都必須能被玩家推算出來」,設計測試選「保持完全資訊透明的計算」。

### 2.2 漏掉是怎麼發生的(兩個軸在規格裡被寫成同一個詞)

`design/ux/relation-minimap.md`:
- 第 3 節「詳情區」要求列「對象名 + **極性文字** + 強度數字」—— 這是「關係本身」。
- 第 4 節表格卻把「正向 / 負向 / **中立/未生效**」放在同一欄,並寫「與棋盤線的對應:同一對角色的同一極性,語彙一致(棋盤用 `LineTone.POSITIVE/NEGATIVE/MUTED`)」;
  AC-3 要求「地圖上的極性與棋盤線的 `LineTone` 逐對一致」。
- 但 `LineTone` 來自「目前效果」。**規格把「極性」這個詞套在「目前效果」上**,實作者照 AC-3 做,就做成了現在的樣子。
  第 7 節的極性詞「正向/負向/**中立**」也是同一個混淆的痕跡 —— 關係本身沒有「中立」這一種。

所以這不是實作者偷工,是**規格把兩個軸寫成同一個詞**,而且 AC-3 把錯的那一軸鎖死了。

### 2.3 查了、沒找到「故意不顯示」的地方

- `design/gdd/affinity-position-chain.md`:「UI Requirements」節要求游標格顯示 Φ 與逐條貢獻、無關係線者要明示「不適用」、夾限要明示 —— **沒有任何一條說不顯示極性**,也沒說要顯示。它只管數值,不管極性呈現。
- `design/ux/tactical-combat-screen.md`、`design/ux/interaction-patterns.md`:查不到相關裁決。
- `docs/reviews/`:查不到相關裁決(命中「極性」的檔皆與本題無關,或為本檔)。

### 2.4 一個相近、但**不是**同一件事的刻意設計(要分清楚)

`design/quick-specs/tutorial-level.md` 與 `design/gdd/vertical-slice-level-01.md` 驗收第 3 條(「玩家自發歸因」)
刻意**不在教學裡說出「因為好感度」這個因果**,目的是測新玩家會不會自己把站位歸因到「感情好/不好」。
- 這是**不講解因果**,不是**不顯示極性**;但若選項用「好感/惡感」**文字標籤**標在棋盤上,等於把答案直接寫在畫面上,
  **會污染那個探針**。下面選項設計已避開這點(用線型,不用字)。
- ⚠️ **未查證**:該探針目前是否仍要執行、或已執行完畢。若已不需要,此顧慮消失。

### 2.5 劇情/支援對話有沒有在戰前告訴玩家?

**沒有、也來不及。** `design/quick-specs/support-conversation-system.md` 第 2 節:支援對話**全部掛在關卡與關卡之間**,共 3 段
(`design/narrative/support-conversations-script.md`:SC-01 第 1 場**之後**甲×乙正向、SC-02 第 2 場之後甲×丙負向、SC-03 第 3 場之後乙×丁正向)。
- 第 1 場開打前,玩家**沒有任何對話**可得知誰跟誰合不來。
- 對話傳達的是「這次關係變好/變冷」的**方向**,不是一張「目前誰跟誰是什麼關係」的表;而關係圖本來就是設計來當那張表的。
- 結論:劇情可以**補強**記憶,但不能**取代**畫面顯示。

## 三、對照遊戲支柱

| 支柱 | 顯示極性 | 不顯示(現狀) |
|---|---|---|
| 一 精準可預判 | ✅ 「走過去會變好還是變壞」可直接推算 | ❌ 灰線時無法推算;其他時候要心算反推 |
| 二 關係即戰場、**清楚可見** | ✅ 玩家看得到「關係」,不只是「數字」 | ⚠️ 玩家看到的是加減分,看不到「人」 |
| 三 確定性代價 | 中性 | ⚠️ 玩家會把「猜錯」體驗成運氣不好 —— 系統其實沒有隨機,但**感覺上**像有,這正是支柱三要避免的感受 |
| 四 羈絆是雙面刃 | ✅ 「惡感的人拉開反而 +2」只有在玩家知道他們是惡感時,才會被體驗成「雙面刃」 | ❌ 玩家只會覺得「這條線有時紅有時綠」 |

📌 **賣點的核心句**(`game-concept.md`「獨特賣點」與支柱二):本作的差異化在於「**關係**決定站位」。
現狀讓玩家只看到「**數字**決定站位」—— 剛好是驗收第 3 條(自發歸因)要避免的結果:
玩家會說「這樣站傷害比較高」,而不是「因為他們感情不好,我才把他們拉開」。**方向上,顯示極性符合賣點。**

## 四、選項

> 共同前提:**不論選哪一個,「目前效果」都繼續顯示**(那是移動當下最需要的資訊)。差別只在「關係本身」要不要畫、畫在哪裡。

### 選項甲:維持現狀

- **做什麼**:不改。
- 優點:零工作量;畫面不增加任何資訊。
- 缺點:與 `game-concept.md` 的明文要求(全圖顯示極性與強度)不符;灰線時新手完全猜不到;玩家容易把關係當成「會變色的加分線」而不是「人際關係」。
- 對測驗一:**最不利**。新手在灰線與「紅線該靠近還是拉開」的情況會系統性猜錯,量到的會是「畫面沒給資訊」而不是「玩家懂不懂系統」—— 測驗結果會**量錯東西**。
- 工作量:無。

### 選項乙:關係圖改顯示「關係本身」,棋盤不動

- **做什麼**:迷你地圖改成照 `game-concept.md` 的原意:線表示**好感/惡感**(例:好感實線、惡感鋸齒線),詳情區列「對象 + 好感/惡感 + 強度」;
  棋盤上的線維持顯示目前效果。
- 優點:完全照概念文件原裁決;改動集中在一個畫面;棋盤不變,不增加棋盤上的視覺負擔。
- 缺點:玩家要**打開關係圖**才看得到 —— 在棋盤上移動棋子時,答案不在眼前;手把玩家要多按一個鍵切換。新手不一定會想到去開。
- 對測驗一:**中等改善**。會開圖的人能答對;不開圖的人仍會在灰線猜錯。
- 工作量:**小~中**。另需修改 `design/ux/relation-minimap.md` 第 4 節表格與 AC-3(既有檔,要另行核准)。

### 選項丙(推薦):兩個軸各用一種畫法 —— 線的「形狀」表示關係,線的「顏色」表示目前效果;棋盤與關係圖一致

- **做什麼**:
  - 棋盤連線:**形狀**表示關係本身(例:好感 = 實線、惡感 = 鋸齒/波浪線),**顏色**沿用現在的綠/紅/灰表示目前效果。
  - 關係圖:同一套畫法,詳情區列「對象 + 好感/惡感 + 目前效果與強度」。
  - 灰線(距離 2)時,形狀仍在 —— 玩家一眼就知道「往前一步會變好(實線)還是變壞(鋸齒)」。
- 優點:
  - 一眼同時看到兩件事,不必切畫面、不必心算反推;**手把與滑鼠一樣好用**。
  - 不寫任何「好感/惡感」**文字**在棋盤上 → 不會直接把答案講出來,**對「自發歸因」探針的污染最小**(玩家仍需自己理解「鋸齒線的兩人合不來」)。
  - 色盲友善規則本來就要求「不得只靠顏色」—— 形狀這個通道**本來就得加**,本案只是讓它承載有意義的資訊,而不是重複顏色已經講過的事。
- 缺點:
  - 棋盤上每條線多一層含義;需要教學讓玩家知道「形狀 = 關係、顏色 = 現在」。教學排序(`game-concept.md` 五層揭露順序)要確認放在哪一層。
  - 鋸齒線在 480×270 的像素畫面上能否清楚辨識,要美術實畫驗證(**未驗證**)。
  - 現行 `relation-minimap.md` 第 4 節是用線型表示「正/負/中立效果」,本案會把線型改拿去表示關係 —— 該規格要改(既有檔,要另行核准)。
- 對測驗一:**改善最大**。畫面上就有判斷所需的全部資訊,測驗量到的才是「玩家懂不懂系統」。
- 工作量:**中**(棋盤繪製、關係圖、規格修訂、美術驗證、教學提示一句)。

### 選項丁:只補最小洞 —— 只在灰線(距離 2)上標出關係本身

- **做什麼**:其他線照舊;只有灰色的線改用兩種不同的灰線樣式(好感/惡感各一種)。
- 優點:精準補上「光看畫面真的無解」的那一種情況;工作量最小。
- 缺點:**同一個樣式在不同顏色下意義不一致**(只有灰線才帶關係資訊),玩家很難建立一致的心智模型;
  紅線「該靠近還是該拉開」仍要靠距離心算反推;不符合概念文件「全圖顯示極性」的要求,關係圖仍是反的。
- 對測驗一:**小幅改善**,只救灰線那一類。
- 工作量:**小**。

## 五、推薦

**推薦選項丙。** 理由:

1. **它是規格原意,不是新增功能。** `game-concept.md` 要求全圖顯示極性、要求連線不得只靠顏色區分;
   現狀是規格用詞混淆造成的偏移(見 2.2)。修回來是還債,不是加範圍。
2. **它直接服務賣點。** 本作要玩家想的是「這兩人合不來,我把他們拉開」;只顯示加減分,玩家想的會是「這格分數比較高」。
   後者是任何數值戰棋都有的體驗,前者才是我們的差異化(支柱二)。
3. **它讓支柱四被感受到。** 「惡感的人拉開反而有加成」是本作最有趣的反直覺規則;玩家必須**知道他們是惡感**,這條規則才會被體驗成「雙面刃」,而不是「線的顏色會亂變」。
4. **它對探針最溫和。** 用形狀而不用文字,不會在畫面上直接寫出「因為感情不好」,保留玩家自己歸因的空間。
5. **選項乙的根本問題是「答案不在眼前」。** 戰棋玩家在移動棋子的那一刻做決定;把關鍵資訊放在另一個要按鍵打開的畫面,實務上大多數新手不會開
   (這是 `game-concept.md`「漸進揭露方案需重新設計」條已指出的同一類風險:把負擔轉到玩家的短期記憶)。

**我接受的代價**:棋盤上多一層視覺語言,需要一句教學與一次美術驗證。若美術驗證發現 480×270 下鋸齒線辨識不清,
**退而求其次選選項乙**(資訊至少在關係圖上是對的),**不建議退到丁**(會建立不一致的視覺語言,之後更難改)。

**這是您的決定** —— 若您認為棋盤已經太擠、寧可讓玩家多按一個鍵,選項乙是合理的保守選擇。

**我們怎麼知道選對了**(驗證標準):
- 協議 1 電腦量測的「光看畫面無法決定」比例,在**戰鬥中段**局面也應為 0%(本案上線後,灰線也帶關係資訊)。
- 新手測驗一裡,「灰線」與「紅線該靠近或拉開」這兩類情況的答對率,不應明顯低於其他情況。
- 賽後訪談(驗收第 3 條),玩家能說出「他們合不來所以分開站」這類話。

## 六、要不要等「戰鬥中段」量測結果再定

**建議:方向現在就定,只有「排在什麼時候做」等中段結果。**

- 開場 0% 的數字**不能**拿來說「沒問題」:
  1. 該 README(`prototypes/protocol1-computer-baseline-2026-11-05/README.md`「觀察」節)自己寫明:開場佈陣下所有連線的距離**都不是 2**,所以符號剛好能唯一對應關係(**作者標為推測、未逐局面檢查**)。也就是說,唯一真正無解的灰線情況,在開場樣本裡**根本沒出現**。
  2. 電腦的「看畫面」讀者(P2)**完全懂規則**,會自動用「顏色 + 距離」反推。新手不會。電腦 0% 是「資訊理論上推得出來」,不是「新手看得出來」。
- 判斷「該不該顯示極性」的依據是**支柱與概念文件的明文要求**(見二、三),這不會因量測數字而改變。
- 中段數字會影響的是**急迫程度**:
  - 若中段「無法決定」比例明顯高(例如兩成以上):應排在**真人測驗一之前**完成,否則測驗會量到畫面的缺口而不是玩家的理解。
  - 若中段仍接近 0%:可排在第 4 階段真人測驗之前任一時點,不必插隊。
- ⚠️ 不論中段結果如何,關係圖顯示的是「目前效果」而非概念文件要求的「極性與強度」,這一項本身就是規格偏離,**不依賴量測結果**。

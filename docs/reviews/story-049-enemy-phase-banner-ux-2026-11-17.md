# story-049 敵方回合橫幅 UX 決定(2026-11-17)

> 撰寫者:ux-designer。**這是建議,不是裁決** —— 標「建議」處需管理者選,標「已查證」處附指令/檔案。
> 顏色由 art-director 另決,本文不涉及。
> 查證標記:**已查證** = 本次實際讀檔;**推算** = 由已查證的常數算出,未跑引擎;**未驗證** = 沒查或沒跑。

## 0. 一句話結論

橫幅放在**棋盤上緣的空帶、窗口水平置中、與左上「回合狀態」同一列**(矩形函式新增於 `HudLayout`)。
因為它**整個在 13×6 棋盤之外**,所以不論敵兵在哪個時間點、走到哪一格,**結構上不可能蓋到任何格**,
不必針對「起始格」或「移動中」分別檢查。文字沿用現有用語「敵方行動」,約 1.3 秒、只做透明度淡入淡出,
不新增「減少動態」設定(專案目前沒有),但設計成日後加設定不必重做。

## 1. 位置

### 1.1 「不蓋敵兵」要針對哪個時間點 —— 我的判斷:全程,而且不是靠避開敵兵,是靠避開整個棋盤

- 敵方回合中敵兵會移動(已查證:`battle_screen.gd` 的 `_end_faction_phase_pressed()` 迴圈逐步 `step_enemy_phase()`,
  再 `_play_enemy_moves_cell_by_cell()` 逐格畫過去,每格 `ENEMY_MOVE_CELL_SECONDS = 0.12`、每步停 `ENEMY_STEP_PAUSE_SECONDS = 0.3`)。
  所以「起始格」只是橫幅出現那一刻的快照;橫幅持續期間敵兵會經過路徑上任何格。
  只避開起始格 = 重蹈昨天 story-048 的覆轍(固定位置避開了當下的東西,卻沒涵蓋會變的東西)。
- 起始格資料(已查證,`assets/data/units/{vs01..vs05,tut01..tut04}_roster.txt` 的 ENEMY 列,欄位 start_x,start_y):

  | 關 | 敵兵起始格 (x,y) |
  |---|---|
  | vs01 | (10,0) (11,1) (9,4) (7,5) (11,5) |
  | vs02 | (8,1) (12,0) (12,5) (11,3) (12,2) |
  | vs03 | (7,2) (8,1) (9,5) (8,4) (7,3) |
  | vs04 | (8,2) (12,0) (11,4) (11,3) (12,2) |
  | vs05 | (8,1) (9,2) (10,2) (9,3) (8,4) |
  | tut01 / 02 / 03 / 04 | (12,3) / (10,2) / (9,3) / (9,1)(9,4) |

  敵兵遍布第 0~5 列(vs01 的 (10,0)、vs02/vs04 的 (12,0) 就在最上列)。**任何畫在棋盤內的橫幅都會蓋到某關某時刻的敵兵。**
- **判準(建議寫進 AC2):橫幅矩形與「整個棋盤矩形(13×6 格的聯集,逐格取 `HudLayout.cell_window_rect`)」不相交。**
  這比「不涵蓋任何敵方單位格」強,因此自動涵蓋所有時間點與所有關卡,測試也不必枚舉敵兵位置。
  (工單 AC2 的「不涵蓋任何敵方單位格」仍成立,是它的子集。)

### 1.2 為什麼棋盤外有空間(與「四周零邊區」的關係)

`technical-preferences.md` 的「零邊區」指**世界層 480×270 填滿視窗**(1080p/4K)。但**棋盤本身 416×192 在世界層內再縮進**:
`BoardCoords.BOARD_ORIGIN = (32, 39)`、13×6 格、每格 32(已查證,`src/ui/battle/board_coords.gd`)。
所以棋盤上下各有 39N 像素(N = `WorldLayout.compute_scale`)的世界層空帶,左右各 32N。
橫幅疊在這條**世界層之上、棋盤之外**的空帶,不違反「介面疊在棋盤上方」的約束(它仍是疊在畫面上的介面),也沒壓到棋盤格。

### 1.3 建議矩形(新函式 `HudLayout.enemy_phase_banner_rect(window_size)`,單一出處,N 一律經 `font_size`)

- 高 = `font_size × LABEL_HEIGHT_MULTIPLIER(1.5)`,與 `status_label_rect` 同高同頂(`y = safe_rect.top`)。
- 寬 = `font_size × 8`(4 個全形字 + 左右各 2 字寬留白);水平置中於 `safe_rect`。
- 字級 = `font_size`(11×N,整數倍,點陣字不糊;960×540 為 22px)。

數值(已查證常數 + **推算**,未跑引擎):

| 視窗 | N | 橫幅 y 範圍 | 棋盤頂 (39N+世界層上邊距) | 橫幅 x 範圍 |
|---|---|---|---|---|
| 960×540 | 2 | 27 ~ 60 | 78 | 392 ~ 568 |
| 1920×1080 | 4 | 54 ~ 120 | 156 | 784 ~ 1136 |
| 2560×1440 | 5 | 72 ~ 154.5 | 240 | ~1096 ~ 1464 |
| 3840×2160 | 8 | 108 ~ 240 | 312 | 1568 ~ 2272 |

一般式(**推算**):橫幅底 = `0.05H + 16.5N`;棋盤頂 = `(H−270N)/2 + 39N`。
不等式 橫幅底 ≤ 棋盤頂 ⇔ `H ≥ 250N`,而 `compute_scale` 保證 `N ≤ H/270`(已查證 `world_layout.gd:58-61`),**恆成立**。
(960×540 空帶最窄:橫幅底 60、棋盤頂 78,餘 18px。)

## 2. 時長與淡入淡出

建議(全為具名常數):

| 常數 | 值 | 理由 |
|---|---|---|
| `BANNER_FADE_IN_SECONDS` | 0.15 | 夠短,不拖慢第一個敵兵動作的可讀性 |
| `BANNER_HOLD_SECONDS` | 0.9 | 4 字短句,閱讀所需遠小於此;與每步 0.3s 的敵方節奏同量級 |
| `BANNER_FADE_OUT_SECONDS` | 0.25 | 比淡入稍長,消失較不突兀 |
| 合計 | 約 1.3s | 在「幾百毫秒」之上限邊緣,仍不致遮蔽(它不在棋盤上) |

- **不阻擋、不延遲**:橫幅動畫與敵方播放並行,**不得為了等橫幅而延後第一個 `step_enemy_phase()`**(工單 AC4)。
  `mouse_filter = IGNORE`。
- **階段先結束就立刻隱藏**:若 `ENEMY_ACTING` 在 1.3s 內結束(敵兵少/不動),**橫幅在離開該階段那一幀硬關,不淡出**。
  理由:淡出殘留進玩家回合,會讓畫面同時寫著「敵方行動」與玩家可操作,等於說謊(同 story-045 要消除的問題)。
  勝敗(`FINISHED`)同理。AC 建議加「離開 ENEMY_ACTING 後橫幅不可見」。
- 敵方回合實際長度:每步 ≥0.3s,**步數與總長未實測**(未驗證);1.3s 是否通常短於整個敵方回合,實作者可量一次,但不影響上述規則。

### 「任意輸入即消失」在實務上代表什麼

- 已查證:`BattleScreen._input()` 在 `phase == ENEMY_ACTING` 時對鍵盤/手把事件直接 return(約 2691),滑鼠移動也凍結(約 2583~2611)。
  **敵方回合本就不接受任何操作,所以「輸入即消失」在現行行為下永遠不會被觸發。** 實務上橫幅的消失條件只有:時間到,或階段結束。
- 我的建議有兩條路,**請管理者選**:
  - **(A)建議:改寫 AC2 為「時間到或階段結束即消失;橫幅不接收也不吞任何輸入」**,不實作輸入關閉。理由:輸入關閉是死碼,且要為它在被凍結的輸入路徑上開洞(違反昨日修補「敵方回合凍結輸入」的原意)。
  - (B)保留字面:在凍結守衛之前加一行「ENEMY_ACTING 下任意鍵/點擊 → 隱藏橫幅」。符合 `ui-code.md`「動畫可跳過」的字面,成本低,但是**對一個 1.3 秒、非阻擋的指示條而言,可跳過的實益近乎零**;且 `battle_screen.gd` 該段(輸入分派)我沒完整讀,**未驗證**加這一行不會影響守衛語意。
  - 兩者都滿足「可跳過」的精神?(A)下橫幅對操作零影響、很快自己消失,我判斷符合 `ui-code.md` 的目的(玩家不會被動畫卡住),但字面上不是「可跳過」,請管理者知情選。

## 3. 文字

- 現有(已查證,`assets/data/locales/strings.csv`):
  - `battle.hud.faction_enemy` = 「敵方行動」(第 5 行);標題格式 `battle.hud.status_format` = 「第 %d 回合．%s」(第 2 行)→ 敵方回合標題實際顯示「第 N 回合．敵方行動」。
  - `battle.hud.hint.status.enemy_phase` = 「敵方行動中」(第 183 行,story-045 的提示列用句)。
- 三處文字都在講同一件事,用詞要統一。我的建議:
  - **橫幅 = 「敵方行動」**(與標題同詞,重用 `battle.hud.faction_enemy`,不新增列)。
  - 不用「敵方回合」:標題裡「回合」指整輪(「第 N 回合」),「敵方回合」會讓「回合」一詞兩義(整輪 vs 半輪)。
  - 不加回合數:標題已有,橫幅只負責「換手」這一個訊號。
  - 提示列「敵方行動中」(story-045)保留:橫幅是瞬間訊號,提示列是持續狀態,「中」字表示進行式,不重複造成矛盾。
- **選項,請管理者選**:(a)重用既有鍵(建議;不動 strings.csv、不動列數斷言,工單 Affected Files 裡 strings.csv 一項可省);
  (b)新增 `battle.hud.banner.enemy_phase` 同文字(日後想讓橫幅與標題分家時較方便,但今天是兩份同文字的複本,會漂移,並需同步列數測試)。
- 無色彩依賴:橫幅以文字承載意義,色彩僅為強化,符合「不單靠顏色」。不閃爍(只做單調透明度變化),無閃光警告問題。

## 4. 動態偏好(減少動態)

- 已查證:`ui-code.md` 規定「所有動畫須可跳過且尊重使用者動態/無障礙偏好」。
- 專案目前**沒有**這個設定:`src/core/settings/` 全目錄對 `motion|reduce|animation` 零命中;`src/ui/` 只命中滑鼠/手把的 `*Motion` 輸入事件;
  `GameSettings` 只有音量/靜音四個常數(`game_settings.gd`)。`design/ux/tactical-combat-screen.md`、`relation-minimap.md`、`support-conversation-screen.md` 都寫「若有則遵從,目前沒有」。
  設定畫面 `settings_screen.gd` 存在,但**我沒讀它的內容**(未驗證有無動態項)。
- 建議(請管理者選):
  - **(A)建議:本單不加設定,橫幅做成「只有透明度變化、沒有位移/縮放」,並把淡入淡出寫成純函式 `banner_alpha(elapsed)`,淡入/淡出秒數為常數。**
    日後加「減少動態」設定時,只需讓兩個淡化常數視為 0(瞬現瞬隱),不必重寫橫幅。純透明度變化也不屬於前庭不適的主要誘因(位移/縮放/閃爍才是);此判斷屬 UX 慣例,**未對本專案玩家測試**。
  - (B)本單連帶新增 `reduce_motion` 設定(動 `GameSettings`、設定檔編解碼、設定畫面、存檔格式)。這是跨系統契約變動,範圍遠大於橫幅,**不建議綁在 049**,另開工單,並一次回頭涵蓋既有的敵兵逐格動畫(`ENEMY_MOVE_CELL_SECONDS`)、手牌展開動畫、關係圖淡入淡出。
  - (C)讀作業系統的減少動態偏好:Godot 4.7.1 是否提供此 API **未驗證**,不採。
- 「有靜態終態」:即使橫幅被關掉,標題「敵方行動」+ 提示列「敵方行動中」+ 手牌變灰仍完整傳達狀態(對應 GDD「動畫類回饋須有靜態終態」)。橫幅是強化層,不是唯一載體。

## 5. 與 story-045 提示列 `ENEMY_PHASE` 的同步(AC3)

- 已查證:`battle_screen.gd` 約 2507-2508 的映射已寫 `Phase.ENEMY_ACTING → HintState.ENEMY_PHASE`;story-045 排在 049 之前(工單序列 043→045→046→048→049)。
- **無衝突**,前提是三者由**同一個階段值**驅動,不各自判斷:標題色、橫幅可見旗標、提示列狀態都從 `_controller.phase()` 映射,並在同一次 `_refresh_view()` 內更新。
- 需注意一個時序坑(推論,**未驗證**):橫幅的「淡入/淡出」是跨幀的,而 AC3 要求「同一次 `_refresh_view` 後一致」。
  建議把橫幅拆成兩個量:**「應顯示」旗標(離散,隨階段,同幀更新,供測試斷言)**與**透明度(連續,由計時驅動)**。AC3 只斷言前者。
- `phase_changed` 訊號目前只接 `_update_status_label()`(約 2195,已查證);橫幅的觸發點建議也掛在同一訊號或 `_refresh_view()`,**不要只掛在 `_end_faction_phase_pressed()`**——該函式是進入敵方回合的目前唯一入口,但(未驗證)日後若有別的入口(例如開場即敵方先手),橫幅會漏。
- 提示列文字(「敵方行動中」)與橫幅文字(「敵方行動」)不衝突,見第 3 節。

## 6. 「玩家回合開始」要不要也做橫幅(工單刻意不做)

- 不對稱的問題:玩家只在敵方回合收到強訊號,回到玩家回合時,變化靠「標題換回、手牌亮起、提示列換內容」這些**較弱**的訊號。
  戰棋中「輪到我了」是最需要被察覺的轉換之一(使用者可能在看別處),弱訊號可能被漏掉。**此為 UX 推論,未做玩家測試。**

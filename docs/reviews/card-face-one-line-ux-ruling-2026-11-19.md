## 一、放得下嗎 —— 放不下(算術推論,未驗證,需截圖)

**UX 規格的規定**(`card-rework-ui-2026-11-17.md` 1.3):Z3「不可打原因行」≤ 9 全形字、確認面板單行 ≤ 14 全形字;兩個上限皆自註「推估,未驗證」。規格**沒有**為 Z3 卡面文字行另訂字數 —— 這是規格缺口,不是實作者違規。但規格的退路寫明「超出時縮短文案,不加寬面板、不縮字級」。

**Z3(`hand_bar.gd`)**
- 寬度 = 卡寬 = `EXPANDED_SLOT_WIDTH_FPX_MULTIPLIER` 4.5 fpx;高度 `DETAIL_PANEL_HEIGHT_FPX_MULTIPLIER` 4.0 fpx。
- 卡面文字 Label:`autowrap_mode = AUTOWRAP_WORD_SMART`、錨點 0~0.5 高,**無 `clip_text`、無 `text_overrun`、Panel 未開 `clip_contents`**(grep 零命中)。字級 = fpx × 16/33。
- 以規格所述 1280×720 最小視窗 N=2、fpx=22 推估(`font_size()` 本體未讀):寬約 99 px、字約 11 px → **每行約 9 全形字**;卡面文字區高約 44 px → **約 3~4 行,約 27~36 字**。
- 新卡單行長度(未代入數字):card_11 約 45 字、card_13 約 70 字、card_19~22 約 60~70 字(渲染後數字再多幾字)。→ **5~8 行,遠超 3~4 行。**
- 失效形狀:Label 自動換行但不裁切 → 文字**向下溢出,蓋到 effect_label(0.5~0.75)與 reason_label(0.75~1.0)**。不可打原因行正是 UX 規格要求「不只靠顏色」的唯一文字通道,被蓋住即違反 AC3/AC-4。**不會報錯**,測試讀節點文字仍全綠(AC-14 人眼項才抓得到)。
- 另:舊卡 card_07(約 33 字)在這個框裡本來就已貼著上限,不是新問題但說明這框本來就小。

**確認面板(`card_confirm_panel.gd`)**
- 面板寬 24 fpx、高 22 fpx;標題 Label 用 `_build_label()`:`AUTOWRAP_WORD_SMART`、字級 = fpx、無截斷設定。
- N=2 推估:內容寬約 22.8 fpx → **每行約 22 全形字**,60~70 字的標題 = **3~4 行**,擠掉下方的代價/前後 HP 列(面板高度當初是照「五~六列各單行」估的,見檔內註解)。
- 45 字以下的卡(card_11/12/14~18)約 2 行,**放得下但標題變成一段說明文**;長卡(13、19~22)是否擠出面板底:**未驗證,需截圖**。
- 內容重複:面板下方已有「代價：…」專屬列(規格 1.2),單行文字裡的「代價：…；」是**第二份**,且兩份數字來源不同(文字表 vs 015 結果物件)—— 規格 AC-1 要求面板數字等於實際扣款,文字表那份**不受此約束**,日後兩者可能不一致。

**結論 1**:單行格式在 Z3 **放不下**(長卡溢出並蓋住不可打原因行),在確認面板**短卡勉強、長卡不確定**,且造成代價資訊重複。皆須 1280×720 截圖確認。

## 二、替代方案

| 案 | 做法 | 優 | 缺 | 動哪些檔(皆另開工單) |
|---|---|---|---|---|
| **A(推薦)** | 文字表改為**分欄**:`id,card_name,effect_line`(只放效果一句,**不放條件、不放代價**)。Z3 顯示 牌名 + 效果行;確認面板標題 = 牌名、風味列 = 效果行;代價/條件交給**既有**專屬列(代價列、不可打原因列) | 每欄長度可被規格約束(牌名 ≤ 4~5 字、效果行 ≤ 27 字);消除代價重複與數字不一致;牌名終於能獨立作標題;舊卡 `card_name` 留空即可相容 | 動解析器與兩個 UI;narrative 定稿要再裁一次(條件句需另處安置) | `card_text.gd`、`vs01/vs02_card_text.txt`、`hand_bar.gd`、`card_confirm_panel.gd`、`strings.csv`(若走本地化)、相關測試 |
| B | 文字表支援換行記號(如字面 `\n`),維持單欄 | 解析器改動最小;保留 narrative 多行原意 | **不解決 Z3 放不下**(行數照樣超);仍重複代價 | `card_text.gd` + 資料檔 |
| C | Z3 只顯示效果行,由 UI 在執行期用 `；` / `【】` 切字串 | 不改資料格式,最快 | UI 解析資料內的標點 = 把格式約定藏在渲染碼裡,narrative 一改標點就壞且不報錯;違反「UI 不擁有資料語意」精神 | `hand_bar.gd`、`card_confirm_panel.gd` |
| D | 加高/加寬 Z3 | 不動資料 | 規格明禁「不加寬面板」;Z3 在手牌上方,加高會壓棋盤(版面硬約束:不得依賴邊區);屬美術/版面裁決 | `hand_bar.gd` + art-director |

**短期止血(不需新工單即可決定)**:在 A 落地前,**合入 022 時資料可照舊單行,但須明載「Z3 長卡溢出為已知缺陷」**,不得標 UX AC 通過。若管理者要求合入即可用,最低成本是方案 C 暫行(僅取第一個 `；` 之前、去掉【】的部分顯示於 Z3),並明文登記為過渡。

**結論 2**:推薦 **A**;C 僅可作登記在案的過渡;B、D 不推薦。

## 三、【牌名】前綴與舊卡並存

- 舊卡(card_01~08 類)是純敘事一句(如 card_07「甲在乙耳邊說了句…」),新卡是「【牌名】+規則句」。同一手牌裡玩家會看到**兩種語氣、兩種資訊密度**:新卡 Z3 在講規則,舊卡在講故事、規則只靠效果摘要行。
- 可接受度:**短期可接受,長期不建議**。理由:① 新卡規則句與下方效果摘要行/代價列資訊重複,舊卡則不重複,玩家會形成「有些卡說明比較多」的落差,但不致誤導;② 最大風險不是落差本身,而是 `【】` 是**字面寫在資料裡的裝飾**,舊卡沒有,日後無法統一換樣式(例如牌名加粗/換色)。
- 解法同方案 A:牌名獨立欄,舊卡留空 → UI 對空牌名不顯示標題列,兩批卡在同一版面規則下共存,日後補舊卡牌名只改資料。
- ⚠️ 附帶發現(需查證):worktree 文字表**只有 card_11~22 共 12 列新卡 + card_07、card_08 兩列舊卡**,與「14 張新卡」「8 張舊卡」的說法對不上。可能是工單敘述、或有 2 列漏、或 card_09/10 另有出處 —— **未查,請實作者或協調者對 `vs02_cards.txt` 逐列核**。

**結論 3**:並存的落差短期可接受;前提是牌名改獨立欄(舊卡留空),不接受把 `【】` 當資料字面長期留著。

## 1. 量測儀器現況

### 1.1 現有腳本能輸出什麼(來源:`prototypes/autoplay-balance-2026-10-28/autoplay_v2.gd` 的 `_run`)

| 協議 2 需要 | 現況 | 依據 |
|---|---|---|
| 勝敗 | ✅ 有 | `_run` 印 `outcome=`,取自 `BattleLoop.run()` 回傳字典的 `"outcome"` |
| 回合數 | ✅ 有 | 同上 `"rounds"`;`aborted`/`abort_reason` 另存,上限 `MAX_ROUNDS := 30` |
| 陣亡數 | ⚠️ 間接 | `res["log"]` 內有 `"<code_name> is defeated"` 字串(`src/gameplay/battle/battle_loop.gd` 的 `run`);現腳本只取「第一個倒下者」(`first_down`),不計總數、不分敵我 |
| 重傷數 | ❌ 沒有 | 腳本只在結束時印每單位 `hp/hp_max`(`END players=...`),**沒有逐回合最低 HP**;且「重傷」在 `game-concept.md` 與 `design/gdd/` 全文**沒有定義**(`src/` 亦無對應概念,grep「重傷/wounded」零命中)。定義須由門檻提案決定(例:HP 曾低於 hp_max 某比例),儀器才能量 |

### 1.2 開/關好感度的開關在哪

- **開關 1(傷害 Φ)**:`autoplay_v2.gd` 的 `_run`:`use_phi = strat != "C_focus_phi0"`;關閉時傳給 `BattleLoop.new(...)` 的 `phi_provider` 為空 `Callable()`。引擎側接收點:`battle_loop.gd` 的 `_compute_phi`(provider 無效即回 0)。
- **開關 2(行為層)**:`_decide_cautious(..., prov)`:`prov == null` 為 B(固定策略),`prov != null` 為 C(集火 + `AffinityRules.bonus_for_at` 站位偏好)。
- 🔴 **程式碼層面發現,影響設計對照臂(讀碼所得,未跑)**:
  1. `C_focus_phi0` 在 `decide` 裡仍走 `strat.begins_with("C_")` → 傳入 `prov`,**站位偏好仍然讀好感度**;被關掉的只有傷害 Φ。所以「phi0」≠「忽視好感度佈局」,它回答的是「同樣站位下 Φ 有沒有用」,不是協議 2 問的「刻意忽視 vs 運用佈局」。
  2. `B_cautious_fixed` 的 `use_phi` 為真,即**引擎仍套用 Φ**,只是 AI 不看好感度選位。B 與 C 的差異同時包含「集火」與「好感度站位」兩件事 —— **混雜變因**:B→C 的任何差距不能全歸因於好感度。
  3. 因此協議 2 需要的「忽視臂 vs 運用臂」**現腳本沒有乾淨的一對**。需要新增一臂:「集火但站位完全不讀好感度」(對比 C),才能把好感度站位單獨隔離。
- 另:腳本遍歷 `campaign_sequence.txt` 全部 5 場(`_init` 的 `for r in rows`),協議 2 只要第 1 場;且 `BattleLoop` 路徑**沒有發卡牌流程**(腳本內無 card 相關程式碼),而真人遊玩可打出好感度卡改寫數值池 —— 兩者資訊面不同,結論只能叫「無卡牌條件下的站位效果」。

### 1.3 缺什麼(清單)
1. 逐回合最低 HP / 重傷計數(取決於「重傷」定義)。
2. 陣亡總數(我方)與陣亡回合。
3. 乾淨的「忽視好感度站位」對照臂(見 1.2-3)。
4. 只跑第 1 場的參數化入口與原始 log 檔輸出(現為 stdout,是否存檔靠人工導向)。
5. 回合數語意一致性:`BattleLoop` 的 `"rounds"` 與 UI `_order.round_number()`(`src/ui/battle/battle_screen.gd` 的狀態列)是否同一定義 —— **未逐行驗證**,人類與電腦指標要合併比較前須先確認。
6. 前置:game-concept 要求「陣亡對好感度網絡的處理規則」先定案並實作,才可測協議 2(同檔「前置條件」段)。**本文未查證現在是否已實作** —— 須先查再排期。

### 1.4 正式遊戲有沒有記錄機制
- `src/` 內檔案操作只有 `FileAccess.open(..., READ)`(`battle_screen.gd`、`support_conversation_screen.gd`),**沒有任何寫檔/遙測**。
- 唯一與量測相關的是 `src/ui/battle/effect_guess_tracker.gd`(`EffectGuessTracker`,**協議 1** 預判一致率),協議 2 沒有對應機制。
- 遊玩中狀態列顯示回合數(`battle_screen.gd`,`_status_label` 以 `_order.round_number()` 組字);結算畫面 `_on_battle_ended` 只顯示勝/敗文字,**是否顯示回合數本文未確認**。
- 結論:**人類試玩目前只能人工記錄**(見第 3 節)。若要自動記錄須新開一張 `src/` 工作單(屬 `lead-programmer` 範圍,需管理者核准),本文不代提。

## 2. 電腦對照的執行規格(門檻提交之後才可執行)

### 2.1 決定性問題
- 查證:`prototypes/autoplay-*/` 下全部 `.gd` 搜尋 `rng|randi|randf|RandomNumberGenerator|seed|shuffle` **零命中**;專案另有明文禁令 `rng_in_combat_settlement`(`.claude/docs/technical-preferences.md` 的「專案級身分/範圍裁決」)。故同一臂重跑**結果逐字相同**,「每臂跑 20 局」只會得到同一局 20 次,**不是 20 個樣本**。
- 規格:電腦對照**不宣稱統計樣本**。它每臂只產生**一個點**,其用途只是「機制上有沒有方向性」,不得拿來取代人類基準。
- 若仍要分布,樣本來源只能是**輸入變異**,且須事先寫死、不得事後挑:
  - (a) 每臂的策略參數變體(例:`_is_better_tile` 平手時的偏好順序、集火排序鍵),預先列表,每個變體 = 一個樣本;
  - (b) 起始站位排列變體 —— 這**改動關卡資料**,須 `level-designer` 同意並在提案裡登記,否則不做。
  變體數 N 與名單由門檻提案/本計畫鎖定時一併寫死;**中位數以變體為單位**,並註明「變體非獨立樣本」。

### 2.2 場次與臂
- 場次:**只第 1 場**(`assets/data/levels/vs01_terrain.txt`,序列表第 1 列,其四個資料檔以 `campaign_sequence.txt` 為準)。其餘 4 場不屬協議 2 範圍,不跑。
- 臂(至少三臂,同一張圖同一份名冊):
  1. 忽視臂:集火、站位不讀好感度、Φ 照引擎套用(新增,見 1.3-3);
  2. 運用臂:現 C(`C_focus_affinity`);
  3. 診斷臂(可選):現 `C_focus_phi0`,僅供判讀「是 Φ 還是站位」。
- 🔴 **前置可行性關**:協調者轉述「10/28 曾跑過一次對照,20 局全敗、無資訊量」(轉述,我未查證也未讀結果)。若某臂在 vs01 上不能勝,回合數**未定義**。事先寫死的處理:**回合數只在 VICTORY 局統計;敗局另列「敗」並計入勝率**;若兩臂皆無勝局,則電腦對照在該版本**不可判讀**,不得改用「敗在第幾回合」硬湊。是否調整 AI 或關卡使其可勝 = 門檻提案之外的新決定,先回報管理者。
- 敵我數值條件:`game-concept.md` 註明門檻是「對稱條件」取得的、之後須以劣勢條件(`enemy_advantage_pct` 起始 0.20)重驗。本計畫只量**當前 build 的設定**,build 的 commit hash 記入每筆原始 log;對稱條件是否要另跑一組,交門檻提案決定。

### 2.3 輸出與留存
- 新腳本放**新目錄** `prototypes/protocol2-measure-<日期>/`(含 README;沿 `autoplay_v2_copy.gd` 先例複製而非改舊檔,依 `.claude/rules/prototype-code.md` 不得動 `prototypes/` 以外檔案)。
- 每次執行存**原始 stdout 全文**於 `run_output_<臂>_<UTC時間>.txt`,另在檔首記:build commit hash、腳本 commit hash、引擎版本、指令。
- 驗收執行必須記錄引擎自身 `ENGINE EXIT`;**不得只 grep 結果行** —— 見 `.claude/docs/coding-standards.md` CI 節的 exit 105(收集階段炸掉時 `grep` 全空,看起來像乾淨)。腳本層同理:進程 exit 非 0 或輸出無 `RESULT` 行 = 該次作廢並如實登記,不是「0 局」。
- 儀器自檢(**可在門檻鎖定前做**,且不屬於看數據):只用 `assets/data/levels/test_fixture_terrain.txt` 夾具,驗證新增的最低 HP/陣亡計數會寫出、格式正確。**不得**在 vs01 上先跑臂對照來「試試看」。

## 3. 人類試玩的執行規格

### 3.1 現實限制(請管理者知情)
- 專案只有一位人類(管理者,非技術人員)。協議原文的「內部/設計者盲測」**嚴格說做不到盲**:他已知道遊戲賣點。再者協議「運用佈局的測試者」原文語意是另一批人;只有一人時,兩臂由**同一人**前後各跑,**不是 3~5 位新手**(那是協議 1 的校準要求,協議 2 原文只要求基準 + 運用者)。
- AI 代理**不能**代為遊玩正式 UI(無可行的前景操作路徑,且搶前景的自動化會打進管理者工作中的視窗 —— 見其記憶 `no_foreground_stealing_automation`)。故人類試玩 = 管理者本人手玩。
- 試玩須在**無人經過座位的時段**進行(管理者既有約束,記憶 `private_dev_at_work`:遊戲畫面不得出現在公司螢幕上)。

### 3.2 如何降低「不自覺利用好感度」
無法完全防止,下列是可操作的降低手段:
1. **機械式站位規則卡**(忽視臂):事前寫死一條與好感度無關的規則,如「每單位一律移到能攻擊且離敵最近的格,同分取編號小者」;試玩中不得開好感度關係視圖/連線 UI(若 UI 有此面板,忽視臂期間不打開,並於 log 勾選「未開啟」)。
2. **不打出好感度對話卡牌**(忽視臂):卡牌會改寫數值池,屬運用行為。
3. **順序保守原則**:同一人跑兩臂會有學習效應。**先跑運用臂、後跑忽視臂** —— 學習效益歸於基準,使「運用優於基準」更難成立,偏誤方向對假說不利、不會放水。兩臂之間至少隔一天,並記錄各臂重試次數。
4. 忽視臂勝出時(基準比運用還好)照樣記錄,**不得重跑**到「合理」為止。
5. 事後自陳一行:「有沒有哪一步其實是因為好感度而選的」—— 只作質性旁證,不修正數字。

### 3.3 記錄表(每一局一列,存 `production/qa/protocol2/human-log-<日期>.md`)
build commit hash;臂(運用/忽視);第幾次嘗試;**是否中途重來(重來原因)**;最終回合數(取自狀態列,結束前截一張圖存證);我方陣亡數與名單;各單位結束 HP;**是否曾低於重傷線**(線值由門檻提案給,試玩中需逐回合看血量,管理者若無法逐回合記,改為**每回合結束截圖**留證,事後由 qa-tester 讀圖補算);結果(勝/敗);好感度視圖是否開啟;卡牌是否打出。
**重來(退出重開)必須記錄,不得只記最後一次** —— 只留成功局會製造倖存者偏誤。

### 3.4 人力成本(接 `one-year-plan.md` 第九節「仍開啟」第 3 項)
至少 2 臂 × 每臂數局;每局時長待實測,建議先請管理者在**夾具關卡**熟悉記錄流程(不影響 vs01 盲度)。這是第 3 階段(2026-12-29 起)的實際人力,不是零成本。

2. 執行任何自動對戰並讀其輸出(含「只看有沒有跑起來」)—— 儀器自檢**限夾具關卡**(2.3)。
3. 人類試玩後,在門檻定案前口頭/文字轉述「這次大概幾回合」給門檻作者。
4. 在 vs01 上做任何「先跑跑看」的探索性對戰。
5. 已知既有污染(須誠實登記,不抹除):協調者已獲悉「10/28 一次對照 20 局全敗、無資訊量」。此為定性資訊、不含門檻方向,但屬**已揭露項**;門檻提案的作者(game-designer)是否也已看過結果,**我無法查證**,請門檻提案自述。

### 4.2 可查對的紀律(建議)
1. **鎖定提交**:門檻定案(含重傷定義、臂清單、變體 N、敗局處理規則、本計畫第 2/3 節的參數)以**單一提交** `H` 鎖定,該提交訊息寫明「門檻鎖定」。
2. **結果檔必須晚於 H**:所有新結果檔放 `production/qa/protocol2/` 與 `prototypes/protocol2-measure-*/`,**首次進版控的提交必須是 H 的後代**。查法(不會自我匹配,因指令寫在文件而查的是 git):
   - `git merge-base --is-ancestor <H> <結果檔首次提交>` 回傳 0 才合格;
   - `git log --diff-filter=A --format=%H%x09%cI -- <結果檔路徑>` 取首次提交。
3. **鎖定後不得修改**:鎖定檔(門檻提案、本計畫、腳本)在結果檔提交之前,`git log -- <檔>` 的最新提交必須是 H 或更早;事後要改 = 視為重新登記,舊結果作廢並於新提交說明。
4. **每臂每配置只跑一次**;重跑僅限「工具故障」,且須附引擎 exit code 與 log 尾段為證(見 2.3),原失敗 log 保留不刪。
5. **腳本也要先鎖**:新增的對戰/記錄腳本的提交須早於第一個結果檔,避免「看到結果再調 AI」。
6. 誰能先看:結果檔產生後,**先由 qa-lead 對照鎖定的門檻出判定**,再交管理者;任何人不得先口頭說「差不多會過」。
7. ⚠️ 與本專案同類規則一樣,**沒有任何自動檢查會攔以上規則** —— 它買到的是「下一個人有明文可查對」。可查項只有 4.2-2、4.2-3 兩條 git 指令。

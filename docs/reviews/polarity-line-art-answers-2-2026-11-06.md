## 先講一個會改變第 2、3 題前提的幾何事實

由常數推出(`BOARD_ORIGIN = (32, 39)`、`CELL_SIZE = 32`,格中心 = 格左上 + 16):
- **所有格中心座標都是整數**;兩格中心的中點 = 其中一格中心 + `16 × (整數, 整數)`,所以**中點座標永遠是整數,且落在以 16px 為間距的格點上**。
- 因此:(a) 第 3 題的「半像素」不是中點造成的,是 **7 是奇數**造成的(7×7 牌的幾何中心若貼齊整數座標,左上角會落在 x.5);(b) 第 2 題**不會有「很近但不重合」**,兩塊牌中心最近也相隔 16px(> 牌寬 7px),**只有「完全同一點」才會疊**。
- 前提:「兩單位不會站同一格」(我依一格一單位假設,**未讀棋盤佔位規則**)。

## 第 1 題:符號牌的層次

**讀到的層序**(`BoardView.tscn`,由下而上):`TerrainLayer` < `ImpassableTerrainLayer` < `MoveHighlightLayer` < `PiecesLayer` < `MoveUnreachableLayer` < **`AffinityLineLayer`** < `ThreatHighlightLayer` < `AttackHighlightLayer` < `AttackLosBlockedLayer` < `CardTargetHighlightLayer` < **`StatsLayer`** < `ActionFlagLayer` < `CursorSprite`。(與 story-002 轉述一致。)
- 所以線**已經畫在棋子之上**;會蓋住線的是威脅/攻擊/卡牌高亮(半透明填色)、HP 條與 HP 文字、行動旗標、游標。

**依常數推算與牌的實際衝突(未經樣張驗證)**,格內座標以格左上為 0:
- HP 條:x 6~26、y 26~29(寬 20、高 3、底距 3),**常駐**。
- HP 文字帶:y 1~11、全格寬,**只在 `show_hp_text` 時畫**。
- 橫向相鄰的線:中點在兩格交界、y = 格中心(16);牌佔 y 13~19 → **與 HP 條、HP 文字都不重疊**。
- 縱向相鄰的線:中點在上下兩格交界、x = 格中心;牌向下伸入下方那格的 y 0~3,**與下方那格的 HP 文字帶(y 1~11)重疊約 3 列** → 顯示 HP 文字時牌的符號會被蓋掉大半。
- 長距離的線:中點落在任意 16px 格點上,可能壓在別的單位的 HP 條或文字帶上,**要看樣張**。

**選項**

| | 做法 | 優點 | 缺點 |
|---|---|---|---|
| **A(推薦)** | 牌與線**同一層**(`AffinityLineLayer`),不動 `.tscn` | 零新節點、與線同生同滅(`_clear_children` 一次清乾淨)、AC-P3「0 效果不畫」自然成立;HP 數字(傷害預覽的唯一顯示處,見 `board_view.gd` 註解)**永遠優先** | 縱向相鄰 + HP 文字顯示時符號被蓋;游標/旗標/高亮也會蓋 |
| B | 新層放在 `StatsLayer` 之上 | 符號永不被遮 | **牌會蓋住 HP 文字**,傷害預覽是遊戲關鍵資訊,不可接受 |
| C | 新層放在 `CardTargetHighlightLayer` 與 `StatsLayer` 之間 | 不被半透明高亮染色,又不蓋 HP 文字 | 要動 `BoardView.tscn`(超出 story-002 的 Affected Files)、牌與線分兩層要同步清除、牌看起來「浮在高亮上而線在高亮下」 |

**結論**:**採 A;被遮住可以接受。** 理由是視覺階層:HP/傷害預覽 > 連線裝飾,而且被遮時**線本身(形狀 + 顏色)仍可見**,只是那一刻看不到效果符號;被遮的情境(顯示 HP 文字)多半是游標正停在單位上,資訊列另有好感度前後值(此為規格草稿 R3(c) 的說法,**我未驗證資訊列**)。
**升級條件**:若樣張 C/D 顯示半透明高亮把牌的符號染到看不清,才改採 C,屆時另行請示加層。**未經樣張驗證。**

## 第 2 題:兩條線中點重疊

**重疊只會發生在「中點完全同一點」**(見上方幾何事實);**同一點最多 2 對**(5 個單位,兩對不相交需 4 個單位,第三對還要再 2 個)。常見成因:一排 4 人等距(0-3 與 1-2)、2×2 方塊的兩條對角線(交在格角)——**不是罕見情況**。

**規則(可直接寫成程式,未經樣張驗證):**
1. 以「中點座標」分組(整數座標,用 `Vector2i` 當鍵,不用浮點比較)。
2. 組內只有 1 對 → 照常畫牌。
3. 組內 2 對、**效果符號相同**(同為 `+` 或同為 `−`)→ **只畫 1 塊牌**。
4. 組內 2 對、**符號不同(一正一負)** → 畫 2 塊牌**並排**:`+` 牌中心在 `M − (4, 0)`,`−` 牌中心在 `M + (4, 0)`(中心相距 8px,牌間留 1px 縫),**固定左正右負,不依線的方向**。
- 為何不依線方向偏移:共線(一排 4 人)時兩條線是同一條直線,沿線方向偏移與固定水平偏移等價;非共線時依方向偏移會讓兩牌在小夾角下重疊,規則變複雜。固定左右最簡單、可測。
- 為何不「後畫蓋前畫」:會讓一正一負疊成只剩一個符號,直接破壞 AC-P6。
- 為何不發明 `±` 第三符號:那是新增資訊語彙(玩家得多學一個符號),**屬設計決定,我不擅自加**;若管理者想要,可作選項,但不是我的推薦。
- **同一點上兩對「牌位置」取整**:各自依第 3 題規則用整數中心算左上角。

🔴 **順帶發現(不在你的 4 題內,但牽動 AC-P6)**:共線的兩對(一排 4 人的 0-3 與 1-2)**線段本身會重疊在同一批像素上**,先畫的線色會被後畫的蓋掉(一條是綠、一條是紅時,重疊段只看得到其中一色)。這不是牌的問題,我**沒有規則可以給**——需要先決定「重疊段誰在上」(例如固定由效果為負的在上、或按單位 id),**這是設計決定,請另行請示**。

**未經樣張驗證**;樣張 D 要加一張「2×2 方塊對角線」與「一排 4 人」。

## 第 3 題:7×7 牌中心落在半像素時的取整

**先更正前提**:中點本身永遠是整數(見上),**不存在「中點落在半像素」**;問題在 7 為奇數,牌的左上角 = 中點 − 3.5。

**規則(未經樣張驗證):全程整數運算,不用 `floor()` 對浮點取整。**
- 牌左上角 = `mid − Vector2i(3, 3)`;牌覆蓋像素 `mid−3 … mid+3`(共 7 格)。
- 符號圖元(5×5)左上角 = 牌左上角 + `(1, 1)`。
- 結果:牌的**中心像素是左上角落在 `mid` 的那一格**,即牌相對真實中點**偏右下 0.5px**。
- 取「右下」而非「左上」的理由:只是需要一個固定、可測的方向;對稱性上兩者等價。
- 🔴 **要看樣張決定是否反向**:1px 的 `Line2D` 中心落在整數座標(像素邊界)時,非反鋸齒下是畫在 `mid−1` 那列還是 `mid` 那列,我**無法確定**。若樣張 D 顯示線進入牌的位置偏離中央一格,把規則改成 `mid − Vector2i(4, 4)`(偏左上)。
- 關係圖(UI 層,座標為浮點、不在世界層整數格上):`牌左上 = (mid − 牌尺寸/2).round()`,同樣取整數。⚠️ **規格沒有規定關係圖牌的原生像素尺寸**(7×7 是世界層 480×270 的像素;介面層倍率為 `N` 時是否為 `7N`?),這是**未決項**,請協調者補問,我不在這裡硬定。

## 第 4 題:鋸齒邊界、Joint 與 Cap

**線太短的情況**
- **棋盤上不會發生**:兩單位的格中心距離最小 32px(相鄰格;斜向 ≈45.25px),依 `L/4` 得 n ≈ 8~11,遠大於 1。(依「一格一單位」假設,**未驗證**。)
- **段數規則寫死(取代上午的「最接近 L/4 的奇數」並補平手)**:`n = 2 × round((L/4 − 1) / 2) + 1`,**平手(L = 32 時 7 與 9 平手)取較大者(9)**,因為半週期 32/9 ≈ 3.56 比 32/7 ≈ 4.57 更接近 4;**n 最小 3,絕不可為 1**。
- **為何 n 不可為 1**:n=1 沒有內部折點,等於一條直線,與實線無法分辨,**違反 R1**。
- 若關係圖上某段 L 小到 n=3 時半週期 < 2px 以致糊成直線:**退回成「畫實線」是違規的**,應回報我(那表示面板太小,是版面問題不是畫法問題)。**未經樣張驗證**。

**頂點定義(補全規則,使中點永遠落在零偏移)**
- 折點 i = 0 … n,沿線位置 `L·i/n`;**i = 0 與 i = n 偏移為 0**,內部 i = 1 … n−1 偏移為 `(−1)^i × A`(垂直於線方向)。
- n 為奇數時,中間那一段連接符號相反的兩個折點,**線的正中點偏移恰為 0** → 符號牌壓在線的中線上,不會壓在齒尖。
- 所有折點座標取整數像素(`Vector2.round()`);45° 線取整後左右不對稱,**預期,未經樣張驗證**。

**Line2D 設定(未經樣張驗證;列舉名請 `godot-specialist` 核對)**

| 屬性 | 值 | 理由 |
|---|---|---|
| `joint_mode` | `Line2D.LINE_JOINT_SHARP` | 圓角(`ROUND`)會把鋸齒頂點磨圓;`BEVEL` 會把尖削平 |
| `sharp_limit` | 明寫 `2.0`(具名常數) | 尖角比 = 1/sin(內角/2);振幅 ±2、半週期 4 時轉折 ≈ 90°,比值 ≈ 1.41 < 2,不會退化;若樣張後改 ±3 / 5,內角 ≈ 79.6°,比值 ≈ 1.56 < 2 仍在限內;**內角 ≥ 60° 才保證不退化** |
| `begin_cap_mode` / `end_cap_mode` | `Line2D.LINE_CAP_NONE` | `ROUND` 在線端畫圓點、`BOX` 多伸半個線寬;端點本來就在棋子底下,不需要 |
| `antialiased` | `false`(沿用現行) | 避免色盤外邊緣像素 |
| 底襯 `Line2D` | 同上全部設定,僅 `width = 3`、顏色不變 | 與線身同組頂點,尖角比 3px 寬時尖端伸出約 2.1px,仍在可接受範圍,**未經樣張驗證** |

**風險**:`sharp_limit` 超過時 Godot 的退化行為(退成斜接削平)我沒在 4.7.1 驗證過;上表的數值刻意留在限內,以避開這個行為。

## 一行結論

1. **牌與線同層(`AffinityLineLayer`),被高亮/HP 文字/旗標/游標遮住可接受**;HP 數字優先;高亮染色若毀掉可讀性才升級成 C(加層)。(未經樣張驗證)
2. **只有「中點完全同點」才會疊(最多 2 對)**:同號只畫一塊、一正一負並排(`+` 左 `−` 右、中心各偏 ±4px);另發現共線線段像素重疊是設計決定,需請示。(未經樣張驗證)
3. **中點永遠是整數,半像素來自 7 為奇數**:牌左上 = `mid − (3,3)`,圖元左上 = 牌左上 + (1,1),全整數運算;若樣張顯示線偏心,改 `mid − (4,4)`。(未經樣張驗證)
4. **n 最小 3、絕不為 1(1 即實線,違反 R1)**,棋盤 L ≥ 32 不會發生;Joint = SHARP、`sharp_limit` 2.0、兩端 Cap = NONE、不反鋸齒,底襯同設定。(未經樣張驗證,列舉名待 `godot-specialist` 核對)

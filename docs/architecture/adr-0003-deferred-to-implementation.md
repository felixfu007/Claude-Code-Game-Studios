## 這份清單怎麼來的

2026-08-21 對存檔格式做了四件事,累積出 40 多項發現:

1. **四支引擎探針**(驗證那份文件依賴的引擎行為)—— 推翻 18 處寫法與三項說法
2. **一次修訂草案** —— 被兩道覆核判定不可寫入,6 項必修、約 15 項次要
3. **一個能真的跑起來的設計骨架** —— 7 項設計層問題、16 項「文件沒講但實作時非決定不可」
4. **一次跨兩個行程的實測** —— 關掉一項至今無人驗證的最壞情況

其中**會讓程式跑不起來或安靜寫壞存檔的**已納入本次修訂。**其餘即本清單。**

> **給未來讀者的提醒**:本清單裡沒有一項是「不重要」。它們是「**現在不修也不會讓文件無法被討論**」。
> 進入實作時請逐項處理,不要因為它們被歸為延後就當成已解決。

## 一、實作第一天就會撞到的(優先處理)

| # | 白話問題 | 技術細節 | 為何能延後 |
|---|---|---|---|
| D-1 | 驗證器如果綁在一個沒人保管的物件上,那個物件被回收後,**所有存檔都會被判定損毀** | 驗證器 `Callable` 不會讓它綁定的 `RefCounted` 續命;擁有者離開作用域後 `is_valid()` 為 `false`、`get_object()` 為 null,**但 `get_method()` 仍回傳方法名**(看起來還活著)。fail-closed 把「有人忘了留參照」放大成全面失敗 | 這是**誰保管驗證器實例**的問題,屬於程式結構決定,文件層只需說「呼叫前先檢查有效性」(本次已納入) |
| D-2 | 檢查一個訊號是否為空,不能用直覺的那個方法 | `Signal.is_null()` 在跨行程情況下回 `false`,但 `get_object()` 是 null、`connect()` 回 `ERR_UNCONFIGURED` | 寫入側閘門已拒絕此型別(本次已納入),所以只有處理**舊有損壞檔案**時才會遇到 |
| D-3 | 型別檢查的寫法讓讀檔慢了三成,而其中大部分不是必需的 | 500 筆記錄下:規格形狀 18–26 毫秒;精簡版(只回代碼、不組路徑字串)2.4–4.2 毫秒;實際編碼只佔 1.4–1.8 毫秒。**85% 的成本來自寫法,不是語意** | 純效能。建議實作:成功路徑走精簡版,偵測到失敗後再跑一次帶診斷版本(失敗是罕見路徑) |
| D-4 | 型別檢查對外公開時,**只能回報「有毒」,無法回報「毒在哪」** | `validate_payload_types()` 的簽章帶不出 `offending_path`,而結果物件規定要有這個欄位。遷移鏈重用它時只知有問題、不知位置 | 診斷品質問題,不影響正確性 |
| D-5 | 深度上限設 64 夠不夠,沒有依據 | 實測合法巢狀深度 256 可正常往返;真實資料約 4 層;引擎遞迴上限約 1024 框 | 64 遠高於實務需求。等有真實資料形狀再校準 |

## 二、文件沒講、實作時必須自己決定的(11 項)

**每一項都是那份文件的一個洞。** 骨架當下的決定記在括號裡,供實作參考,但**那不是文件的裁決**。

| # | 文件沒回答的問題 | 骨架當時怎麼決定 |
|---|---|---|
| D-6 | 編碼結果長度為零時,該回哪一種拒絕代碼? | 視為與「型別違規」不同的獨立情況 |
| D-7 | 目錄裡出現**重複的區塊名稱**怎麼辦? | 拒絕整份檔案 |
| D-8 | 語意驗證的結果型別只有名字、**沒有欄位定義** | 自行定義了最小欄位 |
| D-9 | 逐區塊檢查是「一個一個驗完就用」還是「全部先驗完才開始用」?**副作用:讀取因此不是全有全無** | 採交錯(驗一個用一個) |
| D-10 | 同一個區塊名稱被**登記兩次**驗證器怎麼辦? | 後者覆蓋前者 |
| D-11 | 取驗證器的函式回傳可能是空值,**呼叫端的義務沒寫** | 呼叫端一律先檢查 |
| D-12 | 每個區塊自己的版本號,由誰負責比對? | 骨架未實作,留給遷移文件 |
| D-13 | 外層信封出現**未知的額外欄位**怎麼辦?**副作用:存檔可夾帶任意資料而不被發現** | 忽略 |
| D-14 | 排序函式可不可以改動傳入的資料? | 不改動,回傳新陣列 |
| D-15 | 用 `StringName` 當鍵安不安全? | 實測 `has("k")` 與 `has(&"k")` 四種組合全部互通,故安全 |
| D-16 | 區塊清單的鍵集合**不被任何檢查碼涵蓋**,而且**不能**放進形狀檢查 —— 否則會提前攔下一個規格要求由檢查碼攔的情況。**兩者無法同時滿足,這是設計的真實張力** | 依規格,不放進形狀檢查 |

## 三、文件內部一致性(不影響程式行為)

| # | 內容 |
|---|---|
| D-17 | 「型別白名單不是靠維護清單實現,而是格式選擇的副產品」這句話與新增的檢查機制矛盾 —— 須拆成兩句(類別實例化仍是副產品;資料型別白名單是新增的維護義務) |
| D-18 | 消解某個舊有疑問的那段推導鏈斷了(它的前提是「不存在型別這個維度」,而現在存在) |
| D-19 | 某條需求的涵蓋理由部分為假(保護來自新增的檢查,不來自格式選擇) |
| D-20 | 效能章節完全沒提新增檢查的成本,而該節現行寫「可忽略」 |
| D-21 | 驗收條件沒有任何一條驗證新增的檢查機制 |
| D-22 | 驗證器契約只寫「值域」漏了「型別」,而唯一的實作早已是兩者都做 —— **定義通用契約的文件比它的實作弱** |
| D-23 | 讀取側的失敗回報方式與寫入側不對稱:三種不同失敗塌成同一個空值。而**同日另一份文件剛把這個形狀判定為必修並全數移除** |
| D-24 | 風險等級是否維持、以及「這次的錯不是引擎版本造成的、而是過期的舊版記憶」這件事,都該寫進文件 |
| D-25 | 幾處措辭與已死的交叉引用(某個括號裡的例子指向一個已關閉的項目) |

## 四、實作層陷阱(寫程式時要知道,文件不必寫)

| # | 內容 |
|---|---|
| D-26 | 列舉型別的欄位**不擋超出範圍的整數**。寫字面量 `1.7` 會被編譯器擋;寫 `7` 編譯通過並存進去;經過無型別變數傳入的小數會**靜默截斷**。「編譯期會擋」只對字面量成立 |
| D-27 | 結果物件的預設值等於「成功」—— 忘記賦值會被讀成成功。既有文件有同性質先例,故不改慣例,但須有呼叫端義務與測試 |
| D-28 | 結果物件的型別無法用一般方式辨識(它回報的是父類別名稱),診斷訊息不能依賴它 |
| D-29 | 結果物件本身**永遠不可放進存檔內容**(會被自家檢查拒絕) |
| D-30 | 檢查碼算失敗時若回傳空陣列,而比較用直接相等 → **兩邊都失敗時比較成立,檢查被靜默繞過**(本次已納入修正,此處記錄以免未來重犯) |

## 五、跨文件事項(範圍外,但不可靜默省略)

## 六、仍未查證的引擎行為(9 項)

| # | 內容 | 為何不阻擋 |
|---|---|---|
| D-33 | **發行版本(release build)的行為** —— 全部量測都在除錯版本下 | 與另兩份文件的同一項是同一個洞,**可一次關三份** |

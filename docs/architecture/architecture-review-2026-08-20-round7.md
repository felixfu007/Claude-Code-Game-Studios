## 四、ADR-0002 對抗性覆核:**不可進 `Accepted`**

2026-08-20 的 `/architecture-decision` session 把 ADR-0002 推到「最接近可核准」(BLOCKING 已關、核心結構已真機編譯驗證、24 項零缺口、`Depends On: None`、C1/C3 已關),並建議先跑第七輪再由使用者裁決。**本輪的答案是不行。**

**理由不是修訂做錯方向。** 包裝類別的選擇、兩條邊界規則的分工、`validate_semantics()` 改用 `typeof()` 內省 —— 這三段是這份 ADR 最紮實的部分,且「兩條規則不可互相代用」的推導鏈本輪覆核判定**正確關閉**(定義域不相交、任一方通過不蘊含另一方通過、VC #9 落實為兩個不可合併的測試)。

**理由是修訂在新增範圍宣告時,只稽核了自己剛寫的那兩個方法,沒有回頭稽核 ADR 既有的三個 `Variant` 公開入口。** 這正是第六輪專家要求的自問「這個修法會不會讓某個既有簽章、既有正交性宣告變得不成立」—— 答案是會,**第七次同一模式**。

### 必須先關的項目

| # | 內容 | 嚴重度 | 證據等級 |

### 探針推翻了 ADR-0002 的另一句宣稱(本輪最重要的新事實)

**R7-P1 · 高 · 已實測** —— 機制四步驟 4/5 的註解寫「`source`/`pair` 不在合法列舉值 → `INVALID_SOURCE`/`INVALID_PAIR`(**GDScript enum 本身型別化後這條理論上不可達**,但保留作為跨語言邊界輸入的防禦層)」。**實測直接證偽這句話**:

| 夾帶值 | `f(p: AffinityTypes.Pair)` |
|---|---|
| `-1`(合法 int / 非法 enum 序數) | **不中止,`p = -1` 原封不動傳入,零錯誤、零檢查** |
| `999`(同上) | **不中止,`p = 999` 原封不動傳入** |

enum 型別標註在這個邊界上**只抹平了 String 那一類**,對「合法 int 但非法序數」**完全沒有範圍檢查**。因此:

- **`INVALID_SOURCE`/`INVALID_PAIR` 不是「理論上不可達的防禦層」,而是唯一防線。** ADR 必須刪掉那句已被證偽的推論性描述,並明訂步驟 4/5 的**實際檢查手段** —— 探針 C 已確認 `AffinityTypes.Pair.values().has(int)` 可用,可作為序數合法性檢查的具體實作。
- **這同時收窄了本 ADR 型別安全論證的適用範圍**:「型別錯誤在呼叫端整段中止」對 enum 參數**只對 `String` 成立,對 `float`/`bool` 不成立**。這比 `XCHECK-4` 只驗 `m: float` 邊界所得的結論**範圍更窄**,不能沿用同一句「型別化參數安全」籠統套到 enum 參數上。

**R7-P2 · 中高 · 已實測(推論部分明確標示)** —— 一個此前無人提出的子問題:float(`3.7`→`3`)或 bool(`true`→`1`)若截斷後**剛好落在合法序數範圍內**,會**靜默通過任何值域檢查** —— 因為檢查看到的已經是「合法的 3」,**無從得知它原本是一個型別錯誤的浮點數**。這使 R7E-4 的失敗模式精確化為:不是「寫入被拒」也不是「函式中止」,而是**寫入成功、回傳 `NONE`、資料落在錯誤配對**,且**任何下游檢查都看不出異常**。

**R7-P3 · 中高 · 已實測** —— 機制八 `from_dict()`/`import_state()` 目前寫「先 `typeof()` 內省、後值域運算」,但**沒有涵蓋「型別合法的字串,卻不是任何 enum 成員名稱」這一類輸入** —— 而那正是存檔還原遇到打錯字或版本不相容時最可能出現的錯誤。實測顯示 `Pair[<不可信名稱>]` 遇非法名稱會**中止函式**,`validate_semantics()` 若直接用這個運算式做轉換,會在走到自己的拒絕碼邏輯**之前**就中止,契約承諾的結構化 `ImportResult` 永遠回不去。**正確寫法**:先做存在性檢查(`values().has()` / `keys().has()`)或改用已驗證會乾淨回傳 `null` 的 `find_key()`,**絕不對不可信字串裸用 `Pair[name]`**。

> 附帶觀察(與既有結論一致的獨立佐證):探針 A 的錯誤訊息把容器印成 `Dictionary[int, AffinityRecordList]` —— **enum 鍵在容器層被抹成 `int`**,這是 VR #2 結論在「缺鍵讀取」這條全新路徑上的再次確認。

### R7E-2 的修法必須二選一並明文寫下

機制二明文「首次對某配對寫入時才建立 `AffinityRecordList`」,而實測顯示缺鍵讀取**中止整個呼叫函式**、GDScript 無 try/catch、呼叫端拿不到任何可判斷的回傳值。因此**任何發生在寫入之前的讀取**(對尚無記錄的配對查詢 —— `n(p)=0`,GDD 明文要求處理的合法情境)若天真寫成 `_records[pair].items`,會讓整個讀取方法當場中止。

- **(a)** 建構子預先為全部 10 對配對各建一個空 `AffinityRecordList`,讓 `_records` 永不缺鍵;或
- **(b)** 每個讀取入口一律先 `_records.has(pair)` 守衛。

**這不是可以推遲到 `/create-architecture` 的實作細節** —— 沒選就會在第一次查詢空配對時當場中止。`_death_marks` 同理:`t_death()` 目前只有簽章、沒有函式體,**從 ADR 文字看不出是否已隱含 `has()` 守衛**,需一併明文化。

### 探針 D(2026-08-21):殘留未查證項第 1、2 項**皆已關閉**

| 判定 | 結果 |
|---|---|
| `Pair.values().has(-1)` | **不中止,乾淨回傳 `false`** |
| `Pair.values().has(999)` | **不中止,乾淨回傳 `false`** |
| `Pair.keys().has("C1_C2")`(合法名) | **不中止,回傳 `true`** |
| `Pair.keys().has("NO_SUCH_PAIR")`(非法名,靜態字面量) | **編譯通過、不中止,回傳 `false`** |
| 同一非法名,執行期 `"".join()` 組出(不可常數摺疊) | **不中止,回傳 `false`** |

**對 R7-P1 的影響**:地基成立。機制四步驟 4/5 可以用 `AffinityTypes.Pair.values().has(ordinal)` 作為 `INVALID_PAIR`/`INVALID_SOURCE` 的實際檢查手段 —— 越界輸入的回傳值可安全判讀,不會中止呼叫函式。**R7-P1 本身仍開**(ADR 仍須刪掉已被證偽的「理論上不可達」推論句並明訂檢查手段),但建議修法不再押在未查證行為上。

**對 R7-P3 的影響**:地基成立,且**比原建議更精確**。原建議寫「先做存在性檢查(`values().has()` / `keys().has()`),或改用 `find_key()`」—— 三條路徑現已全部實測可用。**R7-P3 本身仍開**(機制八仍須明文寫下該規則)。

**本探針量到一項探針 C 未區分的事實**:同一個非法名字串,走 `.has()` 方法呼叫與走 `[]` subscript 是**兩種完全不同的命運** ——

| 形狀 | 字面量 | 執行期動態組出 |
|---|---|---|
| `Pair["NO_SUCH_PAIR"]`(subscript) | **Parse Error,整檔編譯失敗** | **`SCRIPT ERROR`,中止呼叫函式** |
| `Pair.keys().has("NO_SUCH_PAIR")`(方法呼叫) | **編譯通過,回傳 `false`** | **回傳 `false`** |

**因此 ADR-0002 的規則措辭必須點名形狀,而不能只點名輸入來源。**「不對不可信字串裸用 `Pair[name]`」與「改用 `keys().has()` 先檢查」不是同一件事的兩種說法 —— 前者禁的是形狀,後者給的是替代形狀,兩句都必須寫。

> **紀律註記**:探針 D 仍把「預期會過」(d1)與「預期可能失敗」(d2/d3)拆成三個檔案並逐檔 `reload()` 編譯檢查,即使檔頭註解已推測 `.has(字串)` 與 c2 的 enum-as-Dictionary 字面量 subscript 不同形狀。**量完證實那個差別確實存在且方向有利,但拆檔紀律不因結果良好而追認為多餘** —— d2 若與 d1 同檔而結果相反,會原地重演探針 C 第一版的整檔封鎖。

## 〇、先回答「有辦法嗎」

**有辦法,但「完全不需要你」這句話有一半做不到,而且做不到的那一半正是這個專案最貴的教訓。**

| | 能不能自動化 | 依據 |
|---|---|---|
| 生圖本身(下提示詞、跑 GPU、存檔) | ✅ 可以全自動 | `architecture-and-risks.md` §3 |
| 機械檢查(尺寸、色盤外的顏色、描邊) | ✅ 可以全自動 | `ai-art-validation-protocol-2026-09-29.md` §3.1 |
| 不合格自動重跑 | ✅ 可以全自動,**但必須有停損** | `job-contract-and-checks.md`(建議重跑上限 3 次) |
| **「這五張看起來像不像同一個人」** | ❌ **不能** | 驗證協議 §3.2 |
| **「這張好不好看」** | ❌ **不能** | 見下方 |

🔴 **不能自動化那兩項,不是偷懶,是本專案實測出來的。** 每次對話開場載入的規範裡逐字寫著:

> Every visual defect found on this project so far was found by a person opening the file;
> the automated suite has never caught one.
>
>(至今這個專案發現的**所有**畫面缺陷,都是人開圖看到的;自動檢查**一次也沒抓到過**。)

當場查證:`grep -n "the automated suite has never caught one" .claude/docs/coding-standards.md`

**所以這套系統的正確定位:把你從「操作員」變成「審圖的人」。**
省掉的是「開軟體、打提示詞、等、存檔、看不行、改參數、再等」這段工時;
**沒有省掉**「看一眼說這批過或不過」。

✅ **這一條已被寫成資料契約裡的硬性欄位,不是口頭約定**:
一張圖在人簽核之前,系統上**沒有任何路徑**能把它標成「完成」
(`job-contract-and-checks.md` 的 `human_signoff` 欄位)。

### 🔴 乙案的弱點是「安靜地壞掉」,但可以補

公司端看到「沒有新的圖」時,分不出四種情況:機器沒開 / 還沒輪到 / 跑失敗 / 推送失敗。

## 附錄 A:協調者自行量測的事實

**2026-09-30 於公司筆電實測:**

```
$ git count-objects -vH
count: 183
size: 4.09 MiB
size-pack: 10.74 MiB

$ git ls-files "*.png" "*.jpg" | wc -l
86
```

**圖檔進版控不是提案,這個專案已經在做了。** 86 張圖已在版控中,倉庫總共仍只有 10.74 MB。
其中 37 張是 `production/qa/evidence` 的 **1920×1080 全視窗截圖** —— 最大的一類。

🔴 **真正的風險不是「圖檔」,是「數量級」。** AI 生圖的中間產物以「每次嘗試數十張」的速度
產生,與截圖那種「一個里程碑存一張」完全不同量級。原生 1024 的圖一張 1~2 MB,
**100 張就把倉庫撐大一個數量級,而且事後刪不掉**(git 歷史要刪必須整個重寫)。

**硬性規則**:只有通過檢查、要進遊戲的最終小圖進 git;
AI 迭代過程中產生的所有嘗試,一律留在家裡那台。

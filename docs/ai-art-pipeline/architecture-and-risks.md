## 1. 技術可行性:RTX 5070 Ti(Blackwell)→ 驅動 / CUDA / PyTorch

**結論:這條鏈在 2026-09 沒有根本性障礙,但有一個幾乎必踩、且訊息會誤導人的坑。**

| # | 宣稱 | 等級 |
|---|---|---|
| 1.1 | RTX 50 系(Blackwell 消費卡)的 compute capability 是 **sm_120**,需 **CUDA 12.8 以上** | (C) |
| 1.2 | **PyTorch 2.7.0(2025-04)是第一個原生支援 sm_120 的穩定版**,提供 cu128 預編 wheel;2.8 / 2.9 / 2.10 線延續支援 | (C) |
| 1.3 | 2026-01 的穩定線為 2.10 | (C) |
| 1.4 | 社群大量回報 `sm_120 is not compatible with the current PyTorch installation ... supports sm_50 ... sm_90` | (C) |

🔴 **1.4 那則錯誤訊息是本節最重要的一條,因為它指向錯誤的結論。** 它字面上讀起來像
「這張卡不被支援」,實際成因是**裝到了預設 wheel(CPU 版或舊 CUDA 版)**,而不是硬體或
框架不支援。這與本專案 `coding-standards.md` 反覆記載的失效模式同形:**訊息本身是真的,
從它推出的結論是錯的。** 排除方法是明確安裝 cu128(或更新)的 wheel,不是換卡、不是等支援。

⚠️ **次要坑(可能不影響本專案)**:另有 Triton 回報 `sm_120 is not defined for option
'gpu-name'`,影響 `torch.compile` 與部分加速路徑。基本生成流程通常不依賴它,**但若照網路教學
開了編譯加速選項就會撞到**。(C)

**明確查不到 / 未查證的四項**(不要當成「沒問題」):
1. PyTorch issue #164342(「stable builds 的官方 sm_120 支援」)**現在是否已關閉**——我查到
   issue 存在,沒查到它的狀態。2.7.0 已支援與該 issue 仍開啟兩件事並不互斥。
2. RTX 5070 Ti 所需的**最低驅動版本號**。
3. AUTOMATIC1111 / ComfyUI **在 2026-09 當下的安裝腳本是否已預設拉 cu128 wheel**。
4. 該卡在 Windows(家中那台的 OS 未查證)vs Linux 下的差異。

## 2. 16GB VRAM 夠不夠

| 用途 | 結論 | 等級 |
|---|---|---|
| **推論**(SDXL 1024x1024 出圖) | **夠,且有餘裕。** 社群普遍 8~12GB 可跑 | (C) |
| **訓練角色專屬 LoRA**(SDXL) | **夠,但不寬裕:12GB 最低、16GB「comfortable」、24GB 才是 recommended** | (C) |

**關鍵技術前提**:Kohya SS v0.9.0(2025-01)加入的 **fused backward pass** 搭配 bf16,把 SDXL
LoRA 訓練的 VRAM 從約 24GB 壓到約 10GB。**16GB 的「夠」建立在有開這項優化之上** —— 沒開就
不夠。(C)

🔴 **一個容易反過來想的地方**:本專案目標素材是 128x128 立繪與 32x40 棋子(很小),但
**SDXL 的訓練與推論都在 1024 級解析度進行,之後才降採樣**(那正是驗證協議第五節後製工具
的工作)。**VRAM 需求按 1024 算,不按 128 算。不要因為成品圖小就推論 VRAM 需求小。**

**吃掉那點餘裕的三個變數**(任一調大就可能 OOM):batch size、解析度 bucket 上限、是否
同時訓練 text encoder。(C)

**與昨天授權稽核的交叉參考**:`design/art/ai-image-licensing-audit-2026-09-29.md` 第八節
「未查證清單」第 4 項正是這題,該文標記為「不屬本次派工範圍」。**本文把它從「完全未查證」
推進到「有二手來源的 (C) 推論」,但沒有結案** —— 唯一能結案的動作是在那台機器上實跑一次
(見 §6 階段 0)。

## 3. 服務端選型

| 選項 | 現成 REST | API 穩定性 | 多養一個相依值不值得 |
|---|---|---|---|
| **AUTOMATIC1111** | 有(`--api`,`/sdapi/v1/txt2img`),最簡單 | 單體式、session-based;Blackwell 支援落後(issue #16884 即此卡) | ✘ API 最好懂,但踩 §1 那個坑機率最高 |
| **ComfyUI** | 有(`POST /prompt` 回 `prompt_id`,再輪詢 `/history/{id}`;另有 WebSocket 進度) | stateless、無 session 耦合;社群回報在 Blackwell 上較容易裝起來 | ✔ **建議** |
| **InvokeAI** | **未查證** —— 本次沒查,不要讀成「沒有」 | 未查證 | 未評估 |
| **自寫 FastAPI 包 diffusers** | 自己定,契約最乾淨 | 自己維護 | ✘ 不建議當第一步(理由見下) |

以上除「未查證」列外皆 (C)。

**建議:ComfyUI。** 三個理由:①有現成 REST,不必自寫;②stateless 提交-輪詢模型**同時適合
甲案與乙案**,不會因為 §4 的裁決結果而白做;③Blackwell 上的安裝成功回報較多。

🔴 **ComfyUI 的代價要先講**:它的 API 是「提交一整份 workflow JSON」,**workflow 改一個節點
就等於改了 API 契約**,而且這個耦合是隱性的 —— 呼叫端看不出來。緩解:把 workflow JSON 當成
版控產物釘死(見 §5 R-3)。另:`/prompt` 只回 `prompt_id`,**結果要自己輪詢**,呼叫端必然是
非同步的,不要規劃成一次同步呼叫就拿到圖。

**為什麼不建議一開始就自寫 FastAPI**:它要自己處理排隊、模型載入/卸載、OOM 復原、進度回報
—— 等於重寫一份 ComfyUI 的排程器。更關鍵的是它**把「跑不跑得出圖」與「服務寫得對不對」兩個
風險綁在一起**,第一步應該一次只擔一個風險。

📌 **相依政策的正確適用範圍(重要,容易誤用)**:`technical-preferences.md` 的
`Allowed Libraries / Addons` 節(至今只有 GdUnit4 一項)管的是**進遊戲 repo、進 `addons/`、
會被 CI 抓取的 Godot 套件**。AI 繪圖服務不在遊戲執行期、不在 CI、不進 `addons/` ——
它是**離線資產產線工具**,**不受該節管轄**,不必為了它去改那份清單。
🔴 **但該節背後的理由完全適用,而且更嚴重**:那條政策的理由逐字是「不同時間 clone 可能
拿到不同版本」。這裡要釘死的不只是一個套件,而是**模型權重 + LoRA + ComfyUI 本體 + 節點
外掛**的版本組合 —— 複雜度高一個數量級。見 §5 R-2 / R-3。

## 4. 兩種傳輸架構:甲(直連 REST)vs 乙(git 當佇列)

| 面向 | 甲:家裡開服務,公司筆電主動連過去 | 乙:公司只 commit 工單,家裡輪詢 git |
|---|---|---|
| **延遲** | 秒級。單張 SDXL 生成約數秒至數十秒 (C),加網路往返 | **分鐘級。** 下限 = 輪詢間隔 + 生成時間 + 兩次 push/pull |
| **需要新開的網路路徑** | 🔴 多:公司端要能對外連任意 host:port、家用端要 port forwarding 或穿透、DDNS 或固定 IP、TLS 與認證 | **零。** 公司端只用既有的 git push/pull |
| **可行性** | 🔴 **未查證,且我判斷是本案最大未知** —— 見下方「甲案的非技術阻斷點」 | 較高。公司端已證實可用(註 1);家裡那台能 push 到 GitHub 為 (C) |
| **失敗時怎麼表現** | ✔ **明確且即時**:連不上就是 connection refused / timeout | 🔴 **沈默** —— 見下方「乙案的致命弱點」 |
| **家裡那台沒開機** | 立即失敗,訊息明確 | 🔴 **與「還沒輪詢到」「腳本掛了」「生成失敗」長得一模一樣** |
| **常駐成本** | 家用機要 24h 開機才有意義 | 可排程;沒開機只是變慢,不是壞掉 |

**註 1(本文唯一 (A) 級宣稱)**:公司筆電到 GitHub 的 push 路徑實際可用 —— 本 repo
2026-09-29 的提交 `f0399510d0316c4da0b9d04d44d0518441d79b5a` 即由這台推出,可用
`git log -1 --format='%H %ad' --date=short` 當場重驗。**其餘任何對外連線路徑一律未查證。**

🔴 **甲案的非技術阻斷點(我不評估,也不該由技術總監裁定)**:這台是台灣期貨交易所
(金融機構)配發的筆電。「在公司配發設備上主動對外連線到家用 IP 的自架服務」**是公司
網路與資安政策問題,不是技術問題。** 本文不判定它可不可以,**但它必須在甲案被選之前先問清楚**
—— 因為它會一票否決整個甲案,而且技術上再怎麼準備都繞不過去。

🔴 **乙案的致命弱點是沈默失敗,但我不否決它 —— 因為這個弱點是可緩解的,而且緩解是強制的。**
公司端看到「沒有新 commit」時,無法區分四種狀態(機器沒開 / 還沒輪到 / 跑失敗 / 推送失敗)。
**這與本專案 `coding-standards.md` 反覆記載的失效模式完全同形**:exit 0 的假綠燈、
`grep -c` 回 0 與「乾淨」長得一樣、空結果不是通過的結果。
**強制緩解(不是選配)**:輪詢端每次醒來都必須 commit 一個心跳檔(含時間戳與版本指紋),
失敗時必須 commit 失敗報告。**有工單、無回應**這個狀態一定要有檔案能區分成因。

**圖檔進 git —— 技術上沒被擋,但要加約束**:`.gitignore` 的 `*.png` / `*.jpg` 兩行確實是
被註解掉的(未生效),可當場重驗:`sed -n '134,140p' .gitignore`。等級 (B)(讀檔實測,
**不是 (A)** —— 依「(A) 的精確定義」,沒有引擎執行專案程式碼就不是 (A))。
體積:本 repo 現值 `.git` 17M、`size-pack` 10.74 MiB(`git count-objects -vH` 當場可重驗,(B))。
🔴 **PNG 已是壓縮格式,git 無法再壓;每次重生成都是全新 blob,且永久留在歷史裡。**
SDXL 原生 1024 圖一張約 1~2MB (C) → 100 張就把 repo 撐大一個數量級,**且事後無法瘦身
(除非重寫歷史)**。**約束:工單檔與最終量化後的小圖(128x128 索引色,數 KB)可進 git;
原生解析度中間產物不進 git,留在家那台。** 這樣乙案的體積代價可接受。

**我的建議(非裁決)**:若甲案的公司網路政策問題無法先確認為「可以」,乙案是**唯一能在不
觸碰該問題的前提下推進的路**。但**現在不需要裁決** —— 理由見 §6。

## 5. 風險登記(本專案現在沒有、這條路會新增的)

| ID | 風險 | 為什麼本專案現在沒有 | 緩解 |
|---|---|---|---|
| R-1 | **家用機常駐服務可用性**:單點、無 UPS、無監控,停電或 Windows 自動更新重開就消失 | 目前所有產出都在一台筆電上完成,無遠端相依 | 乙案天生較耐(沒開機只是變慢);甲案必須接受這是單點故障 |
| R-2 | **模型檔與 LoRA 的版本釘死**:權重檔 GB 級,不可能進 git,而「換了一版模型」不會有任何徵兆 | 唯一相依 GdUnit4 是靠**整包進版控**釘死的,該手段對 GB 級權重不適用 | 版控一份 manifest:每個模型/LoRA 的檔名 + **SHA256** + 來源 URL + 取得日期 |
| R-3 | **產出不可重現**:seed、模型 hash、取樣器、步數、CFG、LoRA 權重、ComfyUI workflow JSON、節點外掛版本 —— 任一項沒留下,就再也生不出同一張圖 | 目前產出物(程式碼、文件)本質可重現 | 每張圖配一份**獨立的版控文字參數檔**,與圖同 commit |
| R-4 | **公司網路與資安政策**(甲案專屬) | 目前唯一對外行為是 git push | 選甲案前先確認;本文不判定 |
| R-5 | **repo 膨脹不可逆** | 目前 repo 幾乎純文字 | §4 的進 git 約束(只進小圖與工單) |
| R-6 | **多出一整條無人擁有的技術棧**(Python / CUDA / 模型生態),本專案至今只有 Godot + GDScript 一條 | — | 明確登記擁有者;若無人擁有,這條路的維護成本會在半年後才浮現 |
| R-7 | **服務暴露與認證**(甲案為主):ComfyUI / A1111 預設無認證,等於把一台家用機的 GPU 與檔案系統開在公網 (C) | 目前沒有任何對外監聽的服務 | 甲案必須有認證與 TLS;乙案結構上不產生這個風險 |
| R-8 | **紀律不可觀測**:上述 R-2 / R-3 全是「寫下來的規則」,沒有任何閘門會檢查 | 這不是新風險,是本專案**既有的**已知狀態(多份文件明文登記) | 誠實登記,不要假裝有檢查 |

🔴 **R-3 有一個具體且幾乎一定會發生的陷阱**:AI 繪圖工具習慣把參數寫進 PNG 的 metadata,
於是很容易以為「圖檔自己記得參數」。**但驗證協議第五節的後製工具會降採樣並重新存檔,
metadata 大機率在那一步被剝掉。** 亦即:**最終進 repo 的那張圖,正是最可能不帶參數的那張。**
參數必須是獨立的文字檔,不能靠圖檔內嵌。

## 6. 分階段落地建議

🔴 **我同意協調者的猜測(第一步是在家手動跑通一張圖),但理由不同,而且交付物不是那張圖。**

- **階段 0 —— 完全不碰網路、不碰 REST、不碰 LoRA。** 在家那台手動跑通一張 SDXL 圖。
  理由:①它一次只擔一個風險(§1 的驅動/CUDA/PyTorch 鏈);②**它是唯一能把本文幾乎所有
  (C) 升級成 (A) 的動作。**
  🔴 **交付物不是圖,是一份環境指紋**:驅動版本、CUDA 版本、torch 版本、
  `torch.cuda.get_device_capability()` 的原始輸出、模型檔 SHA256、單張耗時、VRAM 峰值。
  **沒有它,日後每一次「為什麼今天跑不出昨天那張」都無解**,而且會發生在最不方便的時候。
- **階段 1 —— 重現性先於自動化。** 用階段 0 的參數檔再跑一次,確認兩張一致。
  **一條不可重現的產線自動化之後,只會更快地產生無法追溯的東西。**
- **階段 2 —— 接上驗證協議第五節的後製工具**(降採樣 + 量化),走完一張立繪的完整鏈路,
  跑一次協議第三節的過關判準。⚠️ **已知上游阻擋**:該節第 3 項輸入「色階庫參考檔」
  目前**尚不存在**(`art-direction.md` 第十節明文留給實作時再定)。這會擋住階段 2,不擋階段 0/1。
- **階段 3 —— 到這裡才談甲/乙。** 屆時管理者手上會有實測的單張耗時與 VRAM 峰值,
  §4 的延遲比較才有意義。**現在比是紙上談兵。**
- **階段 4 —— LoRA 訓練**(§2 的那一半)。它的風險與階段 0~3 正交,不要混在同一批做。

🔴 **建議現在不裁決甲/乙。** 兩案都需要階段 0 的產物才談得下去,而階段 0 對兩案完全相同
—— 現在裁決不會讓任何事提早開始,只會讓一個未查證的選擇變成既成事實。

## 7. 與既有文件的關係

- **不與驗證協議第一節(SDXL 先行)衝突。** 我 §1/§2 查到的方向與它一致:SDXL 的 16GB
  LoRA 社群證據確實較多。
  ⚠️ **但要更正它第 3 點的一句話**:該句寫「SDXL LoRA 訓練在 8~12GB 社群配置下已是常見設定」,
  而我查到的是**12GB 最低、16GB comfortable、24GB recommended**,8GB 是重度優化下的特例。
  **方向一致,但那句讀起來比實際寬鬆。建議讀成「12GB 起跳」。**
  這是**更正建議,不是否決** —— 該節自己已明文「0% 是量測結果,100% 是推論」。
- **不與第五節(後製工具規格)衝突**,§6 階段 2 正是餵給該工具的上游;該節的色階庫依賴
  已登記為階段 2 的阻擋項。
- **相依政策**:見 §3 末段 —— 本產線不受 `Allowed Libraries / Addons` 節管轄,但其理由適用。

## 8. 本文明確未評估的事(不要讀成「沒問題」)

1. **Git LFS**。`.gitignore` 那段註解逐字寫著 `use Git LFS instead`,**而本文 §4 完全沒有評估
   它** —— 它可能讓乙案的體積問題有第三條路(既非「全進 git」也非「不進 git」)。
   ⚠️ LFS 會替公司端新增一條對 GitHub LFS 端點的相依,**與乙案「零新路徑」的賣點可能衝突**,
   需要實測才知道現有 git 憑證/代理是否涵蓋它。

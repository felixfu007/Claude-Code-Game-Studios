# AI 生圖管線 — 安全與政策風險

標籤說明：**(A)** 實機驗證　**(B)** 專案文件明文　**(C)** 推測/業界通識,未針對本情境實測。

## 0. 背景與我尚未查證的部分

- 甲案:家用桌機開一個 REST 服務對外,公司筆電主動連進去呼叫生圖。
- 乙案:公司筆電只 push 一個工單檔到 GitHub,家用桌機輪詢取件、跑完把成品 push 回去,
  **公司端不開任何新的對外連線**(推論,見第 3 節查證)。
- 🔴 **公司(台灣期貨交易所)實際的資安/使用規範,我查不到、也無權查** —— 本文件中所有「政策/合規」
  段落都會明白標成未查證,只提供金融業常見的規範**類型**當參考,不是這家公司的實際條文。
  這件事**只有管理者本人問公司資安或 IT 部門才問得到**。

## 1. 甲案 vs 乙案 風險對比

### 1a. 技術風險

| 面向 | 甲案(對外開 REST 服務) | 乙案(GitHub 工單輪詢) |
|---|---|---|
| 攻擊面 | 家用主機需要有一個「監聽中」的服務,若用連接埠轉發(port forwarding)或動態 DNS 對外公開,理論上任何人都掃得到這個位址,包括自動化掃描工具(如 Shodan 類服務)。(C) | 家用主機是主動「拉」(pull),不需要開放任何對外可連入的埠。這是網路架構的通用原則:輪詢式架構不必開 inbound port,攻擊面在「能不能被連進來」這一項上結構性較小。(C,技術原理成立,但未針對此案例實機驗證) |
| 驗證/憑證外洩 | 需要一組驗證機制(API 金鑰、密碼等)。若寫在公司筆電的設定檔或腳本裡,筆電遺失或被檢查時可能連帶外洩。(C) | 仍需要一把 GitHub 存取憑證(個人存取權杖或 SSH 金鑰)放在雙邊主機上,外洩後果取決於這把權杖的權限範圍——若權限沒收窄到「只能存取這一個倉庫」,外洩的殺傷力可能不小於甲案的金鑰。(C) |
| 家用網路成為入侵跳板 | 若家用網路本身遭入侵(家中其他裝置中毒、IoT 設備被攻陷),攻擊者有機會透過這條連線嘗試碰觸公司筆電,或反過來利用連線本身。(C) | 沒有「公司筆電到家用網路」這條直連,少了這個方向的路徑;但家用桌機本身依然是一台連網電腦,一般資安衛生問題(中毒、被入侵)兩案皆存在,與架構選擇無關。(C) |
| 服務本身的已知弱點 | 若跑的是 AUTOMATIC1111/ComfyUI 這類 Web UI,某些版本的分享功能(如 gradio 的 `share=True`)會產生公開連結,等於又開一個未預期的對外入口;這類工具過去也有公開記載的漏洞。(C) | 不涉及對外暴露這類生圖 Web UI 本身,少了這個風險項。(C) |

### 1b. 資料風險

| 問題 | 甲案 | 乙案 |
|---|---|---|
| 什麼資料離開公司裝置 | 呼叫請求本身(提示詞、生圖參數)經網路送到家用主機,若做好加密(見第 2 節),第三方看不到明文。(C) | 工單檔案(提示詞、生圖參數,可能含遊戲美術方向或設計文字)會被 `git push` 到 GitHub 這個外部第三方雲端服務,並**永久留在版本紀錄裡**——即使之後刪除檔案,舊的 commit 歷史通常還在。(C,git 行為屬公開已知事實) |
| 誰看得到 | 只有這條連線的雙方(公司筆電、家用主機),前提是走加密傳輸且沒有中間人。(C) | 取決於 GitHub 倉庫的可見度設定與帳號權限——private 倉庫只有授權帳號看得到;若不慎誤設 public,或與工作帳號混用導致權限外溢,暴露範圍會不同。 |
| 資料落地位置 | 資料不離開這兩台主機。(C) | 資料多了一個落地點:GitHub 的伺服器(在台灣以外的司法管轄權)。這件事本身是否需要另外考慮資料所在地的合規顧慮,屬於下方「政策/合規風險」,未查證。 |

### 1c. 政策/合規風險(🔴 全段標「未查證」——只提供金融業常見規範類型參考)

- 公司資產(筆電)上安裝、執行未經核准的軟體,通常受公司的「軟體安裝限制/白名單政策」管轄。
- 從公司資產建立新的對外網路連線(尤其是連到員工個人家用網路的伺服器),通常受「網路使用政策」
  或「資訊安全政策」管轄——這條**甲案明顯適用**,乙案是否適用要看公司怎麼定義「新的對外連線」
  (甲乙都是新增的網路行為,只是乙借用了原本就在用的 git 通道,公司政策不一定會區分這個差異)。
- 在上班時間、用公司資產做與工作無關的活動,即使不涉及資安漏洞,也可能受「可接受使用政策」
  (Acceptable Use Policy)一類規範管轄,這是行為規範問題,不是技術安全問題。
- 金融機構(尤其台灣證券期貨業)常見受金管會資安相關規範與公司內部資安規範雙重約束,對「資料外流
  到未經核准的第三方服務」通常有更嚴格的認定標準。
- 🔴 **特別提醒**:即使乙案在「網路攻擊面」上比甲案小(見 1a),乙案把資料 push 到 GitHub 這件事,
  若該倉庫不是公司核准的企業版帳號或未經 IT 同意,**本身可能仍構成政策問題**——這是與「傳輸架構
  技術上安不安全」完全不同的另一個問題,兩者不能互相抵銷。乙案「網路面較安全」不等於「政策面沒問題」。
- 以上全部是**業界常見規範類型**,不是台灣期貨交易所的實際條文。實際條文、罰則、是否有例外,
  **只有管理者本人問公司資安或 IT 部門才能確認**。

## 2. 若走甲案:最低限度應做到的安全措施

1. **驗證**:對外服務必須要求身分驗證(API 金鑰、雙向 TLS 憑證、或至少 HTTP Basic Auth 搭配 HTTPS)。
   不可以是任何人都能呼叫的無驗證端點。
2. **傳輸加密**:全程使用 TLS(https),不可用明文 http,尤其若這條連線會經過公司網路或公網。
3. **不對整個網際網路開放**:
   - 優先架設私有通道(例如自架 WireGuard、或 Tailscale 這類工具),讓公司筆電與家用主機之間走
     一條非公開的私有連線,而不是直接把埠口對公網開放(port forwarding)。
   - 若無法避免對公網開放,至少用防火牆限制「只接受公司對外 IP 範圍」的連線來源。
   - 使用非標準連接埠、搭配自動封鎖暴力嘗試的工具(如 fail2ban 類)。
4. **失效時的預設行為**:驗證失敗或服務異常時,行為必須是「拒絕並記錄」,絕不能是「驗證機制連不上
   就預設放行」這種失效開放(fail-open)設計。
5. **憑證管理**:金鑰/密碼不可寫死在程式碼或明文設定檔裡,至少用環境變數或加密儲存;金鑰要能個別
   撤銷與更換,不要一把金鑰全部通用。
6. **紀錄與監控**:至少記錄誰在何時呼叫了什麼,方便異常大量請求或未預期存取被發現。
7. **限制服務功能範圍**:這個對外端點應該**只**能觸發生圖,不能連帶提供 shell 存取、任意檔案讀寫等
   額外能力——功能範圍越窄,即使被入侵,損害範圍也越小。

## 3. 乙案的結構性優勢是什麼(協調者的推論,查證後的判斷)

協調者的推論方向**成立**:乙案的公司端不需要開放任何對外可連入的服務,家用主機是「主動去 GitHub
拉工單」,這在網路架構上屬於「僅對外連出」(outbound-only),不需要監聽對外連入的埠——這是通用的
網路安全設計原則,拉取式(pull/polling)架構的攻擊面天生比開放服務式架構小。(C,原理成立但未實機
驗證此specific 案例)

**但這個優勢有前提,不是自動成立**:
- 若家用主機用來輪詢的 GitHub 存取憑證權限設得太寬(例如可寫入其他倉庫、有組織層級權限),一旦這台
  家用電腦被入侵,攻擊者反而可能拿這把憑證去碰觸憑證範圍內的其他東西——優勢成立的前提是**權限最小化**
  (這把權杖只能讀寫這一個工單用的倉庫)。
- 乙案並非「沒有風險」,只是把風險**從「網路入侵面」換成了「資料外流到第三方服務 + 憑證管理」面**
  (見 1b、1c)。網路攻擊面較小,不代表整體風險較小,要看管理者比較在意哪一類風險。
- 我不認為乙案「更糟」,協調者的推論在網路攻擊面這一項上是站得住的判斷。

## 4. AI 生圖本身的安全面(不含授權——授權見另一份報告)

- **模型檔案來源信任問題**:從 Civitai、Hugging Face 等社群平台下載的 checkpoint/LoRA 檔案,尤其是
  較舊的 `.ckpt`/`.pt`(基於 Python pickle)格式,業界已有公開記載的案例顯示這類格式可以被植入惡意
  程式碼,載入時等同執行任意程式。(C,業界公開已知風險類型,非本專案實測)
  - 建議:優先使用 `.safetensors` 格式(純張量資料,不含可執行程式碼),避免下載 `.ckpt`/`.pt`;
    若必須使用,先用掃毒工具或社群提供的掃描服務檢查過再載入。
  - 只從有信譽的來源下載(官方帳號、知名作者、社群評價良好的頁面),避免來路不明的分享連結。
- 若走甲案且對外暴露生圖用的 Web UI(AUTOMATIC1111、ComfyUI 等),這些工具本身的介面與外掛生態
  也曾有公開記載的安全問題,對外暴露前應確認版本與已知漏洞修補狀況。(C)

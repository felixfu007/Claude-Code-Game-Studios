## 一、這台機器要做什麼

一台放在本機、常駐執行的小伺服器。它開著的時候,外面的程式丟一段文字描述(連同尺寸、
隨機種子、要用哪個模型等參數)進去,它還回一張圖片檔。**就這樣,沒有別的。**

它**不**負責:決定要畫什麼、判斷畫得好不好、把圖送到任何地方去。

### 交付邊界(請照這條線切)

**在範圍內:**

- 一台 Windows 機器上的產圖服務,可常駐、可重啟
- 一個**本機 HTTP API**:送出文字描述 → 取回圖片
- 模型與相依套件的安裝、版本釘死、環境可重現
- 效能與記憶體的實測數字(見第八節,屬驗收條件)

**不在範圍內(委託方自理,請不要做):**

- ❌ 工單從哪裡來、成品送到哪裡去 —— 傳輸層
- ❌ 圖片品質的機械檢查與驗收
- ❌ 美術風格好壞的判定

### 為什麼規格刻意不綁任何傳輸方式

伺服器**只需要**提供一個本機 HTTP API。去雲端硬碟 / 版控 / 訊息佇列取工單、呼叫這個 API、
把成品放回去的那一支橋接程式,**跑在委託方自己的機器上,不是本次外包範圍。**

這樣切的好處:日後換傳輸方式(今天用雲端硬碟、明天改版控、後天改訊息佇列),
**外包方交付的東西一個字都不用改。**

⚠️ 連帶要求:請**不要**把任何雲端帳號、憑證、同步邏輯寫進伺服器。伺服器不該知道
工單從哪來、成品要去哪。它只認得「收到描述 → 回傳圖片」。

## 三、最關鍵的一條:驅動 / CUDA / PyTorch 的最低版本

🔴 **這一節寫錯,專案會卡在第一步,而且會往錯誤的方向排查。**

### 結論(已查證,查證日期 **2026-10-05**)

| 元件 | 最低版本 | 說明 |
|---|---|---|
| NVIDIA 驅動(Windows) | **570 以上**(實務上建議 572 以上) | 更舊的驅動不會正確辨識這張卡 |
| CUDA | **12.8 以上** | 12.8 是第一個原生支援 Blackwell(`sm_120`)的 CUDA 版本 |
| PyTorch | **2.7.0 以上** | 2.7.0 是第一個發行支援 Blackwell 的穩定版 |

🔴 **只看 PyTorch 的版本號是不夠的 —— 要看它是用哪一版 CUDA 建置的。**

`pip install torch` 抓到的預設 wheel 可能是用 CUDA 12.6 建的。版本號看起來夠新,
但 `sm_120` 不在它編譯出來的目標清單裡,**卡一樣不能用**。
必須明確指定 **CUDA 12.8(或更新)的 wheel index**,並確認安裝後的版本字串帶有
`+cu128` 之類的尾碼。

### 為什麼這一條要單獨拉出來警告

版本裝錯時,錯誤訊息長這樣:

```
NVIDIA GeForce RTX 5070 Ti with CUDA capability sm_120 is not compatible
with the current PyTorch installation.
```

**這句話讀起來像「這張顯示卡不被支援」,實際意思是「你裝的 PyTorch 太舊」。**

這個誤導很貴:已經有人因此判定硬體不行,轉而去換卡或改用雲端算力。
網路上大量仍在流通的舊教學寫的是 CUDA 12.1 —— **照那些教學裝,必然撞上這個訊息。**

### 裝完任何東西之前,先跑這三行

在安裝任何產圖軟體之前,先確認底層環境是活的:

```python
import torch
print(torch.__version__)                   # 期望 2.7.0 以上,且帶 CUDA 尾碼
print(torch.version.cuda)                  # 期望 12.8 以上
print(torch.cuda.get_device_capability())  # 期望 (12, 0)
```

**在 `(12, 0)` 出現之前,不要往下做任何一步。** 這三行的原始輸出是交付物之一(見第八節)。

### 這一節裡哪些是推測,不是已查證

- **「更新的 CUDA(12.9 / 13.x)也可以」是推測。** 有來源提到 CUDA 13.0 的 wheel 已存在、
  且有人建議用 12.9,但本文**沒有**找到一份明確寫「CUDA 13.x + RTX 5070 Ti 已驗證可用」的頁面。
  **保守做法:先用 CUDA 12.8 這條已知可行的路把第一張圖跑出來,之後再談升級。**
- **「2026 年 10 月當下最新的 PyTorch 穩定版是哪一版」本文無法確認。** 查到的來源彼此矛盾
  (同一次查詢同時出現「最新為 2.7.0」與「2.13.0 已於 2026-07-08 發行」兩種說法)。
  **因此本文只寫最低版本,不寫建議版本** —— 最低版本有多個獨立來源一致,最新版本沒有。

## 四、16GB VRAM 夠不夠

分兩種情形,答案不一樣。

### 情形一:只做推論(丟描述、出圖)—— 夠

查證到的量級(1024×1024,已查證):

| 模型類型 | 約略 VRAM |
|---|---|
| SDXL 這一級(較輕的一代) | 基礎模型約 3.5 GB(8 位元量化);加上精修模型約 7 GB |
| FLUX.1 dev 這一級(較大的新一代) | 8 位元量化約 **13–15 GB** |

**結論:16 GB 做推論可行。但 FLUX 這一級是「剛好塞得下」,不是「寬裕」。**

已查證的省法:文字編碼器也改用 8 位元版本,可再省約 5 GB。

⚠️ **餘裕會被桌面環境吃掉。** 這台是桌機,瀏覽器與桌面合成本身就要 VRAM。
請把「服務啟動時已有 1–2 GB 被別人佔走」當成常態而非例外 —— 這是風險登記第 3 項的來源。

### 情形二:要訓練 / 微調風格 —— 16GB 有前提

以 1024 解析度訓練估算(已查證):

| VRAM | 判定 |
|---|---|
| 12 GB | 最低可行,實務上不穩定 |
| **16 GB** | **尚可,但有前提 —— 見下方紅字** |
| 24 GB | 建議值,有餘裕(可提高批次大小) |

🔴 **16 GB 那一格的「尚可」是有條件的,條件沒開就是不夠:**

- **fused backward pass**(把 optimizer 步驟併進反向傳播)—— 查證到可把需求從約 24 GB 壓到約 10 GB
- **bf16 混合精度**
- **gradient checkpointing**

**用預設設定、不開這些選項,1024 解析度訓練在 16 GB 上會記憶體不足。**

**建議的先後順序:先把推論跑通並交付,訓練/微調列為第二階段另行評估。**
理由:推論的風險已知且可控;訓練的風險(時數、資料集規模、失敗重跑的代價)
本文完全沒有評估(見第七節第 5 項)。

- LoRA 訓練需求(含 fused backward pass 數字):<https://sanj.dev/post/lora-training-requirements-guide/>

## 五、服務端軟體選型

評分軸只有一條:**「要被另一支程式呼叫」這個用途的適配度。** 好不好用滑鼠操作不在評分範圍內。

| 方案 | 被程式呼叫的適配度 | 優點 | 代價 |
|---|---|---|---|
| **ComfyUI**(建議) | **高** | 前後端本來就是分離的:工作流是一份 JSON,`POST /prompt` 排入佇列拿到工作編號,再查 `/history/{id}` 取結果。無介面模式是原生設計而非外掛。內建佇列,可多個呼叫端同時排隊 | 工作流是節點圖,第一次上手較陡。節點版本與自訂節點是重現性風險(風險第 4 項) |
| **AUTOMATIC1111 / WebUI 系** | 中 | 有現成 REST API(`/sdapi/v1/txt2img`),參數扁平、最容易上手 | 本體是以「人用網頁操作」為中心,API 是附加品;佇列管理與高吞吐支援較弱 |
| **自寫 diffusers 服務** | 高(完全掌控) | 相依最少、介面想怎麼定就怎麼定、最容易做到環境可重現 | **所有東西都要自己寫**:排程、記憶體管理、模型切換、取樣器、各種格式支援。工作量最大,且多半是在重造已經存在的輪子 |

### 建議:ComfyUI,以無介面模式常駐,外面再包一層很薄的自有 HTTP 介面

**為什麼還要再包一層,而不是直接把 ComfyUI 的 API 當成交付介面:**

1. 呼叫端只該認得「送描述 → 拿圖」這一組呼叫。ComfyUI 的工作流 JSON 會因為節點改版而變動,
   那是伺服器內部的事,**不該漏到呼叫端**。
2. 日後若整個換掉底層(例如改成自寫服務),呼叫端一行都不用改。

**這層薄介面至少要提供:**

- 送出一次產圖請求:文字描述、反向描述、尺寸、**隨機種子**、模型識別、步數
- 查詢狀態 / 取回結果
- 健康檢查:服務活著嗎、看得到 GPU 嗎、目前 VRAM 用量多少
- 🔴 **同一組參數 + 同一個隨機種子,必須產出位元層級相同的圖。** 這是驗收項,不是加分項
  (沒有這個,就無法重跑、無法比較、無法回報問題)

## 六、風險登記

走這條路,會新增以下目前不存在的失敗模式。

| # | 風險 | 一句話後果 |
|---|---|---|
| 1 | 裝到以 CUDA 12.8 以下建置的 PyTorch | 顯示卡完全不能用,**而錯誤訊息指向「硬體不支援」,排查方向會整個走偏** |
| 2 | 顯示卡驅動或系統更新打壞可用組合 | 某天早上服務起不來,前一天還好好的;沒有版本紀錄就無從回頭 |
| 3 | VRAM 被桌面其他程式吃掉 | 同一份請求有時成功、有時記憶體不足,**看起來像隨機故障** |
| 4 | 產圖軟體或自訂節點自動更新 | 同一份工作流突然跑不動,或畫出不一樣的圖,**而沒有人改過任何設定** |
| 5 | 模型檔被換掉,或不同時間抓到不同版本 | 風格悄悄變了,**沒有任何錯誤訊息** —— 這是本表裡最安靜的一種 |
| 6 | 隨機種子不可重現 | 無法重跑、無法比較兩次結果、無法回報問題 |
| 7 | 服務無聲掛掉或卡死 | 工單一直堆積,呼叫端只看到逾時,不知道是慢還是死了 |
| 8 | 單張耗時遠超預期 | 上層流程的節奏假設失效,但要等到量產才會發現 |
| 9 | 這是桌機不是伺服器 | 有人關機、有人拿去打遊戲、有人讓它睡眠 —— **服務可用時間不等於 24 小時** |
| 10 | 第一次成功是手動拼湊出來的,沒有人記得怎麼辦到的 | 機器一重灌就全部重來,且不保證能重現 |

**對應的最低限度要求(請視為交付的一部分):**

- 所有版本釘死並寫成一份**可重現的安裝說明**:驅動、CUDA、Python、PyTorch、產圖軟體、
  每一個自訂節點,各自的確切版本
- **關閉所有自動更新**(產圖軟體本體與節點管理器)
- 每個模型檔記錄 **SHA256 與下載來源網址**
- 提供健康檢查端點
- 服務對每一次請求記錄:耗時、VRAM 峰值、使用的模型雜湊、隨機種子

**為什麼要原始輸出,而不是一句「已確認正常」:**
原始輸出可以被接手的人自己核對,「已確認正常」這五個字無法被任何第三方複驗。
當交付內容與驗收方之間唯一的連結是一份自述時,自述寫得再誠實也沒有用 ——
讀的人沒有辦法分辨「確實測過」和「以為測過」。**留輸出,不要只留結論。**

⚠️ 第 6、7、8 項**必須在開窗(非 headless)的情況下取得並附上一張實際產出的圖**。
一份只有環境版本、沒有任何產出圖的指紋,證明的是「環境裝起來了」,
不是「這台機器能產圖」—— 這兩件事不一樣,而且本文從頭到尾只能回答前者。

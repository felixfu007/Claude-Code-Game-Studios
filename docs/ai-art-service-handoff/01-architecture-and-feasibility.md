## 一、這台機器要做什麼

一台放在本機、常駐執行的小伺服器。它開著的時候,外面的程式丟一段文字描述(連同尺寸、
隨機種子、要用哪個模型等參數)進去,它還回一張圖片檔。**就這樣,沒有別的。**

它**不**負責:決定要畫什麼、判斷畫得好不好、把圖送到任何地方去。

### 交付邊界(請照這條線切)

**在範圍內:**

- 一台 Windows 機器上的產圖服務,可常駐、可重啟
- 一個**本機 HTTP API**:送出文字描述 → 取回圖片
- 模型與相依套件的安裝、版本釘死、環境可重現
- 效能與記憶體的實測數字(見第八節,屬驗收條件)

**不在範圍內(委託方自理,請不要做):**

- ❌ 工單從哪裡來、成品送到哪裡去 —— 傳輸層
- ❌ 圖片品質的機械檢查與驗收
- ❌ 美術風格好壞的判定

### 為什麼規格刻意不綁任何傳輸方式

伺服器**只需要**提供一個本機 HTTP API。去雲端硬碟 / 版控 / 訊息佇列取工單、呼叫這個 API、
把成品放回去的那一支橋接程式,**跑在委託方自己的機器上,不是本次外包範圍。**

這樣切的好處:日後換傳輸方式(今天用雲端硬碟、明天改版控、後天改訊息佇列),
**外包方交付的東西一個字都不用改。**

⚠️ 連帶要求:請**不要**把任何雲端帳號、憑證、同步邏輯寫進伺服器。伺服器不該知道
工單從哪來、成品要去哪。它只認得「收到描述 → 回傳圖片」。

### 逐項評估:夠不夠,以及**不夠的時候會怎樣**

#### 系統記憶體 32 GB —— 推論夠用;訓練是這台機器最可能先撞到的牆

**為什麼產圖會吃系統記憶體,而不是只吃 VRAM:**模型檔要先讀進系統記憶體才搬得進 VRAM,
載入那一刻兩邊同時被佔住;VRAM 不夠時,工具會把塞不下的部分「卸載」回系統記憶體;
而 Windows 本身加上常駐程式,開機就先吃掉 4~8 GB。

| 情境 | 32 GB 夠不夠 | 不夠的時候會怎樣 |
|---|---|---|
| 推論,SDXL 這一級 | 寬裕 | — |
| 推論,FLUX 級 **8 位元量化** | 夠 | — |
| 推論,FLUX 級 **fp16 不量化** | 🔴 **緊** —— 有來源直接建議 64 GB | 載入階段大量動用分頁檔;單張從數十秒變成數分鐘,或載入直接失敗 |
| **訓練 / 微調** | ⚠️ **剛好踩在經驗法則的下限,沒有餘裕** | 同上,再加上資料前處理與 latent 快取階段的額外佔用 |

查證到的經驗法則:**系統記憶體至少要是 VRAM 的 2 倍。** 16 GB × 2 = 32 GB ——
這台**剛好等於下限,一點餘裕都沒有**。

🔴 **系統記憶體不足的症狀不是錯誤訊息,是「變得很慢」。**
Windows 會動用分頁檔(把記憶體內容寫到硬碟上),程式不崩潰、不報錯,
只是從數十秒變成數分鐘,看起來像「這台電腦就是慢」。
**接手的人非常容易把它誤判成「GPU 不夠力」而去考慮換顯示卡 —— 那會花錢而且不會解決問題。**

**降低風險的做法(建議寫進安裝說明):**

- **優先選 8 位元量化版的模型與文字編碼器** —— 同時省 VRAM 和系統記憶體,是 CP 值最高的一招
- 跑產圖時關掉瀏覽器等吃記憶體的常駐程式
- 確認分頁檔沒有被關掉(有些人為了省 SSD 壽命會關掉它)

#### 系統碟 2 TB NVMe —— 總容量寬裕,但「還剩多少」沒人知道

模型檔大小量級(已查證):

| 檔案 | 大小 |
|---|---|
| FLUX.1 dev 擴散模型,fp16 | 約 **23 GB** |
| 同上,8 位元量化版 | 約 **12 GB** |
| T5-XXL 文字編碼器,fp16 | 約 **9.8 GB** |
| 同上,8 位元量化版 | 約 **4.6 GB** |
| CLIP 類文字編碼器 | 0.2 ~ 1.6 GB |
| SDXL 這一級的完整 checkpoint | 約 **6.5 GB** |

**量級感:**一套完整的 FLUX fp16 工作環境(擴散模型 + 文字編碼器 + VAE)約 **35~40 GB**;
8 位元量化版約 **18~20 GB**;SDXL 級的一個 checkpoint 約 **6.5 GB**。
換算:2 TB 的總容量上,就算擺 **20 套 FLUX fp16 等級的完整模型**,也只吃掉約 700~800 GB。
**總容量不是瓶頸。**

🔴 **但有意義的數字是「剩餘空間」,而那個沒有人知道 —— 這台是日常使用的桌機,
2 TB 可能已經用掉大半。** 請在動工前先回報剩餘空間。

⚠️ **另外兩件不要漏算的事:**

- **訓練會產生中間檔** —— latent 快取、每個 epoch 的檢查點。單次訓練可能額外吃掉數十 GB,
  而且這些檔案不會自己清掉。
- **Gen4 NVMe 這一項是加分不是風險。** 一個 23 GB 的模型從機械硬碟載入是分鐘級,
  從 Gen4 NVMe 是十幾秒級。換模型頻繁時,這個差異很有感。

#### CPU(R7 7700)—— 產圖本身不吃它,但有四個環節會變成瓶頸

產圖的矩陣運算全部在 GPU 上,**穩態產圖時 CPU 大多在等**。會變成瓶頸的是這幾處:

1. **模型載入與反序列化** —— 多半是單緒作業,換模型時感覺得到
2. **文字編碼器被擠到 CPU 執行時** —— VRAM 不足時,某些工具會把文字編碼器移到 CPU 跑,
   此時每張圖會多出數秒到數十秒
3. **影像後處理與存檔**(PNG 壓縮、放大、格式轉換)—— 批次量大時會疊加
4. **訓練時的資料前處理**(讀圖、裁切、產生 latent 快取)—— 這一段幾乎是純 CPU

**8 核 16 緒對上述四項都夠。本文判定 CPU 不是風險項。**
⚠️ 但這是**推測**:本文沒有找到任何「CPU 不足以跑產圖」的案例,也沒有人在這台上量過。

#### 🔴 電源供應器 —— 本節唯一可能讓機器當場跑不起來的項目,**而且症狀會把人指到錯的方向**

已查證(查證日期 2026-10-05):

- RTX 5070 Ti 的板卡功耗(TGP)為 **300 W**
- **NVIDIA 官方建議的系統總電源為 750 W**,但該數字是以 Ryzen 9 9950X 這種高功耗 CPU 估算的
- 本機的 R7 7700 標稱 TDP **65 W**、實測封裝峰值約 **83~90 W** —— 屬於低功耗 CPU,
  壓力明顯小於 NVIDIA 估算時用的那顆
- 板卡供電:兩條 PSU 側 8-pin(透過隨附轉接),或一條至少 300 W 等級的 Gen 5 線
- 同級系統的建議區間:搭 Ryzen 5 / Core i5 級 CPU 約 650 W,搭 Ryzen 9 / Core Ultra 9 級約 850 W

→ **推測(不是查證):**以 R7 7700 這個級別搭配,**750 W 是合理的目標值,650 W 是會讓人睡不好的下限。**

🔴 **委託方尚未確認實際裝的是幾瓦。這是他自己要去量的第一件事,而且不需要任何工具 ——
打開機殼看電源供應器側面的標籤就有。**

⚠️ **為什麼這一條要單獨拉出來寫:電源不足的症狀長得像軟體問題。**
電源餘裕不夠時,GPU 滿載的那一瞬間會突然當機、藍畫面、或整機重開,
而且**只在跑大負載時發生,平常用都正常**。
接手的人第一直覺會去查驅動、查 CUDA、查產圖軟體的 bug —— **而那些地方什麼都查不到。**

**這跟第三節那個「`sm_120` 錯誤訊息看起來像硬體不支援、實際是版本裝錯」是同一類形狀:
症狀把排查方向指到錯的地方。** 差別在於版本問題一裝就撞到,
**電源問題只在滿載時才撞到 —— 可能已經做了兩週才第一次出現。**

**具體要求:在產出第一張圖之前先確認電源瓦數。若低於 650 W,請先回報再動工。**

### 🔴 這是一台桌上型電腦,不是機房伺服器

請在設計時假設:

- 它會被關機、會進睡眠、會被拿去做別的事
- GPU **不是**獨佔的 —— 瀏覽器、桌面合成、其他程式都會吃 VRAM
- 系統記憶體同理 —— 32 GB 不是全部給你用的
- 沒有遠端管理、沒有備援電源
- 服務必須能一鍵啟動或開機自動啟動,並且在被關掉之後能乾淨地重來

## 三、最關鍵的一條:驅動 / CUDA / PyTorch 的最低版本

🔴 **這一節寫錯,專案會卡在第一步,而且會往錯誤的方向排查。**

### 結論(已查證,查證日期 **2026-10-05**)

| 元件 | 最低版本 | 說明 |
|---|---|---|
| NVIDIA 驅動(Windows) | **570 以上**(實務上建議 572 以上) | 更舊的驅動不會正確辨識這張卡 |
| CUDA | **12.8 以上** | 12.8 是第一個原生支援 Blackwell(`sm_120`)的 CUDA 版本 |
| PyTorch | **2.7.0 以上** | 2.7.0 是第一個發行支援 Blackwell 的穩定版 |

🔴 **只看 PyTorch 的版本號是不夠的 —— 要看它是用哪一版 CUDA 建置的。**

`pip install torch` 抓到的預設 wheel 可能是用 CUDA 12.6 建的。版本號看起來夠新,
但 `sm_120` 不在它編譯出來的目標清單裡,**卡一樣不能用**。
必須明確指定 **CUDA 12.8(或更新)的 wheel index**,並確認安裝後的版本字串帶有
`+cu128` 之類的尾碼。

### 為什麼這一條要單獨拉出來警告

版本裝錯時,錯誤訊息長這樣:

```
NVIDIA GeForce RTX 5070 Ti with CUDA capability sm_120 is not compatible
with the current PyTorch installation.
```

**這句話讀起來像「這張顯示卡不被支援」,實際意思是「你裝的 PyTorch 太舊」。**

這個誤導很貴:已經有人因此判定硬體不行,轉而去換卡或改用雲端算力。
網路上大量仍在流通的舊教學寫的是 CUDA 12.1 —— **照那些教學裝,必然撞上這個訊息。**

### 裝完任何東西之前,先跑這三行

在安裝任何產圖軟體之前,先確認底層環境是活的:

```python
import torch
print(torch.__version__)                   # 期望 2.7.0 以上,且帶 CUDA 尾碼
print(torch.version.cuda)                  # 期望 12.8 以上
print(torch.cuda.get_device_capability())  # 期望 (12, 0)
```

**在 `(12, 0)` 出現之前,不要往下做任何一步。** 這三行的原始輸出是交付物之一(見第八節)。

### 這一節裡哪些是推測,不是已查證

- **「更新的 CUDA(12.9 / 13.x)也可以」是推測。** 有來源提到 CUDA 13.0 的 wheel 已存在、
  且有人建議用 12.9,但本文**沒有**找到一份明確寫「CUDA 13.x + RTX 5070 Ti 已驗證可用」的頁面。
  **保守做法:先用 CUDA 12.8 這條已知可行的路把第一張圖跑出來,之後再談升級。**
- **「2026 年 10 月當下最新的 PyTorch 穩定版是哪一版」本文無法確認。** 查到的來源彼此矛盾
  (同一次查詢同時出現「最新為 2.7.0」與「2.13.0 已於 2026-07-08 發行」兩種說法)。
  **因此本文只寫最低版本,不寫建議版本** —— 最低版本有多個獨立來源一致,最新版本沒有。

## 四、16GB VRAM 夠不夠

分兩種情形,答案不一樣。

### 情形一:只做推論(丟描述、出圖)—— 夠

查證到的量級(1024×1024,已查證):

| 模型類型 | 約略 VRAM |
|---|---|
| SDXL 這一級(較輕的一代) | 基礎模型約 3.5 GB(8 位元量化);加上精修模型約 7 GB |
| FLUX.1 dev 這一級(較大的新一代) | 8 位元量化約 **13–15 GB** |

**結論:16 GB 做推論可行。但 FLUX 這一級是「剛好塞得下」,不是「寬裕」。**

已查證的省法:文字編碼器也改用 8 位元版本,可再省約 5 GB。

⚠️ **餘裕會被桌面環境吃掉。** 這台是桌機,瀏覽器與桌面合成本身就要 VRAM。
請把「服務啟動時已有 1–2 GB 被別人佔走」當成常態而非例外 —— 這是風險登記第 3 項的來源。

### 情形二:要訓練 / 微調風格 —— 16GB 有前提

以 1024 解析度訓練估算(已查證):

| VRAM | 判定 |
|---|---|
| 12 GB | 最低可行,實務上不穩定 |
| **16 GB** | **尚可,但有前提 —— 見下方紅字** |
| 24 GB | 建議值,有餘裕(可提高批次大小) |

🔴 **16 GB 那一格的「尚可」是有條件的,條件沒開就是不夠:**

- **fused backward pass**(把 optimizer 步驟併進反向傳播)—— 查證到可把需求從約 24 GB 壓到約 10 GB
- **bf16 混合精度**
- **gradient checkpointing**

**用預設設定、不開這些選項,1024 解析度訓練在 16 GB 上會記憶體不足。**

🔴 **訓練還有第二個限制,不在 VRAM 上:系統記憶體 32 GB 也剛好只踩在經驗法則的下限。**
詳見第二節「系統記憶體」一段 —— **兩個限制同時成立,而且是不同的資源。**
把 VRAM 調得剛好塞下,不代表訓練就跑得動。

**建議的先後順序:先把推論跑通並交付,訓練/微調列為第二階段另行評估。**
理由:推論的風險已知且可控;訓練的風險(時數、資料集規模、失敗重跑的代價)
本文完全沒有評估(見第七節第 5 項)。

## 五、服務端軟體選型

評分軸只有一條:**「要被另一支程式呼叫」這個用途的適配度。** 好不好用滑鼠操作不在評分範圍內。

| 方案 | 被程式呼叫的適配度 | 優點 | 代價 |
|---|---|---|---|
| **ComfyUI**(建議) | **高** | 前後端本來就是分離的:工作流是一份 JSON,`POST /prompt` 排入佇列拿到工作編號,再查 `/history/{id}` 取結果。無介面模式是原生設計而非外掛。內建佇列,可多個呼叫端同時排隊 | 工作流是節點圖,第一次上手較陡。節點版本與自訂節點是重現性風險(風險第 4 項) |
| **AUTOMATIC1111 / WebUI 系** | 中 | 有現成 REST API(`/sdapi/v1/txt2img`),參數扁平、最容易上手 | 本體是以「人用網頁操作」為中心,API 是附加品;佇列管理與高吞吐支援較弱 |
| **自寫 diffusers 服務** | 高(完全掌控) | 相依最少、介面想怎麼定就怎麼定、最容易做到環境可重現 | **所有東西都要自己寫**:排程、記憶體管理、模型切換、取樣器、各種格式支援。工作量最大,且多半是在重造已經存在的輪子 |

### 建議:ComfyUI,以無介面模式常駐,外面再包一層很薄的自有 HTTP 介面

**為什麼還要再包一層,而不是直接把 ComfyUI 的 API 當成交付介面:**

1. 呼叫端只該認得「送描述 → 拿圖」這一組呼叫。ComfyUI 的工作流 JSON 會因為節點改版而變動,
   那是伺服器內部的事,**不該漏到呼叫端**。
2. 日後若整個換掉底層(例如改成自寫服務),呼叫端一行都不用改。

**這層薄介面至少要提供:**

- 送出一次產圖請求:文字描述、反向描述、尺寸、**隨機種子**、模型識別、步數
- 查詢狀態 / 取回結果
- 健康檢查:服務活著嗎、看得到 GPU 嗎、目前 VRAM 用量多少
- 🔴 **同一組參數 + 同一個隨機種子,必須產出位元層級相同的圖。** 這是驗收項,不是加分項
  (沒有這個,就無法重跑、無法比較、無法回報問題)

## 六、風險登記

走這條路,會新增以下目前不存在的失敗模式。

| # | 風險 | 一句話後果 |
|---|---|---|
| 1 | 裝到以 CUDA 12.8 以下建置的 PyTorch | 顯示卡完全不能用,**而錯誤訊息指向「硬體不支援」,排查方向會整個走偏** |
| 2 | 顯示卡驅動或系統更新打壞可用組合 | 某天早上服務起不來,前一天還好好的;沒有版本紀錄就無從回頭 |
| 3 | VRAM 被桌面其他程式吃掉 | 同一份請求有時成功、有時記憶體不足,**看起來像隨機故障** |
| 4 | 產圖軟體或自訂節點自動更新 | 同一份工作流突然跑不動,或畫出不一樣的圖,**而沒有人改過任何設定** |
| 5 | 模型檔被換掉,或不同時間抓到不同版本 | 風格悄悄變了,**沒有任何錯誤訊息** —— 這是本表裡最安靜的一種 |
| 6 | 隨機種子不可重現 | 無法重跑、無法比較兩次結果、無法回報問題 |
| 7 | 服務無聲掛掉或卡死 | 工單一直堆積,呼叫端只看到逾時,不知道是慢還是死了 |
| 8 | 單張耗時遠超預期 | 上層流程的節奏假設失效,但要等到量產才會發現 |
| 9 | 這是桌機不是伺服器 | 有人關機、有人拿去打遊戲、有人讓它睡眠 —— **服務可用時間不等於 24 小時** |
| 10 | 第一次成功是手動拼湊出來的,沒有人記得怎麼辦到的 | 機器一重灌就全部重來,且不保證能重現 |
| 11 | **電源供應器瓦數不足**(實際瓦數目前無人知道,見第二節) | GPU 滿載瞬間當機 / 藍畫面 / 整機重開,**平常用都正常**;排查會全部耗在驅動與軟體上,而那裡什麼都查不到。**嚴重度與第 1 項同級** |
| 12 | **系統記憶體不足**(32 GB 剛好等於經驗法則下限) | **不會報錯,只會變得很慢** —— 從數十秒變成數分鐘,看起來像「這台電腦就是慢」,**容易被誤判成 GPU 不夠力而去考慮換顯示卡** |
| 13 | **磁碟剩餘空間不足**(總容量 2 TB,但剩多少無人知道) | 模型下載到一半失敗,或訓練跑到一半因為檢查點寫不下而中斷 |

📌 **第 11、12、13 項是 2026-10-05 加入的** —— 加入的原因是委託方的完整機器規格
(CPU / 記憶體 / 系統碟)**一直都在紀錄上,只是初版交付包沒有把它帶進來**。
三項都不改變本文的整體可行性結論(見下),但**第 11 項是本表裡唯一可能讓機器
當場跑不起來的風險**,請優先處理。

**可行性結論有沒有因此改變:**

- **推論(產圖)的結論不變** —— 仍然判定可行,且 8 位元量化的建議從「省 VRAM」
  升格為「同時省 VRAM 和系統記憶體」,**理由變強了**。
- 🔴 **訓練 / 微調的結論變得更保守。** 原本只有一個限制(VRAM 16 GB 須開三個省記憶體選項);
  現在是**兩個限制同時成立** —— 系統記憶體 32 GB 也剛好只踩在下限上。

**對應的最低限度要求(請視為交付的一部分):**

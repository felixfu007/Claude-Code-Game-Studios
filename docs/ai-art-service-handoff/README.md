## 一、要建的是什麼(一段話)

一台跑在 Windows 桌機上的**本機服務**:外部程式用 HTTP 呼叫它、附上文字描述與參數,它用 GPU 產生圖片並回傳。
目標硬體(委託方 2026-09-29 提供的書面紀錄,**非本交付包量測**):

| 項目 | 值 |
|---|---|
| CPU | AMD Ryzen 7 7700(8 核 16 緒) |
| GPU | **NVIDIA RTX 5070 Ti,16GB GDDR7,Blackwell 架構(`sm_120`)** |
| 系統記憶體 | 32 GB DDR5-6000 |
| 系統碟 | Kingston KC3000 2TB,PCIe Gen4 NVMe |
| 電源供應器 | ❓ **未知** |
| 磁碟剩餘空間 | ❓ **未知**(只知總容量) |
| Windows 版本 | ❓ **未知** |

逐項的「夠不夠、不夠會怎樣」評估在第一章第二節。

去雲端空間(Google Drive、GitHub 或其他)取工單、呼叫這支 API、把成品放回去的那一支橋接程式,
**跑在委託方自己的機器上,不是委託範圍**。

## 四、🔴 最容易出錯的一條:版本鏈

完整說明在第一章第三節,這裡只放結論與獨立查證紀錄:

| 項目 | 最低版本 |
|---|---|
| NVIDIA 驅動(Windows) | **570.65**(CUDA 12.8 GA);**572.61**(CUDA 12.8 Update 1) |
| CUDA | **12.8** |
| PyTorch | **2.7.0**,且**必須是以 CUDA 12.8 建置的版本**(版本字串帶 `+cu128`) |

**這條鏈有兩個入口會出錯,而且第二個比較隱蔽:**

1. **裝到舊版 CUDA / 驅動** → 錯誤訊息是 `sm_120 is not compatible...`,
   🔴 **這句話會讓人誤判為「這張顯示卡不支援」,實際上只是裝錯版本。**
2. 🔴 **PyTorch 版本號夠新,但它是用 CUDA 12.6 建置的** —— `pip install torch` 用預設來源就可能中獎。
   **版本號檢查會通過**,但 `sm_120` 不在它的編譯目標裡,**撞的是一模一樣的錯誤訊息。**
   **確認方式**:裝完印出版本字串,必須看到 `+cu128` 尾碼。

**獨立查證紀錄**(2026-10-05,由委託方自行查核,非承包方自述):

- [NVIDIA CUDA Toolkit 12.8.0 Release Notes](https://docs.nvidia.com/cuda/archive/12.8.0/cuda-toolkit-release-notes/index.html)
- [Official support for sm_120 (RTX 50-series / Blackwell) in stable PyTorch builds — pytorch/pytorch#164342](https://github.com/pytorch/pytorch/issues/164342)
- [Install NVIDIA Drivers and CUDA for RTX 50 series — LeaderGPU](https://www.leadergpu.com/articles/616-install-nvidia-drivers-and-cuda-for-rtx-50-series)
- [PyTorch Versions and Supported NVIDIA GPU Compute Capability Levels (2026-06)](https://journal.qualiteg.com/pytorch_and_supported_gpu_version/)

⚠️ **CUDA 13.x 能不能用,查不到確證。** 建議先走 12.8 這條已知可行的路把第一張圖跑出來,再談升級。

## 五、交付時必須附上的「環境指紋」

**這是驗收的一部分,不是可選項。** 它的用途是:日後任何人接手這台機器時,
不必相信任何人的自述,就能知道它當初是在什麼環境下跑成功的。

1. 顯示卡驅動版本(`nvidia-smi` 原始輸出)
2. CUDA 版本
3. PyTorch 版本字串(**必須看得到 `+cu128` 尾碼**)
4. `torch.cuda.get_device_capability()` 的**原始輸出**
5. 模型權重檔的 **SHA256**
6. 產出單張圖的耗時
7. VRAM 峰值用量
8. 作業系統版本
9. 產圖框架的版本或 commit

🔴 **請附原始輸出,不要只附結論數字。** 結論可以手打錯,原始輸出不會。

## 六、🔴 驗收時最該盯的幾條(它們做錯了,委託方不會立刻發現)

第三章末有完整清單,這裡點名四條最隱蔽的:

1. **批次產圖的「全有全無」語意被偷偷改成「部分成功也算成功」** ——
   平常測不出來,只有卡在 VRAM 邊界、批次中途失敗那一刻才會暴露,
   **而那正是最少被測試覆蓋到的情境。**
2. **健康檢查端點回「GPU 正常」但其實沒有真的碰 GPU**(例如只讀了快取的數字)——
   GPU 正常時,敷衍的實作跟認真的實作**回應一模一樣**;
   **而「出事時說真話」正是這個端點存在的唯一理由。**
3. **「同參數 + 同隨機種子 = 完全一樣的圖」可能只是看起來成立** ——
   若產圖框架不保證逐像素一致而承包方沒有誠實揭露,
   **要等到真的拿它做版本比對時才會發現圖其實有微小差異。**
4. **伺服器重啟時卡在進行中的工作怎麼處理** ——
   只有「真的中途重啟、而且剛好有工作在跑」才會暴露,一般功能測試完全測不到。

## 七、委託方自己要先確認的事(承包方無從得知)

1. 🔴 **電源供應器瓦數 —— 這是派工給承包方之前就該確認的一件事,不是驗收項。**
   **打開機殼看電源側面標籤就有,不花錢、不需要任何工具、幾秒鐘。**
   - 顯示卡板卡功耗 300 W;原廠建議系統總電源 750 W(但那是以高功耗 CPU 估的,
     本機 CPU 標稱 65 W,壓力較小)。**目標值 750 W,650 W 是下限。**
   - 🔴 **低於 650 W 請先回報再動工。**
   - **為什麼不能留到最後**:供電不足的症狀是「GPU 滿載那一瞬間當機 / 藍畫面 / 整機重開,
     平常用都正常」。承包方第一直覺會去查驅動、查 CUDA、查產圖軟體 —— **那些地方什麼都查不到。**
     而且**它只在滿載時才會出現,可能已經做了兩週才第一次撞到。**
2. 🔴 **系統記憶體 32 GB 剛好等於下限,零餘裕。**
   查證到的經驗法則是「系統記憶體至少 2 倍顯示卡記憶體」—— 16 × 2 = 32,**剛好踩在線上。**
   - **不夠的症狀不是錯誤訊息,是「變得很慢」**(系統動用分頁檔,不崩不報錯,數十秒變數分鐘)。
   - 🔴 **接手的人非常容易把它誤判成「顯示卡不夠力」而去考慮換顯示卡 —— 那會花錢,而且不會解決問題。**
   - 降風險:優先用 8 位元量化版模型、跑圖時關瀏覽器、確認分頁檔沒被關掉。
3. **磁碟剩餘可用空間**(只知總容量 2 TB)。
   量級感:一套完整高階模型環境約 35~40 GB,8 位元量化版約 18~20 GB ——
   **總容量不是瓶頸,但剩多少沒人知道。** 另:訓練的中間檔單次可能額外吃數十 GB **且不會自己清**。
4. **Windows 版本**(`winver` 一行就有)。影響驅動與相依套件的安裝路徑。
5. **要用哪個模型,以及它的授權條款允不允許商用。**
   不同模型的條款差異很大(有的無營收門檻,有的有年營收門檻並要求標示來源)。
   **詳見第四章第五節 —— 那一節不構成法律意見,但它列出了要確認哪些事。**
6. **傳輸方式**(工單怎麼進來、成品怎麼出去)。不在本委託範圍,但要有人做。

### 3. 建議但非必要:A/B 背景變體的存在理由已經消失,建議改成 8 個不同 seed

### 新查到的事實:非正方形結構上可行,但有一個我們看不到的上限

協調者讀了對方服務驗證邏輯與兩份設定檔,原始輸出:

```
# ai_art_service/service.py:229-238(驗證邏輯)
        width, height = body.get("width"), body.get("height")
        if type(width) is not int or type(height) is not int:
            raise ApiError(400, "INVALID_PARAMETER", "width and height must be integers.")
        for dimension in (width, height):
            if (
                dimension < self.config.min_dimension
                or dimension > self.config.max_dimension
                or dimension % 8
            ):
                raise ApiError(400, "INVALID_PARAMETER", "Dimensions must be in the published range and divisible by 8.")
```

→ **寬高不必相等**,只要兩邊都落在 `[min_dimension, max_dimension]` 範圍內、且都能被 8 整除。`896`、`1152` 兩者都是 8 的倍數,這部分沒問題。

但 `max_dimension` 的生效值,兩份來源互相矛盾:

```
# ai_art_service/config.py:123 —— 設定檔沒寫這個鍵時的程式預設
min_dimension, max_dimension = int(dimensions.get("min", 64)), int(dimensions.get("max", 1024))

# config.example.json:57 —— 隨附範例設定檔
  "width_height_range": {
    "min": 64,
    "max": 1536
  },
```

若家用端部署時沒覆寫這個鍵 → 生效值是程式預設 **1024**,`896×1152` 會被退件(1152 > 1024)。
若家用端套用了範例設定檔的 **1536** → 可以過。
🔴 **協調者從公司端查不到家用端實際部署用的是哪一個**——那是對方本機設定檔,真值只能靠對方服務自己回報的 `width_height_range` 欄位(`service.py:165` 有公開這個欄位,但要在他們機器上打 API 才讀得到)。`08` 號手冊也沒有記載這個數字。

### 2. 若每張都要重畫,80 張的成本,以及是否該改變「先產 80 張再挑」的流程

【判斷】**應該改變流程,不建議 80 張全部都畫區域。**

成本估算(人工,每張抓 2–5 分鐘框 4 個矩形,需要目視角色實際位置):80 張 × 2–5 分鐘 ≈ 160–400 分鐘(2.5–7 小時)。這是在「80 張裡大部分最後會被淘汰」的前提下發生的——等於多數矩形工都是白工。

`15` 號文件第三節自己已經留了這條路:「若貴方暫時不想畫區域,也可以只請我方『先跑去背+降採樣看看』。流程會跑完,但狀態會是 FAIL(只因第 4 項)⋯⋯我方會改交付去背後的原尺寸圖+報告」——這正好是兩段式流程需要的中間產出。

建議的兩段式流程:
1. **第一輪(80 張全部)**:只請去背+降採樣,不給區域檔。用去背是否成功(`edge_key` 有沒有 SKIP)、構圖(有沒有碰邊)、畫風觀感,篩出候選短名單(例如 5–10 張)。
2. **第二輪(短名單)**:只替短名單裡的圖手畫區域檔,跑完整管線拿到真正的 PASS 成品。

這樣區域檔的人工成本只發生在真正會被用到的圖上。

**目前判斷:是,方向正確,建議繼續這條路。但有一項「技術檢查全過、人眼卻覺得不夠乾淨」的落差(32×40 成品的軀幹/腿部偏花),以及兩項客觀瑕疵(淺藍地面陰影、制服灰非 navy)——這三項我都建議「先觀察、暫不改 prompt」,理由分別寫在各小節。**

### 1. 畫風是不是真的扁平/cel-shade,還是只是換了一種厚塗?

【觀察,開全解析度 `animagine_seed2001_magenta.png`】整體明顯比厚塗插畫更「平」:外輪廓是乾淨的粗黑描邊;衣服皺褶是用**線條**畫出來(像卡通分色線稿),不是柔和漸層陰影過渡;上衣明暗交界清楚、邊界硬;頭髮雖有一點高光但範圍小。對照 `styleA_seed2003_preview_tol32.png`(舊 SDXL):外套領口到肩膀的色調是漸變的、腳下陰影邊緣是模糊暈開的,明顯更painterly。

【判斷】兩者並排看,新底模確實往「扁平/卡通分色」方向移動了一截,**不是只是換了一種厚塗**——但也不是教科書等級的「死板三階 cel-shade」:頭髮、少數高光區仍有柔和色調過渡。**用「比舊的扁,但不是純三階」描述比較準確,不要誇大成『問題已完全解決』。**

### 2. 跟舊 SDXL 批次比,這條路值不值得繼續?

**判斷:值得,建議繼續。** 理由:
- 上一批換底模的理由是「源頭連續漸層厚塗與目標扁平 cel-shade 不相容,且 prompt 解決不了」——這次拿到的第一張圖直接反駁了「不相容」這個前提的嚴重程度:兩張並排比較,新底模的分色方式明顯更接近目標。
- 管線本身也第一次被證明能跑通到底(見下一小節),把「畫風方向對不對」與「管線能不能用」兩個風險都往好的方向推進了一步。
- 剩下的問題(見第 3、4 小節)屬於「需要人工篩選/觀察」層級,不是「prompt 結構性做不到」層級——這是兩種完全不同的風險,後者才是上一批建議換底模的真正理由。

### 3. 32×40 成品看起來像不像一顆可用的棋子?

【觀察,`animagine_seed2001_32x40_x10_preview.png`,放大 10 倍】整體剪影(站姿、斜扛的斧頭、頭頂髮髻)在小圖上還算看得出來是「一個人扛著一把斧頭」。但**軀幹到大腿這一段,顏色是一塊一塊深淺不一、互相不連貫的小色塊**(灰、深藍、粉膚色、淺藍交錯),不像乾淨的「上衣一塊色+褲子一塊色」那種好辨識的分色。

【觀察,`animagine_seed2001_32x40_check_report.json`】機械檢查**四項硬性檢查全部 PASS**:尺寸正確、0 個離色票像素、描邊 3 種色相且連續無缺口、alpha 二值化乾淨。

【判斷,兩者的落差】技術檢查過關,不代表人眼覺得乾淨——這正是本專案一貫的教訓(`coding-standards.md` 明文:自動檢查從沒抓到過視覺缺陷,都是人開圖看到的)。**我的判斷是:這裡的花雜感,原因是源頭 1024 插畫本身表面細節太多**(背帶扣具、袖口反光條紋、衣服皺褶線、斧柄金屬光澤),這些在 1024 時每處各自只佔幾十像素,縮到 32×40 時通常只分到 1 個輸出像素甚至更少,於是各自就近量化成獨立色塊,而不是先融合成一大塊再量化——**這是推論,不是我逐步追蹤演算法驗證過的結論**,但與驗收報告裡「23 種顏色、各材質矩形內描邊/色票都合法」這件事並不矛盾,兩者可以同時成立。

**要不要接受**:這是美術判斷題,建議**先不要單憑這一張下定論**——樣本數是 1。建議 Q-A 那 8 張出來後,挑 2–3 張構圖差異大的一起跑完整管線比較:若軀幹花雜是這一張構圖(斧頭斜放、背帶複雜)特有的,換一個細節較少的 seed 可能就乾淨很多;若 8 張普遍都花,才是角色設計本身的細節密度對 32×40 來說太高,需要回頭簡化設計(減少背帶、徽章、反光條這類小裝飾)。

### 4. 兩項客觀瑕疵,是否處理?

**①淺藍色地面陰影(連到角色本體,去背後仍留著)**

【觀察】`animagine_seed2001_magenta_preview_tol32.png` 左右兩個畫面都能看到腳下一塊淺藍橢圓,去背後(右側綠底)依然存在,且與靴子像素相連。

【判斷】**需要處理,但不建議現在改 prompt。** 現有負向 prompt 已經有 `shadow on background` 這個標籤,而這張圖依然畫出了陰影——代表這個標籤本來就沒有穩定抑制住這個現象,再加碼一個新標籤(例如泛用的 `shadow`)風險是連帶壓到我們其實想要的、角色身上的三階明暗陰影,這與 `13` 號文件已記錄過的「標籤顆粒度不到位、無法只關掉某個局部概念」是同一種結構性限制。
**建議**:暫不改 prompt,改成「人工篩選標準之一」——8 張挑選時把「陰影是否明顯、是否連到角色本體」列為評分項,優先選陰影不明顯或顏色更接近中性灰黑的那幾張。若 8 張裡全部都有類似陰影,才值得花一輪請家用端評估後製工具加一個「偵測並去除緊貼腳底的獨立色塊」選項。

**②制服是灰色,不是規格的 navy blue**

【觀察】正向 prompt 明確寫了 `navy blue uniform`,實際渲染出來是灰色。

【判斷】**需要觀察,但不建議現在改 prompt——樣本數只有 1,不足以下結論。** 一個合理假設(推論,未驗證):`firefighter` 這個標籤在訓練語料裡可能帶有偏灰/卡其色的「消防裝備」視覺慣性,和 `navy blue uniform` 互相競爭,這次是灰色贏了;但也可能只是這個 seed 剛好如此。本專案剛好有過「只憑一次量測就下定論,結果方向錯」的前例(`技術偏好` 文件「(A) 的精確定義」節記載的棋盤量測案例),性質類似,只是換成美術領域——不應該用 1 張圖就判定「`navy blue uniform` 在這個 checkpoint 上無效」。
**建議**:8 張出來後統計「幾張是 navy blue、幾張是灰」。若多數仍是灰,再考慮加權語法(例如 `(navy blue uniform:1.3)`,前提是服務支援此語法——**未查證**)或換句話說(`dark blue uniform`)當下一步;現在先不動。

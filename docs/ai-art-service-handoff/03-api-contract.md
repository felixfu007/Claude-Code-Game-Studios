# 第三章:API 契約

> 本章是整份交付包的驗收依據 —— 外包方交付的伺服器算不算「做完了」,以本章規定的介面與
> 行為為準。本章完全自給自足:讀者不需要知道委託方是什麼產品、用什麼引擎。你只需要知道:
> **委託方要一支本機跑的 HTTP 伺服器,吃一段文字描述,吐出一張或多張圖。**

## 零、讀這份文件前必須知道的事

**委託方從未在真機上跑過任何一張圖。這份 API 契約是設計規格,不是從可運作系統反推出來的。**

- **「設計決策」**:撰寫者依軟體工程一般考量(例如「長任務該用非同步」「同一條規則不要有
  兩份實作」)自行設計,**沒有**對照特定產圖框架驗證過。有更好做法歡迎提出,但請在交付
  文件寫明「原方案、改成什麼、為什麼」,不要默默改掉。
- **「業界慣例」**:指 Stable Diffusion 系生態系常見做法,**沒有**針對你最終選用的框架
  逐項驗證,請自行核對適用性。
- 本章沒有明講依據的具體數字(逾時秒數、保留期限小時數……)一律是**建議值,不是鐵律**,
  每處都會標明。

## 一、範圍重申

委託方只外包「伺服器本身 + 這一支本機 HTTP API」。**明確不在範圍內**:工單從哪來、成品
送去哪(橋接程式跑在委託方自己機器上,不交給外包方)、圖片品質機械檢查、美術風格判定、
硬體選型/部署/安全性(其他章節負責,本章不複述)。

**設計決策,請連同理由一起看**:伺服器只認得「本機 HTTP 請求進、回應出」,**對傳輸層完全
無知**。好處:委託方日後不管用雲端硬碟、版控、或任何方式搬運工單與成品,**伺服器與這份
API 契約一個字都不用改** —— 橋接程式是呼叫這支 API 的「呼叫端」,不是 API 本身。

## 二、API 總覽

| 方法 | 路徑 | 做什麼 |
|---|---|---|
| `POST` | `/v1/jobs` | 提交一筆產圖請求,立即回傳工作 id(不等完成) |
| `GET` | `/v1/jobs/{job_id}` | 查詢工作狀態 |
| `GET` | `/v1/jobs/{job_id}/result` | 工作成功後取得成品清單(中繼資料 + 下載連結) |
| `GET` | `/v1/jobs/{job_id}/images/{index}` | 下載第 `index` 張圖的原始位元組(PNG) |
| `DELETE` | `/v1/jobs/{job_id}` | 要求取消(盡力而為,見第七節) |
| `GET` | `/v1/models` | 列出可用模型/LoRA/取樣器與其數值範圍 |
| `GET` | `/v1/health` | 行程存活檢查(極快,不碰 GPU) |
| `GET` | `/v1/health/gpu` | GPU 真實可用性檢查(較慢,實際觸碰 GPU) |

路徑皆掛 `/v1/` 下(**設計決策**,沿用版本化 REST 慣例,未針對特定框架驗證)。

## 三、共用慣例

所有 body 皆為 `application/json`(圖片下載端點例外,回 `image/png` 原始位元組)。時間用
ISO 8601 UTC。`job_id` 由伺服器產生,全域唯一即可,格式不是驗收重點。所有錯誤共用同一
信封(第十節)。Enum 字串一律大寫底線分隔,例如 `QUEUED`。

## 四、提交產圖請求 —— `POST /v1/jobs`

```json
{
  "prompt": "a red apple on a wooden table",
  "negative_prompt": "blurry, low quality",
  "width": 128, "height": 128,
  "seed": null, "steps": null, "cfg_scale": null, "sampler": null,
  "batch_size": 1,
  "model": null,
  "loras": [{ "name": "pixel-art-style-v2", "weight": 0.8 }],
  "upscale_mode": "auto"
}
```

| 欄位 | 型別 | 必填 | 說明 |
|---|---|---|---|
| `prompt` | string | 是 | 正向提示詞。最大長度由 `/v1/models` 公告,超過回 `INVALID_PARAMETER` |
| `negative_prompt` | string | 否 | 預設空字串 |
| `width`/`height` | int | 是 | **目標輸出尺寸**(例如 128×128 像素風小圖)。**不是**模型內部出圖尺寸,見第五節 |
| `seed` | int\|null | 否 | 省略代表伺服器隨機產生。**伺服器必須在結果回寫實際使用的 seed** |
| `steps` | int\|null | 否 | 省略時用目前模型的建議預設值(`/v1/models` 查得) |
| `cfg_scale` | float\|null | 否 | 同上 |
| `sampler` | string\|null | 否 | 合法值見 `/v1/models`,不在清單內回 `INVALID_PARAMETER` |
| `batch_size` | int | 否(預設 1) | 要出幾張。**全有全無語意**:要嘛全部成功要嘛整筆判失敗,不回傳部分成品(理由見第七節) |
| `model` | string\|null | 否 | 省略用目前已載入的預設模型 |
| `loras` | array\|null | 否 | `[{name, weight}]`,省略代表不疊加 |
| `upscale_mode` | enum | 否(預設 `auto`) | `"auto"` / `"native_only"`,見第五節 |

**所有數值欄位的合法範圍由伺服器透過 `/v1/models` 公告,本契約不寫死任何具體數字** ——
合理範圍跟外包方最終選用的模型有關,寫死會變成本章替外包方做技術選型。

**回應(成功,`202 Accepted`)**:
```json
{ "job_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6", "status": "QUEUED", "created_at": "2026-10-05T08:30:00Z" }
```
用 `202` 而非 `200`:語意上明確表達「收下了,但還沒做完」,呼應第六節的非同步設計。

## 五、輸出尺寸:原生解析度 vs 目標尺寸

**背景**:委託方要像素風小圖(例如 128×128),遠小於多數擴散模型的原生訓練解析度。直接
出小圖通常品質較差,**業界慣例**是先出原生解析度再縮小 —— 此落差幅度未針對最終選用模型
驗證過。

**本契約裁決:換算由伺服器端做,不是呼叫端。** 理由:

1. 只有伺服器知道自己載入的模型原生解析度是多少,不該要求呼叫端維護對照表。
2. **本專案在別處付過代價**:同一條換算規則若兩端各自實作一份,黑箱測試無法分辨「共用
   同一份」還是「兩份碰巧算出一樣答案」——之後任何一邊修改都可能悄悄產生不一致。因此這條
   規則的權威歸屬寫死在第十五節,只能有一份實作。
3. 呼叫端只需要說「我要 128×128」,不必知道背後發生了什麼。

**API 設計**:`upscale_mode="auto"`(預設)由伺服器自行決定原生出圖尺寸、出圖後縮小;
`"native_only"` 則強制依 `width`/`height` 直接出圖(可能品質較差,供呼叫端自行比較用)。
**伺服器必須在成品中繼資料誠實回報實際做了什麼**(`native_generation_size` /
`resize_applied` / `resize_filter`,見第九節),不得黑箱轉換。縮放演算法本身不限定種類,
只要求「公告、一致、可重現」。**縮小後的像素化/色盤量化明確不在外包範圍**,由委託方下游
流程處理,避免同一類轉換邏輯再分散到第二個地方。

## 六、回應模式:為什麼選非同步

**設計決策**:單張圖可能要數十秒,多張更久。同步 HTTP 容易撞到用戶端函式庫預設的
30~60 秒逾時,且等待期間呼叫端無法得知進度。**本契約採非同步**:`POST /v1/jobs` 立即回
`job_id`;呼叫端輪詢 `GET /v1/jobs/{job_id}`;終態後呼叫 `.../result` 取得成品。伺服器
**建議**在狀態回應附 `Retry-After` header 提示輪詢間隔(建議值,非硬性,但完全沒有任何
提示會記為缺口)。

## 七、工作狀態機

合法狀態:`QUEUED`、`RUNNING`、`SUCCEEDED`、`FAILED`、`CANCELLED`、`EXPIRED`。後四者為
終態,**一旦進入終態不得再轉換**(`EXPIRED` 是終態之後的終態,見下表)。

| 起始狀態 | 事件 | 結束狀態 | 備註 |
|---|---|---|---|
| (尚未建立) | `POST` 被接受 | `QUEUED` | 佇列已滿時直接 `429 SERVER_BUSY`,**不建立工作、不配發 `job_id`** |
| `QUEUED` | 排程器取出執行 | `RUNNING` | |
| `QUEUED` | `DELETE` | `CANCELLED` | 尚未開始執行,保證成功 |
| `RUNNING` | 全部圖片成功 | `SUCCEEDED` | |
| `RUNNING` | 任何原因失敗(含 OOM) | `FAILED` | 全有全無:`batch_size=4` 只壞 1 張仍整筆判失敗,不回傳其餘 3 張 |
| `RUNNING` | `DELETE` | `CANCELLED`(盡力而為) | 可能來不及,仍可能落在 `SUCCEEDED`/`FAILED` —— 正常競態,**呼叫端以之後查到的實際終態為準** |
| 任一終態 | 保留期限到期 | `EXPIRED` | 期限長度由伺服器設定檔決定,本契約只要求「有期限、可設定」 |
| 重啟前為 `QUEUED`/`RUNNING` | 伺服器程序重啟 | `FAILED`(`code=SERVER_RESTARTED`) | **最低要求**,見第十二節 |

**為什麼全有全無是刻意簡化**:部分成功會讓「這筆工作算不算完成」變模糊,呼叫端還要對帳
哪幾張成功。全有全無讓重試單純 —— 失敗就整筆重新提交同樣 `batch_size`。若外包方因效能
考量想改成部分成功,請先提出討論,不要默默改掉。

## 八、查詢狀態 —— `GET /v1/jobs/{job_id}`

```json
{
  "job_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "status": "FAILED",
  "created_at": "2026-10-05T08:30:00Z", "started_at": "2026-10-05T08:30:02Z", "finished_at": "2026-10-05T08:30:19Z",
  "request_echo": { "prompt": "a red apple on a wooden table", "width": 128, "height": 128, "steps_used": 20, "cfg_scale_used": 7.0, "seed_used": null },
  "error": { "code": "OUT_OF_MEMORY", "message": "CUDA out of memory while allocating batch of 4 at native size 1024x1024", "retryable": true }
}
```

`request_echo` **必須**把所有省略欄位的**實際使用值**填回(例如實際用了幾步),供呼叫端
日後重現同一張圖。`error` 只在 `status=="FAILED"` 時存在。`error.retryable` 是概括提示,
**不是權威** —— 複雜情境(例如 `batch_size=1` 仍 OOM,代表再重試也沒用)以第十節文字為準。

## 九、取得成品與圖片傳輸

```json
{
  "job_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "images": [{
    "index": 0, "seed_used": 1234567890,
    "native_generation_size": { "width": 512, "height": 512 },
    "output_size": { "width": 128, "height": 128 },
    "resize_applied": true, "resize_filter": "lanczos",
    "download_url": "/v1/jobs/3fa85f64-5717-4562-b3fc-2c963f66afa6/images/0",
    "content_type": "image/png", "size_bytes": 45213
  }],
  "expires_at": "2026-10-06T08:30:19Z"
}
```

**圖片怎麼回,三個選項的代價**:(a) base64 內嵌 JSON —— 膨脹約 1/3,16GB 記憶體的機器
在一次多張時這筆額外開銷不可忽略;(b) 伺服器本機檔案路徑 —— 耦合檔案系統佈局與執行身份,
呼叫端不同使用者/容器時讀不到;(c) 獨立下載端點回傳原始位元組 —— 標準 `Content-Length`/
`Content-Type`、可選支援 `Range` 續傳、多張可平行下載,不必等最大那張序列化完。

**本契約選 (c)**:成品清單只放中繼資料與下載連結,位元組由 `.../images/{index}` 回傳,
`Content-Type: image/png`(固定無損格式,避免 JPEG 區塊壓縮弄糊像素邊緣)。

`expires_at` 到期後再查詢,回 `410 JOB_EXPIRED`,**不是** `404 JOB_NOT_FOUND` —— 404 代表
「這個 id 從來沒發生過」,410 代表「發生過,但資料已清除」,兩者在除錯時意義不同,
不建議合併。

## 十、錯誤碼

錯誤信封:
```json
{ "error": { "code": "OUT_OF_MEMORY", "message": "人類可讀,不建議拿來做程式判斷邏輯", "retryable": true, "details": {} } }
```

| `code` | HTTP | 情境 | 呼叫端怎麼辦 |
|---|---|---|---|
| `UNAUTHORIZED` | 401 | 缺少認證標頭,或金鑰不正確(兩種情況回應刻意一致,見第十六節) | 檢查呼叫端設定的金鑰是否正確後重送;若這是正式運作中預期外出現的狀況,視為設定/憑證問題,**停止自動重試並通知人工**——重試不會讓這個錯誤消失 |
| `INVALID_PARAMETER` | 400 | 參數型別錯/超出公告範圍/必填缺漏 | 修正後重送,不要原封不動重試 |
| `MODEL_NOT_FOUND` | 400 | `model`/`loras[].name` 不存在 | 查 `GET /v1/models` 取得合法 id,修正後重送 |
| `JOB_NOT_FOUND` | 404 | `job_id` 從未存在 | 不要重試同一個 id,確認來源是否打錯 |
| `JOB_EXPIRED` | 410 | `job_id` 存在過但已過保留期限 | 需要的話用原始請求內容重新提交新工作,無法復原舊工作 |
| `IDEMPOTENCY_KEY_CONFLICT` | 409 | 同一把 `Idempotency-Key` 帶了不同內容(第十一節) | 通常是呼叫端自己的 bug(重用 key),換新 key 重送 |
| `SERVER_BUSY` | 429 | 佇列已滿,**工作未被建立**(無 `job_id`) | 依 `Retry-After` 秒數之後重送整個請求 |
| `OUT_OF_MEMORY` | 503 | 產圖中 VRAM 不足 | **不是單純等待就會解決** —— 先降 `batch_size`/尺寸再試;`batch_size=1` 仍發生代表硬體容量問題,應停止自動重試並通知人工 |
| `MODEL_LOAD_FAILED` | 500 | 模型/LoRA 檔案載入失敗 | 伺服器端狀況,**不建議自動重試**,通知人工檢查環境 |
| `INTERNAL_ERROR` | 500 | 其他未分類例外 | 記錄完整回應;設保守重試上限(例如 2~3 次)後停下通知人工 |

**為什麼 503 的處置不是「等一下」**:看到 503 的直覺是等待重試,但 `OUT_OF_MEMORY` 的正確
處置其實是換更小的參數。**呼叫端不應只看 HTTP 狀態碼,必須讀 `error.code` 對應到上表文字**
——只給碼不給處置,呼叫端只會寫出「非 200 就重試」,對 `MODEL_LOAD_FAILED` 這類狀況是有害的。

## 十一、冪等性與重試

`POST /v1/jobs` 支援選填的 `Idempotency-Key` header(任意字串,建議 UUID)。同一把 key +
完全相同內容 → 回傳**原本那筆工作**的 `job_id`,不建立新工作(解決「送出後斷線,不確定
有沒有送達」的情境)。同一把 key + 不同內容 → `409 IDEMPOTENCY_KEY_CONFLICT`。不帶 key →
每次視為新工作。key 的有效期與工作保留期限一致,過期後視為全新的 key。

## 十二、伺服器重啟後的工作狀態(最低要求,非建議)

> 若伺服器程序重啟,任何重啟前處於 `QUEUED`/`RUNNING` 的工作,**必須**在查詢時轉為
> `FAILED`、`error.code="SERVER_RESTARTED"`。**不可以**回 `404 JOB_NOT_FOUND`(會讓呼叫端
> 誤以為是自己 id 打錯,而不是伺服器弄丟了它)。

不要求完整持久化續跑(屬加值項,不是必要項)——重啟時掃一遍並批次標記狀態,成本低,但能
避免一個會讓呼叫端除錯方向完全找錯地方的陷阱。

## 十三、健康檢查:行程存活 ≠ GPU 可用

CUDA context 可能已損壞、VRAM 可能卡死,但 HTTP 行程本身完全正常回應 —— 這是兩件不同的
事,必須分兩個端點。

- **`GET /v1/health`**:**不得**觸碰 GPU 或模型,建議 100ms 內回應。
  `{ "status": "ok", "uptime_seconds": 3600 }`
- **`GET /v1/health/gpu`**:**必須**實際觸碰 GPU(查 VRAM 或跑極小運算確認 context 存活),
  建議 2 秒內回應。
  `{ "gpu_available": true, "vram_total_mb": 16384, "vram_free_mb": 9210, "model_loaded": "sdxl-base-1.0", "last_successful_job_at": "2026-10-05T08:25:00Z" }`
  **此端點回 200 不代表 GPU 良好** —— 200 只代表健康檢查程式本身跑完,真正答案在
  `gpu_available` 欄位;只有 handler 自己掛掉/逾時才回非 200。刻意避免把「HTTP 有回應」跟
  「GPU 沒問題」疊在同一個狀態碼裡。

## 十四、能力查詢 —— `GET /v1/models`

```json
{
  "models": [{ "id": "sdxl-base-1.0", "native_resolution": { "width": 1024, "height": 1024 }, "default_steps": 30, "default_cfg_scale": 7.0, "max_batch_size": 4, "available_samplers": ["euler_a", "dpmpp_2m"] }],
  "loras": [{ "name": "pixel-art-style-v2", "compatible_models": ["sdxl-base-1.0"] }],
  "max_prompt_length": 1000,
  "width_height_range": { "min": 64, "max": 1024 }
}
```

呼叫端**可**用這份資料做預先檢查提升體驗,**但這只是 UX 優化,不是權威驗證**——伺服器在
`POST /v1/jobs` 當下**仍必須重新驗證**所有參數,不能假設呼叫端已檢查過(見第十五節)。

## 十五、每條規則由哪一端負責(唯一權威對照表)

| 規則 | 唯一負責端 | 說明 |
|---|---|---|
| 目標尺寸 → 原生出圖尺寸換算 | 伺服器 | 第五節,呼叫端只填最終尺寸 |
| 縮放演算法的選擇與執行 | 伺服器 | 第五節,呼叫端不執行任何影像縮放 |
| 參數合法範圍的最終驗證 | 伺服器 | `/v1/models` 只是參考,提交當下必須重新驗證 |
| Seed 的隨機產生 | 伺服器 | 省略時伺服器生成並回寫實際值 |
| Idempotency key 去重判斷 | 伺服器 | 第十一節 |
| 保留期限到期判斷 | 伺服器 | 第九、十二節 |
| 像素化/色盤量化(若未來需要) | **不在本契約範圍**,委託方下游流程 | 刻意不讓伺服器再長出第二套影像後處理邏輯 |

**關於 seed 數值範圍刻意不寫死**:是否限制在特定位元範圍跟外包方選用的框架有關,本章無法
替外包方做這個選型。若框架本身有限制,**請在交付文件的「已知限制」寫明,不要靜默截斷**
(靜默截斷會讓呼叫端以為自己指定的 seed 被採用,之後想重現同一張圖時會對不起來)。

## 十六、認證機制

**背景**:下方第十八節原本把認證標為「本章未設計的缺口」。**同一份交付包的《第四章:安全
與授權》第二節「網路暴露面——硬性要求」已把它列為硬性要求**(逐字:「無論選哪一種,API
本身都必須有身分驗證機制(金鑰或憑證),不能只靠『位址沒人知道』當作唯一防線」)——**為什麼
要有認證、威脅模型是什麼,見該節,本節不複述,只負責把它落實成本契約可驗收的具體規定。**

### 16.1 認證方式的契約形狀

- **標頭**:每個需要認證的請求必須帶 `X-API-Key: <字串>` 這個 HTTP 標頭。**設計決策**:
  不用 `Authorization: Bearer <token>`——`Bearer` 這個慣例在多數 HTTP 生態系裡隱含「這是
  一個可能有自己格式、簽章、過期時間的權杖」,而這裡要的只是一把不透明的共享密鑰,沒有
  內建過期機制。用專屬標頭名稱,契約本身就講清楚了這一點,不必讓外包方去猜該不該塞 JWT。
- **金鑰的值本身**:不透明字串,本契約不規定格式(不要求 JWT、不要求特定編碼)。
  **伺服器比對金鑰時必須使用常數時間比較(constant-time comparison)**,不得用一般字串
  相等比較逐字元提前中斷——這是避免時序攻擊的標準做法,實作成本低,沒有不做的理由,
  因此列為硬性要求而非建議。
- **金鑰的來源與輪替**:伺服器**必須**支援同一時間存在一把以上「目前有效」的金鑰。這是
  讓輪替不需要停機的機制:操作者先讓新舊兩把金鑰同時有效 → 把呼叫端設定換成新金鑰 →
  確認沒有呼叫端還在用舊金鑰 → 移除舊金鑰,**任何時間點都不會發生「所有呼叫端一起失效」**。
  本契約不規定有效金鑰清單存放在哪裡(檔案/環境變數/其他機制皆可,交給部署手冊決定),
  只規定行為:變更有效金鑰清單**不得**要求重新編譯或改程式碼;若需要重啟伺服器才能套用
  新清單,這是可接受的,但必須在交付文件寫明;**不可接受**的是金鑰被撤銷後仍無限期繼續
  有效(例如被永久快取、從不重新讀取)。
- **伺服器不得在原始碼裡寫死任何金鑰值,也不得內附一把「範例金鑰」在正式環境中仍然有效。**

### 16.2 哪些端點需要認證

| 端點 | 需要認證? | 理由 |
|---|---|---|
| `POST /v1/jobs` | 需要 | 消耗運算資源,且會建立新資料(新工作) |
| `GET /v1/jobs/{job_id}` | 需要 | 避免洩漏工作內容(`request_echo` 含完整提示詞)給未授權呼叫端 |
| `GET /v1/jobs/{job_id}/result` | 需要 | 同上,且是取得成品圖片的前置步驟 |
| `GET /v1/jobs/{job_id}/images/{index}` | 需要 | 圖片本身是委託方的資產 |
| `DELETE /v1/jobs/{job_id}` | 需要 | 會改變系統狀態 |
| `GET /v1/models` | 需要 | 洩漏伺服器內部配置細節(模型/LoRA 清單),沒有正當理由對外公開 |
| `GET /v1/health` | **不需要** | 見下方討論 |
| `GET /v1/health/gpu` | 需要 | 見下方討論 |

**健康檢查兩端點刻意分開判斷,附理由,不是隨意選邊**:

- `GET /v1/health` **不要求認證**。回應只有「活著」與開機時長兩個欄位,資訊量極低,不會
  洩漏模型、VRAM 或任何運算狀態。要求認證的代價是:監控工具(尤其是簡單的 TCP/HTTP 存活
  探測工具)不一定方便附加自訂標頭,而這支端點存在的唯一目的就是讓這類工具在不需要管理
  密鑰的狀況下確認服務是否還活著。真正的防線在網路暴露面本身(《第四章》規定伺服器不得
  對公開網際網路開放)——能連到這支端點的人已經先突破了那一層防線,這支端點本身不會再
  多給他任何有用資訊。
- `GET /v1/health/gpu` **要求認證**。回應含 VRAM 剩餘量、目前載入的模型、上次成功工作的
  時間——這些對攻擊者有操作價值,且這支端點真的會觸碰 GPU(有實際成本),不應該讓任何
  連得到網路的呼叫端免費觸發。監控工具若要用這支端點,一樣得配發金鑰——這是刻意接受的
  額外設定成本,換取不白白暴露系統狀態。

### 16.3 認證失敗與「工作不存在」的優先順序——刻意的判斷

⚠️ **常見陷阱**:若認證失敗與「`job_id` 不存在」回傳不同的碼或不同時序,能送請求過來的人
就能用這個差異反推「這個 `job_id` 到底存不存在」,即使他沒有有效金鑰。

**本契約的判斷**:`job_id` 是不可猜測的 UUID,單純列舉 id 存在與否的實際危害不大(不像
可預測的流水號)。**但本契約仍要求:認證檢查必須發生在任何資源查找邏輯之前**——伺服器
一旦判定金鑰缺漏或錯誤,一律回 `401 UNAUTHORIZED`,**不去查這個請求對應的 `job_id` 是否
存在**。選這個順序的理由不是「否則會被攻擊」,而是**這本來就是比較簡單、比較不容易寫錯的
實作順序**:認證中介層擋在路由邏輯最前面,不必為了「要不要洩漏資源存在性」另外寫特殊判斷
——順帶也就沒有這個側信道。**呼叫端收到 `401` 時,不應該把它讀成「這個 `job_id` 有效或
無效」的任何線索**,它只代表金鑰本身有問題。

## 十七、驗收測試清單

每條皆為「給什麼輸入 → 期待什麼輸出」,請提供實際請求/回應紀錄作為證據,不要用「功能正常」
這類形容詞描述。

| # | 輸入 | 期待輸出 |
|---|---|---|
| T1 | `POST /v1/jobs`,合法請求(`prompt` 非空、`width=128`、`height=128`、`batch_size=1`) | `202`,非空字串 `job_id`,`status="QUEUED"` |
| T2 | 緊接 T1 之後立刻 `GET /v1/jobs/{job_id}` | `status` 為 `QUEUED` 或 `RUNNING`;不可能是 `SUCCEEDED`/`FAILED`/`404` |
| T3 | 持續輪詢 T1 直到終態 | `SUCCEEDED`;`.../result` 回傳 1 筆;下載後實測像素尺寸恰為 128×128 |
| T4 | 兩次提交相同內容且指定同一 `seed` | 兩次 `seed_used` 相同;支援確定性取樣時逐像素差異為 0,否則至少 `seed_used` 一致並於文件註明框架限制 |
| T5 | 提交時省略 `seed` | 成品 `seed_used` 為具體非空數值,不是 `null` |
| T6 | `width=99999`(超出 `/v1/models` 公告上限) | `400 INVALID_PARAMETER`,回應**無** `job_id` |
| T7 | `model` 填不存在的 id | `400 MODEL_NOT_FOUND` |
| T8 | `GET /v1/jobs/{隨機未提交過的 uuid}` | `404 JOB_NOT_FOUND` |
| T9 | 相同 `Idempotency-Key` 送兩次相同請求 | 第二次 `job_id` 與第一次相同,只存在一筆工作 |
| T10 | 相同 key、第二次 `prompt` 不同 | `409 IDEMPOTENCY_KEY_CONFLICT` |
| T11 | `batch_size` 故意遠超 VRAM 容量 | `FAILED`,`error.code="OUT_OF_MEMORY"`;**且伺服器行程存活**——緊接著 `GET /v1/health` 仍 `200` |
| T12 | `GET /v1/health` | `200`,100ms 內,GPU 使用率無變化 |
| T13 | `GET /v1/health/gpu` | `200`,`gpu_available=true`,`vram_free_mb` 為合理整數 |
| T14 | `width=128,height=128,upscale_mode="auto"` | `native_generation_size` 寬高**皆大於 128**,`resize_filter` 非空字串 |
| T15 | `RUNNING` 時強制終止伺服器行程後重啟,再查詢該 `job_id` | `FAILED`,`error.code="SERVER_RESTARTED"`;**不可以**是 `404`,也不可無限停在 `RUNNING` |
| T16 | `DELETE /v1/jobs/{job_id}`,目標仍在 `QUEUED` | 之後查詢 `status="CANCELLED"`(保證成功) |
| T17 | `POST /v1/jobs`,不帶 `X-API-Key` 標頭,其餘參數合法 | `401 UNAUTHORIZED`,回應**無** `job_id`(工作未被建立) |
| T18 | `POST /v1/jobs`,帶一把格式正確但內容錯誤的金鑰 | `401 UNAUTHORIZED`,回應內容與 T17 **一致**(不得讓呼叫端分辨「完全沒帶」與「帶錯」兩種情況) |
| T19 | `GET /v1/health`,不帶任何認證標頭 | `200`(依第十六節設計,此端點不要求認證) |
| T20 | `GET /v1/health/gpu`,不帶任何認證標頭 | `401 UNAUTHORIZED`(依第十六節設計,此端點要求認證,與 T19 行為刻意不同) |

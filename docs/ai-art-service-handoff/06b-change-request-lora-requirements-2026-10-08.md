## 一、為什麼委託這件事:兩個至今零實測數據的問題

我方 2026-09-29 的驗證協議第〇節逐字記載,這次驗證要回答兩個**目前完全沒有實測數據**的問題:

1. **風格一致性守不守得住** —— 逐字:「AI 工具宣稱的『風格一致性』(Style Lock / LoRA)在
   本專案的具體約束下(**128×128、64 色、5 位角色跨數月**)能不能真的守住 —— 沒有實測
   任何一款工具的輸出」。
2. **16GB VRAM 訓練 LoRA 實際可不可行、要花多久** —— 逐字:「各模型/服務在 16GB VRAM 下
   訓練 LoRA 的實際可行性與所需時間……完全沒有觸及」。

🔴 **因此本次委託的驗收標準不是「做出一個 LoRA」,而是「交付物足以回答上面兩題」。**
一個訓練成功、但沒有留下 VRAM / 耗時 / 磁碟數字的 LoRA,**不算完成**;一個訓練成功、但沒有
產出可並排比較的樣張組的 LoRA,**也不算完成**。

## 二、交付物

**D1~D5 不需要我方任何訓練素材,收到本文當天即可開始。D6~D7 需要素材。** 理由見第四節。

### D1 —— 系統碟剩餘可用空間回報(開工第一件事,約五分鐘)

原委託規格書的硬體表裡,「磁碟剩餘可用空間」欄位逐字是「**未知**(只知總容量)」——
我方至今不知道那台機器還剩多少,而同一份文件另有一句警告:訓練中間檔「**單次可能額外吃
數十 GB 且不會自己清**」。

**交付**:系統碟(以及放模型/訓練輸出的那顆碟,若不同碟則兩者都要)的剩餘可用空間,
**附產生它的指令原始輸出**(例如 `fsutil volume diskfree C:`),不要只給結論數字。

### D2 —— 可行性探測:這台機器跑不跑得動、跑一次要多久

**用任意合法的佔位素材**(你們自備、公開授權、或任何湊得出來的一組圖,張數比照正式訓練
量級即可),在 **SDXL base 1.0** 上跑**一次完整的 LoRA 訓練**。目的不是得到一個能用的
LoRA,而是取得下列數字:

| 必交數字 | 取法 |
|---|---|
| VRAM 峰值 | `nvidia-smi` 取樣,整卡用量,**並附閒置基線** |
| 單次訓練牆鐘時間 | 總時間,以及每 step 或每 epoch |
| 磁碟:訓練前 / 峰值 / 訓練後殘留 | 三個數字,含中間檔(latent 快取、每 epoch 檢查點) |
| 是否需要開 fused backward pass + bf16 才跑得動 | 開與不開各自的結果 |
| 有沒有 OOM、用什麼參數避開 | 照實回報 |

🔴 **這一項的失敗也是有效交付。** 若實測結論是「16GB 跑不動」或「一次要跑一整晚」,那正是
我方要買的答案。**請不要為了讓它成功而默默縮小訓練規模或降低解析度 —— 改了就要寫下來,
否則我方拿到的數字會回答一個不存在的訓練的問題。**

### D3 —— 訓練環境與版本指紋,且既有指紋不得改變

訓練器(Kohya SS 或其他,**本文不指定**)**必須裝在獨立的虛擬環境**,
**不得更動 ComfyUI 既有 venv 的任何套件版本。**

理由是你們自己量到的:同為 torch 2.11.0,cu128 與 cu130 的輸出位元相同;**但換到
torch 2.14.1+cu130,chilloutmix 與 SDXL 的 SHA 全部改變**,因此版本被釘死在 2.11.0。
**訓練器的相依很可能要求不同的 torch —— 那就讓它待在自己的 venv 裡。**

**交付**:比照原委託第五節「環境指紋」的既有慣例,給訓練環境一份:訓練器版本或 commit、
該 venv 的 Python 與 torch 版本字串、`pip freeze` 檔的路徑、OS 版本。

### D4 —— 把 LoRA 掛進既有 API 的路徑(端到端打通)

現況:產圖 API **已經有** `loras` 參數,但沒有任何 LoRA 可掛 —— `config.example.json`
第 30 行為 `"loras": []`。

**交付**:一份「把 `.safetensors` 放到哪個目錄 + 在設定檔加哪一行」的步驟,並**實跑驗證過**。
**這一項可以用任意一個 LoRA 檔驗證**(D2 探測產出的那個就可以),不必等我方素材。

一併補上三條至今不可能被真的觸發過的路徑(因為那個陣列一直是空的):`GET /v1/models` 要
列得出它;`loras[].name` 不存在 → 既有契約規定的 `400 MODEL_NOT_FOUND`;LoRA 檔載入失敗
→ `500 MODEL_LOAD_FAILED`。

### D5 —— 訓練與產圖服務的共存政策 + 回退程序

你們量到 SDXL 1024² 推論的整卡 VRAM 峰值 **≈10.2 GB**(閒置桌面約 0.8–1.3 GB);我方查到
SDXL LoRA 訓練在 16GB 屬「尚可」,而那個「尚可」建立在開啟 fused backward pass + bf16
(把約 24GB 壓到約 10GB)之上。**兩者相加會超過 16GB。**
⚠️ **這是推論不是量測** —— D2 會給出真值,請以 D2 為準。

**交付**:一份明文政策,說明訓練期間產圖服務怎麼處理(停掉 / 暫停收單 / 或**實測證明**可
共存),以及訓練結束後怎麼回到可用狀態。你們已有 `start-stack.ps1` / `stop-stack.ps1` 與
工作排程器常駐機制,**這一項是把它們接起來並寫下來,不是重寫。**

### D6 —— 可重跑的訓練設定檔與執行腳本(需素材才能完成)

- 訓練參數**外部化成設定檔並進版控**,不是只存在某個人機器上的 GUI 設定。
- 至少這些要能從設定檔改:底模路徑、素材目錄、訓練解析度、network dim / alpha、
  learning rate、batch size、epoch 數、輸出路徑、**隨機種子**。
- 每次訓練輸出的 `.safetensors` **必須附一份 metadata**,內含:所用設定檔內容、素材清單
  (**每個檔案的 SHA256**)、種子、訓練器版本、起訖時間,以及該 `.safetensors` 自己的 SHA256。

### D7 —— 風格一致性評估樣張組(需素材)

這是回答第一節問題①的物證。**你們不做美術判定**(見第六節),你們要交的是**一組條件受控、
可並排比較的圖**:

- 固定的 prompt 清單 × 固定的 seed 清單(建議至少 8 prompt × 4 seed = 32 張,張數可議)。
- **同一組 prompt/seed 在三種條件下各跑一次**:不掛 LoRA / LoRA weight 0.6 / weight 1.0。
- 1024×1024 原生輸出 PNG,每張附 `seed_used` 與 SHA256。
- 降採樣到 128×128、調色板量化、描邊檢查 —— **不屬本次委託**,那是 06a 的後製工具。

## 三、驗收條件

寫法比照既有 `03-api-contract.md` 第十七節的雙方共用慣例:**每條都是「給什麼輸入 → 期待
什麼輸出」,請附實際請求/回應或指令紀錄作為證據,不要用「功能正常」這類形容詞描述。**

| # | 輸入 / 動作 | 期待輸出 |
|---|---|---|
| L1 | 查詢系統碟剩餘空間 | 一個具體數字,**加上產生它的指令原始輸出** |
| L2 | 跑完一次 D2 探測 | VRAM 峰值、總耗時、磁碟三個數字、是否 OOM,全部有數字。**「跑不動」也算通過本條** |
| L3 | 訓練環境安裝完成後,照 `docs/verification/phase2-py312-sdxl.md` §0 記載的那組 SDXL 基準條件重跑 | PNG SHA256 **逐字等於** `ce87fe0f…0855a`(seed 123456789);M5 002(seed 12345)逐字等於 `acb2589d…cb91` |
| L4 | 比對訓練環境 venv 與 ComfyUI venv | 兩份 `pip freeze` 可證明是不同環境;ComfyUI venv 的 torch 仍為 `2.11.0+cu130` |
| L5 | 放入一個 LoRA 並改設定後 `GET /v1/models` | 回應中列得出該 LoRA 的 name |
| L6 | `POST /v1/jobs` 帶 `loras:[{name, weight:0.8}]`,其餘條件同 L3 | `SUCCEEDED`,輸出 SHA **不等於** L3 基準值(證明 LoRA 真的生效,不是被接受後忽略) |
| L7 | 同 L6,`weight` 改 0.2 | `SUCCEEDED`,SHA 與 L6 **不同**(證明 weight 真的有作用) |
| L8 | `POST /v1/jobs`,**不帶** `loras` | SHA **逐字等於** L3 基準值(證明掛載機制沒有副作用) |
| L9 | `loras[].name` 填不存在的名字 | `400 MODEL_NOT_FOUND`,回應**無** `job_id` |
| L10 | 換成一個壞掉或不相容的 LoRA 檔再送 | `FAILED` 且 `error.code="MODEL_LOAD_FAILED"`;**伺服器行程存活**,緊接著 `GET /v1/health` 仍 `200` |
| L11 | **同設定連續訓練兩次**,比對兩個 `.safetensors` 的 SHA256 | **相同或不同都算通過**,但必須明文寫出是哪一個,並附兩個 SHA |
| L12 | 用**同一個** `.safetensors`(以 SHA 認定)+ 同 prompt + 同 seed + 同 weight 產圖兩次 | 兩張 PNG **位元相同**。⚠️ 這一條是硬性的 |
| L13 | 一次訓練跑完後查 `GET /v1/health` 與 `/v1/health/gpu` | 皆 `200`,服務回到可用狀態 |
| L14 | 交付 D7 樣張組 | 議定張數的 PNG + 每張的 prompt / seed / weight / SHA 對照表 |

### 🔴 關於「訓練不是位元可重現」這件事,怎麼處理

你們現行的驗收慣例是「固定種子 → 固定輸出指紋」,公司端 2026-10-08 的跨機器驗收也是用這個
方式過的。**但這個慣例不能直接套到訓練上,而我方不打算假裝可以:**

- **本次明確不要求訓練產物位元可重現。** 訓練會經過非確定性 kernel、資料載入順序、多執行緒
  排程 —— 即使固定種子,兩次訓練產出的 `.safetensors` 也可能不同。
- **改要求三件可驗的事**:
  ① **設定可重現** —— D6 的 metadata 要讓「同樣的輸入再跑一次」在操作上做得到。
  ② **推論端仍然位元可重現** —— 即 L12。**訓練不可重現,不代表使用它的那一步可以不可重現。**
     這一條是硬性的,它才是既有指紋慣例真正要守住的東西。
  ③ **誠實揭露** —— 即 L11。兩次訓練的 SHA 相同或不同,**我方至今不知道答案**,而這個事實
     本身就是交付物的一部分:它決定日後「重建某個 LoRA」是不是一個可行的操作。
- 🔴 **不得為了符合舊慣例而宣稱可重現。** 這與既有契約 T4 的處理方式同形 —— T4 逐字寫
  「支援確定性取樣時逐像素差異為 0,**否則**至少 `seed_used` 一致並於文件註明框架限制」。
  **既有慣例自己就留了誠實揭露的出口,請走那個出口,不要硬套前半句。**

2. **後製工具、去背、色票清單檔** —— 見另一份 06a,本文一字不提。
3. **不要求訓練產物位元可重現**(第三節已詳述)。
4. **不要求支援 SD 3.5 或任何其他底模。** 本次固定 SDXL base 1.0。換底模是我方的下一次
   裁決,不是你們的工作。
5. **不要求把訓練做成 HTTP 端點。** 訓練是離線操作,**不進既有 API 契約**。既有契約只需要
   多一條「掛載已經訓練好的 LoRA」的路徑(D4),不需要「透過 API 發起訓練」。
6. **不要求多個 LoRA 疊加的品質保證。** 既有參數是陣列,本次只驗單一 LoRA 的路徑;陣列給
   多筆時不崩潰即可。
7. **不要求訓練自動化、排程或 Web 介面。** 人工跑、留下紀錄就夠。
8. **不要求你們評估「該不該用 AI 產圖」或「這個 LoRA 夠不夠好」** —— 兩者都是我方的裁決。

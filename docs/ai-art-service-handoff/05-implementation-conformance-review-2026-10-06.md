你那份規格書要的是:**一支跑在家裡那台電腦上的程式,別的程式餵它一段文字,它用顯示卡畫出圖來。**

**這套流程有三段:公司筆電把工單送出去 → 家裡那台畫圖 → 成品送回公司筆電。這個倉庫只做了中間那一段。**

### 2.1 `POST /v1/jobs` 的四項偏離

1. 🔴 **未知欄位一律退件。** `service.py` 的 `set(body) - allowed` 檢查:請求裡只要出現契約 12 個欄位以外的任何欄位,整筆回 `400`。契約沒要求、也沒禁止。**後果**:日後橋接程式若想多塞一個自己用的欄位(例如工單編號),會被退件而不是被忽略。這是刻意從嚴,但沒有寫在它的 README 的「已知限制」裡。
2. 🔴 **寬高被加上「必須是 8 的倍數」這條契約沒有的限制。** 這是擴散模型的通例,實作把它公告在 `/v1/models` 的 `width_height_range.multiple_of` 裡 —— 但契約第十四節的回應格式沒有這個欄位,**照契約寫的呼叫端不會知道要去讀它**,只會在送出 `width=100` 時收到看不懂的 `400`。
3. ⚠️ **批次的 seed 推導方式未在契約內。** 指定 `seed=7` 且 `batch_size=2` 時,兩張圖實際用的是 7 和 8。實作誠實回報(`request_echo.seeds_used` 陣列、每張成品各自的 `seed_used`),但契約第八節只定義了單數的 `seed_used`。**行為合理,是契約沒寫到的地方,不是實作做錯。**
4. ⚠️ **冪等性重送可能回傳非 `QUEUED` 的狀態。** 同一把 `Idempotency-Key` 重送時,回應帶的是**資料庫裡那筆工作的當下狀態**,可能已經是 `SUCCEEDED`,但 HTTP 仍是 `202`。契約沒規定,行為合理。

### 2.2 `.../result` 用了契約沒定義的狀態碼組合

工作還在 `QUEUED` / `RUNNING`,或已 `FAILED` / `CANCELLED` 時,這支端點回 **`409` + `error.code = "INVALID_PARAMETER"`**。
契約第十節的對照表把 `INVALID_PARAMETER` 固定配 `400`,把 `409` 固定配 `IDEMPOTENCY_KEY_CONFLICT`。
**後果是具體的**:契約第十節明文要求呼叫端「必須讀 `error.code` 對應到表上的處置文字」,而 `INVALID_PARAMETER` 的處置是「修正參數後重送」—— 對「工作還沒做完」這件事,這是錯誤的指示。
📌 **根因有一半在我們自己的契約**:第三章從未規定「工作尚未成功時呼叫 `.../result` 該回什麼」。這是我們的缺口,實作只是自己填了一個。

### 2.3 `GET /v1/health/gpu` 沒有自己觸碰 GPU

契約第十三節這支端點存在的**唯一理由**,是「HTTP 行程活著」與「GPU 還能用」是兩件事 —— CUDA context 可能已損壞而 HTTP 完全正常。
實作的做法是向 ComfyUI 要 `/system_stats`。**這把判斷委託給了 ComfyUI**,於是:

- ComfyUI 整個掛掉 → 回 `gpu_available: false`。**正確的結論,錯誤的診斷** —— GPU 可能好得很,掛的是 ComfyUI。
- ComfyUI 活著但 CUDA context 壞了 → `/system_stats` 是否仍回一組快取數值,**本次審查無法回答**(需要真機)。若它回快取值,這支端點就會在 GPU 已壞時回報 `gpu_available: true` —— 那正是契約寫這支端點要防的那個情境。
- ⚠️ **逾時預算不符**:契約建議這支端點 2 秒內回應,而 ComfyUI 用戶端的預設逾時是 10 秒。ComfyUI 卡住時這支端點會卡到 10 秒。(「2 秒」在契約裡是建議值不是硬性要求。)

另兩項小偏離:`model_loaded` 回的是「上一次成功工作用的模型」,服務剛啟動還沒跑過圖時恆為 `null`;`last_successful_job_at` 只存在記憶體,**重啟即歸零**,即使資料庫裡還留著紀錄。

### 2.4 兩處錯誤碼被挪作他用

- **路由不存在**(例如打錯網址 `/v1/job/...`)回的是 `404` + `JOB_NOT_FOUND`。契約第十節對這個碼的定義是「`job_id` 從未存在」。**後果**:橋接程式分不出「我網址打錯了」和「那筆工作不存在」,而這兩件事的處置完全不同。
- **不支援的 HTTP 方法**(`PUT`/`PATCH`/`OPTIONS`)回 `405` + `INVALID_PARAMETER`。契約表上沒有 `405` 這一列。影響小。

### 3.1 錯誤分類是「比對錯誤訊息裡有沒有某個英文字」

`service.py` 的 `_generate()` 失敗時,把例外訊息轉小寫,然後:含 `out of memory` → `OUT_OF_MEMORY`;含 `model` 或 `workflow` → `MODEL_LOAD_FAILED`;其餘 → `INTERNAL_ERROR`。

**為什麼這值得寫下來**:契約第十節花了整整一段解釋「呼叫端不應只看 HTTP 狀態碼,必須讀 `error.code` 對應處置」,而這三個碼的處置**互相矛盾** —— `OUT_OF_MEMORY` 要「降參數重試」,`MODEL_LOAD_FAILED` 要「停止自動重試、通知人工」。分類錯了,處置就會錯。而這個分類依賴的是 **ComfyUI 的錯誤訊息用了哪些英文字**,那是本倉庫管不到的東西。

兩個靜態讀得出來的問題:

- 它自己丟的 `ComfyUIError("The image backend rejected the generation workflow.")`(送出工作流被拒,例如取樣器名稱 ComfyUI 不認得)含 `workflow` → 被分類成 `MODEL_LOAD_FAILED`,呼叫端會被導向「檢查環境」,而真正的問題在請求參數。
- Python 自己的 `MemoryError` 訊息是**空字串**,不含 `out of memory` → 會被分類成 `INTERNAL_ERROR`。
- ⚠️ 緩解措施它有做一半:`comfyui.py` 在 ComfyUI 回報錯誤時會先比對訊息,命中就丟一個訊息逐字為 `OUT_OF_MEMORY` 的例外,算是一條明確通道。但這條通道一樣靠字串比對。

**這條是 (C) 級推論** —— 要確認實際命中率,必須在真機上故意製造各種失敗並記錄 ComfyUI 的原始訊息。

### 3.2 `auto` 推導的長寬比會有不到 1% 的偏差

倍率算完後,寬高各自**獨立**進位到 8 的倍數,於是原生出圖的長寬比與目標長寬比不會完全相同(目標 128×72 時實測推導為 1368×776,比值 1.763 對 1.778)。最後 Lanczos 縮到目標尺寸時,這點差異會變成極輕微的拉伸。
**不影響驗收**(契約只要求「公告、一致、可重現」,三者都成立),但它的 README 寫「依…目標長寬比推導」,嚴格說是「近似長寬比」。方形尺寸(128×128、256×256)無此問題。

### 5.4 🔴 一項這份實作會直接擋住美術驗收的事:它無條件丟掉透明度

`service.py` 在存檔前固定執行 `image.convert("RGB")`,**沒有任何條件分支**。PNG 的 alpha 通道因此一律被移除,`auto` 與 `native_only` 兩種模式都一樣。

**為什麼這件事重要**:我們交付包 README 第二節列出的機械檢查逐字包含「**透明底**」。立繪與棋子素材若需要透明背景,這支服務**結構上交付不出來**。

⚠️ **誠實說明兩件事,免得被當成已定讞的缺陷**:
1. 我方文件內部對此並不一致 —— `deployment-and-transport.md` 第三節列的四項檢查是「尺寸/色盤/描邊/格線對齊」,**不含透明底**;而交付包 README 第二節的括號裡有它。**兩處說法不同,而這決定了這條算不算缺陷。**
2. 契約第三章從頭到尾**沒有提過 alpha 或透明背景**。所以嚴格對帳,這不是「違反契約」,是「契約沒寫、實作選了一個方向、而那個方向與美術需求可能相反」。
**這需要管理者裁決「成品要不要透明底」,不是工程師自行補上。**

### 5.5 🔴 一項架構層的銜接問題:橋接層的規格根本不知道這支服務存在

`deployment-and-transport.md` 第二節逐字寫的流程是:

### 6.1 `config.json` 會不會被誤提交 —— 不會,而且有兩道保險

`.gitignore` 六行,逐字:`__pycache__/`、`*.py[cod]`、`.venv/`、`config.json`、`data/`、`*.log`。

- `config.json`(設定)被忽略 ✅
- `data/`(**提示詞資料庫與全部成品圖**)被忽略 ✅ —— 這條比第一條更重要
- `*.log` 被忽略 ✅
- 🔴 **第二道保險才是關鍵:API 金鑰根本不在 `config.json` 裡**,只在環境變數。所以即使 `.gitignore` 哪天被改壞,**金鑰也不在任何檔案裡,提交不出去**。`config.example.json`(會進版控的那份)裡也沒有任何金鑰欄位。

### 6.2 路徑遍歷(`images/{index}` 直接 `read_bytes()`)—— 靜態閱讀下找不到可用路徑

這是任務點名要查的一條。那條路由確實最後直接 `read_bytes()`,但在抵達那一行之前有**四道獨立的限制**,任何一道成立就擋住:

1. **路由正規表示式的字元集是 `[0-9a-fA-F-]`,長度固定 36**。這個集合**不含 `/`、`\`、`.`** —— `..` 在字面上構不出來,編碼過的 `%2e%2e%2f` 也過不了,因為比對發生在 `urlsplit().path` 解碼後。
2. **`image_path()` 第一件事是呼叫 `result()`**,而 `result()` 要求這個 `job_id` 真的存在於 SQLite 且狀態為 `SUCCEEDED`。**猜不中資料庫裡的 UUID 就到不了讀檔那一步。**
3. **index 必須是整數,且必須落在該工作成品清單的長度範圍內。**
4. **最終檔名是用整數組出來的 `f"{index}.png"`** —— 呼叫端對檔名部分的影響力是零。

另外 `data_dir` 在載入設定時就 `.resolve()` 成絕對路徑。
**判定:符合。** ⚠️ **但這是 (C) 級** —— 我是讀程式碼推導的,沒有真的對它跑過任何模糊測試或惡意請求。

### 6.3 成品檔案的保留與清除 —— 做了,但清除機制可能安靜地死掉

**做對的**:`retention_hours`(範例設定 24)到期後,背景執行緒每 60 秒掃一次,刪掉成品目錄、把資料庫裡的提示詞欄位覆寫成 `{}`、把 echo/成品清單/錯誤/冪等鍵全部清成 `NULL`。另外每次有人查狀態時也會順手清一次。重啟時還會刪掉中斷工作留下的半成品。

🔴 **做不對的一處,而且它壞掉的方式是安靜的**:那個 `while True` 的清除迴圈**沒有任何例外保護**。`expire_jobs()` 只要丟出一次例外(SQLite 被鎖住、磁碟滿、檔案被防毒軟體佔用都可能),**整條執行緒就結束了,不留任何痕跡,之後再也不會自動清除任何東西**,直到有人重啟服務。那條「查狀態時順手清」的半備援同樣沒有保護 —— 它丟例外時會讓呼叫端收到一個 500。

**為什麼我把這一條寫進安全性而不是穩定性**:第四章第四節要求提示詞「日誌保留原則上從簡,不做超出除錯需要的長期保存」。清除執行緒死掉的後果,是**提示詞與成品圖無限期留在那台機器上**,而且沒有任何徵兆。

⚠️ 另一項小偏離:到期時間是從**建立**時刻起算,不是從**完成**時刻。契約第九節的範例是完成時間 +24 小時。工作若在佇列裡排了很久,會比預期早過期。

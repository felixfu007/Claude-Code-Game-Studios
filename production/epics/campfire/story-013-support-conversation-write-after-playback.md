## 為什麼有這張(白話)

管理者 11-20 裁決勝利後順序為「勝利 > 營火 > 對話 > 編牌組 > 下一場」,理由逐字:「這樣如果因為對話導致好感度變化的話,我才知道怎麼調整牌組」。
但現行程式在**勝利當下**就把對話造成的好感度變化寫進戰役累積記錄,比玩家看到對話早 —— 營火畫面看到的關係等於先劇透了還沒播的對話,營火卡也依含對話變化的數值產出。本單把寫入延後到對話播完。

## 背景(引自 `lead-programmer` 2026-11-23 讀碼,證據等級 (B),行號會漂、要現值重 grep)

- 勝利分支 `_on_battle_ended` 的順序:挑對話並寫累積記錄 → `advance_on_victory`;被選中的對話 id 存進 `_completed_support_conversation_ids`,結果顯示結束後才播。
- 挑段只看資料表 `trigger_after_mission` 與兩位參與者**勝利當下**是否存活,**完全不讀好感度池** —— 所以「挑哪一段」維持在勝利當下決定,不受本單影響。
- 對話畫面 `support_conversation_screen.gd` 目前沒有讀/寫好感池或累積記錄的程式碼。
- 寫入量由資料表的正向/負向/中性決定固定值(`SupportConversationRules.trigger`,中性不寫)。

## 規則摘要

- 挑段與存活判斷**仍在勝利當下**(用勝利當下的 `_state`),把「要寫哪幾筆」帶到對話畫面;**寫入**改在該段對話播完時執行。
- 寫入仍走既有 `SupportConversationLedgerWritePort`,來源值、寫入量、拒絕處理一律不變。
- 多段對話依播放順序逐段寫入(累積記錄附加順序會微幅影響結果,見 `campfire-open-tech-2026-11-23.md` 題 1「新發現」—— 測試不得假設順序無關)。
- 本單**不**負責把營火插進流程(那是 006);本單完成後,不論營火是否已接上,「勝利當下寫入筆數」都應為 0。

## Acceptance Criteria

- [ ] **AC1** 勝利後、對話開始播放前:累積記錄**沒有**本場對話的筆數(以真實戰鬥場景檔載入、走真實 `SceneRouter`)。
- [ ] **AC2** 對話播完後:累積記錄新增的筆數、配對、數值與改動前「勝利當下寫入」的內容逐筆相同(回歸對照)。
- [ ] **AC3** 多段對話:寫入順序 = 播放順序。
- [ ] **AC4** 挑段結果不變:同一場勝利、同一份存活名單,改動前後挑中的對話 id 相同;勝利當下已陣亡角色的對話仍不觸發。
- [ ] **AC5** 下一場開局重播後讀到的關係,與改動前相同(兩段流程結束點的累積記錄內容相同 → 重播結果相同)。
- [ ] **AC6** 敏感度證明(常駐 `test_sensitivity_proof_*`,一個 mutant 一次獨立執行):①保留勝利當下寫入 → AC1 紅 ②播完不寫 → AC2 紅 ③播完時改用「播完當下」的存活判斷重新挑段 → AC4 紅(需構造播放期間名單改變的情境;若構造不出,回報並說明)。交付前掃殘留注入標記。
- [ ] 交付前全套 `GODOT_BIN=<路徑> bash tools/build/run_tests_with_import.sh`,回報貼 `ENGINE EXIT` 與 `Overall Summary` 原始三行。

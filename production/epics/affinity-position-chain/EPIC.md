### M1 — 驗收基準對齊(零前置,建議第一個做)

**範圍**:讓 GDD 的 17 條 BLOCKING 驗收準則**每一條都有一個叫得出名字的測試**。

🔴 **第一個動作是反查,不是補寫。** 第 4 節已登記:AC-R3 的**行為**其實被 7 條
`test_delta_*` 測到了,只是沒標代號 —— 那種情況正確的動作是**加註解標上代號**,
不是再寫一條重複的測試。**AC-R1 與 AC-R5 我沒有做同等強度的反查**,
先反查再決定「補標」或「補寫」。

⚠️ **AC-R5 是三條裡唯一我有把握是真缺的**:它要驗「X 被移除後 **Y 和 Z 各自** +1」,

### M2 — 上游接線(本 epic 的主線,也是唯一真正改變行為的模組)

**範圍**:把配對資料(極性、強度)的來源從

**GDD 明文兩件事,缺一不可**(Interactions ①):

1. 改為即時查詢(不再讀靜態檔);
2. 🔴 **逐次查詢、禁止建構時快取** —— 逐字:「**遷移時真正要改的是這一點,
   不只是把靜態檔換成函式呼叫。**」

**完成的定義**:`test_phi_reflects_a_pairing_polarity_flip_made_after_construction`
(目前刻意紅)變綠,**且不是靠改測試變綠的**。

✅ **這個模組的最大前置已經解除,而且很多人不知道**:GDD 的 **OQ-3(`amp` 量化方式未定)**
曾經擋著它,**已於 2026-09-08 結案**,逐字:

> ①**Interactions ① 的即時查詢遷移不再被阻擋** —— 它等的就是這個答案,現在可以排了

答案是 **`amp` 恆為 1**(只取符號、丟棄量值)。**亦即遷移後 `Φ` 的數值不會改變,
改變的是「資料從哪來、什麼時候取」。** 這讓 M2 成為一個**行為不變的重構**,
可以用「遷移前後 `Φ` 逐格相等」當回歸斷言。

### M3 — 夾限與逐條貢獻的揭露

🔴 **這是我在本次盤點中找到的、GDD 有明文要求但程式碼結構上做不到的一項。**

GDD 的 UI Requirements 逐字:「**原始和被夾限壓回時,必須明示『已達上限/下限』**」,
Edge Cases 也寫「這會讓畫面上逐條顯示的數字加起來不等於總和」。

**但現行 API 無法滿足它**:

- `bonus_for_at()` 回傳 **已夾限** 的 int,呼叫端看不出有沒有被壓回;
- `lines_for()` 回傳的每條 `delta` 是 **未夾限** 的。

**呼叫端要判斷「有沒有壓回」,只能自己把 `lines_for()` 的 delta 加總一次再跟
`bonus_for_at()` 比 —— 那就是在 UI 層長出第二份加總實作。**
本專案對這個形狀有明確的登記立場(`technical-preferences.md`,由 R2 的兩份曼哈頓實作而來):
黑箱比對輸出**永遠無法區分「共用同一份」與「兩份碰巧一致」**。

**M3 的範圍**:在本系統側提供「原始和 / 是否被夾限 / 夾到哪一邊」的查詢,
讓 UI 不必重算。**具體 API 形狀由 `lead-programmer` 決定,本 epic 不指定** ——
本 epic 只負責指出「現在的形狀滿足不了 GDD 的硬性要求」。

### M4 — 陣亡回饋的資料擁有權(被擋,不要在本批動它)

GDD **OQ-6** 逐字:「**陣亡前的 `Φ` 值無人擁有。** …… 但 R10 使本系統無狀態
(**此為正確設計,不改**)。誰負責快照?」擁有者欄寫的是 `/ux-design` + `lead-programmer`。

**它擋的是「陣亡回饋的呈現」,不擋本系統。** 本 epic 把它列為獨立模組而非塞進 M3,
理由是:**它需要的是一個裁決,不是一段程式碼** —— 混進別的模組會讓它繼續沒人認領
(本專案已登記過這個形狀:「裁決被記錄 ≠ 裁決被排程」,見 `production/epics/index.md`)。

### M5 — 結構紀律與效能基準

兩件 GDD 明文點名「自動測試涵蓋不到」或「還沒有基準」的事:

   📌 本專案**已有**這種測試的前例:`tests/unit/gameplay/affinity/affinity_link_no_direct_return_test.gd`

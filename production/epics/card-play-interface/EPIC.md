## 一、切片內 / 切片外的邊界,以及它的依據

### 🔴 切片邊界的依據是一條已生效的硬性義務,不是工作量

**取消鍵重綁(`Esc` / 手把 `B`)與戰鬥選單必須同批上線。**
來源:`design/ux/skill-card-play.md` **AC-U12** 與 `design/ux/battle-menu.md` **AC-M1**,
**兩者是同一條驗收條件的兩側。**

理由逐字寫在 `skill-card-play.md`:

> `battle_end_phase` 目前的兩個綁定(Esc、手把 B)**就是玩家唯一能把回合交給敵方的手段**。
> 一旦把它們移交給取消而選單還沒做好,**玩家無法結束回合,戰鬥永遠停在自己的回合。**

**而這條義務有明文的適用邊界**:

> **純資料層的接線不碰按鍵,不受該義務約束;接輸入才受。**

### 由這條邊界導出的三段切法

| 段 | 內容 | 受不受同批義務約束 | 能不能單獨上線 |
|---|---|---|---|
| **A 資料層** | 卡表解析器 + 把真牌組接進 `BattleController` | ❌ **不受** —— 一個按鍵都不碰 | ✅ **可以** |
| **B 卡牌介面** | 手牌帶、展開、選牌、選對象、確認面板、強制棄牌 | ✅ **受** —— 它要求新增 `battle_cancel` | ❌ **不可以** |
| **C 戰鬥選單** | 選單畫面、暫停閘控、結束回合的新家、離開確認 | ✅ **受** —— 它是取消鍵的交換條件 | ❌ **不可以** |

🔴 **下一個人最可能犯的錯,寫在這裡:不要以為「只做卡牌介面」可以收工。**
B 一旦上線就會把 C 整段拉進來,因為 B 需要 `Esc` / `B` 當取消鍵,
而那兩個鍵現在是結束回合的唯一出口。**B 和 C 是一批,沒有半批。**

A 則是真的可以單獨先上,而且**建議先上** —— 它把「資料讀得到」這個風險提早暴露,
且它壞掉的話後面全部白做。

## 五、開工前必讀的陷阱

以下每一條都是本次調查**實際讀到的檔案內容或 grep 結果**,不是防禦性直覺。

### 陷阱一:`Card` 的兩個建構入口各只收 4 個參數,而資料表有 8 欄

**不能照 `Unit.from_csv_line()` 的「一個建構子吃全部欄位」形狀直接抄。**
兩個入口逐字是:

```text
Card.new_temporary_stat_modifier(p_id, p_delta_atk, p_delta_def, p_duration_rounds)
Card.new_permanent_affinity_write(p_id, p_character_a, p_character_b, p_magnitude)
```

解析器必須**先讀 `category` 欄再分派**到兩者之一。

🔴 **而 `category` 是字串,絕不可寫 `Card.Category[value]`** ——
已登記禁令 `raw_enum_name_subscript_from_untrusted_string`:
**動態非法字串索引會當場中止呼叫函式**(2026-08-20 探針 C 實測)。
**照抄 `AffinityLink._polarity_from_string()` 的 `match` 形狀**(`affinity_link.gd:138`)——
它的 doc comment 逐字說明了自己為什麼寫成那樣,就是為了這條禁令。

### 陷阱二:`0` 在這張表上是三種不同的東西,不得收斂成同一個判斷

逐字出自 `vs01_cards.txt` 檔頭與 `card.gd` 的 doc comment:

| 欄位 / 類別 | `0` 的意思 | 合法嗎 |
|---|---|---|
| 甲類的 `delta_def = 0` | 「這張牌不動這個軸」 | ✅ **正常值,不是 sentinel** |
| 甲類的 `affinity_magnitude = 0` | unset sentinel | ✅ 合法 |
| 丙類的 `affinity_magnitude = 0` | GDD 公式三的非法值 | 🔴 **會被寫入埠拒絕**(AC-9) |

**同一個欄位、同一個值、三種語意。** 解析器若寫成「0 就是沒填」會把第一種也吃掉,
而其後果是**一張純 ATK 卡被當成資料錯誤** —— 不崩潰、不報錯。

### 陷阱三:`affinity_character_a` / `_b` 只是牌面敘事,機制上不讀

2026-09-10 管理者裁決:**實際作用的配對由玩家在棋盤上兩步選定(S2p / S2q)**,
`PermanentAffinityWriteRules.play()` **不讀這兩欄**。

**對介面的後果**:確認面板顯示的配對**必須來自玩家的選取**,不得從卡片欄位讀。
**AC-U13 的後半句就是為了抓這個而寫的**(換一對之後不得殘留前一對)。

⚠️ 管理者已知情接受的代價:牌面可能寫「甲對乙說話」而玩家打在丙丁身上,
**故事與效果對不上**。**這不是 bug,不要去修。**

### 陷阱四:`battle_screen.gd` 對資料檔有**兩套不同的載入失敗政策**,而卡表該走哪一套沒人決定過

實測 `battle_screen.gd` 的 `_ready()`:

- **terrain / roster**:解析出 0 筆 → `_fail_load()`,**整個畫面停掉**。
- **affinity**:解析出 0 筆 → **只 `push_warning()`**,因為「沒人配對」是合法的設計狀態
  (戊刻意沒有任何關係線,且有一條測試釘住它)。該檔註解逐字寫明兩者是
  「deliberately a DIFFERENT policy」。

**卡表解析出 0 筆是哪一種?沒有人決定過。**
📌 **這是我的推論,需要裁決** —— 見第八節第 1 項。

### 陷阱五:`CardDeck` 的 RNG 預設未注入,會讓截圖證據無法重現

`card_deck.gd:81` 逐字 `func _init(cards: Array[Card], rng: RandomNumberGenerator = null)`,
第 83 行 `_rng = rng if rng != null else RandomNumberGenerator.new()`。

**U-003 若用預設值,每次開遊戲手牌都不同。** 本 epic 有 6 條 AC 要求截圖或灰階比對,
而 `coding-standards.md` 的 Determinism 規則逐字要求 no random seeds。

⚠️ **要處理的不是「能不能隨機」,是「測試與截圖時怎麼固定」。**
牌面隨機本身是合法的、且是本作唯一的隨機豁免(`game-concept.md` 第三輪裁決:
牌面隨機、**發牌節奏固定**);禁令 `rng_in_combat_settlement` 管的是**結算路徑**,不是洗牌。
**U-003 的工作單要決定注入形狀。**

**同一句話,同一個功能,第二次。** 處置見第二節 U-005 / U-016 那段。

## 九、為什麼本 epic **不需要**新的 ADR

依 `.claude/docs/coding-standards.md`(2026-09-01 管理者裁決):
**架構文件(ADR)只在跨系統契約時才寫**,單一系統內部技術細節寫在該系統設計文件裡。

**本 epic 從頭到尾是既有跨系統契約的「呼叫方」,不是新契約的「定義方」**:

| 它碰到的契約 | 定義在哪 | 本 epic 的角色 |
|---|---|---|
| 游標裁定的暫停閘控 | ADR-0005 機制九(**Accepted**) | **第一個呼叫方** —— 該機制自 2026-08-11 寫下起就假設有一個呼叫方,而那個呼叫方從未被指派,**直到本 epic** |
| 結算路徑的原子性 | ADR-0001(**Accepted**) | 呼叫方,不改契約 |
| 好感度寫入埠 | ADR-0002 / `affinity_write_port.gd` | 呼叫方,**不得修改其語意** |
| 卡牌資料模型 | `card.gd`(`skill-card-system` epic 已交付) | 讀取方 |

**唯一逼近「新契約」的是 U-006 的 `process_mode` 排除** —— 但 `battle-menu.md` 已把它
登記為 **BM-9**、擁有者指名游標系統(#3),且它是 ADR-0005 機制九的**實作細節補完**,
不是新的跨系統介面。**登記進 `docs/registry/architecture.yaml` 即可,不寫 ADR。**
本專案已有「用登記表條目取代一份 ADR」的前例(`affinity_pairing_data_per_query_refetch`,`adr: none`)。

📌 **這與流程劑量規則的預估一致**:剩下 6 個系統預期只再產生 **0~1** 份新 ADR。

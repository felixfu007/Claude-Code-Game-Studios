# Story 002:甲類的回合存續、到期與清除

> **Epic**:技能卡牌系統 —— 邏輯層
> **型別**:Logic(**BLOCKING**)
> **狀態**:📋 Ready
> **估時**:M
> **依賴**:Story 001

## 目標

讓甲類修正會隨回合遞減、到期自動移除,並在戰鬥結束時全部清乾淨。

## 規則(來源:GDD 公式二 + Edge Cases)

| 規則 | 內容 |
|---|---|
| 剩餘回合 `r` | `∈ {1, 2}`,由卡牌定義 |
| 遞減時點 | **玩家回合開始時** `r ← r − 1`;遞減後為 0 者**立即移除** |
| 順序 | 🔴 **移除必須早於該回合任何查詢**,且**先遞減與移除,再補牌** |
| `r = 1` 的語意 | 涵蓋「本回合 **+ 緊接的敵方回合**」 |
| `r = 2` | 再多涵蓋玩家的下一個回合 |
| 戰鬥結束 | 所有生效中的修正**一併清除**,不帶到下一場 |

🔴 **`r = 1` 涵蓋緊接的那個敵方回合,這是刻意的,不是寬鬆。**
若到期發生在玩家回合**結束**時,防禦增益永遠撐不到敵人動手 —— 而玩家買防禦的唯一動機
就是撐過敵方那一輪。**到期在自己回合開頭而非結束,是這條規則的全部意義所在;
改動它等於刪掉整類防禦牌。**

🔴 **「先清乾淨再發牌」不是實作偏好,它改變玩家的決策品質**:若先補牌而觸發滿手強制棄牌,
玩家會在一個**還掛著已到期修正**的盤面上,做那個**不可逆**的棄牌決定。

## 🔴 實作硬性約束:遞減與補牌必須在同一個函式內依序執行

**不得寫成兩個各自訂閱「回合開始」訊號的獨立處理常式。**
那樣執行順序取決於**連線順序**而非任何顯式優先序 —— 與 ADR-0001 機制二記載的同鏈排序陷阱同類,
且**順序錯了不會報錯**,只會讓玩家在錯的盤面上做決定。

⚠️ **本專案有兩條平行、互不呼叫的回合驅動路徑**:`BattleController` 與 `BattleLoop`
(見 `src/gameplay/battle/battle_state.gd` 檔頭)。**回合開始的掛鉤必須是兩者共用的那一個,
不得各寫一份** —— 這正是 ADR-0001 第一次修訂踩到的形狀(寫入路徑實際有六條而文件只畫一條)。
**動手前先 grep 玩家回合開始的實際落點,不要憑架構圖假設。**

## 驗收條件

| # | GIVEN / WHEN / THEN |
|---|---|
| **AC-3** | 玩家回合打出 `r=1` 的防禦增益 → **緊接的敵方回合中該增益仍生效** → 玩家下一回合開始後失效 |
| **AC-4** | `r` 遞減至 0 的那個回合 → **該回合第一次查詢 `effective_def()` 時修正已移除**(不是查完才移除) |
| **AC-11a** | 戰鬥結束 → **所有生效中的甲類修正清除**,不帶入下一場(AC-11 的另一半在 Story 003) |

**AC-4 是本 story 最容易寫成「永遠會通過」的一條。**
若測試在回合開始事件之後才建立查詢,它驗不到順序 —— **必須讓查詢發生在回合開始處理的
最早可觀測時點**,或以呼叫序斷言(遞減函式回傳後、補牌前的狀態)。

## 補測(GDD 登記為零 AC 覆蓋)

- **`r=2` 的完整軌跡**:打出 → 本玩家回合生效 → 敵方回合生效 → 下個玩家回合仍生效
  → 再下個玩家回合開始時移除
- **遞減先於補牌的順序**:在一個「補牌會觸發滿手強制棄牌」的情境下,
  斷言棄牌決策點看到的盤面**已經沒有**那個到期修正

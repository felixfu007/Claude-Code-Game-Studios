# Story 004:丙類的合法配對集合與寫入埠

> **Epic**:技能卡牌系統 —— 邏輯層
> **型別**:Logic(**BLOCKING**)
> **狀態**:📋 Ready
> **估時**:M
> **依賴**:無

## 目標

決定「這張永久關係牌可以作用在哪幾對角色身上」,並把寫入動作送出去。

🔴 **本 story 的價值幾乎全在「排除誰」,不在「寫進去」** —— 見下方兩節。

## 🔴 它要寫進去的地方不存在,這是本 story 最該先讀懂的事

GDD 把「好感度數值池的寫入介面(ADR-0002,**Accepted**)」列為硬依賴。
**2026-09-10 實測:零實作。**

```
grep -rn "append_record\|combat_card\|AffinityPool\|data_pool" src/ --include=*.gd   → 零命中
```

`src/gameplay/affinity/` 現有四檔全部是**關係線極性的讀取路徑**(餵給 `Φ`),
**沒有任何 append-only 記錄結構。**「ADR 已 Accepted」是設計層通過,不是程式已存在。

**處置(套用 `.claude/docs/coding-standards.md` 的 dependency injection,非新裁決)**:
定義一個**窄寫入埠**並由外部注入。介面形狀比照 ADR-0002 機制四:

```gdscript
# 回傳拒絕碼,而非 bool —— GDScript 無 try/catch,ADR-0002 的錯誤處理哲學是
# 「錯誤一律以回傳值表達」。
func append_record(pair, m: int, source) -> <WriteRejection>
```

⚠️ **`m` 在 ADR-0002 是 `float`,本系統的 `m` 是 `int`({−3…+3})。**
接上真品時這裡會是一個型別邊界 —— **ADR-0002 明文:型別錯誤會讓呼叫端整段中止,
不是回傳一個拒絕碼。** 埠的簽章必須現在就對齊,不要留到接線那天。

🔴 **誠實登記的限制**:本 story 只能驗到**埠**這一層。
「記錄真的落在池裡、`source` 欄真的是 `combat_card`」的端到端驗證**待 #1 實作**,
**不得計入完成度。**

## 合法作用配對的定義(GDD Core Rules 一之三)

| # | 界線 |
|---|---|
| 1 | **不得翻轉任何角色設定的正負號**(甲乙合作、丙丁對立皆為 Canon `Established`) |
| 2 | 卡池中的丙類張數設上限 —— **待卡表(OQ-6),不在本 story** |
| 3 | 合法配對 = `design/narrative/characters.md` **現有關係線**,隨劇情推進自動擴大 |
| 4 | **不創造角色設定沒有的關係線** |

**垂直切片的真實資料**(`assets/data/affinity/vs01_affinity_links.txt`):
只有兩條 —— `1,2,POSITIVE`(甲乙)與 `3,4,NEGATIVE`(丙丁)。**戊(5)沒有任何配對,且那是刻意的。**

⚠️ **合法集合必須從關係線資料推導,不得寫死兩對。** 界線 3 明訂它隨劇情擴大 ——
寫死會讓「新增關係線屬敘事工作、系統端不需改動」這句話變成假的。
**現成的來源**:`AffinityPhiProvider.links()` 已經回傳這張表。

## 🔴 保護戊的不是界線 4 —— 釐清這件事會改變該寫哪一條測試

`Φ` 只加總 `characters.md` 現有的關係線,故**即使一筆 `(戊, 甲)` 記錄漏進池裡,
戊的 `Φ` 照樣恆為 0** —— 戰鬥端的保護是**結構性的**,不依賴任何驗證邏輯。

**但敘事端沒有這層保護**:好感度數值池對「角色設定關係線」**零認知**,
它視 10 對配對一律合法。**故一筆漏寫的記錄不影響傷害,卻會被敘事深度與形狀特徵讀取
全額算進去,而池是 append-only、永不刪除。**

→ **界線 4 的唯一防線在本 story 的合法配對集合,上游不會攔。**

## 其他拒絕條件

| 條件 | 處置 |
|---|---|
| `m == 0` | **拒絕並拋驗證錯誤,不靜默糾正、不產生記錄、計數器不遞增**(上游明訂) |
| 配對有成員陣亡 | 🔴 **必須在「選作用對象」階段就排除在合法集合外**,不是「選了之後被拒絕」 |

🔴 **陣亡配對為什麼要在集合階段就排除,而不是等寫入被拒**:
若等到確認後才被拒,**玩家已經花掉一張牌卻什麼都沒發生。**
**這不是防禦性程式設計,是合法集合的定義的一部分。**

## 驗收條件

| # | GIVEN / WHEN / THEN |
|---|---|
| **AC-6** | 打出丙類 → 埠收到一次呼叫,`source` 為 `combat_card`、幅度為該卡定義值。⚠️ **只驗到埠** |
| **AC-7** | 配對成員已陣亡 → 該配對**不出現在合法作用對象集合中** |
| **AC-7b** | 繞過選擇介面,直接以**陣亡配對**呼叫寫入 → **回傳驗證錯誤,記錄筆數不變** |
| **AC-8a** | 嘗試對無關係線的配對(含戊者)作用 → **該配對不在合法集合中** |
| **AC-8b** | 已有關係線的配對(甲乙)**正常可選定、寫入成功、記錄筆數 +1**,且**極性不變** |
| **AC-9** | `m = 0` → 寫入被拒並拋驗證錯誤,不靜默糾正、不產生記錄、計數器不遞增 |

🔴 **AC-8b 是正面控制組,不是湊數的。** 沒有它,AC-8a 無法區分
**「正確排除了戊」**與**「全部配對都被排除了」** —— 一個全拒的實作會讓 AC-8a 通過。

⚠️ **AC-7b 的第二道防線原本在池,而池不存在。**
本 story 由**埠契約**承擔:埠的測試替身必須實作陣亡拒絕,且要有一條測試斷言
**呼叫確實送到了埠並被拒**(而不是被本系統提前攔下)—— 否則接上真品那天,
沒有人知道這條防線到底在哪一側。

⚠️ **AC-8 沒有第二道防線,這一點與 AC-7 不同** —— 池對關係線零認知,不會拒絕 `(戊, 甲)`。
GDD 明文:**本規則的唯一防線在本系統的合法配對集合。**

## 已知會被寫成「永遠會通過」的一條(GDD 第一輪審查已拆解)

原 AC-8 斷言「戊的 `Φ` 在任何丙類打出後仍恆為 0」—— 那是**結構性事實**,
**與驗證邏輯有沒有生效完全無關**:就算過濾整個壞掉、`(戊, 甲)` 真的被寫進池裡,
那條斷言照樣通過。**可保留作輔助回歸檢查,但不得單獨作為驗證邏輯生效的證據。**

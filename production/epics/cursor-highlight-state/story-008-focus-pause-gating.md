## Implementation Notes

*出自 ADR-0005 機制九:*

1. **拒絕 `SceneTree.paused` 作為判準** —— 專案內存在不透過它實作的非阻斷式彈窗,以它為判準會漏。
2. 🔴 **兩條路徑的正交性(必須忠實承載)**:`_arbitration_suspended` **只**閘控**被動裁定路徑**(機制五的 `_input()` 收集與 `_process()` 裁決),**不閘控**呼叫方透過機制十寫入介面發起的主動改標。
3. **suspend / resume / FOCUS_OUT / FOCUS_IN 四個進出點全數呼叫 `_frame_events.clear()`** —— 原版本有兩個確定性漏洞(競窗 100% 存在、緩衝殘留)。
4. ✅ **FOCUS 通知時序已實測乾淨**(2026-09-01,非 headless、真實 OS 焦點切換):每一格皆為「全部 FOCUS 通知先於全部 PROCESS」,跨 5 個 `process_priority` 一致。證據 `prototypes/adr0005-engine-probes-2026-09-01/logs/probe10_windowed.txt`
5. 🔴 **一項本機無法驗證的風險**:**Steam 疊加層是否觸發 `NOTIFICATION_APPLICATION_FOCUS_IN` 未知** —— 本機無 Steam 環境。AC-30 依賴此通知涵蓋 alt-tab / 最小化 / Steam 疊加層三情境,而 Steam 疊加層常以應用程式內 swapchain 層級掛鉤,**不一定產生 OS 層焦點轉移**。
   **若實際不觸發,機制九需備援偵測路徑。列為整合測試期的觀察項,不是本 story 的失敗條件。**

## Acceptance Criteria

*以下為 `design/gdd/cursor-highlight-state.md` 的條文**原文轉錄**,未改寫:*

- **AC-18**: **GIVEN** 滑鼠目前持有權威,**WHEN** 滑鼠游標移出遊戲視窗邊界(不論之後是否移回),**THEN** 游標目標與裝置權威維持在移出視窗前最後一次有效 `ui_*` action 的值,不清空、不跳到預設值,視窗外的滑鼠移動不產生任何狀態變更。
- **AC-21**: **GIVEN** 手把持有權威期間發生斷線,**WHEN** 檢視斷線事件發生後的下一個影格,**THEN** 游標目標與裝置權威與斷線前最後一次有效值完全相同,對應的高亮視覺持續顯示於原位置,不消失、不重置為預設值。
- **AC-22**: **GIVEN** 手把已斷線且系統維持斷線前狀態(AC-21),**WHEN** 滑鼠之後產生一個有效的 `ui_*` action,**THEN** 裝置權威依 Group B 一般規則轉移給滑鼠,並依 Group C 一般交接繼承規則承接斷線前的游標目標;若斷線後始終無任何裝置產生新輸入,游標狀態持續保持靜止不變。
- **AC-23**: **GIVEN** 游標持有特定目標與裝置權威時遊戲進入暫停選單或彈出對話框,**WHEN** 玩家關閉選單/對話框返回原畫面,**THEN** 游標的裝置權威與目標值與進入暫停前完全相同,不因暫停期間任何背景輸入訊號或選單內部操作(例如選單內以手把導覽選項)而被竄改。
- **AC-30**(2026-08-04 新增,回應 ux-designer 審查發現的 OS 焦點遺失覆蓋缺口): **GIVEN** 遊戲視窗失去 OS 層級焦點(非遊戲內暫停)後又重新取得焦點,**WHEN** 檢視 `NOTIFICATION_APPLICATION_FOCUS_IN` 觸發後的下一個渲染影格,**THEN** 目前權威裝置對應的高亮視覺已確認重繪,且原生滑鼠指標的顯示/隱藏狀態已依目前裝置權威重新套用,不依賴失焦前的舊渲染狀態殘留。
- **AC-30b**(2026-08-04 第七輪新增,回應 systems-designer、qa-lead 審查發現;**2026-08-05 第十輪重寫,回應同方兩位發現的定序缺口與運算範圍真歧義,見 Core Rules #3 累積起點重置規則觸發點 (c)〔第十輪重新編號並重寫〕**): **GIVEN** 鍵盤/手把持有權威,滑鼠奪權累積位移量介於 0 與門檻之間(即有進行中但未完成的奪權嘗試),遊戲視窗於此時失去作業系統層級焦點、期間滑鼠被移動至遠離失焦前位置之處,**WHEN** 分別檢視(i)失焦**期間**(重新取得焦點之前)任一影格的 `accumulated_net_displacement_px`,與(ii)遊戲視窗重新取得焦點(`NOTIFICATION_APPLICATION_FOCUS_IN` 觸發後)的下一個影格,**THEN** (i) 失焦期間全程,該欄位維持失焦當下的舊值不變、不逐幀更新,不因失焦期間滑鼠實際移動而產生任何變化(驗證 Core Rules #3「此欄位的即時運算範圍」新增的失焦排除條件——確認本欄位在失焦期間根本不可能悄悄逼近或跨過門檻);(ii) 復焦後的下一個影格,該欄位已重置為 0,累積起點已更新為復焦當下的滑鼠螢幕座標——不因失焦期間滑鼠實際位移量,在重新取得焦點的當下產生偽造的高累積位移讀數、進而讓奪權判定失真。
- **AC-59**(暫停/模態期間不裁定,回應對抗性覆核發現 F2-1 的伴生缺口,見 Edge Cases「若遊戲於游標持有某個目標時進入暫停選單/彈出對話框」新增的「成立機制」段落): **GIVEN** 鍵盤/手把持有權威、滑鼠奪權累積位移量處於任意中間值(0 與 `reclaim_threshold_px` 之間),**WHEN** 遊戲進入暫停選單/模態 UI(`SceneTree.paused = true`)、暫停期間玩家以任意裝置在暫停選單內操作、隨後恢復遊戲畫面,**THEN** 恢復當下裝置權威與游標目標與暫停前完全相同,累積位移量已重置為 0、累積起點已更新為恢復當下的滑鼠螢幕座標——本系統在暫停/模態全程未消費任何輸入事件供自身裁定邏輯使用,不因暫停期間背景輸入訊號或選單內部操作而竄改狀態。**執行前提**:本 AC 依賴 `/create-architecture` 階段確認的暫停讓路機制(見 Edge Cases 新增段落),今日可依現行設計文字構造測試替身驗證裁定邏輯本身是否被正確跳過,不需要等待該機制的實際實作。**範圍排除:不涵蓋暫停期間發生的呼叫方主動改標/讀檔交接(2026-08-13 第十四輪新增,回應對抗性覆核 qa-lead 發現本 AC 的「完全相同」「不竄改狀態」斷言未隨 Edge Cases 修訂 1 的範圍收斂同步,與 AC-63b 直接矛盾——若暫停選單內觸發讀檔、甲分支標記待重新解析、讀檔取消、丙分支依 AC-63b 改為呼叫 Core Rules #6 重新計算的新目標,恢復後游標目標與暫停前不同,這是文件明文要求的正確行為,不是本 AC 應涵蓋的例外情況)**:本 AC 的 GIVEN/WHEN 情境明文排除暫停/模態期間發生任何呼叫方透過本系統寫入介面的主動 API 呼叫(「設定新目標」「標記目前目標為待重新解析」)——即 Edge Cases 修訂 1 所稱的「呼叫方主動 API 呼叫」路徑,見 Core Rules #7 甲/丙分支。本 AC 只驗證本系統對原生輸入事件的**被動裁定路徑**在暫停期間確實不受任何背景輸入或選單內部操作竄改;若暫停期間發生甲/丙分支的主動改標,恢復後的狀態依 AC-61/AC-63a/AC-63b 各自定義,不受本 AC「完全相同」的斷言涵蓋。

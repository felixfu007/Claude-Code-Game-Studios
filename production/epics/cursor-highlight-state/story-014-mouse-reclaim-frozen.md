## Implementation Notes

*出自 ADR-0005 機制八:*

1. **`evaluate()` 收「目前滑鼠座標」,不收位移量** —— 策略物件內部持有 `_seed` 自行計算淨位移。
   🔴 **這個簽章形狀是刻意的**:它**結構性杜絕** GDD 明文禁止的「路徑總和」實作。舊簽章 `evaluate(mouse_motion_net_delta)` 的參數命名**邀請**這個錯誤。
2. **門檻是逐表面類型的像素常數**,基於**淨位移**(非路徑總和),於**根視窗座標空間**。
3. ✅ **淨位移計算不受 `CanvasLayer` 變換影響** —— 全程只是兩個 viewport-space 座標相減求距離,兩個座標都來自 `get_viewport().get_mouse_position()`,**從未轉進 `CanvasLayer` 的局部空間**。(這一項曾被列為高風險,已由引擎專家更正為虛驚。)
4. **常數配置為 0 或負值時系統必須拒絕啟動**(AC-46),且不得只驗證「常數已存在」(AC-46b)。

- **AC-58(確認類動作不否決滑鼠奪權,2026-08-06 第十一輪新增,回應 qa-lead 審查發現的真矛盾、使用者裁決,見 Core Rules #3 觸發點 (d)「確認類動作不觸發本重置路徑」)**: **GIVEN** 鍵盤/手把持有權威,滑鼠當影格的累積淨位移已達到或超過 `reclaim_threshold_px`,鍵盤/手把於同一影格內**僅**產生確認類或其他非導覽類 `ui_*` action(不產生任何導覽類動作),**WHEN** 檢視該影格結束時的狀態,**THEN** 裝置權威轉移為滑鼠(奪權主張未被否決),游標目標依滑鼠當下懸停目標更新,滑鼠奪權累積位移量已依 Core Rules #3 觸發點 (a) 歸零——確認 Edge Cases 母規則「確認類動作不具備主張裝置權威資格、不落入本規則仲裁範圍」確實延伸至此情境,不與 Core Rules #3 觸發點 (d)/AC-35b(僅導覽類動作否決,見上方窄化修訂)產生相反判定。**與 AC-35b 互為正反面測試**:AC-35b 驗證「鍵盤/手把同幀產生導覽類動作 → 否決成立」,本 AC 驗證「鍵盤/手把同幀僅產生確認類動作 → 否決不成立、滑鼠正常轉移」,兩者共同覆蓋本情境的正反兩面。

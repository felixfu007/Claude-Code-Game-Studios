## 你要決定的:核准這兩份

核准的門檻有五個條件,兩份的對照如下:

| 條件 | 好感度 | 存檔格式 |
|---|---|---|
| 用到的引擎行為都在真的引擎上跑過 | ✅ | ✅ |
| 沒有任何一句話被測試推翻 | ✅ | ✅ |
| 「總共幾項」這類說法都改成逐條列清楚 | ✅ | ✅ |
| 專家覆核跑過,沒有必須先修的問題 | ✅ | ✅ |
| 它依賴的文件已經先被核准 | ✅ 不依賴任何文件 | ⚠️ **依賴好感度那份** |

**最後一格就是為什麼要兩份一起核准。** 存檔那份建立在好感度那份的決定上,
單獨核准它沒有意義。兩份同時核准,兩格就同時成立。

**還有兩件事沒測完,但不擋核准**:一個引擎細節、一個出貨版本的行為
(本機缺少必要元件,已試過三條替代路都不行)。
兩件的共同點是:**不論答案是什麼,文件的決定都不會改變** —— 這正是門檻允許放行的情況。

## 一件你堅持而且做對的事

你要求存檔那份也照同樣強度重來一遍。結果:

| 檢查的人 | 抓到那 3 項必修中的幾項 |
|---|---|
| 引擎專家 | **0**(他判定幾乎全部沒問題) |
| 安全專家 | 1 |
| 技術總監 | 2 |

**如果照原定計畫直接一起核准,這 3 項會原封不動進到一份標著「已核准」的文件裡。**

其中一項的修法**四天前就寫好了** —— 就在測試用的程式碼裡,連「為什麼要這樣做」
都想清楚了,只是從來沒有人把它讀回文件。

**這件事的教訓不是「多查一次比較好」,而是:「已經檢查過」不等於「檢查乾淨」。**
另一份文件也是同樣情形 —— 先前兩道關卡告訴我們「有一個東西沒定義」,今天發現是三個。

| 順序 | 事項 |
|---|---|
| 1 | **你核准兩份** → 程式碼可以開始寫 |
| 2 | 我補上核准紀錄,並更新那份每次開工都會讀到的設定檔 |
| 3 | 之後才輪到:游標那份要不要凍結、戰棋那份要不要檢查 |

⚠️ **一個技術上的提醒,但後果你需要知道**:文件裡「狀態」那一欄是**程式會讀的**,
旁邊的說明文字不是。所以核准必須真的把那一欄改掉 ——
只在旁邊寫一句「已同意」,程式看不到,開發會被自動放行,而人卻以為還擋著。
**那比留在草案更危險。**

## 今天下午電腦閃退了,原因查清楚了 —— 不是這個專案

下午 2 點 26 分,Windows 自己記錄了「記憶體不足」,一分鐘後桌面的檔案總管當掉
(你看到的閃退)。**機器沒有重開,是程式崩潰後自動重啟。**

**真兇是你另一個視窗開著的那個 Java 專案**(`D:\fcm2`)。它的一個 Java 擴充功能
壞掉了:每 1~2 秒重開一次語言分析程式,舊的從不關掉,29 分鐘內失敗了 407 次,
記憶體就這樣一路堆到滿。Windows 點名的前三名是兩個 VS Code 視窗和一個 Java 程式,
**沒有 Claude。**

你關掉那個視窗後,**釋放了約 14.6 GB**,機器從「只剩 3.8 GB」回到「剩 18.4 GB」。

> ⚠️ **下次再開那個 Java 專案之前要先處理,否則同一件事會再發生一次。**
> 這不是第一次了 —— 9 月 8 日發生過完全一樣的一次,連肇事的程式都相同。
> 最小的處理方式:那個專案同時裝了兩套互相打架的 Java 分析工具,關掉其中一套。

## 🔴 今天最值得你知道的一件事:一半的測試證明不了自己有用

**背景**:一條測試如果不管程式壞不壞都顯示綠燈,它就是裝飾品 —— 而且比沒有更糟,
因為它讓人以為有在把關。這個專案上個月才真的踩到:有 6 條測試全綠,結果一查,
**它們根本沒讀過要檢查的那段內容**。

所以今天的工作是:**逐條證明每條測試在程式被弄壞時真的會變紅。**

**結果**:47 條裡 **23 條證明成功**,**24 條證明不了** —— 而且證明不了的原因不是偷懶,
是結構上就做不到。它們檢查的東西(設定檔的內容、資料檔的內容、隨機數的重現性)
沒有可以動手腳的地方;硬要做,只能證明「電腦分得出兩個不同的數字」,
卻要冒讓其他 700 多條測試一起壞掉的風險。

> **這份清單的真正價值,是標出了哪些地方電腦幫不上忙、只能靠人去看。**
> 三位專家各自獨立走到同一個結論,理由已逐條寫進存檔紀錄,任何人都能自己查。

**目前測試總數 670 → 748 條**,我親自跑了全套:61 個套件全跑、零錯誤、零殘留,
唯一失敗仍是那條刻意留紅、你已核准的。

## 過程中抓到的三件事(都是「看起來正常、實際有問題」那一類)

1. **有人為了測試而故意把程式弄壞,清理時只清了一半。** 被弄壞的地方還留在檔案裡,
   而被暫停的測試恢復了 —— 結果會是「測試全部在跑,但測的是一份被動過手腳的程式」。
   **是那位專家自己發現並補救的,我當時只查到另外一半。**
2. **有一條測試明明出錯了,卻回報「通過」。** 原因是那類錯誤在畫面上很大聲,
   但不算在測試結果裡。這是這個專案記錄到的第三種同類型陷阱。
3. **有一個排序假設是錯的**,新寫的測試第一次跑就被抓出來 —— 正好證明了
   「新測試自己也要先跑過才能信」。

## 🔴 需要你裁決兩件事

### 一、「把卡牌接上戰鬥畫面」這份工作,算不算完成?

- **已經達成的**:功能寫完、驗收條件逐條核對**全部通過**、測試全綠。
- **沒達成的**:它的 24 條測試裡,**15 條屬於上面說的「結構上證明不了」那一類**。
- **當初寫的門檻**是「全部證明完才算完成」—— 但那時我們還不知道有證明不了的情況。

> **我的建議**:門檻改成「**每條測試要嘛有證明,要嘛有寫下來的『為什麼證明不了』**」。
> 照這個標準,這份工作已經達標,可以算完成。
> **如果你堅持原門檻,這份工作會永遠無法標記完成** —— 因為那 15 條在結構上就做不到。

### 二、有一條測試「站錯地方」,要不要搬家?

有一條檢查「兩張卡片資料表的編號有沒有對得上」的測試,被放在「卡牌接畫面」那份
工作的檔案裡,但它**不屬於那份工作的驗收範圍**,工作單自己還明文排除了它。

- **專家建議**:測試本身有用、留著,但**搬到別的地方、另開一份工作單**,
  讓它有自己的負責人。
- **不搬的後果**:以後有人要查「卡牌接畫面那份工作驗收了哪些東西」,
  會把它誤算進去。

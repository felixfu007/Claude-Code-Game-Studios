## 行 151 —— 機制七:型別白名單版本域範圍問題(GDD Open Question 4)

### 原文(`draft.md` 第 151 行,逐字)

> GDD Open Question 4 問的是:若採「扁平聯集」型別白名單(所有版本曾經合法過的型別皆
> 列入),存在攻擊者宣告舊規則集版本以繞過較新版本較嚴格檢查的理論風險;若採「依版本
> 分域」,則需要額外的版本↔合法型別集合對照機制。**本 ADR 的格式選擇讓這個問題不成
> 立**:`bytes_to_var(buffer)` 從不產生任何自訂 `Object`,因此不存在「型別」這個維度
> 需要按版本分域——**唯一與版本相關的合法性檢查,是機制六的 `validate_semantics()`
> (語意層級的欄位值域,可以且應該依格式版本分流其檢查邏輯,但那是語意驗證,不是型別
> 白名單)**。GDD 原本擔心的「宣告舊版本以繞過較新版本檢查」風險,在本 ADR 的架構下
> 轉譯為「宣告舊 `format_version` 觸發舊版遷移函數鏈,而非新版驗證邏輯」——這正是
> Core Rules #16 鎖定順序中「遷移鏈執行完成後仍須通過目前版本的語意驗證」(GDD 第二輪
> 裁決)本就防範的情境,不需要本 ADR 額外處理。

### 哪裡是假的

「`bytes_to_var(buffer)` 從不產生任何自訂 `Object`,因此不存在『型別』這個維度」——
**前半句對,後半句的推論不成立**。

- 前半句對:`bytes_to_var()`(1 引數版)遇到 `Object`(typeof 24,含所有自訂
  `class_name` 子類別)時,整包解碼原子性失敗,回傳 `null`,不會產生任何自訂類別的
  實例。這一段沒有問題。
- 但「因此不存在型別這個維度」不成立:`RID`(23)/`Callable`(25)/`Signal`(26)
  **全部不受 `allow_objects` 那道閘門管控**——plain `bytes_to_var()` 對三者一律零
  `ERR_UNAUTHORIZED`、零丟鍵、零整包失敗,寫入側 `var_to_bytes()` 對三者同樣不拒絕
  編碼。型別這個維度沒有消失,只是它的**成員換了一批**(從「所有自訂 Object 子類別」
  換成「23/25/26 這三個固定的引擎內建型別」),而且擋它們的**不是引擎**,是本 ADR
  新增的機制一之二(寫入側 + 讀取側各一道遞迴型別閘門)。

**證據**:`docs/engine-reference/godot/modules/core-serialization.md` 第 4 節開頭段落
逐字:「這三個型別**全部不受 `allow_objects` 那道閘門管控**——plain `bytes_to_var()`
對三者一律零 `ERR_UNAUTHORIZED`、零丟鍵、零整包失敗」;第 3 節「整包解碼原子性失敗」
段落(Object 部分)。

### Core Rules #16 那句論證也需要撤回,理由與上面獨立

原文用「遷移鏈執行完成後仍須通過目前版本的語意驗證」(Core Rules #16)來論證「宣告舊
版本」的風險已被涵蓋。這個論證即使在只考慮 Object 的舊框架下也有時序問題,在新框架下
問題更明顯:

- 語意驗證(機制六 `validate_semantics()`)發生在**遷移鏈執行完成之後**。
- 但型別閘控(機制一之二)必須發生在**遷移鏈執行之前**——因為遷移函數本身要拿到已
  解碼的 `Dictionary` 資料操作,若 `RID`/`Callable`/`Signal` 沒有在解碼後、遷移前就被
  擋下,遷移函數的程式碼就有機會拿到一個活的 `Signal`(同行程內 `connect()`/`emit()`
  真的會生效,見下方 309 節證據)或一個指向真實伺服器資源的 `RID` 去操作——這時語意
  驗證還沒開始跑,Core Rules #16 承諾的「事後驗證」根本還沒到場。
- 這正是機制一之二本身存在的理由(`docs/engine-reference/godot/modules/core-serialization.md`
  各節與骨架驗證 C 都已證明引擎的讀取側除了 Object 之外沒有任何原生閘門)——所以
  「風險已被 Core Rules #16 涵蓋,不需要本 ADR 額外處理」這句話,原本就跟機制一之二
  被加入的理由自相矛盾:如果 Core Rules #16 真的夠了,機制一之二一開始就不必存在。

### 這一段真正該回答的問題

GDD Open Question 4 的實質問題不是「型別白名單存不存在」,而是:**現在型別檢查由本
ADR 自建的 `SaveTypeGate`(機制一之二)承擔,那份允許/拒絕集合需不需要按
`format_version` 分域?**

**我的判斷:仍然不需要分域,但理由與原文完全不同。**

1. **拒絕清單錨定在引擎的 Variant 型別列舉,不是遊戲內容 schema。**
   `RID`(23)/`Object`(24)/`Callable`(25)/`Signal`(26)是 Godot 4.7.1 這個引擎版本
   固定的結構性危險型別(`TYPE_MAX=39`,見 `core-serialization.md` 第 9 節型別枚舉
   全表)。它們的危險性來自 Godot 自身的物件模型(跨行程 ObjectID/RID 語意、Signal
   的 `connect()`/`emit()` 副作用),不是隨遊戲內容版本演進而變動的東西。這與「哪些
   自訂 `class_name` 曾經合法過」是完全不同性質的清單——後者才是 GDD 原本設想的、
   會隨版本成長的「型別白名單」。

2. **統一的拒絕集合本身就消解了 GDD 擔心的繞道情境,而不是靠版本鎖定去防它。**
   GDD 擔心的攻擊面是「宣告舊規則集版本以套用較寬鬆的檢查」。如果拒絕集合按版本分域
   (例如舊版本的清單比較寬鬆),攻擊者確實可能靠宣告舊 `format_version` 去啟用較弱
   的閘門。但如果拒絕集合**對所有宣告版本一視同仁**(不管 `format_version` 寫什麼,
   一律拒絕 23/24/25/26),這個攻擊面根本不存在——不是被防禦擋住,而是沒有「較寬鬆
   的舊版本規則」這個選項可以宣告。

3. **這與語意驗證(機制六)刻意保留版本分流的理由不衝突,而是同一套邏輯的兩個不同
   應用**:語意驗證管的是遊戲內容的值域(例如「好感度數值上限」隨版本調整),這種
   東西天然該隨版本演進;型別閘控管的是「這個位元組序列裡藏了什麼引擎物件」,這是
   跟遊戲內容版本無關的結構性安全問題。原文其實已經隱約點出這個區分(它把
   `validate_semantics()` 標為「可以且應該依版本分流」),只是誤以為型別白名單那邊
   已經因為「不存在」而不需要討論——現在型別白名單确实存在(只是換了地方),但上面
   兩點說明它同樣不需要分域,分域甚至有害。

4. **輔助佐證(非決定性理由)**:目前 `src/` 尚無任何實作程式碼,本 ADR 的機制一之二
   從一開始就會涵蓋所有本 ADR 生效後寫出的存檔——不存在「舊版本存檔是在機制一之二
   實裝前寫的、所以帶著危險型別」這種歷史相容性負擔。但這只是專案現況的附加支持,
   不是分域與否的核心理由(核心理由是第 1、2 點),避免日後專案進度變化就讓這段論證
   失效。

### 建議取代第 151 行的文字(供併入時採用或再調整)

> GDD Open Question 4 問的是:若採「扁平聯集」型別白名單,存在攻擊者宣告舊規則集
> 版本以繞過較新版本較嚴格檢查的理論風險;若採「依版本分域」,則需要額外的版本↔合法
> 型別集合對照機制。**型別這個維度沒有消失,只是換了承擔者與成員**:引擎的
> `allow_objects` 閘門只擋 `Object`(24),`RID`(23)/`Callable`(25)/`Signal`(26)
> 三者完全不受它管控(見 `core-serialization.md` 第 4 節),因此本 ADR 自建機制一之二

> 提供的閘門。**這份拒絕集合本身不需要依版本分域**:它錨定在 Godot 引擎的 Variant
> 型別列舉(結構性、與遊戲內容版本無關),對所有宣告的 `format_version` 一視同仁地
> 拒絕這四個型別,GDD 擔心的「宣告舊版本套用較寬鬆檢查」在這個設計下沒有「較寬鬆的
> 舊版本」可以宣告。機制六 `validate_semantics()` 的欄位值域檢查仍可、也應該依版本
> 分流,但那是語意層級的問題,與型別閘控是兩個不同的維度。⚠️ 原文引用 Core Rules #16
> (「遷移鏈執行完成後仍須通過目前版本的語意驗證」)來佐證風險已涵蓋——這個引用不成立:
> 語意驗證發生在遷移鏈**之後**,而型別閘控必須發生在遷移鏈**之前**(遷移函數本身會
> 操作已解碼的資料),兩者順序不能對調,語意驗證不能替代型別閘控。

## 行 309 —— TR-save-002 的涵蓋理由

### 原文(`draft.md` 第 309 行,逐字)

> | TR-save-002 | 型別白名單須在任何實例化之前完成閘控 | `allow_objects=false` 使白
> 名單問題在引擎層級結構性消除,無自訂型別可被實例化(機制一);讀取順序上白名單解碼
> (機制三步驟 5)先於語意驗證/遷移(步驟 6) |

### 哪裡是假的

- `allow_objects=false` **不是一個可以傳的參數**。全域函式 `bytes_to_var(bytes)` 只有
  一個引數,沒有 `allow_objects` 這個形參;會接受 `allow_objects` 布林參數的是
  `FileAccess.get_var(allow_objects: bool = false)`,是完全不同的 API 形狀(見
  `core-serialization.md` 第 1 節,本 ADR 已因此明文禁止在存檔路徑上使用
  `FileAccess.store_var()`/`get_var()`,見 line58)。原句把兩套 API 混用,是本專案
  已知的「18 處以上」錯誤來源之一。
- 「使白名單問題在引擎層級結構性消除」這句只對 `Object`(24)成立;對
  `RID`(23)/`Callable`(25)/`Signal`(26)**不成立**——引擎的讀取側閘門對這三者
  一律不拒絕,解碼一律成功。

### 重寫成兩段式:寫入側閘門 + 讀取側獨立掃描

> `SaveFormat` 的寫入側(機制一之二,`serialize_block()` 內部呼叫的遞迴型別閘門)在
> 呼叫 `var_to_bytes()` 之前,先掃描整個 payload(含巢狀容器、含 Dictionary 的鍵),
> 遇到 `RID`(23)/`Object`(24)/`Callable`(25)/`Signal`(26)一律拒絕整次序列化
> (`FORBIDDEN_TYPE`),不寫入任何位元組。讀取側(`deserialize_block()`)在
> `bytes_to_var()` 解碼**之後**、任何語意驗證或遷移函數執行**之前**,對解碼出來的
> `Dictionary` 再跑一次**同一份**遞迴型別閘門,同樣拒絕這四個型別
> (`DATA_CORRUPTED`)。兩道閘門共用同一份型別白名單邏輯,避免寫入側與讀取側各自
> 維護一份清單而漂移。這道獨立的讀取側掃描是必要的,不是保守作法:plain
> `bytes_to_var()` 對這四種型別編碼出的位元組,一律**靜默解碼成功**(`Object` 還原成
> `EncodedObjectAsID`;`RID`/`Callable`/`Signal` 還原成對應的活體或半活體值),引擎
> 自身在讀取側**不會**替我們擋下除了 `Object` 以外的三種型別。

**證據**:`docs/engine-reference/godot/modules/core-serialization.md` 第 2-4 節(逐型別
的讀寫行為表);`prototypes/save-format-skeleton-2026-08-21/README.md` 驗證 C(寫入側
毒藥向量表、讀取側對稱閘門表)與判讀陷阱「讀取側必須再跑一次同一組型別閘門——實測是
必要的而非贅餘」。

### 這條需求現在算完全涵蓋還是部分涵蓋——我的判讀

**部分涵蓋,不是完全涵蓋。理由不是「還有型別漏掉」,而是涵蓋的『性質』變了,原文把
兩種不同等級的保證混在一起算成同一格。**

把 TR-save-002 的字面要求(「須在任何實例化之前完成閘控」)拆成兩個部分分別看:

1. **`Object`(24)——是否構成「實例化」、是否被擋:兩者皆是。**
   `Object`(含所有自訂 `class_name` 子類別)若真的被還原,會涉及建構函式與屬性
   setter 執行,是字面意義上的「實例化」。這一項由引擎的讀取側原生行為
   (`bytes_to_var()` 對含 Object 的位元組整包原子性失敗、回傳 `null`)**無條件**
   擋下——不需要本 ADR 的機制一之二介入也會擋住,機制一之二只是加一層縱深防禦
   (防範有人誤用 `_with_objects` 變體,或防範未來 API 變動)。這一部分**完全涵蓋**,
   而且是引擎保證,不是我們自己寫的程式碼保證。

2. **`RID`(23)/`Callable`(25)/`Signal`(26)——嚴格說不算「實例化」,但危險程度
   不亞於實例化,而且涵蓋來源完全不同。**
   這三者的解碼不會建構新的類別實例、不會執行任何建構子——`RID` 只是一個數值 id、
   `Signal`/`Callable` 是還原一個指向既有 ObjectID 的殼。若照需求字面「實例化」來看,
   這三者根本不在 TR-save-002 的討論範圍內,那麼這格的字面涵蓋率反而是「完全」(因為
   唯一符合「實例化」定義的型別已被引擎擋住)。但這種讀法明顯不是需求的本意——需求
   關心的是「解碼出來的東西在被驗證之前不能被拿去做危險的事」,而 `Signal` 同行程內
   `connect()`/`emit()` 真的會觸發處理函式(`core-serialization.md` 第 4 節)、`RID`
   在跨行程情境下會指向一個真實存在、屬於別人的活體伺服器資源(骨架驗證 F-3,已實測
   成立且具決定性,非機率碰撞)——這些後果不比「實例化一個惡意物件」溫和。若採這種
   目的性的讀法,這三個型別的涵蓋**完全依賴機制一之二被正確實作**:它不是引擎給的
   免費保證,是本 ADR 自己要求寫、要求維護、要求測試的程式碼。一旦這道閘門漏掃某個
   巢狀路徑或某個 Dictionary 鍵位置,涵蓋就會破。

**結論**:這格不能整格記為「完全涵蓋」,因為它混合了兩種不同確定性等級的保證
(引擎結構性保證 vs. 本 ADR 自建機制的正確性),而原文的敘述方式(「引擎層級結構性
消除」)把整格都算成第一種等級,這對 `Object` 是對的,對另外三個型別是不成立的。
**是否要把它記為「部分涵蓋」還是換一種方式標註(例如標「完全涵蓋,但條件式」)**,
留給第八輪審查依涵蓋判定的既定方法採計——我只確認:原文的理由對三分之四的相關型別
不成立,而修正後的理由是否構成「完全」,取決於審查是否接受「涵蓋來源可以是本 ADR
自建機制,不必是引擎原生保證」這個前提。

### 建議取代第 309 行表格列的文字(供併入時採用或再調整)

> | TR-save-002 | 型別白名單須在任何實例化之前完成閘控 | 分兩部分:(1)`Object`
> (24)由引擎讀取側原生行為無條件擋下(`bytes_to_var()` 對含 Object 的位元組整包
> 原子性失敗),這部分不依賴本 ADR 的任何額外機制;(2)`RID`(23)/`Callable`(25)/
> `Signal`(26)不受引擎任何原生閘門管控,由本 ADR 新增的機制一之二(寫入側 +
> 讀取側各一道遞迴型別閘門,兩者共用同一份型別判定邏輯)在遷移/語意驗證(機制六)
> **之前**攔截,讀取順序上型別閘控(機制三步驟 5)先於語意驗證/遷移(步驟 6)不變 |

   精確化(不是修正):「不擋」指的是**解碼/編碼本身不失敗**(零 `ERR_UNAUTHORIZED`、
   零整包失敗),不代表這三者解碼後一定「可正常使用」——`Callable` 解碼後其實是個
   空殼(`is_valid()=false`),呼叫它會中止呼叫端函式;`Signal` 跨行程解碼後
   `get_object()` 是 `null`、`connect()` 會失敗。這些是解碼**之後**的不同下場,
   跟「有沒有被擋」是兩個不同的問題,協調者的行文在 309 段落已經正確地把
   「真的可用」限定在「同行程內」,沒有誤用到跨行程情境,所以這不算協調者的錯誤,
   只是我在下筆時把這個區分明寫出來,避免後續讀者把「不擋」誤讀成「解碼結果都安全
   可用」。

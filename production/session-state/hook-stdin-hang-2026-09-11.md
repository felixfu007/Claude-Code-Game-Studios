> ⚠️ **檔名 `hook-stdin-hang` 已不準確** —— 保留原檔名只因它已被其他紀錄引用。
> 真正的根因不是 stdin,是逾時上限,見下方「更正」節。

## 🔴 更正(2026-09-11 傍晚,由第三個 session 實測推翻本檔原判定)

**本檔原本的根因判定「hook 卡在 `INPUT=$(cat)` 讀 stdin」是錯的。** 兩項證據:

1. **修補在 16:30 就已寫進工作區,而同型卡死在 16:52、16:56 再度發作** ——
   兩個 session(`f370b9c1` 卡在 `git status`、`657c8e77` 卡在 `git commit`)各自停住
   超過 20 分鐘,使用者輸入的下一則訊息被排進佇列但從未被處理。
   **修完之後才發作,就不可能是被修掉的那個原因。**
2. **殘留卡死行程(PID 15916)的執行緒狀態實測為 `Suspended`、起始位址 0、累計 CPU
   `00:00:00`,且無任何子行程。** 真的卡在 `INPUT=$(cat)` 的話,前面 70 行早已執行完畢,
   而且會有一個 `timeout` / `cat` 子行程存在。
   ⚠️ **原判定其實與本檔自己列的「CPU 0.00 秒、一步都沒跑」互相矛盾** —— 那句量測是對的,
   但它否證的是原判定,不是支持它。

### 真正的根因:逾時上限訂得比實際耗時短

**這台機器每開一個外部行程要 0.5~1.5 秒。** 對照組:空的 `bash -c 'exit 0'` 只要 **0.78 秒**,
而 `date`、`mkdir`、`jq` 各要 0.8~1.5 秒 —— **慢的不是 bash 啟動,是每一次 `fork`/`exec`**
(很可能是防毒軟體逐一掃描)。因此一支 hook 有多慢,與它的邏輯複雜度無關,
**與它開了幾個外部行程成正比。**

實測(本機,真實負載輸入):

| Hook | 實測耗時 | 原上限 | |
|---|---|---|---|
| `validate-commit`(真提交) | **22.0 秒** | 15 | 🔴 必然逾時 —— `657c8e77` 卡在這 |
| `pre-compact` | 16.0 秒 | 10 | 🔴 |
| `advise-file-owner` | 8.5~10.7 秒 | 5 | 🔴 —— `f370b9c1` 卡在這 |
| `detect-gaps` | 10.5 秒 | 10 | 🔴 |
| `advise-skill-owner` | 5.6 秒 | 5 | 🔴 |

**已處置**:`.claude/settings.json` 全部 16 個 hook 上限依實測重訂,一律留至少 3 倍餘裕。

⚠️ **原本的 stdin 保護予以保留,但要知道它擋的不是這次的問題。** 它本身無害(那種卡法
理論上存在),只是它每支 hook 要多付約 1.5 秒(`timeout` 與 `cat` 各一個行程)——
在這台機器上這個代價不小。要再加快,方向是換成 bash 內建的 `read -t`(零外部行程),
但**那屬於效能優化,不是修正確性**。

🔴 **第三節第 2 點的教訓,在本檔自己身上又發作了一次。** 那一點寫的是
「自述與量測衝突時以量測為準」,而本檔的根因正是從「第一行寫著 `cat`」**推論**出來的,
不是量出來的 —— **沒有人量過那個行程實際停在哪一步。** 寫下它的人同一天剛寫完那條教訓。

## 一、發生了什麼

一個 session(`f370b9c1`)從 **14:28 停到 16:28,整整 89 分鐘沒有任何動作**。

它在 14:27:58 發出一個唯讀指令(讀 `battle_controller.gd` 的 `end_faction_phase`),
**該指令從頭到尾沒有拿到任何結果**。卡住的不是指令,是擋在它前面的
`advise-file-owner.sh`。

### 決定性證據(實機量測,非推論)

| 量測項 | 值 |
|---|---|
| hook 行程 PID 9240 存活時間 | 14:28:11 → 15:58(89 分鐘) |
| 該行程累計 CPU | **0.00 秒** —— 從啟動到被殺,一步都沒跑 |
| 該行程執行緒數 / 記憶體 | 1 / 3 MB |
| 父行程 | **已不存在**(孤兒行程) |
| 對應的 tool_use | `toolu_018y1wiBVBJkXKiNSpwUuGUp`,**永遠沒有 tool_result** |

同時間 `validate-commit.sh`(PID 35748,14:29:53 起)以完全相同的形狀卡死。

### 根因

兩支 hook 的第一個動作都是裸的 `INPUT=$(cat)` —— 讀 stdin 直到 EOF。
**Claude Code 若沒有關閉 stdin,這一行就無限期阻塞:CPU 0%、無輸出、不留痕跡,
從外面看跟「還在努力工作」一模一樣。**

🔴 **Claude Code 的 hook 逾時只取消了「邏輯上的 hook」,沒有殺掉行程。**
事發前 7 分鐘內同一支 hook 已被逾時取消兩次(14:21:48 用 6.7 秒、14:28:02 用 6.1 秒,
設定上限 5 秒)——**第三次就再也沒回來。那兩次逾時是預警,當下沒有人看出來。**

## 二、處置

### 已做

- 結束兩個卡死的孤兒行程(PID 9240、35748)。
- **9 支 hook 全部加上 stdin 讀取超時保護**(不只卡死的那兩支 —— 缺陷是共通的):
  `advise-file-owner` / `advise-skill-owner` / `log-agent` / `log-agent-stop` /
  `notify` / `validate-assets` / `validate-commit` / `validate-push` /
  `validate-skill-change`。
- 讀取上限 **2 秒**(最短的 hook 逾時是 5 秒,留 3 秒給實際工作)。
- 逾時後**放行,但大聲說「本次閘門未執行,這不是檢查通過」**。
  依本專案既有規則(commit `c9f2f88`):沉默不得與「hook 沒跑」長得一樣。
- 逾時時**絕不**拿讀到一半的資料繼續跑(避免半截 JSON 造成無聲誤判),直接退出。

### 驗證(兩個方向都測,不只測「不當機」)

| 測試 | 結果 |
|---|---|
| stdin 永不關閉(重現卡死) | 從**無限**變成 2 秒後退出並警告 ✅ |
| Bash `sed -i` 改 `design/ux/` | 照常點名 `ux-designer` ✅ |
| Write 改 `.gd` | 照常點名 `gameplay-programmer` + `godot-gdscript-specialist` ✅ |
| 唯讀指令 `git status` | 照常完全安靜,無誤報 ✅ |
| `git push` 到 main | 照常跳保護分支提醒 ✅ |
| 9 支 `bash -n` 語法檢查 | 全過 ✅ |

**未動任何檢查邏輯,只動阻塞行為。**

## 三、🔴 三件必須傳下去的事

1. **殺行程並沒有讓 session 恢復。** 時間序:15:58 殺行程 → 15:58~16:28 那個 session
   **完全沒有新動作** → 16:28:43 **使用者手動中斷**才恢復。
   **結論:hook 行程卡死後,Claude Code 端也會一起卡住,只有手動中斷能救。**
   下次再遇到,不要只殺行程就以為會自己好。

2. ⚠️ **那個 session 恢復後自述是「卡在一個被拒絕的指令上」—— 那是它的猜測,不是證據。**
   實測是 hook 卡在 `INPUT=$(cat)`。若照它的說法理解成「權限沒給」,
   就不會去修真正的原因。**自述與量測衝突時以量測為準。**

3. ⚠️ **本次修改跳過了專家覆核,待補。**
   `.claude/hooks/` 依 `agent-routing.tsv` 應由工具/流程專家經手,但事發當下的
   session 明文禁止派工,由協調者自行修改。修改內容是機械式的(9 檔同一段、
   每檔 +19 行、全數 `bash -n` 通過、功能雙向實測),但**「機械式」不等於「已覆核」**。
   **建議補一輪 `tools-programmer` 覆核,重點看:2 秒是否合適、
   逾時後 exit 0(放行)對 `validate-commit` / `validate-push` 這兩道阻擋型閘門
   是否可接受。**
   🔴 後者是真的取捨:逾時放行代表提交/推送可能在未經檢查的情況下通過。
   選它的理由是「無限卡死更糟,且現在會大聲說出來」,但**這是協調者的判斷,不是裁決過的**。

## 四、🔴 順帶查到的第二個問題(已定位根因,尚未處理)

`production/session-logs/session-log.md` 已達 **195 MB / 217 萬行**。

**根因在 `session-stop.sh` 第 20-25 行:每次觸發都 `cat` 整份 `active.md` 追加進去。**

| 量測項 | 值 |
|---|---|
| 整份 `active.md` 被複製進去的次數 | **970 次** |
| `active.md` 現在的大小 | **520 KB** |
| 今天(09-11)觸發次數 | **10 次** |

🔴 **Stop hook 不是「每個 session 一次」,是每次 Claude 回完話就觸發一次。**
今天的時間戳(08:28、08:38、08:43 … 14:23、16:29、16:36)可以直接看出來。

**而且是加速膨脹的**:`active.md` 越長,每次複製就越大。以現在的速度約
**5 MB/天**,且會隨 `active.md` 成長而變快。

✅ 該檔已在 `.gitignore`,**沒有污染版控**。
⚠️ 但它會拖慢任何掃描 `production/` 的工具,而本專案有數支 hook 會掃該目錄。

**尚未處理 —— 這需要一個決定,不是清掉檔案就好:**
究竟要不要每次都存一份 `active.md` 快照?若要,該存差異而非全文;
若不要,該改成只記 commit 與變更檔清單(也就是 `session-stop.sh` 後半段本來就在做的事)。

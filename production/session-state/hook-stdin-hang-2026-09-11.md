### 真正的根因:逾時上限訂得比實際耗時短

**這台機器每開一個外部行程要 0.5~1.5 秒。** 對照組:空的 `bash -c 'exit 0'` 只要 **0.78 秒**,
而 `date`、`mkdir`、`jq` 各要 0.8~1.5 秒 —— **慢的不是 bash 啟動,是每一次 `fork`/`exec`**
(很可能是防毒軟體逐一掃描)。因此一支 hook 有多慢,與它的邏輯複雜度無關,
**與它開了幾個外部行程成正比。**

## 一、發生了什麼

一個 session(`f370b9c1`)從 **14:28 停到 16:28,整整 89 分鐘沒有任何動作**。

它在 14:27:58 發出一個唯讀指令(讀 `battle_controller.gd` 的 `end_faction_phase`),
**該指令從頭到尾沒有拿到任何結果**。卡住的不是指令,是擋在它前面的
`advise-file-owner.sh`。

### 決定性證據(實機量測,非推論)

| 量測項 | 值 |
|---|---|
| hook 行程 PID 9240 存活時間 | 14:28:11 → 15:58(89 分鐘) |
| 該行程累計 CPU | **0.00 秒** —— 從啟動到被殺,一步都沒跑 |
| 該行程執行緒數 / 記憶體 | 1 / 3 MB |
| 父行程 | **已不存在**(孤兒行程) |
| 對應的 tool_use | `toolu_018y1wiBVBJkXKiNSpwUuGUp`,**永遠沒有 tool_result** |

同時間 `validate-commit.sh`(PID 35748,14:29:53 起)以完全相同的形狀卡死。

### 根因

兩支 hook 的第一個動作都是裸的 `INPUT=$(cat)` —— 讀 stdin 直到 EOF。
**Claude Code 若沒有關閉 stdin,這一行就無限期阻塞:CPU 0%、無輸出、不留痕跡,
從外面看跟「還在努力工作」一模一樣。**

🔴 **Claude Code 的 hook 逾時只取消了「邏輯上的 hook」,沒有殺掉行程。**
事發前 7 分鐘內同一支 hook 已被逾時取消兩次(14:21:48 用 6.7 秒、14:28:02 用 6.1 秒,
設定上限 5 秒)——**第三次就再也沒回來。那兩次逾時是預警,當下沒有人看出來。**

# Spike:Story 010 的「圖層變換恆等」測試,在 headless 下驗不驗得到東西?

> PROTOTYPE - NOT FOR PRODUCTION / 拋棄式驗證探針
> **日期**:2026-09-04
> **執行**:主 session,本機 Godot 4.7.1 headless
> **log**:`logs/probe_output.txt`(逐字輸出,未編修)

## 為什麼要先跑這支

Story 010 的核心價值是一條防護測試:確認游標圖層的變換是恆等的。
但工作單自己寫了一句警告 ——「四種解析度在 headless 測試環境下如何模擬,若做不到,如實登記為
未涵蓋,不要用一個測得到但驗不到東西的替代寫法」,並點名本專案已有三次同形失效
(Story 003 AC-51、Story 007 AC-32、Story 012 全案)。

**所以開工前要先回答的不是「測試會不會綠」,是「它該紅的時候會不會紅」。**

⚠️ 本探針專案的 `project.godot` **刻意複製主專案的畫面設定**(480×270 / canvas_items /
keep / integer)。用預設值會量到一個「本來就沒有縮放」的乾淨環境,那樣的恆等結論是假的。

## 四個問題與答案

| | 問題 | 答案 |
|---|---|---|
| Q1 | headless 下模擬得出四種解析度嗎? | ✅ **可以,但只有一條路** |
| Q2 | 專屬圖層在四種解析度下恆等嗎? | ✅ 四種全部恆等 |
| Q3 | 故意做出失效態,斷言會紅嗎? | ✅ **會紅**(兩種失效形狀都會) |
| Q4 | headless 有真的套用畫面縮放嗎? | ✅ **有,而且數字與真實 GPU 一致** |

### Q1 🔴 `DisplayServer` 在 headless 是空殼,不能用它設解析度

逐字量測:

```
DisplayServer.window_get_size() = (0, 0)   ← 四種解析度下全部回傳 (0, 0)
root.size                       = (1920, 1080) / (2560, 1440) / (3840, 2160) / (3440, 1440)
```

**`DisplayServer.window_set_size()` 在 headless 是 no-op,而且它不報錯。**
唯一有效的是直接指派 `get_tree().root.size`。

⚠️ **這正是本專案最怕的失效形狀**:若測試改用 `DisplayServer` 設解析度,
它會安靜地什麼都不做,四個迴圈全部在同一個尺寸下跑,**然後四條斷言全部通過**。
測試會綠、報告會漂亮、而它一種解析度都沒驗到。**寫測試時必須用 `root.size`。**

### Q4 headless 確實套用了 content scale,而且數字對得上真實 GPU

```
1920×1080 → 縮放 4×,offset (0, 0)
2560×1440 → 縮放 5×,offset (80, 45)
3840×2160 → 縮放 8×,offset (0, 0)
3440×1440 → 縮放 5×,offset (520, 45)
```

🔴 **這四組數字與 2026-09-01 那支非 headless、真實 GPU 的 spike 逐項一致**
(該 spike 量到 2K 為 `scale=(5.0, 5.0) offset=(80.0, 45.0)`;超寬的左右各 520 px 亦見
`design/art/screen-architecture.md` 的倍率表)。

**這一致性是本探針最重要的結論**:它證明 headless 不是一個「什麼都沒發生所以恆等」的空環境
—— 根視窗**確實帶著一個非恆等的變換**,而專屬圖層**確實逃出了它**。
兩者若沒有分別,Q2 的恆等就毫無資訊量。

### Q3 靈敏度 —— 兩種失效形狀都抓得到

| 失效形狀 | 量到的變換 | 斷言 |
|---|---|---|
| 圖層被縮放(與介面圖層共用的真實形狀) | `x=(2.667, 0) y=(0, 2.667)` | 🔴 紅 |
| 圖層乾淨但被 offset 推開 | `o=(80, 45)` | 🔴 紅 |

第二列值得記:**只有位移、沒有縮放的失效態一樣抓得到** —— 恆等比對涵蓋兩者,
不需要為位移另寫一條。

## 對 Story 010 的結論

✅ **AC-S010-a 可以寫成一條會執行、且會在正確時機失敗的自動化測試,不必登記為未涵蓋。**

**寫測試時的三條硬性要求(全部出自上方量測,不是推論)**:

1. **解析度一律用 `get_tree().root.size` 指派,不得用 `DisplayServer.window_set_size()`**
   —— 後者在 headless 靜默失效,會把四條斷言變成同一條。
2. **測試專案的畫面設定必須是主專案的實際值**(480×270 / canvas_items / keep / integer)。
   跑在預設設定下,恆等會因為「本來就沒縮放」而恆真。
3. **同一支測試檔必須含一條靈敏度測試**(故意建一顆被縮放的圖層並斷言它不恆等),
   否則沒有任何東西能證明前一條斷言不是假警報器。

## 已知未涵蓋

- **本探針全程 headless。** 真實視窗下的行為由 2026-09-01 那支非 headless spike 涵蓋,
  本探針只補「headless 能不能重現它」這一段。
- **沒有畫任何東西、沒有截圖。** 量的是變換矩陣,不是畫面。
  「游標實際畫在正確位置」屬 Story 011 的自繪載體,不在本張範圍。
- Q3 印出的偏差像素數是本探針自己用 2.667 倍率算的示意值,
  **與文件既有的 1440 / 2178 / 3304 px 不是同一組量測,不要互相引用。**

## 追加(2026-09-04 下午):兩支排序/邊界探針

本目錄原本只回答「Story 010 的測試驗不驗得到」。同日下午為了決定**下一張做什麼**,
在同一個探針專案裡追加兩支,一併留在這裡(它們共用同一份 `project.godot` 設定)。

### `order_probe.gd` —— 切換縮放模式會不會改變游標系統讀到的座標?

**會,而且差 4~8 倍。** log:`logs/order_probe_output.txt`

| 視窗 | `canvas_items` 下 `root.get_visible_rect()` | 執行期切成 `disabled` 後 |
|---|---|---|
| 1920×1080 | 480 × 270 | **1920 × 1080** |
| 2560×1440 | 480 × 270 | **2560 × 1440** |
| 3840×2160 | 480 × 270 | **3840 × 2160** |

**用途**:這個量測直接決定了工作單排序 —— Story 011(自繪游標)吃這個座標,
若先做 011 再切設定,等於照著一個已決定放棄的座標系去做,手感數字要重調。
管理者據此把 `screen-scaling` 001 排在 Story 011 之前。

⚠️ **本探針是在執行期用 `root.content_scale_mode` 切換**,不是改 `project.godot` 重跑。
兩者是否在所有面向等價**未經驗證** —— 但本探針只讀 `get_visible_rect()` 這一個量,
且切換前的值與專案設定一致(480×270),足以支撐「座標空間會變」這個結論。
**不要把本探針當成「執行期切換與設定檔切換等價」的證據。**

### `minsize_probe.gd` —— 引擎有沒有現成的最小視窗尺寸機制?

**有,而且是引擎強制的。** log:`logs/minsize_probe_output.txt`

- `Window.min_size` 屬性存在,預設 `(64, 64)`;`DisplayServer.window_set_min_size()` 存在。
- 實測:設 `min_size = (480, 270)` 後指派 `size = (320, 180)` → **讀回來是 `(480, 270)`**。
  引擎當場夾回,不需要自己寫防護。

**用途**:回答 `story-001-manual-world-scaling.md` 明文標為「停下來問」的那條邊界
(視窗小於棋盤基準時倍率會算出 0)。管理者 2026-09-04 裁決**最小視窗 960×540**(棋盤 2 倍,
與專案現行預設視窗一致),使「倍率為 0」在結構上不可能發生。

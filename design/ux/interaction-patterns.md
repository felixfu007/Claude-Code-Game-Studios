## Overview

本文件是《盲目於微光》的互動模式庫:一組跨畫面共用的互動規則,讓不同系統的介面在行為上一致,並讓實作者不必為每個畫面重新發明已經定案過的東西。

**本庫的來源與眾不同的一點**:一般模式庫是從既有 UX 規格反推出來的,但本專案在撰寫時**尚無任何 UX 規格**(`design/ux/` 只有無障礙需求)。因此這 15 個模式全部**從已 Approved 的 GDD 行為規格推導**——主要是戰棋移動與交戰系統的 UI Requirements §1–§7,加上單一游標/高亮狀態系統的 Core Rules。這反而更穩:模式的權威來源是已收斂的行為契約,不是別人的版面選擇。

**因此本庫只定案行為與結構,不定案外觀。** `/art-bible` 尚未執行,色彩、圖示、邊框、字級、動效曲線全部未定,每個模式因此都帶一個「外觀:待 art bible」欄位。

### 貫穿全庫的三條通則

這三條不是模式,是模式背後反覆出現的同一種思考。實作者遇到本庫沒涵蓋的新情境時,應該回頭套用它們:

**通則一 —— 顯示與結算必須一致,且「零/空」不得被隱藏。**
`P-D1` 不准為了效能放棄成因區分、`P-D3` 不准預覽路徑與動畫路徑不一致、`P-D5` 不准 0 傷害不顯示、`P-M1` 不准 `Φ=0` 時隱藏欄位。四者指向同一個失敗模式:**玩家事後才發現系統跟他看到的不一樣**。隱藏一個零值省下的版面,遠不及玩家因此無法區分「沒發生」與「沒算進去」的代價。

**通則二 —— 用生命週期做區隔,比用外觀做區隔更穩固。**
兩個語意不同但長得像的東西(預判 vs 確認、預判無效果 vs 結算 0 傷害),靠**存在時機**區分比靠**視覺差異**區分更難出錯。玩家在快速操作時不會細看外觀差異,但「這個東西只在我停在候選格時才存在」是身體記得住的。見 `P-M2`。

**通則三 —— 結構保證優於紀律要求。**
凡是「靠實作者記得遵守」的規則都會在第 N 次修改時失守。因此:全手把對等寫成**原則**而非清單(`P-I2`,該清單兩輪內漏掉兩項)、拒絕原因拆成**兩個獨立查詢**而非一個合併布林(`P-F2`,合併會讓可區分回饋結構上不可能)、單一高亮靠**單一狀態源**而非各表面自律(`P-N2`)。設計介面時優先問「怎麼讓錯誤的實作寫不出來」,而不是「怎麼提醒實作者不要寫錯」。

## Patterns

### 導覽類(Navigation)

#### P-N1 游標即檢視(Cursor-as-Inspection)

| 欄位 | 內容 |
|---|---|
| **類別** | 導覽 |
| **來源** | 戰棋 GDD UI Requirements §1、§3;`.claude/docs/technical-preferences.md`「禁止 hover-only」 |
| **使用於** | 棋盤格、關係圖迷你地圖、卡牌選取區、對話選項(全部四種已註冊表面) |

**描述**:檢視任何目標狀態的**唯一**機制是把游標移到它上面。資訊面板隨游標所在位置**即時更新**,不需要額外的確認鍵展開,也不得只在滑鼠懸停時出現。

**規格**:
- 面板內容於游標目標改變的**同一影格**更新,不延遲、不需二次輸入。
- 面板更新前**必須**先查詢游標系統的有效性旗標;旗標無效時走 **P-F1 未解析態**,不得沿用上一格的殘留內容。
- 「移到就顯示」對鍵鼠與手把**行為完全相同**——手把 d-pad 移動游標所觸發的面板更新,與滑鼠移動觸發的**不得有任何差異**。
- 路徑預覽等衍生資訊同樣適用:游標停在可達格即顯示完整路徑,不需按鍵展開(見 **P-D3 決定性路徑預覽**)。

**何時用**:任何「玩家需要在決策前得知某個目標的狀態」的介面。

**何時不用**:需要玩家**主動確認**才應發生的破壞性操作——那是 **P-M1 確認面板**的領域。**檢視是免費的,執行不是。**

> **⚠️ 本模式禁止**:任何「滑鼠懸停才顯示、手把要按鍵才顯示」的實作。主機沒有游標,那樣的介面在手把上等於不存在。

**外觀**:待 art bible(面板版面、字級、更新動效皆未定)。

#### P-N2 單一高亮不變式(Single Highlight Invariant)

| 欄位 | 內容 |
|---|---|
| **類別** | 導覽 |
| **來源** | 游標 GDD AC-2、AC-4、AC-5、Core Rules #7 |
| **使用於** | 所有已註冊表面(**跨表面全域不變式**) |

**描述**:**跨全部已註冊表面加總,任一影格恰有一個游標高亮**——不是 0 個,也不是 2 個以上。**包含未初始化狀態。**

**規格**:
- 所有表面的高亮**只讀同一個狀態源**,不得各自維護高亮邏輯。
- 對表面 A 產生有效輸入時,表面 B 上原本的高亮**立即消失**。
- 新增第三方表面時,只需接上共用讀寫介面即自動參與此不變式,**不需修改游標系統本體**。
- 已註冊表面**不得**使用引擎原生 Control focus/hover 繪製高亮——那會產生第二個高亮(見 ADR-0005 機制十四;注意該約束只適用根節點為 `Control` 的表面)。

**何時用**:任何具「目前選中/懸停目標」語意的表面。

**何時不用**:**釘選/多選標記不受此約束**——關係圖迷你地圖可同時有多個釘選標記,那是下游系統自己維護的視覺,與游標高亮是兩回事。

> **⚠️ 範圍界線**:此不變式管的是 hover/游標高亮,不管釘選集合。把兩者混為一談會讓多選功能被誤判為違反不變式。

**外觀**:待 art bible(高亮的形式、三態視覺差異皆未定;唯一已定案的約束是**不得只靠色彩區分**,見 **P-F3**)。

#### P-N3 取消/返回(Cancel & Back,零狀態寫入)

| 欄位 | 內容 |
|---|---|
| **類別** | 導覽 |
| **來源** | 戰棋 GDD UI Requirements §6、Core Rules #8 |
| **使用於** | 移動目的地選取、攻擊目標選取、預判標記 |

**描述**:任何**尚未確認**的選取都必須可以取消回上一步,而且**取消本身不得產生任何狀態寫入**。

**規格**:
- 取消是純函數操作:執行前後,遊戲狀態逐欄位相同。
- 每一層選取都有對應的返回層級,不得出現「只能整個取消、不能退一步」的死路。
- 鍵鼠與手把各自都要有取消路徑(見 **P-I2 全手把對等**)。
- **已確認執行**的行動可否撤銷**不屬於本模式**——那是回合/存檔互動的範圍,戰棋 GDD 已登記為 **OQ-11** 未決。

**何時用**:所有多步驟、有中間狀態的操作序列。

**何時不用**:已寫入持久狀態之後。那時需要的是明確的「復原」功能,**語意與代價都與取消不同——不要用同一個按鍵、也不要用同一個詞。**

**外觀**:待 art bible。

### 輸入類(Input)

> 本節兩項的性質與其他模式不同:它們是**全域約束**,不是「某個畫面怎麼做」,而是「所有畫面都不准違反」。放在同一份庫裡是因為實作者查模式時需要在同一個地方看到它們。

#### P-I1 裝置權威交接(Device Authority Handoff)

| 欄位 | 內容 |
|---|---|
| **類別** | 輸入(全域約束) |
| **來源** | 游標 GDD Core Rules #3/#4、AC-10/10b/11/12/14;ADR-0005 |
| **使用於** | 全域(所有表面共用同一個裝置權威欄位) |

**描述**:任一時刻只有一個裝置持有「權威」。權威轉移時,**失去權威的裝置其原生視覺立即被抑制**,游標目標依裝置類別決定是否沿用。

**規格**:
- **判定依據是 `ui_*` action 的來源裝置類別,絕不讀裝置 ID**(Godot 4.7 重新編號了鍵鼠裝置 ID;ADR-0005 機制四對此為結構性免疫)。
- 原始輸入事件本身**不足以**觸發權威轉移——滑鼠移動未觸發任何 `ui_*` action 時,權威不變。
- **無逾時釋放**:裝置 A 取得權威後,在 B 產生下一個 `ui_*` action 之前,權威恆為 A,不論經過多久。
- 交接視覺延遲 **≤ 1 影格**(ADR-0005 機制六的 `process_priority` 定序使它實際上是同影格完成)。
- 兩種裝置的「重新取得權威」門檻**不同**:滑鼠需累積淨位移達空間門檻;鍵盤/手把任一導覽動作即可。

**何時用**:任何同時支援鍵鼠與手把、且兩者會競爭同一個焦點/游標的介面。

**何時不用**:**未註冊表面**不受管轄——非模態設定側欄等可照常使用引擎原生 focus/hover(AC-60)。若希望該類表面在手把持權威時仍看得見原生指標,必須**明文登記**至例外白名單(`CursorSurfaceRegistry.register_native_pointer_exception()`,ADR-0005 機制十三之二)。

> **⚠️ 已知殘留缺陷**:類比搖桿持續按住會造成滑鼠奪權**永久鎖死**(E1,spike 實測 100% 可重現)。該子機制已由使用者裁決凍結、待手把硬體,本模式**不宣稱此風險已被圍堵**。此缺陷高度命中**運動無障礙**——切換式輔助裝置模擬按鍵的持續觸發模式正好會踩中(已登記於 `design/ux/accessibility-requirements.md`)。

**外觀**:待 art bible(全域裝置指示元件的形式未定;已定案的約束是**不得只靠色彩區分**,見 **P-F3**)。

#### P-I2 全手把對等(Full Gamepad Parity)

| 欄位 | 內容 |
|---|---|
| **類別** | 輸入(全域約束,**無例外**) |
| **來源** | 戰棋 GDD UI Requirements §6(原則陳述)、`.claude/docs/technical-preferences.md`、無障礙 Tier **Standard** |
| **使用於** | **全專案** |

**描述**:**每一個玩家可發起的操作,一律須有完全不依賴滑鼠的操作路徑。不得存在任何僅滑鼠可達的功能。**

**規格**:
- 這是**原則陳述,不是清單**。新增任何玩家操作時自動落入涵蓋範圍,不需要有人記得去補清單。
- 主機無游標,滑鼠路徑在主機上等於不存在——因此「手把路徑」不是備援,是**主要路徑**。
- 無障礙 Tier 為 **Standard**,因此**全平台完整輸入重新綁定**是硬性要求。⚠️ 承擔此功能的「輸入設定/重新綁定」系統**尚未列入 `systems-index.md`**,下次系統盤點必須納入(見 `design/ux/accessibility-requirements.md` Open Questions)。

> **這條為什麼必須是原則而不是列舉**(戰棋 GDD 的修法史,原樣搬進模式庫):該清單在兩輪內連續漏掉兩項——第一輪漏了 Core Rules #9 新增的「主動結束行動」,第二輪漏了「確認移動」(「確認攻擊」的對稱操作)。**裸列舉不會自動涵蓋新增的操作,而漏一項就等於開一個「僅滑鼠可達」的缺口。**

**何時用**:永遠。這是專案級約束,不是可選模式。

**何時不用**:**無例外**。若某個功能真的無法設計出手把路徑,那是**設計缺陷**,不是本原則的例外——回頭改設計。

**外觀**:不適用(本項不涉及呈現)。

### 資料呈現類(Data Display)

> **本節五項中有三項(P-D1 / P-D3 / P-D5)共用同一條底層原則**:**顯示與結算必須一致,且「零/空」不得被隱藏**。三者各自對應戰棋 GDD Player Fantasy 的具名失敗模式「事後才知道」的一個面向,見 Overview。

#### P-D1 三態範圍疊加圖(Tri-state Range Overlay)

| 欄位 | 內容 |
|---|---|
| **類別** | 資料呈現 |
| **來源** | 戰棋 GDD UI Requirements §2、Visual/Audio §1.1、Formulas 公式三 |
| **使用於** | 移動範圍顯示(棋盤) |

**描述**:範圍顯示必須把「不可達」拆解出**成因**,不能只給可達/不可達的二元。三態**互斥且窮盡**:

| 呈現狀態 | 集合運算 |
|---|---|
| 可達 | `A = reachable_set(u, ignore_occupancy=false)` |
| 不可達——**被佔位擋死** | `B \ A`,其中 `B = reachable_set(u, ignore_occupancy=true)` |
| 不可達——**移動力不足** | `Grid \ B` |

**規格**:
- 三集合的聯集恆等於整張棋盤,**無第四類殘留**;`A ⊆ B` 恆成立,故 `B \ A` 恆為良定義。
- ⚠️ **`B` 絕不得作為移動合法性依據**,實際可移動的目的地永遠只採 `A`。任何以 `B` 判定合法性的實作皆為錯誤,須有對應 AC 防守。
- 單位自身所在格 `origin` 恆屬 `A`,不得被標示為任何一種不可達。
- **效能取捨**:每次刷新需兩趟 Dijkstra。**不得以「合併為單趟、放棄成因區分」作為最佳化手段**——那是拿硬性需求換效能。

**何時用**:任何「不可達有多種成因、且成因會改變玩家解法」的範圍顯示。

**何時不用**:成因對玩家的**解法相同**時不必再細分。`B \ A` 目前刻意合併了「目的格被佔」與「路徑被堵死」兩種子情境,因為兩者的解法都是「先把擋路的單位移開」。**若未來出現解法不同的第三類佔位成因(例如不可推開的中立物件),須回頭重新評估此合併。**

**外觀**:待 art bible。已定案的約束:三態**不得只靠色彩區分**(見 **P-F3**)。

#### P-D2 並存疊加圖(Coexisting Overlays)

| 欄位 | 內容 |
|---|---|
| **類別** | 資料呈現 |
| **來源** | 戰棋 GDD UI Requirements §1a |
| **使用於** | 敵方威脅範圍疊加圖 × 移動範圍疊加圖 |

**描述**:多層資訊疊加圖**必須能同時可見**,不得實作為互斥的模式切換。

**規格**:
- 具體案例:威脅範圍疊加圖與被操作單位自身的移動範圍疊加圖**必須同時可見**。
- **理由**:疊加圖的存在目的是讓玩家「在評估某個候選落點時,**同時**看到該落點是否受威脅」。若必須關掉移動範圍才能看威脅範圍,玩家得靠記憶跨兩個畫面比對,該用途即失效,且回到本專案反覆要防的「事後才知道」模式。
- **職責劃分**:「必須可同時可見」屬需求層,**不下放**;「視覺上如何同時呈現兩層而不互相淹沒」(層次、透明度、圖樣區分)屬 art bible / `/ux-design` 範疇。

**何時用**:兩層資訊需要被**交叉比對**才能支撐一個決策時。

**何時不用**:兩層資訊在語意上互斥、同時顯示會產生矛盾讀法時。那種情況要回頭檢查是不是分層分錯了,而不是改成模式切換。

**外觀**:待 art bible(**這是 art bible 對本模式庫最關鍵的一筆待辦**——兩層疊加而不互相淹沒是純視覺問題)。

#### P-D3 決定性路徑預覽(Deterministic Path Preview)

| 欄位 | 內容 |
|---|---|
| **類別** | 資料呈現 |
| **來源** | 戰棋 GDD UI Requirements §3、Core Rules #7(零隨機承諾) |
| **使用於** | 移動路徑預覽 |

**描述**:多條等成本路徑通往同一可達格時,依**三層決定性 tie-break** 選出唯一路徑:

1. **累積地形成本最低**(公式三既有語意)
2. 平手時,**轉彎次數最少**(轉彎 = 相鄰兩步的行進方向不同)
3. 仍平手時,**依固定方位優先序逐步決定**:`上 > 右 > 下 > 左`

**規格**:
- 第 3 層保證**無殘留平手**:同一棋盤狀態、同一起訖點,選出的路徑恆等且可重現。
- **不得引入任何隨機或與時間/幀序相關的因素。**
- ⚠️ **預覽路徑與移動動畫實際行經路徑必須完全一致。** 預覽走一條、動畫走另一條,與範圍顯示錯誤是同一種背叛。
- 預覽時機:游標停在可達格時**即顯示完整路徑**,不需按鍵展開(見 **P-N1**)。
- 方位優先序 `上 > 右 > 下 > 左` 是**呈現層常數,不是平衡旋鈕**,故不列入 Tuning Knobs;但它是可觀測行為,更動時須同步對應 AC。

**何時用**:任何「系統替玩家在多個等價選項中選一個」的預覽。

**何時不用**:玩家應該自己選路的設計。那時需要的是路徑選擇介面,不是 tie-break 規則。

**外觀**:待 art bible。

#### P-D4 回合層級總覽查詢(Roster Overview Query)

| 欄位 | 內容 |
|---|---|
| **類別** | 資料呈現 |
| **來源** | 戰棋 GDD UI Requirements §1「回合層級的剩餘旗標總覽」、Core Rules #9、AC-22 |
| **使用於** | 戰鬥 HUD(#10,Not Started) |

**描述**:逐格查詢(P-N1)無法有效率回答「我方這回合還有誰沒動完」。因此除了逐格面板外,必須另有**回合層級查詢**:列出我方所有存活單位,依當前狀態分組或標示(皆未用 / 只剩攻擊 / 只剩移動 / 已行動)。

**規格**:
- **不得只顯示二元的「可行動 / 已行動」**——「可行動」是雙旗標複合狀態,只給二元會讓玩家無法規劃回合內的操作順序,而**順序自由正是這個行動經濟模型的核心價值**;讀不出剩餘旗標等於這個自由度不存在。
- 受**即時性 + 單一快照原子性**約束:**總覽顯示期間玩家使用了某單位的旗標時,重繪須反映新狀態**,不得沿用面板開啟時的快照。
- 版面形式(名冊列表、迷你圖示列等)由戰鬥 HUD 決定;本模式只定案**必須有這筆資料可查詢**。

**何時用**:當某個狀態需要跨多個實體被統覽,而逐一查詢在實際操作節奏下不可行時。

**何時不用**:實體數量少到逐格查詢就夠用時。此模式的成本是一個額外的常駐/可切換面板,不是免費的。

**外觀**:待 art bible;版面歸戰鬥 HUD(#10)。⚠️ 戰棋 GDD **OQ-21** 未決:本總覽是常駐 HUD 還是可切換面板。

#### P-D5 結算飄字(Settlement Floating Text)

| 欄位 | 內容 |
|---|---|
| **類別** | 資料呈現 |
| **來源** | 戰棋 GDD UI Requirements §4、Visual/Audio §2 |
| **使用於** | 傷害結算 |

**描述**:結算飄字只顯示**最終傷害總數 + 一個表示修正(`Φ`)介入方向的標記(正/負/無)**,**不重複完整算式**。

**規格**:
- **傷害為 0 時仍須顯示「0」**,並使用**結算語言而非拒絕語言**。「0」代表「打中了但沒造成傷害」,與「這次攻擊被拒絕」是兩件事,**玩家必須能分辨**(拒絕見 **P-F2**)。
- 多單位連續結算時飄字須維持可讀。
- 完整算式屬 **P-M1 確認面板**的領域,飄字不重複。

**何時用**:需要在世界空間即時回報結算結果、且不打斷操作節奏時。

**何時不用**:玩家需要**理解成因**而非只知道結果時——那要用面板,不是飄字。飄字的資訊密度上限很低,塞算式進去只會兩邊都做不好。

**外觀**:待 art bible(字級、動效曲線、多筆並發時的排版策略皆未定)。

### 回饋與模態類(Feedback & Modal)

#### P-F1 未解析態(Pending Re-resolve State)

| 欄位 | 內容 |
|---|---|
| **類別** | 回饋 |
| **來源** | 戰棋 GDD UI Requirements §1;游標 GDD Core Rules #2「下游預覽渲染義務」 |
| **使用於** | 所有讀取游標目標的下游面板 |

**描述**:游標目標的有效性旗標為無效時,面板必須呈現**明確的未解析態**,**不得沿用上一格的殘留內容**。

**規格**:
- 殘留內容是 Player Fantasy 具名失敗模式「**狀態轉換造成的資訊斷裂**」的**直接成因**。
- 未解析態是**一個明確的視覺狀態**,不是「面板變空白」——空白與「這格真的沒東西」無法區分。
- 所有讀取游標目標的下游面板都負有此義務,不只戰棋的格位資訊面板。

**何時用**:任何內容衍生自游標目標的面板。

**何時不用**:目標本來就合法、只是資料為空的情況——那是**空狀態**,不是未解析態。**兩者必須可區分。**

**外觀**:待 art bible。

#### P-F2 可區分的拒絕回饋(Distinguishable Rejection Feedback)

| 欄位 | 內容 |
|---|---|
| **類別** | 回饋 |
| **來源** | 戰棋 GDD UI Requirements §6;游標 GDD Core Rules #3 (iv) |
| **使用於** | 全部確認類操作 |

**描述**:拒絕**絕不靜默**,而且**兩種拒絕在感知上必須可區分**——因為它們的正確補救動作**相反**:

| 拒絕原因 | 查詢方法 | 玩家該做什麼 |
|---|---|---|
| 目標處於待重新解析 | `is_current_target_valid()` | **等待重新解析,或導覽到別的目標** |
| 裝置權威不在滑鼠 | `get_device_authority()` | **移動滑鼠**達門檻取回權威,**而非再點一次** |

**規格**:
- 若回饋無法區分,玩家會嘗試**錯誤**的補救動作。
- 系統層因此把判別資訊拆成**兩個獨立查詢**而非一個合併的「可否確認」布林——**合併會讓呼叫方結構上無法產生可區分的回饋**(ADR-0005 機制十)。
- **拒絕音為硬性要求**(戰棋 Visual/Audio §5)。
- 具體回饋內容由各呼叫方系統決定,游標系統只保證判別資訊可取得。

**何時用**:任何可能被閘門擋下的玩家輸入。

**何時不用**:可以直接讓操作成功的時候。**拒絕回饋做得再好,都不如不需要拒絕。**

**外觀**:待 art bible(兩種拒絕的視覺/聽覺差異如何設計,是本模式對 art bible 的具體待辦)。

---

#### P-F3 非色彩單一通道禁令(No Colour-Only Channel)

| 欄位 | 內容 |
|---|---|
| **類別** | 回饋(全域約束,**無例外**) |
| **來源** | 戰棋 Visual/Audio §6.1;`game-concept.md`;無障礙 Tier **Standard** |
| **使用於** | **全專案** |

**描述**:**本專案定義的任何狀態區分,一律不得只靠顏色作為唯一區分通道。**

**規格**:
- 適用範圍(非窮盡):三態範圍疊加圖(**P-D1**)、游標三態視覺、全域每裝置待機指示、好感度正負連線、預判三態。
- 至少要有第二通道:線型、圖樣、圖示、標籤、位置、動效。
- 這是 Tier Standard「至少一種色盲模式」的**上位要求**——**不是提供色盲模式就免除**,而是**預設呈現本身**就不得依賴色彩。

**何時用**:永遠。

**何時不用**:**無例外**。色彩可以是**其中一個**通道,永遠不能是唯一那個。

**外觀**:待 art bible(第二通道具體採用什麼形式,是 art bible 的核心工作之一)。

#### P-M1 確認面板(Confirmation Panel with Full Breakdown)

| 欄位 | 內容 |
|---|---|
| **類別** | 模態 |
| **來源** | 戰棋 GDD UI Requirements §4、Visual/Audio §2 |
| **使用於** | 攻擊確認 |

**描述**:玩家已選定目標、尚未確認執行時顯示。最小必要欄位:

| 欄位 | 內容 |
|---|---|
| `ATK` | 攻擊方有效攻擊力 |
| `DEF` | 目標有效防禦力 |
| `Φ` | **帶號**的好感度—位置修正 |
| 結果傷害 | `max(0, ATK − DEF + Φ)` |
| 目標剩餘 HP 預估 | 結算後預期 HP |

**規格**:
- `Φ` 的**正負方向與量值須單獨可讀**,不得只呈現合併後的結果數字。
- ⚠️ **`Φ=0` 時仍須顯示該欄位並標示為 0,不得隱藏。** 隱藏會讓玩家無法區分「好感度確實沒有介入」與「這個面板根本沒把好感度算進去」——與 **P-D5** 的「0 傷害不得隱藏」是同一條理由的同構套用。
- 數值欄寬須能容納非預期的大數值而不截斷、不溢位、不改變版面(`Φ` 目前**無上界**,已登記風險;待好感度—位置連鎖系統定案 `Φ_max` 後可收斂)。

**何時用**:不可逆或有代價的操作,且玩家需要理解**成因**而非只知道結果時。

**何時不用**:檢視性操作。確認面板的成本是**打斷節奏**,只有值得的操作才付得起。

**外觀**:待 art bible。⚠️ 戰棋 GDD **OQ-6** 未決:傷害拆解面板的實際排版。

#### P-M2 預判模式(What-if Preview with Lifecycle Separation)

| 欄位 | 內容 |
|---|---|
| **類別** | 模態 |
| **來源** | 戰棋 GDD UI Requirements §5、Visual/Audio §3、Core Rules #8 |
| **使用於** | 攻擊預判 |

**描述**:預判結果**只在游標停留於候選格期間存在**,游標一離開即整體消失,**不寫入任何常駐 HUD 區塊**。

**規格**:
- ⚠️ **預判面板與 P-M1 確認面板不得是同一個 UI 元件,即使欄位完全相同。** 共用元件會讓玩家在快速操作時把「假設」讀成「事實」,支柱一的核心承諾即名存實亡。
- 游標**每次**進入候選格都必須重新呼叫、重新計算,**不得沿用離開前的結果**。**快取顯示結果與快取計算結果同樣違規。**
- 預判三態中的「無效果」與已結算 0 傷害共用同一識別符號,但**兩者必須位於不同 UI 層級**(預判層 vs 結算層)——**符號相同、層級不同**。

**何時用**:玩家需要在承諾前評估後果,而評估本身不應產生任何狀態變更時。

**何時不用**:結果已確定的情況。**預判的價值全在「這還沒發生」**,用它顯示既成事實會摧毀這個區隔。

**外觀**:待 art bible。

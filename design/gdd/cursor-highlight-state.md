## Overview

單一游標/高亮狀態系統維護一份全域唯一的「當前游標目標」狀態——不論是滑鼠懸停、d-pad 移動、或類比搖桿導航,所有輸入裝置最終都寫入同一個狀態源,而所有需要顯示高亮/選取視覺的畫面(棋盤格選取、關係圖迷你地圖、任何具懸停目標的 UI 表面)只讀取這個單一狀態來決定要渲染什麼。它不依賴 Godot 引擎原生的 Control focus/hover 主題渲染機制,因為引擎將滑鼠/觸控懸停視覺(hover)與鍵盤/手把導覽視覺(focus)實作為兩套獨立的主題狀態(2026-08-04 第八輪修訂,回應 godot-specialist 審查發現的事實反轉——第五輪曾將此獨立性的版本歸因判定為「未經查證且可能不準確」並移除,但本輪覆核本專案自有的 `docs/engine-reference/godot/breaking-changes.md`〔4.5→4.6 表〕與 `modules/input.md`/`modules/ui.md`,三份文件皆明確將滑鼠/觸控焦點與鍵盤/手把焦點的分離歸因於 Godot 4.6——第五輪的移除判斷本身才是未經查證的錯誤,已撤銷該次移除、恢復版本歸因,並改為引用本專案自有的已驗證參考文件,不再依賴未具名的審查記憶;無論此行為分離最初於何時引入,本文件的立場僅取決於目前釘選版本〔Godot 4.7.1〕下的實際行為),若讓兩套系統各自驅動視覺,會在玩家切換輸入裝置時產生「兩種高亮同時存在」或「高亮消失」的視覺錯亂。本系統存在的目的,是把「目前選中的是哪一格」這個所有下游玩法邏輯(移動範圍、攻擊射程、好感度連線預覽等)共同依賴的單一事實,收斂成一個不受輸入裝置切換影響的權威來源。

## Player Fantasy

《弈緣》承諾每一步的後果都能事先算清。這個系統守住那個承諾的第一格:玩家在計算之前,必須毫無疑問地知道自己正在計算哪一格。整場對局中,「現在選的是哪裡」永遠只有一個答案,且答案永遠在畫面上——這是支柱一(精準可預判的戰術)的前置條件:可預判性建立在可指認性之上。

失敗不是「高亮顯示錯誤」,而是「玩家開始自我懷疑、多做一次探測性輸入來確認游標在哪」。三種會破壞這份確定性的具體情境,決定了下游章節(Edge Cases、Acceptance Criteria)必須以什麼標準書寫:
- **同時存在兩個高亮,或瞬間沒有高亮**——玩家看到畫面上有矛盾的資訊,或完全找不到目前的焦點。
- **切換裝置後高亮跳到非預期位置**(例如跳回預設格,而非承接前一個裝置留下的位置)——玩家的心智模型在裝置交接的那一刻斷裂。
- **交接延遲可被玩家感知**——即使最終高亮正確,若切換裝置後有明顯延遲,玩家仍會下意識地多操作一次來確認。

其中**滑鼠與手把的交接瞬間是本系統風險最高的單一時刻**——這決定了 Edge Cases 章節必須逐條列出交接情境(手把輸入時滑鼠靜止、滑鼠移出視窗、滑鼠停在無效區域、同幀雙裝置輸入、手把斷線、暫停/彈窗奪取焦點後返回),而 Acceptance Criteria 必須寫成可觀測的不變式(例如「任一幀恰有一個高亮,永不為 0 或 2」「切換裝置後高亮繼承前一裝置的位置,不重置」),不能寫「感覺清楚」這類無法驗證的措辭。**已知缺口(2026-08-07 新增,回應對抗性覆核發現)**:本文件宣稱風險最高的這個交接時刻,目前有一個已用 spike 實測證實成立、尚未修復的缺陷(持續按住方向鍵/搖桿導致滑鼠奪權永久鎖死)——見 Known Confirmed Defects 節。此處明文交叉引用,避免文件自陳的最高風險時刻與其已知失效狀態脫節、被讀者誤判為已妥善處理。

## Detailed Rules

*(2026-08-03,`/design-review` 完整模式已補齊 `godot-specialist` 諮詢。原 Lean mode 標記的兩項 HIGH 風險知識落差——裝置 ID 重新編號、Control offset transforms——已由 godot-specialist 覆核:裝置 ID 重新編號風險已由 Core Rules #3 的 `ui_*` action 判定機制迴避,但該機制實際依賴檢視原始 `InputEvent` 子類別、且要求「無 `ui_*` action 綁定滑鼠按鍵」的前提,兩者原先都未寫明,已於 Core Rules #3 補上;Control offset transforms 對高亮視覺的影響仍待實作階段驗證,見 Open Questions。AC-20 原先涉及的引擎輸入佇列處理順序可重現性疑慮,已於 2026-08-04 第三輪 `/design-review` 審查後,透過改採不依賴引擎行為的固定優先序規則解決,不再是待驗證項目,見 Edge Cases 與 AC-20。)*

### Core Rules

1. **單一狀態源**(2026-08-04 第五輪修訂欄位數,回應 systems-designer、ui-programmer 審查發現——原版本「至少兩個欄位」與 AC-1「僅兩個欄位」自相矛盾,且 Core Rules #3 奪權機制實際需要的累積位移量從未被承認為欄位,本次一併補齊):全域維護一份游標狀態,包含三個頂層欄位——**目前游標目標**(一組「表面類型標籤 + 該表面內的具體目標識別」,例如〔棋盤格,座標〕、〔關係圖迷你地圖節點,節點ID〕、〔卡牌選取區,槽位索引〕——表面類型標籤讓每個具懸停/游標目標的 UI 表面能判斷「目前的全域目標是否屬於自己」,不需各自猜測識別碼型別,**外加一個有效性旗標**,見下方「目標失效與待重新解析」規則——旗標是目標欄位本身內部結構的一部分,不算獨立的頂層欄位)、**目前裝置權威**(標示這個狀態值最後由哪一類輸入裝置寫入,值域為三者之一:**未初始化**、**滑鼠**、**鍵盤/手把**,對應下方 States and Transitions 的三個狀態)、**滑鼠奪權累積位移量**(見 Core Rules #3「滑鼠奪回權威的空間門檻」的完整狀態模型定義,僅在裝置權威為鍵盤/手把期間有意義的暫態純量;此欄位為本文件明文承認、非隱藏的頂層欄位,見 AC-1 修訂)。所有需要顯示高亮/選取視覺的畫面只讀這份狀態,不各自維護獨立的高亮邏輯。
2. **寫入規則**:滑鼠懸停/移動與 d-pad/類比搖桿導航,兩者都寫入同一個狀態源(而非各自維護獨立狀態再於渲染層合併判斷顯示哪一個)。任何具懸停/游標目標的 UI 表面(棋盤格、關係圖迷你地圖、其他需要選取視覺的介面)皆透過同一套寫入介面更新狀態,不得繞過本系統直接操作各自的高亮視覺。**寫入介面的資料需求(2026-08-04 第五輪新增,回應 ui-programmer 審查發現的幾何來源缺口;2026-08-04 第六輪修訂為純拉模型,回應 ui-programmer 審查發現的推/拉雙模型自相矛盾——原版本同時要求寫入介面提供幾何、又在 Core Rules #3 宣稱每幀即時查詢,兩者互斥且未裁定何者為準)**:「設定新目標」方法需要呼叫方提供兩項資料——目標識別(含 Core Rules #1 所述的表面類型標籤)、此次寫入是否由裝置 `ui_*` action 觸發(用於判定是否連動裝置權威轉移,見下方「系統主動改標與裝置權威的關係」)。**命中框幾何不屬於寫入介面的資料需求(2026-08-05 第九輪註記——本節「純拉模型」原本解決的是「寫入介面該不該附帶幾何」的推/拉矛盾,但 Core Rules #3 已改為錨定表面類型的固定像素常數,不再存在任何形式的命中框幾何查詢,本節論證的前提已不成立,保留文字僅供沿革參照,不代表本系統仍有幾何查詢機制)**:目標識別中的表面類型標籤(見 Core Rules #1)即為 Core Rules #3 空間門檻查表的鍵值,足以取得該表面類型的固定門檻常數,不需要任何額外的幾何資料或每幀查詢。
   - **目標失效與待重新解析(2026-08-04 新增,回應 game-designer、systems-designer 審查發現的獨立收斂——原版本將失效目標完全交給呼叫方決定「畫面上要顯示什麼」,若呼叫方未介入,高亮會無限期停在空格/屍體格上,違反 Player Fantasy 明訂的「兩個高亮同時存在或畫面顯示矛盾資訊」失敗情境的精神)**:本系統的寫入介面除了「設定新目標」外,額外提供第二個方法——**「標記目前目標為待重新解析」**。此方法不清空目前游標目標的座標值,只將其有效性旗標(見 Core Rules #1)由有效翻轉為無效。任一具游標目標的 UI 表面讀到有效性旗標為無效時,**必須**統一以本系統定義的「待重新解析」視覺呈現(具體樣式留待 `/art-bible`,但呈現本身的存在是硬性行為要求,比照 Visual/Audio Requirements 的待機指示規則),不得沿用原本的一般高亮樣式、也不得各自決定是否要有區別。呼叫方(例如戰棋移動與交戰系統偵測到目標單位死亡/移動)須主動呼叫此方法通知本系統;若呼叫方完全不介入,本系統無法自行偵測目標是否失效(本系統不理解遊戲實體語意,只持有座標),現況維持不變——這個邊界仍然存在且合理,但呼叫方一旦呼叫此方法後,視覺呈現的一致性由本系統統一保證,不再是呼叫方的責任。呼叫方之後呼叫「設定新目標」介面時,有效性旗標自動翻回有效,待重新解析視覺自動解除。
   - **下游預覽渲染義務(2026-08-05 第十輪新增,回應帳本 L1 連續四輪未處置達自動升級門檻、game-designer、ux-designer、ui-programmer 三方獨立收斂發現)**:本節前段的義務範圍原本僅涵蓋兩件事——目標高亮視覺呈現「待重新解析」樣式、呼叫方拒絕確認/選定操作生效於此目標(見下方「確認鍵行為」)。但有效性旗標為無效期間,目前游標目標的**座標值本身刻意不被清空**(見上方),而這個座標值除了驅動高亮與確認攔截外,還被至少兩類下游消費者讀取以計算**玩家可見的戰術/敘事預覽**——移動範圍與攻擊射程預覽(戰棋移動與交戰系統)、好感度連線與關係圖預覽(好感度視覺呈現 UI)。這兩類預覽此前完全不受本節義務約束,若照常渲染,會對一個系統自己已標記為「有疑問」的目標,同時顯示一份精確、自信的計算結果——直接重現 Player Fantasy 明訂的第一號失敗情境(「玩家看到畫面上有矛盾的資訊」),且發生在支柱一(精準可預判)最核心的承諾位置。**本文件明文擴大本節義務範圍**:任何下游系統若讀取目前游標目標的座標值以渲染**任何形式的玩家可見預覽**(不限於已知的移動範圍/攻擊射程/好感度連線,泛指未來新增的同類消費者),**必須**先查詢有效性旗標;旗標為無效期間,該預覽**必須**被抑制(不渲染)或以明確的「不確定」佔位樣式呈現,不得渲染成與旗標有效時相同的確信樣式。具體的抑制/佔位視覺留待各下游系統的 GDD 與 `/art-bible` 決定,但「不得對已標記無效的目標渲染確信預覽」本身是本文件對下游的硬性契約,已登記至 Dependencies 章節與 `systems-index.md` Cross-System Obligations Registry(見下方新增 AC-50)。
   - **呼叫參數與競態防呆(2026-08-04 第八輪新增,回應 ui-programmer 審查發現的競態條件——原版本此方法無條件作用於「系統當下持有的目標」,若呼叫方的失效偵測與玩家自己同時期的正常導覽操作(見下方「玩家導覽自動解析」)發生時間差,呼叫方原本想標記的舊目標可能已被玩家導覽替換為另一個完全有效的新目標,若方法仍無條件套用,會誤將玩家剛選中的合法目標標記為待重新解析,依 Core Rules #2「確認鍵行為」阻擋玩家對該合法目標的確認輸入,直到玩家再次導覽離開又返回才能解除——這是玩家可實際感知、可重現的功能性缺陷,命中 Player Fantasy 明訂的最高風險失敗情境之一)**:「標記目前目標為待重新解析」方法**必須**要求呼叫方一併傳入其認知的目標識別(與「設定新目標」介面要求的目標識別格式相同,見上方「寫入介面的資料需求」)。本系統於執行前比對:若傳入的目標識別與系統當下實際持有的目前游標目標**相符**,才執行有效性旗標翻轉;若**不相符**(代表目前目標已在偵測與呼叫之間的時間差內被替換),本次呼叫視為過期,系統**回傳明確的「已過期,未套用」結果**、不執行任何旗標翻轉,目前有效目標與其有效性旗標維持不變——不因過期的標記呼叫而誤傷玩家當下正持有的合法目標。
     **回傳值與呼叫方重驗義務(2026-08-06 局部修訂,非重開對抗性審查,回應 `/review-all-gdds` Scenario Walkthrough 發現的真實失效路徑,使用者裁決——原版本「靜默忽略、不產生任何效果」字面上包含「不回傳任何結果」,呼叫方無從得知自己的標記請求被丟棄。具體失效場景:單位 A 死亡的同一影格,玩家已導覽離開 A、目標變為 B,呼叫方(例如戰棋移動與交戰系統)偵測到 A 死亡後呼叫本方法標記 A,因目標不符而過期被丟棄——若玩家隨後導覽**回到** A 格,依「玩家導覽自動解析」規則,A 會被判定為合法有效目標,因為 A 死亡這件事從未成功傳達給本系統,重演本系統本要防止的矛盾資訊失敗情境)**:本方法的回傳值為**結構化結果**,至少區分兩種:「已套用」(旗標翻轉成功)與「已過期,未套用」(目標不符,本次呼叫未產生效果)。**呼叫方收到「已過期,未套用」時,不得視為「該目標已被妥善處理」而放棄**——呼叫方須自行判斷該目標(本情境中的 A)是否仍具備原本觸發標記的遊戲語意條件(例如 A 是否仍是死亡狀態):若玩家日後再次將游標導覽至該目標,呼叫方須能重新偵測並重新呼叫本方法(此時目標識別已相符,標記會成功套用),或呼叫方自行在確認/選定邏輯的前置檢查中,獨立於本系統的有效性旗標之外,額外核對該目標的遊戲語意是否仍然合法——兩者擇一即可,但至少須有一者存在,不得假設「呼叫過一次就等於問題已解決」。此義務已登記至 Dependencies 與 `systems-index.md` Cross-System Obligations Registry。
   - **玩家導覽自動解析(2026-08-04 新增,回應 ux-designer 審查發現的無限期停滯風險)**:有效性旗標為無效期間,若玩家透過任一裝置產生一個帶有新座標目標的有效 `ui_*` action(例如移動到別格、或切換到其他 UI 表面的目標),此動作等同呼叫方呼叫「設定新目標」介面——因為所有裝置的寫入皆透過同一套介面更新同一個狀態物件(見 Core Rules #1、#2 開頭),玩家自己的正常導覽操作本就會呼叫這套介面,不需要呼叫方額外介入即可自然翻回有效、解除待重新解析視覺。這不代表呼叫方的偵測與標記義務因此消失(呼叫方仍須主動標記失效,見上方),只是說明「呼叫方完全不介入」與「玩家完全不操作」兩個條件同時成立,才會持續停滯——只要其中一個條件被打破,狀態就會解除。
   - **確認鍵行為(2026-08-04 新增,同上回應)**:有效性旗標為無效期間,呼叫方系統(例如戰棋移動與交戰系統)**必須**將該游標目標視為無合法目標,拒絕任何確認/選定類操作以該目標為對象生效,直到有效性旗標翻回有效為止——具體確認輸入的攔截路徑屬於呼叫方系統自己的輸入處理範圍,不受本系統管轄,但呼叫方必須查詢本系統的有效性旗標作為攔截依據,不得忽略此旗標、逕自對失效目標的舊座標值執行確認動作。

     **累積量重置與視覺平滑的關係,含收斂上限(2026-08-05 第九輪新增收斂上限,第十輪重寫涵蓋範圍與下限約束——原規則〔第九輪〕只涵蓋觸發點 (a)(d)(e)〔舊編號〕,靜默排除觸發點 (b),qa-lead 於第十輪指出這是與本規則存在目的相同的「呈現值說謊」風險換一個未覆蓋的觸發點重新發生;`reclaim_visual_convergence_max_frames` 本身亦僅有上限約束、無下限約束,systems-designer 指出配置為 0 時「於 0 影格內收斂」定義上即為單影格瞬間歸零,與本規則「不得瞬間跳變」的要求自我矛盾)**:`reclaim_progress` 本身仍必須立即反映**上方全部四個重置觸發點 (a)(b)(c)(d) 之任一**造成的重置(通常為 0),不因呈現層考量而延遲判定,不限定特定子集——這確保未來若重置觸發點清單再有變動,呈現層義務的範圍表述本身(「全部觸發點」而非枚舉字母子集)不需要跟著重新核對;驅動漸進回饋透明度的呈現層,已顯示的透明度不得因這類非玩家滑鼠動作直接造成的重置而單影格內瞬間歸零,但**呈現值必須於新增 Tuning Knob `reclaim_visual_convergence_max_frames`(見 Tuning Knobs)所定的影格數上限內,收斂至與當下 `reclaim_progress` 相差不超過可感知門檻的數值**——「維持」不再是可無限期持續的合法終態,只是收斂過程中允許的暫態手段之一,不得成為最終停留狀態。**`reclaim_visual_convergence_max_frames` 必須嚴格大於 0(2026-08-05 第十輪新增硬性約束,回應 systems-designer 審查發現)**:配置為 0 時,「於 0 影格內收斂」即為單一影格內的瞬間歸零,直接違反本規則前段「不得瞬間跳變」的要求——與 `mouse_reclaim_threshold_px_by_surface_type` 已有的 `>0` 約束同位階,見 AC-46b。具體漸退曲線與時長留待 `/create-architecture`/`/art-bible` 定案,但收斂上限本身與其下限約束皆為硬性行為要求,見 AC-41。

     **觸發點 (d) 的收斂例外——允許單影格瞬間歸零(2026-08-06 第十一輪新增,回應 ux-designer 審查發現、使用者裁決)**:上述「不得瞬間跳變、須於收斂上限內漸退」的規則,**明文排除觸發點 (d)**(同影格內滑鼠已達門檻但被否決)。理由:觸發點 (d) 是四個重置觸發點中唯一「重置發生當下 `reclaim_progress` 恰為或極接近 1.0」的情況——(a)(b)(c) 重置時的進度值通常任意或為 0,套用漸退收斂是為了避免無意義的視覺抖動;但觸發點 (d) 的重置時機,玩家剛被展示「即將完成」甚至「已完成」的視覺承諾,此刻若仍讓透明度緩慢收斂,呈現層會在收斂窗口內持續顯示一個與底層判定值(已歸零)不符的高透明度讀數——這正是本規則存在的目的(避免呈現值說謊)要防止的事,套用在觸發點 (d) 上卻反而製造了它。**因此觸發點 (d) 發生時,漸進回饋視覺元素的透明度須於觸發的同一影格內立即歸零,不適用收斂上限、不維持前一影格數值、不漸退**——這是「不得瞬間跳變」規則的唯一例外,理由僅限於此觸發點的進度值分布特性,不代表本規則對其餘三個觸發點的態度有任何鬆動。見新增 AC-41b。
     **規則(2026-08-05 第九輪修訂,錨定對象改變後的文字同步)**:鍵盤/手把持有權威時,滑鼠須累積淨位移達目前高亮目標所屬**表面類型**的 `reclaim_threshold_px`(見 Tuning Knobs `mouse_reclaim_threshold_px_by_surface_type`)以上,才視為產生有效的奪權 `ui_*` action;未達此距離的滑鼠移動,即使落在合法游標目標區域內,也不觸發權威轉移。**此門檻是每個表面類型各自的固定像素常數,不是任何目標的相對百分比**——棋盤格與任何非格狀 UI 表面(關係圖迷你地圖節點、卡牌選取區等,見 Core Rules #7)依其表面類型各自查表,不需要換算比例,也不需要對個別目標做幾何查詢。**此門檻是空間門檻,不是時間防抖**——不引入任何延遲,判定仍然是每一幀即時比對移動距離是否達標。
     **漸進回饋**(硬性行為要求,2026-08-04 第五輪修訂為結果導向措辭,回應 systems-designer、godot-specialist 審查發現——原版本明文指定「原生滑鼠指標圖案」的透明度漸變,但原生 OS/引擎游標通常不支援逐幀連續透明度動畫,這是尚待 `/create-architecture` 驗證的引擎能力假設,不應寫死在行為規格層級,見 Open Questions 新增項):單純不給予任何回饋直到跨過門檻,會讓玩家無法區分「我的輸入太小」與「遊戲沒有回應」,直接重現 Player Fantasy 明訂的失敗情境。因此,鍵盤/手把持有權威期間,一旦偵測到滑鼠產生任何非零淨位移(不論是否已達門檻),**必須**有一個可觀察的視覺元素(原生滑鼠指標圖案,或改用下游自行繪製的替代游標圖形——具體載體留待 `/create-architecture` 的 ADR 決定)以與移動進度(目前累積淨位移 ÷ 門檻距離,見 Formulas)成正比的透明度漸進顯示——0% 進度時完全不可見,達到門檻的當下透明度達 100%、同時完成權威轉移;滑鼠移動停止或朝門檻方向的累積進度沒有持續增加時,已顯示的透明度不得瞬間跳變(可維持或依實作漸退)。具體緩動曲線、透明度衰減速率、呈現載體等細節留待 `/art-bible` 與 `/create-architecture` 決定,但「移動進度必須有連續、可感知的視覺回饋」本身是本文件對下游的硬性行為要求,比照 Visual/Audio Requirements 既有待機指示規則的約束層級。**此規則是 Core Rules #5「失去權威裝置的視覺抑制」在滑鼠嘗試奪權期間的例外**——該情境下指標的抑制不是二元的「完全隱藏或完全顯示」,而是連續透明度漸變,直到門檻觸發前都尚未真正取得權威。

     **載體形狀約束(2026-08-04 第六輪新增,回應 game-designer 審查發現、creative-director 裁決——漸進回饋期間,畫面上同時存在一個全不透明的鍵盤/手把高亮與一個逐漸顯現的滑鼠指標,觀感上有被誤讀為「兩個目標高亮同時存在」的風險,牴觸 Player Fantasy 明訂的最高風險失敗情境)**:此漸進回饋視覺元素,不論其載體是原生滑鼠指標或下游自繪的替代圖形,**不得**呈現為與本系統定義的「目標高亮」相同或相似的視覺形狀(例如格子外框、目標框選標記等會被玩家讀成「這是被選中的目標」的形式)——必須是明確可與高亮區分的進度/意圖指示形式(例如箭頭、量規、軌跡光點等指向性或量化性圖形,而非包覆目標的框選形式)。具體圖形設計留待 `/art-bible` 決定,但「不得與高亮同形狀」本身是本文件對下游的硬性限制——即使系統邏輯上尚未完成權威轉移,玩家仍可能把兩個同形狀的視覺元素在感官層面讀成「兩個高亮同時存在」,而這正是 Player Fantasy 定義的最高風險失敗情境,載體形狀的區分是消除這個感官混淆的必要條件,不是錦上添花。

     **反方向(鍵盤/手把從滑鼠手中奪權)——僅限導覽類動作**(2026-08-04 第七輪修訂縮小範圍,回應 game-designer 審查發現、creative-director 裁決——原版本對「任一」`ui_*` 動作一律零門檻立即奪權,但此假設從未被檢驗:手把靜置於玩家腿上時遭誤觸的風險,與滑鼠在桌面上被碰到的風險屬同一類物理現象,不因裝置種類不同而消失,而原版本僅對滑鼠方向建立防抖用的空間門檻,鍵盤/手把方向卻毫無對稱防護,使本專案定義的主要輸入裝置〔鍵盤/滑鼠,見 `technical-preferences.md`〕結構性地承擔次要裝置雜訊的全部代價):不受上述空間門檻與漸進回饋規則限制、立即生效的零門檻豁免,**其範圍限縮為導覽類 `ui_*` action**——即由方向鍵/d-pad(`InputEventKey`、`InputEventJoypadButton` 觸發的方向性動作,例如 `ui_up`/`ui_down`/`ui_left`/`ui_right`)或類比搖桿位移(`InputEventJoypadMotion`)觸發、語意上代表「移動游標」的動作。**確認類或其他非導覽類 `ui_*` action(例如 `ui_accept`、`ui_cancel`)不適用本豁免,不論其底層觸發事件為 `InputEventKey` 或 `InputEventJoypadButton`,一律不轉移裝置權威**——見下方「確認類動作與裝置權威的關係」。**豁免成立的前提約束**:本豁免假設 Input Map 為每個由類比搖桿軸觸發的導覽類 `ui_*` action 綁定,已設定足以濾除搖桿飄移(drift,例如電位器老化、死區校準不當)的死區(deadzone)——`ui_*` action 本身只有在搖桿軸值跨越該死區後才會觸發,飄移訊號若未跨越死區,根本不會產生本系統需要判定的 `ui_*` action。本系統**不**在此之上疊加額外的門檻或防抖機制(比照本節前段「滑鼠奪權前提約束」的既有處理方式,同一套「機制成立與否依賴前提被遵守,而非本系統自動保證」的模式)——死區設定是否足以應對實際硬體老化情境,屬於 Input Map 設定與 `/create-architecture` 階段的驗證範圍,不屬於本系統規則本身的正確性範圍,已於 Open Questions 登記待驗證。此豁免的其餘理由不變:導覽類離散按鍵/搖桿位移是玩家針對游標移動的主動操作,不存在「手不小心碰到」的等效風險,鍵盤/手把也沒有可見的「移動中」游標概念需要漸進回饋。

     **確認類動作與裝置權威的關係**(2026-08-04 第七輪新增,回應 game-designer 審查發現、creative-director 裁決——縮小反方向豁免範圍後的配套規則,取代原本「確認鍵可零門檻奪權」的行為):滑鼠持有權威期間,若鍵盤或手把產生一個確認類或其他非導覽類 `ui_*` action(例如確認鍵/取消鍵),**裝置權威維持滑鼠不變,不因此次動作而轉移**——該動作本身仍正常派發給任何監聽該 `ui_*` action 的下游系統(例如戰棋移動與交戰系統的確認/選定邏輯),下游系統依 Core Rules #2「確認鍵行為」與本系統的有效性旗標查詢介面決定是否接受,「該次輸入不改變本系統的裝置權威欄位」這件事本身由本系統保證,不屬於下游系統的職責。此規則同時消除原設計的一個隱性風險:原版本下,確認鍵即使未改變游標目標也會零門檻奪權,玩家可能在毫無預期的情況下發現裝置權威已易主(原 AC-35 情境,見 Acceptance Criteria 群組 F 的改寫說明,**2026-08-06 第十一輪修正死連結——AC-35 實際位於群組 F「Additional Coverage」,原引用「群組 B」有誤,回應 qa-lead 審查發現**)。

     **本規則與 Edge Cases「同一影格雙裝置」固定優先序母規則的範圍關係(2026-08-05 第九輪新增,回應 systems-designer 審查發現的真矛盾——原版本下,「滑鼠持權威、同影格鍵盤/手把產生確認類動作」這組輸入,本規則斷言權威維持滑鼠,而 Edge Cases 母規則〔第八輪已明文擴大範圍為不限動作類別〕斷言鍵盤/手把恆勝,兩條規則字面上給出相反判定,且各有對應 AC(本規則對應原 AC-35,母規則對應 AC-20)。此非排序未定義,是真矛盾。第七、八輪只檢查了「鍵盤/手把已持權威、滑鼠奪權被否決」方向,鏡像方向〔滑鼠已持權威〕從未被檢查。使用者第七輪裁決〔確認類動作不轉移權威〕已回答此題,本輪不重啟裁決,只修正母規則的適用範圍使其與既有裁決一致)**:確認類或其他非導覽類 `ui_*` action **本身不具備主張裝置權威的資格**——它不是 Edge Cases 母規則所仲裁的「兩個互相競爭的權威主張」之一,而是**始終被排除在裝置權威仲裁之外的一類事件**,不論當下權威在何方、也不論同影格是否有另一裝置的其他事件。Edge Cases 母規則因此明文限縮適用範圍為:**僅在雙方於同影格內產生的事件皆具備主張裝置權威的資格時,才適用鍵盤/手把恆勝的固定優先序**——具備資格的事件僅兩類:鍵盤/手把的導覽類動作(見上方「反方向」)、滑鼠達到 `reclaim_threshold_px` 的位移。確認類動作既不主張權威,也不與另一方主張權威的事件產生衝突,因此「滑鼠持權威 + 同影格鍵盤/手把確認類動作」根本不落入母規則的仲裁範圍,母規則不適用於此情境,本規則(裝置權威維持滑鼠不變)是唯一適用的規則,兩條規則因此不再互相矛盾。**母規則理由文字的同步修正**:Edge Cases 母規則原本的論證文字(「玩家會感受到自己剛按下的方向鍵/確認鍵沒有反應」)字面上曾涵蓋確認鍵,與本次範圍限縮的結論相反,已於 Edge Cases 一併改寫,不留下會被誤讀為支持相反結論的殘留文字。

     **同一裝置類別內多個 `ui_*` 動作同影格並存的優先序(2026-08-05 第九輪新增,回應 ui-programmer 審查發現的相鄰缺口——若不與本次修法一併處理,母規則修正後仍會在「同一裝置、同影格兩個動作」這一列舉維度上留下對稱的未定義缺口,重演本文件的招牌失敗模式:規則 A 在時間點 T 寫下一份列舉,T+n 新增了一個成員,T 的列舉沒有回頭同步)**:若同一影格內,鍵盤/手把產生**兩個** `ui_*` 動作(例如自動重複的導覽動作與一個確認動作同時抵達緩衝區),依 Edge Cases「實作架構約束」緩衝後統一裁定時,**導覽類動作先套用其目標變更,確認類動作再讀取套用後的最新目標**——即同影格內,寫入類事件(改變游標目標)先於讀取類事件(確認/選定操作讀取目前目標)生效。此順序與 Core Rules #2「玩家導覽自動解析」的既有精神一致(玩家的導覽操作優先反映在目標值上),避免確認動作誤讀到本影格已經過期的舊目標。

     **滑鼠點擊確認與裝置權威的關係(2026-08-04 第八輪新增,回應 game-designer 審查發現、使用者裁決——原版本從未規定鍵盤/手把持有權威、原生滑鼠指標依 Core Rules #5 被隱藏期間,玩家的滑鼠點擊該如何處理;Core Rules #3「前提約束」禁止把語意上屬於確認的 `ui_*` action〔例如 `ui_accept`〕綁定滑鼠按鍵,代表點擊確認若要支援滑鼠,必須由呼叫方系統直接處理原始 `InputEventMouseButton`,繞過本系統的 `ui_*` 判定機制——但繞過判定機制不代表繞過裝置權威本身,這個缺口若不填補,玩家可能在鍵盤/手把持有權威、指標不可見時點擊畫面上與目前高亮任意分離的座標,卻不確定該次點擊會發生什麼)**:呼叫方系統若直接處理原始滑鼠點擊事件作為確認/選定操作的觸發來源(不透過本系統的 `ui_*` 判定),**必須**先查詢本系統目前的裝置權威欄位——**若裝置權威此刻不是滑鼠,呼叫方必須拒絕/忽略該次點擊,不得使其生效**,不論點擊發生的螢幕座標是否恰好落在目前權威高亮的目標上,也不得將該次點擊解讀為確認動作或計入 Core Rules #3 空間門檻的奪權判定。唯有裝置權威已經是滑鼠時,滑鼠點擊才可能被呼叫方系統採納為確認操作,此時屬於呼叫方一般輸入處理的範圍,不特別涉及本系統。此義務的分工比照 Core Rules #2「確認鍵行為」的既有模式:本系統只負責正確回傳裝置權威欄位的查詢結果,查詢結果是否被遵守屬於呼叫方系統自己的驗收範圍,已登記至 Dependencies 章節。

     **拒絕生效須伴隨主動回饋,且範圍明文涵蓋未初始化狀態(2026-08-05 第九輪修訂,回應 game-designer B1 與 ux-designer 兩方獨立收斂發現,creative-director 綜合裁決加重——第六輪已對「有效性旗標無效期間拒絕確認」建立「必須提供主動可感知回饋,不得靜默拒絕」的呼叫方義務,但第八輪新增的本規則完全沒有繼承這條回饋要求,AC-38 甚至主動要求靜默。原生指標依 Core Rules #5 被隱藏,玩家連視覺錨點都沒有,而「點一下看看」往往是玩家第一次嘗試換裝置的動作,是 Player Fantasy 明訂的最高風險時刻。creative-director 進一步發現:本規則的觸發條件「裝置權威此刻不是滑鼠」字面上包含「未初始化」狀態——意味著一位純滑鼠玩家開啟需要游標的畫面、系統處於未初始化、玩家不移動滑鼠直接點擊〔滑鼠通常已停在他想點的位置,是常見操作〕,該次點擊依本規則會被拒絕;而未初始化狀態下原生指標是否可見,全文從未定義,這是玩家整場遊戲第一次輸入就可能靜默失效、且連指標是否存在都不確定的情境)**:(i) 本規則的拒絕生效,**必須**比照 Core Rules #2「確認鍵行為」既有的呼叫方義務(見 Dependencies),伴隨某種主動、可感知的回饋(音效、震動、畫面搖晃,或其他呼叫方選擇的呈現手段),不得靜默拒絕——具體回饋形式由呼叫方系統與 `/art-bible`/`/sound-designer` 決定,回饋**內容**是否需要具體指出補救方式(例如提示「先移動滑鼠再點擊」)不在本輪定案,併入 Open Questions 已登記的「滑鼠奪權機制教學掛鉤」義務,由教學/上手引導系統統一處理,避免逐次點擊都彈出提示變成噪音;若採用畫面搖晃等具方向性/劇烈度的視覺回饋手段,須遵循前庭無障礙的一般性設計原則(避免高頻重複觸發時造成不適),具體門檻與是否需要 reduce-motion 選項留待 `/art-bible`/`design/ux/accessibility-requirements.md` 決定,不在本文件定案;(ii) 本規則明文涵蓋**未初始化狀態**——系統處於未初始化時,裝置權威不屬於任何裝置(見 Core Rules #1 值域),依本規則的判斷邏輯「裝置權威此刻不是滑鼠」為真,滑鼠點擊同樣須被拒絕/忽略,並比照上述 (i) 提供主動回饋;(iii) **未初始化狀態下原生滑鼠指標的可見性**:比照 Core Rules #5「原生滑鼠指標的涵蓋範圍」對鍵盤/手把權威期間的既有立場,未初始化狀態下原生指標**同樣預設隱藏**,直到滑鼠產生第一個有效 `ui_*` action(見 AC-16)為止——這確保未初始化狀態下的滑鼠行為(指標隱藏、點擊被拒絕但有回饋)與鍵盤/手把權威期間完全一致,不需要下游系統為「未初始化」另外處理第三套邏輯;(iv) **拒絕原因須可感知區分(2026-08-05 第十輪新增,回應 ux-designer 審查發現)**:滑鼠點擊可能因兩種語意不同的原因被拒絕——裝置權威此刻不是滑鼠(本規則,涵蓋鍵盤/手把持有權威與未初始化兩種情境),或裝置權威已是滑鼠但目前目標的有效性旗標為無效(Core Rules #2「確認鍵行為」)——這兩種拒絕原因所對應的正確補救動作彼此相反(前者:玩家須先以滑鼠**移動**達到奪權門檻;後者:玩家須**等待**呼叫方系統解析或自行導覽離開該目標)。**本規則明文要求:兩種拒絕原因觸發的主動回饋,必須在感知上可區分**,不得使用完全相同的回饋(例如同一種音效/同一種震動模式)覆蓋兩種情境——若回饋無法區分,玩家會在兩種情境下嘗試同一種(可能錯誤的)補救動作,直接重現本文件宣稱要消除的自我懷疑失敗情境。具體區分手段(音效音色、震動強度/節奏、畫面搖晃方向等)留待 `/art-bible`/`/sound-designer` 決定,回饋內容是否指出具體補救方式仍依 (i) 併入教學系統義務,本條只要求「可區分」本身,不要求「內容解釋原因」。
4. **裝置交接繼承規則**:裝置權威切換時,新裝置**繼承**舊裝置留下的游標目標值,不重置到任何預設位置——呼應 Player Fantasy「玩家從不需要重新尋找自己的位置」。
   - **未初始化邊界的延伸(2026-08-03,systems-designer 審查補上)**:若系統目前處於**未初始化**狀態,任一裝置產生的第一個 `ui_*` action 同樣視為觸發本繼承規則——「舊裝置留下的值」在此情境下即為 Core Rules #6 由呼叫方設定的初始目標。此延伸對兩類裝置的實際效果不同:對**鍵盤/手把**(相對定位裝置)而言,繼承值是後續相對移動的實際起點,具有可觀察意義;對**滑鼠**(絕對定位裝置)而言,其第一個有效 `ui_*` action 本身自帶螢幕座標推導出的目標位置,繼承值會在同一次輸入中立即被覆蓋,不產生可觀察效果——但這不代表規則對滑鼠不適用,只是滑鼠情境下的繼承是暫態的,兩者皆不違反本規則。
   - **一般化至所有交接情境,並與 AC-10 對齊(2026-08-04,`/design-review` 完整模式審查後補上——原版本此邏輯僅寫在「未初始化邊界的延伸」條目中,但推理本身不限於未初始化情境,導致本規則與 AC-10 原本的無條件敘述互相矛盾,由 game-designer 審查發現)**:上述「鍵盤/手把繼承值具可觀察意義、滑鼠繼承值為暫態」的區分,適用於**任何**裝置交接情境,不限於從未初始化狀態交接。具體而言——**B(新裝置)= 鍵盤/手把**時:繼承規則具有可觀察意義,交接觸發影格結束時的游標目標值等於 A 最後寫入的值(見 AC-10)。**B = 滑鼠**時:滑鼠取得權威的同一個 `ui_*` action 本身即帶有螢幕座標推導出的目標位置,繼承值在同一次輸入中立即被覆蓋——交接觸發影格結束時的游標目標值等於滑鼠當下懸停目標,而非 A 最後寫入的值(見 AC-10b)。
5. **失去權威裝置的視覺抑制**:未持有目前權威的裝置,即使其底層仍持續產生游標移動訊號(例如滑鼠 hover 天生一直在更新引擎原生的滑鼠位置),其對應的高亮視覺**必須被主動抑制**,不得顯示——確保任一時刻畫面上只有一個高亮來源。
   - **原生滑鼠指標的涵蓋範圍(2026-08-03,game-designer 審查補上)**:「高亮視覺」的抑制範圍明文包含**系統原生滑鼠游標圖案**(作業系統或引擎繪製的箭頭/指標圖案),不僅限於本系統渲染的格子高亮框。鍵盤/手把持有權威期間,若螢幕上仍可見一個移動中的滑鼠箭頭停在另一格,即構成 Player Fantasy 明訂的「同時存在矛盾資訊」失敗情境,不因該箭頭是引擎原生元件而豁免於本規則。具體隱藏機制(例如 Godot 的滑鼠模式切換)留待 ADR,但「鍵盤/手把持有權威時,原生滑鼠指標圖案必須被隱藏」本身是行為規格,不留給下游決定。
   - **與滑鼠奪權漸進回饋的交互例外(2026-08-04 新增)**:上述「必須被隱藏」是滑鼠靜止或移動進度為零時的預設狀態。一旦滑鼠開始朝奪權門檻累積移動,依 Core Rules #3「滑鼠奪回權威的空間門檻與漸進回饋」規則,指標的抑制不再是二元的隱藏/顯示,而是依移動進度連續變化透明度——這不是對本條規則的違反,是本條規則明文登記的例外情境,兩者共同構成完整的抑制規格。
6. **初始狀態**:進入戰鬥/需要游標的畫面時,若尚無任何裝置產生過 `ui_*` action(例如純手把玩家的第一次互動前),初始游標目標落在**玩家可操作單位所在的格**;若場上有多個可操作單位,初始落點規則由呼叫方(戰棋移動與交戰系統)決定並告知本系統,本系統只保證有一個明確的初始值可用,不自行判斷「哪個單位」。
7. **應用範圍一般化(2026-08-03,範圍界定修訂——見 Open Questions 與 Cross-System Obligations Registry)**:本系統的狀態源與規則不限於棋盤格選取,任何具懸停/游標目標的 UI 表面(關係圖迷你地圖、卡牌選取等)皆使用同一套介面決定**目前 hover/游標目標**——不得每個下游系統各自重新實作一套裝置權威判定邏輯。

   **管轄範圍判準:以共用列舉登記為唯一判準,不以「是否有下游消費者」判斷(2026-08-11 第六輪新增,回應對抗性覆核發現 F2-1——AC-23 斷言暫停選單操作不竄改游標狀態,與本規則「任何具懸停/游標目標的表面」字面上矛盾,因為本規則的例舉清單從未明文排除暫停選單)**:本規則的管轄範圍,**以該表面是否已在 Core Rules #7「表面類型標籤的型別契約」定義的共用列舉中登記為表面類型成員為唯一判準**——已登記者受本規則全部管轄,不得繞過本系統直接操作自己的高亮視覺;**未登記者不落入本規則管轄範圍**,得直接使用 Godot 4.6+ 引擎原生的 Control focus/hover 雙軌機制(見 Overview 對此機制的既有查證),不需要透過本系統的裝置權威判定介面。**任何下游系統不得讀取未登記表面的懸停/游標目標作為本系統的游標目標**——若日後某未登記表面確實需要被下游讀取,必須先在共用列舉登記為正式成員,並就此變更走一輪 `/design-review`,不得以「反正它已經被讀取了」的既成事實直接進入管轄。**此判準刻意不採用「該表面的目標值是否會被至少一個下游系統讀取以驅動玩法預覽」這種消費者導向的判斷方式**——後者會讓管轄範圍隨未來下游系統的設計選擇悄悄改變,而不需要本文件任何版本異動,重演本文件反覆出現的「規則 A 在時間點 T 寫下一份列舉,T+n 新增了成員,T 的列舉沒有回頭同步」失敗模式;登記制判準把這個問題轉成一個查表即可回答的結構題。

   **暫停選單/彈出對話框的明文排除(2026-08-11 第六輪新增,回應對抗性覆核發現 F2-1)**:暫停選單、彈出對話框等**疊加於原畫面之上、且其焦點狀態不被任何下游系統讀取以驅動玩法可見預覽**的瞬時 UI,依上述登記制判準,**不登記進共用列舉、不落入本規則管轄範圍**——這與現有 4 個已知下游(棋盤格、關係圖迷你地圖、卡牌選取區、支援對話選單)性質不同:後者彼此是**替換關係**(進入新表面,前一表面通常卸載,見「表面卸載前的目標交接義務」),暫停選單則是**疊加關係**(開啟時,底下表面不卸載、只是被暫停/視覺蓋住)——若強行納入管轄,Core Rules #1 目前的單一扁平游標目標欄位必須擴充為可疊加的堆疊結構才能同時容納兩者,牽動 AC-2 恆一高亮不變式與 AC-37 競態防呆比對的共同基礎,結構性代價遠超暫停選單本身的功能價值,故不採此方向。**AC-23 的斷言範圍註記**:AC-23 保證的是「暫停選單與本系統之間不存在耦合」(未登記表面的操作不寫入本系統狀態),不是「本系統在暫停期間執行了某種保存/還原機制」——暫停選單若需要選項焦點的保存/還原,由其自身的 Godot 原生實作負責,不屬於本系統職責範圍。
   - **跨表面單位缺口已修復(2026-08-04,回應 game-designer、systems-designer、ux-designer 審查發現;2026-08-05 第九輪更新換算機制,回應 game-designer 審查發現、使用者裁決)**:本一般化規則先前遺留一個字面上的矛盾——Core Rules #3 的滑鼠奪權空間門檻原以「格」為單位定義,但棋盤格以外的表面(關係圖迷你地圖節點、卡牌選取區)沒有「格」的概念,規則對這些表面literal上無法實作。Core Rules #3 第三~八輪曾改以「目標命中框〔bounding box〕對角線長度的百分比」重新定義該門檻;**第九輪進一步改為「依表面類型分表的固定像素常數」**(見 Core Rules #3「奪權門檻的錨定對象」)——任何表面只需依其表面類型標籤查表即可取得門檻值,不需個別下游系統另行定義換算比例、也不需對個別目標做幾何查詢,比第三~八輪的百分比方案更簡單。本條「不得各自重新實作」的承諾至此仍對所有已知表面成立,且成立方式更直接。
   - **表面類型標籤禁止同標籤多實例掛載(2026-08-05 第九輪新增,回應 ui-programmer 審查發現、綜合裁決收窄範圍——ui-programmer 原始發現聚焦於查詢介面的註冊/發現機制〔屬 `/create-architecture` ADR 層級,本文件維持委派〕,但 creative-director 覆核後指出其中包含一個真正的設計層問題:若同一個表面類型標籤〔單一共用列舉的同一成員〕允許多個實例同時掛載〔例如完整關係圖檢視與關係圖迷你地圖皆標記為同一個「關係圖節點」列舉成員〕,則 Core Rules #1 定義的目標識別元組「表面類型標籤 + 該表面內的具體目標識別」不足以唯一定位一個目標實例——而此元組是本系統的核心資料模型,是 AC-37 競態防呆比對的依據,也是 AC-2 全域單一高亮不變式的計數依據)**:**同一表面類型標籤,在任一時刻,至多只能有一個實例掛載於場景樹中**——若某類 UI 表面天生會有多個同時存在的變體(例如同時提供完整檢視與縮圖檢視的關係圖),下游系統須在共用列舉中為每個變體各自登記獨立的表面類型成員(例如「關係圖節點・完整檢視」與「關係圖節點・縮圖檢視」分屬不同列舉成員),不得共用同一個成員。此為本系統對下游的硬性契約,已登記至 `design/gdd/systems-index.md` 的 Cross-System Obligations Registry(見 Dependencies)。具體的實例註冊/發現機制(`_ready` 自行註冊、group 查詢、或注入參考)維持委派給 `/create-architecture` 的 ADR,不受本條約束。
   - **表面卸載前的目標交接義務(2026-08-05 第十輪新增,回應 ui-programmer 審查發現——上一條「單一實例」契約只禁止**多於**一個實例同時掛載,從未規範**零個**實例的情況;若持有目前游標目標的表面(例如支援對話 UI 的對話選單)直接卸載/關閉,而未交接游標目標,系統會持有一個所屬表面已不存在的目標——沒有任何已掛載的表面能渲染它,AC-2「任一影格恰有一個高亮,不為 0」的不變式因此在狀態層通過、卻在渲染層失守,且此路徑此前無任何規則或 AC 能捕捉)**:任一 UI 表面若在卸載/關閉前,發現自己是目前游標目標所屬的表面類型(即目前游標目標的表面類型標籤等於自己的類型),**必須**在卸載前執行下列兩者之一:(a) 呼叫本系統既有的「標記目前目標為待重新解析」介面(見 Core Rules #2)通知本系統該目標暫時無主,由後續接手的表面或呼叫方系統決定下一步;或 (b) 若卸載當下已知替代目標(例如切換至另一個仍持有有效目標的表面),直接呼叫「設定新目標」介面完成交接。不得直接卸載而不呼叫任一介面——這會複用 Core Rules #2 已建立的機制(包含其競態防呆與呼叫參數比對),不需要新增機制。已登記至 Dependencies 章節與 `systems-index.md` Cross-System Obligations Registry(見新增 AC-51)。

     **觸發情境明文擴充涵蓋存檔載入(2026-08-11 第六輪新增,回應對抗性覆核發現 F2-2——`save-system.md` 全文對「游標」零提及,兩份文件之間先前零登記依賴,存檔載入後游標可能持有指向已不存在單位的有效目標,下游會渲染確信樣式的預覽,命中 Player Fantasy 第一號失敗情境)**:上述交接義務的「卸載/關閉」情境,明文涵蓋「存檔讀取導致目前表面內容整批替換」——不只是玩家主動切換畫面或單一目標局部失效(單位死亡/移動)。**責任歸屬不在本系統、也不在存檔系統**:兩者皆已明文聲明「不理解遊戲實體語意」(本系統見 Core Rules #2;`save-system.md` 見其 Overview 與 Core Rules #3),讓其中任一方跨界判斷「整個戰場是否被替換」都違反雙方既有的設計哲學。**責任歸屬於呼叫存檔系統讀取介面、且擁有游標目標所在表面的下游系統**(最可能是戰棋移動與交戰系統),依以下兩種進入情境分別處理,不得只處理其中一種:
     - **(甲)舊表面存在時讀檔**(例如戰鬥中經暫停選單載入另一存檔):讀檔流程開始、舊表面即將拆除時,呼叫方依上方交接義務呼叫「標記目前目標為待重新解析」;新表面建置完成後,依下方「(乙)」的初始狀態流程設定新目標。
     - **(乙)無舊表面時讀檔**(例如自標題畫面/戰役選單直接讀檔進入戰鬥,或情境(甲)拆除舊表面後接續的建置階段):沒有目標可交接,直接複用 Core Rules #6「初始狀態」既有的初始目標設定流程——新戰場建置完成視同「進入需要游標的畫面時,尚無任何裝置產生過 `ui_*` action」的情境,呼叫方呼叫「設定新目標」介面帶入依 Core Rules #6 規則計算出的初始可操作單位格,裝置權威依 Core Rules #4「系統主動改標與裝置權威的關係」維持呼叫前的值不變(此次呼叫非任何裝置的 `ui_*` action 觸發)——不需要新介面,與「新開局進入戰鬥」走完全相同的程式碼路徑。**乙分支兩個子情境的區分(2026-08-13 第十四輪新增,回應對抗性覆核 systems-designer 發現本段「完全相同的程式碼路徑」宣稱與 AC-62 已修訂的斷言範圍不同步——AC 層第十三輪引入了「乙-直接路徑」/「甲→乙路徑」兩個術語區分本分支的兩個子情境,但本段〔規則本體,唯一事實來源〕從未同步,仍對整個情境(乙)維持無條件的「完全相同」宣稱,與 AC-62「與甲→乙路徑的區隔」段落矛盾)**:上述「完全相同的程式碼路徑」宣稱,對本段開頭列舉的兩個子情境並非同等成立——**乙-直接路徑**(自標題畫面/戰役選單直接讀檔,無任何舊表面存在過)在檢查點一(呼叫「設定新目標」介面之前)與新開局路徑確實一致:裝置權威皆為未初始化。**甲→乙路徑**(情境(甲)拆除舊表面後接續本分支)則不同——依 Core Rules #4「系統主動改標與裝置權威的關係」,裝置權威在甲分支拆除舊表面的過程中維持呼叫前的值不變;若讀檔前玩家正以某裝置(例如滑鼠)持有權威,甲→乙路徑的裝置權威在檢查點一**不是**未初始化,這與新開局路徑不同——是**正確實作下就該如此的差異**,不是缺陷。「完全相同的程式碼路徑」這句話僅指本分支複用 Core Rules #6 既有初始目標設定流程本身(不需要新介面、走同一段程式碼設定游標目標座標值與有效性旗標),不涵蓋裝置權威這個獨立正交欄位(見 Core Rules #4)在甲→乙子情境下的初始值——該欄位不受本分支邏輯寫入,其值單純延續讀檔前的既有狀態。此區分見 AC-62「與甲→乙路徑的區隔」段落的驗收層對應。**滑鼠奪權累積位移量的處置(2026-08-12 第九輪新增,回應對抗性覆核 systems-designer 發現本情境從未定義此欄位的行為——它是 Core Rules #1 明文承認的三個頂層欄位之一,卻是唯一未被本節交接義務涵蓋的欄位)**:此欄位於甲/乙兩分支皆**重置為 0**——理由與「視同尚無任何裝置產生過 `ui_*` action」同源:此欄位是「鍵盤/手把持有權威期間,滑鼠正朝奪回權威累積淨位移」這個進行中事件的暫態量,一旦舊表面整批替換(甲分支拆除)或根本尚無舊表面(乙分支獨立進入),原本的累積起點與其所依附的表面一併不再有意義,延續一個依附對象已消失的累積值不具備任何行為意義——比照 AC-59 對暫停/模態情境的既有處理原則(該情境下亦明文重置為 0、累積起點更新為當下滑鼠座標)。**裝置權威欄位本身(如上述)則維持不變——兩者是可獨立變動的正交欄位(見 Core Rules #4),重置累積位移量不代表也重置裝置權威。**

       **已知體感落差:高亮位置與滑鼠實際螢幕位置不同步(2026-08-12 第七輪新增,回應對抗性覆核 game-designer 發現;嚴重度為建議級,不阻擋)**:本分支複用 Core Rules #6 初始狀態流程,而該流程**依規則計算初始可操作單位格**,不參考滑鼠當下的實際螢幕座標;同時裝置權威依 Core Rules #4 維持讀檔前的值不變。因此若讀檔前由**滑鼠**持有權威,讀檔完成瞬間玩家會看到高亮出現在一個與實體游標位置無關的格子上——狀態層完全正確,體感上是「我的滑鼠在這裡,但高亮在那裡」。**本輪不修改此行為**,理由與 2026-08-11 第十二輪使用者對滑鼠奪權子機制的裁決一致(《弈緣》是回合制戰棋,不需要即時操作反應;此子機制已連續多輪反覆審查,投入產出比持續下降),且既有的 Core Rules #3 滑鼠奪權機制已提供自然解法:玩家只要移動滑鼠超過門檻即奪回權威、高亮隨即跟上,無需額外機制。**明文登記為已知落差而非未發現的缺口**,若未來取得手把硬體後重啟滑鼠奪權子機制的重新設計(見 Open Questions「手把硬體取得」列),應將本情境一併納入評估範圍。
     - **(丙)讀檔流程被取消、返回原表面(2026-08-12 第七輪新增,回應對抗性覆核 systems-designer 發現——`save-system.md` Core Rules #5「生命週期通知的終止路徑」路徑〔三〕**自己明文點名**「非互動式載入過場被取消」為真實情境,但本節第六輪定案時只涵蓋甲/乙兩種前進路徑,未涵蓋這條回頭路)**:若情境(甲)已執行「標記目前目標為待重新解析」之後,讀檔流程因故中止(玩家取消、載入過場被上層取消、或存檔系統回傳拒絕讀取/該槽處理中等結果),而**原表面未被拆除或已被還原**,則呼叫方**必須**在返回互動式畫面之前,重新呼叫「設定新目標」介面完成收尾——不得讓游標停留在「待重新解析」狀態返回一個可互動的畫面。**此要求的存在理由**:待重新解析狀態下,AC-2「任一影格恰有一個高亮,不為 0」的不變式在狀態層仍成立,但下游依 Core Rules #2「下游預覽渲染義務」會抑制預覽或改用不確定佔位樣式;若玩家已回到可操作的戰鬥畫面卻持續看到不確定樣式且無任何操作能解除,正是 Core Rules #7 這條交接義務當初被建立來防止的「所屬表面已不存在的目標」在渲染層失守的等價狀態,只是成因從「表面消失」換成「表面回來了但沒人通知」。**重新設定的目標值**:若原目標在取消後仍然有效(原表面未拆除、該目標所指實體仍存在),得直接以原目標值重新設定,不需要重新計算;僅當原目標已失效時才依 Core Rules #6 計算初始目標。已登記至 `systems-index.md` Cross-System Obligations Registry 第 166 列(觸發情境枚舉再擴充)。**與 `save-system.md` 路徑四的關係(2026-08-13 第十三輪新增,回應對抗性覆核 systems-designer 發現丙分支未對齊 `save-system.md` 現行的四條終止路徑)**:上述丙分支的觸發原因(玩家取消、拒絕讀取、該槽處理中)對應 `save-system.md` 路徑〔二〕〔三〕與拒絕讀取狀態,**明文不包含**路徑〔四〕(遷移成功、但回寫存檔到磁碟失敗)——路徑四情境下,記憶體內已完成遷移的遊戲資料本身有效、可玩,回寫失敗是 `save-system.md` 自身 Core Rules #13 的內部關注(是否重試、是否於下次存檔時機重新嘗試回寫),**就本系統關心的分支路由決策而言視同成功,但呼叫方並非對路徑四本身無感(2026-08-13 第十四輪修正措辭,回應對抗性覆核 systems-designer 直接核對 `save-system.md` 第 76/78/290 行發現原「對呼叫方透明⋯呼叫方不需要知道路徑四是否發生過」宣稱與該文件自身規則矛盾——`save-system.md` 明文要求完整讀取介面在路徑四**第一次發生**即回傳一個與正常成功可程式化區分的獨立結構化結果,且下游 UI「不得呈現為讀取畫面靜默淡出或原地無回饋」,必須主動告知玩家)**:路徑四情境下遷移語意已成功、記憶體內遊戲資料本身有效可玩,就**本系統的分支路由決策**而言,呼叫方依然直接依甲/乙分支的正常前進路徑處理、**不落入丙分支**(丙分支的存在前提是讀檔流程中止、返回原表面,路徑四不是中止,是「成功但附帶一項獨立告知義務」)。但呼叫方**確實會收到、也確實需要知道**路徑四發生過——`save-system.md` 賦予呼叫方的義務(向玩家呈現可與正常成功區分的告知,見該文件 Interactions「重複回寫失敗須主動告知」第一級)獨立於本系統的分支路由邏輯之外,由呼叫方自行依 `save-system.md` 的契約履行,不屬於本系統(不理解遊戲實體語意,也不理解存檔語意)的職責範圍,亦不改變本系統游標目標交接甲/乙路由結論本身。

     **時機點的安全窗口(呼應 `save-system.md` Core Rules #5「觸發情境限制」)**:上述兩種情境的呼叫時機,不需要精確對齊存檔系統反序列化完成的那一刻——`save-system.md` 明文規定會觸發遷移鏈的完整讀取,只能從下游 UI 指定的**非互動式載入過場**情境呼叫,此期間玩家看到的是進行中/忙碌指示,互動式戰鬥畫面尚未出現。只要交接呼叫發生在互動式戰鬥畫面重新出現之前的任何時間點,「下游預覽渲染義務」(AC-50)就不會被觸犯,不需要更精確的時機定義——**此為 F2-1 與 F2-2 共用的唯一情境定義錨點**:AC-23(見上方「暫停選單/彈出對話框的明文排除」)保證的是「暫停 → 返回**原**畫面」路徑;「暫停選單內觸發讀檔」依 `save-system.md` Core Rules #5 觸發情境限制,其真實序列是「暫停選單 → 玩家確認讀取 → 進入非互動式載入過場(暫停選單與原表面於此時卸載)→ 載入/遷移 → 建置新表面 → 依 Core Rules #6 設定初始目標」,不是「暫停 → 讀檔 → 關閉選單返回原畫面」——兩者不落在同一條路徑上,AC-23 與本節新增規則因此不矛盾。已登記至 `systems-index.md` Cross-System Obligations Registry 第 165 列(觸發情境枚舉擴充)。
   - **範圍界定(回應 game-designer、ux-designer 審查發現與 `game-concept.md` 第五輪已裁決的關係圖迷你地圖多選釘選規則)**:本一般化規則的範圍僅止於**單一 hover/游標目標**本身,**不涵蓋**下游系統可能另外維護的**多選/釘選集合**。多選/釘選集合(例如關係圖迷你地圖同時比較多組配對的聚合值)是下游系統自行擁有、維護的**獨立狀態**,其生命週期、增減規則由該系統自己的 GDD 定案,不受本系統管轄,也不需要修改本系統本體程式碼即可存在。
   - **兩層的介面關係**:集合中「目前正被 hover/瞄準以決定是否加入/移除」的那一個候選目標,仍必須透過本系統的單一游標狀態決定,不得繞過(呼應 Core Rules #2)。換言之——「hover 中的哪一格」永遠由本系統仲裁,單一、全域唯一,受 AC-2 的恆一高亮不變式約束;「已經被永久釘選、同時顯示多個」與否是下游的選取邏輯,不受 AC-2 約束。兩者在視覺上通常也應可區分(例如游標用外框閃爍,釘選用常駐圖示),避免玩家把兩種不同性質的資訊誤讀成同一種。
   - **表面類型標籤的型別契約(2026-08-04 第七輪新增,回應 ui-programmer 審查發現的抽象型別缺口)**:Core Rules #1 定義的「表面類型標籤」自本文件建立以來從未定案其具體資料型別(列舉?字串?類別參考?)。由於本系統的下游依賴系統(見 Dependencies)尚未設計、且將各自獨立進行設計 session,若型別留待各自設計時才各自決定,極可能在 `/create-architecture` 定案前就已產生互不相容的標籤 schema,屆時共用讀寫介面在型別層面即無法通用,直接牴觸本條「不得各自重新實作」的初衷。本文件定案最小契約:**表面類型標籤必須是單一共用列舉(enum)的成員,該列舉集中定義、集中擴充——任何下游系統新增自己的表面類型時,須在此列舉新增對應成員,不得自行發明字串或獨立型別**。具體列舉的實作位置與擁有者(本系統的 Autoload/常數檔,或 `/create-architecture` 另行指定)留待 `/create-architecture` 定案,但「單一集中列舉、集中擴充」本身是本文件對下游的硬性契約,已登記至 `design/gdd/systems-index.md` 跨系統義務登記表(見 Dependencies)。

## Formulas

**(2026-08-04 第五輪補齊,回應 creative-director 綜合裁決發現——Core Rules #3 的滑鼠奪權空間門檻在第三/四輪加入後,實際引入了一個真正的公式,卻從未被送進本章節做邊界值檢查,這是本輪多項阻擋項〔累積量定義、退化命中框、AC-1 欄位矛盾〕的共同根因,不能再以散文形式留在 Core Rules 裡)**

**奪權門檻與漸進回饋公式(2026-08-05 第九輪重寫,回應 game-designer 審查發現、使用者裁決——門檻錨定對象由「目前目標命中框的百分比」改為「表面類型的固定像素常數」,見 Core Rules #3「奪權門檻的錨定對象」。原公式的 `min(max(...), ...)` 三層鉗制結構、`bounding_box_diagonal_px` 即時幾何輸入、`mouse_reclaim_min_target_percent`/`mouse_reclaim_max_threshold_px` 兩個旋鈕,整組被單一查表動作取代,原本 6 條邊界值分析中,有 4 條〔涉及命中框對角線本身或兩個舊旋鈕的排序關係〕隨旋鈕移除而不再適用,僅保留與「必須 > 0」這個安全約束同構的邊界情境,並新增查表本身特有的邊界情況)**:

```
reclaim_threshold_px = mouse_reclaim_threshold_px_by_surface_type[surface_type]
reclaim_progress = clamp(accumulated_net_displacement_px / reclaim_threshold_px, 0.0, 1.0)
```

- `mouse_reclaim_threshold_px_by_surface_type`:見 Tuning Knobs,依 Core Rules #7 共用列舉的表面類型分表的固定像素常數表。
- `surface_type`:目前高亮目標的表面類型標籤(見 Core Rules #1),查表鍵值。
- `accumulated_net_displacement_px`:見 Core Rules #3「狀態模型」,累積起點到目前滑鼠位置的直線距離,逐幀更新,依四項重置時機歸零(2026-08-05 第十輪由五項簡化為四項,見 Core Rules #3「累積起點的重置時機」)。
- `reclaim_progress`:驅動漸進回饋視覺元素的透明度(0.0 = 完全不可見,1.0 = 完全不透明且完成權威轉移)。

**邊界值**:
- `mouse_reclaim_threshold_px_by_surface_type[X] = 0`(某表面類型的常數被配置為 0)→ `reclaim_progress` 公式除以零。**此為文件明文禁止的配置**,見 Tuning Knobs 新增的硬性約束(每個表面類型的常數必須 > 0,見 AC-46)。
- `mouse_reclaim_threshold_px_by_surface_type[X] < 0`(某表面類型的常數被配置為負值)→ `reclaim_threshold_px` 為負值;因 `accumulated_net_displacement_px` 依定義恆為非負,`displacement / 負值 ≤ 0`,`clamp()` 後 `reclaim_progress` 恆為 `0.0`——該表面類型上滑鼠**永久無法奪回權威**,不拋出任何例外,是比除以零更難察覺的靜默死鎖。**此同樣是文件明文禁止的配置**,見 Tuning Knobs 新增的硬性約束。
- **表面類型列舉新增成員,但查表未同步新增對應常數(2026-08-05 第九輪新增,回應 creative-director 綜合裁決指出的本文件招牌失敗模式——列舉式規則在新增成員後,較早寫下的對應表未回頭同步)**:若下游系統依 Core Rules #7「表面類型標籤的型別契約」在共用列舉新增了自己的表面類型成員,但 `mouse_reclaim_threshold_px_by_surface_type` 表未同步新增該成員的對應常數,則該表面類型的目標永遠無法讀到合法的 `reclaim_threshold_px`(查表未命中)。**此為與上述「必須 > 0」同一位階的硬性約束**:任何新增至共用列舉的表面類型成員,必須在同一次變更中於本表新增對應常數,兩者視為單一原子變更,不得分開提交——已登記至 Core Rules #7 的表面類型契約(見 Dependencies 章節的跨系統義務)。**此邊界情況此前雖已明文定案,卻無對應 AC 驗證初始化階段是否真的檢查「查表未命中」這個失敗模式(與 AC-46 只驗證「配置為 0/負值」這個已存在但非法的值不同)——2026-08-05 第十輪新增 AC-46b 補齊此驗證缺口(回應 systems-designer、qa-lead、ui-programmer 三方獨立收斂發現)。**
- 極小但合法的常數值(例如 1px)→ 允許,但實務上會讓微小滑鼠抖動即可完成奪權,喪失防抖意義。這是校準責任,不是公式錯誤——各表面類型的常數值須於垂直切片階段以真實手把+滑鼠混合輸入實測,校準責任見 Core Rules #3「校準與後續驗證」。

**原有保留說明**(2026-08-03,systems-designer 諮詢確認,本系統其餘部分仍非公式導向):交接防抖時間若未來需要,是單一常數(Tuning Knob),不涉及變數運算;高亮移動的插值/緩動屬於 Visual/Audio Requirements 的呈現時序,不是玩法數值;多目標歧義解析(例如游標目標失效時該如何處理)依 Core Rules #6 的既有設計精神,本系統本就不自行解析「該落在哪」,而是委派給呼叫方系統決定——已列入 Edge Cases 一併處理。

## Edge Cases

*(2026-08-03,`/design-review` 完整模式已補齊 `systems-designer` 諮詢。覆核發現並已修正:未初始化狀態與 AC-2 恆一高亮不變式的矛盾(見 States and Transitions 表與 AC-15)、Core Rules #4 交接繼承規則未涵蓋「從未初始化狀態繼承」的邊界情況、裝置權威欄位的值域未含「未初始化」、AC-12 的影格延遲門檻應登記為 Tuning Knob 而非埋在 AC 裡、以及本節「同一影格雙裝置」情境需要補充連續多影格穩定性條款(見下方新增內容與 AC-20)。)*

- **若手把持續產生方向輸入,滑鼠同時靜止不動**:滑鼠靜止不產生新的 `ui_*` action,不會因為滑鼠仍「停留」在畫面某處就奪回權威——權威繼續留在手把。
- **若鍵盤/手把持有權威,滑鼠同時在合法游標目標區域內移動**(2026-08-04,`/design-review` 完整模式審查後新增,回應 ux-designer 審查發現的「滑鼠移動但未被承認」失敗情境;**2026-08-05 第九輪術語同步,回應 game-designer 審查發現、使用者裁決——門檻錨定對象已由目標命中框百分比改為表面類型固定像素常數,見 Core Rules #3「奪權門檻的錨定對象」**)**:滑鼠須累積淨位移(見 Core Rules #3「狀態模型」——直線距離,非路徑總和)達目前高亮目標所屬表面類型的 `reclaim_threshold_px`(見 Tuning Knobs)以上,才視為產生有效的奪權 `ui_*` action,依 Core Rules #3 取得權威,並依 AC-12 的延遲上限更新顯示。移動過程中,漸進回饋視覺元素(原生指標或替代載體,見 Core Rules #3)依累積淨位移進度連續淡入顯示(不是等到門檻觸發才突然出現)。未達此距離的移動(不論是次像素移動或未滿門檻的移動),不觸發權威轉移、不更新游標目標——但已淡入的視覺元素透明度仍會反映累積進度,玩家能持續看到自己正在接近門檻,這正是用來消除「探測性輸入後仍不確定」失敗情境的機制本身,而非放任該情境發生。
- **若滑鼠移出遊戲視窗範圍**:不產生任何有效 `ui_*` action,游標狀態維持在移出視窗前最後一次有效的目標與權威,不清空、不跳到預設值。
- **若滑鼠懸停於非合法游標目標的區域**(例如 UI 面板本身、棋盤外的空白處):不觸發權威切換,也不更新游標目標——維持既有有效目標不變,直到滑鼠移回合法區域並產生有效的 `ui_*` action。
- **若滑鼠與手把在同一影格內皆產生 `ui_*` action**(理論邊界情況)**(2026-08-04 重寫,回應 systems-designer、godot-specialist、qa-lead 三方獨立收斂發現——原規則將最終權威交給「引擎輸入佇列處理順序」,但該順序本身從未實測驗證是否確定、是否跨執行可重現,對雙實體裝置而言更是作業系統層級的輪詢/中斷時序競爭,引擎不保證可重現。一個把「不要讓輸入裝置的不確定性洩漏到玩家眼前」當作存在理由的系統,不應該把最終判定結果建立在未經驗證的引擎行為上,這個矛盾由 creative-director 綜合裁決確認為阻擋項目)**:不依賴引擎輸入佇列處理順序,改採**明文固定優先序:鍵盤/手把恆優先於滑鼠**——若兩裝置在同一影格內皆產生對應的 `ui_*` action,最終權威判定為鍵盤/手把,即使滑鼠事件在引擎內部可能被判定為「較晚處理」。**理由**:滑鼠是絕對定位裝置,即使本次同幀被鍵盤/手把搶先,滑鼠只需要下一次達到 Core Rules #3「滑鼠奪回權威的空間門檻」的移動,就能立即重新取得權威,誤判代價趨近於零;鍵盤/手把是相對定位裝置,若在同幀競爭中意外落敗,玩家會感受到自己剛按下的**方向鍵/導覽動作**「沒有反應」,心智模型斷裂的代價遠高於滑鼠。此規則完全不依賴任何引擎內部行為,可 100% 決定性測試,原本「引擎佇列分派順序是否確定、是否可重現」的疑問(見 Open Questions)因此從阻擋項降級為技術好奇心,不再影響本規則的正確性。**適用範圍(2026-08-05 第九輪新增,回應 systems-designer 審查發現的真矛盾,修正本規則與 Core Rules #3「確認類動作與裝置權威的關係」曾對同一組輸入給出相反判定的問題——上一句理由文字原本泛稱「方向鍵/確認鍵」皆適用本規則,但這與 Core Rules #3 明訂「確認類動作不轉移裝置權威」直接衝突,已改寫為僅提及方向鍵/導覽動作)**:本規則**僅**適用於雙方於同影格內產生的事件皆具備主張裝置權威資格的情境——具備資格的事件僅兩類:鍵盤/手把的導覽類 `ui_*` action、滑鼠達到 `reclaim_threshold_px` 的位移。**確認類或其他非導覽類 `ui_*` action 不具備主張裝置權威的資格,不落入本規則的仲裁範圍**(見 Core Rules #3「確認類動作與裝置權威的關係」)——例如滑鼠持有權威、同影格鍵盤/手把僅產生確認類動作時,不適用本規則,裝置權威依 Core Rules #3 維持滑鼠不變。**持續按住造成鎖死的已知殘留風險(2026-08-06 第十一輪修訂措辭,回應對抗性審查發現、使用者裁決——原第十輪同日曾嘗試的「持續按住的例外 + 保險上限」修法已撤回)**:若鍵盤/手把在方向鍵/搖桿持續按住期間每影格皆重複產生合格導覽動作,本規則理論上可能讓滑鼠永久無法完成奪權——`prototypes/cursor-reclaim-godot-spike-2026-08-05/` 已人工實測證實此風險成立(類比搖桿持續按住 5-10 秒,`device_authority` 全程鎖在 `KEYBOARD_GAMEPAD`)。第十輪曾同日直接寫入一套修法(否決資格限縮為「新按下」的那一影格,對應 `Input.is_action_just_pressed()`,另加連續否決影格數保險上限),但該修法**未經對抗性審查即寫入文件**,經第十一輪正式覆核後判定不成立並撤回——核心問題:所引用的 API 從未被 spike 實際測試(spike harness 實際使用的是語意不同的 `event.is_action_pressed()`)、新增的保險上限計數器是未被 Core Rules #1/AC-1 承認的隱藏狀態欄位且歸零時機自我抵銷、鍵盤/D-pad/類比搖桿三種輸入來源是否行為一致從未驗證。**本風險維持登記為已知殘留風險,本規則本身不因此風險採取任何設計動作**,列入 Open Questions,待未來以已實測驗證的機制重新設計並完整走過一輪對抗性審查後才可寫入規則本體。
  - **連續多影格穩定性**:由於判定規則現在是固定優先序(鍵盤/手把恆勝),不依賴任何運行時狀態或引擎內部順序,連續多影格下的判定結果天然穩定、不會逐影格搖擺——這點不再需要額外驗證引擎行為,規則本身的確定性已經保證了這點。
  - **實作架構約束(2026-08-04 第六輪新增,回應 godot-specialist 審查發現——本規則第三輪已因引擎順序依賴問題被升級為阻擋項一次,但「不依賴引擎內部行為」的保證此前只隱含在 AC-20 的驗證註記裡,從未寫進 Detailed Rules 本身作為明文實作限制,修法並不完整;**2026-08-05 第九輪修訂,回應 godot-specialist 本輪審查發現、綜合裁決升級為阻擋項**——原文字把 `_input`/`_unhandled_input` 當作可互換的實作選擇,但 godot-specialist 指出兩者對本規則的正確性不等價:`_unhandled_input` 只會收到 Control 自身 GUI 處理〔透過 `accept_event()`〕未消費的事件,若一個被聚焦的 Control 內建的焦點導覽邏輯消費了 `ui_up`/`ui_down` 事件,該事件會**完全不會抵達**以 `_unhandled_input` 為基礎的緩衝區——這是遺漏,不是重排序,足以讓文件最核心的「100% 決定性測試」宣稱被推翻,因為緩衝架構本身無法補救一個從未進入緩衝區的事件)**:上述固定優先序規則要成立,實作**必須**採「緩衝該影格內全部輸入事件、待事件收集完畢後才統一裁定裝置權威」的架構,**不得**採逐事件即時處理。**緩衝掛載點是正確性要求,不是風格偏好**:此緩衝**必須**掛載於 `_input`(在事件到達任何 Control 的 GUI 處理、可能被 `accept_event()` 消費之前),**禁止**掛載於 `_unhandled_input`——若掛 `_unhandled_input`,則影格內最後派發的 `ui_*` action 可能悄悄勝出(逐事件即時處理的舊風險重現),或某些事件可能被 Control 內建處理消費而完全不抵達緩衝區(比逐事件即時處理更嚴重的遺漏風險),兩者皆會推翻本規則「不依賴引擎內部行為、100% 決定性測試」的核心宣稱。這是本規則要成立的必要架構前提,不是實作細節的自由選擇,須列入 `/create-architecture` 的強制驗證項。**專案層級的隱性依賴(2026-08-05 第九輪新增)**:上述「一次 `_process` 週期 = 一批原子化派發的事件」假設,依賴 Godot 專案設定「Input Devices → Buffering → Agile Event Flushing」維持關閉(預設值)——若專案任何其他系統(例如低延遲繪圖/拖曳工具)日後為求即時性開啟此設定,事件會即時派發而非批次收集至下一次 `_process` 前,將全域破壞本規則「同一影格 = 一次原子化裁定」的定義前提,不僅限於本系統。此依賴已登記至 Open Questions,須列入 `/create-architecture` 的專案層級驗證項,不得僅由本系統自行確認。「同一影格」的精確定義(以視覺影格/`_process` 迴圈週期計數,涵蓋該週期內收到的全部 `InputEvent`)比照 AC-12 對「影格」的定義方式辦理,不留給實作階段自行認定。
  - **與 Steam Input 前提約束的交叉關聯(2026-08-04 第六輪新增,回應 game-designer 審查發現)**:Core Rules #3「滑鼠奪權前提約束」已說明 Steam Input 可能同時發出與真實滑鼠事件無法區分的合成滑鼠事件。若某 Steam Input 控制器設定在同一影格內**同時**觸發合成滑鼠事件與真實 `InputEventJoypadButton`,依本固定優先序規則,鍵盤/手把仍會勝出——這與前提約束段落描述的「合成滑鼠事件竊取權威」風險方向相反,不構成新風險,但兩條規則的交互效果先前從未被文件明文承認,此處登記以避免遺漏,不需額外規則因應。
  - **與滑鼠奪權累積量重置的交叉關聯(2026-08-04 第七輪新增,回應 creative-director 本輪審查發現;2026-08-04 第八輪修訂範圍,回應 systems-designer、qa-lead 兩方獨立收斂發現、使用者裁決——原版本僅限「導覽動作」否決時觸發重置,與本規則母句〔鍵盤/手把不限動作類別、恆優先於滑鼠〕範圍不同步,若否決滑鼠的是確認類動作,累積量會殘留、於下一影格靜默完成奪權,已修訂為不限動作類別;2026-08-05 第十輪重新編號,見 Core Rules #3 觸發點 (d);**2026-08-06 第十一輪重新窄化,回應 qa-lead 審查發現的真矛盾、使用者裁決,對齊第九輪母規則從未同步的範圍限縮——第八輪的「擴大範圍」裁決與第九輪母規則的「確認類不具資格」裁決彼此矛盾,本輪以第九輪母規則為準**)**:若本規則否決的是滑鼠已達奪權門檻的當次嘗試(即滑鼠當幀累積淨位移已達到或超過 `reclaim_threshold_px`,但因鍵盤/手把同幀產生**導覽類** `ui_*` action 而依固定優先序未能完成轉移),依 Core Rules #3「累積起點的重置時機」觸發點 (d),累積位移量與起點須同步重置,不得殘留在滿格進度、於下一影格在鍵盤/手把未有進一步輸入下自動完成奪權。**若鍵盤/手把同幀僅產生確認類動作(不具備主張裝置權威資格,不落入本規則仲裁範圍),滑鼠的奪權主張不被否決,不觸發本重置——見 Core Rules #3 觸發點 (d)「確認類動作不觸發本重置路徑」。**

- **若手把在持有權威期間斷線**:游標狀態維持在斷線前的最後目標與視覺,不消失、不重置。若之後滑鼠產生有效輸入,依正常規則接手權威;若沒有任何裝置產生新輸入,游標保持靜止顯示。
- **若遊戲於游標持有某個目標時進入暫停選單/彈出對話框**:返回遊戲畫面時,游標的裝置權威與目標值維持暫停前的狀態不變,不因暫停期間任何背景輸入或選單內的操作被竄改。**成立機制:暫停/模態期間本系統不參與裁定(2026-08-11 第六輪新增,回應對抗性覆核發現 F2-1 的伴生缺口——Core Rules #3「實作架構約束」明文要求本系統的裝置權威判定緩衝必須掛載於 `_input()`,在事件到達任何 Control 的 GUI 處理之前;若暫停選單本身也在同一輪 `_input` 派發中接收事件驅動其原生 focus 系統,兩者對同一批 `ui_up`/`ui_down` 事件的處理順序此前從未定義,是本規則與暫停情境的第一次真正碰撞)**:本系統將「遊戲進入暫停選單/模態 UI 期間」比照 Core Rules #3「累積起點的重置時機」觸發點 (c)(視窗失去/取得 OS 層級焦點)已驗證過的「不運算 + 重新播種」模式一般化處理——**本系統的裝置權威判定緩衝(見 Core Rules #3「實作架構約束」)於暫停/模態期間全程不參與裁定、不消費任何輸入事件供自己的判定邏輯使用**;返回遊戲畫面(暫停/模態結束)的當下,若持有權威的裝置是滑鼠,Core Rules #3 的滑鼠奪權累積位移量依既有觸發點 (c) 的精神重置為 0、起點重新播種於復焦當下的滑鼠螢幕座標。此模式選擇複用觸發點 (c) 已通過第十輪對抗性審查驗證的既有規則形狀,不新增未經驗證的機制(呼應第十一輪撤回「保險上限計數器」修法的教訓)。**範圍澄清(2026-08-13 第十三輪新增,回應對抗性覆核 systems-designer 發現本段宣稱與 Core Rules #7 F2-2 甲/丙分支互相矛盾)**:上述「不參與裁定/不消費輸入」限定於本系統對原生輸入事件的被動裁定路徑(即 Core Rules #3 的裝置權威判定緩衝),**不涵蓋**呼叫方系統透過本系統既有寫入介面(「設定新目標」「標記目前目標為待重新解析」)發出的主動 API 呼叫——後者是獨立於裁定緩衝之外的呼叫方驅動寫入路徑,其發生時機與 `SceneTree.paused` 當下的實際布林值無關,不受本段拘束(見 Core Rules #7 F2-2 甲分支〔讀檔流程開始、舊表面拆除前的標記呼叫〕與丙分支〔讀檔取消、返回原畫面前的設定呼叫〕,兩者皆可能發生於暫停選單仍處於顯示狀態轉場的期間)。本段原文字「不更新任何狀態欄位」的措辭過寬,已收斂為與本節新增 AC-59 實際測試的範圍一致(AC-59 驗證的是「背景輸入訊號或選單內部操作不竄改狀態」,從未涵蓋禁止呼叫方主動呼叫)。**具體讓路手段**(例如依賴 `SceneTree.paused` 搭配本系統 Autoload 節點的 `process_mode` 維持預設 `PROCESS_MODE_PAUSABLE`,暫停選單自身的 `Control` 樹設為 `PROCESS_MODE_WHEN_PAUSED` 以便接收輸入、運作其原生 focus 系統)委派 `/create-architecture` 決定,但「本系統於此期間不裁定」本身是行為規格,不留給實作階段自行認定,已列入該階段強制驗證項(見 Open Questions 新增列)。若專案內存在**不**透過 `SceneTree.paused` 實作的非阻斷式彈窗(例如遊戲邏輯仍在背景執行的確認提示),須額外的顯式暫停/恢復旗標達成同等效果,不能假設 `SceneTree.paused` 涵蓋全部彈出情境——此為 `/create-architecture` 階段須一併確認的前提,不在本文件定案範圍。見新增 AC-59。
- **若游標目前指向的目標本身失效**(例如目標格上的單位在游標對準時死亡或被移動)**(2026-08-04 修訂,回應 game-designer、systems-designer 審查發現)**:本系統**不自行判斷**目標是否失效、也不自行重新解析新目標——這部分沿用 Core Rules #6 的委派精神,由呼叫方系統偵測失效並決定後續動作(維持原格待重新解析、或直接呼叫「設定新目標」介面)。但本系統現在**主動承擔視覺呈現的一致性**:呼叫方偵測到失效後,應呼叫 Core Rules #2 新增的「標記目前目標為待重新解析」介面,而非放任舊視覺原樣顯示——此後畫面上的「待重新解析」呈現由本系統統一定義,不再讓下游各自決定。若呼叫方完全不介入(既不標記失效、也不設定新目標),本系統仍保證目前狀態值維持不變、有效性旗標維持原樣,不會自動變成空值或拋出例外——這是本系統在無呼叫方介入下唯一能做的保證,防止靜默資料錯誤,但不能替呼叫方偵測失效本身。**若呼叫方偵測失效的時間點與玩家自己的導覽操作發生時間差**(2026-08-04 第八輪新增,回應 ui-programmer 審查發現的競態條件,見 Core Rules #2「呼叫參數與競態防呆」;**2026-08-06 修正末句與 Core Rules #2 結構化回傳值機制不一致的殘留舊文字,回應 `/review-all-gdds` 驗證重跑發現**)**:呼叫方呼叫「標記目前目標為待重新解析」時傳入的目標識別,若與系統當下實際持有的目前游標目標不相符(代表玩家已在此期間導覽至另一個完全有效的新目標),本次標記呼叫視為過期,系統**回傳明確的「已過期,未套用」結構化結果**(不是靜默忽略、不回傳任何結果),玩家當下持有的合法目標不受影響、不會被誤標記為待重新解析——呼叫方收到此結果後,依 Core Rules #2「回傳值與呼叫方重驗義務」須自行判斷是否需要重新偵測並重試,不得假設「呼叫過一次就等於問題已解決」。
- **若遊戲視窗失去或重新取得作業系統層級焦點**(例如 alt-tab 切換視窗、視窗最小化、Steam 疊加層開啟,不同於遊戲內暫停選單/彈出對話框——見上方暫停情境的既有規則)**(2026-08-04 新增,回應 ux-designer 審查發現的覆蓋缺口)**:遊戲失去 OS 層級焦點期間,游標的裝置權威與目標值維持不變,比照暫停情境的既有精神。**重新取得焦點時**(對應 Godot 的 `NOTIFICATION_APPLICATION_FOCUS_IN`),本系統須強制觸發目前權威裝置對應高亮的重繪,並重新套用目前裝置權威所要求的原生滑鼠指標顯示/隱藏狀態(見 Core Rules #5)——因為某些作業系統或引擎行為可能在失去焦點期間重置滑鼠模式或暫停渲染迴圈,若不強制重繪與重新套用,玩家回到遊戲畫面時可能同時看不到原生指標、也看不到確認過的高亮,重現 Player Fantasy 明訂的「兩個高亮同時存在或完全找不到高亮」失敗情境。**與滑鼠奪權累積量的交叉關聯(2026-08-04 第七輪新增,回應 systems-designer、qa-lead 兩方獨立收斂發現;2026-08-05 第十輪重寫,回應同方兩位審查發現的定序缺口與運算範圍真歧義)**:上述「裝置權威與目標值維持不變」的保證,不包含 Core Rules #3 的滑鼠奪權累積位移量與累積起點——依 Core Rules #3「累積起點的重置時機」觸發點 (c)(第十輪重寫),失焦**整段期間**本欄位完全不運算(不只是復焦當幀才處理),復焦當下重置為 0、累積起點更新為復焦當下的滑鼠螢幕座標,不得殘留失焦前的舊起點,也不存在失焦期間本欄位在背景悄悄逼近或跨過門檻的可能。

- **滑鼠奪回權威的表面類型門檻表(`mouse_reclaim_threshold_px_by_surface_type`,依表面類型分表,各表面類型的初始建議值待垂直切片階段實測;**初步校準數據(2026-08-05,`prototypes/cursor-reclaim-godot-spike-2026-08-05/` Test 2 程序 C 人工實測):單一合成測試表面上,約 50-100px 區間手感自然〔不易誤觸、也不需刻意找滑鼠〕,僅供垂直切片階段各表面類型分別校準時參考起點,非最終值,亦未依表面類型分別測試**)(2026-08-05 第九輪重寫,取代原三個旋鈕`mouse_reclaim_min_target_percent`/`mouse_reclaim_max_threshold_px`/`mouse_reclaim_min_pixels`,回應 game-designer 審查發現、使用者裁決,見 Core Rules #3「奪權門檻的錨定對象」)**:定義鍵盤/手把持有權威時,滑鼠須累積淨位移達多少**絕對像素值**,才視為對**該表面類型**產生有效的奪權訊號(公式見 Formulas)——**每個表面類型(見 Core Rules #7 共用列舉)各自一個固定像素常數**,不再依賴任何目標的即時命中框幾何。**改用表面類型分表而非目標百分比的理由**:第三~八輪的百分比方案曾解決「棋盤格以外表面沒有『格』單位」的問題,但把門檻錨定在「目前(鍵盤/手把持有的)目標」的命中框上,會讓一次朝鄰近小目標的普通短距點擊,因目前目標較大而被迫先做一段與該次點擊距離無關、不可預測的滑鼠位移,在一般情況下(不只是極端情況)損害可預判性;表面類型分表消除此問題,同時仍保留「不同表面可各自有合理門檻、不強制全域單一數值」的設計意圖。**硬性約束(2026-08-05 第九輪新增,回應 qa-lead 審查發現的驗證缺口,見 AC-46)**:表中每個表面類型的常數值**必須嚴格大於 0**,不得配置為 0 或負值——若為 0 或負值,會導致 `reclaim_progress` 公式除以零或恆為 `0.0`(靜默死鎖),見 Formulas 邊界值。**新增列舉成員與本表的原子同步約束**:任何新增至 Core Rules #7 共用列舉的表面類型成員,必須在同一次變更中於本表新增對應常數,不得分開提交(見 Formulas 邊界值)。此數值須列入 `/create-architecture` 或初始化階段的合法值檢查項(見 AC-46,新增列舉成員未同步的情況見 AC-46b)。**此為空間門檻,不是時間防抖**——不引入任何延遲,每一幀即時比對移動距離,不違反下方「交接防抖時間窗」建議不加入的立場(兩者是正交的旋鈕,一個測距離、一個測時間)。實際數值待垂直切片階段以真實手把+滑鼠混合輸入實測校準,並與 Open Questions 已登記的「是否需要恢復每目標差異化」spike 一併驗證。**無障礙覆寫點的明文承認(2026-08-05 第九輪補回登記——此建議項於第七輪提出,但在第八輪的遺留清單中無聲消失,未經解決或明文延期,本輪回應 ux-designer 審查發現正式補回)**:本旋鈕(以及反方向零門檻豁免所依賴的搖桿死區設定)是本系統對運動無障礙(motor accessibility)需求的**明文覆寫點**——若 `design/ux/accessibility-requirements.md`(見 Open Questions)日後定案需要玩家可調整的奪權門檻或死區,本旋鈕與死區設定即為該調整的落地位置,不需修改本系統的規則本體。此承認本身不預先定案任何無障礙覆寫的具體機制,只確認覆寫點的存在與位置。

### A. Single State Source & Dual-Write

- **AC-1**(2026-08-04 第五輪修訂,回應 systems-designer、ui-programmer 審查發現的欄位數矛盾——原版本斷言「僅兩個欄位」與 Core Rules #3 奪權機制實際需要的累積位移量欄位矛盾,本次承認第三欄位為公開、非隱藏狀態): **GIVEN** 系統的全域狀態物件,**WHEN** 檢視其結構,**THEN** 恰包含三個頂層欄位——目前游標目標(含表面類型標籤與有效性旗標,見 Core Rules #1)、目前裝置權威、滑鼠奪權累積位移量(見 Core Rules #3)——沒有第四個會影響任何 UI 表面高亮顯示決策的隱藏欄位或分散狀態。三者皆為本文件明文承認、非隱藏的狀態,本 AC 驗證的是「不存在第四個未被文件承認的隱藏欄位」,不是「只能有兩個欄位」。**(驗證方式:程式碼審查/靜態分析,非執行期黑盒測試——本 AC 斷言的是「不存在」,無法透過執行期觀察窮舉證明。)**
- **AC-2**: **GIVEN** 任一具游標目標的 UI 表面組合已掛載(棋盤格、關係圖迷你地圖等),**WHEN** 檢視連續任一影格(**含未初始化狀態**,見 States and Transitions 與 AC-15),**THEN** 跨全部表面加總,恰有一個 **hover/游標高亮**存在,不為 0 也不為 2(或以上)。**範圍澄清**:此處「高亮視覺」specifically 指本系統仲裁的 hover/游標高亮,不含下游系統自行維護的釘選/多選標記視覺(見 Core Rules #7 範圍界定)——釘選標記可與 hover 高亮同時存在多個,不違反本不變式。
- **AC-3**: **GIVEN** 滑鼠懸停/移動與 d-pad/類比搖桿導覽兩種輸入來源,**WHEN** 分別觸發有效輸入,**THEN** 兩者皆呼叫同一個寫入介面更新同一個狀態物件——不存在任一輸入來源繞過寫入介面、直接改變某表面已渲染高亮的路徑。**(驗證方式:程式碼審查/靜態分析為主;執行期測試僅能驗證「有」繞過路徑的反例存在與否,無法窮舉證明「不存在」。)**
- **AC-4**: **GIVEN** 棋盤格與關係圖迷你地圖(或任兩個具游標目標的獨立 UI 表面)同時掛載,**WHEN** 對其中一表面產生有效輸入,**THEN** 另一表面上原本顯示的高亮立即消失——證明兩表面共享同一狀態源,而非各自獨立維護高亮邏輯。
- **AC-5**: **GIVEN** 一個新增、先前不存在的第三方 UI 表面(例如卡牌選取)透過本系統的共用讀寫介面接入其**單一 hover/游標目標**,**WHEN** 對該表面產生有效輸入,**THEN** 該表面的 hover 高亮正確參與 AC-2 的單一高亮不變式,且不需要修改本系統本體程式碼——驗證 Core Rules #7(應用範圍一般化)未被綁死在棋盤格。**範圍排除**:若該表面另外維護多選/釘選集合(例如關係圖迷你地圖的多選釘選,見 Core Rules #7 範圍界定),該集合本身不屬於本系統管轄範圍,不受本 AC 保證涵蓋,新增或修改該集合的邏輯不算違反「不需修改本體程式碼」。

### B. Device Authority Determination

- **AC-6**: **GIVEN** 一個原始輸入事件尚未對應到任何 `ui_*` action(例如滑鼠 `InputEventMouseMotion` 未觸發任何映射動作),**WHEN** 該事件被引擎處理,**THEN** 裝置權威與游標目標皆不變——原始輸入事件本身不足以觸發權威轉移。
- **AC-7**: **GIVEN** 同一實體裝置在事件流中的裝置 ID 發生變化(模擬 Godot 4.7 裝置 ID 重新編號情境),**WHEN** 該裝置持續產生同一類別的 `ui_*` action,**THEN** 裝置權威不因裝置 ID 改變而發生非預期的轉移或狀態重置——判定依據僅為 `ui_*` action 的來源裝置類別,不含裝置 ID。
- **AC-8**: **GIVEN** 一個非使用者直接操作的來源注入了合成滑鼠事件(例如 Steam Input 或觸控板模擬),**WHEN** 該注入未實際觸發對應的 `ui_*` action,**THEN** 裝置權威不轉移給該來源。
- **AC-9**: **GIVEN** 裝置 A 剛產生 `ui_*` action 取得權威,**WHEN** 在裝置 B 產生下一個 `ui_*` action 之前經過任意長時間、或裝置 A 停止產生任何輸入,**THEN** 裝置權威持續維持為 A——不存在逾時或閒置自動釋放權威的行為。**(驗證方式:優先以程式碼審查確認實作中不存在逾時/倒數計時器邏輯;若採執行期測試,建議以模擬至少 10,000 個影格、裝置 B 全程無輸入為操作化下限,確認裝置權威持續為 A 作為通過條件——「任意長時間」本身不可窮舉驗證,以此為可執行的下限替代。)**

### C. Handoff Continuity & Visual Suppression

- **AC-10**(2026-08-04,`/design-review` 完整模式審查後重寫,原版本未區分 B 裝置類型,與 Core Rules #4 的滑鼠暫態繼承邏輯矛盾,由 game-designer 審查發現): **GIVEN** 裝置權威從 A 轉移到 B 的觸發影格,且 **B 為鍵盤/手把**,**WHEN** 檢視該影格結束時的游標目標值,**THEN** 其與轉移前最後一次由 A 寫入的值完全相同——不重置為任何預設格或空值。**範圍排除(B 為滑鼠的情境)**:若 B 為滑鼠,依 Core Rules #4 的一般化說明,滑鼠取得權威的同一個 `ui_*` action 本身帶有螢幕座標推導出的目標位置,交接觸發影格結束時的游標目標值應等於滑鼠當下懸停目標,而非 A 最後寫入的值——此情境不受本 AC 約束,見 AC-10b。
- **AC-10b**(2026-08-04 新增,涵蓋 B=滑鼠情境): **GIVEN** 裝置權威從 A 轉移到滑鼠(B=滑鼠)的觸發影格,**WHEN** 檢視該影格結束時的游標目標值,**THEN** 其等於滑鼠取得權威的同一個 `ui_*` action 所推導出的懸停目標——不殘留 A 的舊值超過該觸發影格本身。
- **AC-11**: **GIVEN** 裝置權威剛從 A 轉移到 B,**WHEN** 檢視下一個渲染影格,**THEN** A 對應的原生高亮/焦點視覺已被抑制不再顯示,即使 A 之後持續產生非 `ui_*` 的原生訊號(例如滑鼠持續移動但未觸發新的 `ui_*` action)。
- **AC-12**(2026-08-03,qa-lead 審查後重寫,原版本未定義「影格」與「正確反映」的可觀測基準,不可測): **GIVEN** 裝置權威轉移事件發生的影格(定義:以視覺影格——即引擎每次 `_process` 邏輯更新週期——計數,轉移影格 = 該次 `_process` 迴圈內偵測到新裝置 `ui_*` action 觸發的影格),**WHEN** 量測新裝置對應高亮節點的可觀測渲染屬性(例如 `visible` 或 `modulate.a`)翻轉為呈現新權威狀態的影格,**THEN** 兩者相差 ≤ `max_handoff_visual_latency_frames`(見 Tuning Knobs,目前定案值 1)個影格——以明確的節點屬性變化作為量測依據,不依賴主觀肉眼判斷。
- **AC-13**(2026-08-04 修訂,移除主觀措辭,回應 qa-lead 審查發現): **GIVEN** 裝置權威剛轉移到 B 且游標目標已依 AC-10 承接舊值,**WHEN** B 隨後產生一個帶有明確新目標的 `ui_*` action(例如手把方向鍵移動),**THEN** 游標目標欄位的值於該次輸入的同一影格內,立即等於 B 該次 `ui_*` action 所指定的新座標值,不停留在繼承自 A 的舊值、不延遲到下一影格才更新——繼承規則只作用於交接觸發影格本身,不會持續阻擋新權威裝置後續影格的操作。
- **AC-14**(2026-08-04 第五輪補充「有效」定義的裝置別差異,回應 qa-lead 審查發現的隱性歧義): **GIVEN** 裝置 A 失去權威且其視覺被抑制(AC-11),**WHEN** A 之後再次產生一個有效的 `ui_*` action,**THEN** A 依 Group B 的一般規則重新取得權威且視覺恢復顯示——先前的視覺抑制不會遺留任何狀態,阻止 A 之後正常取回權威。**「有效」的定義依 A 的裝置類別而異,不是單一標準**:若 A 為滑鼠,「有效」指累積淨位移已達 Core Rules #3 空間門檻(見 AC-28、AC-28b);若 A 為鍵盤/手把,「有效」指任一 `ui_*` 導覽動作本身,不需額外累積門檻(見 Core Rules #3 反方向段落、AC-34、AC-34b)——本 AC 驗證兩種裝置類別重新取得權威後視覺恢復的共同行為,門檻是否達標的判定由對應的 AC 群組驗證,不在本 AC 重複驗證。

### D. Initial State

- **AC-15**(2026-08-03,qa-lead 審查後補強,原版本未鎖定高亮是否實際顯示,與 AC-2 的恆一不變式產生落實缺口): **GIVEN** 一個純手把 session,自畫面載入以來尚未有任何裝置產生過 `ui_*` action,**WHEN** 查詢游標狀態,**THEN** 目前游標目標等於呼叫方(戰棋移動與交戰系統)指定的可操作單位所在格,裝置權威欄位標示為未初始化(不指向任何已生效裝置),且此讀取過程未讀取任何裝置的原生 hover 位置作為判斷依據。**且對應的高亮視覺已顯示於該目標**——不存在「目標值已設定但高亮尚未顯示」的過渡窗口;呼叫方須保證在需要游標的畫面首次可互動前,初始目標已透過本系統的寫入介面設定完畢,此為規範行為(見 States and Transitions 表的未初始化狀態列)。
- **AC-16**: **GIVEN** 系統處於未初始化狀態(AC-15),**WHEN** 任一裝置(滑鼠或鍵盤/手把)產生第一個 `ui_*` action,**THEN** 系統立即離開未初始化狀態,依該裝置類別進入對應的權威狀態,後續行為依 Group B/C 的一般規則運作。

### E. Edge Case Coverage

- **AC-17**: **GIVEN** 手把持有權威並持續產生方向輸入,滑鼠同時完全靜止(無移動、無點擊),**WHEN** 檢視連續多個影格的裝置權威欄位,**THEN** 該欄位維持為手把——滑鼠僅「停留」在畫面某處不觸發權威轉移或游標目標變更。
- **AC-18**: **GIVEN** 滑鼠目前持有權威,**WHEN** 滑鼠游標移出遊戲視窗邊界(不論之後是否移回),**THEN** 游標目標與裝置權威維持在移出視窗前最後一次有效 `ui_*` action 的值,不清空、不跳到預設值,視窗外的滑鼠移動不產生任何狀態變更。
- **AC-19**: **GIVEN** 滑鼠懸停於非合法游標目標區域(例如 UI 面板本身或棋盤外空白處),**WHEN** 滑鼠在該區域內持續移動(不論產生多少次原生移動事件),**THEN** 游標目標與裝置權威保持不變,直到滑鼠移回合法區域並產生對應的有效 `ui_*` action 為止。
- **AC-20**(2026-08-04 第二次修訂,統一驗證標準,回應 qa-lead 審查發現的內部不一致;2026-08-04 第八輪修訂 THEN 子句;**2026-08-05 第九輪修訂適用範圍,回應 systems-designer 審查發現的真矛盾——原版本的 GIVEN 未限定鍵盤/手把該次事件是否具備主張權威的資格,若鍵盤/手把該次僅產生確認類動作,依 Core Rules #3「確認類動作與裝置權威的關係」的範圍澄清,母規則根本不適用於該情境,本 AC 與 Core Rules #3、AC-35 曾各自斷言相反結果,已修正為本 AC 僅適用於雙方事件皆具權威資格的情境**): **GIVEN** 滑鼠與手把在同一影格內皆產生對應的 `ui_*` action,**且鍵盤/手把該次動作為導覽類(具備主張裝置權威的資格,見 Edge Cases 母規則「適用範圍」)**,**WHEN** 該影格處理完畢,**THEN** 最終的裝置權威為**鍵盤/手把**,不論滑鼠事件是否在引擎內部被視為同幀內較晚處理,游標目標同時等於該導覽動作所指定的新值。**範圍排除(鍵盤/手把該次僅產生確認類動作的情境)**:若鍵盤/手把該次動作為確認類或其他非導覽類動作,該動作不具備主張裝置權威的資格,本 AC 不適用於此情境——裝置權威判定改依 AC-35 驗證(確認類動作不轉移裝置權威)。**滑鼠奪權累積量的重置行為(不限動作類型皆須重置)由 AC-35b 驗證,不在本 AC 重複驗證。**驗證方式:以程式碼審查為主**——確認判定邏輯是否真的無條件優先鍵盤/手把、且不依賴任何引擎內部事件處理順序或到達順序(此為規則本身的確定性保證,不隨執行次數改變),另須確認判定邏輯正確排除確認類動作不落入本規則仲裁範圍。**執行期測試作為輔助佐證(2026-08-05 第九輪修訂,回應 qa-lead 審查發現——原版本以相同輸入序列重複執行 20 次,對決定性實作沒有額外資訊量,因為固定優先序判定不依賴到達順序,重複相同序列無法驗證「不依賴到達順序」這件事本身)**:以**模擬測試框架控制、逐次刻意變動滑鼠與鍵盤/手把事件到達緩衝區順序**的輸入注入序列,重複執行至少 20 次,確認每次判定結果皆為鍵盤/手把勝出、100% 一致——變動到達順序才能實際佐證「判定不依賴到達順序」的宣稱,單純重複相同序列的佐證力極低,僅作為程式碼審查結論的交叉驗證,不取代程式碼審查。**延伸(連續多影格情境)**:**GIVEN** 此雙裝置同幀觸發情境於連續 10 個以上影格重複發生,**WHEN** 檢視逐影格的裝置權威判定結果序列,**THEN** 每一影格皆為鍵盤/手把勝出,不因連續發生而產生任何滑鼠意外奪權的影格——與上方單幀情境採用相同的驗證標準(程式碼審查為主,執行期測試為輔佐證),不再是兩套不同標準。
- **AC-20b**(2026-08-05 第九輪新增,回應 ui-programmer 審查發現的相鄰缺口,見 Core Rules #3「同一裝置類別內多個 `ui_*` 動作同影格並存的優先序」): **GIVEN** 同一影格內鍵盤/手把產生兩個 `ui_*` 動作——一個導覽類(改變游標目標)、一個確認類(讀取目前游標目標作為確認/選定對象),**WHEN** 緩衝後統一裁定,**THEN** 確認類動作讀取到的游標目標,是導覽類動作套用後的最新值,不是該影格開始前的舊值——確認同一裝置類別內的寫入類事件先於讀取類事件生效,避免確認動作誤讀到本影格已過期的目標。
- **AC-21**: **GIVEN** 手把持有權威期間發生斷線,**WHEN** 檢視斷線事件發生後的下一個影格,**THEN** 游標目標與裝置權威與斷線前最後一次有效值完全相同,對應的高亮視覺持續顯示於原位置,不消失、不重置為預設值。
- **AC-22**: **GIVEN** 手把已斷線且系統維持斷線前狀態(AC-21),**WHEN** 滑鼠之後產生一個有效的 `ui_*` action,**THEN** 裝置權威依 Group B 一般規則轉移給滑鼠,並依 Group C 一般交接繼承規則承接斷線前的游標目標;若斷線後始終無任何裝置產生新輸入,游標狀態持續保持靜止不變。
- **AC-23**: **GIVEN** 游標持有特定目標與裝置權威時遊戲進入暫停選單或彈出對話框,**WHEN** 玩家關閉選單/對話框返回原畫面,**THEN** 游標的裝置權威與目標值與進入暫停前完全相同,不因暫停期間任何背景輸入訊號或選單內部操作(例如選單內以手把導覽選項)而被竄改。
- **AC-24**(2026-08-04 修訂,涵蓋新增的「標記失效」介面): **GIVEN** 游標目前指向的目標本身失效,且沒有任何呼叫方系統呼叫「標記目前目標為待重新解析」或「設定新目標」介面,**WHEN** 查詢游標狀態,**THEN** 目前游標目標的座標值與有效性旗標皆維持失效前的原始值不變——系統不自動清空、不拋出例外、不自動重新解析成其他目標。
- **AC-25**(2026-08-04 修訂,移除主觀措辭,回應 qa-lead 審查發現): **GIVEN** 游標目前指向的目標已失效(AC-24 情境),**WHEN** 呼叫方系統(例如戰棋移動與交戰系統)主動呼叫本系統的「設定新目標」介面,**THEN** 游標目標欄位的座標值立即等於呼叫方傳入的新目標值、有效性旗標立即翻回有效,且此後任何時間點查詢游標狀態、或任一掛載的 UI 表面渲染,皆讀取到此新值與有效旗標,不殘留失效前的舊座標值或無效旗標——確認委派給呼叫方的解決路徑本身可被驗證地正常運作,而非僅止於假設可運作。

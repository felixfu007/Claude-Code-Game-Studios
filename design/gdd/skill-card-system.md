## Overview

每隔固定回合數,玩家必定拿到一張「好感度對話卡牌」。牌上是一組角色關係的互動選項——打出它,就改變某一對角色之間的好感度,而好感度直接進傷害公式,所以這是一個戰術決定。但它同時是一個敘事決定:同一次選擇也會牽動這兩個角色之後的劇情走向。玩家永遠可以選擇**不打**,也永遠自己決定**作用在哪一對關係上**。

**本系統是本作核心支柱的其中一半。** 角色本身的數值不足以過關,差距要靠好感度佈局的加成與卡牌效果補足——好感度—位置連鎖系統負責前者,本系統負責後者。

🔴 **本系統含全作唯一允許隨機的地方,而它的界線是刻意畫的:發牌節奏固定、牌面隨機。** 每 N 回合必定發一張牌,隨機的只有「這張牌提供哪些選項」。**隨機絕不進入結算**——牌一旦攤開,它的每個選項會造成什麼後果都完全可推算,沒有骰子、沒有機率。這同時保住兩件看似衝突的事:戰鬥層 100% 資訊透明,以及每一場戰鬥的牌面組合不重複。
(界線的來源:creative-director 裁決,2026-07-29 第三輪,`game-concept.md` 核心機制節。專案級禁令 `rng_in_combat_settlement` 明訂結算路徑不得使用 RNG,本節所述的牌面隨機即該禁令唯一的明文豁免。)

**在系統層,本系統是好感度數值池的三個寫入來源之一**(`combat_card`,另兩者為 `support_conversation`、`story_event`)。它**不持有**好感度數值,只產生寫入記錄;數值的儲存、時近性衰減與讀取全歸好感度數值池。卡牌也**不作為單位死亡的載體**——它代表技能與事件觸發,獨立於棋子本身(`game-concept.md` 機制 2)。

**實作契約見三份已核准的 ADR,本文件不重述其技術細節**(重述會製造漂移面,是本專案已記載的失效模式):

| ADR | 狀態 | 它對本系統的實際約束 |
|---|---|---|
| ADR-0001 戰棋查詢介面原子性契約 | Accepted | 卡牌效果的執行時機受結算步邊界約束——需玩家選對象的輸入須在結算**開始前**完成 |
| ADR-0002 好感度數值池資料結構與並發契約 | Accepted | 寫入介面的形狀與並發規則;本系統只呼叫,不自行定義 |
| ADR-0005 單一游標/高亮狀態系統 | Accepted | 卡牌介面的選取視覺**必須**走單一游標狀態源,**不得**使用引擎原生 Control focus/hover |


## Player Fantasy

**目標感受:「這一手打得漂亮。」**

這是一個**打起來爽快**的系統。手上有牌,盤面有解,你看得到那個解 —— 甲的傷害預覽從 4 跳到 7,眼前那個原本殺不掉的敵人這回合就倒了。**沒有骰子、沒有意外,爽快感完全來自你算對了。**

⚠️ **語域界線(2026-09-08 管理者裁決)**:**戰鬥層的情感是爽快,與劇情無關。** 本作核心幻想節那種「把每一題都算對了,卻仍眼睜睜看著關係磨損」的清醒感屬於**劇情層**,不得搬進本系統的戰鬥體驗。兩層各自成立,不互相稀釋。

**關鍵時刻**:敵方遠程單位剛移進射程,下一回合會打到殘血的丙。你手上還有兩張牌:一張讓甲這回合攻擊力上升、一張暫時把丙丁的負關係當成正的。你算了一下 —— 用第一張,甲這回合能殺掉那個遠程;用第二張,丙站到丁旁邊能多撐一擊。**兩張都有用,而你只來得及用一張。** 你選了殺掉威脅,丙這回合安全了。下一回合你手上補進一張新牌,盤面又不一樣了。


⚠️ **本例有一半在 MVP 範圍內,一半不在**(2026-09-08 二次裁決後更新):例中第一張牌(甲攻擊力上升)屬**甲類**,**MVP 實作**;第二張(暫時把丙丁的負關係當成正的)屬**乙類**,**MVP 不實作**。因此本例描述的「兩張都有用,而你只來得及用一張」這個取捨結構,在 MVP 會以「兩張甲類牌」或「一張甲類 + 一張丙類」的形式出現,而不是原例的甲+乙。**MVP 驗收不得以本例逐字為基準**,驗收基準見 Acceptance Criteria。

**牌是會用完的資源,而補充速度是固定的。** 開局給你一手,之後每回合只補一張。前期把牌花光很痛快,但盤面到後期一定會出現你沒預料到的變數 —— **那時候手上有沒有牌,是你前面自己決定的。** 這是這個系統真正的難度所在:不是單張牌怎麼用,是整場戰鬥的節奏怎麼分配。

📌 **稀缺是時間上的,不是數量上的**(2026-09-08 管理者裁決,更正撰寫期一次方向性誤判):本系統的張力**不是**「牌太多所以沒有取捨」,而是**每回合只補一張,前期亂花的人在後期翻不了身**。任何對發牌節奏或手牌規則的調整,都要回頭檢查這一條是否還成立。

**絕大多數的牌只影響一、兩回合。** 它們是戰術工具,用完就過去了。**但有少數幾張會永久改變兩個角色之間的關係** —— 而那少數幾張,是這個系統與劇情唯一的接點。

🔴 **這種牌必須看得出來不一樣**(管理者裁決的具體手段):用**文字說明**、或用**不同的卡牌邊框**,暗示玩家這一張會造成長遠影響。系統不說它會導向什麼結果,只讓玩家知道**這一張會留下來**。

**關係是角色與角色之間的,不是玩家與角色之間的。** 玩家安排的是這五個人彼此的羈絆與嫌隙 —— **戰友情誼,不是戀愛**(`game-concept.md` 反支柱節明文:「好感度系統刻意限定為羈絆/戰友情敘事」)。配對的定義本身就是「5 名固定角色中的其中兩人」,**玩家不在那段關係裡**,結構上不存在「攻略角色」這件事。

**反面感受(必須避免)**:

- 🔴 **「我不知道這張牌會做什麼」** —— 牌一攤開,每個選項的後果都必須完全可推算。**牌面是隨機的,結算永遠不是。** 這是本作零隨機承諾在卡牌層的兌現。
- **「我沒得選」** —— 若某一回合手上的牌對當前盤面全部無用,爽快感當場變成無力感。發牌內容的設計必須讓「至少有一個有意義的選項」成為常態,而不是碰運氣。
- **「原來那張會留下來,我不知道」** —— 會永久改變關係的牌若沒有被清楚標示,玩家會在不知情的情況下動到劇情。**標示是硬性要求**(見上方),且依 `game-concept.md` 第七輪裁決須明示「此牌的敘事影響小於戰場影響」,不得讓玩家誤以為兩者等重。

**與敘事的連結**:玩家打牌的動機幾乎總是戰術性的 —— 他要那 3 點傷害。而那少數幾張永久牌,會把這些純戰術的決定累積成一種關係的形狀,那個形狀決定了故事怎麼收。**重量不在某一張牌上,在那一疊牌加起來的樣子。**


## Detailed Design

### Core Rules

#### 一、卡牌效果的三類框架

🔴 **本節定義的是框架,不是完整卡表。** 個別卡牌可以推翻下方的預設規則 —— 這是刻意保留的設計餘裕(2026-09-08 管理者裁決,原話:「這邊不能寫死」)。

| 類別 | 效果性質 | 是否寫入好感度數值池 | MVP 是否實作 |
|---|---|---|---|
| **甲類:暫時性戰鬥數值** | 改變單位的戰鬥數值,**持續 1~2 回合** | ❌ 不碰 | ✅ **MVP 實作,但只限 ATK / DEF 兩項**(見下方③) |
| **乙類:暫時性關係極性覆蓋** | 計算位置加成時,**暫時**把某對關係的極性當成相反的(例:負關係當成正的),**關係本身不變** | ❌ 不碰 | ❌ 定義不實作 |
| **丙類:永久好感度寫入** | 永久改變兩個角色之間的關係 | ✅ 寫一筆記錄(`source=combat_card`) | ✅ **MVP 實作** |

**絕大多數卡牌屬甲/乙類(暫時性);丙類是少數**(2026-09-08 管理者裁決)。

#### 一之二、🔴 MVP 範圍於 2026-09-08 二次裁決擴大:甲類納入

**本節的裁決推翻了同日較早的「MVP 只實作丙類」。** 保留原委的理由是它解釋了三個下游數字為何長這樣:

**① 撤銷的原因(查證發現,不是偏好改變)**:加成公式的實作(`src/gameplay/affinity/affinity_rules.gd` 的 `delta()`)只吃**極性**(正/負)、**距離**、**倍率 `amp`**(恆為 1)三項,**完全不讀好感度的數值大小**。因此丙類卡牌對傷害的影響**只有在它把某段關係的正負號翻過來時才非零**;任何「讓已經是正向的關係更好」的寫入,對 `Φ` 的改變**剛好是 0**。垂直切片只有 2 條關係線(甲乙正、丙丁負),而「丙丁對立」是 Canon level `Established` 的角色設定(三輪裁決),**不該由一張牌翻掉**。**淨結果:純丙類的 MVP,卡牌在戰鬥中實質無效。**

**② 它同時撞倒三件已定案的事**,故不是可以帶著走的小瑕疵:
- 支柱明訂「差距要靠好感度佈局的加成**與卡牌效果**補足」(`game-concept.md`,管理者原話)。前半已在可玩版本中運作,後半在純丙類 MVP 下不存在。
- 本節自己寫「丙類是**少數**」,但純丙類 MVP 的牌堆會是 100% 丙類。
- Player Fantasy 寫「絕大多數牌只影響一、兩回合,少數幾張才永久」;純丙類下**每一張都永久**,而一場戰鬥會抽 9~11 張(開局 5 + 每回合 1 × 4~6 回合),全部永久寫入好感度並餵給結局判定。

**③ 裁決:甲類納入 MVP,但範圍收窄為 `ATK` / `DEF` 兩項數值,不含移動力。**
- **不含移動力是刻意的**,理由是上游 OQ-4 未關的那一半:「額外移動力」在雙旗標行動經濟下是「補 MP」還是「重置移動旗標」尚未定案。**把移動排除在 MVP 外,等於不必現在回答它** —— 這是範圍決定,不是遺漏。
- **甲類完全不碰好感度數值池**,故不受 append-only 與「無期限概念」的限制,乙類那個困難在甲類身上不存在。
- **丙類維持實作,並回到「少數」的定位** —— 它是本系統與劇情唯一的接點,不是主要的戰鬥手段。

**為什麼乙類不能用寫入實現**:好感度數值池是**只增不減**(append-only)的記錄表,且全文**沒有「暫時」或「期限」這個概念**(2026-09-08 實測:`design/gdd/affinity-data-pool.md` 對「暫時/期限/失效」零命中)。若乙類去寫入,那筆記錄會永久留著,就不叫暫時。**因此乙類是讀取時的覆蓋,不是寫入** —— 玩家的關係沒有真的變好,是這幾回合戰場上表現得像變好了。

⚠️ **乙類需要一個尚不存在的介面(已登記於 Open Questions)**:位置加成公式 `Φ = Σ amp_i × B(極性_i, 距離_i)` 屬於**已核准**的好感度—位置連鎖系統,而「暫時覆蓋極性」需要本系統向它注入一個覆蓋值。**該介面不存在,且不得由本系統單方面新增。** MVP 不實作乙類,故此事**不阻擋**;實作前須雙方同意。

#### 二、發牌與手牌

| 規則 | 值 |
|---|---|
| 開局手牌 | **5 張** |
| 補牌 | **每回合開始補 1 張** |
| 手牌上限 | **5 張**。滿手時仍補牌,但**強制玩家棄一張**(可棄新抽的、也可棄原本手上的 —— 選擇權在玩家,系統不代為決定) |
| 每回合出牌數 | **不限** |
| 戰鬥結束 | **未打完的牌全部收回,退回卡池,不帶到下一場戰鬥** |

**「至少發牌 3 次」的硬性約束已滿足且有餘裕**:每回合都補牌,而典型戰鬥為 4~6 個玩家回合(`vertical-slice-level-01.md` 三處明載,查法:`grep -n "回合" design/gdd/vertical-slice-level-01.md`)。最短情境(4 回合)發牌 4 次,超過下限 3 次。**這條約束不再是限制因素。**

🔴 **「戰鬥結束收回」是繼承義務 2 的滿足手段,不可省略。** 該義務要求防止玩家囤牌至戰役尾聲一次打出以規避時近性衰減。數學依據:好感度讀值為 `Σ m_i·λ^(t_query−t_i)`,而囤積 K 張一次打出相對於分散打出的讀值放大倍數 ≈ `Σ_{j=0}^{K−1} λ^j`,在 λ∈[0.90,0.98] 下約為 4.1~4.8 倍(K=5)。**亦即手牌能囤幾張,放大倍數就大約是幾倍。** 戰鬥結束收回把囤積的作用範圍**限制在單場戰鬥內**,跨戰役囤積在物理上不可能。**牌不會消失** —— 退回卡池後未來仍可能抽到。

#### 三、隨機的界線

**隨機只發生在一個地方:這次補牌從卡池裡抽到哪一張。**

牌一進手,它的全部內容(效果類別、幅度、可作用對象)**完全確定、公開、可推算**。沒有任何「打出後才知道」的成分。**結算路徑零 RNG**(專案級禁令 `rng_in_combat_settlement`)。

**保底規則(防「我沒得選」)**:必須存在保底機制,使「手上的牌對當前盤面全部無用」不成為常態。具體形式待卡表設計時定案,但**保底規則本身必須完全公開** —— 玩家可以知道規則、可以推算。**規則透明本身即是資訊透明的一部分**,比純隨機更可推算。

#### 四、打出流程(滿足繼承義務 1 的關鍵)

打牌是**獨立的自由動作**,不消耗移動或攻擊旗標,僅限玩家自己的回合。流程分四步:

1. **開啟手牌** —— 純唯讀,無任何寫入
2. **選牌** —— 選定後系統立即算出合法作用對象集合
3. **選作用對象** —— 玩家從合法集合中選定
4. **確認** —— 顯示效果內容與(若為丙類)永久標示,玩家確認後**同步執行完畢**

第 2~4 步任一時點皆可取消,取消不產生任何寫入。

🔴 **打牌與戰棋結算互斥,這是結構性保證而非紀律要求**:結算進行中(`settlement_in_progress`)不得開啟打牌介面;打牌介面開啟中不得發起攻擊。兩者結構上不可能同時存在,**因此「結算跑到一半才回頭要玩家選作用對象」在本設計下不可能發生**。此互斥沿用 ADR-0001 / AC-24 既有的「結算進行中拒絕其他操作」機制,**不新增機制**。

✅ **本系統據此確認可滿足 `tactical-combat-system.md` Core Rules #11 + AC-24 的同步契約,不需要修訂上游。**
🔴 **須由兩側各自記錄,不得單方面記帳** —— 單方面替他人記帳是本專案已發生兩次的失效模式(`docs/consistency-failures.md` 模式 G)。

⚠️ **關閉的只有上游 OQ-4 的一半,不是整條(2026-09-08 自我更正)。** 本節原文寫「OQ-4 由此關閉」,查證後不成立 —— 該項有**兩個獨立的問題**,而本節只回答了後加的那一個:

#### 五、`amp`(關係強度倍率)—— MVP 不修改

**`amp` 恆為 1。** 本系統擁有它的量化權(繼承義務 3),而 **MVP 的答案是「不做量化」** —— 上方三類效果中沒有任何一類修改倍率。

✅ **因此 `phi_max`(+12)與 `phi_min`(−4)不需要重算**,`design/registry/entities.yaml` 兩條「對話卡牌加乘系統定案後必須重算」警語可結案。

🔴 **但結案的方式是寫下觸發條件,不是刪掉警語**:**若未來新增任何會修改 `amp` 的卡牌,`phi_max` / `phi_min` 必須在同一次變更中重算。** 算式為 `phi_max = 4 × amp_max × (+3)`、`phi_min = 4 × amp_max × (−1)`,其中 **`4` 是幾何事實** —— 曼哈頓距離恰為 1 的格子只有 4 個(棋盤為正交四鄰),故同時享有「緊鄰」加成的線最多 4 條。框架允許這種卡牌存在,但它會連帶推翻兩個已登記的邊界值,**而那兩個值直接進傷害公式**(`max(0, atk − def + Φ)`)。

⚠️ **上式的 `4` 不是「每角色關係線上限」,兩者長得一樣但意思相反,寫錯會推導出錯的邊界值**(2026-09-08 自我更正):關係線數量**不設上限**(2026-08-31 管理者裁決:不讓數值設計限制敘事),第 5 條以上的線合法且會計入 `Φ`,只是拿不到緊鄰的最高加成。`design/registry/entities.yaml` 的 `affinity_links_per_character_max` 條目已因此 `status: retracted`,而兩個夾限值的推導依據已於 2026-09-01 稽核改寫為上述幾何事實。**本行原文沿用了那個已撤銷的前提** —— 若照原文重算,只要卡表允許某角色多於 4 條線,算出的上界就會虛高。


### States and Transitions

本系統有兩組互不相干的狀態,**不共用生命週期**:

**① 一張牌的位置**:`卡池 → 手牌 →(打出|棄掉)→ 卡池`。牌**永不銷毀** —— 打出與棄掉都是退回卡池,未來仍可能再抽到(Core Rules 二)。戰鬥結束時手上所有牌一併退回卡池。

**② 一個甲類修正的存續**:`生效中(r=2)→ 生效中(r=1)→ 已移除`。遞減與移除皆發生於玩家回合開始時,詳見公式二。丙類**沒有**這組狀態 —— 它寫完那一筆就結束了,後續全歸好感度數值池管。

🔴 **兩組狀態都不是「打牌介面」的狀態。** 打牌介面本身的四步流程(開手牌 → 選牌 → 選對象 → 確認)在 Core Rules 四,而**它整段是零寫入的**:上述①②的任何轉換只發生在第 4 步確認之後。第 2~3 步取消不留任何痕跡。**把介面狀態與資料狀態混成一台狀態機,會讓「取消」變成需要回滾的操作** —— 本設計下它不需要,因為還沒寫。

- **若戰鬥中可手動存檔**:手牌內容與生效中的甲類修正**必須**進入存檔,否則有兩個後果 ——

## Formulas

### 公式一:甲類的有效戰鬥數值

`ATK_eff(u) = max(0, ATK_base(u) + Σⱼ Δatkⱼ)`  ,  `DEF_eff(u) = max(0, DEF_base(u) + Σⱼ Δdefⱼ)`

`j` 遍歷單位 `u` 身上所有**仍生效**的甲類修正(存續規則見公式二)。

| 變數 | 符號 | 型別 | 值域 | 說明 |
|---|---|---|---|---|
| 基準數值 | `ATK_base` / `DEF_base` | int | ≥0 | 我方單位基準值表。🔴 **該表尚不存在** —— `tactical-combat-system.md` OQ-2,2026-09-02 已指派 `systems-designer`,**工作尚未執行** |
| 單卡修正量 | `Δatkⱼ` / `Δdefⱼ` | int | 非 0 | 帶號:正為增益、負為減益。逐卡定義,本文件不寫死 |
| 有效數值 | `ATK_eff` / `DEF_eff` | int | ≥0 | 直接作為戰棋公式一的 `ATK` / `DEF` 輸入 |

🔴 **夾限在 0 是硬性要求,不是保守寫法。** 戰棋公式一的變數表宣告 `ATK`/`DEF` 型別為 `int, ≥0`。若允許 `DEF` 減成負值,`ATK − DEF` 會**大於** `ATK`,亦即一張減益牌能造成比「把防禦完全歸零」還多的傷害 —— 那是公式定義域外的行為,而公式本身不會報錯。**減益超出目標當前防禦力的部分一律浪費,不得溢出成傷害加成。**

✅ **本公式不需要戰棋系統新增任何掛鉤點,上游一字不改。** 戰棋公式一的變數表寫的是「攻擊單位的**當前**攻擊數值」與「目標單位的**當前**防禦數值」—— 甲類改的正是那個「當前」值。三個連帶好處,每一個都是選擇這個位置而非結算步掛鉤的實質理由:

- **傷害預覽自動正確**:預判模式依定義必須讀取即時狀態(上游 Core Rules #10 a),故打出增益後預覽立即反映,不需要第二條路徑。**Player Fantasy 那句「傷害預覽從 4 跳到 7」的機制就是這個**,不是額外功能。
- **防禦增益在敵方回合也生效**:`DEF_eff` 是單位自身的屬性,任何人攻擊他都讀得到。**若改走結算步②a 就做不到** —— ②a 是「本次攻擊的傷害修正」、由**攻擊方**的結算套用,防禦方的增益在那裡無處可放。
- **不觸及 ADR-0001 的原子性契約**:打牌是結算外的獨立自由動作,且打牌與結算結構性互斥(Core Rules 四)。修正值在結算**開始前**即已寫定,①~④全程不變 —— 與上游「`Φ` 取值為快照」是同一個形狀,不是新的例外。

⚠️ **上游既有的②a 與②c 兩個掛鉤點在 MVP 皆無內容**:②a 是「本次攻擊的傷害修正」,②c 是「以致死預測為條件的效果」,兩者都不是甲類的形狀。**保留但暫無觸發,不是矛盾**(比照 Core Rules 四對②c 的同型聲明)。

### 公式二:甲類修正的存續與到期

每個甲類修正攜帶剩餘回合數 `rⱼ ∈ {1, 2}`,由卡牌定義。

- **遞減時點**:玩家回合**開始時**,與補牌同一時點,`rⱼ ← rⱼ − 1`;遞減後為 0 者**立即移除,且須在該回合任何查詢之前完成**。
- **語意**:`r = 1` 涵蓋「本回合 + 緊接的敵方回合」;`r = 2` 再多涵蓋玩家的下一個回合。

🔴 **`r = 1` 涵蓋緊接的那個敵方回合,這是刻意的,不是寬鬆。** 若到期發生在玩家回合**結束**時,防禦增益就永遠撐不到敵人動手,在戰術上完全無用 —— 而玩家買防禦的唯一動機就是撐過敵方那一輪。**到期在自己回合開頭而非結束,是這條規則的全部意義所在;改動它等於刪掉整類防禦牌。**

⚠️ **戰鬥結束時所有甲類修正一併清除**(比照手牌收回,Core Rules 二)。甲類不寫入任何持久化資料,**故不需要存檔系統支援** —— 這與丙類相反,見公式三。

### 公式三:丙類的寫入幅度

`丙類打出 → 好感度數值池.附加記錄(配對 p, 幅度 m, 來源 = combat_card)`

| 變數 | 符號 | 型別 | 值域 | 說明 |
|---|---|---|---|---|
| 寫入幅度 | `m` | int | **`{−3, −2, −1, +1, +2, +3}`** | 逐卡定義。🔴 **不得為 0** —— 上游明訂幅度 0 為非法輸入、拋驗證錯誤且不靜默糾正 |
| 作用配對 | `p` | 配對 | **僅限角色設定已存在關係線的配對** | 見下方界線 |

**`m` 為何是 ±3 而不是更大 —— 這是起始值,不是推導結果。** `m` 在**戰鬥**端的作用極其有限:`Φ` 只讀極性正負與距離,**不讀數值大小**(Core Rules 一之二①)。因此 `m` 的尺度應由**敘事**端校準,而敘事端讀值 `Σ mᵢ·λ^age` 再乘來源折扣 `α`,兩個係數目前**都還沒有定值**。選 ±3 的理由是讓單張牌與「緊鄰正向線的單條 `Φ` 貢獻(+3)」同尺度、便於人工對讀。🔴 **它沒有從任何敘事門檻反推**,列入 Tuning Knobs,待 `λ`/`α` 定案後重校。

🔴 **界線:丙類不創造新的關係線。** 可作用配對限於角色設定已有關係線者(垂直切片為甲乙、丙丁兩對)。**理由是繞過這條會靜默推翻一份已核准文件的邊界情況**:好感度—位置連鎖系統明訂「角色沒有任何關係線(如戊):`Φ` **恆為 0,不論站哪**」,而管理者已明確接受「麥子健站哪都一樣」這個玩起來的後果。若一張牌能對(戊, 甲)寫入,戊當場長出關係線,**那條邊界情況與那項裁決同時失效,而兩份文件都不會報錯。** 要放寬須先改 `design/narrative/characters.md`(Canon level `Established`)。

### 公式四:單場戰鬥的抽牌數(供下游校準,非玩法規則)

`抽牌數 = 5(開局) + T`,其中 `T` = 玩家回合數 ∈ [4, 6] → **9 ~ 11 張**。

此數字的用途是兩個下游的輸入,不是玩法設計:①**卡池規模下限** —— 低於此數同一場就會重複到失去意義;②**丙類佔比的上限檢查** —— 若這 9~11 張全屬丙類,一場戰鬥即產生 9~11 筆**永久**好感度寫入,而那些寫入會餵給結局判定的形狀特徵(方向反轉次數、總波動量)。**甲類納入 MVP 之後丙類回到「少數」,此數字才不再是問題** —— 這是甲類納入的第三個理由(Core Rules 一之二②)。

## Edge Cases

| 情境 | 處置 |
|---|---|
| **手牌已滿(5)時補牌** | 仍補,然後**阻塞回合開始直到玩家棄掉一張**。不得由系統代選、不得跳過補牌、不得靜默丟棄新抽的牌 —— 三者都會讓「每回合補一張」這個節奏承諾在滿手時悄悄失效 |
| **卡池張數少於開局手牌數** | 開局發不滿 5 張,**合法且不報錯**(牌不足就是牌不足)。🔴 **但卡表設計須保證卡池 > 11 張** —— 見公式四 |
| **卡池抽空** | 結構上不會發生:打出與棄掉皆退回卡池(States ①),故池中總量恆定。**若實作讓牌消失,此保證即失效** —— 這是一條需要測試守著的不變量,不是自然成立的 |
| **同一單位身上疊多個甲類修正** | **逐條加總**(公式一的 `Σⱼ`),不取最大值、不互斥、不覆寫。與好感度加成的 R4「所有關係線全部生效」同一原則 |
| **減益使 `DEF_eff` 落到 0** | **合法結果,不是錯誤。** 超出的部分浪費(公式一) |
| **甲類修正的宿主單位陣亡** | 修正隨單位一併消失,**不轉移給任何人、不延續**。單位不在場,`ATK_eff`/`DEF_eff` 無查詢對象 |
| **丙類的目標配對有成員陣亡** | 🔴 **必須在「選作用對象」階段就把該配對排除在合法集合外。** 上游明訂陣亡配對的 `combat_card` 來源寫入**一律拒絕並拋驗證錯誤**;若等到確認後才被拒,玩家已經花掉一張牌卻什麼都沒發生。**這不是防禦性程式設計,是合法集合的定義的一部分** |
| **戰鬥結束時仍有生效中的甲類修正** | 一併清除(公式二),不帶到下一場 |
| **打牌介面開啟時敵方回合開始** | 結構上不可能:打牌僅限玩家自己的回合,且與結算互斥(Core Rules 四) |
| 🔴 **好感度數值池正處於「操作進行中」時打出丙類** | **寫入會被上游拒絕**(存檔生命週期權杖機制)。牌已經打出去了,**不得靜默吞掉**。<br>⚠️ 若採納本文件對存檔的建議(戰鬥中禁止手動存檔),此情境**在 MVP 不可能發生**,故本文件不定案其處置 —— 但**該建議一旦沒被採納,這一格就必須先有答案才能實作丙類**。兩者綁在一起,見 Interactions 的存檔段與 Open Questions |

## Tuning Knobs

| 旋鈕 | 值 | 安全範圍 | 調它會連帶影響什麼 |
|---|---|---|---|
| 開局手牌 | **5** | [3, 7] | 與手牌上限綁在一起(滿手開局是刻意的:第一回合就要做取捨) |
| 每回合補牌 | **1** | [1, 2] | 🔴 **改成 2 會推翻「稀缺是時間上的」這條管理者裁決** —— 前期亂花的人就翻得回來了。**不是純數值調整** |
| 手牌上限 | **5** | [3, 7] | 上調會放大囤積讀值(Core Rules 二的 `Σλʲ` 估算);上限幾張,單場內的放大倍數大約就是幾倍 |
| 甲類持續回合 `r` | **{1, 2}** | 逐卡 | 上調會讓「一、兩回合的戰術工具」變成半永久增益,侵蝕 Player Fantasy 的節奏 |
| 甲類修正量 `Δatk`/`Δdef` | 逐卡定義 | 待基準表 | 🔴 **無法在基準表(OQ-2)產出前校準** —— `+3` 對 `ATK=12` 與對 `ATK=30` 是兩種遊戲 |
| 丙類幅度 `m` | **±1 ~ ±3** | 非 0 | **起始值,非推導結果**(公式三)。待 `λ`、`α` 定案後重校 |
| 卡池規模 | 待卡表 | **> 11** | 低於此值單場就會重複(公式四) |

⚠️ **本節有兩項不是「調數值」而是「改設計」**:每回合補牌數與甲類持續回合。兩者各自綁著一條已裁決的體驗承諾,**動它們要回頭改 Player Fantasy,不是改一個常數。**

## Visual/Audio Requirements

- **卡面尺寸須沿用 480×270 套裝的既有規格**,不得自訂 —— 立繪 128×128、64 色、1px 描邊(`design/art/art-direction.md`)。**對話正文用一般繁體中文字型,不是像素字型**(該檔明文裁決)。
- 🔴 **永久牌(丙類)的視覺區別不得只靠顏色。** 須搭配邊框形狀、圖示或文字說明等非色彩通道 —— 此為 `tactical-combat-system.md` UI Requirements 已立、涵蓋「未來修訂新增的每一個狀態區分」的原則陳述,本系統的丙類標示自動落入其涵蓋範圍。
- **甲類生效/到期須有可辨識的瞬間回饋**(打出時、以及到期移除時各一次)。⚠️ **到期那一次特別容易漏掉** —— 它發生在玩家回合開始、與補牌同一時點,兩件事撞在一起。
- **音效不得早於邏輯結算**:比照上游「邏輯狀態為唯一權威,視覺表現不得作為規則判定依據」。動畫播完與否不影響任何數值。

## UI Requirements

🔴 **1. 卡牌介面必須疊在棋盤上方,不得佔用側邊固定欄位。** 這不是偏好,是 2026-09-01 畫面架構裁決導出的硬性約束:世界層取螢幕塞得下的最大整數倍並置中,而**兩種最常見的螢幕(1920×1080、3840×2160)的剩餘邊區為零**。任何「把手牌放在棋盤旁邊」的版面在這兩種螢幕上無處可放。**手牌須為半透明疊層 / 可收合 / 遷入遷出**。

**2. 傷害預覽必須反映生效中的甲類修正。** 打出增益後,預覽數字須立即改變 —— 這是本系統對玩家唯一的「我算對了」的證據(Player Fantasy)。機制上自動成立(公式一),但**須有測試守著**,因為它依賴預判模式讀即時狀態這個上游性質,而那是別人的文件在保證的事。

**3. 手把與十字鍵必須能完整操作手牌,不得有僅滑鼠可達的互動。** 主機無游標(`technical-preferences.md` 平台註記)。選取視覺一律走單一游標狀態源,**不得**使用引擎原生 Control focus/hover(ADR-0005)。

🔴 **4. 同一對角色關係,介面上不得同時呈現兩個好感度數值。** `game-concept.md` 第七輪裁決的 UI 硬性約束(理由:第三輪駁回雙軸分流時的「玩家會困惑哪個才是真的」)。**本系統特別容易違反它** —— 丙類卡牌天然想同時顯示「戰場影響」與「敘事影響」。

**5. 丙類須揭露「此牌的敘事影響小於戰場影響」的定性提示,且不得揭露 `α` 的數值**(同上裁決)。**只揭露事實層**:這一張會留下來。**不揭露它會導向什麼結果。**

**6. 手牌滿時的強制棄牌必須是明確的、阻塞的玩家選擇**,不得做成可忽略的提示。系統不代為決定(Core Rules 二)。

## Acceptance Criteria

**驗收基準是本節,不是 Player Fantasy 的舉例**(該例有一半屬乙類、MVP 不實作)。型別依 `coding-standards.md` 的測試證據表。

| # | GIVEN / WHEN / THEN | 型別 |
|---|---|---|
| AC-1 | 單位身上有兩個甲類修正 `+2`、`+3` → 查 `ATK_eff` → 等於基準 `+5`(**逐條加總,不取最大**) | Logic |
| AC-2 | 單位 `DEF_base = 3`,受 `−5` 減益 → `DEF_eff = 0`,**且該單位受到的傷害不超過 `ATK`** —— 證明減益未溢出成傷害加成 | Logic(邊界) |
| AC-3 | 玩家回合打出 `r=1` 的防禦增益 → **緊接的敵方回合中該增益仍生效** → 玩家下一回合開始後失效 | Logic |
| AC-4 | `r` 遞減至 0 的那個回合 → **該回合第一次查詢 `DEF_eff` 時修正已移除**(不是查完才移除) | Logic |
| AC-5 | 打出 `+3` 攻擊增益 → **傷害預覽數字當場改變 `+3`**,無需任何額外操作或重開介面 | Integration |
| AC-6 | 打出丙類 → 好感度數值池新增一筆記錄,`source` 欄為 `combat_card`、幅度為該卡定義值 | Logic |
| AC-7 | 配對成員已陣亡 → 該配對**不出現在合法作用對象集合中**(不是「選了之後被拒絕」) | Logic |
| AC-8 | 嘗試對無角色設定關係線的配對(如含戊者)作用 → 該配對不在合法集合中;**戊的 `Φ` 在任何丙類打出後仍恆為 0** | Logic |
| AC-9 | 幅度 `m = 0` 的丙類 → 寫入被拒並拋驗證錯誤,**不靜默糾正、不產生記錄、計數器不遞增** | Logic(邊界) |
| AC-10 | 手牌 5 張時回合開始 → 補牌後**回合流程阻塞直到玩家棄掉一張**;系統未代為選擇 | UI |
| AC-11 | 戰鬥結束 → 手牌全數退回卡池、**所有生效中的甲類修正清除**,兩者皆不帶入下一場 | Logic |
| AC-12 | 連續打出並棄掉 20 次 → **卡池 + 手牌的總張數與開局相同**(牌永不銷毀的不變量) | Logic |
| AC-13 | 開手牌 → 選牌 → 選對象 → **在確認前取消** → 好感度數值池筆數不變、無任何甲類修正產生 | Logic |
| AC-14 | 結算進行中(`settlement_in_progress`)嘗試開啟手牌 → **得到明確的拒絕回饋**,不靜默丟棄、不無限期等待 | Integration |

⚠️ **AC-1~AC-4、AC-6~AC-9、AC-11~AC-13 皆為 BLOCKING 級**(Logic 型);AC-5/AC-14 為 Integration 型,同屬 BLOCKING;AC-10 為 UI 型,ADVISORY。

🔴 **AC-2 與 AC-5 是本節最容易寫成「永遠會通過」的兩條**,理由不同:AC-2 若只斷言 `DEF_eff == 0` 就漏掉了「沒溢出成傷害」那一半(那才是它存在的原因);AC-5 依賴上游預判模式讀即時狀態,若測試自己去算一次期望值而不是讀畫面上的預覽,它證明的是算術而非串接。**兩條都須做敏感度證明**(故意改壞程式碼、確認它會轉紅),並注意本專案已記載的陷阱:**一個測試失敗會中止同檔後續測試**,故每條要證明的斷言各需一次執行(`coding-standards.md`)。

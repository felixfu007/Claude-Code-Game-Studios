## Overview

每回合玩家都會拿到一張「好感度對話卡牌」。**牌面永遠是一組具名角色之間的互動**,而效果分兩種:多數牌**暫時改變戰鬥數值**(甲對乙說了句鼓勵的話 → 甲這回合攻擊力上升,持續一兩回合);少數牌**永久改變那兩個角色的關係**。玩家永遠可以選擇**不打**,也永遠自己決定作用在誰身上。

🔴 **兩種效果的分工是本系統最反直覺、也最該先讀懂的一件事**:
**戰鬥數值牌負責戰鬥,永久牌純粹負責劇情 —— 永久牌對傷害的影響是零。**
理由與完整推理見 Core Rules 一之二。**照「打牌改好感度 → 好感度進傷害公式 → 所以是戰術決定」這個直覺去設計卡表或介面的人會做錯東西**,那條鏈在第二步就斷了(傷害只讀關係的正負號,不讀累積多少)。

**本系統是本作核心支柱的其中一半。** 角色數值不足以過關,差距要靠好感度佈局的加成與卡牌效果補足 —— 好感度—位置連鎖系統負責前者,本系統負責後者,而**後者 100% 由戰鬥數值牌兌現**。

🔴 **本系統含全作唯一允許隨機的地方,而它的界線是刻意畫的:發牌節奏固定、牌面隨機。** 隨機的只有「這次補牌抽到哪一張」。**隨機絕不進入結算** —— 牌一攤開,每個選項的後果都完全可推算,沒有骰子、沒有機率。(來源:creative-director 裁決,2026-07-29 第三輪。專案級禁令 `rng_in_combat_settlement` 明訂結算路徑不得使用 RNG,牌面隨機即該禁令唯一的明文豁免。)

**在系統層,本系統是好感度數值池的三個寫入來源之一**(`combat_card`,另兩者為 `support_conversation`、`story_event`)。它**不持有**好感度數值,只產生寫入記錄。卡牌也**不作為單位死亡的載體**(`game-concept.md` 機制 2)。

## Player Fantasy

**目標感受:「這一手打得漂亮。」**

這是一個**打起來爽快**的系統。手上有牌,盤面有解,你看得到那個解 —— 甲的傷害預覽從 4 跳到 7,眼前那個原本殺不掉的敵人這回合就倒了。**沒有骰子、沒有意外,爽快感完全來自你算對了。**

⚠️ **語域界線(2026-09-08 管理者裁決)**:**戰鬥層的情感是爽快,與劇情無關。** 本作核心幻想節那種「把每一題都算對了,卻仍眼睜睜看著關係磨損」的清醒感屬於**劇情層**,不得搬進本系統的戰鬥體驗。兩層各自成立,不互相稀釋。

**關鍵時刻**:敵方遠程單位剛移進射程,下一回合會打到殘血的丙。你手上有兩張牌 —— 一張讓甲攻擊力上升、一張讓丙防禦力上升。你算了一下:用第一張,甲這回合就能殺掉那個遠程,威脅直接消失;用第二張,丙能撐過那一擊,但遠程還在。**兩張都打得起** —— 規則不限出牌數 —— **但打完你下回合就空手**,而盤面還有三個回合。你選了殺掉威脅,留著另一張。下一回合補進一張新牌,而你手上仍有兩張可用。

🔴 **取捨是「現在花掉還是留著」,不是「只能選一個」**(2026-09-08 管理者裁決:維持不限出牌數)。**這一段先前寫成「你只來得及用一張」,那是錯的** —— 規則從未限制每回合出牌數,也不消耗移動或攻擊,玩家可以兩張都打、兩個好處都拿。**取捨仍然存在,但它在時間軸上,不在單一回合內。** 這正是下方「稀缺是時間上的」那條裁決的具體樣貌。

**牌是會用完的資源,而補充速度是固定的。** 開局給你一手,之後每回合只補一張。前期把牌花光很痛快,但盤面到後期一定會出現你沒預料到的變數 —— **那時候手上有沒有牌,是你前面自己決定的。** 這是這個系統真正的難度所在:不是單張牌怎麼用,是整場戰鬥的節奏怎麼分配。

📌 **稀缺是時間上的,不是數量上的**(2026-09-08 管理者裁決,更正撰寫期一次方向性誤判):本系統的張力**不是**「牌太多所以沒有取捨」,而是**每回合只補一張,前期亂花的人在後期翻不了身**。任何對發牌節奏或手牌規則的調整,都要回頭檢查這一條是否還成立。

**絕大多數的牌只影響一、兩回合。** 它們是戰術工具,用完就過去了。**但有少數幾張會永久改變兩個角色之間的關係** —— 而那少數幾張,是這個系統與劇情唯一的接點。

🔴 **這種牌必須看得出來不一樣**(管理者裁決的具體手段):用**文字說明**、或用**不同的卡牌邊框**,暗示玩家這一張會造成長遠影響。系統不說它會導向什麼結果,只讓玩家知道**這一張會留下來**。

**關係是角色與角色之間的,不是玩家與角色之間的。** 玩家安排的是這五個人彼此的羈絆與嫌隙 —— **戰友情誼,不是戀愛**(`game-concept.md` 反支柱節明文:「好感度系統刻意限定為羈絆/戰友情敘事」)。配對的定義本身就是「5 名固定角色中的其中兩人」,**玩家不在那段關係裡**,結構上不存在「攻略角色」這件事。

**反面感受(必須避免)**:

- 🔴 **「我不知道這張牌會做什麼」** —— 牌一攤開,每個選項的後果都必須完全可推算。**牌面是隨機的,結算永遠不是。** 這是本作零隨機承諾在卡牌層的兌現。
- **「我沒得選」** —— 若某一回合手上的牌對當前盤面全部無用,爽快感當場變成無力感。發牌內容的設計必須讓「至少有一個有意義的選項」成為常態,而不是碰運氣。
- **「原來那張會留下來,我不知道」** —— 會永久改變關係的牌若沒有被清楚標示,玩家會在不知情的情況下動到劇情。**標示是硬性要求**(見上方),且依 `game-concept.md` 第七輪裁決須明示「此牌的敘事影響小於戰場影響」,不得讓玩家誤以為兩者等重。

**與敘事的連結**:玩家打牌的動機幾乎總是戰術性的 —— 他要那 3 點傷害。而那少數幾張永久牌,會把這些純戰術的決定累積成一種關係的形狀,那個形狀決定了故事怎麼收。**重量不在某一張牌上,在那一疊牌加起來的樣子。**


## Detailed Design

### Core Rules

#### 一、卡牌效果的三類框架

🔴 **本節定義的是框架,不是完整卡表。** 個別卡牌可以推翻下方的預設規則 —— 這是刻意保留的設計餘裕(2026-09-08 管理者裁決,原話:「這邊不能寫死」)。

| 類別 | 效果性質 | 是否寫入好感度數值池 | MVP 是否實作 |
|---|---|---|---|
| **甲類:暫時性戰鬥數值** | 改變單位的戰鬥數值,**持續 1~2 回合** | ❌ 不碰 | ✅ **MVP 實作,但只限 ATK / DEF 兩項**(見下方③) |
| **乙類:暫時性關係極性覆蓋** | 計算位置加成時,**暫時**把某對關係的極性當成相反的(例:負關係當成正的),**關係本身不變** | ❌ 不碰 | ❌ 定義不實作 |
| **丙類:永久好感度寫入** | 永久改變兩個角色之間的關係 | ✅ 寫一筆記錄(`source=combat_card`) | ✅ **MVP 實作** |

**絕大多數卡牌屬甲/乙類(暫時性);丙類是少數**(2026-09-08 管理者裁決)。
#### 一之二、🔴 兩類效果的分工:甲類負責戰鬥,丙類純粹負責劇情

**這是本系統最重要的一條,因為它與直覺相反:丙類對傷害的影響是零,而那是設計,不是缺陷。**

**推理只有三步**(依據:`src/gameplay/affinity/affinity_rules.gd` 的 `delta()` 只吃極性、距離、`amp`,**完全不讀好感度的數值大小**):

1. 傷害加成只看關係的**正負號**,不看累積了多少。
2. 因此丙類唯一能改變傷害的方式,是把某段關係的正負號**翻過來**。
3. 而 **2026-09-08 管理者裁決:丙類不得翻轉任何角色設定的正負號**(見下方一之三)。

→ **所有合法的丙類寫入都不改變極性,故不改變任何傷害。** 支柱後半「差距要靠卡牌效果補足」**100% 由甲類獨力兌現**。

📌 **撰寫沿革(2026-09-08 同日兩次裁決)**:MVP 原訂只做丙類,查證發現上述推理後改為納入甲類 —— 因為純丙類的 MVP,卡牌在戰鬥中實質無效。**完整原委在 git 提交訊息與 `production/session-state/active.md`,不在本檔累積**(依專案慣例,歷史屬按需查閱)。

**甲類的範圍收窄為 `ATK` / `DEF` 兩項,不含移動力** —— 刻意的:「額外移動力」在雙旗標行動經濟下是「補 MP」還是「重置移動旗標」尚未定案(上游 OQ-4 未關的那一半),排除它等於不必現在回答。**義務未免除,只是延後。**

**為什麼乙類不能用寫入實現**:好感度數值池是**只增不減**(append-only)的記錄表,且全文**沒有「暫時」或「期限」這個概念**(2026-09-08 實測:`affinity-data-pool.md` 對「暫時/期限/失效」零命中)。若乙類去寫入,那筆記錄會永久留著,就不叫暫時。**因此乙類是讀取時的覆蓋,不是寫入。**

#### 一之三、🔴 丙類的四條硬性界線(2026-09-08 管理者四項裁決)

| # | 界線 | 理由 |
|---|---|---|
| 1 | **不得翻轉任何角色設定的正負號** | 甲乙合作、丙丁對立皆為 `characters.md` Canon `Established`(三輪裁決)。⚠️ **管理者裁決的原文只點名丙丁,本文件按對稱延伸至甲乙** —— 同一個洞的反方向(一張夠強的負向牌可把甲乙翻成敵對)。**若只欲禁丙丁一側,須回頭更正本列。** |
| 2 | **卡池中的丙類張數設上限**(具體值待卡表,列 Tuning Knobs) | 這是「丙類是少數」這句裁決唯一會被執行的手段。**它同時是結局判定份量問題的解法** —— 見下方⚠️ |
| 3 | **合法作用配對 = `characters.md` 現有關係線,隨劇情推進自動擴大** | 不是凍結在垂直切片的兩對。新增關係線屬**敘事工作**,系統端不需改動 |
| 4 | **不創造角色設定沒有的關係線** | 由界線 3 導出(可用配對即 canon 現有者)。⚠️ **但保護戊的不是這條** —— 見下方 |

⚠️ **界線 2 的份量問題,是本輪審查抓到的最嚴重一項**:結局判定用的形狀特徵讀取**不套用任何加權或折扣**(`affinity-data-pool.md` 明文「承諾一(形狀特徵,永久成立,不受任何加權影響)」),故丙類與支援對話**同等計分**。而支援對話全戰役僅 **35 次 / 10 對配對 = 平均每對約 3.5 筆**(`gameplay-flow-decisions.md`),丙類若不設張數上限,單對輕易達十餘筆 —— **純戰術驅動的打牌會以約 3:1 壓過玩家真正有意經營的關係。** 管理者裁決以「限制張數」解決,理由是它**不需要改動任何已核准文件**(替代方案是給戰鬥來源一個折扣,但那要推翻上述「永久成立、不受任何加權影響」的承諾)。

🔴 **保護戊的機制不是界線 4,而且釐清這件事會改變該寫哪一條測試**:`Φ` 只加總 `characters.md` 現有的關係線,故**即使一筆 `(戊, 甲)` 記錄漏進池裡,戊的 `Φ` 照樣恆為 0** —— 戰鬥端的保護是**結構性的**,不依賴任何驗證邏輯。
**但敘事端沒有這層保護**:好感度數值池對「角色設定關係線」**零認知**(該檔對 `關係線`/`characters.md` 零命中),它視 10 對配對一律合法,拒絕規則只涵蓋陣亡配對/幅度 0/非法來源/序列化中。**故一筆漏寫的記錄不影響傷害,卻會被敘事深度與形狀特徵讀取全額算進去,而池是 append-only、永不刪除。**
→ **界線 4 的唯一防線在本系統的合法配對集合,上游不會攔。** 對應驗收條件見 AC-8a/AC-8b。

⚠️ **乙類需要一個尚不存在的介面(已登記於 Open Questions)**:位置加成公式 `Φ = Σ amp_i × B(極性_i, 距離_i)` 屬於**已核准**的好感度—位置連鎖系統,而「暫時覆蓋極性」需要本系統向它注入一個覆蓋值。**該介面不存在,且不得由本系統單方面新增。** MVP 不實作乙類,故此事**不阻擋**;實作前須雙方同意。

#### 二、發牌與手牌

| 規則 | 值 |
|---|---|
| 開局手牌 | **5 張** |
| 補牌 | **每回合開始補 1 張** |
| 手牌上限 | **5 張**。滿手時仍補牌,但**強制玩家棄一張**(可棄新抽的、也可棄原本手上的 —— 選擇權在玩家,系統不代為決定) |
| 每回合出牌數 | **不限** |
| 戰鬥結束 | **未打完的牌全部收回,退回卡池,不帶到下一場戰鬥** |

**「至少發牌 3 次」的硬性約束已滿足且有餘裕**:每回合都補牌,而典型戰鬥為 4~6 個玩家回合(`vertical-slice-level-01.md` 三處明載,查法:`grep -n "回合" design/gdd/vertical-slice-level-01.md`)。最短情境(4 回合)發牌 4 次,超過下限 3 次。**這條約束不再是限制因素。**

🔴 **「戰鬥結束收回」是繼承義務 2 的滿足手段,不可省略。** 該義務要求防止玩家囤牌至戰役尾聲一次打出以規避時近性衰減。數學依據:好感度讀值為 `Σ m_i·λ^(t_query−t_i)`,而囤積 K 張一次打出相對於分散打出的讀值放大倍數 ≈ `Σ_{j=0}^{K−1} λ^j`,在 λ∈[0.90,0.98] 下約為 4.1~4.8 倍(K=5)。**亦即手牌能囤幾張,放大倍數就大約是幾倍。** 戰鬥結束收回把囤積的作用範圍**限制在單場戰鬥內**,跨戰役囤積在物理上不可能。**牌不會消失** —— 退回卡池後未來仍可能抽到。

#### 三、隨機的界線

**隨機只發生在一個地方:這次補牌從卡池裡抽到哪一張。**

牌一進手,它的全部內容(效果類別、幅度、可作用對象)**完全確定、公開、可推算**。沒有任何「打出後才知道」的成分。**結算路徑零 RNG**(專案級禁令 `rng_in_combat_settlement`)。

**保底規則(防「我沒得選」)**:必須存在保底機制,使「手上的牌對當前盤面全部無用」不成為常態。具體形式待卡表設計時定案,但**保底規則本身必須完全公開** —— 玩家可以知道規則、可以推算。**規則透明本身即是資訊透明的一部分**,比純隨機更可推算。

#### 四、打出流程(滿足繼承義務 1 的關鍵)

打牌是**獨立的自由動作**,不消耗移動或攻擊旗標,僅限玩家自己的回合。流程分四步:

1. **開啟手牌** —— 純唯讀,無任何寫入
2. **選牌** —— 選定後系統立即算出合法作用對象集合
3. **選作用對象** —— 玩家從合法集合中選定
4. **確認** —— 顯示效果內容與(若為丙類)永久標示,玩家確認後**同步執行完畢**

第 2~4 步任一時點皆可取消,取消不產生任何寫入。

🔴 **打牌與戰棋結算互斥,這是結構性保證而非紀律要求**:權威寫入進行中(`authoritative_write_in_progress`,2026-09-09 前名為 `settlement_in_progress`)不得開啟打牌介面;打牌介面開啟中不得發起攻擊。兩者結構上不可能同時存在,**因此「結算跑到一半才回頭要玩家選作用對象」在本設計下不可能發生**。此互斥沿用 ADR-0001 / AC-24 既有的「結算進行中拒絕其他操作」機制,**不新增機制**。

✅ **本系統據此確認可滿足 `tactical-combat-system.md` Core Rules #11 + AC-24 的同步契約,不需要修訂上游。**
🔴 **須由兩側各自記錄,不得單方面記帳** —— 單方面替他人記帳是本專案已發生兩次的失效模式(`docs/consistency-failures.md` 模式 G)。

⚠️ **關閉的只有上游 OQ-4 的一半,不是整條(2026-09-08 自我更正)。** 本節原文寫「OQ-4 由此關閉」,查證後不成立 —— 該項有**兩個獨立的問題**,而本節只回答了後加的那一個:

#### 五、`amp`(關係強度倍率)—— MVP 不修改

**`amp` 恆為 1。** 本系統擁有它的量化權(繼承義務 3),而 **MVP 的答案是「不做量化」** —— 上方三類效果中沒有任何一類修改倍率。

✅ **因此 `phi_max`(+12)與 `phi_min`(−4)不需要重算**,`design/registry/entities.yaml` 兩條「對話卡牌加乘系統定案後必須重算」警語可結案。

🔴 **但結案的方式是寫下觸發條件,不是刪掉警語**:**若未來新增任何會修改 `amp` 的卡牌,`phi_max` / `phi_min` 必須在同一次變更中重算。** 算式為 `phi_max = 4 × amp_max × (+3)`、`phi_min = 4 × amp_max × (−1)`,其中 **`4` 是幾何事實** —— 曼哈頓距離恰為 1 的格子只有 4 個(棋盤為正交四鄰),故同時享有「緊鄰」加成的線最多 4 條。框架允許這種卡牌存在,但它會連帶推翻兩個已登記的邊界值,**而那兩個值直接進傷害公式**(`max(0, atk − def + Φ)`)。

⚠️ **上式的 `4` 不是「每角色關係線上限」,兩者長得一樣但意思相反,寫錯會推導出錯的邊界值**(2026-09-08 自我更正):關係線數量**不設上限**(2026-08-31 管理者裁決:不讓數值設計限制敘事),第 5 條以上的線合法且會計入 `Φ`,只是拿不到緊鄰的最高加成。`design/registry/entities.yaml` 的 `affinity_links_per_character_max` 條目已因此 `status: retracted`,而兩個夾限值的推導依據已於 2026-09-01 稽核改寫為上述幾何事實。**本行原文沿用了那個已撤銷的前提** —— 若照原文重算,只要卡表允許某角色多於 4 條線,算出的上界就會虛高。



#### 六、🔴 打牌算「改變盤面」,已算好的查詢結果一律作廢(2026-09-08 管理者裁決)

**玩家可觀測的義務只有一句**:**打出任何卡牌後,畫面上的傷害預覽必須是新值,不得殘留舊值。**

**為什麼這需要一條規則,而不是自動成立**:引擎會把算好的傷害結果快取起來重複使用,並以 ADR-0001 的 `combat_state_version`(戰鬥狀態版本號;2026-09-09 前名為 `board_version`)判斷它有沒有過期 —— 版本號沒變就視為仍然有效。而打牌**不是**結算,若它不遞增版本號,打牌前算的「傷害 4」會通過過期檢查、繼續顯示,而實際打出 7。**那正是本作明訂要避免的「顯示與實際結算不符」,且不會有任何錯誤訊息。**

✅ **2026-09-09:ADR-0001 已完成第一次修訂,本項落地,第二把鎖解除。** 追溯 ID **`TR-card-001`**(在此之前,追溯登記表對本系統**零命中** —— 本系統的需求從未進入任何一次架構涵蓋率統計的分母)。

🔴 **修訂查出來的事比本文件原本寫的嚴重,而原本的描述是錯的框架 —— 保留供追溯:**

**本文件原寫**「該 ADR 自己講兩種相反的話:寬讀法 1 處 vs 窄讀法 4 處」。**`TD-ADR` 覆核推翻了這個框架。** 寬讀法那句寫的是「任一其他改變**盤面**權威狀態的已提交指令」,而該 ADR 自己定義的「盤面」只裝版本號、佔位表、地形、結算旗標四樣 —— **單位攻防值不在其中。兩種讀法都沒有涵蓋打牌。**

**差別會改變修法規模**:兩句話不一致 → 改措辭(5 處);**機制管轄範圍不夠大 → 改它在替什麼背書**(所有權、名稱、介面簽章、驗證條件、登記表、規則表,實測 20 處以上)。

**ADR-0001 第一次修訂的五項實質變更**(全文見該檔 `## Status` 的修訂說明):
1. `board_version` → **`combat_state_version`**,自 `Board` 移交 `BattleState`,並把 `TurnOrder` 一併收進 `BattleState` —— 計數器必須與唯一寫入口同物件,否則 GDScript 沒有存取修飾詞會讓既有防護失效。
2. 寫入路徑由「一條」改為**以 mutator 列舉的逐條清單,至少六條** —— 修訂過程另外查出**三條任何文件都沒登記、而今天就在跑**的路徑(敵方回合整批結算、玩家主動結束單位行動、玩家結束陣營回合)。
3. 打牌第 4 步確認列為第 6 條路徑,**單位攻防有效值明文納入版本號的背書範圍**。

🔴 **修訂另外找到第三個權威狀態零件,而它跟本系統無關 —— 但它解釋了為什麼這次改動這麼大。**

⚠️ **本次修訂留下一張重構工作單,它落在本系統的關鍵路徑上**:把 `TurnOrder` 收進 `BattleState`。規模是四個檔案各約 3~5 行 + 四個測試檔的建構點(`_order.` 的 27 個呼叫點**不用動**,它是欄位)。**「小而機械」不等於零風險。**

🔴 **隨修訂產生一條本系統的新實作義務(這一條原本沒有人知道,而它不會報錯):**

> **打牌確認若要讀「游標系統裁定後的狀態」(當前選了哪張卡、哪個目標、哪個裝置持有權威),

### States and Transitions

本系統有兩組互不相干的狀態,**不共用生命週期**:

**① 一張牌的位置**:`卡池 → 手牌 →(打出|棄掉)→ 本場已用區 →(戰鬥結束)→ 卡池`。

🔴 **「已用區」是第一輪審查新增的,它解決一個兩處互斥的讀法。** 原文的箭頭直接從「打出|棄掉」回到卡池、未加時間限定,讀起來是**立即**退回;而 Core Rules 二 只寫「**未打完的**牌」於戰鬥結束退回,**從未交代已打出的牌**。兩種讀法各自壞掉一件事:
- **立即退回** → 同場可重複抽到同一張,**公式四「卡池 > 11 就不會重複」在數學上失效**(不是機率降低,是保證消失)。
- **照 Core Rules 二 嚴格字面** → 已打出的牌永遠離開卡池,**卡池單調萎縮**,牴觸 Edge Cases「池中總量恆定」與 AC-12「牌永不銷毀」。

「已用區」是**唯一同時滿足那四處既有承諾**的讀法,且不新增任何玩家可見的概念 —— 它只是把 Core Rules 二 那句話的沉默處補上。**牌永不銷毀**,退回卡池後未來仍可能抽到。

**② 一個甲類修正的存續**:`生效中(r=2)→ 生效中(r=1)→ 已移除`。遞減與移除皆發生於玩家回合開始時,詳見公式二。丙類**沒有**這組狀態 —— 它寫完那一筆就結束了,後續全歸好感度數值池管。

🔴 **兩組狀態都不是「打牌介面」的狀態。** 打牌介面本身的四步流程(開手牌 → 選牌 → 選對象 → 確認)在 Core Rules 四,而**它整段是零寫入的**:上述①②的任何轉換只發生在第 4 步確認之後。第 2~3 步取消不留任何痕跡。**把介面狀態與資料狀態混成一台狀態機,會讓「取消」變成需要回滾的操作** —— 本設計下它不需要,因為還沒寫。

## Formulas

### 公式一:甲類的有效戰鬥數值

`ATK_eff(u) = max(0, ATK_base(u) + Σⱼ Δatkⱼ)`  ,  `DEF_eff(u) = max(0, DEF_base(u) + Σⱼ Δdefⱼ)`

`j` 遍歷單位 `u` 身上所有**仍生效**的甲類修正(存續規則見公式二)。

| 變數 | 符號 | 型別 | 值域 | 說明 |
|---|---|---|---|---|
| 基準數值 | `ATK_base` / `DEF_base` | int | ≥0 | 我方單位基準值表。🔴 **該表尚不存在** —— `tactical-combat-system.md` OQ-2,2026-09-02 已指派 `systems-designer`,**工作尚未執行** |
| 單卡修正量 | `Δatkⱼ` / `Δdefⱼ` | int | 非 0 | 帶號:正為增益、負為減益。逐卡定義,本文件不寫死 |
| 有效數值 | `ATK_eff` / `DEF_eff` | int | ≥0 | 直接作為戰棋公式一的 `ATK` / `DEF` 輸入 |

🔴 **夾限在 0 是硬性要求,不是保守寫法。** 戰棋公式一的變數表宣告 `ATK`/`DEF` 型別為 `int, ≥0`。若允許 `DEF` 減成負值,`ATK − DEF` 會**大於** `ATK`,亦即一張減益牌能造成比「把防禦完全歸零」還多的傷害 —— 那是公式定義域外的行為,而公式本身不會報錯。**減益超出目標當前防禦力的部分一律浪費,不得溢出成傷害加成。**

🔴 **本節原寫「不需要戰棋系統新增任何掛鉤點,上游一字不改」—— 後半是錯的,已於第一輪審查以檔案證據推翻(2026-09-08)。** 更正如下,因為三件事的真假不同:

| 原宣稱 | 判定 |
|---|---|
| 傷害公式本身不變(仍是 `max(0, ATK − DEF + Φ)`) | ✅ **成立** —— 甲類只改變它的輸入 |
| 不需要新增**結算步**掛鉤點(②a/②c 仍空) | ✅ **成立** —— 甲類在結算外套用,詳見下方 |
| **「上游一字不改」** | ❌ **不成立** —— 見下 |

**實測**:`src/gameplay/battle/battle_state.gd` 的傷害呼叫為 `CombatRules.damage(attacker.atk, target.def, effective_phi)`,直接讀 `Unit` 的**裸 `int` 欄位**;`Unit`(`RefCounted`)只有 `var atk: int` / `var def: int`,**沒有基準值與有效值之分**;`src/gameplay/` 全域對 `atk_eff`/`def_eff`/`modifier`/`buff` **零命中**。
→ **實作甲類必須在戰棋系統既有檔案中新增「基準值 vs 有效值」的存取層**(`Unit` 加 `atk_eff()`/`def_eff()`,呼叫端改讀它)。
🔴 **不得改用「打牌時就地 `+=`、到期 `-=`」繞過** —— 那會摧毀本公式要求的基準/有效分離,且未來若出現任何永久成長來源,到期時減去修正量會算錯。

✅ **2026-09-08 管理者裁決:允許改動戰棋系統的程式碼與設計文件。** 該存取層的資料模型歸**戰棋系統**擁有(它是戰鬥數值模型的擁有者),須在 `tactical-combat-system.md` 補一節;本文件只定義 `Δ` 怎麼疊加。**本文件不得單方面替它定案。**

**三個仍然成立的好處**(選擇「改單位當前值」而非結算步掛鉤的實質理由):

- **傷害預覽自動反映** —— 預判模式依定義讀即時狀態(上游 Core Rules #10 a),不需要第二條路徑。⚠️ **但這句話有一個前提,而它不是自動成立的 —— 見 Core Rules 六。**
- **防禦增益在敵方回合也生效** —— `DEF_eff` 是單位自身屬性,誰攻擊他都讀得到。**若改走結算步②a 就做不到**(②a 由**攻擊方**的結算套用,防禦方的增益無處可放)。
- **不觸及結算步的原子性** —— 打牌是結算外的獨立自由動作,且與結算結構性互斥(Core Rules 四),修正值在結算**開始前**即已寫定,①~④全程不變。

🔴 **甲類的合法作用對象:僅限我方單位。** 由檔頭那條判準直接導出 —— 每張 MVP 卡牌的牌面必須是**具名角色**之間的互動,而敵人不是那 5 名具名角色,**故作用於敵方的甲類牌進不了 MVP 卡表**。連帶不必回答三件事:敵方基準值讀哪張表、`Δ` 疊在敵方數值縮放之前還之後(實測兩種順序在 `DEF_base=5`、`pct=0.9`、`Δdef=−3` 下算出 7 與 4,**差 3 點防禦力直接進傷害**)、以及 Dependencies 是否要登記敵方數值來源。**這是範圍決定,不是遺漏。**

🔴 **`Σⱼ Δ` 須設累計夾限,而理由是它讓一句上游斷言失真了。** 上游 `affinity-position-chain.md` **四處**宣稱 `Φ` 的夾限(−4/+12)是「唯一擋住數值的東西」—— 那句話在甲類納入 MVP 的那一刻變成假的,因為甲類是一條**平行於 `Φ`、餵進同一條傷害公式、而完全沒有上界**的通道。
→ **本文件要求 `Σⱼ Δatkⱼ` 與 `Σⱼ Δdefⱼ` 各有累計上下界**(具體值待基準表,列 Tuning Knobs),**且該值域須與 `Φ` 的 −4/+12 做尺度校準,不得獨立決定。**
→ ⚠️ **連帶待辦:須通知 `affinity-position-chain.md` 更正那四處措辭。** 本文件不單方面代改(模式 G)。

⚠️ **上游既有的②a 與②c 兩個掛鉤點在 MVP 皆無內容**:②a 是「本次攻擊的傷害修正」,②c 是「以致死預測為條件的效果」,兩者都不是甲類的形狀。**保留但暫無觸發,不是矛盾。**

### 公式二:甲類修正的存續與到期

每個甲類修正攜帶剩餘回合數 `rⱼ ∈ {1, 2}`,由卡牌定義。

- **遞減時點**:玩家回合**開始時**,`rⱼ ← rⱼ − 1`;遞減後為 0 者**立即移除,且須在該回合任何查詢之前完成**。
  🔴 **與補牌的相對順序定案:先遞減與移除,再補牌**(2026-09-08 第一輪審查新增)。原文只寫「與補牌同一時點」,未定序 —— 而順序會改變玩家的決策品質:若先補牌而觸發滿手強制棄牌,玩家會在一個**還掛著已到期修正**的盤面上做那個**不可逆**的棄牌決定。**先清乾淨再發牌**,玩家看到的盤面才是真的。
  ⚠️ **實作提醒**:這條要求「早於該回合任何查詢」,故遞減與補牌**須在同一個函式內依序執行**,不得寫成兩個各自訂閱「回合開始」訊號的獨立處理常式 —— 那樣執行順序取決於連線順序而非任何顯式優先序(`godot-specialist` 第一輪指出,與 ADR-0001 機制二記載的同鏈排序陷阱同類)。
- **語意**:`r = 1` 涵蓋「本回合 + 緊接的敵方回合」;`r = 2` 再多涵蓋玩家的下一個回合。

🔴 **`r = 1` 涵蓋緊接的那個敵方回合,這是刻意的,不是寬鬆。** 若到期發生在玩家回合**結束**時,防禦增益就永遠撐不到敵人動手,在戰術上完全無用 —— 而玩家買防禦的唯一動機就是撐過敵方那一輪。**到期在自己回合開頭而非結束,是這條規則的全部意義所在;改動它等於刪掉整類防禦牌。**

⚠️ **戰鬥結束時所有甲類修正一併清除**(比照手牌收回,Core Rules 二)。甲類不寫入任何持久化資料,**故不需要存檔系統支援** —— 這與丙類相反,見公式三。

### 公式三:丙類的寫入幅度

`丙類打出 → 好感度數值池.附加記錄(配對 p, 幅度 m, 來源 = combat_card)`

| 變數 | 符號 | 型別 | 值域 | 說明 |
|---|---|---|---|---|
| 寫入幅度 | `m` | int | **`{−3, −2, −1, +1, +2, +3}`** | 逐卡定義。🔴 **不得為 0** —— 上游明訂幅度 0 為非法輸入、拋驗證錯誤且不靜默糾正 |
| 作用配對 | `p` | 配對 | **僅限角色設定已存在關係線的配對** | 見下方界線 |

**`m` 為何是 ±3 而不是更大 —— 這是起始值,不是推導結果。** `m` 在**戰鬥**端的作用極其有限:`Φ` 只讀極性正負與距離,**不讀數值大小**(Core Rules 一之二①)。因此 `m` 的尺度應由**敘事**端校準,而敘事端讀值 `Σ mᵢ·λ^age` 再乘來源折扣 `α`,兩個係數目前**都還沒有定值**。選 ±3 的理由是讓單張牌與「緊鄰正向線的單條 `Φ` 貢獻(+3)」同尺度、便於人工對讀。🔴 **它沒有從任何敘事門檻反推**,列入 Tuning Knobs,待 `λ`/`α` 定案後重校。

🔴 **界線:丙類不創造新的關係線。** 可作用配對限於角色設定已有關係線者(垂直切片為甲乙、丙丁兩對)。**理由是繞過這條會靜默推翻一份已核准文件的邊界情況**:好感度—位置連鎖系統明訂「角色沒有任何關係線(如戊):`Φ` **恆為 0,不論站哪**」,而管理者已明確接受「麥子健站哪都一樣」這個玩起來的後果。若一張牌能對(戊, 甲)寫入,戊當場長出關係線,**那條邊界情況與那項裁決同時失效,而兩份文件都不會報錯。** 要放寬須先改 `design/narrative/characters.md`(Canon level `Established`)。

### 公式四:單場戰鬥的抽牌數(供下游校準,非玩法規則)

`抽牌數 = 5(開局) + T`,其中 `T` = 玩家回合數 ∈ [4, 6] → **9 ~ 11 張**。

此數字的用途是兩個下游的輸入,不是玩法設計:①**卡池規模下限** —— 低於此數同一場就會重複到失去意義;②**丙類佔比的上限檢查** —— 若這 9~11 張全屬丙類,一場戰鬥即產生 9~11 筆**永久**好感度寫入,而那些寫入會餵給結局判定的形狀特徵(方向反轉次數、總波動量)。**甲類納入 MVP 之後丙類回到「少數」,此數字才不再是問題** —— 這是甲類納入的第三個理由(Core Rules 一之二②)。

## Edge Cases

| 情境 | 處置 |
|---|---|
| **手牌已滿(5)時補牌** | 仍補,然後**阻塞回合開始直到玩家棄掉一張**。不得由系統代選、不得跳過補牌、不得靜默丟棄新抽的牌 —— 三者都會讓「每回合補一張」這個節奏承諾在滿手時悄悄失效 |
| **卡池張數少於開局手牌數** | 開局發不滿 5 張,**合法且不報錯**(牌不足就是牌不足)。🔴 **但卡表設計須保證卡池 > 11 張** —— 見公式四 |
| **卡池抽空** | 結構上不會發生:打出與棄掉皆退回卡池(States ①),故池中總量恆定。**若實作讓牌消失,此保證即失效** —— 這是一條需要測試守著的不變量,不是自然成立的 |
| **同一單位身上疊多個甲類修正** | **逐條加總**(公式一的 `Σⱼ`),不取最大值、不互斥、不覆寫。與好感度加成的 R4「所有關係線全部生效」同一原則 |
| **減益使 `DEF_eff` 落到 0** | **合法結果,不是錯誤。** 超出的部分浪費(公式一) |
| **甲類修正的宿主單位陣亡** | 修正隨單位一併消失,**不轉移給任何人、不延續**。單位不在場,`ATK_eff`/`DEF_eff` 無查詢對象 |
| **丙類的目標配對有成員陣亡** | 🔴 **必須在「選作用對象」階段就把該配對排除在合法集合外。** 上游明訂陣亡配對的 `combat_card` 來源寫入**一律拒絕並拋驗證錯誤**;若等到確認後才被拒,玩家已經花掉一張牌卻什麼都沒發生。**這不是防禦性程式設計,是合法集合的定義的一部分** |
| **戰鬥結束時仍有生效中的甲類修正** | 一併清除(公式二),不帶到下一場 |
| **打牌介面開啟時敵方回合開始** | 結構上不可能:打牌僅限玩家自己的回合,且與結算互斥(Core Rules 四) |
| **好感度數值池正處於「操作進行中」時打出丙類** | **MVP 不可能發生**,故本文件不定案其處置 —— 依 2026-09-08 裁決戰鬥中不可手動存檔,而自動存檔只在戰鬥結束/章節邊界觸發,那些時點沒有手牌可打。<br>🔴 **但這一格不是「沒事」,是「前提擋著」**:一旦放寬為戰鬥中可存檔,寫入會被上游的存檔生命週期權杖機制**拒絕**,而牌已經打出去了 —— **不得靜默吞掉**。**該情境必須先有答案才能實作丙類。** 見 Interactions 的存檔段 |

| 旋鈕 | 值 | 安全範圍 | 調它會連帶影響什麼 |
|---|---|---|---|
| 開局手牌 | **5** | [3, 7] | 與手牌上限綁在一起(滿手開局是刻意的:第一回合就要做取捨) |
| 每回合補牌 | **1** | [1, 2] | 🔴 **改成 2 會推翻「稀缺是時間上的」這條管理者裁決** —— 前期亂花的人就翻得回來了。**不是純數值調整** |
| 手牌上限 | **5** | [3, 7] | 上調會放大囤積讀值(Core Rules 二的 `Σλʲ` 估算);上限幾張,單場內的放大倍數大約就是幾倍 |
| 甲類持續回合 `r` | **{1, 2}** | 逐卡 | 上調會讓「一、兩回合的戰術工具」變成半永久增益,侵蝕 Player Fantasy 的節奏 |
| 甲類修正量 `Δatk`/`Δdef` | 逐卡定義 | 待基準表 | 🔴 **無法在基準表(OQ-2)產出前校準** —— `+3` 對 `ATK=12` 與對 `ATK=30` 是兩種遊戲 |
| 丙類幅度 `m` | **±1 ~ ±3** | 非 0 | **起始值,非推導結果**(公式三)。待 `λ`、`α` 定案後重校 |
| 🔴 **卡池中的丙類張數上限** | **待卡表定案** | 必須存在 | 2026-09-08 管理者裁決,見 Core Rules 一之三界線 2。**這是三個問題的共同解法**:①讓「丙類是少數」真的被執行;②壓低丙類在結局判定裡壓過支援對話的比例(約 3:1);③降低極性翻轉的機會。**它不需要改動任何已核准文件,這是選它的理由** |

## Visual/Audio Requirements

- 🔴 **卡面尺寸規格尚不存在,本行原寫「沿用 480×270 套裝的既有規格」是假宣稱,已於第一輪審查刪除(2026-09-08)。** 實測 `design/art/art-direction.md` 對「卡面/卡牌」**零命中** —— 該套裝只有立繪 128×128、棋盤單格 32×32、棋子 32×40 三個條目,**沒有卡面可以沿用**。
  🔴 **而這不只是缺一個數字,它有一個會出錯的方向**:手牌依 UI Requirements #1 是**介面層**元素,而介面層的基準畫布 = 螢幕實際解析度、**不做整數倍縮放**(2026-09-01 畫面架構裁決);128×128 立繪是為**世界層整數倍縮放**設計的。**直接把立繪貼進手牌,在 2K(5 倍)等非整除解析度上會被非整數縮放拉伸**,產生 `coding-standards.md` 專門立了一套檢查方法防範的像素網格違規 —— 而該檔明文記載這種缺陷「不留痕跡」(資產照樣正常渲染,只有人眼比對才抓得到)。
  **卡面規格本體外移至 `/ux-design` 與美術方向文件定案**,本文件只登記上述約束。**對話正文用一般繁體中文字型,不是像素字型**(`art-direction.md` 明文裁決)。
- 🔴 **永久牌(丙類)的視覺區別不得只靠顏色。** 須搭配邊框形狀、圖示或文字說明等非色彩通道 —— 此為 `tactical-combat-system.md` UI Requirements 已立、涵蓋「未來修訂新增的每一個狀態區分」的原則陳述,本系統的丙類標示自動落入其涵蓋範圍。
- **甲類生效/到期須有可辨識的瞬間回饋**(打出時、以及到期移除時各一次)。⚠️ **到期那一次特別容易漏掉** —— 它發生在玩家回合開始、與補牌同一時點,兩件事撞在一起。
- **音效不得早於邏輯結算**:比照上游「邏輯狀態為唯一權威,視覺表現不得作為規則判定依據」。動畫播完與否不影響任何數值。

## UI Requirements

🔴 **1. 卡牌介面必須疊在棋盤上方,不得佔用側邊固定欄位。** 這不是偏好,是 2026-09-01 畫面架構裁決導出的硬性約束:世界層取螢幕塞得下的最大整數倍並置中,而**兩種最常見的螢幕(1920×1080、3840×2160)的剩餘邊區為零**。任何「把手牌放在棋盤旁邊」的版面在這兩種螢幕上無處可放。**手牌須為半透明疊層 / 可收合 / 遷入遷出**。

**2. 傷害預覽必須反映生效中的甲類修正。** 打出增益後,預覽數字須立即改變 —— 這是本系統對玩家唯一的「我算對了」的證據(Player Fantasy)。機制上自動成立(公式一),但**須有測試守著**,因為它依賴預判模式讀即時狀態這個上游性質,而那是別人的文件在保證的事。

**3. 手把與十字鍵必須能完整操作手牌,不得有僅滑鼠可達的互動。** 主機無游標(`technical-preferences.md` 平台註記)。選取視覺一律走單一游標狀態源,**不得**使用引擎原生 Control focus/hover(ADR-0005)。

🔴 **4. 同一對角色關係,介面上不得同時呈現兩個好感度數值。** `game-concept.md` 第七輪裁決的 UI 硬性約束(理由:第三輪駁回雙軸分流時的「玩家會困惑哪個才是真的」)。**本系統特別容易違反它** —— 丙類卡牌天然想同時顯示「戰場影響」與「敘事影響」。

**5. 丙類須揭露「此牌的敘事影響小於戰場影響」的定性提示,且不得揭露 `α` 的數值**(同上裁決)。**只揭露事實層**:這一張會留下來。**不揭露它會導向什麼結果。**

**6. 手牌滿時的強制棄牌必須是明確的、阻塞的玩家選擇**,不得做成可忽略的提示。系統不代為決定(Core Rules 二)。

## Acceptance Criteria

**驗收基準是本節,不是 Player Fantasy 的舉例**(該例有一半屬乙類、MVP 不實作)。型別依 `coding-standards.md` 的測試證據表。

| # | GIVEN / WHEN / THEN | 型別 |
|---|---|---|
| AC-1 | 單位身上有兩個甲類修正 `+2`、`+3` → 查 `ATK_eff` → 等於基準 `+5`(**逐條加總,不取最大**) | Logic |
| AC-2 | 攻擊方 `ATK_base=6`、無修正;防禦方 `DEF_base=3` 受 `−5` 減益;**雙方 `Φ` 固定為 0**(無關係線介入或以測試替身隔離) → `DEF_eff = 0` **且本次傷害恰為 6,不多不少** —— 證明減益溢出的部分未轉為傷害加成 | Logic(邊界) |
| AC-3 | 玩家回合打出 `r=1` 的防禦增益 → **緊接的敵方回合中該增益仍生效** → 玩家下一回合開始後失效 | Logic |
| AC-4 | `r` 遞減至 0 的那個回合 → **該回合第一次查詢 `DEF_eff` 時修正已移除**(不是查完才移除) | Logic |
| AC-5 | 打出 `+3` 攻擊增益後,呼叫**與畫面呈現同一份**預判查詢介面取值(🔴 **不得由測試自行重算傷害公式** —— 那證明的是算術,不是「打牌→預覽」這條串接)→ 回傳值較打牌前 `+3`,且中間不插入任何額外操作 | Integration |
| AC-6 | 打出丙類 → 好感度數值池新增一筆記錄,`source` 欄為 `combat_card`、幅度為該卡定義值 | Logic |
| AC-7 | 配對成員已陣亡 → 該配對**不出現在合法作用對象集合中**(不是「選了之後被拒絕」) | Logic |
| AC-8a | 嘗試對無角色設定關係線的配對(如含戊者)作用 → **該配對不在合法作用對象集合中** | Logic |
| AC-8b | 已有關係線的配對(甲乙)**正常可選定、寫入成功、記錄筆數 +1**,且**極性不變** —— 正面控制組。無它則 AC-8a 的訊號強度打折(無法區分「正確排除」與「全部都排除」) | Logic |
| AC-9 | 幅度 `m = 0` 的丙類 → 寫入被拒並拋驗證錯誤,**不靜默糾正、不產生記錄、計數器不遞增** | Logic(邊界) |
| AC-10 | 手牌 5 張時回合開始 → 補牌後**回合流程阻塞直到玩家棄掉一張**;系統未代為選擇 | UI |
| AC-11 | 戰鬥結束 → 手牌全數退回卡池、**所有生效中的甲類修正清除**,兩者皆不帶入下一場 | Logic |
| AC-12 | 連續打出並棄掉 20 次 → **卡池 + 手牌的總張數與開局相同**(牌永不銷毀的不變量) | Logic |
| AC-13 | 開手牌 → 選牌 → 選對象 → **在確認前取消** → 好感度數值池筆數不變、無任何甲類修正產生 | Logic |
| AC-14 | 權威寫入進行中(`authoritative_write_in_progress`)呼叫開啟手牌的輸入事件 → **在同一次函式呼叫內同步回傳可觀測的拒絕結果**(回傳值或訊號),手牌介面斷言為未開啟;**判準是「呼叫的下一行即可斷言結果」,不依賴逾時** | Integration |

| AC-7b | 繞過選擇介面,直接以**陣亡配對**呼叫好感度數值池的丙類寫入介面 → **回傳驗證錯誤,記錄筆數不變** —— 第二道防線。Edge Cases 明文要求兩層,AC-7 只驗了第一層 | Logic(邊界) |

⚠️ **除 AC-10(UI 型,ADVISORY)外全部為 BLOCKING 級。**

🔴 **AC-8 原本是一條「永遠會通過」的測試,已於第一輪審查拆解(2026-09-08)。** 原文斷言「戊的 `Φ` 在任何丙類打出後仍恆為 0」—— 而那是**結構性事實**(`Φ` 只加總 `characters.md` 現有的關係線),**與驗證邏輯有沒有生效完全無關**:就算過濾整個壞掉、`(戊, 甲)` 真的被寫進池裡,那條斷言照樣通過。它看起來在驗「防線守住了」,實際在驗「`Φ` 公式的讀取範圍」。
**現改為 AC-8a(負面:不在合法集合)+ AC-8b(正面控制組)。** 原斷言可保留作輔助回歸檢查,**但不得單獨作為驗證邏輯生效的證據**。
⚠️ **注意 AC-8 沒有第二道防線可驗,這一點與 AC-7 不同**:好感度數值池對「角色設定關係線」零認知,它**不會**拒絕 `(戊, 甲)`。故本規則的唯一防線在本系統的合法配對集合(見 Core Rules 一之三)。

🔴 **兩條特別容易寫成「永遠會通過」的,已就地改寫**:AC-2 原未鎖定攻擊方 `ATK` 與 `Φ`(不同人會寫出彼此不一致的測試,且若選到 `Φ≠0` 連正常情況都可能矛盾);AC-5 原未鎖定驗證管道(測試自算期望值就只證明了算術)。

⚠️ **敏感度證明的做法要用對,否則「已證明」是假的**:本專案記載的陷阱不只是「一次只看到一個結果」——**注入的錯誤常會波及排在目標之前的測試,使套件在到達目標斷言前就中止**(Story 010 實例:11 條檔案只跑了 2 條,真正該被證明的第 3~6 條一次都沒執行)。正確做法是**暫時把較早的 `test_` 函式改名移出收集範圍**,跑完再改回,不是單純多跑幾次。
🔴 **並依此把這些 AC 拆到多個測試檔案**(建議分組:甲類數值計算 / 丙類寫入 / 手牌與回合流程 / 介面互斥)—— 全放同一檔時,任何一條真實失敗都會讓它後面全部**不執行**,而 `failures` 計數與 exit code 的既有陷阱會讓人誤讀成「只有一個東西壞了」。

🔴 **以下規則目前零 AC 覆蓋,已登記為實作期必補(第一輪 `qa-lead` 發現)**:保底規則(Core Rules 三)、打牌不消耗移動/攻擊旗標、**打牌介面開啟中不得發起攻擊**(互斥的另一半,AC-14 只驗了「結算中不得開手牌」這一向)、每回合出牌數不限、卡池不足 5 張時開局發不滿、甲類修正隨宿主單位陣亡消失。**列在這裡而非留白,是因為「規則已定案卻沒有任何驗收路徑」這件事本身必須可被追蹤。**

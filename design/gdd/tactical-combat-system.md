## Overview

戰棋移動與交戰系統是《弈緣》玩法迴圈的骨幹:它讓每個單位在方格棋盤上依移動力與地形規則移動,依武器種類分層的射程(至少涵蓋 2 格與 3 格遠程,不得全數限定近戰 1 格——落實空間餘裕原則)攻擊敵方單位,並以零隨機判定的公式計算戰鬥結果——玩家移動前就能算清楚這步棋的後果。對玩家而言,這是《弈緣》唯一直接操作的玩法本體:移動棋子、選擇攻擊目標、讀懂射程與命中線,是每一回合實際做的事。同時,這個系統也是好感度—位置連鎖系統賴以運作的地基——它維護的單位站位資料(誰跟誰相鄰),正是「好感度即戰場」把角色關係轉譯成空間戰術規則的唯一輸入來源。沒有這個系統提供的可計算戰場,好感度佈局就只是劇情裝飾,不是玩法。

## Player Fantasy

戰棋移動與交戰系統要兌現的,是核心幻想承諾的「以弱勝強」的智力優越感——`game-concept.md` 核心幻想「機制錨點」段落原本只把這句話標記為行銷詞彙,尚未轉譯成規則;本系統的 Core Rules #7(敵方數值優勢)是這個承諾實際落地的規則本體。本系統是這個承諾唯一該由其兌現的系統:敵方單位的基礎數值必須高於我方一定比例,玩家不是靠數值輾壓取勝,而是靠精準的移動/射程計算與好感度佈局帶來的加成,把數值劣勢打平甚至逆轉。

玩家在每一回合實際做的事——移動棋子、選擇攻擊目標、讀懂射程分層——必須讓「這步棋的後果」在移動前就能被完全算清楚(支柱一、三):零隨機判定,傷害、命中、後果全部是玩家能自行驗算的公式。失敗不是「打輸了」,而是「玩家事後才發現某個後果其實早就能被算出來,只是移動前沒看懂」——如果玩家常有這種「早知道」的挫折感,代表本系統的可預判性設計失敗了,不是玩家技術不夠。

武器射程分層(至少涵蓋 2 格、3 格遠程)承擔的是空間餘裕原則的具體實作——若射程全數是近戰 1 格,好感度佔位跟戰鬥站位會直接搶奪同一塊棋盤空間(v2 原型已驗證這會讓好感度機制被排擠)。射程分層讓玩家有餘裕同時解兩道題:「這場仗該怎麼贏」與「誰該站在誰旁邊」——這正是核心動態明訂的關鍵玩家行為,也是本系統存在的理由之一,不只是戰鬥數值的載體。

三種會破壞這份確定性的具體情境,決定了下游章節(Edge Cases、Acceptance Criteria)必須以什麼標準書寫:**移動/射程範圍的顯示與實際結算不一致**(玩家依畫面判斷卻算錯)、**陣亡等狀態轉換造成的資訊斷裂**(單位陣亡後,牽動的好感度連鎖/射程關係消失卻沒有明確提示)、**敵我數值劣勢的翻轉路徑不可驗算**(玩家能感覺到「靠好感度佈局打贏了」,但不能事前算出「打平/逆轉需要湊齊哪些條件」)。

*`creative-director` 未諮詢——Lean 模式。正式製作前建議人工複核本節的語氣與情感錨點是否貼合支柱一/三/四。*

## Detailed Design

### Core Rules

1. **座標與距離系統**:棋盤為方格網格,每格座標 `(x, y)`。射程/距離判定一律採**曼哈頓距離**(`|dx| + |dy|`),不採對角線相鄰;此為本文件、`game-concept.md` 空間餘裕原則四項量化指標(可站格數、可達格數、局部窗口密度、走廊寬度)共用的唯一距離量尺,任何下游系統(關卡設計、UI 距離顯示)不得另採歐幾里得距離或切比雪夫距離。

2. **移動規則**:每單位每回合擁有固定的**移動力(MP)**;每格地形有各自的**移動成本**(≥1,可能因地形種類不同)。單位的**可達格集合**,是從其目前座標出發,以 Dijkstra/BFS 展開、沿途累積地形成本 ≤ 該單位當前 MP 的所有格子,且不得穿越任何已被單位佔據的格子(不論敵我)——佔位格本身若在路徑終點以外,視為障礙,不計入可達格。可達格計算為本系統對外的核心查詢介面,供 UI 呈現移動範圍。**演算法選用提醒(2026-08-17(三)修正措辭,回應 `/design-review` 第二輪發現)**:僅當全圖地形成本一致(退化情境,見公式三邊界行為)時,BFS 才會產生與 Dijkstra 相同的正確結果;本系統的地形成本表(Tuning Knobs)並非全部一致,實作應以 Dijkstra(或等效的成本感知展開演算法)為準——「Dijkstra/BFS」並非兩者可互換之意,僅表示兩者是同一類展開演算法的成員。

3. **武器射程分層**:每個武器種類定義一組 `(最小射程, 最大射程)`。三個分層作為起點(**具體數值見 Tuning Knobs「武器射程分層」,此處只定案結構性質**):
   - **近戰**:必須與目標相鄰(`min=max`,無延伸範圍)
   - **中程**:無近身盲區、有限延伸的泛用分層(`min=1`,`max>1`)
   - **遠程**:**有近身盲區**、延伸最遠的專精分層(`min>1`,`max` 為三層最大)
   **(2026-08-13 修訂:本項原寫「中程:射程 2 起跳的窄帶(min≈2)」,與 Edge Cases「武器最小射程」的「三層皆以 1 為下界」互斥。Tuning Knobs 定案數值時一併裁決為混合型——中程無盲區、遠程有盲區,兩處敘述同步修正,使用者裁決 R-G1 甲案。近身盲區改由遠程分層承擔,是本文件唯一抑制遠程優勢的機制,理由見 Tuning Knobs。)**
   至少須同時存在「射程 1」與「射程 ≥2」兩種武器,不得全數為近戰(呼應空間餘裕原則、game-concept.md MVP 必要內容第 1 項)。

4. **視線遮蔽**:射程 ≥2 的攻擊(中程、遠程)須額外通過**視線檢查**——沿攻擊者與目標連線經過的每一格(不含起訖點本身),若任一格的地形標記為「遮蔽」,該次攻擊不合法,UI 須明確標示為不可攻擊而非隱藏選項。近戰(射程 1)不受視線檢查限制(相鄰格恆可視)。此規則呼應 `game-concept.md`「視線通透度指標缺口」——遠程武器提供的空間餘裕效益,實際受地形遮蔽率制約,不是無條件成立。**視線阻擋的判定依據僅為地形的「遮蔽」標記,單位(不論生死、不論敵我)不影響視線判定(2026-08-17(三)新增,回應 `/design-review` 第二輪 BLOCKING-NOW B-5,使用者裁決甲案)**——一個單位站在攻擊方與目標之間,不會使原本視線暢通的攻擊變為不合法。此裁決同時保證 Tuning Knobs `max_occlusion_ratio` 這個關卡層閘門足以完整保證空間餘裕效益的承諾(若單位也能遮蔽視線,關卡設計時無法預先擔保實際遮蔽率,閘門將失去約束力)。

5. **結算步內的操作順序(硬性,呼應支柱一/三的可預判性)**:玩家對目標發起攻擊時,本系統依下列固定順序處理,不受平台/引擎排程影響:
   ① 查詢好感度—位置連鎖系統對攻擊雙方(及其各自鄰接配對)的加成/懲罰輸出,作為傷害公式輸入(見 Formulas)
   ② 套用任何攻擊/技能卡牌自身觸發的效果,依序執行三個子步驟(2026-08-17(三)新增,回應 `/design-review` 第二輪 BLOCKING-NOW B-4,使用者裁決選項二):
      ②a **傷害修正效果套用**:套用所有會改變本次攻擊傷害數值的卡牌/技能效果(例如傷害加成、減免),得出套用後的傷害修正值
      ②b **致死預測(唯讀,不消耗任何狀態)**:以步驟①查得的 `Φ` 快照 + ②a 套用後的傷害修正值,代入公式一試算本次攻擊的傷害,並與目標當前 HP 比較,得出「本次攻擊是否致命」的布林值——此值在零隨機承諾(Core Rules #7)下恆為可決定值,**本身不觸發任何寫入,亦不提前判定陣亡**
         > **與 Core Rules #8 預判模式的關係(2026-08-18 修訂,回應 `/design-review` 第四輪 BLOCKING-NOW B-4,`qa-lead` 發現)**:本子步驟與 Core Rules #8 預判模式**僅共享「唯讀、零寫入、純函數」這一項性質,不共享輸入集,亦不得共享呼叫路徑**。兩者的輸入集不同且不可互換:Core Rules #8 的預判以步驟①的原始 `Φ` 試算(其語意是「若現在發動這次攻擊,結果會如何」);②b 的輸入嚴格更大——是「①的 `Φ` 快照 **加上** ②a 已套用完成的傷害修正值」(其語意是「在本次結算已套用卡牌傷害修正之後,這一擊是否致命」)。**舊版措辭的缺陷**:原文寫「語意與 Core Rules #8 預判模式的純函數試算**相同**」,字面上邀請實作者直接複用 Core Rules #8 對外提供的預判查詢介面來實作②b。該複用會使②b **獨立重新查詢** `Φ`(因為 Core Rules #8 的介面依其自身定義必須讀取呼叫當下的即時狀態,見 Core Rules #10 a 項),而非沿用本次結算①已捕獲的快照——正是本文件「`Φ` 的取值時點為快照」規則(見下方)與 AC-6 既有向量費力堵住的同一個危害,只是換從「呼叫路徑複用」這個此前未設防的角度進來。因此:**②b 的 `Φ` 值須直接沿用本次結算步①既有的快照,不得對好感度—位置連鎖系統發起任何獨立查詢,亦不得呼叫 Core Rules #8 的對外預判介面本身。** 對應驗收條件見 AC-6 新增之 THEN 子句。
      ②c **條件式卡牌效果套用**:依②b 的預測結果觸發任何以「本次攻擊是否致命」為條件的卡牌效果(例如殺招觸發的好感度對話卡牌),含其可能寫入好感度數值池的變化
      本子步驟拆分只精確化②內部的執行順序,不改變①②③④的頂層順序,亦不改變下方「陣亡通知」的觸發時機(仍在④)。若②c 觸發的效果又反過來改變了傷害修正,②b 的預測值與③的實際結算值可能出現落差——此時**恆以③的實際結算結果為準**,②b 僅供②c 的觸發判斷之用,不作為傷害或陣亡的最終依據。
   ③ 計算並套用傷害
   ④ 檢查目標 HP,若 ≤0 則判定陣亡,進入下方陣亡處理流程
   此順序**明文定案**「陣亡通知」與同結算步好感度寫入的相對順序——先完成 ①②③ 的所有好感度寫入,**最後**才於 ④ 觸發陣亡處理,確保擊殺當下的卡牌好感度效果不會被陣亡標記表的「陣亡配對寫入限制」規則(見 `affinity-data-pool.md` Core Rules #2)誤判為死後寫入而遭拒絕(使用者裁決,回應 `affinity-data-pool.md` Dependencies 對本系統的明文要求)。

**`Φ` 的取值時點為快照,不因步驟②的寫入而重新查詢(2026-08-17(二)新增,回應 `/design-review` 第一輪 BLOCKING-NOW #3)**:步驟①查得的 `Φ` 是本次結算步**唯一**餵給步驟③傷害公式(見 Formulas 公式一)的值——即使步驟②套用的卡牌效果本身寫入了好感度數值池、進而改變了「若此刻重新查詢會得到的 `Φ`」,步驟③**仍然使用步驟①當下查得的原始值,不重新查詢**。這與 Core Rules #8 預判模式「依上方結算流程①的好感度加成/懲罰預先試算」的既有語意一致——若步驟③改為重新查詢,預判結果將系統性地與實際結算的傷害數字不符,直接牴觸 Player Fantasy 具名的可預判性承諾。**實作提醒(2026-08-17(三)修正措辭範圍,回應 `/design-review` 第二輪傳播失敗)**:`Φ` 型別為 `int`(見 Formulas 公式一變數表),在 GDScript 中傳遞本來就是值拷貝,不會自動產生別名風險。本提醒僅在以下條件成立時才有實際效力:**若好感度—位置連鎖系統(#5)未來的查詢介面回傳的不是裸 `int`/`float`,而是 `Dictionary`/`Resource`/`Object` 等參照型別**(例如為了同時攜帶逐配對明細而包裝成複合結構),則步驟①的查詢結果須顯式複製後才能視為快照(依回傳型別分別處理:`Dictionary` 用 `.duplicate(true)`;**巢狀 `Resource` 須用 `duplicate_deep()`——`duplicate()` 對巢狀 Resource 自 Godot 4.5 起已標記為不建議使用,見 `docs/engine-reference/godot/deprecated-apis.md`,舊行為仍保留故不會壞,但不應寫進新程式**;2026-08-17(四)修正,回應第三輪 `godot-specialist` ADVISORY;或直接做欄位抽取),不得直接持有該參照——否則步驟②的寫入會就地改變步驟③實際讀到的值,即使呼叫序列本身完全符合上方定案的 ①②③④ 順序,也會產生與本規則矛盾的傷害結果(見 AC-6 新增向量)。

6. **陣亡處理**:單位 HP 歸零時:
   a. **若該單位屬於我方(5 名固定主角之一)**,立即呼叫 `affinity-data-pool.md` 的「陣亡通知」介面,傳入該角色識別碼(冪等性拒絕由對方系統保證,本系統只需保證不重複呼叫同一角色)。**敵方單位陣亡不呼叫此介面(2026-08-18 修訂,回應 `/design-review` 第四輪 BLOCKING-NOW B-3,`gameplay-programmer` 發現+主 session 查證)**:本項原文無陣營限定,字面上要求任一單位(含敵方)陣亡皆呼叫此介面;但 `affinity-data-pool.md` Core Rules #1 的陣亡標記表明文將鍵域定義為「5 名固定主角之一」(該文件的 `Dictionary[角色, ...]` 鍵集合上界即以此為據,支撐其 O(1) 效能保證與診斷範圍排除的正當性),敵方角色不在此鍵域內。好感度—位置連鎖系統(#5)所服務的關係網路本就只涵蓋我方 5 人的兩兩配對(呼應 `game-concept.md`「固定 5 人」裁決與 `affinity-data-pool.md`「配對集合封閉且固定」),敵方陣亡對它而言不是一個需要記錄的事件——收斂呼叫範圍不是新開一個裁決分支,是既有兩份文件已經鎖死的唯一解。**呼叫失敗的處理義務(2026-08-18 新增,回應 `gameplay-programmer` 發現本項原本沒有失敗處理,與下方 (b) 項對跨系統呼叫的謹慎處理不對稱)**:若該次呼叫的回傳結果非「已接受」(重複呼叫以外的拒絕情形——雖然雙方文件現階段皆未定義此類情境的具體樣態),呼叫方**不得**將未確認接受的呼叫視為已完成,須有對應的偵測/重試機制,比照下方 (b) 項對「已過期,未套用」回傳值的處理原則;具體介面錯誤處理慣例由 `/create-architecture` 決定。
   b. 若該單位當下是單一游標/高亮狀態系統的目前游標目標,呼叫其「標記目前目標為待重新解析」介面(見 Dependencies),**並檢查其回傳值(2026-08-17(二)新增,回應 `/design-review` 第一輪 BLOCKING-NOW #6)**:`cursor-highlight-state.md` Core Rules #2 對呼叫方課予「不得把過期回傳視為問題已解決」的義務——若回傳「已套用」,本步驟完成;若回傳「已過期,未套用」(代表玩家已在陣亡判定與本次呼叫之間導覽離開該目標),本系統**不得**視為已妥善處理,須保有於玩家日後再次導覽回該已陣亡單位所在格時,重新偵測其陣亡狀態並重新呼叫本介面的機制——**此為硬性義務,不得僅以「於自己的確認/選定前置檢查中獨立核對該目標是否仍為合法游標目標」取代(2026-08-17(三)修正,回應 `/design-review` 第二輪 BLOCKING-NOW B-3,gameplay-programmer 與 qa-lead 獨立發現同一缺陷)**:後者只能攔下玩家對已陣亡單位發起的非法確認動作,無法修正持續停留在該單位上的誤導性高亮——高亮不修正,玩家仍會被「這格看起來還是合法目標」誤導,直到嘗試操作才被拒絕,重現本規則存在目的要防的「早知道」失敗模式。前置檢查式核對可以**額外**疊加作為防線,但不得作為替代方案——單純呼叫介面而不檢查回傳值,無法排除游標停留在一個已陣亡單位上卻未被標記為待重新解析的情形,直接命中 Player Fantasy 具名失敗模式「陣亡等狀態轉換造成的資訊斷裂」
   c. 該單位從棋盤佔位中移除,不再參與移動範圍/射程/視線計算,不再是任何合法攻擊目標
   d. 陣亡對好感度—位置連鎖系統的鄰接加成/懲罰的具體處理規則(移除連鎖/凍結/觸發事件)**歸屬該系統**(系統 #5,含陣亡處理於其系統名稱),本系統只負責觸發陣亡事件本身,不裁定好感度連鎖規則

7. **敵方數值優勢(「以弱勝強」機制錨點,正式落地 `game-concept.md` 懸而未決的承諾)**:敵方單位的基礎數值(HP/攻擊/防禦,具體如何組合待 Formulas 章節)以均勻比例浮點,系統性高於我方同階單位一定百分比(`enemy_advantage_pct`,Tuning Knob,見下方)。玩家透過精準的射程/站位計算與好感度佈局帶來的加成,是抵銷/逆轉此優勢的**唯一**機制——本系統不提供任何隨機判定(命中率/爆擊率)作為變數,傷害結果 100% 由雙方數值、地形、好感度加成決定。

8. **預判模式**:玩家可在確認移動/攻擊前,對候選目的地啟用「預判標記」——系統回傳「預期正效果/預期負效果/預期無效果」三態摘要(依上方結算流程①的好感度加成/懲罰預先試算,不實際寫入任何狀態,純函數呼叫)。此為正式遊戲功能(`game-concept.md` 裁決),非臨時量測工具。

9. **行動經濟(每回合每單位)**(2026-08-17 新增,使用者裁決 OQ-9 兩軸皆採乙案;**2026-08-17(二)修訂範圍與陣營用詞,回應 `/design-review` 第一輪 BLOCKING-NOW #1**):每個單位在**其所屬陣營的**回合內擁有**兩個彼此獨立的行動旗標**——「移動」與「攻擊」,各有「未用/已用」兩值。本規則對我方與敵方單位同樣適用,各自綁定**自身所屬陣營**的回合(我方單位綁我方回合,敵方單位綁敵方回合)——下方所有提及「我方回合」之處,對敵方單位應讀作「敵方回合」,不是本規則只管我方單位的例外。
   - **順序自由**:兩者可以任意順序使用——可先移動後攻擊,也可**先攻擊後移動**。
   - **皆非強制**:單位可只用其一,或兩者都不用。
   - **可暫緩**:使用其中一個旗標後,該單位**不會**立即結束行動;玩家可轉去操作其他單位,稍後於**同一回合內**回頭使用剩餘的旗標。
   - **各限一次、不可拆分**:每個旗標每回合各只能使用一次;移動不得分段(一次移動即用掉整個移動旗標,無論實際消耗多少 MP,剩餘 MP 不保留)。
   - **預判標記不消耗任何旗標**(Core Rules #8 為純函數,無狀態寫入)。
   - **主動結束行動**:玩家可對任一「可行動」單位主動下達「結束行動」指令,不要求兩旗標皆已使用——此指令本身是一個明確的玩家操作,須有對應的輸入路徑(見 UI Requirements 第 6 節)。兩旗標皆已使用、或玩家主動下達此指令時,該單位轉為「已行動」狀態。
   - **回合邊界重置(獨立規則,不經由「已行動」狀態,2026-08-17(二)新增,回應 `/design-review` 第一輪 BLOCKING-NOW #1)**:每當該單位**所屬陣營**的回合結束、其下一次**同陣營**回合開始時,不論該單位當下處於「可行動」或「已行動」、不論兩旗標目前的使用情形,兩旗標**一律**重置為「未用」。此重置動作是回合邊界本身觸發的獨立效果,**不要求單位先轉為「已行動」,也不要求玩家曾對其下達過「結束行動」**——這是本條獨立規則存在的直接理由:上方「可暫緩」明文允許單位只用一個旗標、不主動結束、暫緩到之後處理甚至整回合都不再理會;若旗標重置只掛在「兩旗標皆已使用/主動結束→已行動→回合邊界→轉回可行動」這條路徑上,上述被暫緩、未被主動結束的單位就永遠碰不到重置(見 States and Transitions 表)。「未使用的旗標作廢,不累積至下回合」與「已使用的旗標重置為未用」是同一個回合邊界動作的兩面,由本條規則一併保證,不是兩條各自獨立、可能只實作一半的規則。對已經在「已行動」狀態的單位,此重置與其「轉回可行動」的狀態轉換同時發生;對仍停留在「可行動」狀態的單位(旗標部分或全未使用,無論是否曾被主動結束),此重置**單獨生效**,不改變、也不需要改變其狀態標籤本身。
   - **回合邊界的定義範圍(僅限本條規則所需)**:本文件不定義完整的回合順序/階段推進系統(例如「玩家階段→敵方階段」的全局轉換由哪個系統觸發、勝負判定於何時檢查等)——那屬於尚未拆分出獨立系統條目的範疇,見 Dependencies 章節的對應說明。本條規則只取用其中「我方/敵方回合的開始與結束」這一個時間點作為旗標重置的觸發時機,不預設其上層實作細節;若未來確認有專屬系統擁有完整回合結構,本條規則的觸發點定義應回頭與該系統對齊,不視為本文件現有裁決被推翻。
   - **對結算的影響**:攻擊後移動會改變該單位與其他單位的鄰接關係,進而改變**其他單位後續攻擊**在上方 Core Rules #5 步驟①查得的 `Φ`。這是刻意允許的戰術編排空間(直接服務支柱二的好感度佈局),也是 Edge Cases「預判模式必須讀取即時狀態」之所以為硬性要求的主因之一。

10. **對外查詢介面的共用義務(總則)(2026-08-17(四)新增,回應 `/design-review` 第三輪 BLOCKING-NOW F3-4/F3-5/F3-6,使用者裁決:總則式修法而非逐項補條款;2026-08-18 第四輪修訂,回應 BLOCKING-NOW B-1/B-2,使用者裁決選項B——本條僅保留玩家可觀測義務,內部機制細節外移至 ADR)**:本文件對外提供的**每一個**查詢介面,除其各自的數學定義外,一律另受本條 a/b/c 三項義務約束。**本條為總則,適用於本文件現有與未來新增的所有對外查詢介面;下方「現況盤點」僅為此刻的清單,不是本條的涵蓋範圍上限。**

    **本條存在的理由(修法史,不得刪除)**:查詢介面的**數學定義本身不足以**保證互動式 UI 的正確性——這是本文件連續三輪各自獨立撞到的同一個結構性缺口。第一輪為預判模式補了 Edge Cases「預判模式必須讀取即時狀態」+ AC-11;第一輪 BLOCKING-NOW #4 為移動/攻擊範圍疊加圖補了另一條 Edge Cases 條款 + AC-20;第三輪又發現第二輪才新增的「回合層級剩餘旗標總覽」(UI Requirements §1)與「敵方威脅範圍疊加圖」(UI Requirements §1a、公式四)**同樣沒補**。逐一補個案條款的作法已三次證明每次都會漏掉下一個,故改為總則,使未來新增的查詢介面自動被涵蓋。既有的 Edge Cases 條款與 AC-11/AC-20 保留在冊,**視為本條的具名實例**,不是與本條並列的獨立規則。

    **現況盤點(非窮盡)**:可達格集合(公式三)、攻擊範圍/視線合法性(Core Rules #3/#4)、預判摘要(Core Rules #8)、**站位/鄰接查詢(供系統 #5——該系統尚未設計,此介面的資料形狀待其 `/design-system` 時定案,現階段本條 a/b/c 對它的約束是前瞻性宣告,不代表現在已有可執行的驗收條件;定案後自動落入本條涵蓋範圍,不需回頭修改本清單)**、回合層級剩餘旗標總覽(UI Requirements §1)、敵方威脅範圍(公式四、UI Requirements §1a)。

    a. **即時性**:任一查詢的輸出,恆須等於「以呼叫當下的棋盤狀態從頭重新計算一次」的結果。實作可採任何內部手段(**含快取**),但輸出不得偏離此斷言——**判準是輸出正確性,不是特定實作手段本身**。此義務對「輸出已被渲染到畫面上、玩家仍停留於該檢視狀態、期間棋盤發生變化」的情形同樣成立:任何導致重繪的事件發生時,重繪結果須反映重繪當下的狀態,不得沿用先前一次計算的畫面或計算結果。**本項不定案重繪多久觸發一次**(觸發時機屬呈現層,由 UI Requirements / `/ux-design` 定案),只定案「**若**重繪,結果必須正確」。**但「若重繪」本身不得無限期不發生(2026-08-18 新增,回應第四輪 BLOCKING-NOW B-1,`game-designer` 發現):任一改變某查詢輸出正確答案的已提交結算邊界事件(見 Core Rules #11)發生時,該查詢當下顯示中的輸出至少須被標記為過期(stale),系統不得以過期輸出接受下一個玩家輸入(例如:接受一個以過期疊加圖為依據的移動/攻擊確認)。呈現層仍可自由決定「多快把過期輸出重繪成新值」,但不能對「該不該重繪」保持沉默——這是本項的最低限度義務,填補「一個渲染一次、永不失效的實作完全合規」這個此前存在的漏洞。**
       > **為何本項對每一個介面都是實質約束,而非形式宣告**:公式三的 `occupied(tile)` 明文「不論敵我」,因此 `reachable_set(e)` 乃至 `threat_range(e)` 在數學上**保證**會隨我方單位移動而改變;Core Rules #9 的「可暫緩」模型又明文允許玩家在同一回合內交錯操作多個單位。兩者相乘的結果是:玩家極容易在某個疊加圖仍顯示於畫面上時,親手改變了它的正確答案。此情境直接命中 Player Fantasy 具名的失敗模式「移動/射程範圍的顯示與實際結算不一致」與「早知道」型挫折。

    b. **單一快照原子性**:任一查詢的計算過程,須對**單一**盤面快照完成;計算期間發生的盤面變動**不得**中途套用,須排入佇列於計算結束後處理。**理由**:若計算中途讀到新舊混合的狀態,輸出既不等於「變動前的正確答案」也不等於「重繪當下的正確答案」,靜默違反上方 a 項。**原子性的範圍不限於單一查詢自身(2026-08-18 新增,回應第四輪 BLOCKING-NOW B-2,`game-designer`/`systems-designer` 各自從橫向、縱向獨立發現)**:若同一次呈現週期內,有一組查詢輸出被合併判讀為單一畫面提供給玩家(例如 UI §1a 要求同時可見的移動範圍疊加圖與威脅範圍疊加圖;或 `threat_range_all(E)` 對多個存活敵人各自計算後聯集),**該組輸出視為同一次「查詢」,共用同一份盤面快照——不得由各自獨立、對應不同時刻盤面狀態的快照拼接而成**,即使每一份子輸出各自對其自身的快照仍是原子的。組合後呈現給玩家的畫面,必須對應到真實存在過的**單一**盤面狀態,不能是「兩張各自正確、但彼此不同時」的畫面疊在一起。跨幀展開等內部機制的具體實作手段(重入鎖、快照資料結構、佇列處理方式)由 **ADR-0001**(`docs/architecture/adr-0001-tactical-query-atomicity-contract.md`) 定案,本條只定案玩家可觀測的正確性義務。
    c. **佔位資料的所有權**:單位佔位(公式三的 `occupied(tile)`)須由一份**邏輯資料結構**承載(概念上為「座標 → 單位識別碼」的對映;具體型別由 `/create-architecture` 決定),**並隨任一改變單位邏輯位置或存活狀態的事件同步更新**(2026-08-18 修訂範圍,回應第四輪 BLOCKING-NOW B-1,`systems-designer` 發現原文僅點名陣亡一種觸發事件,AC-22 卻已有測試移動同步的向量,規範與驗收條件不對稱)——**現況已知的觸發事件包含**:Core Rules #5 步驟④陣亡佔位釋放、單位完成移動(**邏輯完成即算,不論動畫/視覺過渡是否播放完畢**)。本項為原則陳述,未來新增的佔位變化事件(例如技能卡牌系統帶入的位移效果)自動落入涵蓋範圍,不需要逐項列舉才算數——這正是本條當初改為總則要根絕的「舉一漏一」失效模式,同樣的失效模式不應在本條自己的子項裡重演。**不得**以「查詢場景/節點樹上該座標是否存在單位物件」的方式導出,亦**不得**以視覺/動畫狀態作為佔位判定的依據(呼應 Core Rules #11 的邏輯狀態唯一權威原則)。**理由**:Edge Cases「陣亡單位的佔位立即釋放」與 AC-7(c) 要求該格自陣亡發生的**下一次查詢**起即為可通行,且明訂在**同一結算步內**完成;而多數引擎(含本專案的 Godot)移除節點的慣用手法會延後至當前幀結束才真正生效,節點在該結算步內仍掛在場景樹上。若佔位由節點樹導出,該格在同一結算步內仍會讀為已佔據,直接違反 AC-7(c)。此為引擎穩定的既有行為而非某個版本的特性,正因如此才特別容易被漏掉。

11. **結算步的不可重入邊界(2026-08-18 新增,回應 `/design-review` 第四輪 BLOCKING-NOW B-1,使用者裁決選項B——本條僅保留玩家可觀測義務,機制實作細節見 ADR)**:Core Rules #5 的結算步(①→②→③→④)一旦開始,在其完成(④執行完畢)之前,**不接受任何其他操作輸入**——不論是對同一單位發起的其他操作,或依 Core Rules #9「可暫緩」模型切換至其他單位進行操作。「可暫緩」允許的跨單位交錯操作,其粒度是**結算步與結算步之間**,不是結算步**進行中**——這是本條要明訂的邊界,避免「可暫緩」的既有裁決被誤讀為連結算步中途都可以插入其他操作。

    若結算步的任一子步驟(尤其②c「條件式卡牌效果套用」)需要玩家輸入才能決定其行為(例如卡牌效果要求玩家選擇加成對象),**該輸入須在本次結算開始之前完成**——本系統對技能卡牌系統(#6)的效果掛鉤契約定案為**同步、結算步進行中不得要求玩家輸入**。此契約待 #6 執行 `/design-system` 時雙方確認是否可行(已登記 Open Questions OQ-4 補充範圍)——若 #6 設計時發現某類效果無法避免結算中玩家輸入,須回頭修訂本條,不得由 #6 單方面繞過本條的同步契約。

    **邏輯狀態(佔位、HP、行動旗標)為唯一權威**;動畫、淡出效果、節點生命週期等視覺表現**不得**作為任何規則判定的依據,也不得被規則邏輯讀取為狀態的一部分——呼應並擴大 Core Rules #10(c) 的原則,範圍不限於佔位查詢,涵蓋本文件的所有規則判定。此原則同時解決 Visual/Audio 第 4 節「陣亡最小限度移除過渡」與其他查詢介面(尤其移動範圍疊加圖)在同一格上可能產生的顯示衝突:即使該格的死亡淡出效果仍在播放,只要邏輯佔位已釋放,其他查詢對該格的判定即以邏輯狀態為準,不受淡出效果是否播完影響;呈現層若認為兩者同格重疊會造成觀感混淆,可自行決定是否延後對該格渲染新的疊加標示,但**不得**延後邏輯判定本身去配合視覺效果。

    重入防護的具體實作手段(鎖定機制、輸入佇列/丟棄策略)由 **ADR-0001**(`docs/architecture/adr-0001-tactical-query-atomicity-contract.md`) 定案,本條只定案玩家可觀測的義務:結算進行中,玩家的任何操作嘗試必須得到明確的拒絕回饋(比照 UI Requirements 第 6 節既有的合法性閘門機制),不得靜默丟棄也不得排入無限期等待。對應驗收條件見新增 AC-24。

### States and Transitions

| 狀態 | 進入條件 | 允許操作 | 離開條件 |
|---|---|---|---|
| **可行動** | 該單位所屬陣營回合開始、單位存活;**兩個行動旗標至少一個未使用** | 使用任一未用旗標(移動 / 攻擊)、預判標記(不消耗旗標)、主動結束行動 | 兩旗標皆已使用,或玩家主動結束該單位行動 → 轉為「已行動」;HP 歸零 → 轉為「陣亡」 |

| **陣亡** | HP ≤ 0 | 無(移出棋盤佔位、不參與任何後續計算) | 終態,本文件範圍內無復活機制 |

**「反擊」用詞範圍聲明(2026-08-17(三)新增,回應 `/design-review` 第二輪,使用者裁決:保留詞條、現階段不展開規則)**:上表「反擊」一詞保留,但不在本文件展開規則——本系統的 Core Rules #5 結算流程只定義攻擊方主動發起的傷害路徑,**現階段核心戰鬥規則不含任何防守方自動迎擊/反擊機制**。若未來反擊效果存在,其來源預期是技能卡牌系統(#6)的卡牌效果,或特定角色的被動技能,而非本系統的常規戰鬥規則——觸發條件、傷害公式、與行動經濟(Core Rules #9)雙旗標的互動(例如近身盲區的遠程單位能否反擊)等細節屬於該來源自身的設計範疇,由其定案時自行決定是否引入及如何定義,不在本文件預先規定(見 Open Questions OQ-19)。

**旗標重置與上表狀態轉換相互獨立(2026-08-17(二)新增,回應 `/design-review` 第一輪 BLOCKING-NOW #1;規則本體見 Core Rules #9「回合邊界重置」)**:上表「已行動」列的「轉回可行動」轉換,與兩旗標的重置是**同時**發生、但**不是同一件事**——旗標重置由 Core Rules #9 的獨立規則保證,在該單位所屬陣營的每次回合邊界一律執行,不論此刻單位處於「可行動」或「已行動」。這意味著:一個仍停留在「可行動」狀態的單位(例如只用了移動旗標、未主動結束、玩家在回合內沒再理會它),回合邊界發生時,它的旗標**照樣**被重置為未用——它**不會**、也**不需要**先被推進「已行動」再轉回「可行動」才能重置(那樣反而會與「已行動」的進入條件「兩旗標皆已用完,或玩家主動結束行動」矛盾,因為此類單位兩者皆未成立)。**舊版(2026-08-17 首版)的缺陷**:舊版把旗標重置寫成「已行動」列離開條件的附帶動作,導致仍停留在「可行動」的部分使用/零使用單位永遠碰不到任何重置路徑——已修正為上述獨立規則。

**「可行動」是複合狀態**:依兩旗標的使用情形有三種可觀測組合(皆未用 / 只用了移動 / 只用了攻擊),第四種組合「皆已用」即刻轉為「已行動」。玩家必須能分辨出**某個可行動單位還剩什麼可做**——此為呈現層的硬性要求,落地於 UI Requirements 第 1 節格位資訊面板的「當前狀態」欄位,以及 UI Requirements 第 1 節新增的回合層級總覽(見該節)。

## Formulas

### 公式一:傷害計算公式(`damage_formula`)

`damage_formula(attacker, target) = max(0, ATK − DEF + Φ)`

**變數:**
| 變數 | 符號 | 型別 | 範圍 | 說明 |
|---|---|---|---|---|
| 攻擊方有效攻擊力 | `ATK` | int | ≥0 | 攻擊單位的當前攻擊數值(若為敵方單位,即公式二輸出的 `enemy_stat`) |
| 防禦方有效防禦力 | `DEF` | int | ≥0 | 目標單位的當前防禦數值(若為敵方單位,即公式二輸出的 `enemy_stat`) |
| 好感度—位置修正 | `Φ` | int | 不限正負;上界待好感度—位置連鎖系統定案(見 Dependencies) | 呼叫好感度—位置連鎖系統對攻擊雙方(及其鄰接配對)的加成/懲罰查詢介面(見 Core Rules #5 步驟①)所得的帶號整數,已換算為傷害單位 |
| 結果 | `damage_formula` | int | 0 至無界 | 本次攻擊造成的最終傷害 |

**輸出範圍**:下界硬性夾在 **0**,不設「至少造成 1 點傷害」的地板——「預期無效果」是預判模式明訂的合法結果之一,傷害算到 0 是精準防禦/好感度佈局換來的正當結果,不是需要修飾的邊緣情況。上界目前無夾限,直接反映 `ATK`、`Φ` 的合法值,實務上界待好感度—位置連鎖系統(`Φ` 的值域)與未來單位數值表(`ATK`/`DEF` 的基準範圍)定案後才能收斂。

**範例**:`ATK=12`、`DEF=8`、`Φ=+3`(好感度佈局正向加成)→ `max(0, 12−8+3) = 7` 點傷害

**邊界行為**:
| 情境 | 代入 | 結果 | 說明 |
|---|---|---|---|
| `Φ` 極端負值 | `ATK=12,DEF=8,Φ=−999` | `0` | 防禦方可被完全免傷——精準站位+好感度佈局理論上能完全抵銷一次攻擊,呼應「以弱勝強」機制錨點,非 bug |
| `DEF=0` | `ATK=12,Φ=0` | `12` | 傷害等於原始攻擊力,無衰減 |
| `ATK=DEF`,`Φ=0` | `ATK=8,DEF=8,Φ=0` | `0` | 勢均力敵、無好感度介入時,0 傷害是自然穩態,不是異常 |
| `Φ` 極端正值(未設上限的已知風險) | `Φ=+500` | `504` | **待確認風險,已登記至 Dependencies**:若好感度—位置連鎖系統對 `Φ` 沒有自己的合法範圍上限,理論上可造成任意大傷害——須在該系統設計時明確聲明 `Φ` 值域,屆時本公式可能需要加 `min(Φ, Φ_max)` 夾限 |

### 公式二:敵方數值縮放公式(`enemy_stat_scaling`)

`enemy_stat = ceil(player_baseline_stat × (1 + enemy_advantage_pct))`

**變數:**
| 變數 | 符號 | 型別 | 範圍 | 說明 |
|---|---|---|---|---|
| 玩家同階基準數值 | `player_baseline_stat` | int | ≥0 | HP/ATK/DEF 三者分別代入本公式一次;數值來自尚未設計的單位數值表 |
| 敵方優勢百分比 | `enemy_advantage_pct` | float | [0, 1.0) 建議安全範圍,Tuning Knob | Core Rules #7「均勻比例」定案語意:HP/ATK/DEF 三者共用同一個 `enemy_advantage_pct`,不分別給不同係數 |
| 結果 | `enemy_stat` | int | ≥ `player_baseline_stat` | 敵方單位對應的 HP/ATK/DEF 有效值,餵給公式一的 `ATK`/`DEF` |

**取整規則**:採**無條件進位(ceil)**,不用四捨五入——四捨五入在「基準值小 + 百分比小」時會把優勢加成靜默捨去為 0(例如 `DEF=1, pct=0.20` 時 `round(1.2)=1`),違反「敵方優勢應恆成立」的機制錨點前提;`ceil` 保證只要 `pct>0` 且基準值 `>0`,`enemy_stat` 必然嚴格大於基準值,不會靜默失效。

**輸出範圍**:下界 = `player_baseline_stat`(`pct=0` 時退化為平手,合法邊界);上界隨 `pct` 線性無界。

**起始校準建議**:`enemy_advantage_pct = 0.20`(20%)——同類戰棋/戰術遊戲常見的敵方優勢落在 15%–30%,是「需要策略介入但不至於數值上打不過」的經驗起點;確切值待好感度—位置連鎖系統定案其加成幅度後交叉校準(若 `Φ` 能提供的加成遠小於 20%,`pct` 需下修,否則「以弱勝強」數學上不可達成)。

**範例**:`player_baseline` 為 `HP=30, ATK=10, DEF=6`,`pct=0.20` → `enemy_HP=ceil(36)=36`、`enemy_ATK=ceil(12)=12`、`enemy_DEF=ceil(7.2)=8`

**邊界行為**:
| 情境 | 代入 | 結果 | 說明 |
|---|---|---|---|
| `pct=0` | 任意基準值 | `enemy_stat = player_baseline_stat` | 合法下界,完全平手 |
| 基準值小、百分比小 | `DEF=1, pct=0.20` | `ceil(1.2)=2`(優勢保留) | 這正是選 `ceil` 而非四捨五入的直接證據 |
| `pct` 過大(未設上限的風險) | `pct=5.0` | `HP: ceil(30×6)=180` | **校準風險,已登記至 Tuning Knobs**:建議資料驗證硬性拒絕 `pct≥1.0` 的輸入,防止設計時誤輸入失控數值 |
| **`baseline=0`(2026-08-17(二)新增,回應 `/design-review` 第一輪 systems-designer 發現)** | `player_baseline_stat=0`,任意合法 `pct` | `ceil(0 × (1+pct)) = 0` | **DEFER-TO-CALIBRATION,歸入 OQ-2 一併處理**:變數表宣告 `player_baseline_stat` 定義域為 `int, ≥0`,`0` 是合法輸入(例如某單位刻意將 `DEF` 基準設為 0)。此輸入下敵方在該項數值上的優勢**靜默歸零**,字面上與 Core Rules #7「均勻比例…系統性高於我方」的措辭有落差——但這不是公式本身的缺陷(公式對此輸入行為良好,無負值/除零/無窮大),而是資料層須自行迴避的邊界:未來擁有 `player_baseline_stat` 數值表的系統,若某數值需要承載「敵方系統性優勢」這項承諾,該數值的基準下限應設為 ≥1,不設為 0。此註記本身不影響本公式或本文件既有 AC 的正確性,不重開裁決 |

### 公式三:可達格範圍公式(`reachable_tile_formula`)

`reachable_set(u) = { t ∈ Grid : accumulated_cost(origin, t) ≤ MP(u) ∧ occupied(t) = false }`
`accumulated_cost(origin, t) = min` over all legal orthogonal paths(不穿越已佔位格,終點除外)`Σ terrain_cost(每一步)`;無合法路徑時 `:= ∞`;`accumulated_cost(origin, origin) := 0`(單位不被自己擋路)。

**`ignore_occupancy` 參數(2026-08-17 新增,使用者裁決 R-UI1 甲案)**:完整簽章為 `reachable_set(u, ignore_occupancy=false)`,預設值 `false` 即上式語意。當 `ignore_occupancy=true` 時,`occupied(t) = false` 這個合取項、以及 `accumulated_cost` 的「不穿越已佔位格」路徑限制**同時**解除,其餘語意完全不變。此參數**僅供 UI Requirements 標示不可達成因**使用(見 UI Requirements「移動範圍呈現與不可達成因」),**不得作為移動合法性判定依據**——合法目的地永遠只取 `ignore_occupancy=false` 的輸出。

**變數:**
| 變數 | 符號 | 型別 | 範圍 | 說明 |
|---|---|---|---|---|
| 起始/目的座標 | `origin` / `t` | `(x,y)` | 棋盤範圍內整數座標 | — |
| 移動力 | `MP(u)` | int | ≥0 | Core Rules #2 已定案 |
| 地形移動成本 | `terrain_cost(tile)` | int | ≥1(硬性下限,資料寫入時驗證,非本公式夾限) | 依地形種類查表 |
| 佔位判定 | `occupied(tile)` | bool | — | 該格是否已被**除查詢單位 `u` 以外**的任一單位(不分敵我)佔據。**`u` 自身所在的 `origin` 不計為佔位**,故 `origin` 恆滿足 `occupied=false` 這個合取項,與下方「輸出範圍」的非空保證一致(2026-08-17 修正:原敘述為「已被任一單位佔據」,字面上會讓 `occupied(origin)=true` 而把 `origin` 排除出集合,與「輸出範圍」明文宣稱的「至少含 `{origin}`」互相矛盾;原有的「單位不被自己擋路」旁註只掛在 `accumulated_cost` 上,未涵蓋本合取項) |
| 忽略佔位旗標 | `ignore_occupancy` | bool | 預設 `false` | `true` 時解除佔位障礙;僅供 UI 標示不可達成因,不改變任何合法移動判定 |
| 結果 | `reachable_set(u)` | 座標集合 | 至少含 `{origin}` | 供 UI 呈現移動範圍的核心查詢輸出 |

**輸出範圍**:恆非空——零步路徑成本恆為 0,恆 ≤ 任意 `MP≥0`,即使 `MP=0` 或單位被完全包圍,集合至少含 `{origin}`。**`MP=0` 或被完全包圍時,單位雖無法移動到其他格,但仍可原地發動攻擊**(移動與攻擊是並列的允許操作,不要求先移動)。上界受棋盤大小與 `MP` 雙重夾限,天然有界。

**範例**:開放地形(全格成本 1),`origin=(0,0)`,`MP=2`,無其他佔位 → 以 `origin` 為中心、曼哈頓半徑 2 的菱形,共 13 格

**邊界行為**:
| 情境 | 結果 | 說明 |
|---|---|---|
| `MP=0` | `reachable_set={origin}`,但仍可攻擊 | 見上方裁決 |
| 目的格成本單獨大於 `MP` | 自然被排除,`accumulated_cost≥` 該格成本 | Dijkstra 展開本身天然安全,無需特判 |
| 全圖成本 ≡1(退化情境) | 等價於純曼哈頓距離 BFS 環狀範圍 | 與 Core Rules #1 距離量尺定義完全一致 |
| 單位被完全包圍 | `reachable_set={origin}`,與 `MP=0` 輸出相同但成因不同(路徑封死 vs 移動力不足) | 兩者的呈現層區分由 `ignore_occupancy=true` 的差集取得(見 UI Requirements「移動範圍呈現與不可達成因」);預設語意的輸出本身不攜帶成因 |
| `terrain_cost<1`(非法輸入) | 定義域外 | 資料驗證層級須在寫入時拒絕,非本公式運算時處理 |
| `ignore_occupancy=true` 且全圖無其他單位 | 兩種呼叫輸出相同,差集為空集合 | 無佔位時該參數無作用,UI 標示不出任何「被佔位擋死」格——這是正確行為,不是失效 |

*`systems-designer` 已諮詢(Formulas 屬高風險節,lean 模式下仍強制諮詢)。「W_mod」提案已依使用者裁決捨棄;「敵方數值均勻比例縮放」對齊既有 Core Rules #7,不重開;`Φ` 上界待好感度—位置連鎖系統設計時交叉確認,已登記為 Dependencies 待補項(見下節)。*

### 公式四:威脅範圍公式(`threat_range_formula`)(2026-08-17(三)新增,回應 `/design-review` 第二輪 BLOCKING-NOW B-2,使用者裁決乙案)

`threat_range(e) = { t ∈ Grid : ∃ r ∈ reachable_set(e, ignore_occupancy=false), manhattan_distance(r, t) ∈ [min_range(e), max_range(e)] }`

即:敵方單位 `e` 能移動到的每一格 `r`(依公式三既有語意),各自以其武器 `(min_range, max_range)` 投影出一圈可攻擊範圍,`threat_range(e)` 是這些投影範圍的聯集——集合中的任一格 `t`,代表「`e` 本回合有辦法移動到某格後攻擊到 `t`」。

**視線的刻意省略**:本公式**不**檢查視線(Core Rules #4)。任一格只要落在幾何射程投影內就算入威脅範圍,不論從 `r` 攻擊 `t` 是否實際被地形遮蔽阻擋。這是刻意的保守近似,理由:視線判定綁定特定的 `(r, t)` 配對,而 `r` 本身有多個候選(`e` 的整個可達格集合),若要精確排除被遮蔽的組合,威脅範圍會隨玩家考慮的候選目的地不同而變動,失去「一次查詢、涵蓋整回合決策」的用途。寧可讓威脅範圍**略為高估**危險(玩家看到某格在威脅範圍內、實際上因視線而安全),也不要低估(玩家以為安全、實際上會被打中)——高估的代價是玩家多一分警覺,低估的代價是直接命中 Player Fantasy 具名的「早知道」失敗模式,兩者不對等。

**保守性的邊界:佔位軸上本公式確實會低估(2026-08-18 新增,回應 `/design-review` 第四輪 BLOCKING-NOW——`game-designer` 發現、`creative-director` 判定為設計內容缺陷)**:上段以「寧可高估、絕不低估」作為省略視線檢查的正當性依據,但這項保守性**只在視線軸上成立,在佔位軸上不成立**,本公式在後者確實會低估威脅。成因:`threat_range(e)` 建立在 `reachable_set(e, ignore_occupancy=false)` 之上,而公式三的 `occupied(tile)` 明文「不論敵我」——因此 `e` 的可達格集合會被**其他敵方單位**當下的站位所限制。若在 `e` 自己的回合內,另一個敵方單位先行移開、讓出了原本堵住 `e` 的路徑,`e` 的真實可達集會**大於**玩家查詢當下所看到的那一份,`threat_range(e)` 相應擴大——玩家依查詢結果判定為安全的格子,可能實際上會被打中。

**本文件不修正此低估,理由與代價**:要精確涵蓋此情形,需要窮舉所有敵方單位在其回合內的移動序列組合(每個敵人的移動又會改變其他敵人的可達集,組合爆炸),成本不可接受,且結果會隨敵方 AI 實際選擇的行動而變,無法作為一次靜態查詢的輸出。因此本公式的輸出定義為「**依查詢當下盤面快照**計算的威脅範圍」,不含對敵方未來重新佈局的預測。**由此衍生的呈現層與教學義務(硬性)**:威脅範圍疊加圖**不得**被呈現、命名或教學為「絕對安全/絕對危險」的保證——它是「以當下盤面為準的威脅估計」。此揭露義務與上段視線軸的自我揭露對稱:兩者都是刻意接受的近似,差別在視線軸偏保守(高估)、佔位軸偏樂觀(低估),而**唯一不可接受的做法是讓玩家以為它是精確的**。教學/上手引導系統(#12)須涵蓋此概念(已同步 Dependencies #12 列);相關認知負荷風險已併入 Open Questions OQ-13 的 playtest 範圍。

**變數:**
| 變數 | 符號 | 型別 | 範圍 | 說明 |
|---|---|---|---|---|
| 敵方單位 | `e` | 單位識別碼 | 存活敵方單位 | 查詢目標 |
| 可達格集合 | `reachable_set(e, ignore_occupancy=false)` | 座標集合 | 見公式三 | 直接沿用公式三既有定義,不重新定義 |
| 武器射程 | `(min_range(e), max_range(e))` | `(int, int)` | 見 Core Rules #3 | `e` 當前裝備的武器分層 |
| 結果 | `threat_range(e)` | 座標集合 | ⊆ Grid,可為空集合 | 供 UI 呈現威脅範圍疊加圖(見 UI Requirements §1a)的查詢輸出 |

**輸出範圍**:下界可為空集合(理論邊界,例如 `e` 被完全包圍到連自身所在格都無法以任何射程覆蓋其他任何格,集合為空;此邊界情境極罕見但公式本身正確處理,不需特判)。上界受 `reachable_set(e)` 與 `max_range(e)` 雙重夾限,天然有界,與公式三同構。

**多敵聯集(2026-08-17(四)新增,回應 `/design-review` 第三輪 `godot-specialist`/`ux-designer` 共同指出的定義缺口)**:UI Requirements §1a 允許以「目前所有存活敵方單位」為輸入,但上式只定義單一 `e`。多敵情形的定義為逐敵聯集:

`threat_range_all(E) = ⋃ threat_range(e) for e ∈ E`,其中 `E` 為存活敵方單位集合。

**介面回傳形狀須同時提供兩種切面**:①**扁平聯集**(單一座標集合,供「這格會不會被打到」的二元判斷);②**逐敵拆分**(座標集合對每個 `e` 的歸屬,供「是誰威脅這格」的追因)。理由:只給扁平聯集時,玩家無法在多敵盤面上判斷「移開哪一個威脅來源就安全」;只給逐敵拆分時,呈現層每次都要自行聯集,而 Core Rules #10 a 項的即時性義務會被推給呈現層各自實作,增加漏項面。兩者由同一次查詢一併回傳,不是兩個介面。

**範例**:`e` 的 `reachable_set = { (0,0) }`(`MP=0` 或被包圍)、武器為遠程 `(2,4)` → `threat_range(e) = { t : manhattan_distance((0,0), t) ∈ [2,4] }`,即以 `(0,0)` 為中心的環狀區域(內半徑 2、外半徑 4)。

**邊界行為**:
| 情境 | 結果 | 說明 |
|---|---|---|
| `e` 的 `reachable_set` 僅含 `origin`(`MP=0` 或被包圍) | 威脅範圍退化為單一射程環 | 與公式三 `MP=0` 邊界一致,不需特判 |
| `min_range=max_range=1`(近戰) | 威脅範圍是 `reachable_set(e)` 每一格各自的曼哈頓距離 1 環,聯集後通常是 `reachable_set(e)` 外圍一圈加厚的環帶 | 直觀對應「近戰單位威脅範圍=移動範圍向外擴張一圈」 |
| `e` 已陣亡 | 查詢不合法(陣亡單位已移出佔位,不再是合法查詢對象)——具體介面錯誤處理慣例由 `/create-architecture` 決定,不影響本公式的數學定義 | 對照 Core Rules #6c「陣亡單位不再參與任何後續計算」 |

## Edge Cases

- **視線遮蔽的連線幾何(補充 Core Rules #4)**:攻擊方與目標不在同一行/列時,「連線經過的每一格」採**歐幾里得直線**的網格化演算法(Bresenham 類型)判定——在攻擊方與目標格心之間畫一條幾何直線,依演算法規則判定該線實際「進入」哪些格,逐格檢查是否標記為遮蔽。此幾何獨立於曼哈頓距離量尺(移動/射程的距離量測與視線的物理直線是兩件不同的事,不得混用同一套量尺)。
  **穿角情形的判定慣例(2026-08-17(三)新增,回應 `/design-review` 第二輪 BLOCKING-NOW B-1,使用者裁決甲案;2026-08-17(四)修正觸發條件、補上多穿角點的組合規則,回應 `/design-review` 第三輪 F3-1/F3-2——上輪的「兩側皆遮蔽才擋」裁決本體不變,只修正其適用範圍與合併方式)**:當攻擊方與目標的連線**恰好通過某個角點**(四格共用的頂點)時,「Bresenham 類型演算法」不是單一規格——Bresenham、supercover、DDA 等演算法在這個情形各自自洽卻可能產生不同的中繼格清單,而遠程 `max_range=4` 下穿角是日常盤面,不是罕例。本文件明文定案下列三條,合起來對任一射線給出唯一答案:
    1. **單一穿角點的判定(兩側皆遮蔽才擋)**:每一個穿角點,取其相鄰的兩個格子(射線左右兩側各一格),**須兩者皆標記「遮蔽」,該穿角點才判定為阻擋;只要其中一格未標記遮蔽,該穿角點即視為暢通**(即便另一格是遮蔽)。此慣例左右對稱、無隱藏偏向,玩家可透過「兩側都要擋」這條規則自行驗算,呼應支柱一的可預判性承諾。
    2. **逐穿角點獨立套用,再與普通中繼格 OR 合併**:一條射線可能通過**多個**穿角點(例如偏移 `(2,2)` 通過兩個:`(1,0)/(0,1)` 之間與 `(2,1)/(1,2)` 之間),也可能同時明確穿過若干**格心**(同一例中射線穿過 `(1,1)` 的格心,該格不具角點歧義)。第 1 條對**每一個**穿角點各自獨立套用;射線明確穿過格心的中繼格,依 Core Rules #4 的**普通單格規則**判定(該格標記遮蔽即阻擋)。最終結果為 OR 合併——**任一穿角點被判定阻擋、或任一普通中繼格標記遮蔽,該次攻擊即不合法**。此合併方式與 Core Rules #4「沿線任一格標記遮蔽即不合法」的既有語意一致,不是新增的獨立裁決。
    3. **穿角的觸發條件不限於 `|dx| = |dy|`**:上輪原文把「連線通過角點」等同於「`|dx| = |dy|` 的正對角偏移」,此等價**不成立**。射線由格心出發、恰好通過角點的充要條件是 `|dx|` 與 `|dy|` **各自能被 2 整除的次數相同**(形式化:`v₂(|dx|) = v₂(|dy|)`),而非兩者數值相等。遠程 `max_range=4` 之內符合此條件的偏移包含 `(1,1)`(`d=2`)以及 `(2,2)`、`(1,3)`、`(3,1)`(皆 `d=4`)——後兩者 `|dx| ≠ |dy|` 卻同樣穿角(`(1,3)` 的射線 `y = 3x` 在 `x = 0.5` 時 `y = 1.5`,恰為四格共用頂點),若沿用上輪的條件敘述將完全落在規則之外,中繼格清單重回實作分歧狀態,B-1 想消除的分歧只被消除一半。**實作上不需自行推導此算式**:直接以幾何方式偵測「射線是否同時落在某格的兩條邊界上」即可;算式僅供撰寫測試向量時列舉案例之用。
  此三條合起來會使遠程武器在穿角地形略微更有利,與 Open Questions OQ-18 已登記的「遠程可能偏強」風險同向,已於該項補充註記。
- **武器最小射程**:若目標與攻擊方的曼哈頓距離**小於**武器的 `min_range`(例如未來新增「純遠程、不能打相鄰格」的武器種類),該次攻擊不合法,判定方式與超出 `max_range` 相同(距離不在 `[min_range, max_range]` 區間內即不合法)。Tuning Knobs 定案的三個起始分層中,**遠程武器的 `min_range=2`**(近戰、中程為 1),因此本規則自第一天起就有實際案例觸發,不是預留的假想條款——遠程單位被敵方貼身時**無法對其發動攻擊**(2026-08-17(三)修正措辭,回應 `/design-review` 第二輪 grep 自核:原「無法反擊」的用詞與 States and Transitions 表「反擊」用詞範圍聲明不一致,此處描述的是攻擊方自己的攻擊旗標受盲區限制,非反擊機制),必須先退開,這是刻意的戰術代價(理由見 Tuning Knobs 射程分層)。公式與判定邏輯本就須支援 `min_range>1`,不得以特判方式處理。**(2026-08-13 修訂:原敘述為「三個起始分層皆以 1 為下界,此規則暫無實際案例觸發」,與 Core Rules #3「中程 min≈2」互斥;Tuning Knobs 定案數值時一併裁決並同步兩處,使用者裁決 R-G1 甲案。)**
- **陣亡單位的佔位立即釋放**:單位進入「陣亡」狀態(Core Rules #6)的同一結算步內,該格立即從 `occupied` 集合移除——不存在「屍體暫留擋路」的中間狀態,其餘單位的**移動範圍計算**自陣亡發生的下一次查詢起,即視該格為可通行。實作上此即時性由 Core Rules #10 c 項(佔位資料的所有權)保證,不得以節點樹存在性導出。
  **本條不涉及視線(2026-08-17(四)修正措辭,回應 `/design-review` 第三輪傳播失敗 P-1)**:陣亡**不會**改變該格的視線判定,因為依 Core Rules #4,單位(不論生死、不論敵我)**從來就不遮蔽視線**——該格是否遮蔽視線,自始至終只取決於地形的「遮蔽」標記,陣亡前後完全相同。**舊版措辭的缺陷**:原文寫「自陣亡發生的下一次查詢起,即視該格為可通行、**不遮蔽視線**」,而「自 X 起…不遮蔽」在本文件其他各處一律用於表達**狀態改變**,字面上暗示該格在陣亡前曾遮蔽視線——正是 Core Rules #4 的 B-5 裁決要排除的模型;若下游依此實作,會做出「活單位擋視線、死單位不擋」的錯誤行為。
- **移動路徑非唯一時的顯示**:當多條路徑通往同一可達格且累積成本相同(例如開放地形上的多條等長路徑),`reachable_tile_formula` 的可達性判定不受影響(只看是否存在 ≤MP 的合法路徑,不指定哪一條),但移動動畫/路徑預覽需要選定**一條**具體路徑呈現給玩家——具體選擇規則已於 **UI Requirements「路徑預覽與選路規則」**定案為三層決定性 tie-break(累積成本 → 最少轉彎 → 固定方位優先序),此處不重述;該規則屬呈現層,不影響本節任何規則的正確性。
- **預判模式必須讀取即時狀態(本條為 Core Rules #10 a 項的具名實例,2026-08-17(四)標注;總則涵蓋所有查詢介面,本條只是其中最早被發現的一個)**:預判標記(Core Rules #8)每次呼叫的回傳結果都必須反映呼叫當下的棋盤狀態(單位位置、HP、好感度加成),且恆與「從未呼叫過、只叫這一次」的結果完全相同(2026-08-17(三)修正措辭,回應 grep 自核:與 AC-11 的結果斷言式判準同步,不禁止特定實作手段——含快取——只要求輸出正確)——若呼叫之間棋盤狀態發生變化(例如同一回合內另一友軍單位已完成移動,改變了鄰接關係與好感度加成),預判結果必須反映最新狀態,否則會呈現與實際結算不符的預測,直接違反支柱一的可預判性承諾。
- **移動範圍/攻擊範圍疊加圖同樣必須讀取即時狀態(2026-08-17(二)新增,回應 `/design-review` 第一輪 BLOCKING-NOW #4;本條為 Core Rules #10 a 項的第二個具名實例,2026-08-17(四)標注——第三輪正是因為只有這兩個實例、而新增的 §1/§1a 查詢介面沒被涵蓋,才改立總則)**:與預判模式同理,移動範圍(`reachable_tile_formula`)與攻擊範圍/視線疊加圖(見 UI Requirements 第 2 節)在玩家仍停留於選取/檢視狀態期間,**不得**沿用先前一次計算所渲染的疊加結果——若疊加圖仍在畫面上顯示的期間,棋盤狀態發生變化(最典型情境:Core Rules #9 的可暫緩模型下,玩家在同一回合內操作了另一個單位,使其穿越或佔據了原本正在檢視之單位的移動/攻擊範圍內某格),下一次任何會導致該疊加圖重繪的事件(例如游標移動、面板重新取得焦點,具體觸發時機屬呈現層,由 UI Requirements 第 2 節/`/ux-design` 定案)發生時,疊加圖必須反映重繪當下的最新棋盤狀態,不得沿用重繪前快取的畫面或計算結果。這不改變 UI Requirements 第 2 節「每次刷新需兩趟 Dijkstra 展開」的既有效能討論(刷新的觸發頻率仍是 OQ-16 的校準範疇)——本條規則只定案**若重繪,結果必須正確**這個正確性義務,不定案重繪本身多久發生一次一次。對應驗收條件見新增 AC-20。
- **禁止友軍互攻**:本系統的攻擊行動只能以敵方陣營單位為合法目標,友軍單位不得被選為攻擊目標(不論其好感度數值為何)。「內鬨懲罰」是好感度—位置連鎖系統對站位的**被動數值懲罰**(降低鄰近友軍的有效戰力),不是本系統提供的一種可主動發起的攻擊行為——兩者不得混淆。
- **地形動態演變(活棋盤,系統 #14,Not Started)的邊界**:本系統的移動成本表/視線遮蔽標記假設在單一回合的結算步內保持穩定不變;地形規則隨劇情演變(支柱五)屬於系統 #14 的職責,若地形在戰鬥**進行中**(而非戰鬥之間)動態改變,本系統目前**不**定義行為——留待系統 #14 設計時,雙方共同確認是否存在「戰鬥中途地形改變」這個情境,若存在則須回頭補上本系統對應的重新計算時機規則。

## Tuning Knobs

本節旋鈕全部由 Core Rules 與 Formulas 的變數機械導出,不新增任何前面章節未定義的概念。每個旋鈕標註:來源、起始值、安全範圍、過高/過低的具體後果、與其他旋鈕的交互。**起始值皆為待實測校準的建議值,不是定案平衡數字**——本專案尚無可玩建置,任何精確數字都缺乏實證基礎(比照 `save-system.md` 對 `save_write_max_duration_ms` 的既有寫法)。

### 1. `enemy_advantage_pct` — 敵方數值優勢百分比

| 欄位 | 內容 |
|---|---|
| **來源** | 公式二 `enemy_stat_scaling`;落實 Core Rules #7「以弱勝強」機制錨點 |
| **型別/值域** | float,`[0, 1.0)`。**資料驗證層須硬性拒絕 `≥1.0` 的輸入**(見公式二邊界行為) |
| **起始建議** | `0.20`(20%) |
| **影響的玩法面向** | 玩家與敵方的基礎數值落差,即「需要多少策略介入才能打平」 |

- **設太高**(例如 >0.35):好感度佈局能提供的 `Φ` 加成不足以抵銷數值差,「以弱勝強」在數學上不可達成——玩家無論多精準都會輸,支柱一的可預判性反而變成「算得出自己必敗」。
- **設太低**(例如 <0.10):敵方優勢被玩家的基礎數值直接輾壓,好感度佈局與射程計算失去存在理由,本系統退化成沒有策略深度的移動+平砍。
- **交互(關鍵)**:與 `Φ_max`(由 #5 擁有)**強耦合**。兩者必須滿足 `Φ` 可提供的實際加成幅度 ≥ `enemy_advantage_pct` 造成的數值差,否則機制錨點失效。**#5 定案 `Φ` 值域後必須回頭交叉校準本旋鈕**,不得各自獨立調整(見下方「跨系統校準義務」)。

### 2. 武器射程分層 `(min_range, max_range)`

| 分層 | `min_range` | `max_range` | 戰術定位 |
|---|---|---|---|
| **近戰** | 1 | 1 | 唯一能處理貼身情境的分層;前排主力 |
| **中程** | 1 | 2 | 泛用主力,無盲區,可近可退 |
| **遠程** | **2** | 4 | 有近身盲區,不能打相鄰格;必須與敵人保持距離 |

- **來源**:Core Rules #3(結構)+ 本節(數值);2026-08-13 使用者裁決 R-G1 甲案。
- **此組數值同時解決一項內部矛盾**:Core Rules #3 原寫「中程 min≈2」,Edge Cases「武器最小射程」原寫「三個起始分層皆以 1 為下界」,兩者互斥。本輪定案為**中程 min=1、遠程 min=2**,並同步修訂 Edge Cases 該條目的敘述(見該節)。
- **遠程設 `min=2` 的設計理由**:傷害公式 `max(0, ATK − DEF + Φ)` **不含武器係數**,射程長短不付出任何傷害代價。若遠程 `min=1`,其射程集合會完全涵蓋近戰與中程,近戰武器將沒有存在理由(嚴格劣勢)。近身盲區是本文件目前**唯一**在抑制遠程優勢的機制。
- **副作用(刻意)**:遠程單位被貼身時必須先退開,這把遠程單位推向棋盤後方,釋出前排空間給好感度佈局——直接服務 Player Fantasy 的空間餘裕原則,不只是平衡補丁。
- **設太寬**(遠程 `max` >4):遠程單位的威脅範圍(移動力+射程)覆蓋過大棋盤比例,玩家的站位選擇失去意義,且 UI 呈現的攻擊範圍會大到難以判讀。
- **設太窄**(全部 `max` ≤1):直接違反 Core Rules #3 的硬性下限(「至少須同時存在射程 1 與射程 ≥2 兩種武器」)與 `game-concept.md` MVP 必要內容第 1 項,v2 原型已驗證這會讓好感度機制被空間排擠。
- **交互**:與 `base_mp` 共同決定「威脅範圍」= 移動力 + `max_range`。起始值下遠程單位威脅半徑為 `4+4=8` 格——調整任一方都會改變安全距離的實際意義。
- **⚠️ 校準前提已於 2026-08-17 改變(Core Rules #9 行動經濟採乙案的直接後果)**:順序自由意味著遠程單位可以**「打完就退」**——在 `d=2` 開火後,再用整個移動旗標退開至多 `base_mp` 格,起始值下開火後可位於距目標 `2+4=6` 格外。這使遠程單位的**開火後暴露風險**大幅低於原本的校準假設(原假設是開火站位即為敵方回合的承受站位)。**近身盲區這條規則本身仍然生效**(遠程確實無法攻擊相鄰格,Edge Cases 的「必須先退開」敘述維持成立),但它作為遠程抑制機制的**實際力度已被削弱**——盲區只懲罰「回合開始時已被貼身」,不再懲罰「主動進場開火」。**後果**:遠程分層可能較原設計偏強,`max_range=4` 與 `base_mp=4` 這組數值須在首次可玩建置時一併重新檢視,不得沿用 2026-08-13 的校準推論。已登記 Open Questions。

### 3. `base_mp` — 單位基礎移動力

| 欄位 | 內容 |
|---|---|
| **來源** | Core Rules #2;公式三 `reachable_tile_formula` 的 `MP(u)` |
| **型別/值域** | int,`≥0`。建議安全範圍 `[3, 6]` |
| **起始建議** | `4` |
| **影響的玩法面向** | 每回合的重新佈局自由度;站位錯誤的懲罰輕重 |

- **設太高**(>6):站位錯誤幾乎沒有代價(下回合就能走回來),支柱三「確定性代價」被稀釋,好感度佈局也失去「必須提前規劃」的張力。
- **設太低**(<3):好感度佈局可能因為單位挪不動而**實際上無法執行**——v2 原型已驗證好感度機制會被空間因素排擠,這是已知的真實風險而非假想。
- **交互**:與 `terrain_cost` 是**相乘關係**,不是相加。起始值下,`base_mp=4` 表示平地 4 格 / 全森林 2 格 / 全山地 1 格。調高地形成本級距等同於調低有效移動力。

### 4. `terrain_cost` — 地形移動成本表

| 地形 | 成本 |
|---|---|
| 平地 | 1 |
| 森林 | 2 |
| 山地 | 3 |

- **來源**:公式三的 `terrain_cost(tile)`;硬性下限 `≥1` 已由公式三定義域規定(資料寫入時驗證,非運算時夾限)。
- **起始建議**:三階(1/2/3)。
- **設太高**(最高階 >3):搭配 `base_mp=4` 時,高成本地形實質上變成不可進入區域,但**不會**觸發公式三「無合法路徑」的明確語意,而是靜默表現為可達格突然縮小——玩家難以區分「走不到」與「被卡住」(Edge Cases 已標記此呈現需求)。
- **設太低**(全部 =1):地形失去戰術意義,公式三退化為純曼哈頓 BFS,棋盤變成無地貌的空盤。
- **本表不含「不可通行」地形**:目前三階皆為有限成本。若未來需要真正的牆壁/峽谷,須另行決定以 `cost=∞` 或獨立旗標表達,並回頭確認 Edge Cases「單位被完全包圍」條目仍然成立(已登記 Open Questions)。

### 5. `max_occlusion_ratio` — 遮蔽格佔比上限

| 欄位 | 內容 |
|---|---|
| **來源** | Core Rules #4(視線遮蔽);回應 `game-concept.md`「視線通透度指標缺口」 |
| **型別/值域** | float,建議 `[0, 0.5]` |
| **起始建議** | `0.25`(任一關卡的遮蔽格不得超過全圖 25%) |
| **影響的玩法面向** | 遠程武器的實際效益;空間餘裕原則能否真正兌現 |

- **性質**:這是本系統對**關卡設計的硬性約束**,不是關卡自由裁量的參數。由本系統擁有的理由:遠程武器提供的空間餘裕效益是本系統 Player Fantasy 明文承諾的,遮蔽率過高會直接抵銷它——閘門必須放在做出承諾的系統這一側,承諾才可被驗證。
- **設太高**(>0.4):遠程武器的 `max_range=4` 在多數站位下無法實際發揮,空間餘裕原則名存實亡,好感度佈局重新與戰鬥站位搶奪同一塊空間(v2 原型的失敗模式)。
- **設太低**(<0.1):視線檢查規則形同虛設,Core Rules #4 的計算成本卻仍要付出,且棋盤缺乏地貌變化。
- **交互**:與**射程分層**耦合——遮蔽率越高,遠程 `max_range` 的邊際效益越低;兩者不可獨立校準。亦與 `terrain_cost` 有隱含耦合:若遮蔽格同時是高成本地形(常見設計,例如森林既遮蔽又難行),對機動性與視線形成雙重壓縮,實測時須分開量測。

### 跨系統校準義務(硬性)

`enemy_advantage_pct` 與 `Φ_max` **不得各自獨立校準**。Core Rules #7 明文指定好感度佈局帶來的加成是抵銷敵方數值優勢的**唯一**機制(本系統無隨機判定可作為變數),因此兩者必須滿足:

> `Φ` 在合理佈局下可提供的實際加成幅度 **≥** `enemy_advantage_pct` 造成的數值差

若此不等式不成立,「以弱勝強」在數學上不可達成,Core Rules #7 與 Player Fantasy 第一段的承諾同時失效。**#5 好感度—位置連鎖系統定案 `Φ` 值域時,必須回頭與本旋鈕交叉校準,並在雙方文件記錄校準結果**——此義務同時登記於 Dependencies 對 #5 的待補項。

## Visual/Audio Requirements

*本節由 `art-director` 諮詢產出(2026-08-13)。**本專案尚未執行 `/art-bible`**,無色彩、字型、美術風格可依循——因此本節只定義**必須被玩家看懂/聽懂的資訊**與**必須可區分的狀態**,不定案任何美術實作。任何未來的視覺風格,只要滿足本節的可區分性要求,即符合本系統需求。具體美術實作項目已登記於 Open Questions。*

**本節的取捨基準**:依 `game-concept.md` MDA 美學優先序,**Challenge 為第 1 優先、Sensation 為第 4(最低)**。因此:**任何會讓玩家多花一次「重新確認」才能讀懂戰場的處理,即使更有打擊感,都是錯誤選擇**。下列每項需求皆標注其服務的支柱或具名失敗模式。

### 1. 狀態/範圍視覺化

#### 1.1 移動範圍:可達,以及兩種成因不同的不可達

| 狀態 | 必須傳達 | 為何是獨立狀態 |
|---|---|---|
| 可達格 | 本回合可移動至此 | 規劃站位的基本資訊 |
| 不可達——**移動力不足** | 所有合法路徑成本皆 > 目前 MP | 玩家的解法是「換單位或等下回合」 |
| 不可達——**被佔位擋死** | 路徑被單位堵死,即使名目 MP 足夠 | 玩家的解法是「先移動擋路的隊友」 |

兩者若合併為單一「不可達」樣式,玩家會誤判解法——直接命中 Player Fantasy 具名的失敗模式「移動/射程範圍的顯示與實際結算不一致」。公式三 Edge Cases 已明文要求區分呈現(「單位被完全包圍」與 `MP=0` 輸出相同但成因不同)。

> **介面缺口(`art-director` 諮詢時發現)——已於 2026-08-17 關閉**:公式三 `reachable_tile_formula` 原本只回傳可達格集合,**不輸出不可達的成因**,無法支撐上表的三態區分。本節將「必須能區分」定為硬性需求;對應的查詢介面已由 **UI Requirements「移動範圍呈現與不可達成因」**定案(公式三新增 `ignore_occupancy` 參數,呈現層取差集,使用者裁決 R-UI1 甲案),此處不重述其運算。

#### 1.2 武器射程三分層(尤其遠程盲區)

| 分層 | 覆蓋(曼哈頓) | 圖形性質 |
|---|---|---|
| 近戰 (1,1) | 距離恰為 1 | 單環,無盲區 |
| 中程 (1,2) | 距離 1–2 | 實心菱形,無盲區 |
| 遠程 (2,4) | 距離 2–4,**排除距離 1** | **環狀(中心鏤空)** |

**硬性規則**:
- 所有範圍圖形一律呈現為**曼哈頓菱形**,不得為了視覺順眼而畫成圓形或方形。Core Rules #1 明訂曼哈頓是唯一距離量尺。這是明確的 Sensation-vs-Challenge 取捨案例:柔化菱形邊角更悅目,但會讓玩家目測時系統性算錯格數——此處選可預判性。
- **遠程盲區絕不得被吸收進「可攻擊」的視覺語言**。它是本文件**唯一**抑制遠程優勢的機制(見 Tuning Knobs)。誤讀盲區為可攻擊會導致致命的站位誤判,且屬於「早知道」型挫折,正是 Player Fantasy 明訂要消除的失敗類型。
- **盲區格不另設獨立視覺狀態,與「範圍外」共用同一處理**(2026-08-13 使用者裁決 R-VA1 乙案)。即遠程的攻擊範圍疊加圖呈現為中心鏤空的環,鏤空處不加任何特殊標示,與距離 5 以上的格子看起來相同。**此裁決的取捨**:狀態數量少、實作與教學成本低;代價是玩家無法從畫面主動讀出「敵人站在這裡對我的遠程單位是安全的」這項戰術資訊,只能在嘗試選取時被拒絕音/拒絕回饋告知(見第 5 節、第 6 節第 3 點的範圍限定)。**此取捨的實際影響待 playtest 驗證**——若玩家反覆誤判遠程單位的安全距離,應重新評估是否升級為獨立第三態(`art-director` 原建議案),已登記 Open Questions。

#### 1.3 視線遮蔽:「範圍內但不可攻擊」是第三態

Core Rules #4 明文:視線被擋的格子「須明確標示為不可攻擊而非隱藏選項」。攻擊範圍疊加圖因此至少需三層權重:

| 層級 | 條件 |
|---|---|
| 無疊加 | 距離不在 `[min_range, max_range]` 內 |
| 疊加:合法可攻擊 | 距離在區間內 **且** 視線暢通 |
| 疊加:範圍內但不可攻擊 | 距離在區間內 **但** 視線被遮蔽格阻擋 |

若第三層被畫成與「無疊加」相同(即被隱藏),玩家會誤判可攻擊格數,違反 Core Rules #4 的明文要求。

**與 1.2 盲區處理的差異(刻意,非不一致)**:視線阻擋是**第三態**、盲區是**併入範圍外**,兩者處理不同。理由:視線阻擋由 Core Rules #4 明文要求「不得隱藏」,是規則層級的硬性義務;盲區則無對應的規則層要求,其呈現方式屬可裁決範圍,本輪裁定從簡。

**近戰的簡化**:近戰不受視線檢查(Core Rules #4),其範圍疊加圖只需二元狀態,**不需實作第三態**——避免過度設計。

#### 1.4 遮蔽地形本身

遮蔽(視線)與高移動成本(森林/山地)是**正交屬性**——同格可能兼具(Tuning Knobs 已提及此耦合),也可能只有其一。視覺語言必須讓玩家**分別**讀出「這格移動貴不貴」與「這格擋不擋視線」,不得合併為單一「特殊地形」標示。理由:兩者分屬本系統兩把不同的尺(曼哈頓距離 vs Bresenham 幾何),Edge Cases 已明文警告「不得混用同一套量尺」——此禁令對呈現層同樣成立。

### 2. 攻擊/傷害回饋(含合法的 0 傷害)

本系統零隨機、無命中判定,**沒有「miss」這個狀態**。每次攻擊都結算出 ≥0 的傷害,0 傷害是「防禦方精準佈局換來的正當結果」(見 Formulas),不是異常。

| 需求 | 理由 |
|---|---|
| 傷害數值**含 0 在內必須可見地顯示**,不得因為是 0 就隱藏 | 隱藏 0 會讓攻擊看起來「什麼都沒發生」,玩家誤判為操作未生效的 bug,而非我方防禦生效 |
| 0 傷害須沿用「攻擊已合法結算」的回饋語言(仍有攻擊動作、仍有數值呈現),只是數字為 0 | 0 傷害**不得**重用「非法操作/無法選取」的視覺語言——那是完全不同的系統狀態,混用會把「精準防禦」誤讀成「這次操作失敗」 |
| 傷害回饋須讓玩家看出 `Φ`(好感度—位置修正)對該數字的貢獻,而非只給結算後的單一整數 | 支柱二要求好感度是「可操作的空間戰術要素」而非劇情裝飾。若回饋只顯示最終數字,`Φ` 的因果貢獻在玩家認知裡不可見,支柱二在回饋層失效。本節只定案「必須拆解出 `Φ` 的貢獻」;**呈現位置已於 UI Requirements「攻擊確認與傷害拆解面板」定案**(確認/預判面板完整拆解、結算飄字顯總數+`Φ` 方向標記,使用者裁決 R-UI3 甲案),此處不重述 |

### 3. 預判模式三態回饋

**兩個獨立要求**:

1. **預判與已結算的呈現體系必須完全不同**,不得只是同一套視覺加註「(預覽)」。預判是純函數、不寫入任何狀態(Core Rules #8);若視覺上與已結算共用同一渲染層,玩家在快速操作時會混淆「假設」與「事實」,支柱一的核心承諾即名存實亡。
   **建議做法(功能性,非美術決定)**:預判結果綁定在「候選目的地」這個暫時性標記上,只在玩家持續停留於該候選格時存在,一離開即整體消失,不留在任何常駐 HUD 元素中——**用生命週期本身做區隔,比用外觀做區隔更穩固**。
2. **三態彼此互斥且可辨識,「無效果」尤其需專門處理**——理由同 0 傷害:「無效果」代表系統已算過、答案是中性,不是「按鈕沒反應」。

**「無效果」與「已結算的 0 傷害」建議共用同一套識別符號**(一個在預判層、一個在結算層)。兩者語意上是同一件事的兩個時態——「這一步算出來沒有正負效果」——共用符號讓玩家用同一套心智模型理解,並直接呼應零隨機系統「沒有意外」的承諾。

### 4. 陣亡回饋

1. **即時消失本身的可讀性**:單位陣亡後於同一結算步內立即移除、無屍體暫留(Core Rules #6c)。純粹的瞬間消失容易被讀成畫面故障。**此處保留最小限度的移除過渡**——但這不是為了打擊感而加的 Sensation,而是**維持 Challenge 層級清晰度所必要**:沒有任何過渡的瞬間消失,玩家無法確認這是死亡判定生效還是畫面出錯,本身就構成可預判性缺口。取捨基準不是「加不加特效」,而是「省略是否會製造新的判讀模糊」。
2. **好感度連鎖後果的可追溯性**:單位死亡會觸發好感度通知,並可能改變其他存活單位的鄰接加成(`Φ`)。這是 Player Fantasy 具名的失敗模式「陣亡等狀態轉換造成的資訊斷裂」。**死亡回饋與受影響單位的加成變化回饋須為兩個先後可辨識的視覺事件**,不得疊在同一瞬間——讓玩家能按時序讀出因果鏈,而非被同時發生的多個變化淹沒。具體節奏待美術/HUD 動效階段。

游標在目標死亡後的重新解析,其高亮呈現歸屬 `cursor-highlight-state.md` 與戰鬥 HUD,本節不重述;僅要求「重新解析後的游標落點轉換須為可視過渡而非瞬間跳變」,理由同上。

### 5. 音效需求(GDD 層級)

| 事件 | 音效必須傳達 | 理由 |
|---|---|---|
| 合法動作確認 | 操作合法且已被接受 | 本專案全手把支援、無游標,音效是唯一不佔用視覺注意力的確認通道 |
| **非法動作嘗試**(選中盲區/視線被擋/不可達格/**旗標已用過**,2026-08-17(二)補上「旗標已用過」——Core Rules #9 於 2026-08-17 首版新增後未回頭同步本表,回應 `/design-review` 第一輪傳播失敗 P2) | 操作被系統**拒絕**,不是輸入沒收到 | 拒絕音必須與「靜默」明確不同——沉默在快節奏操作下會被讀成「輸入沒被收到」。與非法選取的視覺回饋共構雙通道確認。**依 1.2 的裁決,盲區不另設視覺狀態,因此本項拒絕音是玩家得知「這是遠程單位死角」的主要通道**,其可辨識性要求比其他非法情境更高。**旗標已用過的拒絕情境在可暫緩模型下屬高頻**(玩家隔了數個單位才回頭操作,忘記某旗標已用掉是常見情形,不是邊緣案例) |
| 攻擊結算——傷害 >0 | 命中並造成傷害 | 一般結算回饋 |
| 攻擊結算——**傷害 =0** | 合法命中但被完全抵銷 | 須與「傷害>0」及「非法拒絕」**三方互不相同**:沿用拒絕音會讓玩家以為攻擊沒發動;完全沉默會讓玩家以為系統沒反應 |
| 陣亡 | 該單位已永久移除,結算完成 | 與傷害音區隔,標記狀態轉換的終局性 |
| 預判模式進入/離開 | 目前看的是假設結果,非既成事實 | 在玩家來不及分辨 UI 差異時,提供不佔視覺頻寬的狀態確認 |
| 預判三態(正/負/無) | 三態可辨即可,輕量處理 | 優先序低於上列各項(Sensation 排序最低),建議僅做最小化音高/音色差異,不投入不成比例的製作資源 |

具體音色、音長、是否有旋律動機待未來音訊方向與 art bible 決定;本節只定案「以上事件之間必須互相可辨」。

### 6. 無障礙限定條件

依 `.claude/docs/technical-preferences.md`(全手把對等、無游標、禁止 hover-only)與 `design/ux/accessibility-requirements.md`:

1. **本文件定義的任何狀態區分,一律不得只靠顏色作為唯一辨識依據**——須搭配形狀、圖示、邊框、動畫或音效等非色彩通道。**本項為原則陳述,適用於本文件(含未來修訂新增)的每一個狀態區分;下方僅為非窮盡範例,不是本項的涵蓋範圍上限(2026-08-17(三)修訂,回應 `/design-review` 第二輪 ux-designer 發現:本清單已連續 3 次因新規則加入而漏未同步——第一輪 P1、本輪 UI Requirements §6 手把清單、本清單自身——改為原則陳述以根絕此類遺漏,而非再修補一次列舉)**:可達/兩種不可達成因、三層射程、LoS 阻擋、0 傷害、預判三態、**單位當前行動狀態的各個可觀測值**(2026-08-17(四)修正:原寫「三態」不精確——依 Core Rules #9 雙旗標模型,面板上至少有四個可觀測值:皆未用/只剩攻擊/只剩移動/已行動)、地形成本階層(平地/森林/山地)、遮蔽標記本身、單位陣營(敵/我)、武器分層/射程識別、**敵方威脅範圍疊加圖**(2026-08-17(三)新增,見 UI Requirements §1a)。此延續 `cursor-highlight-state.md` 對三態高亮已做出的同一承諾。
2. **禁止「hover 才看得到理由」的模式**:視線阻擋的說明性資訊,不得只在懸停某格時才出現(常見策略遊戲 tooltip 模式)。本專案明確禁止此模式,非次要建議——須在選定單位/武器後持續呈現於範圍疊加圖本身。此同時服務支柱一:被動試探式資訊本質上是「行動後才知道」,與可預判性矛盾。
3. **遮蔽地形必須能被「主動察覺」,而非「嘗試後被拒絕」才發現**——否則玩家永遠是事後才知道,正是「早知道」失敗模式的定義。
   > **本項的範圍限定(2026-08-13,配合 1.2 使用者裁決 R-VA1 乙案)**:本項**明文不涵蓋遠程盲區**。乙案選擇讓盲區與「範圍外」共用視覺處理,其直接後果就是盲區只能在嘗試選取被拒絕時才被察覺——與本項的原則相反。此為**已知並接受的取捨**,不是疏漏:盲區的位置是可從武器射程規則直接推導的固定幾何(永遠是自身相鄰的 4 格),與遮蔽地形「因關卡而異、必須看畫面才知道」的性質不同,推導成本遠低於後者。**緩解**:第 5 節的拒絕音對盲區情境負有更高的可辨識性要求;教學/上手引導系統(#12)須明確教過遠程盲區這個概念。**待驗證**:若 playtest 顯示玩家仍反覆誤判遠程安全距離,應重新評估 1.2 的裁決,見 Open Questions。
4. **動畫/轉場類回饋須有可讀的靜態終態**:即使動畫被關閉或跳過(未來若有 reduce-motion 選項),棋盤在動畫結束後的靜態畫面本身須完整傳達狀態,不得有資訊只存在於過程中而終態不呈現。

## UI Requirements

*本節為 **GDD 層級**的介面需求:定義「必須讓玩家取得哪些資訊、透過哪些查詢、在什麼生命週期內」,**不定案版面座標、控制項外觀、字級或動效曲線**。本專案尚未執行 `/art-bible`,亦尚未執行 `/ux-design`。正式 UX spec 於 Pre-Production 產出,實作故事應引用該 spec 而非本節。*

### 1. 資訊查詢模型:游標即檢視

本專案全手把對等、無游標裝置假設、明文禁止 hover-only(見 `.claude/docs/technical-preferences.md`、`design/ux/accessibility-requirements.md`)。因此:

- 「檢視某一格的狀態」的唯一機制是**把游標移到該格**。**格位資訊面板**須隨游標所在格**即時更新**,不得要求額外確認鍵,不得只在滑鼠懸停時出現。
- 格位資訊面板的最小必要欄位:該格**地形種類**、**`terrain_cost`**、**是否標記遮蔽**、**佔位單位**(若有)之陣營/HP/當前狀態、**武器分層與 `(min_range, max_range)`**、**當前 MP**(2026-08-17(三)新增,回應 `/design-review` 第二輪 BLOCKING-NOW B-2,使用者裁決乙案)——缺少這兩項時,玩家無法透過本節宣稱的「唯一檢視機制」算出敵方單位的威脅範圍(見下方新增「1a. 敵方威脅範圍疊加圖」)。
- **「當前狀態」不得只顯示「可行動 / 已行動」**:依 Core Rules #9 的雙旗標行動經濟,「可行動」是複合狀態,面板必須讓玩家分辨出該單位**還剩哪個旗標可用**(皆未用 / 只剩攻擊 / 只剩移動)。只呈現二元狀態會讓玩家無法規劃回合內的操作順序——而順序自由正是此模型的核心價值,讀不出剩餘旗標等於這個自由度不存在。
- `terrain_cost` 與遮蔽標記**必須分欄呈現**,不得合併為單一「特殊地形」欄位——落實 Visual/Audio 第 1.4 節的正交性要求。
- 面板更新前須查詢 `cursor-highlight-state.md` 的有效性旗標(見該文件 Core Rules #2「下游預覽渲染義務」)。旗標為無效時,面板須呈現明確的**未解析態**,**不得沿用上一格的殘留內容**——殘留內容是 Player Fantasy 具名失敗模式「狀態轉換造成的資訊斷裂」的直接成因。
- **回合層級的剩餘旗標總覽(2026-08-17(二)新增,回應 `/design-review` 第一輪 BLOCKING-NOW #5)**:格位資訊面板本身是逐格查詢——玩家須把游標移到某單位所在格,才能得知該單位的剩餘旗標狀態。但 Core Rules #9 的「可暫緩」模型明確設計成讓玩家在同一回合內操作多個單位、暫緩部分單位的行動,這使得「我方這回合還有誰沒動完」成為一個必須被回答、卻無法只靠逐格查詢有效率回答的問題(在多單位的忙碌回合中,逐格開過整張棋盤才能確認並不可行)。因此:本系統須額外提供一個**回合層級的查詢介面**——列出我方目前所有存活單位、依當前狀態分組或標示(皆未用 / 只剩攻擊 / 只剩移動 / 已行動),供戰鬥 HUD(#10)渲染為某種形式的單位總覽(名冊列表、迷你圖示列等,版面由 #10 決定,本節只定案**必須有這筆資料可查詢**)。此為本節「必須提供哪些資訊項」職責範圍內的資料層義務,不是 #10 的版面裁量範圍——已同步更新 Dependencies 表對 #10 的介面需求。**本介面受 Core Rules #10 a/b 項約束**(即時性 + 單一快照原子性),驗收條件見 AC-22:總覽面板顯示期間玩家使用了某單位的旗標時,重繪須反映新狀態,不得沿用面板開啟時的快照(2026-08-17(四)補上,回應第三輪 BLOCKING-NOW F3-4)。

### 1a. 敵方威脅範圍疊加圖(2026-08-17(三)新增,回應 `/design-review` 第二輪 BLOCKING-NOW B-2,使用者裁決乙案)

格位資訊面板的武器分層/MP 欄位(見上)只解決「單一敵方單位的射程/MP 是多少」,不解決「這格對所有附近敵人而言安不安全」這個玩家實際要做的判斷——多個敵方單位同時存在時,逐一心算每個敵人的威脅範圍在忙碌盤面上不切實際(呼應 Visual/Audio 第 1.2 節、Open Questions OQ-13 已登記的「多敵人同時判讀」風險)。本系統須額外提供一個**威脅範圍查詢介面**:

- **輸入**:一個敵方單位識別碼(或「目前選取的所有存活敵方單位」)。
- **輸出**:一組座標集合;多敵輸入時同時回傳扁平聯集與逐敵拆分兩種切面(定義與理由見 Formulas 公式四「多敵聯集」,2026-08-17(四)補上)。
- **即時性**:本介面受 **Core Rules #10 a/b 項**約束(即時性 + 單一快照原子性),驗收條件見 AC-22。**這不是可選項**:公式三的 `occupied` 明文「不論敵我」,故我方單位移動會改變 `threat_range(e)` 的正確答案,而 Core Rules #9 的可暫緩模型明文允許玩家在疊加圖顯示期間移動我方單位(2026-08-17(四)補上,回應第三輪 BLOCKING-NOW F3-4)。
- **呈現**:由戰鬥 HUD(#10)決定具體版面與觸發方式(例如切換鍵顯示/隱藏疊加圖),本節只定案**必須有這筆資料可查詢**,不定案呈現形式——與上方「回合層級剩餘旗標總覽」的職責劃分方式相同。
- **並存性屬資訊可得性、不屬版面裁量(2026-08-17(四)新增,回應第三輪 `ux-designer` ADVISORY)**:威脅範圍疊加圖**須能與被操作單位自身的移動範圍疊加圖同時可見**,不得實作為互斥的模式切換。理由:本疊加圖的存在目的是讓玩家「在評估某個候選落點時,同時看到該落點是否受威脅」——若必須關掉移動範圍才能看威脅範圍,玩家得靠記憶跨兩個畫面比對,該用途即失效,且回到本文件反覆要防的「事後才知道」模式。**具體如何在視覺上同時呈現兩層而不互相淹沒**(層次、透明度、圖樣區分)屬 `/ux-design` 範疇,但「必須可同時可見」這件事屬本節職責,不下放。
- **與 R-VA1 乙案(遠程盲區不獨立呈現)的一致性**:威脅範圍疊加圖回答的是「這格會不會被打到」,不回答「為什麼打不到」——盲區格本來就不在敵方的威脅範圍內(不屬於 `threat_range_formula` 的輸出,因為盲區距離小於 `min_range`),因此威脅範圍疊加圖與盲區的呈現裁決不衝突,兩者是同一底層資料的不同切面(已回頭同步 Open Questions OQ-13)。

### 2. 移動範圍呈現與不可達成因

Visual/Audio 第 1.1 節已把「可達 / 移動力不足 / 被佔位擋死」三態訂為硬性需求,但公式三原本不輸出成因。**本節定案該缺口的介面形式(2026-08-17 使用者裁決 R-UI1 甲案)**:

公式三新增布林參數 `ignore_occupancy`(定義見 Formulas 公式三,本節不重述)。呈現層據此取得三個**互斥且窮盡**的集合:

| 呈現狀態 | 集合運算 |
|---|---|
| 可達 | `A = reachable_set(u, ignore_occupancy=false)` |
| 不可達——**被佔位擋死** | `B \ A`,其中 `B = reachable_set(u, ignore_occupancy=true)` |
| 不可達——**移動力不足** | `Grid \ B` |

**硬性約束:**
- `A ⊆ B` 恆成立(解除障礙只會擴大或維持集合),故 `B \ A` 恆為良定義;三集合的聯集恆等於 `Grid`,**無第四類殘留**——滿足 Visual/Audio 第 1.1 節的區分要求,且不留任何未定義狀態的格子。
- **`B \ A` 涵蓋兩種子情境,刻意合併為單一呈現狀態**(2026-08-17 補充聲明):①**目的格本身被其他單位佔據**(站不上去);②**通往該格的所有路徑被其他單位堵死**(名目 MP 足夠但走不到)。Visual/Audio 第 1.1 節只描述了②,但兩者對玩家的解法完全相同——**先把擋路的單位移開**——故不再細分為第四種狀態。若未來出現「解法不同」的第三類佔位成因(例如不可推開的中立物件),須回頭重新評估此合併。
- **`ignore_occupancy=true` 的輸出僅供成因標示,絕不得作為移動合法性依據**。實際可移動的目的地永遠只採 `A`。任何以 `B` 判定移動合法性的實作皆為錯誤,須有對應 AC 防守。
- 單位自身所在格 `origin` 恆屬 `A`(公式三輸出範圍已保證),不得被標示為任何一種不可達。
- **效能取捨**:每次刷新需兩趟 Dijkstra 展開。**初步假設在回合制戰棋、格數有限的前提下可落於 16.6ms 預算內,但此假設未經量化驗證(2026-08-17(三)修正措辭,回應 `/design-review` 第二輪 BLOCKING-NOW performance-analyst 發現:原「可接受」寫法與 Open Questions OQ-16 自陳「無法寫出任何 Performance AC」互相矛盾,同一份文件不得對同一件事既給出既成事實陳述、又承認無法驗證)**,實際是否達標見 OQ-16(已於該項銳化為「實作是否為有界前緣展開」這個真正的風險變數)。若未來實測超出預算,最佳化手段屬 `/create-architecture` 範圍,但**不得以「合併為單一趟、放棄成因區分」作為最佳化方式**——那是拿硬性需求換效能。

### 3. 路徑預覽與選路規則

落實 Edge Cases「移動路徑非唯一時的顯示」留下的待決項(2026-08-17 使用者裁決 R-UI2 甲案)。當多條路徑通往同一可達格且累積成本相同時,依下列**三層決定性 tie-break** 選定唯一路徑:

1. **累積地形成本最低**(公式三既有語意)
2. 平手時,**轉彎次數最少**(轉彎定義:相鄰兩步的行進方向不同)
3. 仍平手時,**依固定方位優先序逐步決定**:`上 > 右 > 下 > 左`——在每一步的候選方向中取序位最前者

**硬性約束:**
- 第 3 層保證**無殘留平手**:同一棋盤狀態、同一起訖點,選出的路徑恆等且可重現。選路**不得引入任何隨機或與時間/幀序相關的因素**,呼應 Core Rules #7 的零隨機承諾。
- **路徑預覽與移動動畫實際行經路徑必須完全一致**。這是 Player Fantasy 具名失敗模式「移動/射程範圍的顯示與實際結算不一致」在路徑層的對應——預覽走一條、動畫走另一條,與範圍顯示錯誤是同一種背叛。
- 預覽時機:游標停在可達格時**即顯示完整路徑**,不需按鍵展開(同第 1 節的 hover-only 禁令)。
- 方位優先序 `上 > 右 > 下 > 左` 是**呈現層常數,不是平衡旋鈕**,故不列入 Tuning Knobs;但它是可觀測行為,更動時須同步對應 AC。

### 4. 攻擊確認與傷害拆解面板

落實 Visual/Audio 第 2 節第三列「必須拆解出 `Φ` 的貢獻」(2026-08-17 使用者裁決 R-UI3 甲案)。

**攻擊確認面板**(玩家已選定目標、尚未確認執行時)最小必要欄位:

| 欄位 | 內容 |
|---|---|
| `ATK` | 攻擊方有效攻擊力(敵方單位即公式二輸出) |
| `DEF` | 目標有效防禦力 |
| `Φ` | **帶號**的好感度—位置修正 |
| 結果傷害 | `max(0, ATK − DEF + Φ)` |
| 目標剩餘 HP 預估 | 結算後預期 HP |

**硬性約束:**
- `Φ` 的**正負方向與量值須單獨可讀**,不得只呈現合併後的結果數字。
- **`Φ=0` 時仍須顯示該欄位並標示為 0,不得隱藏**。隱藏會讓玩家無法區分「好感度確實沒有介入」與「這個面板根本沒把好感度算進去」——與 Visual/Audio 第 2 節「0 傷害不得隱藏」是同一條理由的同構套用。
- **結算飄字**只顯示最終傷害總數 + 一個表示 `Φ` 介入方向(正/負/無)的標記,**不重複完整算式**;多單位連續結算時飄字須維持可讀。
- 傷害為 0 時飄字仍須顯示「0」,並使用結算語言而非拒絕語言(見 Visual/Audio 第 2 節)。
- **上界未定的風險傳導**:`Φ` 目前無上界(見 Formulas 公式一邊界行為的已登記風險),因此數值欄寬須能容納非預期的大數值而不截斷、不溢位、不改變版面。待好感度—位置連鎖系統(#5)定案 `Φ_max` 後,欄寬可收斂。

### 5. 預判模式的 UI 生命週期

落實 Visual/Audio 第 3 節「用生命週期做區隔,比用外觀做區隔更穩固」:

- 預判結果**只在游標停留於候選格期間存在**,游標一離開即整體消失,**不寫入任何常駐 HUD 區塊**。
- **預判面板與第 4 節的攻擊確認面板不得是同一個 UI 元件**,即使欄位完全相同。共用元件會讓玩家在快速操作時把「假設」讀成「事實」,支柱一的核心承諾即名存實亡。
- 游標**每次**進入候選格都必須重新呼叫、重新計算,**不得沿用離開前的結果**——這是 Edge Cases「預判模式必須讀取即時狀態」在呈現層的對應要求;快取上一次的預判**顯示結果**與快取其**計算結果**同樣違規。
- 預判三態中的「無效果」與已結算 0 傷害共用同一識別符號(Visual/Audio 第 3 節已定案),但**兩者必須位於不同 UI 層級**(預判層 vs 結算層)——符號相同、層級不同。

### C. 結算順序與陣亡(跨系統契約)

### H. 路徑選擇決定性

**AC-17(Logic / BLOCKING)**
GIVEN 多條路徑通往同一可達格且累積地形成本相同
WHEN 系統選定唯一路徑供路徑預覽/移動動畫使用
THEN 依三層決定性 tie-break 選定:① 累積成本最低 → ② 平手時轉彎次數最少 → ③ 仍平手時逐步依固定方位優先序 `上 > 右 > 下 > 左` 取序位最前者;同一棋盤狀態、同一起訖點,選路結果**恆等且可重現**

| 向量 | 情境 | 期望輸出 |
|---|---|---|
| 成本平手、轉彎數不同 | 兩條等成本路徑,一條轉彎較少 | 選轉彎少者 |
| 成本與轉彎數皆平手 | 兩條路徑轉彎次數相同 | 依方位優先序逐步決定的固定座標序列 |
| 重現性 | 同輸入重複呼叫 100 次 | 輸出路徑逐格相同 |

**AC-18(Integration・禁止型 / BLOCKING)**
GIVEN 玩家已取得對某可達格的路徑預覽(AC-17 的輸出)
WHEN 玩家確認移動、系統播放移動動畫
THEN 移動動畫實際行經的格序列與路徑預覽輸出的格序列**逐格相同**——兩者必須讀取同一次路徑選定呼叫的輸出(或以完全相同的輸入重新呼叫、由 AC-17 保證得到相同結果);**動畫層不得自行決定路徑**

| 向量 | 情境 | 期望輸出 |
|---|---|---|
| — | 預覽路徑 `[(0,0),(0,1),(1,1)]` | 動畫行經序列逐格等於此陣列 |
| — | 確認移動前後棋盤狀態未變 | 預覽查詢與動畫前查詢得到逐格相同的路徑 |

### I. 行動經濟

**AC-19(Logic / BLOCKING)**(**2026-08-17(二)修訂 WHEN 涵蓋範圍與向量表,回應 `/design-review` 第一輪 BLOCKING-NOW #1/#2**)
GIVEN 一個處於「可行動」狀態的單位,其移動旗標與攻擊旗標皆未使用
WHEN 玩家以任意順序使用**零、一或兩個**旗標(含**先攻擊後移動**),中間允許穿插操作其他單位,且該單位所屬陣營的回合邊界可能在旗標未全部使用、亦未被主動結束的情況下發生
THEN 每個旗標每回合各只能成功使用一次;對已使用旗標的再次嘗試必須被拒絕;兩旗標皆用完或玩家主動結束時單位轉為「已行動」;**不論該單位當下是「可行動」或「已行動」**,其所屬陣營的下一回合開始時兩旗標**一律**同時重置為未用(未使用的旗標**不累積**,已使用的旗標**同樣**被重置,不殘留)

| 向量 | 操作序列 | 期望輸出 |
|---|---|---|
| 先移動後攻擊 | 移動 → 攻擊 | 兩者皆成功,單位轉「已行動」 |
| **先攻擊後移動** | 攻擊 → 移動 | 兩者皆成功,單位轉「已行動」(此向量專門驗證順序自由,採甲案的實作會在此失敗) |
| **暫緩** | A 移動 → 操作 B → 回頭 A 攻擊 | A 的攻擊成功;A 在中間期間維持「可行動」 |
| 重複使用同一旗標(移動) | 移動 → 再次嘗試移動 | 第二次移動被拒絕 |
| 重複使用同一旗標(攻擊) | 攻擊 → 再次嘗試攻擊 | 第二次攻擊被拒絕(與移動旗標對稱驗證,Core Rules #9「各限一次」對兩旗標同等適用) |
| 只用其一後主動結束 | 移動 → 主動結束行動 | 轉「已行動」;攻擊旗標作廢 |
| **零旗標主動結束行動(2026-08-17(三)新增,回應 `/design-review` 第二輪 qa-lead 發現:Core Rules #9 明文允許零使用即主動結束,原向量表僅測試「先用過一個旗標再結束」)** | 兩旗標皆未觸碰 → 玩家主動下達「結束行動」指令 | 指令成功,單位轉「已行動」,兩旗標皆作廢(不要求先使用任一旗標) |
| **暫緩、未主動結束、回合邊界(此向量專門驗證 BLOCKING-NOW #1 的修法——舊版狀態表在此向量會失敗)** | 移動(不再使用攻擊、不主動結束行動)→ 該單位所屬陣營回合結束 → 下個同陣營回合開始 | 移動旗標與攻擊旗標**皆**重置為未用(不是只有從未用過的攻擊旗標維持未用——已用過的移動旗標同樣被重置);單位維持/轉為「可行動」 |
| **兩旗標皆不用、回合邊界** | 兩旗標皆不觸碰 → 該單位所屬陣營回合結束 → 下個同陣營回合開始 | 兩旗標維持/重置為未用(不變化的退化案例,驗證零使用路徑同樣被本規則正確覆蓋,不需要特判) |
| **敵方單位的回合邊界重置(驗證 Core Rules #9 的陣營一般化)** | 敵方單位於敵方回合內使用移動旗標,之後歷經一次我方回合 | 敵方單位的旗標狀態在我方回合內不受影響;直到**下一次敵方回合**開始時,其兩旗標才依同一規則重置——不提前於我方回合邊界重置,也不延後 |
| 旗標不累積(2026-08-17(三)修訂措辭,回應 `/design-review` 第二輪 qa-lead 發現:原「非×2」表述對布林旗標易誤讀) | 上回合只用移動 → 下個我方回合 | 攻擊旗標的狀態僅有「未用」一種值,不因跨回合而累積出「可用兩次」的狀態(布林旗標無「用量」概念,此處是排除「錯誤實作把旗標做成計數器」的可能) |

### L. 對外查詢介面的共用義務(2026-08-17(四)新增,回應 `/design-review` 第三輪 BLOCKING-NOW F3-4/F3-5/F3-6)

**測試撰寫提醒(2026-08-17(四)新增,回應第三輪 `godot-specialist` ADVISORY,不影響本 AC 的斷言內容)**:本 AC 與 AC-2/AC-13/AC-21 的輸出皆為**座標集合**。GUT 測試須斷言**集合相等**(大小 + 互相包含,或排序後比對),**不得**直接比對 `Dictionary.keys()` 的序列——Godot 的 `Dictionary` 保留插入序,兩個語意相同但經不同程式路徑算出的集合可能有不同插入序,以序列比對會產生偽失敗。另:AC-20 與本 AC 的測試證據須斷言疊加圖**底層的已算 tile-set**(須有可查詢的 getter),不得斷言 `_draw()`/`queue_redraw()` 的繪製輸出——後者在 headless 環境無法有意義地斷言,亦違反 `.claude/docs/coding-standards.md`「視覺保真度不自動化」的既有分工。

### N. 結算步不可重入(2026-08-18 新增,回應 `/design-review` 第四輪 BLOCKING-NOW B-1)

**AC-24(Integration・禁止型 / BLOCKING)**
GIVEN 某單位的結算步(Core Rules #5 ①→②→③→④)已開始、尚未完成
WHEN 玩家於結算進行中嘗試發起任何操作(對同一單位的其他操作,或依 Core Rules #9「可暫緩」模型切換至其他單位進行移動/攻擊/預判/主動結束行動)
THEN 該操作**不得**被接受、**不得**中途插入結算序列、**不得**靜默丟棄——須觸發明確的拒絕回饋(比照 UI Requirements 第 6 節的合法性閘門),或排入佇列於結算完成後處理(不得無限期等待);結算步完成(④執行完畢)之後,玩家操作恢復正常受理

| 向量 | 情境 | 期望輸出 |
|---|---|---|
| 結算中切換單位 | 單位 A 的結算步進行至②;玩家嘗試操作單位 B 移動 | B 的移動未被執行;A 的結算序列未被打斷,①②③④ 順序完整;玩家獲得明確拒絕回饋或該操作被排入佇列 |
| 結算中重複發起同一攻擊 | 單位 A 的結算步進行至③;玩家再次送出對同一目標的攻擊確認 | 第二次確認未產生第二次結算;不得出現同一次攻擊被結算兩次(交叉驗證 AC-7「陣亡通知恰好一次」的同結算窗雙重觸發向量) |
| 結算完成後恢復 | 單位 A 的結算步完成(④已執行);玩家操作單位 B | 正常受理——本 AC 只約束結算**進行中**,不改變 Core Rules #9「可暫緩」在結算步**之間**的自由度 |
| **卡牌效果不得於結算中要求玩家輸入** | 技能卡牌系統(#6)提供一個於②c 觸發、且需要玩家選擇作用對象的效果 | 該效果的玩家輸入須於本次結算**開始之前**完成;②c 執行期間不得阻塞等待玩家輸入。此向量驗證 Core Rules #11 對 #6 的同步契約——若 #6 設計時確認某類效果無法滿足此契約,須回頭修訂 Core Rules #11,不得由 #6 單方面繞過(見 OQ-4) |

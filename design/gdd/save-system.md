## Overview

存檔系統負責將遊戲的全部持久化狀態——好感度數值池的完整 Delta Log(含戰役刻度標記列表)、章節/戰役進度、活棋盤地形規則版本、以及未來其他系統陸續產生的存檔需求——無損序列化到磁碟,並在讀取時完整還原。它不參與任何玩法規則的計算,純粹是一個資料持久化與版本相容性的基礎設施層:任何系統只要遵循本系統的介面寫入自己的狀態,就能保證該狀態在存檔/讀檔之間不遺失、不被靜默竄改,也不會因為遊戲版本推進(尤其是活棋盤規則隨劇情演變導致存檔跨版本不相容)而在舊存檔上讀取時損毀或需要玩家重新開局。

## Player Fantasy

好感度數值池對玩家的承諾是「你做過的事永遠算數」。存檔系統是那句承諾在時間軸上的延伸——跨過關機、跨過版本更新,那份共同歷史仍然逐筆完整。玩家感受到的不是本系統,而是回到遊戲時關係從未被重設的踏實感。**這份承諾的範圍是「已成功寫入的最後一個進度邊界」**(2026-08-05 第二輪新增,回應 game-designer 審查發現)——一場尚未觸發自動存檔就當機的戰鬥,遺失其間發生的好感度變化,是任何存檔系統的標準行為,不構成對本節承諾的違反;本節保證的是「已經存下的,永遠不會不見、不會被靜默改變」,不是「任何已發生但尚未存檔的事都會被保留」。

這裡的信任是二元的:一次失敗就永久摧毀,不會被九十九次成功補回。三種讓玩家失信的具體情境,依嚴重度排序(最嚴重者排最先),決定了本文件下游章節(Edge Cases、Acceptance Criteria)必須以什麼標準書寫:
- **靜默資料遺失最毒**——版本更新後好感度形狀變了卻沒人告訴玩家,玩家會開始懷疑整套關係系統本身是否誠實。
- **要求玩家管理存檔本身次之**(手動備份、自行判讀哪些資料還在哪些不在、自行選擇存檔槽版本)——把基礎設施的責任外包給玩家,即使沒有資料遺失,也已經違反本節「玩家從不需要想到存檔」的體驗目標**(此為本節整體追求的基準線,遷移失敗狀態下的等待/放棄殘餘成本是本文件承認的例外,見下方「此取捨的殘餘成本」——2026-08-06 第四輪新增範圍聲明,回應 game-designer 審查發現,與 R3-B5 同型:新誠實揭露段落寫對了但未回頭替此處舊句子加註範圍)**,而且比單純的中斷更傷,因為它要求玩家持續投入認知努力去判讀一份不完整的存檔,不是一次性的挫折。
- **可見的中斷再次之**——讀檔失敗且清楚呈現、明確可理解的拒絕,雖然打斷了遊戲流程,但玩家不需要自己判斷任何事,一次性承受、隨即恢復正常。

> **(2026-08-05 第二輪 `/design-review` 修訂,使用者裁決 A2)**:第一輪版本的清單順序與同節取捨聲明的文字互相矛盾——清單原將「要求玩家管理存檔」列為最輕,取捨聲明卻稱其為「第二嚴重」。本輪以取捨聲明的判斷為準,改寫清單順序:要求玩家管理存檔本身,比單純的可見中斷更嚴重,因為後者只是一次性事件,前者要求玩家持續承擔判讀責任。這連帶修正了下方取捨聲明的論證方向。

這決定了下游設計原則:規則集遷移必須被當成**常態路徑**而非例外處理;任何無法保證無損的情況,**寧可拒絕載入並明確告知玩家,也不可靜默降級或部分還原**。

**取捨聲明(2026-08-05,第一輪 `/design-review` 補述;第二輪修訂與上方清單順序一致化)**:上述「寧可拒絕載入」的政策,曾在審查中被挑戰是否該改成允許部分載入(僅標示受影響區塊遺失,其餘資料正常還原)——這樣理論上能保留更多資料,似乎更貼近承諾一。裁定維持整份拒絕,理由回到本節自訂的三級嚴重度排序本身:部分載入需要玩家理解「哪些資料還在、哪些不在」並決定如何看待這份不完整的存檔,這正是排序中第二嚴重(要求玩家管理存檔本身)的具體樣貌,而整份拒絕只觸及第三級(可見的中斷),兩者之間本系統選擇犧牲「保留更多資料」以換取「絕不讓玩家承擔判讀殘缺存檔的責任」。這是刻意的取捨,不是未經檢視的預設值。

**此取捨的殘餘成本(2026-08-05 第三輪修訂,回應 game-designer 審查發現,取代原「此取捨的成立前提」段落——原文宣稱前提已被滿足,但與 States and Transitions 表對緩解後狀態的描述互相矛盾,本輪誠實重新計價而非宣稱問題已消失)**:上一段的論證原本依賴一個前提:「整份拒絕」不能退化成要求玩家管理存檔。誠實檢視 Core Rules #13 的唯讀存取緩解機制後,這個前提**只被部分滿足**——玩家確實不需要判讀哪些資料還在、哪些不在(讀懂殘缺存檔的認知負擔已被移除),但在遷移失敗的槽被修補之前,玩家仍然必須反覆面對「要不要繼續等這個槽,還是放棄」的決定,且這個決定會跨越 session 持續存在,不是一次性事件——這與本節對「可見的中斷」的定義(一次性承受、隨即恢復正常)不完全吻合,結構上更接近第二嚴重級的持續性負擔,只是負擔的內容(判讀資料 vs. 判斷是否繼續等)不同於第二嚴重級原本描述的樣貌。

本系統不假裝這個殘餘成本不存在,而是刻意把它壓到最低,並要求下游正確傳達,讓「放棄」不再感覺像損失:**唯讀匯出的存在,把玩家面對的問題從「繼續等,還是永遠失去這段關係史?」改變成「繼續等,還是帶著完整保存的歷史重新開始?」**——匯出的資料不是安慰性質的殘影,而是**與該槽第一次遷移前的最後一次有效內容逐位元組相同**(見 Core Rules #13)。**(2026-08-06 第四輪修訂措辭,回應 qa-lead 審查發現——原「與正常存檔同等完整」的措辭是過度宣稱)**:這句話陳述的是**內容**等同性(位元組層級的無損),不宣稱**保護等級**等同性——創世存底(`slot_N.pre_migration.bak`)寫入後永久不再重寫,但沒有滾動備份或等效冗餘保護它自己免於位元腐蝕(D-4 為一般存檔新增滾動備份時,已明文承認位元腐蝕比遷移程式碼的 bug 更常見),與正常存檔面對相同的位元腐蝕曝險,不享有額外保護,此為已知並接受的殘餘風險(比照 Core Rules #14 耐久性範圍聲明的既有寫法)。下游 UI 系統的最低呈現契約(見 Interactions with Other Systems)因此新增一項**條件式**強制要求:任一存檔槽進入「遷移失敗」狀態時,若透過唯讀存取介面確認創世存底仍可正常讀取(通過 Core Rules #8/#9 檢查),呈現訊息必須主動告知玩家「此槽的完整歷史已安全保存,可隨時檢視或匯出」;**若該次確認顯示創世存底本身已無法讀取(見 AC-53),下游 UI 必須改為明確告知「此槽的備份本身也已損毀」,不得呈現任何「已安全保存」字樣**——不得只呈現拒絕理由與空白選項。玩家做的仍是一個等待/放棄的決定,但不再是在「等待」與「損失一切」之間選,而是在「等待」與「換一個乾淨的開始、舊的完整保留在旁」之間選(除非備份本身也已損毀,此為誠實揭露而非承諾消除)。

這個殘餘成本不影響上一段取捨聲明本身的結論:部分載入仍然要求玩家做主動判讀(排序中的第二嚴重),整份拒絕+唯讀匯出+主動告知不要求玩家判讀任何資料內容,只留下一個有明確資訊支持的二選一決定——兩者的認知負擔性質不同,取捨聲明選擇整份拒絕的理由依然成立,本輪修正的只是「這個殘餘成本等於零」這個過度宣稱本身。

### Core Rules

1. **存檔資料結構(manifest + 版本化區塊)**:每份存檔是一個帶有明確 schema 版本號的檔案,內含一份 manifest,列出這份存檔包含哪些系統的資料區塊(例如:好感度數值池的 Delta Log + 戰役刻度標記列表、章節/戰役進度、活棋盤地形規則版本、未來新增系統的資料)。每個資料區塊各自標註自己的來源系統與該系統當下的資料格式版本——這讓不同系統的資料可以獨立演進格式,不需要每次任何一個系統改格式就牽動整份存檔重新定義。
2. **存檔槽**:支援多個獨立存檔槽,每槽各自持有完整的 manifest 與全部資料區塊,槽與槽之間互不影響、互不共用狀態。存檔槽數量上限與槽位管理 UI(建立/覆寫/刪除槽位)屬於下游 UI 系統的範圍,本系統只保證槽與槽之間的資料隔離性。
3. **觸發模式**:
   - **自動存檔**為主要機制,於明確定義的進度邊界點觸發(例如每場戰鬥結束、每個章節開始/結束——實際觸發點清單由呼叫方系統〔章節/戰役結構〕決定並呼叫本系統的寫入介面,本系統不主動偵測遊戲狀態)。
   - **手動存檔**作為額外入口,供玩家自行選擇存檔時機,寫入同一套存檔槽機制,不是獨立的存檔類型。
   - 兩者共用同一套寫入邏輯與資料完整性保證,差異只在觸發來源。
4. **寫入行為(同步阻塞式,provisional——範圍限定為一般寫入,不含遷移執行模型)**:**一般存檔寫入**(自動/手動存檔,未觸發遷移鏈)目前設計為**同步阻塞式**——呼叫存檔介面的執行緒會等待序列化完成才繼續執行,接受寫入當下的短暫卡頓(而非引入非同步/背景執行緒序列化)。**本系統假設所有寫入呼叫皆發生於同一個執行緒**(例如 Godot 主執行緒的事件迴圈)——這是「不需額外鎖定」結論成立的前提;若未來出現真正跨執行緒的寫入呼叫者,此假設需要重新驗證。

   **此決定的狀態是 provisional(傾向,非定案)**,理由:(a) 主機平台的 SaveData API 常見設計上即為非同步,**本系統的主機平台目標已於第四輪審查確認為既定(見 Dependencies「平台範圍聲明」與 `game-concept.md` 平台列,2026-08-06 修訂)**,`/create-architecture` 開始前必須確認同步阻塞語意在目標主機平台上是否可直接支援;(b) 寫入耗時是否落在可接受的卡頓範圍尚未實測(見 Tuning Knobs `save_write_max_duration_ms`)。**若之後需要重新啟用非同步寫入**,以下介面需要回頭補上:好感度數值池(`design/gdd/affinity-data-pool.md`)Edge Cases 提出的序列化生命週期通知介面(begin/end)、對應的 AC-47(目前狀態:N/A,見下方 Dependencies 的交接註記——本輪修訂**不**回頭重開該文件的 AC-47,留待格式/架構決策階段與此處一併處理)。

   **範圍聲明(2026-08-05 第三輪新增,回應 performance-analyst 審查發現、使用者裁決 D-2)**:本條的「同步阻塞、provisional」狀態**僅適用於一般寫入路徑**。遷移執行模型(讀取時觸發的版本躍遷鏈)自本輪起改為獨立決定,**不再是 provisional、不再與一般寫入共用同一個執行模型假設**——見 Core Rules #5「遷移執行模型」小節。此區分理由:一般寫入的卡頓可被單一次短暫阻塞吸收,遷移鏈長度政策上無上限(見 Tuning Knobs `max_supported_migration_depth`),若沿用同一個「單次阻塞呼叫」模型,會與 Interactions with Other Systems 要求的「遷移進行中須有進度/忙碌呈現、不得表現為無回應的凍結畫面」結構性衝突——單一阻塞式主執行緒呼叫期間,Godot 無法渲染任何新影格,包含忙碌動畫本身;超過一至兩秒的連續主執行緒阻塞,作業系統(尤其 Windows)即可能將視窗標記為「沒有回應」,這正是該呈現要求明文禁止的結果。這個矛盾在第二輪同時新增這兩項要求時未被交叉檢查,第三輪由 performance-analyst 發現。
5. **跨規則集遷移(版本陣列式逐步遷移)**:每份存檔的 manifest 記錄寫入當下的**規則集版本號**(單調遞增整數)。讀取存檔時,若存檔版本號低於目前遊戲版本,依序執行 `v→v+1`、`v+1→v+2`、…、直到目前版本的遷移函數鏈,每個版本躍遷只需定義「這一步」的轉換規則,不需要重寫早期版本到現在版本的直接轉換。新增規則集版本時,只需新增一個對應的遷移函數,既有的遷移函数鏈不受影響。

   **遷移執行模型(分步執行,2026-08-05 第三輪新增,回應 performance-analyst 審查發現、使用者裁決 D-2)**:遷移函數鏈的執行方式與 Core Rules #4 的一般寫入模型**不同**——遷移鏈**每次只執行一個版本躍遷**(例如每影格或每一次引擎 idle tick 執行一步),步與步之間主動讓出控制權,允許引擎渲染新影格、更新忙碌指示、輪詢輸入。這**仍然是單執行緒模型**——不引入背景執行緒、不需要鎖定,只是把「一次呼叫做完整條鏈」拆成「多次呼叫各做一步、呼叫之間控制權交還引擎主迴圈」,因此不會重新開啟 Core Rules #4 provisional 決定所擔心的跨執行緒安全性問題,也不需要回頭補上好感度數值池的序列化生命週期通知介面(該介面服務的是背景執行緒序列化,與本模型無關)。此模型下:
   - 遷移鏈執行期間,槽對外仍是「待遷移」狀態(見 States and Transitions),但下游 UI 可透過 Core Rules #15 的可觀測性介面查詢「目前執行到第幾步/總共幾步」,呈現真實進度而非僅是靜態忙碌指示。
   - Core Rules #11 的遷移函數確定性要求(相同輸入永遠產生相同輸出)不受此模型影響——分步執行不改變每一步遷移函數本身的執行語意,只改變呼叫方在步與步之間交還控制權的時機。
   - **同槽重入不變量(2026-08-06 第四輪新增,回應 godot-specialist/performance-analyst 獨立收斂發現)**:分步執行的存在理由本身(每步之間讓出控制權,允許引擎輪詢輸入、渲染新影格)打破了 Core Rules #4「單執行緒⇒不需鎖定」結論原本免費成立的前提——該結論建立在「同步阻塞、呼叫方執行緒被整段佔用」之上,一旦步與步之間主動交還控制權,「單執行緒」不再自動蘊含「不會交錯」:讓出視窗期間,包含引擎明文會處理的輸入輪詢在內,任何其他程式碼都能在同一條主執行緒上執行,理論上可能觸發對**同一存檔槽**的第二個讀/寫呼叫。**本系統規定:同一存檔槽的分步遷移執行期間,拒絕該槽的任何第二個讀/寫呼叫**——新呼叫須立即回傳明確的「該槽處理中」結果,不得排隊等待、不得靜默合併、不得啟動第二條並行的分步狀態機。此限制僅及於同一槽,不同槽之間不受影響(Core Rules #2 的槽隔離性已保證)。
   - **觸發情境限制(2026-08-05 第三輪新增,回應 performance-analyst 建議 R-a、creative-director 併入本決定必要條款)**:會觸發遷移鏈執行的讀取,**只能從下游 UI 系統指定的非互動式載入過場情境呼叫**(例如「讀取存檔」確認後的載入畫面)——不得從互動式情境(例如存檔槽瀏覽器讓玩家即時懸停預覽各槽內容)直接呼叫會觸發遷移的完整讀取介面。若下游 UI 需要在互動情境顯示槽的中繼資料(例如章節/進度預覽),本系統須提供一條**僅讀取 manifest 本身、不反序列化任何資料區塊、不觸發遷移鏈**的輕量讀取介面,供此類情境使用。此限制不論本輪選擇的遷移執行模型為何皆須成立——分步執行降低了單次阻塞的嚴重度,但沒有消除「遷移鏈本身耗時隨鏈深度增長、政策上無上限」這個事實,互動情境不應該承受這個不確定的耗時。**本介面須套用完整性檢查(2026-08-06 第四輪新增,回應 game-designer 審查發現——本介面是 R3 同批新增的兩個讀取路徑之一,另一個〔Core Rules #13 唯讀存取介面〕已有矩陣列+專屬 AC,本介面原本零覆蓋)**:本介面雖不反序列化 payload,仍必須套用 Core Rules #8 的頂層完整性標記檢查(雜湊驗證本身不需要反序列化 payload)——標記不符時回傳 `DATA_CORRUPTED`,不得回傳任何預覽欄位。這是本系統流量最高的互動路徑(存檔槽瀏覽器每次開啟都會呼叫),若不驗證,一份 manifest 因意外損毀而缺少或錯置區塊條目(正是 Core Rules #8 頂層標記本身要防的失敗類別),會被靜默呈現為看似正常的章節/進度預覽,玩家依據一份未經驗證的資訊決定要載入哪個槽。
6. **遷移失敗處理(拒絕讀取,不靜默降級)**:若遷移函數鏈中任一步驟偵測到無法安全對應的資料(例如舊規則集的某個概念在新規則集中沒有對應結構),**拒絕載入該存檔,並向呼叫方回傳明確的錯誤原因**(哪個版本、哪個資料區塊、為何無法遷移)——不得嘗試部分還原或以預設值靜默補完缺失資料。錯誤訊息的呈現方式屬於下游 UI 系統的範圍,本系統只保證錯誤原因本身是明確、可呈現的結構化資料,不是純文字例外訊息。

   **拒絕原因的機器可讀分類(2026-08-05 第二輪新增,回應 game-designer 審查發現)**:結構化錯誤的原因代碼須至少區分四類,四類彼此獨立、下游 UI 不得合併呈現:(一)`MIGRATION_FAILED`——遷移函數鏈中某步驟無法安全對應;(二)`DATA_CORRUPTED`——完整性標記不符或位元組本身無法解析;(三)`VERSION_TOO_NEW`——存檔版本高於目前遊戲支援版本;(四)`SEMANTIC_VALIDATION_FAILED`(新增)——區塊已是目前版本、未觸發遷移鏈,但未通過 Core Rules #7 語意驗證。第四類與第一類的關鍵差異:第四類沒有任何遷移步驟可以「修復」,其自動痊癒路徑(見 Core Rules #13)依賴的是語意驗證規則本身被修正,而非遷移函數被補齊——兩者的觸發條件與呈現語意都不同,下游 UI 若混用第一類與第四類的訊息模板,會誤導玩家以為問題出在版本相容性,而非資料本身違反目前規則。
7. **語意驗證(反序列化後,非格式驗證)**:每個資料區塊在通過格式層級的反序列化後,還須通過各自來源系統宣告的語意合法性檢查(例如數值欄位落在合法值域內、非 NaN/Infinity、來源標記屬於已知列舉集合)。任何一項語意檢查失敗,依 Core Rules #6 的拒絕路徑處理,回傳 `SEMANTIC_VALIDATION_FAILED` 原因代碼(即使該區塊本身格式版本與目前版本相同、未觸發遷移鏈)——**格式正確不代表語意合法**,這是格式層級的反序列化(尤其若最終格式選用引擎原生序列化器)本身無法保證的一層。

   **驗證器宣告為強制項,未宣告視為錯誤(2026-08-05 第二輪新增,回應 security-engineer 審查發現,fail-open 修正為 fail-closed)**:每個持久化資料區塊,在其來源系統的 GDD 定案時,**必須**明確宣告該區塊每個欄位的語意合法性規則(值域、型別、允許的列舉值等)。manifest 中若列出一個沒有對應驗證器宣告的資料區塊,**該 manifest 本身視為錯誤**,依 Core Rules #6 的 `DATA_CORRUPTED` 路徑拒絕讀取——即「未宣告驗證規則」不等於「跳過驗證」,而是與「驗證失敗」同等對待。此規則翻轉了原本隱含的預設值:第一輪版本允許「來源系統沒宣告驗證器」的區塊悄悄跳過語意檢查,本輪修正為預設拒絕、通過必須是明確結果。目前唯一已定案的來源系統(好感度數值池)已在 Dependencies 章節宣告其驗證規則;尚未設計的下游系統於 `/design-system` 階段須將此列為必要交付項,而非事後補充。

   **語意驗證同樣套用於遷移函數的輸出(2026-08-05 第二輪新增,回應 security-engineer 審查發現,消解 Core Rules #12 與本條之間的曖昧關係)**:每個遷移函數的最終輸出,除了須通過 Core Rules #12 的結構性後置條件檢查,還須通過本條的語意驗證——即語意驗證不只發生在「初次反序列化、未觸發遷移鏈」的路徑,也發生在「遷移鏈執行完成後」的路徑。任何一步遷移的最終輸出未通過語意驗證,依 Core Rules #6 的 `MIGRATION_FAILED` 路徑拒絕(不使用 `SEMANTIC_VALIDATION_FAILED`,因為此情境確實觸發了遷移鏈)。此規則是本輪修法解決「no-op 或輸出恰好滿足結構檢查但語意錯誤的遷移函數被誤判成功」問題(見 Core Rules #13)的第二道防線——Core Rules #13 的原始位元組保留是最後一道安全網,本條是提早攔截、減少需要動用安全網的頻率。
8. **Manifest 自我完整性標記(2026-08-05 第二輪修訂,「位元組筆數或雜湊擇一」改為強制雜湊,回應 systems-designer/security-engineer 獨立收斂發現)**:manifest 除列出各資料區塊的來源與版本外,另記錄一份可驗證的完整性標記——**須為涵蓋該區塊完整內容的加密雜湊值(例如 SHA-256 或等效強度演算法),不得僅以位元組筆數作為完整性標記**(位元組筆數無法偵測任何維持原長度的竄改或位元損毀,例如單一位元翻轉、同寬度欄位互換,不構成有效的完整性控制)。**雜湊的輸入須涵蓋該區塊的宣告身分與宣告版本中繼資料,不得只涵蓋 payload 本身**——否則一份雜湊校驗通過的 payload,可能被錯誤標記成不同的來源系統識別碼或格式版本號(不論是因為攻擊者竄改、或更常見地,是因為一次不完整的寫入/搞砸的遷移回寫導致 manifest 與 payload 錯配),進而被路由進錯誤的遷移函數鏈,造成靜默的語意損壞——這是一般正常操作(誠實玩家、系統本身的 bug)就可能觸發的正確性問題,不需要假設任何惡意行為。讀取時先核對此標記,標記不符視為「資料損毀」(`DATA_CORRUPTED`,見 Core Rules #6,與 AC-19/AC-28 共用錯誤路徑),不進入正常還原或遷移路徑。

   **Manifest 自身須有涵蓋區塊清單的頂層完整性標記(2026-08-05 第三輪新增,回應 security-engineer 審查發現)**:本條前段的雜湊是**逐區塊**的——每個區塊各自有自己的雜湊值,驗證的是「這個仍列在 manifest 裡的區塊,內容有沒有被改」。這不足以偵測「manifest 對某區塊的**列表項目本身**整筆消失」——例如一次不完整的寫入,讓某個資料區塊(例如活棋盤地形規則)的條目完全從 manifest 中丟失,但其餘區塊(例如好感度數值池)的條目與雜湊完全正常。逐區塊雜湊對此無能為力,因為它只驗證仍被列出的區塊,無法驗證「應該被列出卻不見了」的區塊。結合 AC-24b(空 Delta Log 為合法狀態)一併考慮:一個因寫入意外整筆消失的好感度區塊條目,讀取端會將其解讀為「這名玩家的戰役尚未產生任何好感度記錄」,**成功讀取、不觸發任何錯誤**——這正是本文件自陳最毒的「靜默資料遺失」,由一次普通的寫入失誤即可觸發,不需要任何攻擊者。因此 manifest 除了逐區塊雜湊外,**須額外持有一份涵蓋整份區塊清單本身的頂層完整性標記**——雜湊輸入為「(區塊來源系統識別碼, 區塊格式版本號, 該區塊逐區塊雜湊值, **該區塊的遷移完成標記或 null**)」依固定順序排列的完整 tuple 清單,任何一個區塊的新增、刪除、或清單順序異動(若順序本身有意義),都會使頂層標記不符,依 `DATA_CORRUPTED` 拒絕讀取,不得因為「仍存在的區塊各自驗證通過」就判定整份存檔完好。

    **「固定順序」的定義(2026-08-06 第四輪新增,回應 game-designer 審查發現)**:上述 tuple 清單的「固定順序」指**與寫入當下的內部容器迭代順序無關的規範順序**(例如依區塊來源系統識別碼的字典序排列),不是「寫入時實際被序列化的順序」。理由:若「固定順序」隱含依賴寫入時的迭代順序,任何與資料內容本身無關的未來重構(例如區塊註冊順序調整、容器型別改變導致迭代順序不同)都可能在**不改變任何實際資料**的情況下改變此順序,導致舊存檔在下次讀取時被此雜湊誤判為 `DATA_CORRUPTED`——這與本文件全篇防範的「無害的程式碼變動,靜默破壞看似無關的既有存檔正確性」屬同一失敗模式家族(與 `Pair`/`source_i` 序數漂移同型,只是發生在 manifest 層而非欄位層)。採規範順序後,雜湊計算在讀寫兩端皆可獨立重建,不依賴任何隱含的容器迭代行為。

    **遷移完成標記須被本標記涵蓋(2026-08-06 第四輪新增,回應 security-engineer/systems-designer/game-designer 三方獨立收斂發現,本輪最高優先發現)**:Core Rules #13 路徑(二)要求 manifest 額外記錄的「遷移完成標記」(各僅追加型區塊的記錄索引/戰役刻度位置)是與逐區塊雜湊、頂層標記平行存在的 manifest 欄位,若不將其納入頂層雜湊的輸入 tuple,此欄位會完全落在兩層完整性保護範圍之外——一旦此欄位因意外寫入錯誤或維運操作被錯誤改動,現行機制**無法偵測**,會導致路徑(二)的拼接程序在錯誤的記錄索引處拼接(重複或遺漏記錄),且不產生任何錯誤代碼提示,是靜默資料損壞。本次修訂已將此欄位(或其 null 狀態,若該區塊從未觸發過遷移)納入頂層雜湊輸入,關閉此漏洞。

   **威脅模型範圍聲明(2026-08-05 第二輪新增,回應 security-engineer 審查發現)**:本條完整性標記的保護範圍是**意外損毀與未經工具協助的手動編輯**,**不是**反作弊或防止知情攻擊者竄改的保證——雜湊演算法與 manifest 格式本身不是秘密,一個理解本系統設計的攻擊者可以竄改任何欄位後重新計算雜湊值,使竄改後的檔案通過本條的完整性檢查。本系統的所有驗證邏輯(本條、Core Rules #7、Core Rules #9)皆執行於用戶端,不構成伺服器權威式的反作弊保證。此範圍聲明特別重要,因為 Core Rules #9 的理由段落點名「玩家之間分享的存檔」為威脅情境,容易讓讀者誤以為本系統對此有完整防護——實際上本系統只保證「格式與語意層級的自我一致性」,不保證「內容真實反映玩家實際遊玩歷程」。若未來任何系統(例如排行榜、跨玩家好感度軌跡比較)需要消費存檔衍生資料於信任敏感情境,該系統必須將此資料視為玩家可自行宣稱的內容,不得視為已驗證的事實。
9. **反序列化型別白名單**:不論最終序列化格式為何,反序列化路徑僅允許實例化一份預先登記的已知型別清單,任何未登記型別視為資料損毀(同 Core Rules #8 的完整性失敗路徑)。此為防禦措施,防範不受信任的存檔檔案(例如玩家之間分享的存檔)嘗試觸發非預期型別的實例化。

   **白名單的版本分域範圍(2026-08-05 第二輪標記,回應 security-engineer 審查發現;creative-director 綜合裁決降為 `/create-architecture` 階段必辦項,不列為本輪 GDD 阻擋)**:本條未指定白名單是「所有版本曾合法型別的扁平聯集」還是「依存檔宣告版本分域」——若為前者(支援舊存檔遷移的自然實作),理論上存在「宣告舊 schema 版本以路由進較少被檢視的舊版遷移程式碼路徑」的風險。此風險的前提是持有惡意構造存檔的攻擊者,在本系統目前的單機、無伺服器信任邊界威脅模型下(見 Core Rules #8 威脅模型範圍聲明)優先度較低,但機制本身要到序列化格式定案才能具體定義,故列為 Open Questions 的必辦項,不在此階段憑空規定。
10. **索引鍵與持久化列舉欄位一律採字串名稱,不採 enum 序數(2026-08-05 第三輪擴大範圍,回應 creative-director 資深審查發現)**:`Pair`(索引鍵)**以及任何其他以 enum 表示、會被持久化的欄位**(例如好感度數值池 Delta Log 記錄的 `source_i` 來源標記欄位)一律以其**字串名稱**持久化,並在對應資料區塊內維護一份「字串名稱↔目前 enum 定義」的對照表。讀取時以名稱查表還原,若名稱在目前 enum 定義中找不到對應項,視為 Core Rules #6 的 `MIGRATION_FAILED`(需要遷移函數明確處理該重新命名/移除的情況)。**此規則存在的理由**:enum 定義順序調整(重構、插入新項目)是常見且合理的未來變更,若以序數持久化,順序調整會讓存檔靜默還原成錯誤但合法的值,且此錯誤無法被任何現有機制偵測到——這是第一輪審查發現的最高風險項(見 review-log)。

    **範圍擴大的理由(2026-08-05 第三輪新增)**:第一、二輪的措辭僅涵蓋「索引鍵」,而 `source_i` 是被持久化的**欄位值**、不是索引鍵,字面上不在原規則涵蓋範圍內——但 `source_i` 面臨完全相同的風險:它是 enum,若以序數持久化,來源列舉定義順序調整會讓存檔靜默把某個來源的記錄還原成另一個來源,且此錯誤能通過 Core Rules #7(語意驗證只檢查「來源標記屬於已知列舉集合」,序數調整後的錯誤值仍在合法集合內,通過)、Core Rules #8(雜湊涵蓋寫入當下的位元組,順序調整後才讀取不會觸發不符)、以及不觸發遷移鏈(因為格式版本未變)——即現有全部四道防線對此完全無感,是 R1 頭號發現(`Pair` 序數漂移)的同型失敗,存在於一個先前沒有人劃進範圍的欄位上。`affinity-data-pool.md` 須同步擴大其對應段落與 Acceptance Criteria 的涵蓋範圍(見 Dependencies 章節)。

    **退役名稱治理規則,含強制自動化檢查(2026-08-05 第二輪新增,第三輪由治理紀律升級為硬性規則,回應 security-engineer/qa-lead/game-designer 三方獨立收斂發現)**:上一段的緩解機制只擋住「名稱在目前 enum 定義中找不到」(刪除)的情況,不擋「名稱找得到,但目前指向的是另一個語意不同的實體」(重用)的情況——若某個字串曾被除役(對應的值被移除或重新命名),而重構者日後把**同一個字串**重新指派給一個語意不同的新值,舊存檔讀取時查表**會成功**,只是找到的是錯的實體,系統無法從查表機制本身偵測到這個錯誤,原始問題並未真正解決,只是換了觸發途徑,這正是 R2 審查發現的最高風險項(五位專家中三位獨立收斂於此),也是 R3 三位專家(security-engineer、qa-lead、game-designer)獨立指出「唯一沒被翻成 fail-closed 的 R2 修法」之處。**治理規則:任何曾經在對照表中出現過的字串名稱,一旦除役(對應的值被移除或重新命名為其他字串),該字串本身永久保留為「已退役」狀態,不得被重新指派給任何新的值——即使是語意上「感覺相關」的新實體,也必須使用不同的字串名稱。**

    **本規則的執行不得僅依賴人工審查紀律。** `/create-architecture` 階段須提供一個**自動化檢查**,能在對照表資料檔異動時(建置期或 CI 階段皆可,具體機制留給該階段決定)偵測「任一字串名稱由已退役狀態轉回啟用狀態且指向不同實體」並使該次異動失敗——例如:對照表資料檔的版本歷史比對(diff 檢查退役集合是否曾發生名稱重新啟用)、或啟動時掃描目前 enum 定義的全部合法名稱是否與已退役名稱清單有交集。GDD 層級不規定具體實作方式,但**規定「此檢查必須存在」是本條的硬性要求,不是建議**——理由:文件自陳的最高風險失敗類別(靜默語意改變)不需要任何攻擊者即可觸發(一次普通的內容重構即足夠),與同一輪修訂中對等風險的 Core Rules #7(驗證器宣告強制化)一樣,都必須是 fail-closed 且可被自動偵測,不能是本文件唯一僅靠人工紀律把關的最高風險項。對照表本身仍須明確標記退役狀態(而非直接刪除該筆對應),讓「名稱是否曾被使用過」可查詢,供上述自動化檢查讀取。

    **過渡期殘餘風險聲明(2026-08-06 第四輪新增,回應 security-engineer 審查發現)**:「升級為硬性規則」描述的是本條的**目標狀態**,不是**現況**——自動化檢查要到 `/create-architecture` 階段才會真正建置完成,在此之前,本規則的實際執行力與升級前相同,**仍完全依賴人工審查紀律**,這是本系統已知並接受的過渡期殘餘風險(比照 Core Rules #14 耐久性範圍聲明、Core Rules #13 路徑(二)的既有寫法)。AC-51 驗證的是「檢查機制存在且會攔截違規」,在自動化檢查真正交付前,此 AC 處於不可執行狀態,不計入本文件現階段的驗收判定。此聲明的存在理由:本規則保護的是文件自陳的最高風險失敗類別,若讀者誤讀「升級為硬性規則」等於「風險已解決」,可能在防線最脆弱的過渡期窗口降低警覺——見 Ledger S12。
11. **遷移函數的確定性要求**:所有遷移函數必須是純函數——相同輸入永遠產生相同輸出,不依賴當下系統時間、隨機數、或任何遷移鏈之外的可變狀態。這是 Edge Cases「當機安全」論證成立的前提(讀取重跑遷移鏈必須保證與原本執行的結果一致)。
12. **遷移函數的後置條件檢查**:每個遷移函數執行完成後,須通過對應目標版本 schema 的後置條件檢查(至少涵蓋必要欄位存在性、值域合法性)。後置條件檢查失敗視同 Core Rules #6 的遷移失敗,即使遷移函數本身沒有拋出例外——防止「執行成功但轉換錯誤」的遷移函數被誤判為成功。

    **（2026-08-05 第二輪補充說明,回應 systems-designer/security-engineer 審查發現)**:本條的後置條件檢查是**結構層級**(必要欄位存在性、值域合法性),不是**語意正確性**的完整驗證——語意層級的驗證由 Core Rules #7 涵蓋(該條第二輪已明確擴大套用範圍至遷移函數的輸出,見該條)。兩者是遷移鏈輸出必須依序通過的兩道獨立檢查,缺一不可:結構檢查抓「這筆資料還算不算一個合法的目標 schema 實例」,語意檢查抓「這筆資料的內容是否代表一個合理的關係狀態」。一個有 bug 但輸出恰好同時滿足兩道檢查的遷移函數仍然可能存在(語意驗證的涵蓋範圍終究取決於各來源系統宣告的規則有多嚴謹)——這正是 Core Rules #13 新增「原始位元組保留」規則要作為最後一道安全網的理由。

13. **遷移成功後立即回寫,含自動痊癒保證與原始位元組保留(2026-08-05 第二輪修訂,回應 systems-designer/security-engineer/game-designer 獨立收斂發現,使用者裁決 B-甲;第三輪修訂保留策略、寫入順序、自動痊癒路徑(二)措辭,回應四方獨立收斂發現與使用者裁決 D-1/D-3)**:遷移函數鏈完整執行成功且通過 Core Rules #12 後置條件檢查與 Core Rules #7 語意驗證後,系統立即以遷移後的結果覆寫該存檔槽(視同觸發一次新的自動存檔,套用 Core Rules #14 的原子寫入保證)。**回寫時不得銷毀遷移前的原始位元組**——原始版本以獨立的存底檔案形式與遷移後結果並存於同一存檔槽目錄下(例如 `slot_N.dat`〔目前版本〕與 `slot_N.pre_migration.bak`〔遷移前原始位元組,唯讀,不參與正常讀取路徑〕)。

    **保留策略:創世保留,非「最近一次」(2026-08-05 第三輪修訂,使用者裁決 D-1,取代原「保留最近一次遷移前的完整存底」措辭)**:`slot_N.pre_migration.bak` 保留的是該存檔槽**第一次**發生遷移前的原始位元組,**一旦建立,後續任何一次遷移的回寫皆不得覆寫或刪除它**。理由(回應 security-engineer/systems-designer/game-designer 三方獨立收斂發現):若採「僅保留最近一次」的字面定義,一個未偵測到的遷移 bug(例如 v1→v2)會在後續遷移(例如 v2→v3,對已受污染的 v2 資料執行、且同樣通過自己的結構與語意檢查)發生時,被新產生的存底覆寫——此時真正正確的 v1 原始位元組永久消失,「保留原始位元組」這個機制在它原本設計要撐過的情境(bug 在多次規則集推進後才被發現)下反而完全失效。創世保留策略的儲存成本與原「最近一次」策略相同(恆為 1 份存底,數十 KB 級),不因保留代數增加,但能讓下方自動痊癒路徑(二)在任意深度的遷移鏈之後仍有真正的原始資料可用。

    **寫入順序:存底建立與 Core Rules #14 序列須為獨立的兩個依序原子步驟(2026-08-05 第三輪新增,回應 systems-designer/godot-specialist/qa-lead/performance-analyst 四方獨立收斂發現)**:本規則存在的唯一理由是保證原始位元組不會遺失,若存底檔案本身的寫入沒有當機安全保證,這個保證就是空話。回寫因此由**兩個依序執行、各自獨立原子的階段**組成,不得合併或省略任一階段:
    - **階段 A(僅在該槽尚無 `slot_N.pre_migration.bak` 時執行一次)**:以與 Core Rules #14 相同的手法(暫存寫入 → flush → rename 為最終檔名),將遷移前的原始位元組原子性地寫成 `slot_N.pre_migration.bak`。此階段必須確認完整成功後,才可進入階段 B。若該槽已存在 `slot_N.pre_migration.bak`(即創世存底已建立過),階段 A 跳過,不覆寫既有存底。
    - **階段 B**:執行 Core Rules #14 定義的四步驟序列,將遷移後結果換成 `slot_N.dat`。

    若進程在階段 A 完成前中斷,`slot_N.dat` 與既有 `slot_N.pre_migration.bak`(若先前已存在)維持中斷前狀態不變——`.dat` 仍是遷移前版本,下次讀取視為遷移尚未回寫,重新執行完整遷移鏈(與一般遷移執行中當機等價,見 Edge Cases)。若進程在階段 A 完成、階段 B 進行中中斷,依 Core Rules #14 本身的原子性保證,`.dat` 的狀態必為「遷移前」或「遷移後」兩者之一,且此時 `slot_N.pre_migration.bak` 已經確認寫入完成(階段 A 已完成),不存在「`.dat` 已是新版本但存底從未被建立」的中間狀態。

    **此規則存在的理由**:Core Rules #12 的後置條件檢查只驗證結構,不驗證語意正確性——一個有 bug 但輸出恰好滿足結構檢查(且未被 Core Rules #7 語意驗證攔截)的遷移函數,在第一輪設計下會被判定成功並立即覆寫原始資料,而該槽從此不會再進入「遷移失敗」狀態,即使未來修正了該 bug,原本的自動痊癒保證也無法觸及一個從未被判定為失敗的槽——資料已經被靜默、永久、不可逆地覆寫成語意錯誤但格式合法的內容。保留原始位元組把這個失敗模式的傷害上限,從「不可逆覆寫」降回「可逆的錯誤回寫,只要原始資料還在就能重新來過」。

    **自動痊癒保證(擴大範圍,2026-08-05 第三輪修訂路徑(二)措辭與範圍,回應 qa-lead/game-designer 獨立收斂發現、使用者裁決 D-3)**:以下三條路徑**安全性不對等**,不應被讀成三個平行、同等保證強度的項目——(一)(三)為系統自動觸發、可證明無損;(二)為維運層級介入,且僅在特定資料模型下可行,見下方限定範圍。

    **(一)遷移失敗自動重試(無損,自動觸發)**:若某存檔槽先前因某個遷移步驟缺失處理邏輯而進入「遷移失敗」狀態(Core Rules #6,`MIGRATION_FAILED`),而後續遊戲更新為該步驟補上了正確的遷移函數,玩家下次讀取該槽時遷移鏈會自動重新嘗試——若這次成功,槽狀態自動從「遷移失敗」轉為「有效」並依本規則立即回寫,不需要玩家做任何動作。

    **(二)維運層級重跑修正後遷移(資料前提已保證,程序本身留待 `/create-architecture` 定義,對合法後續進度不保證無損)**:若某存檔槽已完成回寫、槽狀態為「有效」,但日後發現該次遷移的後置條件與語意驗證其實遺漏了某個語意錯誤,遊戲更新修正該遷移函數的邏輯後,理論上可對該槽以創世存底重新執行修正後的遷移鏈——**此路徑之所以在資料層面可行,完全依賴上方創世存底保留策略**(若仍是「最近一次」策略,多代遷移後存底可能早已不是真正的原始資料)。**本路徑不在一般玩家讀取路徑中自動觸發,屬於維運/更新層級的補救手段,實際觸發機制與狀態轉換模型留待 `/create-architecture` 階段設計,本 GDD 不對此路徑的執行結果做保證,只保證執行所需的原始資料(創世存底)被保留且不被覆寫**——見下方 AC-37/AC-39 的範圍聲明。

    **玩家進度遺失風險與必要條件(2026-08-05 第三輪新增,回應 game-designer 審查發現)**:若玩家在受損的遷移結果上繼續遊玩並累積了合法的新記錄(例如好感度數值池 Delta Log 的新增條目),單純「以創世存底重跑修正後的遷移鏈」只會重現**修正後的原始遷移點**,不會包含遷移之後才寫入的合法記錄——若直接以此結果取代目前存檔,會靜默遺失這段合法進度,構成與 Core Rules #13 本身要防止的失敗類別(靜默、不可逆的資料損失)同型的失敗,且波及範圍通常更大(涵蓋修補前的全部遊玩時數,不只原始 bug 本身的資料)。因此本路徑的維運程序**必須**滿足以下前提才可執行,不得省略:
    1. Manifest 須額外記錄一個**遷移完成標記**——遷移回寫當下,各僅追加型(append-only)資料區塊(例如好感度數值池 Delta Log)所處的記錄索引/戰役刻度位置。
    2. 維運程序重跑修正後的遷移鏈,產出修正版的遷移結果後,**須將該標記之後、目前 `.dat` 中已合法追加的記錄重新拼接到修正版結果之上**,而非直接以修正版結果整份取代目前存檔。
    3. **此拼接程序僅對明確宣告為「僅追加」的資料區塊成立**(好感度數值池 Delta Log 符合此性質)。對非僅追加型區塊(例如章節/戰役進度這類會被覆寫而非追加的狀態),本規則**不保證**無損拼接——這類區塊若受本情境影響,維運程序須採取更保守的處理(例如僅提供匯出、不自動合併),並在執行前明確告知負責處理的工程/客服人員,不得假設「拼接」對所有區塊類型都成立。
    4. **(2026-08-06 第四輪新增,回應 security-engineer/systems-designer/game-designer 三方獨立收斂發現)拼接完成後,維運程序必須重新計算並寫回受影響區塊的逐區塊完整性雜湊(Core Rules #8 第一段)與 manifest 頂層完整性標記(Core Rules #8 頂層段落,已擴大涵蓋遷移完成標記)——兩者缺一均不得視為拼接程序完成,拼接後的檔案在雜湊重算完成前不應被任何一般讀取路徑存取。此落盤動作不論觸發機制與拼接程序細節如何(觸發機制本身留待 `/create-architecture` 階段設計,見 Ledger S8),都必須重用 Core Rules #13 一般回寫的兩階段流程與 Core Rules #14 的原子置換保證,不得繞過標準寫入管線直接修改磁碟位元組——維運工具不是特權路徑。這條雜湊重算義務本身是 GDD 層級的硬性前提,不受 AC-37「不驗證路徑(二)程序本身」排除條款保護,任何架構階段選定的觸發機制都不得省略它。**若省略此步驟,可能產生兩種失敗結局**:較安全的結局是下次一般讀取偵測到雜湊不符、拒絕載入,槽重新陷入拒絕狀態但至少不會誤判為正常;較危險的結局是重算不完整(例如只重算逐區塊卻未連動頂層 tuple),雜湊顯示「完整性正常」但實際內容已被合法工具覆蓋成錯誤或不完整內容——這是本文件自陳最毒失敗類別的新變體,且是唯一可能繞過所有既有防線的路徑。

    **(三)同版本語意驗證修正自動痊癒(無損,自動觸發)**:若某語意驗證失敗(Core Rules #7,`SEMANTIC_VALIDATION_FAILED`)發生在目前版本區塊(未觸發遷移鏈),而後續版本修正了該驗證規則本身的邏輯或值域定義,玩家下次讀取時語意驗證會以修正後的規則重新執行——若這次通過,槽狀態自動從「遷移失敗」轉為「有效」,不需要玩家做任何動作。

    **維運層級重跑不得覆寫創世存底(2026-08-05 第三輪新增,回應 systems-designer 建議)**:路徑(二)的維運程序執行完成、產生新的回寫結果後,此次回寫**不得**觸發本規則的存底建立邏輯把既有的創世存底覆寫或更新——創世存底一經建立即永久保留,即使後續發生任意次數的一般遷移或維運層級重跑。

    **遭拒存檔的唯讀存取(呼應 Player Fantasy「此取捨的殘餘成本」)**:任一存檔槽處於「遷移失敗」狀態期間,系統必須能讓下游 UI 系統透過獨立的唯讀介面存取該槽最近一次的完好資料,供玩家檢視或匯出,不需要玩家自行判斷「哪些資料還在」。此唯讀介面與正常讀取介面分離,不改變槽的遷移失敗狀態,也不繞過 Core Rules #6 的拒絕政策本身(玩家仍無法把這份資料當成「目前存檔」繼續遊玩,只能檢視/匯出)。

    **唯讀介面的資料來源優先序(2026-08-05 第三輪新增,回應 systems-designer 建議)**:若該槽存在一份仍可正常解析、格式合法的 `.dat`(即使版本落後於目前遊戲版本,只是尚未通過最新一次遷移),唯讀存取回傳該 `.dat` 內容,而非退回 `pre_migration.bak`;僅當 `.dat` 本身也無法安全解析時,才退回創世存底或該槽最後一次成功寫入的內容。

    **唯讀介面須重新套用格式安全與完整性檢查,不得視為自我信任(2026-08-05 第三輪新增,回應 security-engineer 審查發現;2026-08-06 第四輪擴大檔案枚舉範圍,回應 security-engineer 審查發現——原枚舉遺漏 `slot_N.prev.bak`,而 Core Rules #14 步驟四與 AC-54 皆已明確指出該檔案經由本介面存取,原文字造成 AC 單方面加了本規則沒寫的義務)**:本介面雖與正常讀取介面分離,但它讀取的仍是磁碟上的檔案(`.dat`、`slot_N.pre_migration.bak`、或 `slot_N.prev.bak`),與正常讀取路徑面對相同的意外損毀/手動編輯曝險(見 Core Rules #8 威脅模型範圍聲明)——「這是本系統自己產生的備份」不構成任何額外信任基礎,不因檔案類型是本系統自產或未來新增而有差異。本介面在反序列化前**必須**套用與正常讀取路徑相同的 Core Rules #9(型別白名單)與 Core Rules #8(完整性雜湊)檢查,**不論其磁碟來源是上述三種檔案中的哪一種**;若通過,方可提供內容供檢視/匯出。Core Rules #7(語意驗證)在本介面**可降為僅標註、不阻擋**(因為本介面的目的正是讓玩家能看到內容,即使內容語意上有疑慮),但格式安全(型別白名單)與位元組完整性(雜湊)不得放寬。若存底檔案本身未通過型別白名單或雜湊檢查,本介面須回傳「存底本身無法讀取」的明確結果,不得靜默略過檢查、把未經驗證的內容當成「已知良好狀態」呈現給玩家。

14. **跨平台原子置換語意是行為契約,不是機制假設(2026-08-05 第二輪修訂具體安全序列,回應 godot-specialist 審查發現——原範例本身違反自身契約)**:Edge Cases「若寫入過程中途失敗」定義的原子寫入保證(先寫暫存檔案、確認完整後才取代)是本系統對所有平台一致要求的**行為契約**——不綁定任何特定 API 的實作假設。

    **具體安全序列(2026-08-05 第二輪新增,第三輪修訂步驟零與步驟四,回應 godot-specialist/systems-designer/使用者裁決 D-4)**:第一輪版本曾舉例「刪除舊檔前置檢查」作為可能的實作手法,但該序列本身在「刪除完成、置換尚未完成」之間存在一個新舊檔案皆不存在的視窗,若行程於此視窗當機/斷電,會直接違反本節與 Edge Cases 共同定義的保證(既有存檔槽維持寫入前最後一個有效狀態不變)。**該範例已撤回,改為以下已知安全、不依賴任何特定平台「取代已存在目標」語意的序列**,現在鎖定為本規則的具體實作要求(不留給 `/create-architecture` 自由裁量):

    0. **(2026-08-05 第三輪新增)寫入前置檢查**:若 `slot_N.bak` 已存在(代表上一次寫入曾在步驟 3 完成後、步驟 4 完成前中斷,殘留至今),先補完上一次寫入未完成的步驟四(見下方步驟 4 的新定義),再開始本次寫入的步驟 1。此步驟存在的理由(回應 godot-specialist 審查發現):若略過此步驟,步驟 2 會嘗試把 `slot_N.dat` rename 到一個已存在的目標(`slot_N.bak`),這是 `DirAccess.rename()` 在不同平台上行為未經驗證一致的情境——本步驟確保步驟 2 執行時,rename 目標必定不存在,恢復序列原本依賴的不變量。此步驟安全,因為執行期間 `slot_N.dat` 完全未被觸碰。
    1. 寫入暫存檔案(例如 `slot_N.tmp`),確保內容完整寫入並 flush。
    2. 若目標槽既有有效檔案(`slot_N.dat`)存在,將其 rename 為備份檔(`slot_N.bak`)——rename,不是刪除。
    3. 將暫存檔案 rename 為目標檔案(`slot_N.dat`)。
    4a. **(2026-08-06 第四輪新增,回應 godot-specialist 審查發現)若 `slot_N.prev.bak` 已存在,步驟四執行前先將其刪除。** 存在理由:步驟四(見下方)本身是把 `slot_N.bak` rename 為 `slot_N.prev.bak`——若目標檔名已存在,這正是**步驟零存在的理由本身要消除的那一類操作**(rename 到一個可能已存在的目標,在不同平台上行為未經驗證一致),D-4 新增步驟四時未與步驟零交叉檢查,遺漏了等價的前置清空,在 `DirAccess.rename()` 於目標已存在時失敗的平台上,會導致步驟四永久無法完成——而步驟零規定「若 `slot_N.bak` 已存在,先補完上次未完成的步驟四,再開始本次寫入」,一旦步驟四結構性地無法完成,該槽的**後續所有寫入會被步驟零永久卡住**。本步驟安全:執行當下 `slot_N.dat`(新內容)與 `slot_N.bak`(上一代)皆存在且未被觸碰,被刪除的是「上上代」滾動備份,而本文件從未承諾保留上上代內容。
    4. **(2026-08-05 第三輪修訂,使用者裁決 D-4)若備份檔(`slot_N.bak`)存在,將其 rename 為 `slot_N.prev.bak`(取代任何既有的 `slot_N.prev.bak`,見上方步驟 4a),不再直接刪除。** 理由:原設計(直接刪除)讓一般 `DATA_CORRUPTED`(已成功寫入、從未觸發遷移的存檔發生位元腐蝕,例如硬碟位元衰變)沒有任何回退路徑,而這在現實中比遷移程式碼的 bug 更常見——本文件已為遷移失敗建立了完整的存底/唯讀存取機制(見 Core Rules #13),卻對更常見的失敗模式零回復,這個不對稱本輪一併修正。`slot_N.prev.bak` 僅保留「上一代」內容(滾動式,每次成功寫入時被步驟 4 取代),不像 Core Rules #13 的 `slot_N.pre_migration.bak` 是永久創世保留——兩者服務不同的失敗類別,語意與生命週期均不同,不得混淆。

    此序列的每一步邊界都至少存在一個可辨識的有效檔案(`.dat` 或 `.bak`),當機後可靠地推斷上次寫入是否完成,不會出現「兩者皆缺」的視窗。

    **讀取端回復規則(2026-08-05 第二輪新增,補上安全序列原本缺少的另一半;第三輪新增精確檔名比對要求)**:載入存檔槽時,若偵測到目標檔案(`slot_N.dat`)缺失或無法解析、但備份檔(`slot_N.bak`)存在,視為上一次寫入在步驟 3-4 之間中斷,系統須將 `slot_N.bak` 視為該槽最後一個有效狀態,依正常讀取路徑處理(不視為資料損毀)。此規則若缺席,上述安全序列產生的備份檔將無人讀取,退化成單純佔用磁碟空間的殘留物,不提供任何實際保護。

    **精確檔名比對,禁止萬用字元/前綴比對(2026-08-05 第三輪新增,回應 systems-designer 審查發現)**:本規則所指的「備份檔」僅限**精確檔名** `slot_N.bak`,實作**不得**以副檔名(`*.bak`)或前綴萬用字元比對方式偵測——本存檔槽目錄下同時存在三種不同語意、不同生命週期的類 `.bak` 檔案(`slot_N.bak` 本規則的暫態備份、`slot_N.prev.bak` Core Rules #14 步驟四的滾動備份、`slot_N.pre_migration.bak` Core Rules #13 的永久創世存底),寬鬆比對會讓其中任何一個被誤判為另一個的恢復目標,把錯誤 schema 版本或錯誤語意層級的位元組送進不該進入的讀取路徑,重現本文件全篇極力防範的靜默語意損壞。`slot_N.prev.bak` 與 `slot_N.pre_migration.bak` 在任何情況下都不得被視為本讀取端回復規則的備援目標——前者僅透過 Core Rules #13 唯讀存取介面於 `DATA_CORRUPTED` 情境下存取,後者僅透過同一介面於「遷移失敗」情境下存取,兩者皆不參與本規則描述的一般讀取路徑。

    **耐久性範圍聲明(2026-08-05 第三輪新增,回應 godot-specialist 審查發現)**:本節「flush」一詞指引擎緩衝區沖刷至作業系統層級,**不等同於強制作業系統將資料實際落盤的硬體層級同步(fsync/`FlushFileBuffers` 等效操作)**。本規則的原子寫入契約**保證涵蓋進程層級當機、強制關閉**(資料仍停留在作業系統快取但進程本身已終止的情境)——這已是 AC-10 實際斷言的範圍(WHEN 子句寫的是「進程被終止/注入寫入失敗」)。**真正的電源中斷(斷電)需要額外的硬體層級落盤保證,GDScript 目前是否能直接呼叫此類操作尚待查證**,列為 `/create-architecture` 階段必辦查證項;在查證並補上等效機制之前,電源中斷情境下資料遺失是本系統**已知並接受的殘餘風險**,Edge Cases 中的相關敘述已同步修正措辭範圍,不再做無條件承諾。

    若某平台的原生 API 無法直接達成此序列的每一步語意(例如某些主機平台的檔案置換沙盒化行為),該階段須為該平台補上等效機制,但對外行為必須維持本節定義的契約不變。

15. **可觀測性義務(2026-08-05 第二輪新增,回應 systems-designer/qa-lead/godot-specialist 收斂發現)**:為了讓 Acceptance Criteria 中依賴行為觀測的驗收條件(例如遷移呼叫順序、遷移呼叫次數)可被獨立驗證而非仰賴實作者自行遵守文件敘述,本系統須提供以下僅供 QA/除錯用途的診斷介面,不得作為下游系統業務邏輯依賴的正式回傳簽章:
    - **遷移呼叫計數器**:記錄本次讀取實際呼叫了幾次遷移函數(供 AC-15 等驗證「零遷移」與「恰好一次遷移」的情境)。
    - **遷移呼叫順序記錄**:記錄各遷移函數被呼叫的時間順序(供 AC-13 驗證嚴格依序執行)。

### States and Transitions

| 狀態 | 進入條件 | 離開條件 | 行為 |
|---|---|---|---|
| 空(Empty) | 該存檔槽從未寫入過 | 首次寫入成功 | 讀取請求回傳「無資料」,不視為錯誤 |
| 有效(Valid) | 寫入成功且版本號等於目前遊戲版本 | 遊戲版本升級後首次讀取該槽 | 讀取直接還原,不需要遷移 |
| 待遷移(Pending Migration) | 讀取時偵測到存檔版本號低於目前遊戲版本 | 遷移函數鏈執行完成(成功或失敗) | **(2026-08-05 第三輪修訂,配合 Core Rules #5 分步執行模型,使用者裁決 D-2)** 依序**分步**執行遷移函數鏈(每步之間讓出控制權,見 Core Rules #5),期間該槽對外仍視為不可讀取;下游 UI 須呈現進行中/忙碌指示,可透過 Core Rules #15 新增的遷移進度查詢介面呈現真實步數進度,不得表現為無回應(見 Interactions 最低呈現契約);此狀態只能由指定的非互動式載入過場情境觸發,互動式情境(例如存檔槽瀏覽器)須改走 manifest-only 輕量讀取介面,不得觸發本狀態 |
| 遷移失敗(Migration Failed) | 遷移函數鏈中任一步驟偵測到無法安全對應的資料(`MIGRATION_FAILED`),**或**目前版本區塊未通過 Core Rules #7 語意驗證(`SEMANTIC_VALIDATION_FAILED`,2026-08-05 第二輪新增,兩種進入條件對應不同的拒絕原因代碼,見 Core Rules #6) | 下次讀取嘗試時遷移函數鏈(或語意驗證)重新執行且這次成功(例如遊戲更新後補齊了先前缺失的遷移函數,或修正了驗證規則本身,見 Core Rules #13 自動痊癒保證路徑(一)/(三)),或該存檔槽被覆寫 | 拒絕載入,回傳結構化錯誤原因(四類原因代碼之一,見 Core Rules #6);存檔槽本身不被本系統自動刪除或修改;**下游 UI 系統可透過獨立的唯讀介面存取該槽最近一次的完好資料(優先為仍可解析的 `.dat`,其次為創世存底或最後一次成功寫入內容,見 Core Rules #13),該介面重新套用型別白名單與完整性雜湊檢查,不自我信任;玩家不需要自行判讀哪些資料還在,但仍須決定是否繼續等待或放棄該槽——本文件誠實承認此為持續性殘餘成本,不宣稱已完全消除**(2026-08-05 第三輪修訂,回應 game-designer 審查發現、Player Fantasy「此取捨的殘餘成本」,使用者裁決 D-5;**若唯讀介面確認回退資料可正常讀取,下游 UI 須主動告知「歷史已完整保存,可隨時取出」;若回退資料本身也已無法讀取(見 AC-53),下游 UI 須改為明確告知「此槽的備份本身也已損毀」,不得呈現安全保存字樣**——2026-08-06 第四輪修訂,回應 qa-lead 審查發現,見 Interactions);玩家「確認錯誤訊息」只是 UI 層級的告知動作,不改變系統狀態本身——下次讀取仍會重新嘗試 |
| 寫入中(Writing) | 呼叫寫入介面(自動或手動存檔觸發,一般寫入路徑) | 序列化完成(同步阻塞,呼叫方執行緒等待此狀態結束) | 阻塞呼叫方執行緒直到完成;由於採同步阻塞式寫入,不存在「寫入中收到另一個寫入請求」的並發情況(見 Core Rules #4)。**此狀態僅涵蓋一般寫入路徑**——遷移完成後的回寫屬於「待遷移」狀態內部的最終步驟(見 Core Rules #13 兩階段寫入順序),不獨立進入本狀態。 |

### Interactions with Other Systems

- **好感度數值池(持久化義務,讀取方向)**:本系統必須無損序列化/還原完整 Delta Log(所有記錄,含 `c_i` 欄位)與獨立的戰役刻度標記列表,不做壓縮或摘要。索引鍵(如配對 `Pair`)**以及被持久化的列舉欄位(如 `source_i`)**於存檔格式中一律以**字串名稱**持久化(見 Core Rules #10,2026-08-05 第三輪擴大範圍涵蓋 `source_i`),不以 enum 序數持久化——enum 定義順序調整不影響已存檔資料的正確性。由於本系統目前採同步阻塞式寫入(見 Core Rules #4,provisional,範圍限定一般寫入),該文件要求的「序列化生命週期通知介面」(begin/end)目前不需要實作;若該決定日後重新開啟為非同步,此介面需要回頭補上。
- **章節/戰役結構(呼叫方,寫入觸發來源)**:章節/戰役結構系統決定自動存檔的實際觸發時機點(例如每場戰鬥結束、每章開始),呼叫本系統的寫入介面。本系統不主動偵測遊戲進度,純粹被動回應呼叫。
- **活棋盤地形演變系統(資料來源,尚未設計)**:地形規則版本是跨規則集遷移的核心資料——本系統假設該系統的規則資料本身有明確的版本標記機制,若該系統設計時採 Godot Resource 子類別實作規則資料,須遵循 `game-concept.md` 已記錄的「Resource 參照共享風險」對應的深層複製紀律(`duplicate_deep()`),避免存檔寫入時意外持有共享參照而非獨立快照。
- **好感度視覺呈現 UI / 未來的存檔管理 UI(讀取方,尚未設計)**:存檔槽的建立/覆寫/刪除介面、遷移失敗的錯誤訊息呈現,皆屬於下游 UI 系統的範圍——本系統只保證資料完整性與結構化的錯誤資訊,不涉及任何畫面呈現。**最低呈現契約(2026-08-05 第二輪修訂,原三類拒絕原因擴充為四類,並新增三項呈現要求)**:下游 UI 不得允許玩家在未看到結構化錯誤原因的情況下重試同一個已知失敗的操作而不告知後果,且必須將 Core Rules #6 定義的四種拒絕原因(`DATA_CORRUPTED` / `MIGRATION_FAILED` / `VERSION_TOO_NEW` / `SEMANTIC_VALIDATION_FAILED`)以玩家可理解的方式區分呈現,不得統一顯示成單一「讀取失敗」訊息。

- **版本過新的呈現須框為「可回復」,不得與資料損毀同等呈現**(2026-08-05 第二輪新增,回應 game-designer 審查發現):`VERSION_TOO_NEW` 在 PC 平台上很可能是玩家在 Steam beta/穩定分支間切換造成的常態情境,不是罕見的存檔損毀——下游 UI 須明確傳達「切回較新版本的遊戲即可繼續讀取此存檔」,不得使用與資料損毀相同的措辭或視覺樣式。
- **遷移進行中須有進度/忙碌呈現**(2026-08-05 第二輪新增,回應 systems-designer 審查發現;第三輪修訂配合分步執行模型):由於遷移鏈深度目前無上限(見 Tuning Knobs),下游 UI 於「待遷移」狀態期間,須向玩家呈現明確的進行中/忙碌指示,不得表現為無回應的凍結畫面。**自本輪起,由於 Core Rules #5 已將遷移執行模型改為分步執行(使用者裁決 D-2),下游 UI 可透過 Core Rules #15 的遷移進度查詢介面呈現真實的「第 X 步/共 Y 步」進度,不再僅能呈現靜態忙碌指示**——若引擎/平台實作因故無法取得分步進度,至少須呈現「正在處理」的持續性回饋作為最低限度。
- **互動情境須走 manifest-only 讀取,不得觸發遷移(2026-08-05 第三輪新增,回應 performance-analyst 建議、creative-director 併入 D-2 決策必要條款)**:任何互動式 UI 情境(例如存檔槽瀏覽器讓玩家即時懸停預覽各槽的章節/進度資訊)**不得**呼叫會觸發遷移鏈的完整讀取介面——這類情境須改用本系統提供的 manifest-only 輕量讀取介面(僅讀取 manifest 本身,不反序列化任何資料區塊、不觸發遷移),避免耗時隨鏈深度增長的遷移鏈意外阻塞一個原本應該即時回應的互動畫面。只有明確標示為「載入存檔」的非互動式載入過場,才可呼叫會觸發遷移的完整讀取介面。
- **遭拒存檔的唯讀存取,含條件式主動告知(2026-08-05 第二輪新增,第三輪修訂措辭與呼應段落,回應 game-designer 審查發現、Player Fantasy「此取捨的殘餘成本」,使用者裁決 D-5;2026-08-06 第四輪修訂為條件式,回應 qa-lead 審查發現)**:存檔槽處於「遷移失敗」狀態時,下游 UI 須提供存取該槽最近一次完好資料(唯讀)的入口,不得只呈現一個無法互動的錯誤訊息——玩家應能檢視或匯出這份資料,即使無法將其當作可繼續遊玩的存檔載入。**下游 UI 呈現此狀態時,須先透過唯讀介面確認回退資料(創世存底或其他回退來源)是否通過 Core Rules #8/#9 檢查:若通過,必須主動告知玩家「此槽的完整歷史已安全保存,可隨時檢視或匯出」;若未通過(即回退資料本身也已損毀,見 AC-53),必須改為明確告知「此槽的備份本身也已損毀」,不得呈現任何「已安全保存」字樣**——不得只呈現拒絕理由與空白選項。目的是讓玩家面對的決定從「繼續等,還是永遠失去這段關係史?」變成「繼續等,還是帶著完整保存的歷史重新開始?」,把 Core Rules #13 保留的資料真正轉譯成玩家能感知到的保障,而非一個存在但沒人知道的安全網——**但這份保障本身不享有額外冗餘保護(創世存底無滾動備份),條件式告知的存在正是為了不讓這句保障在存底也損毀時變成一句誤導性的安心宣稱**。

## Formulas

不適用——本系統是純基礎設施(存檔序列化/還原/版本遷移),沒有從數學表達式計算出的數值輸出(不像傷害公式、掉落率、或好感度數值池的衰減曲線)。**(2026-08-03,systems-designer 諮詢確認;2026-08-05 第一輪 `/design-review` 修正引用範圍)**:曾評估三個可能的隱藏公式候選——遷移函數鏈深度、存檔檔案大小、自動存檔頻率與寫入阻塞時間的取捨——三者皆非公式導向的問題:遷移鏈深度是架構政策取捨(見 Tuning Knobs);存檔大小在目前規模下是簡單線性乘法(`total_size ≈ slots × per_slot_size`),`per_slot_size` 依 `affinity-data-pool.md` Open Question 9 的估算落在數十 KB 等級,這只回答「存檔多大」,不构成、也不引用該文件對「序列化這份資料需要多少時間」的任何結論(該文件 Open Question 9 明文禁止如此引用,見其護欄註記)。**此公式只涵蓋單一目前版本 payload,不含 Core Rules #13/#14 的備份倍數——完整的 3 倍(穩態)/4 倍(寫入瞬間峰值)倍數見 Tuning Knobs「存檔大小規模」段落(2026-08-06 第四輪新增交叉引用,回應 systems-designer 審查發現)。**自動存檔頻率與寫入阻塞時間之間的實際權衡本身尚未回答**,留待 Tuning Knobs 的 `save_write_max_duration_ms` 由實測校準,不以資料大小反推。

## Edge Cases

*(2026-08-05 第二輪修訂:原「Lean mode 未諮詢」註記移除——本節已於第二輪完整對抗性審查中由 systems-designer、qa-lead、security-engineer、game-designer 四位專家審查,新增兩則邊界情境。)*

- **若寫入過程中途失敗(進程當機、強制關閉、磁碟已滿、權限錯誤;2026-08-05 第三輪修訂移除對「斷電」的無條件承諾,見 Core Rules #14 耐久性範圍聲明)**:採用原子寫入模式——先寫入暫存檔案,確認完整寫入成功後才取代既有存檔槽的檔案,絕不直接覆寫既有有效存檔。若寫入失敗,既有存檔槽維持寫入前的最後一個有效狀態不變,不產生半寫入的損毀檔案。呼叫方(自動/手動存檔觸發來源)會收到寫入失敗的錯誤,由其決定是否重試。**本保證確認涵蓋進程層級的當機/強制關閉;真正的電源中斷需要額外的硬體層級落盤保證,目前是否可由 GDScript 直接達成尚待 `/create-architecture` 階段查證,查證完成前列為已知並接受的殘餘風險——不再無條件承諾「斷電」情境下的完整性,見 Core Rules #14。**
- **若讀取時偵測到存檔槽的位元組本身已損毀(非版本不相容,而是資料本身無法解析)**:視同該存檔槽讀取失敗,回傳結構化錯誤(區分「版本不相容」與「資料損毀」兩種錯誤原因,見 Core Rules #6),不嘗試部分解析或以殘存的可讀片段拼湊還原——呼應 Player Fantasy「寧可拒絕載入也不可靜默降級」。**下游 UI 可透過 Core Rules #13 的唯讀存取介面存取該槽 Core Rules #14 步驟四保留的上一代滾動備份(`slot_N.prev.bak`,2026-08-05 第三輪新增,使用者裁決 D-4)——此為唯讀回退,不自動載入為目前存檔,語意與遷移失敗的唯讀存取一致但資料來源不同(滾動備份 vs. 創世存底)。**
- **若遷移函數鏈執行到一半時遊戲異常終止(當機、強制關閉)**:由於遷移是在讀取時於記憶體中進行、原始存檔槽在遷移完成並確認成功前不會被覆寫(見 Core Rules #13「遷移成功後立即回寫」——回寫本身套用上方「寫入過程中途失敗」的原子寫入原則,只有在遷移鏈**完整成功**後才會觸發),原始存檔槽的資料維持遷移前的舊版本狀態不受影響。玩家下次讀取時,該槽會重新從舊版本開始執行整條遷移函數鏈——此重跑結果與原本被中斷那次的執行結果保證一致,依賴的是 Core Rules #11 的遷移函數確定性要求。不存在「卡在遷移中一半」的中間狀態需要特殊處理。
- **若手動存檔請求與自動存檔觸發在極短時間內先後發生**:由於採同步阻塞式寫入(見 Core Rules #4),兩次寫入不可能真正並發——後發生的請求會在前一次寫入完成後才開始執行,依請求發生的先後順序依序完成,不需要額外的鎖定或佇列機制。
- **若存檔槽的 manifest 列出一個目前遊戲版本已不存在的資料區塊來源(例如某系統被移除或重新命名)**:視為該區塊資料在遷移函數鏈中應被對應版本的遷移函數明確處理(丟棄、合併、或轉換到新系統),不得被本系統的通用讀取邏輯靜默忽略——若沒有任何遷移函數宣告如何處理該區塊,依 Core Rules #6 視為遷移失敗,拒絕讀取。
- **若存檔槽的版本號高於目前遊戲版本(玩家用較舊的遊戲版本讀取較新版本存的檔)**:視為不可遷移(遷移函數鏈只定義「升版」方向,不定義「降版」),依 Core Rules #6 拒絕讀取並回傳明確錯誤原因(區分於「版本過舊需遷移」的錯誤訊息,讓玩家理解是版本方向相反,而非存檔損毀)。
- **若多個存檔槽處於不同的規則集版本(例如槽 A 是舊版本尚未讀取過、槽 B 已升級到最新版本)**:合法且預期的正常狀態——存檔槽彼此完全獨立(見 Core Rules #2),讀取槽 A 時才會觸發槽 A 自己的遷移,不影響槽 B。
- **若遷移函數鏈完整執行成功、系統正在依 Core Rules #13 觸發回寫時遊戲異常終止(當機、強制關閉)**(2026-08-05 第二輪新增,回應 qa-lead 審查發現的缺口;第三輪修訂為三結果模型,回應 systems-designer/godot-specialist/qa-lead/performance-analyst 四方獨立收斂發現——原兩結果模型只斷言 `.dat` 的狀態,從未斷言存底檔案本身的狀態,而這正是本情境唯一該驗證的重點):Core Rules #13 的回寫由**階段 A(存底建立)**與**階段 B(Core Rules #14 原子置換序列)**依序組成,中斷結果為以下三種之一,且絕不出現第四種中間狀態:(a)中斷發生在階段 A 完成之前——槽維持遷移前的原始狀態(舊版本)不變,既有 `slot_N.pre_migration.bak`(若先前已存在)也不變,下次讀取重新從頭執行整條遷移鏈,行為與「遷移執行中當機」等價;(b)中斷發生在階段 A 完成之後、階段 B 尚未進行到步驟 3(暫存檔案 rename 為目標檔案)之前——`slot_N.pre_migration.bak` 已確認寫入完成,但 `slot_N.dat` 仍是遷移前版本,下次讀取視同槽仍處於「待遷移」,重新執行遷移鏈,此次重跑時階段 A 因存底已存在而跳過(見 Core Rules #13),直接進入階段 B;(c)中斷發生在階段 B 已完成步驟 3 之後——`slot_N.pre_migration.bak` 已確認寫入完成,`slot_N.dat` 已是目前版本的正確內容,至多殘留一份尚未依步驟四轉為 `slot_N.prev.bak` 的暫態 `slot_N.bak`,下次寫入的步驟零會補完這個轉換(見 Core Rules #14)。三種結果下,`slot_N.pre_migration.bak` 只要曾經確認寫入完成,即保證不再消失;唯一會反覆重跑的是遷移鏈本身,而 Core Rules #11 的確定性要求保證重跑結果一致。
- **若某個遷移函數本身有 bug,輸出結構上滿足 Core Rules #12 後置條件、但語意錯誤**(2026-08-05 第二輪新增,回應 systems-designer/security-engineer/game-designer 收斂發現;第三輪修訂措辭,回應 security-engineer/systems-designer/game-designer 對「不會有資料永久遺失風險」宣稱過度的發現,使用者裁決 D-1/D-3):依 Core Rules #7 第二輪擴大範圍的規則,此情況若語意驗證能偵測到值域/型別/列舉範圍等違規,會在回寫前被攔截、依 `MIGRATION_FAILED` 拒絕。若語意驗證的涵蓋範圍本身有缺口而未能偵測到(例如驗證規則寫得不夠嚴謹),遷移仍會被誤判成功並觸發 Core Rules #13 的回寫——但依該條「創世保留」規則(2026-08-05 第三輪修訂,取代原「最近一次」措辭),第一次遷移前的原始資料不會被任何後續遷移覆寫或銷毀,日後修正驗證規則或遷移函數邏輯後,可透過 Core Rules #13 自動痊癒保證路徑(二)的維運層級補救流程,以創世存底重新執行修正後的遷移鏈。**此路徑對遷移點本身的資料無損,但對遷移之後玩家繼續遊玩累積的合法進度不保證無損拼接**——路徑(二)的完整限定範圍、拼接前提與例外(僅追加型資料區塊)見 Core Rules #13,本輪不再宣稱此路徑「不會有資料永久遺失的風險」這種無條件措辭。

## Tuning Knobs

- **`max_save_slots`(存檔槽數量上限)**:目前無強制上限的設計必要性(見 Detailed Rules Core Rules #2,存檔槽之間完全獨立)。**起始建議值:待 UI 系統設計時依畫面配置與玩家心智負擔決定**——本系統本身不因槽數增加而有效能或複雜度風險(見下方存檔大小規模註記),上限純粹是 UI/UX 考量,不是本系統的技術限制。
- **`max_supported_migration_depth`(遷移函數鏈深度上限,選用)**:Core Rules #5 目前設計為開放式遷移鏈(無版本數上限,每次新增規則集版本只需新增一個遷移函數)。**目前建議不設上限**——理由:上限本身是「工程維護負擔」與「絕不強迫玩家開新遊戲」(Player Fantasy 核心承諾)之間的政策取捨,在尚未實際累積多個規則集版本、不知道遷移函數維護成本之前,提前設限沒有實證基礎。若未來遷移函数鏈變得難以維護(例如某個早期版本的遷移函數需要理解已被完全重構的舊系統),可回頭評估是否引入此旋鈕,屆時須明確定義「超過上限的存檔」的行為(是否仍拒絕讀取但給出不同錯誤訊息、或提供陽春的資料匯出供玩家手動保存)。**2026-08-05 第三輪補充(回應 performance-analyst 審查發現)**:Core Rules #5 本輪改為分步執行(使用者裁決 D-2)後,單次無回應凍結的風險已解除,但這不代表無上限政策的耗時風險本身消失——遷移鏈總耗時仍是「鏈深度 × 各步驟資料量」的乘積關係,深度無上限的政策讓總耗時理論上同樣無上限,只是玩家現在能看到進度而不是被凍結。此政策仍然開放,待累積 3+ 個規則集版本後依既有觸發條件重新評估(見 Open Questions)。

**2026-08-06 第四輪補充(回應 performance-analyst 審查發現)——耗時模型補上與資料量無關的加性下限**:上方「鏈深度 × 各步驟資料量」的乘積模型不完整——分步執行下,每一步至少需要一次控制權讓出(至少等待一次引擎讓出,粒度須保證引擎能渲染至少一個新影格),此等待時間**不隨該步驟的資料量縮放**,即使某一步遷移函數轉換的資料量趨近於零,仍至少付出一次讓出等待的固定成本。完整模型應為:**總耗時 = Σ(各步驟計算耗時,隨資料量成長) + 鏈深度 × 每步讓出固定成本(與資料量無關的加性下限)**。這對「深度無上限政策仍安全」的既有論證有實質影響——若遊戲生命週期內累積多次「小改動、幾乎不動資料」的規則集版本推進(合理且常見的演進模式),鏈深度本身即可能透過讓出次數把耗時往上推,不需要資料量同步成長。重新評估 `max_supported_migration_depth` 的觸發條件(見 Open Questions)須將「鏈深度本身造成的讓出開銷是否已成為主要成本來源」納入獨立判準,不能只看資料量增長。
- **存檔大小規模(非問題,一句話註記)**:多存檔槽 + 全量 manifest 持久化在目前遊戲規模下是簡單線性關係(`total_size ≈ slots × per_slot_size`),`per_slot_size` 依 `affinity-data-pool.md` Open Question 9 的估算落在數十 KB 等級(5 名固定角色、10 對配對、單一戰役全程)——不構成需要校準的旋鈕,若未來內容量大幅膨脹(例如角色規模政策改變)才需要重新評估。**此估算只回答存檔大小,不回答序列化耗時**(見下方 `save_write_max_duration_ms`)。**2026-08-05 第三輪補充**:本輪新增的兩份備份機制對此估算略有影響但仍在同一數量級——(一)Core Rules #13 創世保留(使用者裁決 D-1)固定為每槽 1 份存底,成本與第二輪的「最近一次」策略完全相同,不隨遷移代數增長;(二)Core Rules #14 步驟四的滾動備份(使用者裁決 D-4)固定為每槽再多 1 份上一代內容,約 +1× `per_slot_size`。**穩態常駐用量為 `per_slot_size` 的 3 倍**(目前版本 + 創世存底 + 滾動備份),仍是數十 KB 等級。

**2026-08-06 第四輪補充(回應 performance-analyst 審查發現)——區分穩態常駐與寫入瞬間峰值**:上方 3 倍是**寫入完成後的靜態常駐用量**,不是**寫入過程中任何時刻磁碟必須保有的最大可用空間需求**。逐步核算 Core Rules #14 步驟 1-3 期間:暫存檔案(`.tmp`,新內容)與既有 `slot_N.dat`(舊內容,尚未被觸碰)**同時存在**,加上 `.prev.bak` 與 `.pre_migration.bak`——**寫入瞬間峰值為 4 倍**(非 3 倍),直到步驟 4 取代舊 `.bak` 才回落至 3 倍穩態。此峰值數字供 `/create-architecture` 階段設計任何主動式可用空間門檻檢查時直接引用(見 Open Questions「`FileAccess.store_*` 布林回傳值檢查」列)——若依 3 倍穩態數字設計門檻,會在磁碟空間介於 3-4 倍之間的邊界情況下,於步驟 1 的 `.tmp` 寫入階段觸發可預期但本可避免的寫入失敗(雖仍是安全失敗,不損毀既有資料,見 Core Rules #14 原子性保證)。此峰值疊加不改變 `per_slot_size` 基準本身的估算方法或量級(見 `affinity-data-pool.md` Open Question 9),純粹是本文件自身備份機制的疊加係數修正。
- **`save_write_max_duration_ms`(存檔寫入卡頓上限,待實測校準)**:存檔寫入為同步阻塞(Core Rules #4,provisional),此門檻是「可接受的卡頓時長」上限參考,**範圍限定於一般自動/手動存檔的單次寫入**(不含遷移觸發的複合回寫,見下方 `migration_chain_load_time_budget_ms` 的範圍聲明)。依專案 60fps/16.6ms 影格預算(`.claude/docs/technical-preferences.md`),單次寫入造成的卡頓不應讓玩家感知為明顯凍結;起始建議值待第一次實測(見 Acceptance Criteria 新增 H 節 AC-36)取得真實數字後校準,目前無法憑空指定。**若同步寫入實測結果持續超過此門檻且無法透過序列化優化解決,是 Core Rules #4「同步阻塞」決定需要被重新開啟評估的具體觸發條件之一。**

  **寬限上限(2026-08-05 第二輪新增,回應 game-designer 審查發現;第三輪補上觸發條件的精確定義,回應 performance-analyst/qa-lead 審查發現)**:AC-36 標記超標為「待校準追蹤項」而非功能性失敗,但追蹤不得無限期持續——若連續兩次正式建置量測(或垂直切片驗收里程碑,以先到者為準)仍超過此門檻,Core Rules #4 的重新評估**由建議升級為必須執行**,不得繼續以「持續追蹤」名義擱置。**觸發條件的精確定義**:(一)量測環境須固定——比較的兩次量測須為相同建置設定(例如皆為 QA 建置或皆為 release 建置,不得混用含 debug 主執行緒斷言額外開銷的建置與不含此開銷的建置);(二)兩次量測之間須有最小間隔(建議至少間隔一個工作天或一次獨立的建置產出,避免同一批連續 CI 執行的雜訊被算成兩次獨立量測);(三)兩次量測之間也須有最大間隔上限(例如一個月內),超過此上限視為計數中斷、須重新累積,避免「連續兩次」在間隔過長時實質上失去偵測持續性衰退的意義;(四)CI 例行量測與垂直切片里程碑量測**視為同一計數池**的兩種來源,但採用其一觸發計數时,另一來源須符合相同的建置設定要求才可採計。**追蹤責任**:由 qa-lead 於 `production/qa/smoke-[date].md` 或對應效能追蹤文件記錄每次正式建置的 AC-36 量測結果與目前連續超標次數,producer 於里程碑檢視時核對此計數。

- **`migration_chain_load_time_budget_ms`(遷移鏈讀取耗時上限,選用,待實測校準)**:目前遷移鏈長度政策上無上限(見 `max_supported_migration_depth`),但玩家實際等待時間有感知上限。建議與 `save_write_max_duration_ms` 一併於實測階段校準;若遷移鏈變長導致讀取耗時超過此門檻,是重新評估 `max_supported_migration_depth` 政策的觸發條件之一。

  **範圍聲明(2026-08-05 第二輪新增,回應 performance-analyst/systems-designer 收斂發現;第三輪補充分步執行模型下的適用方式)**:此門檻涵蓋「遷移鏈執行 + Core Rules #13 觸發的立即回寫」的**複合耗時**,而非只涵蓋遷移函數本身的計算時間——玩家實際等待的是這整段複合阻塞時間,不是其中一部分。此複合路徑發生在讀檔/載入畫面情境,不受 60fps 影格預算(`save_write_max_duration_ms` 的適用範圍)約束,但仍須被量測與追蹤,對應新增的 AC-46(見 Acceptance Criteria 新增 H 節)。**Core Rules #5 改為分步執行後(使用者裁決 D-2),此門檻量測的是「總耗時」(各步驟耗時總和,含步與步之間讓出控制權的排程開銷),不是「單次阻塞呼叫的耗時」——分步執行預期會讓總耗時略高於單次阻塞版本(多了排程開銷),但把耗時從「玩家完全無回應」轉換成「玩家看得到進度」,這是本輪決策刻意接受的取捨,不視為效能倒退。**

- **遷移函數複雜度上限(2026-08-05 第二輪新增,回應 performance-analyst 審查發現,對齊 `affinity-data-pool.md` Core Rules #1 的等價查詢複雜度約束)**:單一遷移函數對其負責轉換的資料區塊,時間複雜度須為 `O(該區塊自身筆數)`,不得因為 schema 變更而需要對區塊做超線性(例如巢狀掃描)的遍歷,除非該版本躍遷語意上確實需要(此例外須在對應遷移函數的文件註解中明確說明理由)。這條約束不是旋鈕(沒有可調數值),而是介面契約,列於本章節是為了與 `migration_chain_load_time_budget_ms` 並列参照——遷移鏈總耗時 = Σ(各步驟耗時),若任何一步驟違反此複雜度約束,會讓遷移鏈耗時隨存檔資料量而非僅隨鏈深度成長,使 `migration_chain_load_time_budget_ms` 的校準基礎失真。

## Acceptance Criteria

*(2026-08-03,qa-lead 諮詢草擬,依 Detailed Rules/Edge Cases 逐條覆蓋。誤差容許:浮點欄位位元完全相同或誤差 <1e-12。2026-08-05 第二輪修訂:新增 AC-24b、AC-37~46,section F2/G2/H;AC-8/14/28/31 內容重寫,AC-30 錯誤代碼措辭更新。2026-08-05 第三輪修訂:新增 AC-14b、AC-48~54;AC-7/37/38/39/46 內容重寫或補充範圍聲明;AC-25/29 新增 `source_i` 對稱版本(AC-49/50)。)*

### A. Manifest & Multi-Slot Isolation

- **AC-1**: **GIVEN** 一次對存檔槽 A 的寫入,內含來自 N 個不同來源系統的資料區塊,**WHEN** 檢視產生的存檔檔案,**THEN** 其 manifest 列出全部 N 個資料區塊,各自標註獨立的來源系統識別碼與獨立的資料格式版本號(不是全部區塊共用單一格式版本)。
- **AC-2**: **GIVEN** 同一存檔中兩個資料區塊(例如好感度區塊為格式版本 2、章節進度區塊為格式版本 1),**WHEN** 後續遊戲版本只提升好感度區塊的格式版本,**THEN** 讀取舊存檔時只會對好感度區塊觸發遷移函數鏈,章節進度區塊的遷移鏈不會被呼叫(其版本未變)。
- **AC-3**: **GIVEN** 存檔槽 A、B 皆已持有有效存檔,**WHEN** 對槽 A 發出新的寫入(自動或手動存檔),**THEN** 槽 B 在磁碟上的檔案在寫入前後逐位元組完全相同。
- **AC-4**: **GIVEN** 一個從未寫入過的存檔槽,**WHEN** 對該槽發出讀取請求,**THEN** 系統回傳一個獨立的「無資料」結果(非錯誤),且此結果須能與 D 節所有拒絕結果(損毀、遷移失敗、未來版本)在程式上明確區分。
- **AC-5**: **GIVEN** 槽 A 為目前 schema 版本 N(有效)、槽 B 為較舊版本 N-2(自版本升級後從未被讀取),**WHEN** 讀取槽 A,**THEN** 槽 B 的磁碟資料與版本標記逐位元組不變——讀取一個槽絕不會觸發另一個槽的遷移或任何狀態變化。

### B. Write Path & Atomicity

- **AC-6**: **GIVEN** 章節/戰役結構系統於進度邊界點觸發自動存檔,**WHEN** 寫入呼叫將控制權交還呼叫方,**THEN** 存檔資料已完整持久化至磁碟——不存在延遲/背景完成的通知機制,呼叫返回即代表序列化已完成。
- **AC-7**(2026-08-05 第三輪修訂措辭,回應 qa-lead 審查發現——原「範圍」一詞不夠精確,改寫為可逐位元組核對的斷言): **GIVEN** 手動存檔請求與自動存檔請求透過同一寫入介面、以相同世界狀態分別觸發,**WHEN** 任一者成功完成,**THEN** 兩份存檔的 manifest 列出的資料區塊集合、各區塊的來源系統識別碼、格式版本號、以及各區塊 payload 的位元組內容逐一比對完全相同,僅允許觸發來源中繼資料欄位(若存在)不同。
- **AC-8**(2026-08-05 第二輪重新指派用途,回應 systems-designer/qa-lead 審查發現——原版本斷言的是任何阻塞式函式呼叫的宿主語言免費保證〔呼叫 A 返回後才呼叫 B,B 必晚於 A 完成〕,無法區分正確與錯誤實作,已重寫): **GIVEN** debug 建置且啟用 Core Rules #15 的主執行緒斷言,**WHEN** 存檔寫入介面被一個非主執行緒呼叫(例如手動建立的 `Thread`,或未使用 `call_deferred()` 轉回主執行緒的 `WorkerThreadPool` 回呼),**THEN** 系統立即觸發斷言失敗,而非靜默完成寫入——此 AC 驗證 Core Rules #4 的單執行緒假設是可被自動偵測違反的不變量,而非僅仰賴人工遵守的文件敘述。
- **AC-9**: **GIVEN** 手動存檔請求與自動存檔觸發在極短時間內針對同一存檔槽先後發生(同一執行緒,先後而非並發),**WHEN** 兩者皆被觸發,**THEN** 兩者嚴格依呼叫順序執行,該槽最終狀態為後發生請求所寫入的內容——兩次寫入的欄位不會交錯或合併。
- **AC-10**: **GIVEN** 槽 A 持有一份有效的既有存檔,**WHEN** 對槽 A 的新寫入在完成前被中斷(進程被終止/注入寫入失敗),**THEN** 槽 A 事後的磁碟檔案與中斷寫入發生前逐位元組完全相同,且能成功讀取。
- **AC-11**: **GIVEN** 對一個空(從未寫入過)存檔槽 A 的寫入在完成前被中斷,**WHEN** 中斷發生,**THEN** 槽 A 之後回報為「空」(依 AC-4 的「無資料」),而非損毀或部分存檔狀態。
- **AC-12**: **GIVEN** 寫入正在進行、且目標槽已存在一份有效檔案,**WHEN** 在寫入呼叫返回前檢視檔案系統,**THEN** 既有的槽檔案未被觸碰,且存在一個獨立的暫存檔案——確認實作為「暫存檔案後置換」模式,而非直接原地修改目標檔案。

### C. Migration Chain

- **AC-13**: **GIVEN** 一份 schema 版本 3 的存檔、目前遊戲版本為 6,已註冊 3→4、4→5、5→6 三個遷移函數,**WHEN** 讀取該存檔,**THEN** 三個函數嚴格依序執行(3→4 完全結束才開始 4→5,4→5 完全結束才開始 5→6)——可透過為每個函數加上呼叫順序偵測工具驗證。
- **AC-14**(2026-08-05 第二輪重寫,移除並發語意——回應 systems-designer/qa-lead 獨立收斂發現:原版本的 WHEN 子句要求「同一執行緒在第一次呼叫返回前發出第二次呼叫」,這在 Core Rules #4 的單執行緒阻塞模型下無法被實際建構,原描述本身自相矛盾): **GIVEN** 一份 schema 版本 3 的存檔於目前遊戲版本 6 下讀取,**WHEN** 讀取請求開始、遷移函數尚未執行完成,**THEN** 該槽對外可查詢的狀態(透過獨立的、不觸發完整讀取的狀態查詢介面,見 Core Rules #15)回傳「待遷移」,不回傳任何部分或中間資料——此 AC 驗證的是狀態可觀測性本身,不涉及任何並發或跨執行緒情境。
- **AC-14b**(2026-08-05 第三輪新增,配合 Core Rules #5 分步執行模型,使用者裁決 D-2): **GIVEN** 一份 schema 版本 2 的存檔於目前版本 5 下讀取,遷移鏈為 2→3→4→5(共 3 步),**WHEN** 在遷移鏈執行期間查詢 Core Rules #15 新增的遷移進度查詢介面,**THEN** 該介面回傳的目前步數與總步數會隨遷移鏈實際執行進度更新(例如第 2→3 步執行完成、第 3→4 步尚未開始時,查詢回傳「已完成 1/3」),而非固定回傳一個與實際執行進度無關的靜態值——驗證 AC-14 的「待遷移」可觀測狀態背後對應的是真實的分步執行進度,而非僅為測試建構的假狀態。
- **AC-15**: **GIVEN** 一份已處於目前 schema 版本的存檔檔案,**WHEN** 讀取它,**THEN** 零個遷移函數被呼叫(例如 QA 可觀測的遷移呼叫計數器維持為 0)——與需要遷移的讀取路徑可觀測地不同。
- **AC-16**: **GIVEN** 新增 schema 版本 N+1,只新增一個 N→N+1 遷移函數,**WHEN** 讀取一份版本 N-2 的存檔於遊戲版本 N+1 下,**THEN** 既有的遷移鏈(N-2→N-1→N)不經修改直接執行,接著執行新增的 N→N+1 步驟——確認新增一個版本步驟不需要修改先前任何步驟。

### D. Migration Failure Handling

- **AC-17**: **GIVEN** 遷移步驟 k(例如 4→5)偵測到無法安全對應到目標 schema 的資料,**WHEN** 處理該次讀取,**THEN** 讀取被拒絕、該槽進入「遷移失敗」狀態,不回傳任何資料(部分或完整)給呼叫方,也不對無法對應的資料代入任何預設值/佔位值。
- **AC-18**: **GIVEN** AC-17 描述的遷移拒絕,**WHEN** 呼叫方檢視回傳的錯誤,**THEN** 它是一個結構化物件,至少包含:失敗發生的 schema 版本、失敗的具體資料區塊識別碼、機器可讀的原因代碼——不需解析自由格式文字即可程式化取得。

- **AC-54**(2026-08-05 第三輪新增,使用者裁決 D-4,驗證一般位元腐蝕的滾動備份回退路徑): **GIVEN** 一份已成功寫入、從未觸發遷移的存檔槽,`slot_N.dat` 的位元組本身已損毀(`DATA_CORRUPTED`,非版本不相容),且該槽先前至少完成過一次成功寫入(存在 `slot_N.prev.bak`),**WHEN** 下游系統透過唯讀存取介面查詢該槽,**THEN** 系統回傳 `slot_N.prev.bak` 的內容供檢視/匯出(唯讀,不自動載入為目前存檔),且此查詢同樣套用 AC-53 描述的型別白名單與完整性雜湊檢查。

### H. 效能量測(非功能性阻擋,2026-08-05 第二輪新增獨立子節)

*(回應 qa-lead 審查發現:AC-36 原本夾在 AC-32–AC-35 的功能性阻擋序列中間,任何掃描「AC-1 至 AC-N 全過」作為 Done 判準的工具或審查者,可能誤將此類量測型 AC 當成阻擋項。本節獨立列出,明確標示本節所有 AC 皆為效能追蹤性質,超標不阻擋 Story 完成,但須被追蹤且有明確的重新評估觸發條件——見 Tuning Knobs 的寬限上限規則。)*

- **AC-36**(2026-08-05 第二輪修訂,拆分子成本量測,回應 performance-analyst 審查發現——原版本只量測單一聚合耗時,無法區分瓶頸來源): **GIVEN** 一次典型規模的存檔寫入(目前遊戲規模的全部資料區塊),**WHEN** 測量從呼叫寫入介面到呼叫返回的總耗時,**THEN** 該耗時被拆分記錄為至少三段子成本——序列化耗時、完整性雜湊計算耗時、原子置換(暫存寫入+rename 序列)耗時——並與 Tuning Knobs `save_write_max_duration_ms` 門檻比較整體耗時;若超過門檻,在 QA 建置中標記為效能待校準項,不視為功能性失敗,但須被追蹤,且依 Tuning Knobs 新增的寬限上限規則,連續兩次超標即升級為 Core Rules #4 同步阻塞決定的必須重新評估觸發條件。子成本拆分的目的是讓超標時能區分「序列化本身太慢」(本系統可優化)與「平台檔案置換/防毒掃描等系統性延遲」(可能需要重新評估同步阻塞決定本身)兩種不同的根因。
- **AC-46**(回應 qa-lead 審查發現——`migration_chain_load_time_budget_ms` 先前完全沒有對應的量測 AC,與 `save_write_max_duration_ms` 不對稱;2026-08-05 第三輪修訂補上子成本拆分,回應 performance-analyst 審查發現——原版本只量測單一聚合耗時,而本路徑結構複雜度不低於 AC-36 的一般寫入路徑,理應有對等的診斷儀器;**2026-08-06 第四輪進一步拆分第一段,回應 performance-analyst 審查發現**——原第一段「遷移函數鏈本身執行耗時,含步間讓出排程開銷」混雜了「遷移函數計算時間」(決定性、可歸因於該步驟邏輯)與「引擎讓出/排程等待時間」(取決於當下影格負載等外部因素)兩種性質不同、無法乾淨切割的成本來源,直接牴觸本 AC 自陳的診斷目的——若不拆分,一條「每步資料量都小、但鏈很深」的遷移鏈量出的第一桶數字會偏高,可能誤導工程資源投向錯誤的優化目標): **GIVEN** 一次觸發遷移鏈的讀取(遷移鏈執行 + Core Rules #13 觸發的兩階段回寫,即 Tuning Knobs `migration_chain_load_time_budget_ms` 定義的複合路徑),**WHEN** 測量從讀取請求開始到該次讀取可用為止的總耗時,**THEN** 該耗時被拆分記錄為至少五段子成本——**遷移函數計算耗時**(各步驟遷移函數本身的邏輯執行時間)、**步間讓出排程等待耗時**(Core Rules #5 分步執行模型下,控制權交還引擎主迴圈的等待時間,與資料量無關)、Core Rules #12/#7 結構與語意檢查耗時、Core Rules #13 階段 A(存底建立)耗時、Core Rules #13 階段 B(即 AC-36 描述的原子置換複合耗時)——並與 `migration_chain_load_time_budget_ms` 門檻比較整體耗時;若超過門檻,標記為效能待校準項並追蹤,是 `max_supported_migration_depth` 政策(目前無上限)重新評估的觸發條件之一。子成本拆分的目的與 AC-36 相同:讓超標時能區分「遷移函數本身變重」(可能需要優化遷移函數邏輯)、「鏈深度本身的讓出開銷隨深度線性成長」(可能需要重新評估鏈深度上限政策)、與「單次寫入相關的系統性延遲」(與 AC-36 根因相同,不需要重複調查)三種不同的根因,不再混算成單一數字。

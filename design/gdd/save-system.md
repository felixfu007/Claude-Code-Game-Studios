## Overview

存檔系統負責將遊戲的全部持久化狀態——好感度數值池的完整 Delta Log(含戰役刻度標記列表)、章節/戰役進度、活棋盤地形規則版本、以及未來其他系統陸續產生的存檔需求——無損序列化到磁碟,並在讀取時完整還原。它不參與任何玩法規則的計算,純粹是一個資料持久化與版本相容性的基礎設施層:任何系統只要遵循本系統的介面寫入自己的狀態,就能保證該狀態在存檔/讀檔之間不遺失、不被靜默竄改,也不會因為遊戲版本推進(尤其是活棋盤規則隨劇情演變導致存檔跨版本不相容)而在舊存檔上讀取時損毀或需要玩家重新開局。

## Player Fantasy

好感度數值池對玩家的承諾是「你做過的事永遠算數」。存檔系統是那句承諾在時間軸上的延伸——跨過關機、跨過版本更新,那份共同歷史仍然逐筆完整。玩家感受到的不是本系統,而是回到遊戲時關係從未被重設的踏實感。**這份承諾的範圍是「已成功寫入的最後一個進度邊界」**(2026-08-05 第二輪新增,回應 game-designer 審查發現)——一場尚未觸發自動存檔就當機的戰鬥,遺失其間發生的好感度變化,是任何存檔系統的標準行為,不構成對本節承諾的違反;本節保證的是「已經存下的,永遠不會不見、不會被靜默改變」,不是「任何已發生但尚未存檔的事都會被保留」。

這裡的信任是二元的:一次失敗就永久摧毀,不會被九十九次成功補回。三種讓玩家失信的具體情境,依嚴重度排序(最嚴重者排最先),決定了本文件下游章節(Edge Cases、Acceptance Criteria)必須以什麼標準書寫:
- **靜默資料遺失最毒**——版本更新後好感度形狀變了卻沒人告訴玩家,玩家會開始懷疑整套關係系統本身是否誠實。
- **要求玩家管理存檔本身次之**(手動備份、自行判讀哪些資料還在哪些不在、自行選擇存檔槽版本)——把基礎設施的責任外包給玩家,即使沒有資料遺失,也已經違反本節「玩家從不需要想到存檔」的體驗目標,而且比單純的中斷更傷,因為它要求玩家持續投入認知努力去判讀一份不完整的存檔,不是一次性的挫折。
- **可見的中斷再次之**——讀檔失敗且清楚呈現、明確可理解的拒絕,雖然打斷了遊戲流程,但玩家不需要自己判斷任何事,一次性承受、隨即恢復正常。

> **(2026-08-05 第二輪 `/design-review` 修訂,使用者裁決 A2)**:第一輪版本的清單順序與同節取捨聲明的文字互相矛盾——清單原將「要求玩家管理存檔」列為最輕,取捨聲明卻稱其為「第二嚴重」。本輪以取捨聲明的判斷為準,改寫清單順序:要求玩家管理存檔本身,比單純的可見中斷更嚴重,因為後者只是一次性事件,前者要求玩家持續承擔判讀責任。這連帶修正了下方取捨聲明的論證方向。

這決定了下游設計原則:規則集遷移必須被當成**常態路徑**而非例外處理;任何無法保證無損的情況,**寧可拒絕載入並明確告知玩家,也不可靜默降級或部分還原**。

**取捨聲明(2026-08-05,第一輪 `/design-review` 補述;第二輪修訂與上方清單順序一致化)**:上述「寧可拒絕載入」的政策,曾在審查中被挑戰是否該改成允許部分載入(僅標示受影響區塊遺失,其餘資料正常還原)——這樣理論上能保留更多資料,似乎更貼近承諾一。裁定維持整份拒絕,理由回到本節自訂的三級嚴重度排序本身:部分載入需要玩家理解「哪些資料還在、哪些不在」並決定如何看待這份不完整的存檔,這正是排序中第二嚴重(要求玩家管理存檔本身)的具體樣貌,而整份拒絕只觸及第三級(可見的中斷),兩者之間本系統選擇犧牲「保留更多資料」以換取「絕不讓玩家承擔判讀殘缺存檔的責任」。這是刻意的取捨,不是未經檢視的預設值。

**此取捨的成立前提(2026-08-05 第二輪新增,回應 game-designer 審查發現)**:上述論證要成立,「整份拒絕」本身就不能退化成要求玩家管理存檔——若拒絕後的唯一出路是無限期等待未來修補、且沒有任何中繼緩解,玩家仍然被迫自行決定「要不要繼續等這個槽」,一樣落入第二嚴重級,取捨聲明的成本估算就不成立。因此本文件的遷移失敗處理(見 Core Rules #13、Edge Cases)必須確保:拒絕載入的同時,系統主動提供一份完好的唯讀資料快照供檢視/匯出,玩家不需要自己判斷任何事——見 Core Rules #13 新增的「原始位元組保留」規則與其唯讀存取契約。

## Detailed Rules

*(2026-08-05 第二輪修訂:標題由「Detailed Design」更名為「Detailed Rules」,對齊 `design/CLAUDE.md`/`.claude/rules/design-docs.md` 標準命名,內容不變。原「Lean mode 未諮詢」註記已由第二輪完整對抗性審查〔systems-designer、godot-specialist 皆已審查本節〕取代,故移除。)*

### Core Rules

1. **存檔資料結構(manifest + 版本化區塊)**:每份存檔是一個帶有明確 schema 版本號的檔案,內含一份 manifest,列出這份存檔包含哪些系統的資料區塊(例如:好感度數值池的 Delta Log + 戰役刻度標記列表、章節/戰役進度、活棋盤地形規則版本、未來新增系統的資料)。每個資料區塊各自標註自己的來源系統與該系統當下的資料格式版本——這讓不同系統的資料可以獨立演進格式,不需要每次任何一個系統改格式就牽動整份存檔重新定義。
2. **存檔槽**:支援多個獨立存檔槽,每槽各自持有完整的 manifest 與全部資料區塊,槽與槽之間互不影響、互不共用狀態。存檔槽數量上限與槽位管理 UI(建立/覆寫/刪除槽位)屬於下游 UI 系統的範圍,本系統只保證槽與槽之間的資料隔離性。
3. **觸發模式**:
   - **自動存檔**為主要機制,於明確定義的進度邊界點觸發(例如每場戰鬥結束、每個章節開始/結束——實際觸發點清單由呼叫方系統〔章節/戰役結構〕決定並呼叫本系統的寫入介面,本系統不主動偵測遊戲狀態)。
   - **手動存檔**作為額外入口,供玩家自行選擇存檔時機,寫入同一套存檔槽機制,不是獨立的存檔類型。
   - 兩者共用同一套寫入邏輯與資料完整性保證,差異只在觸發來源。
4. **寫入行為(同步阻塞式,provisional)**:存檔寫入目前設計為**同步阻塞式**——呼叫存檔介面的執行緒會等待序列化完成才繼續執行,接受寫入當下的短暫卡頓(而非引入非同步/背景執行緒序列化)。**本系統假設所有寫入呼叫皆發生於同一個執行緒**(例如 Godot 主執行緒的事件迴圈)——這是「不需額外鎖定」結論成立的前提;若未來出現真正跨執行緒的寫入呼叫者,此假設需要重新驗證。

   **此決定的狀態是 provisional(傾向,非定案)**,理由:(a) 主機平台的 SaveData API 常見設計上即為非同步,本系統目前未確認的主機平台目標(見 `game-concept.md` 尚待補齊的主機規格缺口)可能無法直接支援同步阻塞語意;(b) 寫入耗時是否落在可接受的卡頓範圍尚未實測(見 Tuning Knobs `save_write_max_duration_ms`)。**若之後需要重新啟用非同步寫入**,以下介面需要回頭補上:好感度數值池(`design/gdd/affinity-data-pool.md`)Edge Cases 提出的序列化生命週期通知介面(begin/end)、對應的 AC-47(目前狀態:N/A,見下方 Dependencies 的交接註記——本輪修訂**不**回頭重開該文件的 AC-47,留待格式/架構決策階段與此處一併處理)。
5. **跨規則集遷移(版本陣列式逐步遷移)**:每份存檔的 manifest 記錄寫入當下的**規則集版本號**(單調遞增整數)。讀取存檔時,若存檔版本號低於目前遊戲版本,依序執行 `v→v+1`、`v+1→v+2`、…、直到目前版本的遷移函數鏈,每個版本躍遷只需定義「這一步」的轉換規則,不需要重寫早期版本到現在版本的直接轉換。新增規則集版本時,只需新增一個對應的遷移函數,既有的遷移函数鏈不受影響。
6. **遷移失敗處理(拒絕讀取,不靜默降級)**:若遷移函數鏈中任一步驟偵測到無法安全對應的資料(例如舊規則集的某個概念在新規則集中沒有對應結構),**拒絕載入該存檔,並向呼叫方回傳明確的錯誤原因**(哪個版本、哪個資料區塊、為何無法遷移)——不得嘗試部分還原或以預設值靜默補完缺失資料。錯誤訊息的呈現方式屬於下游 UI 系統的範圍,本系統只保證錯誤原因本身是明確、可呈現的結構化資料,不是純文字例外訊息。

   **拒絕原因的機器可讀分類(2026-08-05 第二輪新增,回應 game-designer 審查發現)**:結構化錯誤的原因代碼須至少區分四類,四類彼此獨立、下游 UI 不得合併呈現:(一)`MIGRATION_FAILED`——遷移函數鏈中某步驟無法安全對應;(二)`DATA_CORRUPTED`——完整性標記不符或位元組本身無法解析;(三)`VERSION_TOO_NEW`——存檔版本高於目前遊戲支援版本;(四)`SEMANTIC_VALIDATION_FAILED`(新增)——區塊已是目前版本、未觸發遷移鏈,但未通過 Core Rules #7 語意驗證。第四類與第一類的關鍵差異:第四類沒有任何遷移步驟可以「修復」,其自動痊癒路徑(見 Core Rules #13)依賴的是語意驗證規則本身被修正,而非遷移函數被補齊——兩者的觸發條件與呈現語意都不同,下游 UI 若混用第一類與第四類的訊息模板,會誤導玩家以為問題出在版本相容性,而非資料本身違反目前規則。
7. **語意驗證(反序列化後,非格式驗證)**:每個資料區塊在通過格式層級的反序列化後,還須通過各自來源系統宣告的語意合法性檢查(例如數值欄位落在合法值域內、非 NaN/Infinity、來源標記屬於已知列舉集合)。任何一項語意檢查失敗,依 Core Rules #6 的拒絕路徑處理,回傳 `SEMANTIC_VALIDATION_FAILED` 原因代碼(即使該區塊本身格式版本與目前版本相同、未觸發遷移鏈)——**格式正確不代表語意合法**,這是格式層級的反序列化(尤其若最終格式選用引擎原生序列化器)本身無法保證的一層。

   **驗證器宣告為強制項,未宣告視為錯誤(2026-08-05 第二輪新增,回應 security-engineer 審查發現,fail-open 修正為 fail-closed)**:每個持久化資料區塊,在其來源系統的 GDD 定案時,**必須**明確宣告該區塊每個欄位的語意合法性規則(值域、型別、允許的列舉值等)。manifest 中若列出一個沒有對應驗證器宣告的資料區塊,**該 manifest 本身視為錯誤**,依 Core Rules #6 的 `DATA_CORRUPTED` 路徑拒絕讀取——即「未宣告驗證規則」不等於「跳過驗證」,而是與「驗證失敗」同等對待。此規則翻轉了原本隱含的預設值:第一輪版本允許「來源系統沒宣告驗證器」的區塊悄悄跳過語意檢查,本輪修正為預設拒絕、通過必須是明確結果。目前唯一已定案的來源系統(好感度數值池)已在 Dependencies 章節宣告其驗證規則;尚未設計的下游系統於 `/design-system` 階段須將此列為必要交付項,而非事後補充。

   **語意驗證同樣套用於遷移函數的輸出(2026-08-05 第二輪新增,回應 security-engineer 審查發現,消解 Core Rules #12 與本條之間的曖昧關係)**:每個遷移函數的最終輸出,除了須通過 Core Rules #12 的結構性後置條件檢查,還須通過本條的語意驗證——即語意驗證不只發生在「初次反序列化、未觸發遷移鏈」的路徑,也發生在「遷移鏈執行完成後」的路徑。任何一步遷移的最終輸出未通過語意驗證,依 Core Rules #6 的 `MIGRATION_FAILED` 路徑拒絕(不使用 `SEMANTIC_VALIDATION_FAILED`,因為此情境確實觸發了遷移鏈)。此規則是本輪修法解決「no-op 或輸出恰好滿足結構檢查但語意錯誤的遷移函數被誤判成功」問題(見 Core Rules #13)的第二道防線——Core Rules #13 的原始位元組保留是最後一道安全網,本條是提早攔截、減少需要動用安全網的頻率。
8. **Manifest 自我完整性標記(2026-08-05 第二輪修訂,「位元組筆數或雜湊擇一」改為強制雜湊,回應 systems-designer/security-engineer 獨立收斂發現)**:manifest 除列出各資料區塊的來源與版本外,另記錄一份可驗證的完整性標記——**須為涵蓋該區塊完整內容的加密雜湊值(例如 SHA-256 或等效強度演算法),不得僅以位元組筆數作為完整性標記**(位元組筆數無法偵測任何維持原長度的竄改或位元損毀,例如單一位元翻轉、同寬度欄位互換,不構成有效的完整性控制)。**雜湊的輸入須涵蓋該區塊的宣告身分與宣告版本中繼資料,不得只涵蓋 payload 本身**——否則一份雜湊校驗通過的 payload,可能被錯誤標記成不同的來源系統識別碼或格式版本號(不論是因為攻擊者竄改、或更常見地,是因為一次不完整的寫入/搞砸的遷移回寫導致 manifest 與 payload 錯配),進而被路由進錯誤的遷移函數鏈,造成靜默的語意損壞——這是一般正常操作(誠實玩家、系統本身的 bug)就可能觸發的正確性問題,不需要假設任何惡意行為。讀取時先核對此標記,標記不符視為「資料損毀」(`DATA_CORRUPTED`,見 Core Rules #6,與 AC-19/AC-28 共用錯誤路徑),不進入正常還原或遷移路徑。

   **威脅模型範圍聲明(2026-08-05 第二輪新增,回應 security-engineer 審查發現)**:本條完整性標記的保護範圍是**意外損毀與未經工具協助的手動編輯**,**不是**反作弊或防止知情攻擊者竄改的保證——雜湊演算法與 manifest 格式本身不是秘密,一個理解本系統設計的攻擊者可以竄改任何欄位後重新計算雜湊值,使竄改後的檔案通過本條的完整性檢查。本系統的所有驗證邏輯(本條、Core Rules #7、Core Rules #9)皆執行於用戶端,不構成伺服器權威式的反作弊保證。此範圍聲明特別重要,因為 Core Rules #9 的理由段落點名「玩家之間分享的存檔」為威脅情境,容易讓讀者誤以為本系統對此有完整防護——實際上本系統只保證「格式與語意層級的自我一致性」,不保證「內容真實反映玩家實際遊玩歷程」。若未來任何系統(例如排行榜、跨玩家好感度軌跡比較)需要消費存檔衍生資料於信任敏感情境,該系統必須將此資料視為玩家可自行宣稱的內容,不得視為已驗證的事實。
9. **反序列化型別白名單**:不論最終序列化格式為何,反序列化路徑僅允許實例化一份預先登記的已知型別清單,任何未登記型別視為資料損毀(同 Core Rules #8 的完整性失敗路徑)。此為防禦措施,防範不受信任的存檔檔案(例如玩家之間分享的存檔)嘗試觸發非預期型別的實例化。

   **白名單的版本分域範圍(2026-08-05 第二輪標記,回應 security-engineer 審查發現;creative-director 綜合裁決降為 `/create-architecture` 階段必辦項,不列為本輪 GDD 阻擋)**:本條未指定白名單是「所有版本曾合法型別的扁平聯集」還是「依存檔宣告版本分域」——若為前者(支援舊存檔遷移的自然實作),理論上存在「宣告舊 schema 版本以路由進較少被檢視的舊版遷移程式碼路徑」的風險。此風險的前提是持有惡意構造存檔的攻擊者,在本系統目前的單機、無伺服器信任邊界威脅模型下(見 Core Rules #8 威脅模型範圍聲明)優先度較低,但機制本身要到序列化格式定案才能具體定義,故列為 Open Questions 的必辦項,不在此階段憑空規定。
10. **索引鍵持久化採字串名稱,不採 enum 序數**:`Pair`(及未來任何以 enum 表示、需要跨版本穩定持久化的索引鍵)一律以其**字串名稱**持久化,並在對應資料區塊內維護一份「字串名稱↔目前 enum 定義」的對照表。讀取時以名稱查表還原,若名稱在目前 enum 定義中找不到對應項,視為 Core Rules #6 的 `MIGRATION_FAILED`(需要遷移函數明確處理該重新命名/移除的情況)。**此規則存在的理由**:enum 定義順序調整(重構、插入新項目)是常見且合理的未來變更,若以序數持久化,順序調整會讓存檔靜默還原成錯誤但合法的配對,且此錯誤無法被任何現有機制偵測到——這是第一輪審查發現的最高風險項(見 review-log)。

    **退役名稱治理規則(2026-08-05 第二輪新增,回應 systems-designer/qa-lead 獨立收斂發現,堵住「名稱重用碰撞」漏洞)**:上一段的緩解機制只擋住「名稱在目前 enum 定義中找不到」(刪除)的情況,不擋「名稱找得到,但目前指向的是另一個語意不同的實體」(重用)的情況——若某個索引鍵字串曾被除役(該配對被移除或重新命名),而重構者日後把**同一個字串**重新指派給一個語意不同的新配對,舊存檔讀取時查表**會成功**,只是找到的是錯的實體,系統無法從查表機制本身偵測到這個錯誤,原始問題並未被真正解決,只是換了觸發途徑,這正是本輪審查發現的最高風險項(五位專家中三位獨立收斂於此)。**治理規則:任何曾經在對照表中出現過的索引鍵字串名稱,一旦除役(對應的配對被移除或重新命名為其他字串),該字串本身永久保留為「已退役」狀態,不得被重新指派給任何新的配對或索引鍵實體——即使是語意上「感覺相關」的新實體,也必須使用不同的字串名稱。** 對照表須明確標記退役狀態(而非直接刪除該筆對應),讓「名稱是否曾被使用過」本身可查詢,防止未來的內容變更意外撞名。此為治理紀律,不依賴任何執行期機制強制——`/create-architecture` 階段須確保對照表的維護流程(例如版本控制中的資料檔案審查清單)能落實此規則。
11. **遷移函數的確定性要求**:所有遷移函數必須是純函數——相同輸入永遠產生相同輸出,不依賴當下系統時間、隨機數、或任何遷移鏈之外的可變狀態。這是 Edge Cases「當機安全」論證成立的前提(讀取重跑遷移鏈必須保證與原本執行的結果一致)。
12. **遷移函數的後置條件檢查**:每個遷移函數執行完成後,須通過對應目標版本 schema 的後置條件檢查(至少涵蓋必要欄位存在性、值域合法性)。後置條件檢查失敗視同 Core Rules #6 的遷移失敗,即使遷移函數本身沒有拋出例外——防止「執行成功但轉換錯誤」的遷移函數被誤判為成功。

    **（2026-08-05 第二輪補充說明,回應 systems-designer/security-engineer 審查發現)**:本條的後置條件檢查是**結構層級**(必要欄位存在性、值域合法性),不是**語意正確性**的完整驗證——語意層級的驗證由 Core Rules #7 涵蓋(該條第二輪已明確擴大套用範圍至遷移函數的輸出,見該條)。兩者是遷移鏈輸出必須依序通過的兩道獨立檢查,缺一不可:結構檢查抓「這筆資料還算不算一個合法的目標 schema 實例」,語意檢查抓「這筆資料的內容是否代表一個合理的關係狀態」。一個有 bug 但輸出恰好同時滿足兩道檢查的遷移函數仍然可能存在(語意驗證的涵蓋範圍終究取決於各來源系統宣告的規則有多嚴謹)——這正是 Core Rules #13 新增「原始位元組保留」規則要作為最後一道安全網的理由。

13. **遷移成功後立即回寫,含自動痊癒保證與原始位元組保留(2026-08-05 第二輪修訂,回應 systems-designer/security-engineer/game-designer 獨立收斂發現,使用者裁決 B-甲)**:遷移函數鏈完整執行成功且通過 Core Rules #12 後置條件檢查與 Core Rules #7 語意驗證後,系統立即以遷移後的結果覆寫該存檔槽(視同觸發一次新的自動存檔,套用 Core Rules #4 與 Edge Cases 的原子寫入保證)。**回寫時不得銷毀遷移前的原始位元組**——原始版本以獨立的存底檔案形式與遷移後結果並存於同一存檔槽目錄下(例如 `slot_N.dat`〔目前版本〕與 `slot_N.pre_migration.bak`〔遷移前原始位元組,唯讀,不參與正常讀取路徑〕),保留最近一次遷移前的完整存底。回寫完成後,該槽的版本標記即為目前遊戲版本,後續讀取不再重跑已完成的遷移步驟,正常讀取路徑一律讀取目前版本檔案,不讀取存底。

    **此規則存在的理由**:Core Rules #12 的後置條件檢查只驗證結構,不驗證語意正確性——一個有 bug 但輸出恰好滿足結構檢查(且未被 Core Rules #7 語意驗證攔截)的遷移函數,在第一輪設計下會被判定成功並立即覆寫原始資料,而該槽從此不會再進入「遷移失敗」狀態,即使未來修正了該 bug,原本的自動痊癒保證也無法觸及一個從未被判定為失敗的槽——資料已經被靜默、永久、不可逆地覆寫成語意錯誤但格式合法的內容。保留原始位元組把這個失敗模式的傷害上限,從「不可逆覆寫」降回「可逆的錯誤回寫,只要原始資料還在就能重新來過」。

    **自動痊癒保證(擴大範圍)**:(一)若某存檔槽先前因某個遷移步驟缺失處理邏輯而進入「遷移失敗」狀態(Core Rules #6,`MIGRATION_FAILED`),而後續遊戲更新為該步驟補上了正確的遷移函數,玩家下次讀取該槽時遷移鏈會自動重新嘗試——若這次成功,槽狀態自動從「遷移失敗」轉為「有效」並依本規則立即回寫,不需要玩家做任何動作。(二)若某存檔槽已完成回寫、槽狀態為「有效」,但日後發現該次遷移的後置條件與語意驗證其實遺漏了某個語意錯誤,遊戲更新修正該遷移函數的邏輯後,系統可對該槽以存底位元組重新執行修正後的遷移鏈(不在一般玩家讀取路徑中自動觸發,屬於維運/更新層級的補救手段,實際觸發機制留待 `/create-architecture` 階段設計)——此路徑之所以可行,完全依賴存底位元組仍然存在。(三)若某語意驗證失敗(Core Rules #7,`SEMANTIC_VALIDATION_FAILED`)發生在目前版本區塊(未觸發遷移鏈),而後續版本修正了該驗證規則本身的邏輯或值域定義,玩家下次讀取時語意驗證會以修正後的規則重新執行——若這次通過,槽狀態自動從「遷移失敗」轉為「有效」,不需要玩家做任何動作。

    **遭拒存檔的唯讀存取(呼應 Player Fantasy「此取捨的成立前提」)**:任一存檔槽處於「遷移失敗」狀態期間,系統必須能讓下游 UI 系統透過獨立的唯讀介面存取該槽最近一次的完好資料(即遷移前存底,若槽從未成功遷移過,則為該槽最後一次成功寫入的內容)——供玩家檢視或匯出,不需要玩家自行判斷「哪些資料還在」。此唯讀介面與正常讀取介面分離,不改變槽的遷移失敗狀態,也不繞過 Core Rules #6 的拒絕政策本身(玩家仍無法把這份資料當成「目前存檔」繼續遊玩,只能檢視/匯出)。

14. **跨平台原子置換語意是行為契約,不是機制假設(2026-08-05 第二輪修訂具體安全序列,回應 godot-specialist 審查發現——原範例本身違反自身契約)**:Edge Cases「若寫入過程中途失敗」定義的原子寫入保證(先寫暫存檔案、確認完整後才取代)是本系統對所有平台一致要求的**行為契約**——不綁定任何特定 API 的實作假設。

    **具體安全序列(2026-08-05 第二輪新增)**:第一輪版本曾舉例「刪除舊檔前置檢查」作為可能的實作手法,但該序列本身在「刪除完成、置換尚未完成」之間存在一個新舊檔案皆不存在的視窗,若行程於此視窗當機/斷電,會直接違反本節與 Edge Cases 共同定義的保證(既有存檔槽維持寫入前最後一個有效狀態不變)。**該範例已撤回,改為以下已知安全、不依賴任何特定平台「取代已存在目標」語意的序列**,現在鎖定為本規則的具體實作要求(不留給 `/create-architecture` 自由裁量):
    1. 寫入暫存檔案(例如 `slot_N.tmp`),確保內容完整寫入並 flush。
    2. 若目標槽既有有效檔案(`slot_N.dat`)存在,將其 rename 為備份檔(`slot_N.bak`)——rename,不是刪除。
    3. 將暫存檔案 rename 為目標檔案(`slot_N.dat`)。
    4. 若備份檔存在,刪除之(`slot_N.bak`)。

    此序列的每一步邊界都至少存在一個可辨識的有效檔案(`.dat` 或 `.bak`),當機後可靠地推斷上次寫入是否完成,不會出現「兩者皆缺」的視窗。

    **讀取端回復規則(2026-08-05 第二輪新增,補上安全序列原本缺少的另一半)**:載入存檔槽時,若偵測到目標檔案(`slot_N.dat`)缺失或無法解析、但備份檔(`slot_N.bak`)存在,視為上一次寫入在步驟 3-4 之間中斷,系統須將 `slot_N.bak` 視為該槽最後一個有效狀態,依正常讀取路徑處理(不視為資料損毀)。此規則若缺席,上述安全序列產生的備份檔將無人讀取,退化成單純佔用磁碟空間的殘留物,不提供任何實際保護。

    若某平台的原生 API 無法直接達成此序列的每一步語意(例如某些主機平台的檔案置換沙盒化行為),該階段須為該平台補上等效機制,但對外行為必須維持本節定義的契約不變。

15. **可觀測性義務(2026-08-05 第二輪新增,回應 systems-designer/qa-lead/godot-specialist 收斂發現)**:為了讓 Acceptance Criteria 中依賴行為觀測的驗收條件(例如遷移呼叫順序、遷移呼叫次數)可被獨立驗證而非仰賴實作者自行遵守文件敘述,本系統須提供以下僅供 QA/除錯用途的診斷介面,不得作為下游系統業務邏輯依賴的正式回傳簽章:
    - **遷移呼叫計數器**:記錄本次讀取實際呼叫了幾次遷移函數(供 AC-15 等驗證「零遷移」與「恰好一次遷移」的情境)。
    - **遷移呼叫順序記錄**:記錄各遷移函數被呼叫的時間順序(供 AC-13 驗證嚴格依序執行)。
    - **主執行緒斷言(debug 建置)**:存檔寫入/讀取介面入口須在 debug 建置中斷言呼叫執行緒為主執行緒(例如比對 `OS.get_thread_caller_id()` 與 `OS.get_main_thread_id()`,見 godot-specialist 審查發現),讓 Core Rules #4 的單執行緒假設從「文件聲明」變成「可被自動偵測違反的不變量」——任何違反假設的呼叫在 debug 建置中應立即觸發斷言失敗,而非在 release 建置中靜默產生未定義行為。

### States and Transitions

| 狀態 | 進入條件 | 離開條件 | 行為 |
|---|---|---|---|
| 空(Empty) | 該存檔槽從未寫入過 | 首次寫入成功 | 讀取請求回傳「無資料」,不視為錯誤 |
| 有效(Valid) | 寫入成功且版本號等於目前遊戲版本 | 遊戲版本升級後首次讀取該槽 | 讀取直接還原,不需要遷移 |
| 待遷移(Pending Migration) | 讀取時偵測到存檔版本號低於目前遊戲版本 | 遷移函數鏈執行完成(成功或失敗) | 依序執行遷移函數鏈,期間該槽對外仍視為不可讀取;下游 UI 須呈現進行中/忙碌指示(見 Interactions 最低呈現契約),不得表現為無回應 |
| 遷移失敗(Migration Failed) | 遷移函數鏈中任一步驟偵測到無法安全對應的資料(`MIGRATION_FAILED`),**或**目前版本區塊未通過 Core Rules #7 語意驗證(`SEMANTIC_VALIDATION_FAILED`,2026-08-05 第二輪新增,兩種進入條件對應不同的拒絕原因代碼,見 Core Rules #6) | 下次讀取嘗試時遷移函數鏈(或語意驗證)重新執行且這次成功(例如遊戲更新後補齊了先前缺失的遷移函數,或修正了驗證規則本身,見 Core Rules #13 自動痊癒保證擴大範圍),或該存檔槽被覆寫 | 拒絕載入,回傳結構化錯誤原因(四類原因代碼之一,見 Core Rules #6);存檔槽本身不被本系統自動刪除或修改;**下游 UI 系統可透過獨立的唯讀介面存取該槽最近一次的完好資料(遷移前存底或最後一次成功寫入內容,見 Core Rules #13),玩家不需要自行判讀哪些資料還在,只需要決定是否繼續等待或放棄該槽**(2026-08-05 第二輪修訂,回應 Player Fantasy「此取捨的成立前提」);玩家「確認錯誤訊息」只是 UI 層級的告知動作,不改變系統狀態本身——下次讀取仍會重新嘗試 |
| 寫入中(Writing) | 呼叫寫入介面(自動或手動存檔觸發) | 序列化完成(同步阻塞,呼叫方執行緒等待此狀態結束) | 阻塞呼叫方執行緒直到完成;由於採同步阻塞式寫入,不存在「寫入中收到另一個寫入請求」的並發情況(見 Core Rules #4) |

### Interactions with Other Systems

- **好感度數值池(持久化義務,讀取方向)**:本系統必須無損序列化/還原完整 Delta Log(所有記錄,含 `c_i` 欄位)與獨立的戰役刻度標記列表,不做壓縮或摘要。索引鍵(如配對 `Pair`)於存檔格式中以**字串名稱**持久化(見 Core Rules #10),不以 enum 序數持久化——enum 定義順序調整不影響已存檔資料的正確性。由於本系統目前採同步阻塞式寫入(見 Core Rules #4,provisional),該文件要求的「序列化生命週期通知介面」(begin/end)目前不需要實作;若該決定日後重新開啟為非同步,此介面需要回頭補上。
- **章節/戰役結構(呼叫方,寫入觸發來源)**:章節/戰役結構系統決定自動存檔的實際觸發時機點(例如每場戰鬥結束、每章開始),呼叫本系統的寫入介面。本系統不主動偵測遊戲進度,純粹被動回應呼叫。
- **活棋盤地形演變系統(資料來源,尚未設計)**:地形規則版本是跨規則集遷移的核心資料——本系統假設該系統的規則資料本身有明確的版本標記機制,若該系統設計時採 Godot Resource 子類別實作規則資料,須遵循 `game-concept.md` 已記錄的「Resource 參照共享風險」對應的深層複製紀律(`duplicate_deep()`),避免存檔寫入時意外持有共享參照而非獨立快照。
- **好感度視覺呈現 UI / 未來的存檔管理 UI(讀取方,尚未設計)**:存檔槽的建立/覆寫/刪除介面、遷移失敗的錯誤訊息呈現,皆屬於下游 UI 系統的範圍——本系統只保證資料完整性與結構化的錯誤資訊,不涉及任何畫面呈現。**最低呈現契約(2026-08-05 第二輪修訂,原三類拒絕原因擴充為四類,並新增三項呈現要求)**:下游 UI 不得允許玩家在未看到結構化錯誤原因的情況下重試同一個已知失敗的操作而不告知後果,且必須將 Core Rules #6 定義的四種拒絕原因(`DATA_CORRUPTED` / `MIGRATION_FAILED` / `VERSION_TOO_NEW` / `SEMANTIC_VALIDATION_FAILED`)以玩家可理解的方式區分呈現,不得統一顯示成單一「讀取失敗」訊息。

- **版本過新的呈現須框為「可回復」,不得與資料損毀同等呈現**(2026-08-05 第二輪新增,回應 game-designer 審查發現):`VERSION_TOO_NEW` 在 PC 平台上很可能是玩家在 Steam beta/穩定分支間切換造成的常態情境,不是罕見的存檔損毀——下游 UI 須明確傳達「切回較新版本的遊戲即可繼續讀取此存檔」,不得使用與資料損毀相同的措辭或視覺樣式。
- **遷移進行中須有進度/忙碌呈現**(2026-08-05 第二輪新增,回應 systems-designer 審查發現):由於遷移鏈深度目前無上限(見 Tuning Knobs),下游 UI 於「待遷移」狀態期間,須向玩家呈現明確的進行中/忙碌指示,不得表現為無回應的凍結畫面——即使無法呈現精確進度百分比,至少須呈現「正在處理」的持續性回饋。
- **遭拒存檔的唯讀存取**(2026-08-05 第二輪新增,呼應 Core Rules #13 與 Player Fantasy「此取捨的成立前提」):存檔槽處於「遷移失敗」狀態時,下游 UI 須提供存取該槽最近一次完好資料(唯讀)的入口,不得只呈現一個無法互動的錯誤訊息——玩家應能檢視或匯出這份資料,即使無法將其當作可繼續遊玩的存檔載入。

## Formulas

不適用——本系統是純基礎設施(存檔序列化/還原/版本遷移),沒有從數學表達式計算出的數值輸出(不像傷害公式、掉落率、或好感度數值池的衰減曲線)。**(2026-08-03,systems-designer 諮詢確認;2026-08-05 第一輪 `/design-review` 修正引用範圍)**:曾評估三個可能的隱藏公式候選——遷移函數鏈深度、存檔檔案大小、自動存檔頻率與寫入阻塞時間的取捨——三者皆非公式導向的問題:遷移鏈深度是架構政策取捨(見 Tuning Knobs);存檔大小在目前規模下是簡單線性乘法(`total_size ≈ slots × per_slot_size`),`per_slot_size` 依 `affinity-data-pool.md` Open Question 9 的估算落在數十 KB 等級,這只回答「存檔多大」,不构成、也不引用該文件對「序列化這份資料需要多少時間」的任何結論(該文件 Open Question 9 明文禁止如此引用,見其護欄註記)。**自動存檔頻率與寫入阻塞時間之間的實際權衡本身尚未回答**,留待 Tuning Knobs 的 `save_write_max_duration_ms` 由實測校準,不以資料大小反推。

## Edge Cases

*(2026-08-05 第二輪修訂:原「Lean mode 未諮詢」註記移除——本節已於第二輪完整對抗性審查中由 systems-designer、qa-lead、security-engineer、game-designer 四位專家審查,新增兩則邊界情境。)*

- **若寫入過程中途失敗(斷電、磁碟已滿、權限錯誤)**:採用原子寫入模式——先寫入暫存檔案,確認完整寫入成功後才取代既有存檔槽的檔案,絕不直接覆寫既有有效存檔。若寫入失敗,既有存檔槽維持寫入前的最後一個有效狀態不變,不產生半寫入的損毀檔案。呼叫方(自動/手動存檔觸發來源)會收到寫入失敗的錯誤,由其決定是否重試。
- **若讀取時偵測到存檔槽的位元組本身已損毀(非版本不相容,而是資料本身無法解析)**:視同該存檔槽讀取失敗,回傳結構化錯誤(區分「版本不相容」與「資料損毀」兩種錯誤原因,見 Core Rules #6),不嘗試部分解析或以殘存的可讀片段拼湊還原——呼應 Player Fantasy「寧可拒絕載入也不可靜默降級」。
- **若遷移函數鏈執行到一半時遊戲異常終止(當機、強制關閉)**:由於遷移是在讀取時於記憶體中進行、原始存檔槽在遷移完成並確認成功前不會被覆寫(見 Core Rules #13「遷移成功後立即回寫」——回寫本身套用上方「寫入過程中途失敗」的原子寫入原則,只有在遷移鏈**完整成功**後才會觸發),原始存檔槽的資料維持遷移前的舊版本狀態不受影響。玩家下次讀取時,該槽會重新從舊版本開始執行整條遷移函數鏈——此重跑結果與原本被中斷那次的執行結果保證一致,依賴的是 Core Rules #11 的遷移函數確定性要求。不存在「卡在遷移中一半」的中間狀態需要特殊處理。
- **若手動存檔請求與自動存檔觸發在極短時間內先後發生**:由於採同步阻塞式寫入(見 Core Rules #4),兩次寫入不可能真正並發——後發生的請求會在前一次寫入完成後才開始執行,依請求發生的先後順序依序完成,不需要額外的鎖定或佇列機制。
- **若存檔槽的 manifest 列出一個目前遊戲版本已不存在的資料區塊來源(例如某系統被移除或重新命名)**:視為該區塊資料在遷移函數鏈中應被對應版本的遷移函數明確處理(丟棄、合併、或轉換到新系統),不得被本系統的通用讀取邏輯靜默忽略——若沒有任何遷移函數宣告如何處理該區塊,依 Core Rules #6 視為遷移失敗,拒絕讀取。
- **若存檔槽的版本號高於目前遊戲版本(玩家用較舊的遊戲版本讀取較新版本存的檔)**:視為不可遷移(遷移函數鏈只定義「升版」方向,不定義「降版」),依 Core Rules #6 拒絕讀取並回傳明確錯誤原因(區分於「版本過舊需遷移」的錯誤訊息,讓玩家理解是版本方向相反,而非存檔損毀)。
- **若多個存檔槽處於不同的規則集版本(例如槽 A 是舊版本尚未讀取過、槽 B 已升級到最新版本)**:合法且預期的正常狀態——存檔槽彼此完全獨立(見 Core Rules #2),讀取槽 A 時才會觸發槽 A 自己的遷移,不影響槽 B。
- **若遷移函數鏈完整執行成功、系統正在依 Core Rules #13 觸發回寫時遊戲異常終止(當機、強制關閉)**(2026-08-05 第二輪新增,回應 qa-lead 審查發現的缺口——此情境是 Core Rules #12 遷移純函數確定性、Core Rules #13 回寫時機、Core Rules #14 原子置換三項保證的複合情境,不能只從個別保證推論安全):此次回寫本身套用 Core Rules #14 的原子寫入序列(先寫暫存檔案),故中斷結果為兩種之一且絕不出現第三種中間狀態:(a)回寫尚未進行到步驟 3(將暫存檔案 rename 為目標檔案)之前中斷——槽維持遷移前的原始狀態(舊版本),下次讀取重新從頭執行整條遷移鏈,行為與「遷移執行中當機」等價;(b)回寫已完成步驟 3 但備份檔(`.bak`)尚未於步驟 4 清除——槽已是目前版本的正確內容,只是多了一份無害的備份檔殘留,下次讀取正常還原,備份檔可在下次寫入時被清除。不存在「目前版本檔案格式錯誤或內容損毀」的中間狀態,因為 Core Rules #14 的原子置換保證涵蓋這次回寫本身。
- **若某個遷移函數本身有 bug,輸出結構上滿足 Core Rules #12 後置條件、但語意錯誤**(2026-08-05 第二輪新增,回應 systems-designer/security-engineer/game-designer 收斂發現):依 Core Rules #7 第二輪擴大範圍的規則,此情況若語意驗證能偵測到值域/型別/列舉範圍等違規,會在回寫前被攔截、依 `MIGRATION_FAILED` 拒絕。若語意驗證的涵蓋範圍本身有缺口而未能偵測到(例如驗證規則寫得不夠嚴謹),遷移仍會被誤判成功並觸發 Core Rules #13 的回寫——但依該條第二輪新增的「原始位元組保留」規則,遷移前的原始資料不會被銷毀,日後修正驗證規則或遷移函數邏輯後,可透過 Core Rules #13 自動痊癒保證(二)的維運層級補救流程,以存底位元組重新執行修正後的遷移鏈,不需要玩家介入,也不會有資料永久遺失的風險。

## Tuning Knobs

- **`max_save_slots`(存檔槽數量上限)**:目前無強制上限的設計必要性(見 Detailed Rules Core Rules #2,存檔槽之間完全獨立)。**起始建議值:待 UI 系統設計時依畫面配置與玩家心智負擔決定**——本系統本身不因槽數增加而有效能或複雜度風險(見下方存檔大小規模註記),上限純粹是 UI/UX 考量,不是本系統的技術限制。
- **`max_supported_migration_depth`(遷移函數鏈深度上限,選用)**:Core Rules #5 目前設計為開放式遷移鏈(無版本數上限,每次新增規則集版本只需新增一個遷移函數)。**目前建議不設上限**——理由:上限本身是「工程維護負擔」與「絕不強迫玩家開新遊戲」(Player Fantasy 核心承諾)之間的政策取捨,在尚未實際累積多個規則集版本、不知道遷移函數維護成本之前,提前設限沒有實證基礎。若未來遷移函数鏈變得難以維護(例如某個早期版本的遷移函數需要理解已被完全重構的舊系統),可回頭評估是否引入此旋鈕,屆時須明確定義「超過上限的存檔」的行為(是否仍拒絕讀取但給出不同錯誤訊息、或提供陽春的資料匯出供玩家手動保存)。
- **存檔大小規模(非問題,一句話註記)**:多存檔槽 + 全量 manifest 持久化在目前遊戲規模下是簡單線性關係(`total_size ≈ slots × per_slot_size`),`per_slot_size` 依 `affinity-data-pool.md` Open Question 9 的估算落在數十 KB 等級(5 名固定角色、10 對配對、單一戰役全程)——不構成需要校準的旋鈕,若未來內容量大幅膨脹(例如角色規模政策改變)才需要重新評估。**此估算只回答存檔大小,不回答序列化耗時**(見下方 `save_write_max_duration_ms`)。
- **`save_write_max_duration_ms`(存檔寫入卡頓上限,待實測校準)**:存檔寫入為同步阻塞(Core Rules #4,provisional),此門檻是「可接受的卡頓時長」上限參考,**範圍限定於一般自動/手動存檔的單次寫入**(不含遷移觸發的複合回寫,見下方 `migration_chain_load_time_budget_ms` 的範圍聲明)。依專案 60fps/16.6ms 影格預算(`.claude/docs/technical-preferences.md`),單次寫入造成的卡頓不應讓玩家感知為明顯凍結;起始建議值待第一次實測(見 Acceptance Criteria 新增 H 節 AC-36)取得真實數字後校準,目前無法憑空指定。**若同步寫入實測結果持續超過此門檻且無法透過序列化優化解決,是 Core Rules #4「同步阻塞」決定需要被重新開啟評估的具體觸發條件之一。**

  **寬限上限(2026-08-05 第二輪新增,回應 game-designer 審查發現)**:AC-36 標記超標為「待校準追蹤項」而非功能性失敗,但追蹤不得無限期持續——若連續兩次正式建置量測(或垂直切片驗收里程碑,以先到者為準)仍超過此門檻,Core Rules #4 的重新評估**由建議升級為必須執行**,不得繼續以「持續追蹤」名義擱置。

- **`migration_chain_load_time_budget_ms`(遷移鏈讀取耗時上限,選用,待實測校準)**:目前遷移鏈長度政策上無上限(見 `max_supported_migration_depth`),但玩家實際等待時間有感知上限。建議與 `save_write_max_duration_ms` 一併於實測階段校準;若遷移鏈變長導致讀取耗時超過此門檻,是重新評估 `max_supported_migration_depth` 政策的觸發條件之一。

  **範圍聲明(2026-08-05 第二輪新增,回應 performance-analyst/systems-designer 收斂發現)**:此門檻涵蓋「遷移鏈執行 + Core Rules #13 觸發的立即回寫」的**複合耗時**,而非只涵蓋遷移函數本身的計算時間——玩家實際等待的是這整段複合阻塞時間,不是其中一部分。此複合路徑發生在讀檔/載入畫面情境,不受 60fps 影格預算(`save_write_max_duration_ms` 的適用範圍)約束,但仍須被量測與追蹤,對應新增的 AC-46(見 Acceptance Criteria 新增 H 節)。

- **遷移函數複雜度上限(2026-08-05 第二輪新增,回應 performance-analyst 審查發現,對齊 `affinity-data-pool.md` Core Rules #1 的等價查詢複雜度約束)**:單一遷移函數對其負責轉換的資料區塊,時間複雜度須為 `O(該區塊自身筆數)`,不得因為 schema 變更而需要對區塊做超線性(例如巢狀掃描)的遍歷,除非該版本躍遷語意上確實需要(此例外須在對應遷移函數的文件註解中明確說明理由)。這條約束不是旋鈕(沒有可調數值),而是介面契約,列於本章節是為了與 `migration_chain_load_time_budget_ms` 並列参照——遷移鏈總耗時 = Σ(各步驟耗時),若任何一步驟違反此複雜度約束,會讓遷移鏈耗時隨存檔資料量而非僅隨鏈深度成長,使 `migration_chain_load_time_budget_ms` 的校準基礎失真。

## Acceptance Criteria

*(2026-08-03,qa-lead 諮詢草擬,依 Detailed Rules/Edge Cases 逐條覆蓋。誤差容許:浮點欄位位元完全相同或誤差 <1e-12。2026-08-05 第二輪修訂:新增 AC-24b、AC-37~46,section F2/G2/H;AC-8/14/28/31 內容重寫,AC-30 錯誤代碼措辭更新。)*

### A. Manifest & Multi-Slot Isolation

- **AC-1**: **GIVEN** 一次對存檔槽 A 的寫入,內含來自 N 個不同來源系統的資料區塊,**WHEN** 檢視產生的存檔檔案,**THEN** 其 manifest 列出全部 N 個資料區塊,各自標註獨立的來源系統識別碼與獨立的資料格式版本號(不是全部區塊共用單一格式版本)。
- **AC-2**: **GIVEN** 同一存檔中兩個資料區塊(例如好感度區塊為格式版本 2、章節進度區塊為格式版本 1),**WHEN** 後續遊戲版本只提升好感度區塊的格式版本,**THEN** 讀取舊存檔時只會對好感度區塊觸發遷移函數鏈,章節進度區塊的遷移鏈不會被呼叫(其版本未變)。
- **AC-3**: **GIVEN** 存檔槽 A、B 皆已持有有效存檔,**WHEN** 對槽 A 發出新的寫入(自動或手動存檔),**THEN** 槽 B 在磁碟上的檔案在寫入前後逐位元組完全相同。
- **AC-4**: **GIVEN** 一個從未寫入過的存檔槽,**WHEN** 對該槽發出讀取請求,**THEN** 系統回傳一個獨立的「無資料」結果(非錯誤),且此結果須能與 D 節所有拒絕結果(損毀、遷移失敗、未來版本)在程式上明確區分。
- **AC-5**: **GIVEN** 槽 A 為目前 schema 版本 N(有效)、槽 B 為較舊版本 N-2(自版本升級後從未被讀取),**WHEN** 讀取槽 A,**THEN** 槽 B 的磁碟資料與版本標記逐位元組不變——讀取一個槽絕不會觸發另一個槽的遷移或任何狀態變化。

### B. Write Path & Atomicity

- **AC-6**: **GIVEN** 章節/戰役結構系統於進度邊界點觸發自動存檔,**WHEN** 寫入呼叫將控制權交還呼叫方,**THEN** 存檔資料已完整持久化至磁碟——不存在延遲/背景完成的通知機制,呼叫返回即代表序列化已完成。
- **AC-7**: **GIVEN** 手動存檔請求與自動存檔請求透過同一寫入介面、以相同世界狀態分別觸發,**WHEN** 任一者成功完成,**THEN** 產生的 manifest 內容(資料區塊集合、各區塊版本、完整性)兩者相同——兩份檔案至多在觸發來源的中繼資料欄位(若存在)上有差異,絕不影響所含系統資料的範圍。
- **AC-8**(2026-08-05 第二輪重新指派用途,回應 systems-designer/qa-lead 審查發現——原版本斷言的是任何阻塞式函式呼叫的宿主語言免費保證〔呼叫 A 返回後才呼叫 B,B 必晚於 A 完成〕,無法區分正確與錯誤實作,已重寫): **GIVEN** debug 建置且啟用 Core Rules #15 的主執行緒斷言,**WHEN** 存檔寫入介面被一個非主執行緒呼叫(例如手動建立的 `Thread`,或未使用 `call_deferred()` 轉回主執行緒的 `WorkerThreadPool` 回呼),**THEN** 系統立即觸發斷言失敗,而非靜默完成寫入——此 AC 驗證 Core Rules #4 的單執行緒假設是可被自動偵測違反的不變量,而非僅仰賴人工遵守的文件敘述。
- **AC-9**: **GIVEN** 手動存檔請求與自動存檔觸發在極短時間內針對同一存檔槽先後發生(同一執行緒,先後而非並發),**WHEN** 兩者皆被觸發,**THEN** 兩者嚴格依呼叫順序執行,該槽最終狀態為後發生請求所寫入的內容——兩次寫入的欄位不會交錯或合併。
- **AC-10**: **GIVEN** 槽 A 持有一份有效的既有存檔,**WHEN** 對槽 A 的新寫入在完成前被中斷(進程被終止/注入寫入失敗),**THEN** 槽 A 事後的磁碟檔案與中斷寫入發生前逐位元組完全相同,且能成功讀取。
- **AC-11**: **GIVEN** 對一個空(從未寫入過)存檔槽 A 的寫入在完成前被中斷,**WHEN** 中斷發生,**THEN** 槽 A 之後回報為「空」(依 AC-4 的「無資料」),而非損毀或部分存檔狀態。
- **AC-12**: **GIVEN** 寫入正在進行、且目標槽已存在一份有效檔案,**WHEN** 在寫入呼叫返回前檢視檔案系統,**THEN** 既有的槽檔案未被觸碰,且存在一個獨立的暫存檔案——確認實作為「暫存檔案後置換」模式,而非直接原地修改目標檔案。

### C. Migration Chain

- **AC-13**: **GIVEN** 一份 schema 版本 3 的存檔、目前遊戲版本為 6,已註冊 3→4、4→5、5→6 三個遷移函數,**WHEN** 讀取該存檔,**THEN** 三個函數嚴格依序執行(3→4 完全結束才開始 4→5,4→5 完全結束才開始 5→6)——可透過為每個函數加上呼叫順序偵測工具驗證。
- **AC-14**(2026-08-05 第二輪重寫,移除並發語意——回應 systems-designer/qa-lead 獨立收斂發現:原版本的 WHEN 子句要求「同一執行緒在第一次呼叫返回前發出第二次呼叫」,這在 Core Rules #4 的單執行緒阻塞模型下無法被實際建構,原描述本身自相矛盾): **GIVEN** 一份 schema 版本 3 的存檔於目前遊戲版本 6 下讀取,**WHEN** 讀取請求開始、遷移函數尚未執行完成,**THEN** 該槽對外可查詢的狀態(透過獨立的、不觸發完整讀取的狀態查詢介面,見 Core Rules #15)回傳「待遷移」,不回傳任何部分或中間資料——此 AC 驗證的是狀態可觀測性本身,不涉及任何並發或跨執行緒情境。
- **AC-15**: **GIVEN** 一份已處於目前 schema 版本的存檔檔案,**WHEN** 讀取它,**THEN** 零個遷移函數被呼叫(例如 QA 可觀測的遷移呼叫計數器維持為 0)——與需要遷移的讀取路徑可觀測地不同。
- **AC-16**: **GIVEN** 新增 schema 版本 N+1,只新增一個 N→N+1 遷移函數,**WHEN** 讀取一份版本 N-2 的存檔於遊戲版本 N+1 下,**THEN** 既有的遷移鏈(N-2→N-1→N)不經修改直接執行,接著執行新增的 N→N+1 步驟——確認新增一個版本步驟不需要修改先前任何步驟。

### D. Migration Failure Handling

- **AC-17**: **GIVEN** 遷移步驟 k(例如 4→5)偵測到無法安全對應到目標 schema 的資料,**WHEN** 處理該次讀取,**THEN** 讀取被拒絕、該槽進入「遷移失敗」狀態,不回傳任何資料(部分或完整)給呼叫方,也不對無法對應的資料代入任何預設值/佔位值。
- **AC-18**: **GIVEN** AC-17 描述的遷移拒絕,**WHEN** 呼叫方檢視回傳的錯誤,**THEN** 它是一個結構化物件,至少包含:失敗發生的 schema 版本、失敗的具體資料區塊識別碼、機器可讀的原因代碼——不需解析自由格式文字即可程式化取得。
- **AC-19**: **GIVEN** 一份存檔的原始位元組本身無法解析(資料損毀,非版本不相容),**WHEN** 嘗試讀取,**THEN** 回傳的結構化錯誤原因代碼與遷移失敗(AC-18)使用的代碼不同——QA 測試者僅憑錯誤物件即可分辨「資料損毀」與「遷移失敗」。
- **AC-20**: **GIVEN** 存檔的 schema 版本高於目前遊戲支援的版本(例如存檔為 v8、遊戲僅支援到 v6),**WHEN** 嘗試讀取,**THEN** 拒絕讀取,且原因代碼與 AC-18(遷移失敗)、AC-19(資料損毀)皆不同——確認「版本過新、無法降版」是與「版本過舊、遷移失敗」各自獨立可辨識的拒絕原因。
- **AC-21**: **GIVEN** 某存檔槽的 manifest 列出一個目前遊戲版本已不存在的來源系統識別碼,且遷移函數鏈中沒有任何函數宣告如何處理該區塊,**WHEN** 嘗試讀取,**THEN** 依 AC-17/AC-18 視為遷移失敗拒絕——該未知區塊絕不會被通用讀取邏輯靜默捨棄。
- **AC-22**: **GIVEN** 某存檔槽已進入「遷移失敗」狀態(AC-17),**WHEN** 在沒有中間寫入的情況下再次讀取同一個槽,**THEN** 再次以相同的結構化錯誤失敗,且該槽兩次嘗試之間的磁碟檔案逐位元組不變——系統絕不會自動修改或「修復」一個失敗的槽。
- **AC-23**: **GIVEN** 槽 A 的遷移鏈開始執行(狀態=待遷移),進程在完成前被終止(當機/強制關閉),**WHEN** 遊戲重啟後再次讀取槽 A,**THEN** 槽 A 的磁碟檔案與中斷嘗試發生前相同(仍是原始的遷移前版本),完整遷移鏈會從頭重新執行——不存在任何被持久化或可恢復的部分遷移狀態。

### E. Cross-System Persistence Contract

- **AC-24**: **GIVEN** 一份好感度數值池 Delta Log,含 N≥1 筆記錄(全部五個欄位:`pair`、`m_i`、`t_i`、`c_i`、`source_i`)與非空的戰役刻度標記列表,**WHEN** 存檔後重新讀取,**THEN** 每筆記錄的五個欄位與存檔前逐一比對完全相同(浮點欄位位元完全相同或誤差 <1e-12),標記列表的筆數與數值順序完全相同——未發生任何壓縮、去重或摘要。
- **AC-24b**(2026-08-05 第二輪新增,回應 systems-designer 審查發現——N=0 是新戰役第一次自動存檔的真實常見狀態,先前完全沒有 AC 覆蓋,也是 null-vs-empty 序列化 bug 的經典來源): **GIVEN** 一份好感度數值池 Delta Log 為空(N=0,尚未發生任何好感度寫入)且戰役刻度標記列表也為空,**WHEN** 存檔後重新讀取,**THEN** 讀取結果正確回報為「空」而非錯誤或損毀,且後續若對該配對發出寫入,系統行為與從未存檔過的全新狀態一致——不因為「曾經存過一次空 Delta Log」而產生任何殘留副作用。
- **AC-25**(2026-08-05 修訂,配合 Core Rules #10 索引鍵改為字串名稱持久化): **GIVEN** 一份存檔中的好感度記錄以字串名稱持久化 `Pair` 欄位,**WHEN** 在 `Pair` enum 定義順序**未變動**的組建下重新讀取,**THEN** 每筆記錄都還原到寫入當下的邏輯配對——以一份涵蓋全部 10 對合法配對、每對至少一筆記錄的存檔驗證此點。(定義順序**已變動**的等效情境見新增的 AC-29,兩者共同覆蓋字串名稱持久化機制的正反面。)
- **AC-26**: **GIVEN** 同步阻塞式寫入模型(Core Rules #4),**WHEN** 對含有好感度資料的存檔槽執行寫入,**THEN** 整個寫入路徑中不會對好感度數值池發出任何序列化生命週期「begin/end」通知呼叫——確認本系統未實作 `affinity-data-pool.md` AC-47 原本要求的非同步生命週期介面。
- **AC-27**: **GIVEN** 兩個存檔槽在好感度數值池的持久化格式上處於不同 schema 版本(一個為目前版本、一個為舊版本),**WHEN** 分別獨立讀取兩槽,**THEN** 各槽的 Delta Log 嚴格依自己槽的版本遷移——已是目前版本的槽絕不會被重新遷移,舊版本的槽恰好被遷移一次,不受另一槽狀態影響。

### F. 完整性與防禦性驗證(2026-08-05 第一輪修訂新增,對應 Theme A)

- **AC-28**(2026-08-05 第二輪修訂,明確指定等長竄改情境,回應 security-engineer 審查發現——原版本的竄改情境未指定是否維持原長度,容許僅實作位元組筆數的實作在多數常見竄改下仍能通過,給出假信心): **GIVEN** 一份合法存檔,**WHEN** 在磁碟上人為竄改其中一個資料區塊的位元組內容但**維持該區塊原本的位元組長度不變**(例如翻轉單一位元、或交換兩個同寬度欄位的內容)、且不更新對應的完整性標記,**THEN** 讀取時偵測到完整性標記不符(見 Core Rules #8,本輪修訂後須為雜湊而非位元組筆數),回傳 `DATA_CORRUPTED` 錯誤(與 AC-19 共用錯誤路徑),不嘗試以竄改後的資料還原或進入遷移路徑——此 AC 特別驗證等長竄改也能被偵測到,而非只驗證會改變長度的竄改。
- **AC-29**: **GIVEN** 一份已寫入的存檔,其 `Pair` 索引鍵以字串名稱持久化(見 Core Rules #10),**WHEN** 之後改變 `Pair` enum 的定義順序(但不改變字串名稱本身)再重新讀取該存檔,**THEN** 每筆記錄仍正確還原到寫入當下的邏輯配對——確認 enum 定義順序變動不影響已存檔資料的正確性,即使序數本身已經不同。(與 AC-25 互為正反面測試。)
- **AC-30**: **GIVEN** 存檔檔案宣告了一個不在系統已知型別白名單中的型別(見 Core Rules #9),**WHEN** 嘗試反序列化,**THEN** 拒絕讀取並回傳 `DATA_CORRUPTED` 錯誤,不嘗試實例化該未知型別。
- **AC-31**(2026-08-05 第二輪修訂,明確限定為現版本情境,回應 game-designer 審查發現——遷移輸出的對應情境已獨立為新增 AC-45,兩者使用不同原因代碼): **GIVEN** 一個已是目前版本的資料區塊(未觸發遷移鏈)通過格式層級反序列化,但其中某欄位數值超出該欄位宣告的合法值域(例如非法的 `source` 標記、NaN 數值),**WHEN** 讀取該區塊,**THEN** 依 Core Rules #7 回傳 `SEMANTIC_VALIDATION_FAILED` 結構化錯誤,不代入預設值靜默通過。

### F2. 完整性與防禦性驗證(2026-08-05 第二輪新增)

- **AC-41**(回應 systems-designer/qa-lead 獨立收斂發現,補上 AC-25/AC-29 未覆蓋的「名稱重用碰撞」情境): **GIVEN** 一份存檔寫入當下,字串名稱 `"AC"` 指稱配對(Alice, Carol);**WHEN** 之後的版本躍遷除役了 `"AC"` 這個名稱(該配對被重新命名為其他字串),且對應的遷移函數依 Core Rules #10 的退役名稱治理規則明確登記了「`"AC"` → (Alice, Carol) 的新名稱」映射,**THEN** 存檔中以 `"AC"` 持久化的記錄,透過該遷移函數的明確映射正確路由到 (Alice, Carol) 的新索引鍵——不依賴「名稱是否在目前 enum 中找得到」做直接查表判斷。
- **AC-42**(負面情境,與 AC-41 互為正反面測試): **GIVEN** 與 AC-41 相同的名稱除役情境,但**沒有**任何遷移函數登記 `"AC"` 的映射(治理規則被違反,`"AC"` 這個退役名稱後續被錯誤地重新指派給另一個配對),**WHEN** 讀取該存檔,**THEN** 系統依 Core Rules #6 回傳 `MIGRATION_FAILED` 拒絕載入——即使 `"AC"` 這個字串在目前 enum 定義中「找得到」(指向錯誤的新配對),系統不得將「名稱存在」直接等同於「語意延續」,必須依賴遷移函數的明確聲明才能建立跨版本的身分對應。
- **AC-43**(回應 security-engineer 審查發現): **GIVEN** 一份合法存檔,**WHEN** 在磁碟上人為竄改某資料區塊於 manifest 中宣告的來源系統識別碼或格式版本號(而非該區塊的 payload 內容本身),且不更新對應的完整性標記,**THEN** 讀取時偵測到完整性標記不符(見 Core Rules #8——雜湊輸入須涵蓋身分與版本中繼資料,不只 payload),回傳 `DATA_CORRUPTED` 錯誤,不得將竄改後的區塊路由進錯誤的遷移函數鏈。
- **AC-44**(回應 security-engineer 審查發現,驗證 Core Rules #7 的 fail-closed 修正): **GIVEN** 一份存檔的 manifest 列出一個資料區塊,但該區塊的來源系統未依 Core Rules #7 宣告任何欄位的語意合法性驗證規則,**WHEN** 嘗試讀取,**THEN** 系統將此視為 manifest 本身錯誤,回傳 `DATA_CORRUPTED` 錯誤,不得因為「沒有驗證規則可執行」而略過驗證、直接視為通過。
- **AC-45**(回應 game-designer/systems-designer/security-engineer 收斂發現,驗證新增的第四類拒絕原因、其專屬自動痊癒路徑,以及語意驗證套用於遷移輸出的規則): **GIVEN(a)** 某資料區塊已是目前 schema 版本(未觸發遷移鏈),但其中某欄位數值違反目前版本的語意驗證規則,**WHEN** 讀取該存檔,**THEN** 回傳的原因代碼為 `SEMANTIC_VALIDATION_FAILED`,與 `MIGRATION_FAILED`(AC-17/18)使用不同代碼;**GIVEN(b)** 遊戲後續更新修正了該語意驗證規則本身(而非新增任何遷移函數),**WHEN** 再次讀取同一個槽,**THEN** 語意驗證以修正後的規則重新執行,若這次通過,槽狀態自動轉為「有效」並依 Core Rules #13 立即回寫;**GIVEN(c)** 一個遷移函數的輸出違反目標版本的語意驗證規則(即使結構性後置條件檢查通過),**WHEN** 遷移鏈執行到該步驟,**THEN** 回傳的原因代碼為 `MIGRATION_FAILED`(不是 `SEMANTIC_VALIDATION_FAILED`,因為此情境確實觸發了遷移鏈)——三個情境共同驗證 Core Rules #7 第二輪擴大範圍後,語意驗證同時涵蓋「現版本區塊」與「遷移輸出」兩條路徑,且使用彼此一致、可區分的原因代碼。

### G. 遷移健全性與效能(2026-08-05 第一輪修訂新增,對應 Theme C/D)

- **AC-32**: **GIVEN** 一個刻意寫錯的遷移函數(執行不拋出例外,但輸出資料不滿足目標版本 schema 的後置條件),**WHEN** 該遷移函數執行完成,**THEN** 系統偵測到後置條件檢查失敗(見 Core Rules #12),視為 Core Rules #6 的遷移失敗,不將此執行結果視為成功。
- **AC-33**: **GIVEN** 同一份存檔與同一個遷移函數鏈,**WHEN** 分別執行兩次獨立的讀取(在完全相同的目前遊戲版本與遷移函數集合下),**THEN** 兩次遷移結果逐位元組相同——驗證遷移函數鏈的確定性(見 Core Rules #11)。
- **AC-34**: **GIVEN** 一份 schema 版本 2 的存檔於目前版本 5 下讀取並成功完成遷移鏈(2→3→4→5),**WHEN** 讀取成功後立即對該槽追加一筆新記錄並再次寫入,再次讀取,**THEN** 兩次讀取皆回傳目前版本的正確還原資料,追加的新記錄存在且正確,且第二次讀取不再觸發任何遷移函數(依 Core Rules #13,回寫後版本已是目前版本)——驗證「讀取觸發遷移→新資料寫入→再讀」的複合鏈不產生資料遺失或重複遷移。
- **AC-35**: **GIVEN** 某存檔槽因缺少某個遷移步驟的處理邏輯而處於「遷移失敗」狀態,**WHEN** 遊戲更新後為該步驟補上正確的遷移函數,並再次讀取同一個槽(未經任何手動修改存檔或槽狀態),**THEN** 遷移鏈重新執行並這次成功,槽狀態轉為「有效」,且依 Core Rules #13 立即回寫——驗證自動痊癒保證確實生效,不需要玩家採取任何動作。

### G2. 遷移健全性(2026-08-05 第二輪新增,原始位元組保留機制的驗證)

- **AC-37**(回應 systems-designer/security-engineer/game-designer 收斂發現,驗證 Core Rules #13 的原始位元組保留機制): **GIVEN** 槽 A 的遷移函數鏈完整執行成功並觸發回寫,**WHEN** 檢視回寫後的存檔槽目錄,**THEN** 除了目前版本的存檔檔案外,存在一份獨立的遷移前原始位元組存底,且該存底的內容與遷移發生前槽 A 的磁碟內容逐位元組相同——驗證回寫不會銷毀原始資料。
- **AC-38**(回應 qa-lead 審查發現的缺口,驗證 Core Rules #13 回寫本身的中斷安全性,是 AC-10/AC-23/AC-35 個別保證之外的獨立複合情境): **GIVEN** 槽 A 的遷移函數鏈完整執行成功,系統開始依 Core Rules #13 觸發回寫,**WHEN** 進程在回寫的原子置換序列(見 Core Rules #14)完成前被終止,**THEN** 遊戲重啟後讀取槽 A,其結果為以下兩者之一且絕不出現第三種中間狀態:(a) 槽 A 維持遷移前的原始版本狀態,下次讀取重新執行完整遷移鏈;(b) 槽 A 已是目前版本的正確內容(回寫的原子置換序列已完成到 rename 步驟,只是備份檔清除〔步驟四〕未執行,不影響正確性)——不存在「目前版本檔案格式錯誤或內容損毀」的情況。
